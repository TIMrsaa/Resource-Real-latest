# 학습 가이드 — 앱은 멀쩡한데 유저는 5xx를 봅니다

## 13과의 관계: 측정 경로가 하나 늘었습니다

13의 무릎은 "클러스터 안 → Service 직행"의 숫자였습니다. 실제 유저 경로는 `클라이언트 → ALB → (target-type ip라면) Pod 직행`이고, 이 중간 계층엔 자기만의 규칙이 있습니다 — 60초 idle timeout, 300초 deregistration, 라운드로빈 배분. **앱이 완벽해도 이 규칙과 어긋나면 유저는 5xx를 봅니다.** 그 어긋남의 대표가 배포 순간입니다: Pod는 정상적으로 교체됐는데 ALB가 죽은 타깃에 잠깐 보낸 그 몇 초.

## 이 모듈의 증명 방식

13에서 만든 도구를 그대로 무기로 씁니다 — **open 모델(vegeta)을 흘려보내며 배포**하고, 오류 수를 셉니다:

```
[통제 전] 롤링 업데이트 중 오류 N건  →  손잡이 4개 조정  →  [통제 후] 오류 0건
```

"무중단 배포"를 느낌이 아니라 카운트로 증명하는 것 — 이 팀 문화가 이 파트의 목표입니다.

## 미리 보는 손잡이 지도

| 손잡이 | 자리 | 기본값의 함정 |
|--------|------|--------------|
| idle_timeout | ALB 전체 | 60s — 긴 요청/롱폴링이 504로 잘림 |
| 알고리즘 | Target Group | round_robin — 느린 타깃에도 같은 몫 |
| slow_start | Target Group | 0(off) — 새 Pod에 즉시 풀 트래픽 |
| deregistration_delay | Target Group | 300s — 배포가 느려지는 이유 |
| readiness gate | Pod (컨트롤러 주입) | 미설정 — "ALB 등록 전인데 Ready" |
| preStop sleep | Pod | 미설정 — "빠지기 전에 죽음" |

## 스코프

ALB 중심으로 실험합니다(HTTP 계층 = 손잡이가 많습니다). NLB(L4)는 cross-zone·client IP 보존을 theory에서 비교하고, 존 인지 라우팅(Topology Aware)은 비용 관점과 함께 다룹니다. 서비스 메시의 L7 제어(재시도/서킷브레이커)는 20에서.
