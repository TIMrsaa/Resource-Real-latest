# 흔한 함정 5선

## 1. 노드 먼저, 이미지 나중

"Graviton 싸다더라"로 arm 노드그룹부터 만들면 — multi-arch가 아닌 이미지들이 복불복으로 arm에 배치되며 exec format error CrashLoop이 산발합니다. 순서는 반대입니다: **이미지 전수조사 → CI multi-arch 전환 → 그 다음 노드**. 과도기엔 단일 arch 워크로드에 arch nodeSelector를 강제하고, 가능하면 admission(k8s 23)으로 "arm 판본 없는 이미지의 arm 배치"를 막아라.

## 2. 앱만 번역하고 사이드카를 잊음

앱 이미지는 multi-arch로 만들었는데 로그 에이전트·메시 프록시·init 컨테이너가 amd64 전용 — Pod 전체가 CrashLoop인데 "우리 앱은 arm 지원하는데요?"로 조사가 산으로 갑니다. Pod 안의 **모든 컨테이너**가 같은 노드(같은 arch)에서 돕니다 — 전수조사 목록에 사이드카·에이전트·Job 이미지까지.

## 3. GPU 노드에 taint를 잊음

taint 없는 GPU 노드는 스케줄러에게 "그냥 큰 노드"다 — 일반 웹 Pod들이 시간당 $1짜리 노드를 CPU 몇 % 쓰며 점거하고, 정작 GPU Job은 Pending. GPU 노드그룹 생성과 taint는 한 몸(생성 직후가 아니라 노드그룹 설정/Karpenter NodePool의 taints로 — 노드가 뜨는 순간부터). 반대쪽도 확인: device plugin DaemonSet은 그 taint를 tolerate해야 합니다.

## 4. time-slicing을 "작은 GPU 여러 개"로 오해

replicas: 4로 신고하면 스케줄러 장부만 4가 됩니다 — **메모리·연산 격리는 0**입니다. 한 Pod가 VRAM을 다 먹으면 이웃 셋이 CUDA OOM으로 죽고, 원인은 "남의 Pod"라 진단이 미궁에 빠집니다. 신뢰 경계를 넘는 공유(멀티테넌트)는 MIG(하드웨어 분할)로, time-slicing은 같은 팀의 가벼운 추론·개발용으로 — 34의 "커널 공유 = 격리 아님" 논리의 GPU 판입니다.

## 5. 검증 없는 전환 선언

"Graviton으로 바꾸고 20% 아꼈다"는 보고의 절반은 p99를 안 쟀습니다. 특정 네이티브 라이브러리의 arm 최적화 부재, JIT 워밍업 차이 등으로 **단가는 내렸는데 지연이 올라** 총 비용(replicas 증가)이 그대로인 경우가 실존합니다. 전환의 문장은 이래야 합니다: "동일 부하에서 p99 __ms(±__%), 단가 __% 절감, 순절감 __%" — 13의 보고서 양식 그대로.

## 실무 사고 사례

> ML 팀이 추론 서비스를 g5 노드로 옮기고 성능에 만족했습니다 — 청구서를 보기 전까지. GPU 노드 8대의 야간 사용률이 3%였던 것: 트래픽은 주간에 몰리는데 노드는 24시간 상주했고, taint는 있었지만 **줄이는 자동화가 없었습니다.** 더 아픈 발견: 그중 2대는 한 달 전 끝난 실험용 노드그룹의 잔재였습니다(cleanup 누락). 조치: ① 추론을 큐 기반으로 바꾸고 KEDA scale-to-zero(15) ② Karpenter GPU NodePool로 전환해 수요 기반 생성/회수(17) + 학습 Job엔 do-not-disrupt ③ "GPU 사용률 < 20% 지속" 알람(12)과 노드그룹 태그 기반 주기 스캔. 교훈: **GPU 비용 사고의 주범은 비싼 시간당 단가가 아니라 '아무도 안 쓰는 시간'입니다.**
