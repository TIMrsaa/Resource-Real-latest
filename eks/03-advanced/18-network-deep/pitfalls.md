# 흔한 함정 5선

## 1. Flow Logs의 ACCEPT를 "통신 성공"으로 읽기

Flow Logs는 ENI 관문의 기록이지 종단 성공의 기록이 아닙니다 — NetworkPolicy(eBPF)는 그 뒤에서 드롭하고, 앱이 RST를 던져도, 프로세스가 안 떠 있어도 CCTV엔 ACCEPT입니다. 규칙: **REJECT는 확정 증거(SG/NACL), ACCEPT는 무죄 증명이 아님** — ACCEPT+불통이면 진단 계단의 위층(NP/앱)으로 돌아가라.

## 2. NACL을 SG처럼(stateful로) 착각

NACL은 stateless — 요청을 열었어도 **응답이 나가는 규칙**(ephemeral port 1024-65535)을 따로 안 열면 반쪽 통신이 됩니다. 증상이 기묘합니다: SYN은 가는데 응답이 죽어 "간헐적 타임아웃"처럼 보입니다. 서브넷 간 통신 문제에서 NACL을 의심할 땐 항상 **왕복 두 방향 × 포트 범위**를 그려라. (기본 NACL은 all-allow라 만진 적 없다면 대개 무죄)

## 3. 노드 SG를 공유한다는 사실을 잊은 Pod 보안 설계

기본 모드에서 한 노드의 모든 Pod는 **그 노드 ENI의 SG를 공유**합니다 — "이 Pod만 DB에 접근 허용"을 SG로 하려면 그 노드의 모든 Pod에 열리는 셈. Pod 단위 통제는 ① NetworkPolicy(라벨 기반 — 기본 답) ② SG for Pods(branch ENI — AWS 리소스 접근을 SG로 통제해야 할 때)로. 계층의 관할을 섞으면 "느슨한 줄 모르는 허용"이 생깁니다.

## 4. SNAT 전제를 깨고 온프레미스 연결

VPN/DX 너머 방화벽 팀과 "노드 IP 대역만 허용"으로 합의해놓고, 이후 EXTERNALSNAT를 켜거나(Pod 실주소 노출) 100.64 이주(16)를 하면 — 발신 주소가 바뀌며 조용히 끊깁니다. 반대로 SNAT를 켜둔 채 "Pod별 접근 제어"를 온프레 방화벽에 기대하는 것도 불가능(전부 노드 IP로 보임). **발신 주소가 무엇으로 보이는가**는 네트워크 설계 문서의 한 줄로 박아두고, 바꿀 땐 변경 관리로.

## 5. Flow Logs 상시 ALL + 무기한 보존

VPC 전체 ALL 트래픽 상시 수집은 트래픽 큰 클러스터에서 수집비가 순식간에 쌓입니다(12의 그 함정이 네트워크 판으로). 현실적 규율: 평시엔 꺼두거나 REJECT-only/샘플링, 조사·감사 필요 시 기간 한정 ALL, 보존은 며칠, 장기 보관이 필요하면 CW Logs가 아니라 **S3(+Athena)** 로. "켜는 스크립트"와 "끄는 스크립트"를 세트로 관리하세요.

## 실무 사고 사례

> 결제 서비스가 외부 PG사 API에서 간헐 타임아웃 — 앱 팀은 PG사를, PG사는 앱을 의심하며 2주를 소모했습니다. 네트워크 팀이 진단 계단을 밟자 30분 만에 윤곽이 나왔습니다: DNS 정상(0층), NP 없음(1층), SG 아웃바운드 정상(2층)… 5층 Flow Logs에서 **NAT GW ENI의 포트 고갈 신호**가 잡혔습니다 — 노드 수백 대의 아웃바운드가 NAT GW 하나로 SNAT되며 동시 연결이 한계에 닿은 것(경로 ③의 병목). 같은 목적지·같은 시각대의 재전송 폭증이 그래프로 보였습니다. 조치: AZ별 NAT GW 분산 + 연결 재사용(keep-alive) 강화 + NAT 포트 사용률 알람. 교훈: **계층 지도가 없으면 "간헐 타임아웃"은 영원히 남 탓 게임입니다** — 계단을 밟으면 증거가 층을 지목합니다.
