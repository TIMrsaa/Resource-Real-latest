# 흔한 함정 5선

## 1. "노드를 늘리면 되겠지" — 고갈을 가속하는 응급처치

Pod가 Pending이라고 같은 서브넷에 노드를 더 붙이면 — 새 노드마다 warm pool이 **또 수십 IP를 선점**해 고갈이 오히려 앞당겨집니다. IP 고갈의 Pending은 용량 문제가 아니라 주소 문제입니다: 먼저 `describe-subnets`의 free를 보고(확진), 그 다음에 처방(warm 회수/prefix/이주)을 고릅니다. 진단 없는 증설은 기름 붓기.

## 2. warm을 0 근처로 조여놓고 이벤트 맞이

IP가 궁하다고 `WARM_IP_TARGET=1`로 바싹 조이면 — 평시엔 알뜰하지만, HPA가 한꺼번에 50 Pod를 띄우는 순간 **모든 할당이 EC2 API 실시간 호출**이 되어 기동 지연 + API 쓰로틀 연쇄가 옵니다. warm은 "선점 vs 민첩"의 다이얼이지 악당이 아닙니다 — 워크로드의 폭증 패턴을 알고 MINIMUM_IP_TARGET과 조합해 정하세요.

## 3. 파편화된 서브넷에 prefix delegation

몇 년 묵은 서브넷에 `ENABLE_PREFIX_DELEGATION=true` — /28 **연속 블록**이 없어 할당이 실패하고, "free IP는 수백 개인데 Pod가 안 뜨는" 신종 고갈이 됩니다. prefix는 새(깨끗한) 서브넷과 함께가 정석 — 그래서 secondary CIDR(새 대역)과 자연스러운 세트입니다. 켜기 전에 서브넷의 나이와 이력을 물어라.

## 4. 100.64를 붙이고 네트워크 팀에 말하지 않기

secondary CIDR 이주는 Pod의 발신 주소가 바뀌는 사건입니다 — 온프레미스 방화벽이 10.x만 허용하고 있었다면 VPN/DX 너머 통신이 조용히 끊깁니다. 게다가 100.64.0.0/10은 통신사 CG-NAT 대역이라 **일부 사내망·VPN 제품과 충돌** 사례가 있습니다. 이주 전 체크: 온프레 라우팅/방화벽, SG/NACL의 소스 대역 가정, 그리고 "Pod IP를 화이트리스트에 박아둔" 레거시들.

## 5. "나중에 IPv6로 바꾸면 되지"

안 바뀝니다 — IPv6는 **클러스터 생성 시에만** 선택 가능하고, 기존 클러스터의 전환 스위치는 없습니다. "나중에"의 실제 의미는 "새 클러스터를 짓고 전 워크로드를 이사"(35·36의 Blue/Green + Velero)입니다. 신규 클러스터를 설계하는 순간이 IPv6를 공짜로 얻을 유일한 기회 — 그때 IPv4를 관성으로 고르면 이 모듈 전체가 그 클러스터의 미래가 됩니다.

## 실무 사고 사례

> 연말 이벤트에서 HPA와 Karpenter가 설계대로 완벽히 일했습니다 — 그래서 장애가 났습니다. 스케일 아웃으로 노드 40대가 추가되며 각자 warm ENI를 선점, 3개 AZ 중 가장 작던 서브넷(/22)이 먼저 바닥났습니다. 그 AZ의 노드들에서 Pod가 ContainerCreating에 멈췄고, ALB는 healthy 타깃이 남은 두 AZ로 쏠리며 그쪽 무릎(13)까지 넘겼습니다. 전체 IP 합계는 여유가 있었기에 대시보드의 "남은 IP" 총합 그래프는 초록색이었습니다 — **min(AZ)을 보는 사람이 없었습니다.** 복구는 warm 회수 + 해당 AZ 서브넷 노드 비중 축소로, 근본 해결은 분기 뒤 100.64 이주(+prefix)로. 남긴 것: ① 알람을 합계가 아닌 **AZ별 최솟값**에 ② 서브넷 크기를 AZ 간 동일하게 ③ "자동 스케일의 상한은 서브넷"을 용량 계획 문서 첫 줄에.
