# 학습 가이드 — 메시는 답이 아니라 거래입니다

## App Mesh 사건에서 시작합시다

AWS App Mesh는 "AWS 네이티브 메시"였습니다 — 콘솔 통합, IAM 연동, 관리형 control plane. 그리고 2024년 신규 고객을 닫았고 2026년 9월 서비스가 끝납니다. 그 위에 프로덕션을 지은 팀들은 지금 이사 중입니다. 이 사건이 주는 교훈 두 가지:

1. **관리형의 양날**: 운영을 넘기는 대가는 로드맵도 넘기는 것 — 벤더의 전략이 바뀌면 내 아키텍처가 흔들립니다 (11의 관리형 애드온 논리와 대조: 애드온은 표준 오픈소스의 포장이라 탈출구가 있습니다)
2. **이식성의 가치**: Istio·Cilium 같은 CNCF 생태계는 특정 벤더의 사정으로 사라지지 않습니다 — cncf 파트에서 이 관점을 확장합니다

그래서 이 모듈은 Istio로 원리를 배웁니다 — 지금의 사실상 표준이자, 배운 개념(VirtualService, mTLS, sidecar)이 다른 메시에도 이식되는 공용어라서입니다.

## 메시가 "필요한" 신호 / "아닌" 신호

| 필요 신호 | 아닌 신호 |
|-----------|----------|
| 서비스 수십 개, 여러 팀이 서로 호출 | 서비스 3~5개, 한 팀 |
| mTLS가 규제/감사 요구 | "있으면 좋겠다" 수준 |
| 재시도/서킷을 언어별 라이브러리로 N번 구현 중 | 단일 언어, 공용 SDK 있음 |
| 카나리아를 동서 트래픽에도 | 배포는 ALB 앞단에서만 (14로 충분) |

오른쪽 열이라면 정직한 답은 "메시 없이": ALB(14) + NetworkPolicy(15) + 재시도 라이브러리. **메시는 Pod마다 프록시 하나(메모리·지연·운영 지식)를 사는 거래**입니다 — 지불할 문제가 없으면 사지 마세요.

## 이 모듈의 동선

lab-01이 보안 축(mTLS — "누가 누구와 말할 수 있나"), lab-02가 트래픽 축(카나리아·fault·서킷 — "어떻게 말하나")입니다. 둘 다 13의 측정 도구로 검증합니다 — 메시의 주장도 측정 앞에선 평등합니다.
