# 자가 점검 퀴즈

**Q1.** 남북/동서 트래픽의 구분과 각각의 담당 도구(14 vs 이 모듈)는?

**Q2.** App Mesh 종료가 주는 아키텍처 교훈을 11(관리형 애드온)의 논리와 대비해 설명하세요.

**Q3.** sidecar 주입의 메커니즘(k8s 23의 용어로)과, 시점 관련 함정 두 가지는?

**Q4.** mTLS의 신원이 IP가 아니라 SPIFFE ID(SA 기반)인 것의 실질적 이점은?

**Q5.** PERMISSIVE→STRICT 2단계 도입에서 STRICT 전에 반드시 해야 할 조사와 그 이유는?

**Q6.** NetworkPolicy와 mTLS의 분업을 "질문"의 형태로 구분하세요 — 왜 둘 다 필요한가?

**Q7.** 카나리아를 VirtualService weight로 하는 것이 replicas 비율/ALB 가중치와 다른 점은?

**Q8.** retry storm의 메커니즘과 3종 안전벨트는?

---

## 정답

**A1.** 남북 = 유저→클러스터 유입 — ALB의 손잡이들(idle timeout, 알고리즘, readiness gate — 14). 동서 = 서비스 간 상호 호출 — 메시의 관할(mTLS, 재시도/서킷, 카나리아, 골든 메트릭).

**A2.** App Mesh는 벤더 전용 관리형이라 벤더의 전략 변경(EOL)이 곧 내 아키텍처 이사 프로젝트가 됐습니다. 반면 11의 관리형 애드온은 **표준 오픈소스(CoreDNS 등)의 포장**이라 관리형을 떠나도 기술이 이식됩니다. 교훈: 관리형을 살 땐 "안의 것이 표준인가"를 보라 — 표준이면 운영만 위탁한 것, 전용이면 로드맵까지 위탁한 것.

**A3.** ns 라벨(istio-injection=enabled)을 조건으로 **mutating admission webhook**이 Pod 생성 요청에 Envoy 컨테이너를 삽입합니다. 함정: ① 생성 시점에만 작동 — 기존 Pod는 rollout restart 필요 ② Job/CronJob에 주입되면 sidecar가 안 죽어 Job이 완료되지 않음 — 주입 제외 annotation 필수.

**A4.** Pod IP는 재스케줄마다 바뀌지만 SA는 워크로드의 안정적 정체성입니다 — 정책("web은 db에 접근 가능")이 IP 목록 관리 없이 성립하고, 인증서 자동 회전과 결합해 "움직이는 인프라에서의 신원"이 유지됩니다. IP 기반 화이트리스트의 근본 한계를 벗어나는 지점.

**A5.** **메시 밖에서 평문으로 들어오는 정당한 호출자**(레거시 VM, cron, 외부 헬스체커, 미주입 ns) 색출 — STRICT는 그들을 TCP 리셋으로 끊어버리므로, 먼저 메시로 이주시키거나 portLevelMtls 예외를 설계해야 합니다. PERMISSIVE 기간의 mTLS 비율 메트릭이 이 조사의 도구입니다.

**A6.** NetworkPolicy: "이 **주소/라벨**이 이 포트에 접근해도 되는가"(L3/4, eBPF 집행). mTLS: "상대가 **누구인지 증명**했고 통신이 암호화되는가"(신원+기밀성, Envoy 집행). 주소 통제만으론 도청·사칭을 못 막고, 신원 통제만으론 대역 축소가 안 됩니다 — 겹층 방어.

**A7.** weight는 **라우팅 계층의 소유물**이라 Pod 수와 무관하게 1%→100%를 연속 조정할 수 있고(replicas 비율은 조정 단위가 거칠고 자원과 결합), ALB 가중치는 남북 진입점에서만 작동하는 반면 VirtualService는 **동서의 모든 호출 지점**에서 분할합니다.

**A8.** 하류가 과부하로 실패 → 상류들이 일제히 재시도 → 트래픽 배수 증가 → 하류 더 악화의 양성 피드백. 안전벨트: ① perTryTimeout(재시도 예산 상한) ② outlierDetection 서킷(아픈 인스턴스 격리로 실패 자체를 차단) ③ 재시도 대상 제한(멱등 요청만, 5xx 중 일부만).
