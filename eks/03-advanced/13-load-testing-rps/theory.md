# 이론 — RPS, 지연 분포, Little's Law, 그리고 두 가지 부하 모델

> **🌱 17세 눈높이 비유: 편의점 계산대**
> - **RPS** = 초당 들어오는 손님 수. **지연** = 한 손님이 줄 서서 계산 끝날 때까지의 시간
> - **Little's Law** = "줄에 서 있는 사람 수 = 오는 속도 × 머무는 시간" — 초당 2명씩 오고 평균 30초 머물면, 매장엔 늘 60명쯤 있습니다. 마법이 아니라 산수입니다
> - **p99** = 손님 100명 중 가장 오래 기다린 1명의 시간 — "평균 대기 1분"이어도 그 1명은 15분일 수 있고, 단골일수록 자주 오니 그 1명이 **매일 누군가**입니다
> - **포화** = 계산원이 쉴 틈 없이 일하는 순간부터, 손님이 조금만 더 와도 줄은 **무한히** 길어집니다
> - **closed 모델의 착시** = "친구 10명에게 계속 사 오라고 시키기" — 계산이 느려지면 친구들이 덜 자주 오게 되므로(응답을 기다리느라) 줄이 안 길어 보입니다. 진짜 세상(open)은 손님이 가게 사정을 봐주지 않습니다

---

## 1. RPS — 정확히 무엇을 세는가

| 용어 | 정의 | 함정 |
|------|------|------|
| offered load | 부하기가 **보내려는** 초당 요청 | 목표값이지 실측 아님 |
| throughput (RPS) | 서버가 초당 **처리한** 요청 | 5xx도 "처리"에 들어감! |
| **goodput** | 초당 **성공(2xx)** 응답 | 보고서에 쓸 숫자 |

"1,000 RPS 견딤"의 정직한 형태: **"목표율 1,000 rps에서 goodput 998 rps, 오류 0.2%, p99 180ms"**. 넷 중 하나라도 빠지면 해석 불가능한 숫자입니다.

## 2. 지연은 분포입니다 — 평균의 거짓말

지연은 정규분포가 아니라 **오른쪽 꼬리가 긴** 분포입니다. 평균은 꼬리에 묻힙니다:

```
p50(중앙값)  50%가 이보다 빠름 — "보통의 경험"
p95          20명 중 1명의 경험
p99          100명 중 1명 — SLO의 단골
p99.9        대규모 서비스라면 "매초 누군가"
```

꼬리가 중요한 구조적 이유: 페이지 하나가 API 수십 개를 부르면, **유저가 p99를 만날 확률은 요청 수만큼 증폭**됩니다 (100번 호출 시 한 번이라도 p99를 넘을 확률 ≈ 63%). 그래서 "평균 빠름"과 "체감 빠름"은 다른 명제입니다.

## 3. Little's Law — 이 모듈의 물리 법칙

```
L = λ × W
동시 처리 중 요청 수 = 도착률(RPS) × 평균 응답시간(초)
```

정상 상태(도착=처리)라면 예외 없이 성립합니다. 실전 사용법:

- **필요 동시성 계산**: 목표 500 rps, 평균 지연 200ms → 항상 100개 요청이 in-flight → 서버 워커/커넥션이 100 미만이면 물리적으로 불가능
- **부하기 VU 계산**: closed 모델에서 VU 하나는 (1/W) rps를 만듭니다 → 500 rps를 내려면 VU ≥ 500 × 0.2 = 100
- **거짓말 탐지**: 보고서의 세 숫자(RPS·지연·동시성)가 L=λW를 안 만족하면 측정이 틀린 것 — lab-02에서 직접 검증합니다

## 4. open vs closed — 부하기의 두 세계관

| | closed (닫힌) | open (열린) |
|---|---|---|
| 방식 | VU N명이 "응답 오면 다음 요청" | **도착률 고정** — 응답과 무관하게 발사 |
| 서버가 느려지면 | 요청률이 **저절로 줄어듭니다** | 미완료 요청이 쌓입니다 (현실처럼) |
| 현실 대응 | 고정 인원의 폐쇄 시스템 (콜센터 상담원) | 인터넷 트래픽 (유저는 서로를 모릅니다) |
| 도구 | k6 기본 executor, Locust 기본 | vegeta, k6 arrival-rate executor |

### coordinated omission — closed 모델의 착시

서버가 순간 5초 멈추면: open 세계에선 그 5초에도 요청이 계속 도착해 **수천 개가 지연을 겪습니다.** closed 부하기는 응답을 기다리느라 요청 자체를 안 보내 — 그 고통이 **측정에서 누락**됩니다. 결과: "p99 양호"라는 낙관적 보고서. 웹서비스의 용량 질문("1,000 rps 유입을 견디나")에는 **open 모델이 정답**이고, closed는 "동시 사용자 N명 시나리오"에 맞는 도구입니다.

## 5. 포화 곡선 — 무릎을 찾아라

부하를 계단식으로 올리며 goodput과 p99를 같이 그리면:

```
p99 ▲                        ┃ ← 포화(무릎): 큐가 자라기 시작
    │                       ┏┛     이후 지연은 수직 상승, goodput은 정체/하락
    │            ┏━━━━━━━━━┛
    │━━━━━━━━━━━┛
    └────────────────────────────▶ 목표 RPS
         선형 구간(여유)      무릎    붕괴
```

- **용량 = 무릎 직전의 goodput** (붕괴 직전 최대값이 아니라!) — 운영 목표는 보통 무릎의 60~80%
- 무릎 뒤의 지연 폭발은 큐잉 이론의 필연: 사용률 ρ→1이면 대기시간 →∞ (편의점 비유의 그 장면)

## 6. 측정 환경 설계 — 숫자의 신뢰도를 정하는 것들

| 결정 | 선택지와 기준 |
|------|-------------|
| 부하기 위치 | 클러스터 **안**(Service 직접 — 앱 자체 용량) vs **밖**(ALB 경유 — 실제 유저 경로, 14의 주제). 무엇을 재는지 먼저 정합니다 |
| 부하기 병목 | 부하기 CPU/포트/파일디스크립터 감시 — **부하기 사용률 >70%면 결과 폐기**, 부하기를 늘려서 재측정 |
| 변수 통제 | HPA/Karpenter 등 자동 스케일 끄기(또는 그것 자체가 실험이면 명시), replicas 고정 |
| 워밍업 | 첫 30초~수 분은 버립니다 (JIT, 커넥션 풀, 캐시 채움) |
| 지속시간 | 단계당 최소 1~2분 정상 상태 — 10초짜리 스파이크는 통계가 아닙니다 |
| keep-alive | 재사용(일반 API 시나리오) vs 신규 연결(로그인 폭주 시나리오) — TLS 핸드셰이크 비용이 갈립니다 |
