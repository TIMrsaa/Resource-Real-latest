# 자가 점검 퀴즈

**Q1.** offered load / throughput / goodput의 차이와, 보고서에 써야 할 것은?

**Q2.** "평균 지연 100ms"가 위험한 보고인 이유 두 가지는? (분포의 성질 + 사용자 경험 구조)

**Q3.** Little's Law를 쓰고, "목표 500 rps·평균 지연 200ms" 서비스의 필수 동시 처리 능력을 계산하세요.

**Q4.** closed와 open 모델의 동작 차이를 "서버가 느려질 때"를 기준으로 설명하세요.

**Q5.** coordinated omission이란? 어느 모델에서 왜 생기고, 어떤 질문에 치명적인가요?

**Q6.** 포화 곡선에서 "용량"은 어느 지점이며, 왜 최대 처리율이 아닌가?

**Q7.** 측정 결과를 폐기해야 하는 신호 3가지는?

**Q8.** lab-02에서 VU 50 · 지연 2초의 closed 실험이 25 rps가 나오는 이유를 법칙으로 설명하고, 이 성질의 실전 용도 하나를 들라.

---

## 정답

**A1.** offered load = 보내려는 초당 요청(목표), throughput = 서버가 처리한 초당 응답(5xx 포함), goodput = 성공(2xx)만. 보고서는 **넷 다**: 목표율 + goodput + 오류율 + p99 — 하나라도 빠지면 해석 불가.

**A2.** ① 지연은 오른쪽 꼬리가 긴 분포라 평균이 꼬리(p99가 초 단위일 가능성)를 숨깁니다. ② 페이지 하나가 API 수십 개를 부르므로 유저가 한 번이라도 꼬리를 만날 확률이 증폭됩니다(100회 호출 시 ≈63%) — 평균이 좋아도 체감은 나쁠 수 있습니다.

**A3.** L = λ × W. 500 rps × 0.2s = **100** — 항상 100개 요청이 in-flight이므로 워커/커넥션/스레드가 100 미만이면 목표 자체가 물리적으로 불가능합니다.

**A4.** closed: VU가 응답을 받아야 다음 요청 — 서버가 느려지면 **요청률이 저절로 줄어** 부하가 완화됩니다(자기조절). open: 도착률 고정 — 서버가 느려져도 요청은 계속 도착해 미완료가 쌓입니다(현실의 유입).

**A5.** 서버가 멈추거나 느려진 구간에 closed 부하기가 요청을 보내지 않아 그 구간의 지연이 **측정에서 누락**되는 것. closed 모델의 구조적 성질이며, "N rps 유입을 견디나"라는 **용량 질문**에 낙관 편향된 답(가짜 통과)을 주기 때문에 치명적입니다.

**A6.** 무릎(knee) **직전**의 goodput. 무릎 이후는 큐가 자라는 구간이라 처리율이 비슷해 보여도 지연이 발산 중 — 그 상태는 "처리"가 아니라 "지연 축적"이므로 용량으로 셀 수 없습니다. 운영 상한은 무릎의 60~80%.

**A7.** ① 부하기 사용률 >70% 또는 dropped iterations 발생(부하기 병목) ② 자동 스케일 미통제/워밍업 미분리(움직이는 표적) ③ 단계당 정상 상태 미달(수십 초 미만의 스파이크 측정). (+보고 숫자가 L=λW 검산에 실패하는 경우)

**A8.** 정상 상태에서 λ = L/W = 50 VU ÷ 2s = 25 rps — closed 모델은 L(VU)과 W(지연)가 고정되면 처리율이 결정됩니다. 용도: 목표 rps에 필요한 VU 수 사전 산정(VU = 목표율 × W), 또는 보고서의 세 숫자 검산.
