# 이론 — fleet 패턴, 글로벌 트래픽, 그리고 상태라는 화물

> **🌱 17세 눈높이 비유: 프랜차이즈 지점 내기**
> 잘되는 식당(클러스터)이 커지다 지점을 냅니다:
> - **왜 내나** = 한 매장 화재가 전부를 태우면 안 돼서(폭발 반경), 그 지역 법 때문에(규제), 손님이 멀어서(지연)
> - **kubefed의 실패** = "본사에서 전 지점 주방을 원격 조종"하려던 시도 — 본사 전산이 죽으면 전 지점이 멈추고, 지점마다 다른 사정을 본사가 못 담았습니다
> - **GitOps fleet** = 대신 **레시피북(git)을 표준**으로: 지점들은 독립 운영하되 같은 레시피를 각자 받아 갑니다 — 본사가 죽어도 지점은 돕니다
> - **Route53/GA** = 안내 데스크: 손님을 가까운/건강한 지점으로 — 지점 하나가 문 닫으면 자동으로 옆 지점 안내
> - **데이터** = 그런데 **포인트 적립 원장**은? 지점마다 장부가 다르면 대참사 — 장부(상태)를 어디 두느냐가 지점 확장의 진짜 난제

## 1. 아키텍처 스펙트럼

| 패턴 | 구조 | 푸는 문제 | 대가 |
|------|------|----------|------|
| **독립 + 표준화** | 클러스터들 독립, git이 표준 | env 분리, 팀/규제 격리 | fleet 운영(×N) |
| active-passive | 주 리전 + 대기(파일럿/웜 — 36) | 리전 DR | 대기 비용, 전환 리허설 |
| active-active | 복수 리전 동시 서빙 | 지연·가용성 최상 | **데이터 복제** — 최고 난도 |
| cell-based | 셀(클러스터) 단위로 유저 분할 | 폭발 반경을 1/N로 | 셀 라우팅·재분배 복잡성 |

현실 조직의 90%는 첫 줄(독립+표준화)에서 삽니다 — prod/staging/dev 클러스터 + GitOps. 나머지 패턴은 아래 계층들이 갖춰질 때 가능해집니다.

## 2. fleet 표준화 — 선언의 중앙화

```
git repo
 ├─ base/               ← 공통 표준 (테넌트 패키지 34, 애드온 구성 11, 정책 23...)
 └─ overlays/
     ├─ cluster-a/      ← 클러스터별 차이 (리전, 크기, 도메인)만 패치
     └─ cluster-b/
→ ArgoCD ApplicationSet(또는 Flux)이 "클러스터 목록 × base"를 자동 전개 (39의 fleet판)
```

- 규율: **클러스터별 차이는 overlay에만** — base를 클러스터에서 직접 고치는 순간 fleet이 아니라 N개의 눈송이가 됩니다
- **drift 탐지**가 fleet 운영의 심장: "선언과 실물의 차이"를 상시 감시(GitOps 도구의 diff/selfHeal — 39). 클러스터가 늘수록 사람이 못 보는 곳이 늘어서입니다
- 버전 스큐 관리: fleet 내 K8s 버전 차이를 1마이너 이내로 — 업그레이드(21)가 "파도"처럼 fleet을 훑는 파이프라인이 됩니다 (staging 파도 → prod 파도)

## 3. 글로벌 트래픽 계층

| | Route53 (DNS) | Global Accelerator (anycast) |
|---|---|---|
| 원리 | DNS 응답으로 유도 | 고정 IP 2개 — AWS 백본으로 근접 진입 |
| 정책 | weighted / latency / **failover** / geolocation | 리전별 가중치 + 헬스 기반 |
| 페일오버 속도 | **TTL에 묶임** (캐시가 옛 답을 기억) | 초 단위 (DNS 무관) |
| 자리 | 표준 답, 저렴 | 빠른 페일오버·고정 IP 요구 |

공통의 심장은 **헬스체크**입니다 — "지점이 건강한가"를 무엇으로 판정하나(LB 200? 합성 트랜잭션?)가 페일오버 품질을 정합니다. 얕은 헬스체크(포트 열림)는 "죽었는데 산 척"을 못 잡습니다 — 14의 헬스체크 논의가 글로벌 스케일로 재등장.

## 4. 클러스터 간 통신 — 필요해지기 전에 의심하세요

- 대부분의 "클러스터 간 호출"은 사실 **공용 진입점(LB DNS) 경유**로 충분합니다 — 특별한 기술이 필요 없는 경로부터
- 정말 mesh 수준이 필요하면: Istio multi-cluster(east-west gateway로 상호 디스커버리 — 20의 확장), 또는 **VPC Lattice**(AWS 관리형 — 클러스터·VPC·계정 경계를 넘는 서비스 네트워킹, 20에서 예고)
- 원칙: 클러스터 경계는 격리를 위해 그었습니다 — **경계를 다시 꿰매는 기술은 그 격리를 되파는 것**이므로, 필요의 증명을 먼저

## 5. 상태 — 8할의 문제

- 패턴들: 쓰기 단일 리전 + 읽기 복제(Aurora Global — 초 단위 복제 지연), 멀티 마스터(DynamoDB global tables — 충돌 해소 규칙 필수), 유저 파티셔닝(cell — 유저별 홈 리전)
- k8s 쪽 함의: **어느 워크로드가 상태를 가졌는지**를 아키텍처 그림에 명시 — 무상태는 fleet 기술로 자유 이동, 상태는 데이터 계층의 계약을 따라서만
- Velero(36)의 자리: 스냅샷 기반 이사/DR — "복제"가 아니라 "복원"의 RPO/RTO임을 구분
