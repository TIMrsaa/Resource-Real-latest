## 정답

**A1.** ① 폭발 반경 제한(cell) ② 규제/데이터 주권 ③ 지역 지연 ④ 하드 격리(외부 테넌트·보안 등급) ⑤ 환경 분리(prod/staging). 그 전에: 34의 스펙트럼 — ns 패키지 → 노드 격리 → vCluster로 흡수 가능한지 먼저 심문.

**A2.** 중앙 control plane이 하위 클러스터를 원격 제어하는 설계 — 그 중앙이 병목이자 최대 폭발 반경이 됐고, 클러스터별 차이를 추상화가 못 담았습니다. 현대의 답: **제어가 아니라 선언의 중앙화** — git이 표준을 소유하고, 각 클러스터는 독립적으로 그것을 당겨 갑니다(GitOps fleet).

**A3.** 공통 표준은 base에, 클러스터별 차이는 overlay에**만** — base를 특정 클러스터에서 직접 수정 금지. 깨지는 경로: "긴급하니 그 클러스터에서 kubectl로" → 눈송이화 + 다음 전개 파도에서 소리 없이 원복(또는 영구 drift). 그물: 주기적 diff 스캔 + selfHeal + 긴급 수정의 사후 git 반영 의무.

**A4.** R53: RTO ≈ 헬스체크 감지 시간 + **DNS TTL 수렴**(리졸버·클라이언트 캐시가 옛 답을 기억 — TTL이 지배 변수). GA: anycast 고정 IP라 DNS 캐시 항이 사라지고 헬스 판정→백본 경로 전환만 남습니다(초 단위).

**A5.** 최악: "프로세스는 살았는데 의존성(DB)이 죽은" 리전을 건강 판정 — 유저는 오류, 페일오버는 침묵. 처방: 합성 트랜잭션 수준의 깊은 체크. 부작용 관리: 깊은 체크는 무겁고 오탐 가능 — 깊이·주기·판정 임계(연속 N회)를 명시 설계하고, 체크 자체의 부하를 용량에 반영(14의 교훈).

**A6.** failover는 "나쁜 상태에서 탈출" — 빨라야 하고 판단이 단순합니다(주 리전 불능). failback은 "좋아 보이는 상태로 복귀" — 리전이 떠 있음과 **데이터가 수렴했음은 다른 명제**라(복제 지연·유실분 처리), 잘못 복귀하면 시간여행/쓰기 충돌이라는 2차 사고가 됩니다. 그래서 수렴 판정 기준+승인자를 둔 수동 게이트.

**A7.** vCluster는 호스트의 Pod 안에 **완전한 독립 API 서버**를 세웁니다(34 스펙트럼 ③) — 컨텍스트 전환, 독립된 리소스 공간, 클러스터별 배포·drift라는 fleet 운영의 본질이 실물 클러스터와 동일하게 성립하면서, 비용은 Pod 하나 수준입니다.

**A8.** ① 쓰기는 어디서 하나(단일 리전/멀티 마스터+충돌 규칙/유저 파티셔닝) ② 복제 지연 허용치(RPO)와 페일오버 순간의 유실분 처리 방침 ③ failback의 데이터 수렴 판정 기준 — 셋 중 하나라도 공란이면 트래픽 설계가 아무리 좋아도 멀티리전이 아닙니다.
