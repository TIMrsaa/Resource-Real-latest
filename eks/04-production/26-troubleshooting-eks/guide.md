# 학습 가이드 — 증상은 k8s에서, 원인은 AWS에서

## EKS 장애의 특징: 증상과 원인이 다른 세계에 삽니다

38에서 배운 루틴(`describe pod` → events → logs)은 여전히 출발점입니다. 그러나 EKS에선 그 출력이 종종 **원인이 아니라 그림자**를 보여줍니다:

| kubectl이 보여주는 증상 | 실제 원인이 사는 곳 |
|------------------------|-------------------|
| Pod가 ContainerCreating에서 멈춤 | 서브넷 IP 고갈 (VPC — 16) |
| Pod가 AccessDenied 로그 | IAM 신뢰 정책·association (IAM — 09) |
| Service 엔드포인트는 정상인데 유저는 502 | ALB 타깃 등록·draining (ELB — 14) |
| 노드가 NotReady | ENI 부족·SG 규칙·kubelet 인증 (EC2/IAM) |
| DNS 간헐 실패 | CoreDNS replicas·NodeLocal·conntrack (혼합) |

그래서 EKS 진단의 첫 기술은 **계층 판정**입니다: "이 증상은 어느 계층에 물어야 하는가." 잘못된 계층에서 20분을 태우는 것이 온콜 시간의 대부분을 잡아먹습니다.

## 심문의 원칙 세 가지

1. **위에서 아래로**(앱 → k8s → EKS → AWS): 확인 비용이 싸고 변경 빈도가 높은 곳부터 — 18의 진단 계단이 이 원칙의 네트워크판이었습니다
2. **증거를 남기는 곳을 압니다**: k8s events(1시간 후 소멸!), 감사 로그(21), Flow Logs(18의 사각 주의), ipamd 로그(07), 컨트롤러 로그(08). 각 계층의 CCTV 위치를 아는 것이 진단 속도입니다
3. **최근 변경을 먼저 의심**: 배포·애드온 업데이트(11)·정책 변경·노드 교체(21) — "어제까지 됐다"면 어제의 diff가 답입니다 (GitOps라면 git log가 곧 용의자 목록 — 39)
