# 학습 가이드 — 백업은 1층일 뿐, DR은 건축입니다

## 36에서 무엇이 남았나

36의 결론: 검증 없는 백업은 기분입니다, RPO/RTO가 설계를 정합니다, 복구는 훈련입니다. 그 도구(Velero)와 언어(RPO/RTO)는 그대로 가져옵니다 — 다만 36의 시나리오는 "ns를 실수로 지웠다"였습니다. 이 모듈의 시나리오는 다릅니다:

> **"리전 장애로 클러스터가 통째로 없습니다. 지금부터 몇 시간 안에, 다른 리전에서, 전부 다시 세울 수 있는가요?"**

이 질문 앞에서 백업은 필요조건일 뿐입니다 — 백업이 있어도 클러스터를 다시 짓는 데 이틀 걸리면 RTO는 이틀입니다.

## 재건 스택 — RTO는 층의 합입니다

```
4층  데이터        Velero restore / DB 복제 승격     ← 대개 최대 항 (RPO도 여기서)
3층  워크로드       GitOps 포인팅 한 번 (39·23)       ← fleet이 있다면 분 단위
2층  플랫폼        애드온·컨트롤러·정책 표준 (11·23)   ← base가 있다면 분 단위
1층  인프라        eksctl/IaC 선언 재실행 (02)        ← CP 생성 ~20분 + 노드
```

통찰: **평소의 선언화 수준이 곧 RTO입니다.** 1~3층이 전부 git에 선언돼 있는 조직은 재해가 "선언 재실행 + 데이터 복원"이고, 콘솔 클릭으로 자란 클러스터는 재해가 "고고학"이 됩니다. 21의 업그레이드 runbook, 23의 fleet base, 39의 GitOps가 사실은 전부 DR 자산이었던 것.

## 백업 격리의 사다리

36 pitfall 3("같은 바구니")의 체계화: 같은 리전(리전 장애에 동반 소멸) → **크로스 리전**(리전 장애 생존 — lab-01) → **타계정**(계정 탈취·ransomware 생존) → **오브젝트 잠금**(관리자 권한 탈취에도 삭제 불가). 위협 모델이 사다리의 높이를 정합니다 — 전부 오르는 게 아니라, 우리 위협까지 오르는 것.
