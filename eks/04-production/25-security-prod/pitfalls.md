# 흔한 함정 5선

## 1. IMDS를 열어둔 채 IRSA만 자랑

"우리는 IRSA로 최소권한이에요" — 그런데 hop limit이 기본값이면 Pod 하나의 RCE로 **노드 IAM 역할**을 그대로 가져갑니다. 노드 역할엔 대개 ECR pull, CNI(ec2:*NetworkInterface*), 로그 쓰기 권한이 있고, 여기에 누군가 "편의상" 붙여둔 정책이 하나만 있으면 계정 침해가 됩니다. `--http-put-response-hop-limit 1 --http-tokens required`를 노드그룹/launch template 기본값으로 — 이 모듈의 단 한 줄을 고른다면 이것입니다.

## 2. k8s Secret을 "암호화됐다"고 믿기

etcd KMS 봉투암호화를 켜도 **API 읽기 권한이 있으면 평문**입니다 — 암호화는 "etcd 백업/디스크가 유출됐을 때"만 지킵니다. 시크릿 노출의 실제 경로는 대부분 과잉 RBAC(get secrets)과 로그·env 노출입니다. 사다리를 다 오르라: RBAC 최소화 → KMS 암호화 → 외부화(CSI, lab-01) — 그리고 `env`로 주입한 시크릿은 프로세스 목록·크래시 덤프에 샌다는 것도.

## 3. 탐지를 켜고 대응은 사람에게

GuardDuty Finding이 이메일로 쌓이고 아무도 안 봅니다 — 새벽 3시의 크립토마이너는 아침까지 채굴합니다. **탐지는 방어가 아닙니다**: Finding → EventBridge → 자동 격리(deny-all NetworkPolicy 적용, 노드 cordon, 스냅샷)의 최소 자동화가 없으면 탐지 비용은 보험이 아니라 알림 소음입니다. 그리고 그 자동화를 **분기마다 실제로 발화**시켜 보라(침해 훈련).

## 4. PSA를 baseline에 영구 정착

"restricted는 앱이 안 돌아서 baseline으로" — baseline은 hostPath와 대부분의 capability를 여전히 허용합니다(32). 대개 진짜 이유는 앱이 root로 돌거나 임의 uid 대응이 안 된 것이며, 그건 이미지 수정으로 고칠 부채입니다. 기한부 예외(ns 라벨 + 만료일 + 담당자)로 관리하고, 새 ns의 기본값은 restricted. 예외 없는 정책은 무시당하고, 만료 없는 예외는 영구가 됩니다.

## 5. 방어를 세우고 우회 경로를 안 봄

NetworkPolicy로 egress를 잠갔는데 hostNetwork Pod가 허용돼 있습니다(NP는 hostNetwork Pod를 우회당합니다). 이미지 레지스트리를 강제했는데 initContainer는 검사 안 했습니다. IMDS는 막았는데 노드에 마운트된 SA 토큰이 클러스터 관리자급입니다. 심층 방어의 각 층은 **가정을 공유**하므로, 한 층의 우회 경로가 다른 층의 전제를 깹니다 — 정기적으로 lab-02처럼 **공격자 관점의 검증**을 돌려라. 정책 파일을 읽는 것과 공격이 막히는 것은 다른 사실입니다.

## 실무 사고 사례

> 침해 사고: 이미지에 포함된 취약 라이브러리로 RCE → 공격자는 30초 만에 IMDS에서 노드 역할을 획득했고, 그 역할에는 몇 달 전 "S3 접근이 필요해서" 붙여둔 `s3:*`이 있었습니다. 고객 데이터 버킷이 열람됐고, 같은 자격증명으로 다른 계정 리소스까지 정찰당했습니다. 탐지는 GuardDuty가 12분 만에 했지만(Finding: 비정상 IP의 S3 대량 조회), 알림은 아무도 보지 않는 메일함으로 갔고 실제 인지는 다음 날 오전. 사후 대책이 이 모듈의 목차가 됐습니다: ① 전 노드그룹 hop limit=1(하루 만에 적용 — 무중단) ② 노드 역할에서 s3:* 제거, 워크로드는 IRSA로 자원 단위 ③ Finding → EventBridge → Lambda 자동 격리 + 온콜 페이지 ④ 분기 침해 훈련(lab-02의 그 시나리오). 교훈: **가장 비싼 보안 도구보다 한 줄의 hop limit이 그날 더 많은 걸 지켰을 것입니다.**
