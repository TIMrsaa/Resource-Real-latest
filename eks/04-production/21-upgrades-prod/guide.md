# 학습 가이드 — 원리는 배웠습니다, 이제 조직의 절차로

## k8s 35와의 관계

35에서 배운 것: skew가 순서를 강제합니다, drain은 PDB의 박자로 진행됩니다, CP는 비가역이라 preflight가 전부입니다. 그 원리는 변하지 않습니다 — 이 모듈이 더하는 것은 **프로덕션의 세 가지 현실**입니다:

1. **규모**: 노드 3대의 drain과 300대의 drain은 다른 문제입니다 — 시간 산수, 동시성(surge), 용량 여유가 계획의 절반이 됩니다
2. **표면의 다양화**: 이제 우리 클러스터엔 관리형 노드그룹만 있지 않습니다 — Karpenter 노드(17), Fargate(06), 그리고 Auto Mode(04)까지, **각자 업그레이드 방식이 다릅니다**
3. **반복 가능성**: 분기마다 돌아오는 일은 사람의 기억이 아니라 절차(스크립트+계획서 양식)에 실려야 합니다 — lab-01의 산출물이 그것입니다

## 노드 플릿 전략 미리보기 — "어떻게 열차를 바꾸나"

| 전략 | 한 줄 | 롤백 |
|------|------|------|
| 관리형 롤링 | EKS가 자동 drain·교체 (35 lab-02의 자동판) | 구 AMI 재롤링(느림) |
| **Blue/Green NG** | 새 노드그룹 → 이주 → 구 그룹 삭제 (lab-02) | 구 그룹 유지 중이면 즉시 |
| Karpenter drift | AMI alias만 갱신 — drift 감지가 알아서 순환 | NodeClass 되돌리면 역drift |
| Fargate | Pod 재배포 = 새 버전 (노드 개념 없음) | 재배포 |
| Auto Mode | AWS가 순환 (우리는 안 만짐) | — |

같은 클러스터 안에 이 중 셋이 공존하는 게 현대 EKS의 평균입니다 — runbook은 표면별 절을 가져야 합니다.

## 이 모듈의 산출물

lab-01의 **업그레이드 계획서**(현황 표 + 게이트 판정 + 표면별 실행 명령 + 롤백 조건)가 최종 산출물입니다. 잘 쓴 계획서는 "누가 실행해도 같은 결과"를 만듭니다 — 그것이 절차의 정의입니다.
