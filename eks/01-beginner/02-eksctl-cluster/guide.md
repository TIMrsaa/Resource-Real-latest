# 학습 가이드 — "어떻게 만들었는지"가 운영의 절반

## 한 줄 생성의 함정

k8s 파트 모듈 01에서 클러스터를 만들 때는 한 줄 명령이면 충분했습니다. 하지만 운영에선 그 한 줄이 부채가 됩니다:

- 같은 클러스터를 다시 만들 수 있나요? (DR — k8s 36, eks 24)
- 누가 어떤 옵션으로 만들었는지 기록이 있나요?
- 변경(노드그룹 추가, 애드온)을 리뷰할 수 있나요?

답은 k8s 파트 내내 반복한 원칙과 같습니다: **선언형 + Git**. eksctl의 ClusterConfig 파일이 클러스터 버전의 "매니페스트"다. (실무에선 Terraform/CDK도 흔합니다 — 원리는 동일하고, 이 커리큘럼은 eksctl로 통일)

## 두 번째 주제: 인증의 미스터리 풀기

지금까지 kubectl이 "그냥 됐다" — 그 마법의 정체:

```
kubectl → kubeconfig의 exec 플러그인 → aws eks get-token (STS 서명 토큰)
       → API 서버가 토큰 검증 (AWS가 "이 사람은 IAM arn:...이다" 보증)
       → access entry가 그 IAM을 클러스터 주체로 매핑
       → RBAC(k8s 11)이 인가
```

IAM이 **인증**(누구냐)을, RBAC이 **인가**(뭘 할 수 있냐)를 — k8s 11에서 "EKS는 인증을 IAM에 위임한다"고 했던 그 문장이 이 모듈에서 실물이 됩니다.

## aws-auth의 세대교체 — 학습 시 주의

구글링하면 `aws-auth` ConfigMap을 수정하는 글이 쏟아집니다 — **구세대 방식**입니다 (실수 한 번에 전원 잠금 사고로 악명 높았던). 현행 표준은 **access entries**(EKS API 객체) — 이 모듈은 access entries로 배우고, aws-auth는 "옛 클러스터에서 만나면 알아볼" 수준만 다룹니다.
