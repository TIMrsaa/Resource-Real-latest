# 흔한 함정 5선

## 1. "관리형 = 전부 관리"라는 착각

control plane만 AWS 몫입니다. IP 설계, IAM 통합, 노드 패치 트리거, 업그레이드, 비용, 워크로드 보안 — 전부 내 일이고, **실제 장애의 대부분이 내 영역에서 납니다.** EKS 도입 후 "운영자가 필요 없다"가 아니라 "운영자의 일이 위로 올라간다"가 맞는 문장.

## 2. 클러스터를 환경/팀마다 남발

"격리는 클러스터 분리가 깔끔하지" — 클러스터마다 $73/월 고정비 + 노드 중복 + 운영 부담 N배. k8s 34(멀티테넌시)에서 배운 ns 격리/vCluster가 먼저 검토할 선택지입니다. 클러스터 분리는 격리 요구가 그 비용을 정당화할 때만.

## 3. 구버전 방치 → 연장 지원 과금

14개월은 금방입니다 — 어느 날 청구서의 클러스터 항목이 6배가 돼 있습니다(EXTENDED 자동 진입). 모든 클러스터의 버전과 표준 지원 종료일을 달력에 — k8s 35의 "작게 자주"는 EKS에서 재정 정책입니다.

## 4. 노드만 끄고 "다 껐다"고 믿기

휴지기에 노드그룹 0 — 잘했습니다. 그런데 ALB, NAT Gateway, 잔존 EBS, EIP는 계속 과금됩니다(노드와 수명이 독립). lab-02 Step 1의 전수 조사 5종이 진짜 체크리스트입니다. "kubectl로 안 보이는 비용"이 EKS 청구서의 절반입니다.

## 5. 학습 자료의 다른 플랫폼 가정

블로그의 GKE/kubeadm 절차를 EKS에 그대로 — control plane 플래그 수정, etcd 백업, admission 플러그인 활성화 같은 단계에서 막힙니다(EKS는 불가). EKS 문서/베스트 프랙티스 가이드를 1차 소스로, "이건 경계선 어느 쪽 이야기인가"를 항상 먼저 묻는 습관.

## 실무 사고 사례

> 스타트업이 PoC로 만든 EKS 클러스터 3개를 잊었습니다. 노드는 꺼뒀으니 안심 — 8개월 후 정산: 클러스터 3×$73 + 붙어 있던 ALB 2개 + NAT GW 3개 + 잔존 EBS 200GB ≈ **월 $700이 8개월**. 더 아픈 것: 그중 한 클러스터가 연장 지원에 진입해 있었습니다. 정리 후 도입한 수칙: ① 모든 클러스터에 owner/expiry 태그 의무화 ② 주간 비용 리포트에 "태그 없는 리소스" 섹션 ③ PoC는 생성 스크립트(IaC)와 삭제 기한을 함께 — "다시 만들 수 있으면 지울 수 있습니다."
