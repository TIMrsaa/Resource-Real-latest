## 정답

**A1.** 브라우저(콘솔 로그인 IAM) → 콘솔 백엔드가 그 IAM 자격증명으로 EKS API 서버에 K8s API 호출 → access entry가 ARN을 K8s 주체로 매핑 → access policy/RBAC 인가 → 허용된 것만 표시. 콘솔 = 내 IAM으로 대신 쳐주는 kubectl.

**A2.** 로그인 IAM의 access entry 부재(또는 권한 부족). 해결: 그 ARN에 entry 생성 + **AmazonEKSViewPolicy**(필요시 ns 스코프) — 열람 요구에 admin은 과잉(최소 권한).

**A3.** 노드그룹 스케일 변경 → CLI/ClusterConfig(기록·재현). 장애 중 상태 파악 → 콘솔(insights/노드 헬스 한눈). Deployment 이미지 변경 → kubectl/GitOps(K8s 안쪽은 매니페스트가 진실).

**A4.** 관측성 탭의 **insights**(업그레이드 차단 요소 자동 점검 — k8s 35의 preflight) / 컴퓨팅 탭의 **노드 헬스**(degraded 노드그룹 조기 발견).

**A5.** 콘솔에 로그인한 IAM이 자동 주입 — 별도 키 입력 없음. 한계: 그 IAM의 권한 그대로(승격 아님)이며, 콘솔 접근이 곧 CloudShell 접근이라 콘솔 계정 보안이 더욱 중요.

**A6.** `~/`(홈, 리전별 1GB 영속 — `~/bin`에 도구 설치 + .bashrc PATH). 제약: ① 리전이 바뀌면 다른 홈 ② 1GB 용량/세션 타임아웃 — 무거운 작업 부적합.

**A7.** ① 리전 확인(우상단 / CLI --region) ② 계정/IAM 확인(`aws sts get-caller-identity` — 다른 프로파일/SSO 계정으로 로그인했을 가능성). "사라짐"의 대부분은 위치를 잘못 보는 것.

**A8.** CloudTrail에는 "누가 무엇을"은 남지만 **"왜"와 리뷰가 없습니다** — 의도/맥락/승인 없는 기록은 운영 이력으로 불충분하고, IaC와의 drift를 만듭니다. 코드+PR은 왜/리뷰/재현을 함께 남깁니다 (k8s 39의 GitOps 원칙).
