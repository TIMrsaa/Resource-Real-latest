# 학습 가이드 — Auto Mode 시대에 노드그룹을 배우는 이유

## 현실의 분포

신규 클러스터의 추천이 Auto Mode로 기울어도, 실무에서 만날 클러스터의 다수는 관리형 노드그룹입니다. 그리고:

- Auto Mode의 제약(04 — 커스텀 AMI/호스트 접근/특수 하드웨어)에 걸리는 워크로드는 **계속 노드그룹**에 남습니다
- 마이그레이션을 설계하려면 양쪽을 다 알아야 합니다
- 노드그룹은 Karpenter(17)와 비교할 "기준선"입니다 — 무엇이 불편한지 알아야 Karpenter의 가치가 보입니다

## 노드그룹의 사고방식 vs Karpenter/Auto Mode의 사고방식

```
노드그룹:   "이 모양의 노드를 N대 유지하라"     (정적 풀 — 풀이 먼저, Pod가 거기 맞춤)
Karpenter:  "이 Pod들에 맞는 노드를 그때그때"   (동적 — Pod가 먼저, 노드가 맞춤)
```

노드그룹 세계의 설계 단위는 **"풀"**입니다: 일반용 풀, 메모리 집약 풀, GPU 풀, Spot 풀... 각 풀에 라벨(끌어당김)과 taint(밀어냄)를 걸어 워크로드를 분류 배치합니다 — k8s 12에서 배운 그 문법이 인프라 설계 언어가 되는 곳.

## 이 모듈에서 손에 붙일 것

1. **3층 구조 감각**: 노드그룹 이상 동작의 진단은 결국 ASG/EC2 층으로 내려갑니다 (모듈 26의 예고)
2. **풀 설계 문법**: 새 워크로드 유형이 올 때 "풀을 새로 팔까, 기존에 태울까"를 판단하는 기준
3. **업데이트 제어**: k8s 35에서 배운 drain의 속도 조절 손잡이(maxUnavailable)가 어디 붙어 있는지
