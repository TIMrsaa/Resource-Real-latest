# 학습 가이드 — 가장 조용하고 가장 중요한 코드

## 왜 마지막 모듈이 CNI인가

이 파트의 첫 모듈(01)에서 우리는 "EKS는 어디까지 AWS의 것인가"를 물었습니다. 답의 경계선 위에 vpc-cni가 있습니다 — AWS가 만들었지만 **오픈소스이고, 우리 노드에서 돌고, 고칠 수 있습니다.** 그리고 이것은 EKS에서 가장 근본적인 코드입니다: 이게 없으면 Pod에 IP가 없고, IP가 없으면 아무것도 없습니다.

또한 학습적으로 완벽한 종착지입니다. 이 저장소를 읽으려면 지금까지 배운 것이 전부 필요합니다:

- ipamd의 warm pool 계산 → **07**의 IP 회계
- prefix delegation의 /28 할당 → **16**의 소진 방정식
- CNI 플러그인의 veth·라우트 설정 → **18**의 패킷 경로
- DaemonSet으로 배포되는 구조 → **k8s 13**
- 애드온으로 관리되는 버전 → **11**
- 그리고 기여의 문법 → **27·28**

## 두 바이너리라는 첫 이해

대부분의 사람이 "vpc-cni"를 하나로 뭉뚱그립니다. 실제로는:

```
① ipamd (aws-node DaemonSet 안의 장수 데몬)
   EC2 API와 대화 — ENI 부착, IP/prefix 할당, warm pool 유지
   IP 재고 장부(datastore)를 메모리에 들고 있습니다
   gRPC 서버로 대기

② CNI 플러그인 (/opt/cni/bin/aws-cni — kubelet이 Pod마다 실행하는 단명 프로세스)
   ipamd에 gRPC로 "IP 하나 줘" 요청
   받은 IP로 veth 쌍 생성, netns 설정, host route 추가
   끝나면 죽습니다
```

이 분리가 설계의 핵심입니다 — 느리고 실패할 수 있는 **EC2 API 호출**(①)을, Pod 생성 경로의 **빠른 로컬 작업**(②)에서 분리했습니다. warm pool이 존재하는 이유가 바로 이것입니다(07의 그 선점이 여기서 정당화됩니다).

## 기여의 현실적 경로

CNI 코드에 대한 기여는 신중해야 합니다 — 버그 하나가 전 세계 EKS 클러스터의 Pod 생성을 막을 수 있습니다. 그래서 첫 기여는 코드의 가장자리에서 시작합니다:

```
① 로그·메트릭 개선   "IP 할당 실패 시 서브넷 여유를 로그에" ← 16에서 우리가 아쉬웠던 것
② 문서              트러블슈팅 가이드, 환경변수 설명
③ 테스트            엣지 케이스 커버리지
④ 버그픽스          재현 가능한 것부터 (good first issue)
⑤ 코어 로직         충분한 신뢰가 쌓인 후 — 여긴 리뷰가 엄격합니다 (그래야 합니다)
```

## 안전 수칙

**공유 클러스터에 직접 빌드한 CNI 이미지를 배포하지 마세요.** aws-node DaemonSet을 잘못 건드리면 모든 Pod의 네트워킹이 멈춥니다. 실험은 개인 계정의 일회용 클러스터(kind는 VPC CNI를 못 씁니다 — 진짜 EKS가 필요합니다)에서. 이 랩은 코드 읽기와 단위 테스트에 집중합니다.
