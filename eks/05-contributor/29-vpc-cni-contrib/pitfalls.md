# 흔한 함정 5선

## 1. 공유 클러스터에 커스텀 CNI를 배포

이 모듈에서 단 하나의 금기. aws-node DaemonSet을 직접 빌드한 이미지로 바꾸면 — 버그 하나에 **새 Pod가 전혀 뜨지 않고**, 롤백하려 해도 그 롤백 Pod조차 네트워크가 필요합니다. 다른 사람의 워크로드가 인질이 됩니다. 실험은 개인 계정의 일회용 클러스터, 노드 한 대, 그리고 "망가뜨려도 되는" 각오로. 코드 읽기와 단위 테스트만으로도 이 모듈의 목표는 달성됩니다.

## 2. 두 바이너리를 하나로 착각하고 디버깅

"CNI 로그를 보자"며 aws-node Pod 로그만 뒤집니다 — 그건 ipamd의 로그입니다. 플러그인(단명 프로세스)의 로그는 **노드의 파일**(`/var/log/aws-routed-eni/plugin.log`)에 있고, 증상이 "IP는 할당됐는데 Pod가 통신 불가"라면 범인은 플러그인 쪽입니다. 두 바이너리, 두 로그, 두 책임 — 이 구분이 CNI 디버깅의 첫 단추입니다(k8s 38의 진단 루틴이 여기서 갈라집니다).

## 3. 네트워킹 코드를 "테스트할 수 없다"고 단정

netlink 호출과 EC2 API가 있으니 클러스터가 필요하다고 생각하면 개발 루프가 몇 분짜리가 됩니다. 저장소는 이미 그 경계를 인터페이스로 감싸 mock을 주입합니다 — `make unit-test`가 수천 개를 초 단위로 돌리는 이유입니다. **테스트 가능성은 코드 구조의 성질**이지 도메인의 성질이 아닙니다. 당신의 컨트롤러도 그렇게 지어라.

## 4. Pod 생성 경로에 무거운 코드를 넣기

플러그인의 ADD 경로는 **모든 Pod가 지나는 지연 민감 구간**입니다 — 여기에 추가 API 호출, 재시도 루프, 큰 로그 직렬화를 넣으면 클러스터 전체의 Pod 기동이 느려집니다(그리고 대규모 클러스터에서 EC2 API 쓰로틀을 유발합니다). 그래서 ipamd가 warm pool을 미리 채우는 것입니다. 성능 경로에 손대는 PR에는 벤치마크를 첨부하세요 — 리뷰어가 가장 먼저 묻습니다.

## 5. 로그에 IP·계정 정보를 흘리기

CNI 코드는 본질적으로 IP·ENI ID·서브넷을 다룹니다 — 디버깅용 로그를 추가하다 Pod IP, VPC ID, 계정 ID가 로그 레벨 info로 쏟아지게 만들기 쉽습니다. 그리고 그 로그는 CloudWatch(12)로 흘러가 수집 비용이 되고, 유출 시 인프라 지도가 됩니다. 규칙: 식별자는 debug 레벨, 통계·상태는 info. PR에서 "이 로그가 프로덕션에서 초당 몇 줄인가"를 자문하세요.

## 실무 사고 사례

> 한 기여자가 IP 할당 실패 시 재시도를 넣는 PR을 올렸습니다 — 사용자로서 "실패가 너무 쉽게 난다"고 느꼈고, 3회 재시도 + 지수 백오프를 추가했습니다. 벤치마크도 좋았습니다(단일 Pod 기준). 메인테이너의 질문: "1,000개 Pod가 동시에 뜨는 스케일 아웃에서, 재고가 바닥난 상태라면 어떻게 되나요?" — 답은 EC2 API로의 **재시도 폭풍**이었습니다. 실제로 그 상황에서 필요한 것은 재시도가 아니라 빠른 실패(스케줄러가 다른 노드를 고르게)와 비동기 warm pool 보충이었고, 그것이 원래 설계였습니다. PR은 대신 **에러 메시지 개선과 메트릭 추가**로 축소되어 머지됐습니다 — 그리고 그 메트릭 덕에 여러 사용자가 자기 클러스터의 warm 설정을 고쳤습니다. 교훈: **"내 경우에 불편하다"에서 출발한 수정은, 1000배 스케일에서 검증받아야 합니다.** 그리고 가장 좋은 기여는 종종 코드가 아니라 **보이게 만드는 것**입니다.
