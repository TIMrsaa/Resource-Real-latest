# 흔한 함정 5선

## 1. 저장소를 틀리게 고름

consolidation 알고리즘 개선을 프로바이더에, spot 가격 캐시 수정을 코어에 — PR이 저장소를 옮겨 다니며 몇 주가 사라집니다. 판정 규칙 하나로 충분합니다: **"다른 클라우드에서도 의미가 있는가요?"** 애매하면 이슈에서 먼저 물어라("Should this live in core or the AWS provider?") — 30초의 질문이 3주를 아낍니다.

## 2. `replace` 지시자를 PR에 포함

로컬 코어를 가리키는 `go mod edit -replace sigs.k8s.io/karpenter=../core`는 개발엔 필수지만 PR에 섞이면 CI가 깨지거나(경로 없음) 최악의 경우 머지되어 릴리스를 망칩니다. 습관: PR 전 `git diff origin/main -- go.mod go.sum`을 **항상** 확인. pre-commit 훅으로 막아두면 더 좋습니다.

## 3. 두 컨트롤러 동시 실행

로컬에서 `go run ./cmd/controller`를 띄우면서 클러스터의 Karpenter Deployment를 안 껐습니다 — 두 프로세스가 같은 Pending Pod를 보고 각자 NodeClaim을 만들어 **노드가 두 배로** 생기고, 서로의 consolidation과 싸웁니다(그리고 청구서가 옵니다). 로컬 실행 전 `kubectl scale deploy/karpenter -n karpenter --replicas=0`은 체크리스트의 첫 줄.

## 4. 테스트 없는 버그픽스 PR

"고쳤습니다"만 있는 PR은 리뷰어에게 두 가지를 요구합니다 — 버그를 재현해보는 수고와, 회귀를 막을 방법에 대한 걱정. 그래서 대개 "테스트 추가해 주세요"로 되돌아옵니다. **버그픽스의 첫 커밋은 실패하는 테스트여야 합니다**(그 다음 커밋이 그것을 통과시킵니다). 이 순서가 리뷰 시간을 반으로 줄입니다.

## 5. e2e를 로컬에서 무심코 돌리기

`test/suites/`는 실제 AWS에 클러스터와 노드를 만듭니다 — `make e2etests`를 호기심에 돌리면 수십 달러와 정리되지 않은 리소스가 남습니다. e2e는 CI의 몫이고, 로컬 검증은 `make test`(단위·통합)로 충분합니다. 꼭 돌려야 한다면 전용 계정·리전에서, 그리고 실패 시 리소스 잔재를 직접 청소할 각오로(22의 고아 사냥 스크립트가 필요해집니다).

## 실무 사고 사례

> 한 기여자가 consolidation 개선 PR을 열었습니다 — spot 노드를 더 공격적으로 교체해 비용을 줄이는 변경이었고, 벤치마크로 12% 절감을 보였습니다. 메인테이너의 첫 코멘트는 "이 변경이 spot 중단율에 미치는 영향은 측정했나요?"였습니다. 실제로 그 알고리즘은 더 싼 spot을 찾아 교체를 반복하며 **중단 위험을 누적**시켰고, 이미 코어에 그것을 막는 휴리스틱(충분히 많은 저렴 타입이 있을 때만 spot→spot 교체 허용)이 있었습니다 — 기여자는 그 코드를 읽지 않고 우회해버린 것입니다. PR은 닫혔지만 스레드는 훌륭한 설계 문서가 됐고, 기여자는 반년 뒤 그 휴리스틱 자체를 개선하는 PR로 돌아와 머지됐습니다. 교훈: **기존 코드의 "이상해 보이는 조건문"은 대개 누군가의 사고 사례입니다** — 지우기 전에 git blame과 그 PR 스레드를 읽어라. 그리고 최적화 PR에는 개선 지표와 함께 **악화될 수 있는 지표**를 같이 제시하세요.
