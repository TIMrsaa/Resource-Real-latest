# 학습 가이드 — 사용자의 직관을 개발자의 지도로

## 왜 Karpenter가 첫 기여지로 좋은가

kubernetes/kubernetes는 거대하고(수백만 줄), 리뷰 대기열이 길고, SIG 정치가 있습니다(45에서 겪은 그대로). Karpenter는 다릅니다:

- **규모가 인간적**: 코어가 수만 줄 — 한 주면 전체 흐름을 읽을 수 있습니다
- **문제가 선명**: "Pending Pod → 노드"라는 단일 목적. 우리는 이미 17에서 그 동작을 사용자로 압니다
- **테스트가 빠릅니다**: fake client 기반 단위 테스트가 초 단위로 돕니다
- **좋은 첫 이슈가 실재**: `good-first-issue` 라벨이 관리됩니다
- **그리고 우리는 이 도구를 매일 씁니다** — 사용자의 통증이 곧 기여의 재료입니다(27의 결론)

## 두 저장소라는 첫 관문

```
kubernetes-sigs/karpenter        ← 코어(CNCF): 클라우드 중립 로직
  스케줄링 시뮬레이션, disruption(consolidation/drift), NodePool/NodeClaim API

aws/karpenter-provider-aws       ← AWS 프로바이더: 클라우드 고유
  인스턴스 타입 카탈로그·가격, EC2 Fleet 호출, EC2NodeClass, AMI 해석, IMDS/인터럽션
```

**판정 규칙**: "다른 클라우드에서도 의미가 있는가요?" → 예면 코어, 아니면 프로바이더. consolidation 알고리즘 개선은 코어, "spot 가격 캐시 갱신 주기"는 프로바이더. 이 판정을 틀리면 PR이 저장소를 옮겨 다니며 몇 주를 잃습니다.

코어는 프로바이더가 구현해야 할 **인터페이스**(CloudProvider)를 정의합니다 — 코어를 읽을 때 그 인터페이스를 먼저 보면 두 세계의 계약이 한눈에 들어옵니다.

## 학습 동선

theory에서 코드 지도와 기여 절차를 잡고 → lab-01에서 로컬 빌드 + 실제 클러스터를 상대로 컨트롤러를 돌려 **"왜 이 인스턴스 타입을 골랐는지"를 로그로 추적**하고 → lab-02에서 테스트를 먼저 쓰는 습관과 PR 워크플로를 익힙니다.

## 마음가짐

첫 PR의 목적은 코드가 아니라 **관계**입니다. 작게(문서 오타, 테스트 추가, 명확한 버그픽스), 정확하게(테스트 포함), 예의 바르게(리뷰는 선물입니다). 27의 사다리대로 — 신뢰가 쌓이면 더 큰 변경의 리뷰도 빨라집니다.
