# 학습 가이드 — 사용자에서 참여자로

## 이 트랙의 목적

이 커리큘럼의 종착지는 자격증이 아니라 **기여**입니다. k8s 파트의 41~45가 kubernetes/kubernetes로 가는 길을 열었다면, eks 파트의 27~29는 AWS 컨테이너 생태계로 가는 길입니다. 그리고 그 첫 관문은 코드가 아니라 **말**입니다 — 잘 쓴 이슈 하나가 잘못 쓴 PR 열 개보다 제품을 많이 바꿉니다.

## 경계를 알아야 문을 찾습니다

EKS 생태계는 세 구역으로 나뉩니다. 어디에 무엇을 제기하느냐가 반응 여부를 가릅니다:

| 구역 | 예 | 우리가 할 수 있는 것 |
|------|----|--------------------|
| **클로즈드 소스** | EKS control plane, Fargate, Auto Mode 내부 | containers-roadmap 이슈 / 서포트 케이스 |
| **AWS 오픈소스** | amazon-vpc-cni-k8s(07·16), aws-load-balancer-controller(08·14), EBS/EFS CSI(10), Karpenter provider(17) | **이슈 + PR** (29의 무대) |
| **CNCF/업스트림** | Karpenter 코어, Kubernetes 자체, Istio(20) | 이슈 + KEP + PR (28, k8s 43) |

흔한 실수: vpc-cni의 버그를 containers-roadmap에 올리고(그 저장소는 기능 로드맵용), 반대로 "Fargate에 DaemonSet 지원해달라"를 vpc-cni 저장소에 올립니다. 문을 틀리면 답이 안 옵니다.
