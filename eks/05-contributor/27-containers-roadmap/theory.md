# 이론 — 공개 로드맵의 해부와 설득의 구조

> **🌱 17세 눈높이 비유: 학교에 건의하기**
> 급식이 맘에 안 듭니다. 세 가지 방법이 있습니다:
> - **불평(교실에서)**: "급식 진짜 별로야" — 아무것도 안 바뀝니다
> - **건의함(로드맵 이슈)**: "월요일 국이 3주 연속 같은 메뉴입니다. 학생 87명 서명. 대안: 격주 로테이션" — 영양사가 읽고, 근거가 있으면 바뀝니다
> - **직접 요리(오픈소스 PR)**: 조리실이 개방된 반찬(vpc-cni 같은 오픈소스)은 내가 레시피를 고쳐 제출할 수 있습니다
> 그리고 중요한 것: **어느 문으로 가느냐**. 급식 문제를 도서관에 건의하면 답이 없습니다.

## 1. containers-roadmap의 구조

저장소: `aws/containers-roadmap` — 코드가 없는(!) 저장소, 이슈만 있습니다.

| 요소 | 의미 |
|------|------|
| **Shipped** | 출시됨 (닫힘) |
| **Coming Soon** | 개발 완료 단계, 곧 출시 |
| **We're Working On It** | 활발히 개발 중 |
| **Researching** | 조사·설계 단계 |
| **Just Shipped** | 최근 출시 알림 |
| 라벨 `EKS`, `Fargate`, `ECS`, `Karpenter` 등 | 서비스별 분류 |
| 👍 리액션 수 | **우선순위의 공개 신호** — 검색·정렬 기준 |

읽는 법: 이슈를 열기 전 **반드시 검색**(닫힌 이슈 포함). 대개 이미 있고, 그렇다면 새 이슈가 아니라 👍와 구체적 영향 댓글이 훨씬 가치 있습니다 — 신호를 분산시키는 중복 이슈는 오히려 해롭습니다.

## 2. 제출 문을 고르는 결정 트리

```
문제가 무엇인가요?
├ EKS CP/Fargate/Auto Mode의 동작·제약 (클로즈드)
│   ├ "이 기능이 없다" → containers-roadmap 이슈 (기능 요청)
│   └ "우리 클러스터가 이상하다" → AWS 서포트 케이스 (개별 사고)
├ 오픈소스 컴포넌트의 버그·기능 (vpc-cni, LB controller, CSI, karpenter-provider-aws)
│   → 해당 저장소의 이슈 → (가능하면) PR — 29의 무대
├ Kubernetes 자체 / Karpenter 코어 / CNCF 프로젝트
│   → 업스트림 이슈 → KEP/PR — 28, k8s 43~45
└ 문서가 틀렸다/부족합니다
    → 문서 저장소 PR (가장 쉬운 첫 기여! aws/aws-eks-best-practices 등)
```

**서포트 케이스와 이슈의 구분**: 케이스는 "내 클러스터의 문제"(비공개, SLA 있음), 이슈는 "제품의 문제"(공개, SLA 없음). 개별 장애를 로드맵에 올리면 답이 없고, 제품 결함을 케이스로만 올리면 다른 사용자에게 도움이 안 됩니다.

## 3. 좋은 이슈의 해부 — 5부 구조

```markdown
## 1. Community Note (템플릿 — 그대로 유지)
   👍 리액션 요청 / +1 댓글 자제 안내

## 2. Tell us about your request  ← 한 문장으로 "무엇을"
   "EKS 관리형 애드온의 configuration-values가 X를 지원하기를 원합니다."

## 3. Which service(s) is this request for?
   EKS / EKS Managed Add-ons  ← 라벨링을 도와줍니다

## 4. Tell us about the problem you're trying to solve.
   ★ 여기가 본체 ★ — 무엇을 하려다 무엇에 막혔나
   - 재현 절차 (명령어! 버전! 출력!)
   - 영향 정량화 ("노드 40% 증가", "월 $X", "배포마다 30초 5xx")
   - 시도한 우회책과 그 한계  ← "대안을 검토했다"는 신뢰의 증거

## 5. Are you currently working around this issue?
   현재의 우회책 (없으면 "없음 — 그래서 막혀 있습니다")

## 6. Additional context / Attachments
   로그, 매니페스트, 링크 (민감정보 제거!)
```

핵심 원칙 셋:

1. **문제를 요청하지 말고, 해결책을 요청하지도 말라 — 문제와 제약을 서술하세요.** "X API를 추가해주세요"보다 "우리는 Y를 하려는데 Z 때문에 불가능합니다. X면 될 것 같지만 다른 방법도 좋다"가 채택률이 높습니다 (제품팀은 더 나은 해법을 알 수 있습니다)
2. **재현 가능성이 신뢰를 만듭니다** — 버전·명령·출력이 있으면 담당 엔지니어가 30분 만에 확인합니다. 없으면 몇 주 왕복
3. **정량화가 우선순위를 만듭니다** — "불편하다"는 다른 이슈와 비교 불가능하지만 "월 $2,400"과 "노드 40% 증가"는 비교 가능합니다

## 4. 나쁜 이슈의 표본

| 안티패턴 | 왜 실패하나 |
|----------|------------|
| "IP 고갈이 짜증나요" | 재현·영향·맥락 없음 → 분류 불가 |
| "다른 클라우드는 되는데요" | 비교는 근거가 아닙니다 (그 자체로는) — 우리 워크로드의 요구를 서술하세요 |
| 개별 클러스터 장애를 로드맵에 | 문이 틀림 → 서포트 케이스로 |
| 중복 이슈 개설 | 👍 신호가 분산되어 **우선순위가 낮아집니다** |
| 민감정보 첨부(계정 ID, ARN, IP) | 공개 저장소입니다 — 마스킹은 필수 |

## 5. 기여의 사다리

```
0층  읽기: 로드맵·릴리스 노트·EKS Best Practices를 정기 구독 (맥락이 발언권입니다)
1층  피드백: 👍 + 구체적 영향 댓글 → 좋은 이슈 개설
2층  문서: 오탈자·부정확·누락 PR (aws-eks-best-practices, 각 컴포넌트 docs/)
      ← 가장 저평가된 첫 기여. 리뷰어와의 첫 신뢰 관계가 여기서 생깁니다
3층  코드: 오픈소스 컴포넌트의 버그픽스 → 기능 (29)
4층  설계: 업스트림 KEP/디자인 문서 (28, k8s 43)
```

각 층은 다음 층의 사회적 자본이 됩니다 — 이슈에서 좋은 논증을 남긴 사람의 PR은 더 빨리 읽힙니다.

| 질문 | 답 |
|------|----|
| 세 구역? | 클로즈드(로드맵/케이스) · AWS 오픈소스(이슈+PR) · 업스트림(KEP+PR) |
| +1의 올바른 형태? | 👍 리액션 + **구체적 영향 정량화** 댓글 |

| 이슈 전 필수 행동? | 검색 (닫힌 이슈 포함) — 중복은 신호를 분산시킵니다 |
| 케이스 vs 이슈? | 내 클러스터의 문제 vs 제품의 문제 |
| 가장 저평가된 첫 기여? | **문서 PR** — 신뢰 관계의 시작 |
