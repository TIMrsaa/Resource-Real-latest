# 학습 가이드 — "Pod의 신분증" 문제

## 문제 설정부터

Pod가 S3를 읽어야 합니다. 가장 게으른 답: **노드의 IAM 역할에 S3 권한 추가** — 그러면 그 노드의 **모든 Pod**이 S3를 읽습니다. 침해당한 어떤 Pod 하나가 노드 자격증명(IMDS)으로 클러스터의 모든 AWS 권한을 갖는 구조 — k8s 32에서 막던 "탈출 후 신분 도용"의 EKS판입니다.

요구사항은 명확합니다: **Pod(정확히는 ServiceAccount) 단위의 AWS 신분증.** 그 답이 두 세대로 진화했습니다:

```
0세대: 노드 역할 공유          — 금지 (위 문제)
0.5세대: 키를 Secret에         — 금지 (장수 자격증명, 회전 지옥 — k8s 07 pitfall)
1세대: IRSA (2019~)           — SA 토큰을 OIDC 연합으로 STS와 교환. 견고하지만 배선 복잡
2세대: Pod Identity (2023~)   — EKS 전용 단순화. 신규의 기본 후보
```

## 왜 둘 다 배우나

- 기존 환경의 대부분이 IRSA — 운영/디버깅하려면 내부를 알아야 합니다
- IRSA는 **EKS 밖에서도 통하는 일반 원리**(OIDC 연합)입니다 — GitHub Actions→AWS(cicd 파트), GCP↔AWS 등 같은 패턴이 도처에 재등장
- Pod Identity의 "무엇이 단순해졌는지"는 IRSA의 복잡함을 알아야 보입니다

## k8s 11과의 연결이 핵심

IRSA의 재료는 k8s 11에서 배운 **ServiceAccount 토큰(projected, audience 지정)** 그 자체입니다 — "K8s가 발급한 신분증을 AWS가 검증하게 만드는" 다리가 OIDC. k8s 파트의 토큰 이야기가 클라우드 권한의 근간이 되는 순간을 즐기자.
