# 학습 가이드 — EKS 네트워킹은 "IP 재고 관리업"입니다

## 왜 IP가 EKS의 아킬레스건인가

k8s 27에서 본 대로, VPC CNI는 오버레이 없이 **Pod에 진짜 VPC IP**를 줍니다 — 성능/단순성의 대가로 두 가지 유한 자원에 묶입니다:

```
① 서브넷의 IP 총량        (CIDR 설계 — 클러스터 생성 때 정해진 운명)
② 인스턴스의 ENI×IP 한도   (타입마다 고정 — "노드당 Pod 수"의 천장)
```

①이 마르면 "노드는 여유로운데 Pod가 안 뜨고"(스케일아웃 불능), ②가 작으면 "CPU는 노는데 노드를 추가"(비용 낭비)가 됩니다. **EKS 용량 계획 = IP 재고 계획**이라는 감각이 이 모듈의 목표.

## 미리 보는 처방전

| 증상 | 처방 | 모듈 |
|------|------|------|
| 노드당 Pod 수가 적습니다 | **prefix delegation** (×16) | 이 모듈 lab-02 |
| 서브넷이 좁습니다 | secondary CIDR / custom networking | 16 |
| 근본적으로 | IPv6 클러스터 | 16 |
| Pod별 방화벽 요구 | SG-for-Pod (비용: ENI 소비↑) | 이 모듈 §4 |

## 관측이 절반

이 모듈에서 ipamd(IP 관리 데몬)의 로그와 메트릭을 읽는 법을 익힙니다 — "IP가 몇 개 남았지?"를 **장애 전에** 묻는 도구입니다. eks 26(트러블슈팅)의 1번 시나리오가 IP 고갈인 이유는, 대부분의 팀이 이 관측을 안 하기 때문입니다.

## k8s 파트 역참조

- veth/라우팅의 패킷 레벨: k8s 27 (여기선 반복 안 함 — IP 할당 경제학에 집중)
- maxPods가 kubelet 설정인 것: k8s 26 + eks 05의 nodeadm
