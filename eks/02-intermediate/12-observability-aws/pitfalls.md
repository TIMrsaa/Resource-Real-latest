# 흔한 함정 5선

## 1. 보존 정책 미설정 — 무기한이 기본값

CloudWatch 로그 그룹의 retention 기본은 **Never expire**입니다. Container Insights를 켠 날부터 로그가 영원히 쌓이고, 청구서에는 "왜인지 모르게 커지는" 저장 비용으로 나타납니다. 애드온 설치와 retention 설정(lab-02 Step 4)은 한 세트 — 설치 runbook에 묶어라.

## 2. 디버그 로그를 켠 채 전면 수집

개발 중 `LOG_LEVEL=debug`를 올려두고 잊으면, 수집(GB) 과금이 워크로드 비용을 추월하는 사고가 실제로 납니다 — 저장이 아니라 **수집**이 비싼 구조라서 지우는 걸로는 늦습니다. 방어: IncomingBytes 알람(lab-02 Step 6)으로 급증을 조기 포착 + 시끄러운 워크로드는 exclude/필터.

## 3. 권한 없이 설치하고 "로그가 안 와요"

애드온은 ACTIVE인데 로그 그룹이 안 생긴다면 십중팔구 권한 — agent/fluent-bit이 CloudWatch에 **쓸** 자격(CloudWatchAgentServerPolicy)이 없는 것입니다. 진단 순서는 09에서 배운 그대로: Pod 로그에 AccessDenied 확인 → SA에 Pod Identity association이 있나 → 역할에 정책이 붙어 있나. "애드온 상태"와 "권한"은 별개 축입니다(11의 health.issues에도 안 뜰 수 있습니다).

## 4. "로그는 오는데 메트릭이 안 보여요"

Container Insights 메트릭은 API 호출이 아니라 **EMF 로그(/performance)를 경유**해 만들어집니다(theory §4). 그러니 진단도 그 길을 따라: /performance 로그 그룹에 EMF JSON이 오는가 → 온다면 콘솔의 리전/네임스페이스(ContainerInsights) 확인 → 안 온다면 cloudwatch-agent DS의 헬스/권한. 구조를 모르면 이 증상 앞에서 막힙니다.

## 5. 알람 없는 대시보드 — 사람이 상주해야 하는 관측성

대시보드를 아무리 잘 만들어도 사람이 안 보는 새벽에는 장님입니다. 반대로 알람만 수십 개 걸어 매일 울리면 전부 무시됩니다(알람 피로). 규율: **사람이 행동할 수 있는 조건에만 알람**(임계값·기간을 실측 기반으로), 나머지는 대시보드로. lab-02 Step 7의 최소 세트에서 시작해 실제 장애마다 하나씩 다듬는 것이 정석.

## 실무 사고 사례

> 트래픽 급증 조사를 위해 한 팀이 전 서비스의 로그 레벨을 debug로 올렸습니다 — 조사는 이틀 만에 끝났지만 롤백을 잊었습니다. 3주 뒤 재무팀이 물었습니다: "CloudWatch가 EC2보다 비싼 게 정상인가요?" 수집량이 평소의 40배로 뛰어 있었고, 보존은 무기한이라 저장 비용까지 복리로 붙는 중이었습니다. 조치: ① 로그 레벨 원복 + retention 14일 일괄 적용 ② IncomingBytes 알람(시간당 임계) 신설 ③ "debug는 PR로만, 만료일 명시" 규약. 흥미로운 뒷이야기 — 이 팀이 알람을 만들 때 참고한 것은 자기들의 **워크로드** 대시보드가 아니라 **청구서**였습니다. 관측성 스택 자체가 관측 대상이라는 것(lab-02 Step 6)을 청구서로 배운 셈입니다.
