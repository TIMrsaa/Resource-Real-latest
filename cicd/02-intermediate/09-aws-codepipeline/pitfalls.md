# 흔한 함정 5선

## 1. CodeCommit 자료를 그대로 따라 하기

인터넷의 많은 Code 시리즈 튜토리얼은 소스가 CodeCommit입니다 — 그런데 CodeCommit은 신규 가입이 닫혔습니다(루트 버전표). 지금의 표준은 GitHub + CodeStar Connection이고, Connection은 콘솔에서 한 번 OAuth 승인을 거쳐야 AVAILABLE이 됩니다(자동화만으로는 PENDING에 머뭅니다). 옛 자료의 소스 스테이지 설정은 이 지점에서 낡았으니 provider를 `CodeStarSourceConnection`으로 읽어야 합니다.

## 2. 아티팩트 버킷을 암호화하지 않기

파이프라인의 S3 아티팩트 버킷에는 **소스 코드 전체와 빌드 산출물**이 담깁니다 — 시크릿이 코드에 섞여 있거나 빌드 로그가 아티팩트에 들어가면 그대로입니다. KMS 암호화(가능하면 고객 관리 키)와 버킷 정책(파이프라인·액션 역할만 접근)은 선택이 아닙니다. 그리고 이 버킷은 퍼블릭 액세스 차단을 반드시 확인 — eks 25의 시크릿 관문이 CI 인프라에도 적용됩니다.

## 3. 파이프라인 역할에 모든 권한 몰아주기

"복잡하니 파이프라인 역할 하나에 다 넣자"로 `PowerUserAccess`를 붙이면 — Code 시리즈의 유일한 강점(스테이지별 IAM 경계)을 버리는 것입니다. 파이프라인 역할은 오케스트레이션(S3, 액션 호출)만, 각 액션(CodeBuild, 배포)은 자기 역할로 자기 일만. 빌드가 탈취돼도 배포 권한이 없어야 합니다(lab-02 Step 3). 역할이 여러 개인 것은 버그가 아니라 기능입니다.

## 4. 파이프라인을 콘솔로 만들고 방치

콘솔 클릭으로 만든 파이프라인은 재현·버전관리·리뷰가 안 됩니다 — 누가 언제 스테이지를 바꿨는지 모르고, DR(eks 24) 때 재건할 선언이 없습니다. 프로덕션 파이프라인은 CloudFormation/CDK/Terraform으로, 그리고 CDK Pipelines의 self-mutating 패턴이면 "파이프라인 변경도 파이프라인을 거친다". eks 23의 "선언이 진실"이 CI/CD 자체에도 적용됩니다.

## 5. "AWS니까 무조건 Code 시리즈" (또는 그 반대)

도구를 이념으로 고르는 실수. "우리는 AWS 샵이니 CodePipeline"이라며 개발자가 매일 보는 PR에서 CI 피드백이 멀어지거나, 반대로 "요즘은 다 Actions"라며 규제가 요구하는 CloudTrail 기반 배포 감사를 포기합니다. 기준은 이념이 아니라 다섯 질문(lab-02 Step 5): 배포 대상, 감사 요구, 승인 주체, IAM 경계 필요성, 멀티클라우드 계획. 대부분의 답은 **혼용**입니다.

## 실무 사고 사례

> 규제 산업의 한 팀이 "개발 속도"를 이유로 CI/CD를 전부 GitHub Actions로 옮겼습니다 — CodePipeline의 승인 게이트와 CloudTrail 감사를 버리고. 6개월 뒤 규제 감사에서 문제가 됐습니다: "프로덕션 배포를 누가 승인했고, 그 시점에 무엇이 배포됐는지"를 증명하라는 요구에, Actions 로그는 90일 후 사라졌고 environment 승인 기록도 저장소 삭제 시 함께 사라지는 구조였습니다. 그들은 급히 CloudTrail 중심 감사가 되는 CodePipeline으로 프로덕션 CD만 되돌렸습니다 — 그런데 이번엔 개발자들이 두 시스템을 오가며 혼란스러워했습니다. 결국 안착한 형태가 처음 고민했어야 할 답이었습니다: CI와 dev/staging 배포는 Actions(속도), 프로덕션 배포만 CodePipeline(감사·승인), 둘을 Actions가 CodePipeline을 트리거하는 방식으로 연결. 교훈: **도구 선택은 되돌릴 수 있지만 그 비용은 실재합니다** — "무엇이 트렌디한가"가 아니라 "우리의 제약(이 경우 규제 감사)이 무엇을 요구하는가"를 먼저 물었어야 했습니다.
