# 학습 가이드 — 자유를 얻고 책임을 집니다

## GitHub-hosted 러너가 공짜로 주던 것

03에서 우리는 "러너는 잡마다 새 VM"이라는 사실을 재현성의 기반이라고 배웠습니다. 그 한 문장 안에 여러 보장이 접혀 있습니다:

- **격리**: 이전 잡의 파일·프로세스·환경변수가 남지 않습니다
- **깨끗한 상태**: 설치된 툴이 예측 가능합니다
- **신뢰 경계**: 러너가 우리 네트워크 안에 없습니다
- **운영 부담 0**: 패치·용량·장애가 GitHub의 일

self-hosted로 옮기면 이 넷이 전부 **우리 책임**이 됩니다. 그러니 옮길 이유가 분명해야 합니다.

## 정당한 네 가지 이유

| 이유 | 예 |
|------|----|
| **네트워크 접근** | VPC 안의 RDS/내부 API에 붙는 통합 테스트, 프라이빗 EKS 엔드포인트 |
| **하드웨어** | 대용량 빌드(32vCPU), GPU 테스트, ARM 네이티브 빌드(eks 19) |
| **비용** | 대규모 매트릭스가 분당 과금을 압도할 때 (스팟 노드 + Karpenter) |
| **규제** | 코드가 특정 계정·리전을 벗어나면 안 될 때 |

"조금 빠를 것 같아서"는 이유가 아닙니다 — 캐시 설계(04)를 먼저 보라.

## ARC를 쓰는 이유: 러너를 Pod로

self-hosted를 EC2에 직접 설치하면 그 인스턴스는 **오래 사는 러너**가 되고, 잡들이 같은 디스크를 공유합니다. 앞 잡이 심은 파일·설치한 패키지·남긴 자격증명이 다음 잡에 보입니다 — 재현성도 격리도 무너집니다.

ARC(Actions Runner Controller)는 러너를 **Pod로, 잡 하나마다 새로** 만듭니다:

```
잡 대기 → ARC가 러너 Pod 생성 → 잡 실행 → Pod 파괴
```

이것이 **ephemeral 러너**이고, GitHub-hosted의 격리 보장을 EKS 위에서 되찾는 방법입니다. 그리고 Pod니까 Karpenter(eks 17)가 노드를 만들고 consolidation으로 회수합니다 — CI 용량이 수요에 따라 자랍니다.

## 반드시 기억할 하나

> **퍼블릭 저장소에 self-hosted 러너를 붙이지 마세요.**

포크 PR의 워크플로가 우리 VPC 안의 러너에서 실행됩니다 — 03의 인젝션 사고가 이번엔 프로덕션 네트워크 안에서 일어납니다. GitHub 문서도 이것을 명시적으로 경고합니다. theory §5에서 그 이유를 해부합니다.
