# 학습 가이드 — 저장하지 않은 비밀은 유출되지 않습니다

## 장기 키의 세 가지 죄

CI 시크릿에 든 `AKIA...` 키가 나쁜 이유는 "보안 모범 사례"라서가 아닙니다. 구체적입니다:

1. **유출되면 회전 외에 방법이 없습니다** — 누가 언제 복사했는지 알 수 없고, 유효기간이 없습니다
2. **로그·서브프로세스·악성 액션으로 샙니다** — 03의 사고 사례가 정확히 이것이었습니다(마스킹은 인코딩으로 우회됩니다)
3. **범위를 좁히기 어렵습니다** — "이 저장소의 main 브랜치에서만"을 IAM 키로는 표현할 수 없습니다

OIDC는 셋을 한 번에 해결합니다: 토큰은 **몇 분짜리**이고, 저장되지 않으며(요청 시 발급), 신뢰 정책에 **"어느 저장소의 어느 브랜치인지"를 조건으로 쓸 수 있습니다.**

## 이미 아는 원리입니다

eks 09에서 IRSA를 배웠습니다:

```
Pod → SA 토큰(OIDC, 단명) → STS AssumeRoleWithWebIdentity → 임시 자격증명
```

여기서 Pod를 워크플로로, 클러스터의 OIDC 발급자를 GitHub의 발급자로 바꾸면 그대로입니다:

```
워크플로 → OIDC 토큰(단명) → STS AssumeRoleWithWebIdentity → 임시 자격증명
```

**같은 메커니즘의 다른 소비자.** 그래서 이 모듈은 새 개념이 아니라 익숙한 원리의 확장이고, 헷갈리는 지점도 같습니다: **신뢰 정책의 조건을 얼마나 좁힐 것인가.**

## 이 모듈의 위험 지점

OIDC를 켜는 것은 쉽습니다(액션 두 줄). 어려운 것은 신뢰 정책입니다:

```json
"token.actions.githubusercontent.com:sub": "repo:my-org/*:*"
```

이 한 줄이면 — 조직의 **어떤 저장소, 어떤 브랜치, 어떤 PR**에서든 그 역할을 얻습니다. 포크 PR의 워크플로도, 인턴이 만든 테스트 저장소도. lab-02에서 이 구멍을 직접 열어보고 닫습니다.
