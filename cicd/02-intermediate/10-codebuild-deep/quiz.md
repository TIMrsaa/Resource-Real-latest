# 자가 점검 퀴즈

**Q1.** buildspec의 네 페이즈를 순서대로 쓰고, `finally`가 대응하는 GitHub Actions 개념은?

**Q2.** 페이즈가 실패하면 이후 페이즈는 어떻게 되는가요? `finally`는?

**Q3.** CodeBuild 캐시 3종을 안정성 기준으로 비교하고, 04의 어떤 원리가 여전히 적용되는가요?

**Q4.** 로컬 캐시가 "항상 빠르지 않은" 이유를 03의 개념으로 설명하세요.

**Q5.** VPC 빌드가 얻는 것과 그 대가 두 가지는? 대가를 완화하는 방법은?

**Q6.** CodeBuild의 권한 획득 방식은 GitHub Actions(07)와 어떻게 다른가?

**Q7.** CodeBuild 역할로 EKS에 배포하려면 어떤 매핑이 필요한가? (eks·k8s 파트의 개념으로)

**Q8.** `privilegedMode: true`가 필요한 경우와, 그것이 안는 위험, 그리고 신뢰할 수 없는 소스에 대한 대응은?

---

## 정답

**A1.** install → pre_build → build → post_build. `finally`(각 페이즈의)는 성공/실패 무관하게 실행되므로 Actions의 **`if: always()`** 에 대응합니다(정리·리포트 업로드).

**A2.** 한 페이즈가 실패하면 **다음 페이즈로 넘어가지 않습니다**(`on-failure: ABORT` 기본). 단 그 페이즈의 `finally` 블록은 실행됩니다 — 실패한 페이즈 이후의 페이즈들은 시작조차 안 되지만, 실패한 페이즈 자체의 정리는 보장됩니다.

**A3.** 로컬(호스트 재사용에 의존 — 불안정) < S3(명시적·안정, 다운로드 시간) / 커스텀 cache.paths(의존성 디렉터리를 S3로). 여전히 적용되는 04의 원리: **레이어/의존성 캐시가 히트하려면 변경 빈도 낮은 것부터**, 그리고 Docker 빌드는 BuildKit + ECR 레지스트리 캐시가 최선.

**A4.** 로컬 캐시는 **빌드 호스트가 재사용될 때만** 히트합니다 — CodeBuild가 새 호스트를 배정하면 캐시가 없습니다(03의 "러너는 잡마다 새 VM이라 캐시가 자동으로 안 남는다"와 같은 문제). 그래서 "운이 좋으면 빠름"이고 재현 가능한 캐시는 S3/레지스트리입니다.

**A5.** 얻는 것: 프라이빗 VPC 리소스(RDS/ElastiCache/내부 API) 접근. 대가: ① 빌드마다 ENI가 서브넷 IP를 소비(eks 16) ② 외부 접근이 NAT GW 처리 요금을 냄(eks 22 숨은 3대장). 완화: ECR/S3/logs용 VPC 엔드포인트로 NAT 우회, VPC가 정말 필요한 빌드만 분리.

**A6.** GitHub Actions는 워크플로가 OIDC로 역할을 **assume**합니다(단명, sub 조건). CodeBuild는 프로젝트에 붙은 **서비스 역할**로 실행됩니다(eks의 Pod Identity와 유사) — 그 역할이 곧 빌드의 고정 권한 경계입니다.

**A7.** ① CodeBuild 서비스 역할을 클러스터의 **access entry**에 매핑(eks 02)하여 kubernetes 그룹 부여 ② 그 그룹에 **RBAC Role/RoleBinding**(k8s 11)으로 배포 권한(예: 특정 ns의 deployments). 그러면 빌드의 kubectl/helm이 그 권한으로 동작합니다.

**A8.** Docker 데몬(이미지 빌드)에 필요. 위험: 08의 dind와 같이 privileged 컨테이너에서 임의 코드 실행 — 탈취 시 위험이 큽니다(관리형이라 노드 탈출은 AWS가 격리하지만 빌드 환경 내 권한은 열림). 신뢰할 수 없는 소스(포크 PR, 오픈소스)는 이 프로젝트로 빌드하지 말고 GitHub-hosted 러너 등 별도 격리를, 또는 rootless 빌드를 씁니다.
