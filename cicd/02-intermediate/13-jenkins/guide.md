# 학습 가이드 — 오래됨을 경멸하지 말고 이해하세요

## "레거시"라는 편견을 먼저 내려놓기

Jenkins를 "낡은 것"으로 치부하고 넘어가면 두 가지를 놓칩니다:

1. **현실**: 지금 이 순간에도 수많은 조직의 프로덕션 배포가 Jenkins를 거칩니다. 실무에서 Jenkins를 만날 확률은 매우 높고, "마이그레이션 프로젝트"의 대상으로 만날 확률은 더 높습니다
2. **교훈**: Jenkins가 왜 그렇게 오래 살아남았는지 — 플러그인으로 무엇이든 되고, 온프레에서 완전히 통제되며, 특정 벤더에 종속되지 않는다는 점 — 은 도구 선택의 중요한 축을 가르칩니다

이 모듈은 Jenkins를 미화하지도 폄하하지도 않습니다. **왜 살아남았고, 무엇이 부채이며, 언제 떠나야 하는가**를 판단하는 능력이 목표입니다.

## 이식성의 마지막 확인

12에서 "개념은 이식된다"를 배웠습니다. Jenkins는 그 이식성의 극한 시험입니다 — 문법이 가장 다르고(Groovy 기반), 개념도 오래됐습니다. 그럼에도:

```
Jenkins stage    = Actions job / GitLab stage
Jenkins agent    = Actions runner / GitLab runner
Jenkins archive  = artifacts
Jenkins credentials = secrets
Jenkins Shared Library = reusable workflow (06)
```

Jenkinsfile을 앞의 지식으로 읽어내면, "어떤 CI든 하루면 읽는다"(12)가 진짜임을 확인하게 됩니다.

## Jenkins만의 두 가지 특징

1. **플러그인 생태계**: 1,800개 이상의 플러그인 — 어떤 도구·클라우드·프로토콜과도 연결됩니다. 이것이 힘이자 **공급망 위험**(21)이고 **유지보수 부채**(플러그인 버전 지옥)입니다
2. **Controller/Agent 아키텍처**: 중앙 controller가 상태를 갖고 agent에 잡을 분산. 이 상태성이 GitHub Actions의 무상태 모델(03)과 대조되며, HA·백업·업그레이드를 우리 책임으로 만듭니다

## 마이그레이션이라는 현실

이 파트의 독자가 Jenkins를 만나는 가장 흔한 시나리오는 **"레거시 Jenkins를 현대 CI로 옮기는 것"**입니다. lab-02는 그 판단(옮길 가치가 있는가)과 전략(어떻게 점진적으로)을 다룹니다 — eks 23의 kubefed 교훈, 02의 브랜치 바이 앱스트랙션이 여기서 마이그레이션 전략으로 재등장합니다.
