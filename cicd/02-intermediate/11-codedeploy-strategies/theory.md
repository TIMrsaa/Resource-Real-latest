# 이론 — 트래픽 전환의 메커니즘, 롤백의 조건, 마이그레이션의 예외

> **🌱 17세 눈높이 비유: 새 다리로 차량 옮기기**
> 강에 새 다리(신버전)를 놓고 옛 다리(구버전)의 차량을 옮깁니다:
> - **재생성** = 옛 다리를 폭파하고 새 다리 개통 — 그 사이 강을 못 건넙니다(다운타임)
> - **롤링** = 차선을 하나씩 새 다리로 — 부드럽지만 결국 전 차선이 새 다리로 갑니다(나쁜 다리여도)
> - **블루/그린** = 새 다리를 완공해두고 어느 순간 **전체 차량을 한 번에** 새 다리로. 문제 생기면 다시 옛 다리로(스위치 반전)
> - **카나리** = 차량 5%만 새 다리로 보내고 **무너지나 지켜봅니다** → 괜찮으면 25%, 50%, 100%
> - **자동 롤백** = 새 다리에 센서(알람)를 달아, 흔들림이 감지되면 자동으로 차량을 옛 다리로 되돌립니다
> - **DB 마이그레이션** = 다리가 아니라 **강의 방향을 바꾸는 것** — 한번 바꾸면 5%만 되돌릴 수 없습니다

---

## 1. 트래픽 전환 = 배포 전략의 본질

모든 전략은 "라우팅 대상의 가중치를 바꾸는 것"으로 환원됩니다:

```
구버전 100% / 신버전 0%
  → (재생성) 구 0 신 100 (다운타임 사이)
  → (롤링)   구 80/신 20 → 60/40 → ... → 0/100 (Pod 단위)
  → (블루/그린) 구 100/신 0 → [스위치] → 구 0/신 100
  → (카나리) 구 95/신 5 → [관찰] → 90/10 → [관찰] → 0/100
```

전환의 **손잡이**가 어디 있느냐가 구현을 정합니다:

| 전환 손잡이 | 구현 |
|-----------|------|
| ALB 타깃 그룹 가중치 | eks 14, CodeDeploy(ECS) |
| Lambda 별칭 가중치 | CodeDeploy(Lambda) |
| 메시 VirtualService 가중치 | eks 20 (Istio) |
| ReplicaSet replica 수 | k8s 롤링(Deployment) |
| Service selector 전환 | k8s 블루/그린(수동) |

## 2. CodeDeploy 배포 구성

```
대상: ECS / Lambda / EC2·온프레
배포 구성(traffic shifting):
  - AllAtOnce         : 즉시 100% (블루/그린의 스위치)
  - Canary10Percent5Minutes : 10% → 5분 대기 → 90%
  - Linear10PercentEvery1Minute : 10%씩 매분
  - 커스텀 구성 가능
```

CodeDeploy의 강점:

- **자동 롤백**: CloudWatch 알람이 울리면 트래픽을 구버전으로 즉시 되돌림
- **훅(lifecycle hooks)**: `BeforeAllowTraffic`(신버전 검증), `AfterAllowTraffic`(사후 확인) — Lambda로 스모크 테스트
- **ECS 블루/그린**: 새 태스크셋을 띄우고 ALB 리스너를 전환, 실패 시 구 태스크셋 유지

## 3. 자동 롤백의 조건 — 관찰이 전부

자동 롤백은 마법이 아닙니다. **무엇을 보고 되돌릴지**가 정의돼야 합니다:

```
트리거 후보:
  - CloudWatch 알람: 5xx율, p99 지연(eks 13·14), 커스텀 메트릭(eks 15)
  - 배포 실패: 헬스체크 미통과, 태스크 기동 실패
  - 훅 실패: BeforeAllowTraffic 스모크 테스트 실패
```

핵심 원칙(01의 반복): **관찰 지표 없는 카나리는 그냥 느린 배포입니다.** 5%로 내보내도 그 5%의 오류율을 보지 않으면 아무것도 관찰하지 않은 것입니다. 그래서 이 모듈의 진짜 선행 학습은 관측성(eks 12)과 SLI(eks 13)입니다.

### 롤백의 속도 계층

```
빠름:  가중치 0으로 (카나리·메시) — 초 단위, 이미 뜬 구버전으로
빠름:  블루/그린 스위치 반전 — 초 단위, 구 환경이 살아 있으니
느림:  롤링을 이전 이미지로 재롤링 — 분 단위, 다시 교체해야
불가:  DB 스키마 (§5)
```

## 4. k8s에서의 대응 (17의 예고)

| 전략 | k8s 네이티브 | 한계 | 17에서 |
|------|------------|------|--------|
| 롤링 | Deployment(기본) | 관찰 후 확대 아님 | — |
| 블루/그린 | Service selector 수동 전환 | 자동화 없음 | Argo Rollouts |
| 카나리 | (네이티브 없음) | 수동 replica 조작은 조잡 | **Rollouts/Flagger** |

k8s Deployment의 롤링은 "느린 전면 배포"의 전형 — maxSurge/maxUnavailable로 속도만 조절할 뿐 **메트릭 기반 게이트가 없습니다**. 진짜 카나리(관찰 후 자동 확대)는 17의 Argo Rollouts/Flagger가 메트릭 분석 + 트래픽 분할(eks 14/20)을 결합해 제공합니다. 이 모듈은 그 필요성을 CodeDeploy로 먼저 체감하고, 17에서 k8s 네이티브로 완성합니다.

## 5. DB 마이그레이션 — 모든 전략의 예외

코드는 되돌릴 수 있지만 **적용된 스키마 변경은 되돌릴 수 없습니다**(또는 데이터 손실). 카나리가 무의미해지는 지점:

```
❌ 순진한 배포: 코드 v2(새 컬럼 필요) + 마이그레이션을 동시에
   → 카나리 5%가 새 컬럼을 쓰는데, 롤백하면 구버전 95%는? 스키마는 이미 바뀜
```

해법: **expand-contract (parallel change)** — 스키마 변경과 코드 배포를 분리하고 각각 하위 호환으로:

```
1. Expand:   새 컬럼 추가 (구버전도 무시하고 잘 돎 — 하위 호환)
2. Migrate:  코드 v2 배포 (새 컬럼 씀, 구 컬럼도 여전히 읽음)
3. (관찰·안정화)
4. Contract: 구 컬럼 제거 (v2만 남고, 아무도 구 컬럼 안 씀)
```

각 단계가 **독립적으로 롤백 가능**합니다 — 어느 시점에 멈춰도 시스템이 동작합니다. 이것이 배포 전략과 데이터 변경을 화해시키는 유일한 방법이며, 02의 "브랜치 바이 앱스트랙션"과 같은 사상(큰 변경을 안전한 작은 단계로)입니다.
