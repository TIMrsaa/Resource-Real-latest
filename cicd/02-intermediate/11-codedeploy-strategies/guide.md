# 학습 가이드 — 배포는 "옮기기"이고, 안전은 "관찰"입니다

## 01의 약속을 지키는 모듈

01에서 우리는 배포 전략을 표로 봤고, "롤링은 안전장치가 아니라 느린 전면 배포"라고 했습니다. 그 문장의 진짜 의미가 이 모듈에서 드러납니다: **모든 배포 전략의 본질은 "트래픽을 구버전에서 신버전으로 어떻게 옮기는가"** 이고, 안전한 전략은 옮기는 도중에 **관찰하고 멈출 수 있는** 것입니다.

```
재생성:   전부 죽이고 전부 새로       — 관찰 불가, 다운타임
롤링:     조금씩 교체                 — 관찰 가능하나 결국 100%
블루/그린: 통째로 준비 후 스위치       — 스위치 순간 100%, 롤백은 즉시
카나리:   조금 옮기고 → 관찰 → 확대   — ★ 관찰이 게이트가 됩니다
```

카나리만이 "관찰 후 확대"를 구조에 담습니다. 그리고 관찰이 게이트가 되려면 **무엇을 관찰할지**(오류율·지연 SLI — eks 13에서 잰 그 지표)가 먼저 정의돼야 합니다. 지표 없는 카나리는 그냥 느린 배포입니다.

## AWS와 k8s의 두 세계

이 모듈은 두 구현을 나란히 봅니다:

| | AWS 네이티브 | Kubernetes |
|---|---|---|
| 도구 | CodeDeploy | Deployment 전략 / (17) Argo Rollouts |
| 트래픽 전환 | ALB 가중치·Lambda 별칭·ECS | Service·ALB(eks 14)·메시(eks 20) |
| 롤백 | 알람 트리거 | 이전 ReplicaSet / Rollouts |

CodeDeploy는 ECS·Lambda·EC2에 강하고, EKS Pod 배포는 k8s 네이티브(그리고 17의 Rollouts)가 자연스럽습니다. 둘의 공통 원리를 배우면 어느 쪽이든 조립할 수 있습니다.

## 이 모듈이 못 다루는 것

DB 스키마 변경은 **롤백이 안 됩니다** — 이것이 모든 배포 전략의 예외입니다. 카나리로 코드를 5%만 내보내도, 그 코드가 요구하는 새 컬럼이 없으면 5%가 깨집니다. lab-02에서 expand-contract 패턴으로 이 문제를 다루지만, 완전한 데이터 마이그레이션 전략은 데이터 엔지니어링의 영역입니다. 우리의 몫은 "코드 배포와 스키마 변경의 리스크는 다른 종류"임을 아는 것.
