# 흔한 함정 5선

## 1. 지표 없는 카나리

"카나리 배포 도입했어요 — 10%씩 올려요." 그런데 각 단계에서 **무엇을 보고** 다음으로 갈지 안 정했다면, 그것은 카나리가 아니라 느린 전면 배포입니다(01). 나쁜 버전은 10%든 100%든 결국 나갑니다. 카나리의 안전은 트래픽 비율이 아니라 **관찰 게이트**에서 옵니다 — 오류율·지연 SLI(eks 13)를 정의하고, 그것이 임계를 넘으면 자동으로 멈추게 하세요. 관측성(eks 12)이 배포 전략의 선행 조건입니다.

## 2. 자동 롤백을 알람 없이 켜기

CodeDeploy의 `autoRollbackConfiguration`을 `DEPLOYMENT_FAILURE`만으로 켜면 — 태스크 기동 실패 같은 명백한 것만 잡습니다. 정작 "기동은 됐는데 5xx를 뱉는" 나쁜 배포는 통과합니다(배포는 성공했으니까). 진짜 방어는 `DEPLOYMENT_STOP_ON_ALARM` + 실제 SLI 알람입니다. 그리고 그 알람은 배포 전에 존재해야 합니다 — 배포하면서 만드는 알람은 첫 사고를 못 막습니다.

## 3. DB 스키마 변경을 코드 배포와 한 묶음으로

가장 위험한 함정. `ALTER TABLE ADD COLUMN NOT NULL` + 그 컬럼을 쓰는 코드 v2를 한 배포에 넣으면 — 카나리로 5%만 내보내도 롤백이 불가능해집니다(스키마는 이미 바뀌었고, 구버전 95%가 새 제약에 걸립니다). 코드는 되돌릴 수 있지만 적용된 스키마는 아닙니다. **expand-contract**로 분리하세요: 하위 호환 스키마 변경(expand) → 코드 배포(카나리) → 안정화 → 정리(contract). 각 단계가 독립적으로 롤백 가능해야 합니다.

## 4. 롤링을 "안전하니까" 프로덕션 기본으로

k8s Deployment의 롤링은 편하고 무중단이라 기본값이 됩니다 — 그런데 그것은 **메트릭 게이트가 없는** 느린 전면 배포입니다(theory §4). maxSurge/maxUnavailable은 속도만 조절할 뿐 "나쁘면 멈춤"이 없습니다. 나쁜 이미지는 결국 100%에 도달합니다. 리스크가 큰 서비스(결제·인증)는 롤링이 아니라 카나리(17의 Rollouts)로 — 무중단과 안전은 다른 것입니다.

## 5. 블루/그린의 비용과 상태를 잊기

블루/그린은 롤백이 즉시라 매력적이지만, 전환 기간 동안 **두 환경이 동시에** 뜹니다(01의 "일시 2배" 비용). 그리고 상태 저장 워크로드라면 더 복잡합니다 — 두 버전이 같은 DB·큐를 동시에 쓰면 데이터 정합성 문제가 생깁니다(진행 중인 작업을 어느 버전이 처리?). 무상태 서비스에는 깔끔하지만, 상태가 있으면 expand-contract와 큐 드레이닝을 함께 설계해야 합니다. "즉시 롤백"만 보고 고르면 상태 문제에 발목 잡힙니다.

## 실무 사고 사례

> 한 팀이 카나리 배포를 자랑스럽게 운영했습니다 — 10% → 25% → 50% → 100%, 각 단계 5분 대기. 어느 날 인증 서비스 v2를 배포하는데, v2는 세션 토큰 형식을 바꿨고 그것이 DB의 새 컬럼을 요구했습니다. 마이그레이션은 "배포 직전에" 함께 실행됐습니다. 카나리 10% 단계에서 새 토큰을 받은 사용자들은 정상이었지만 — 5분 뒤 문제를 발견하고 롤백합시다, 이미 v2로 로그인한 10%의 사용자들의 세션이 구버전에서 파싱 실패로 전부 로그아웃됐습니다. 게다가 스키마는 이미 바뀌어서 구버전 90%도 간헐적 오류를 뱉기 시작했습니다. "안전한" 카나리가 오히려 부분 장애를 만든 것입니다. 근본 원인 둘: ① 관찰 지표가 "5xx율"뿐이라 "세션 파싱 실패"(4xx로 집계)를 못 잡았다 ② 스키마와 코드를 한 배포에 묶어 롤백이 불가능했습니다. 조치: expand-contract로 토큰 형식을 하위 호환 전환(양쪽 형식을 읽는 v1.5를 먼저), 카나리 지표에 인증 성공률 추가. 교훈: **카나리는 롤백이 가능할 때만 안전하고, 롤백 가능성은 스키마 설계가 정합니다** — 배포 전략보다 데이터 변경 전략이 먼저입니다.
