# 흔한 함정 5선

## 1. `pull_request_target`으로 PR 코드를 실행

포크 PR의 CI가 시크릿을 필요로 해서 트리거를 바꿉니다 — 그 순간 **누구나 PR을 열어 저장소의 모든 시크릿을 훔칠 수 있습니다**(`postinstall` 스크립트, 수정된 테스트, 무엇이든). `pull_request_target`은 base 브랜치 코드로 PR에 라벨·코멘트를 다는 용도이고, **PR의 코드를 체크아웃하거나 실행하는 순간 취약점**이 됩니다. 포크 PR에 시크릿이 필요하다면 설계가 틀린 것 — 배포는 머지 후 별도 워크플로(환경 승인, 07의 OIDC)로.

## 2. 사용자 입력을 `run:`에 직접 보간

`${{ github.event.pull_request.title }}`, `${{ github.head_ref }}`, 커밋 메시지 — 전부 공격자가 제어할 수 있는 문자열이고, 표현식은 **셸 파싱 전에** 치환되므로 코드가 됩니다(lab-01 Step 4에서 재현). 방어는 한 줄입니다: `env:`로 넘기고 `"$VAR"`로 읽어라. 이 규칙을 팀 린터(`actionlint`)로 강제하면 사람의 기억에 의존하지 않습니다.

## 3. 매트릭스 잡을 필수 검사에 개별 등록

브랜치 보호에 `test (3.11)`, `test (3.12)`를 하나씩 등록하면 — Python 3.13을 추가하는 날 그 검사는 필수가 아니게 되고(등록 안 됨), 3.11을 빼는 날 **필수 검사가 영원히 pending**이라 모든 PR이 막힙니다. 해법은 lab-02의 수렴 잡: `needs: [lint, test]` + `if: always()`로 결과를 집계하는 `ci` 잡 하나만 필수로 등록합니다.

## 4. 액션을 태그로 참조하고 잊기

`uses: some-org/some-action@v1`의 `v1`은 **움직이는 포인터**입니다 — 액션 저장소가 탈취되면 다음 실행부터 악성 코드가 우리 러너(시크릿이 있는 곳)에서 돕니다. 실제 사고가 반복된 유형입니다. 규율: 서드파티 액션은 **커밋 SHA로 고정**하고, Dependabot으로 갱신 PR을 받습니다. 신뢰 목록(허용된 액션 org)을 저장소 설정에서 강제할 수도 있습니다.

## 5. 캐시를 믿고 결정성을 잃기

`actions/cache`로 `node_modules`를 통째로 캐시하면 — lockfile이 바뀌어도 낡은 트리가 복원되어 "CI는 통과했는데 프로덕션에서 깨지는" 재현 불가 버그가 생깁니다. 규칙: 캐시 키에 **lockfile 해시**를 포함하고(`hashFiles('**/package-lock.json')`), 캐시는 "다운로드 시간 절약"이지 "설치 단계 생략"이 아니게 설계하세요. 러너가 매번 새 VM인 것은 불편이 아니라 **재현성이라는 기능**입니다.

## 실무 사고 사례

> 한 오픈소스 프로젝트가 포크 PR에서도 통합 테스트를 돌리려고 `pull_request_target`으로 트리거를 바꾸고, PR의 head SHA를 체크아웃했습니다. 6주 뒤 한 기여자가 "빌드 스크립트 개선" PR을 열었습니다 — `package.json`의 `preinstall`에 한 줄이 있었습니다: 환경변수 전체를 base64로 인코딩해 외부 엔드포인트로 POST. 워크플로는 정상 통과했고 CI 로그에는 마스킹된 `***`만 보였습니다(인코딩된 값은 마스킹되지 않았습니다). 유출된 것은 npm 배포 토큰과 AWS 키였고, 공격자는 그 토큰으로 악성 버전을 npm에 게시했습니다 — 수천 개 프로젝트가 그것을 내려받았습니다. 사후 조치: `pull_request_target` 전면 제거, 포크 PR은 시크릿 없이 실행하고 유지보수자가 라벨을 달아야 통합 테스트가 도는 구조로 변경, 모든 액션 SHA 고정, 시크릿 전면 회전. 교훈: **CI 러너는 프로덕션 자격증명이 평문으로 존재하는 곳입니다** — 그곳에서 남의 코드를 실행하는 설계는, 아무리 편해도, 그 편의의 대가가 계정 전체입니다.
