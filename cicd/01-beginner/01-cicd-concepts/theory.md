# 이론 — 통합의 수학, 배포의 전략, 그리고 측정의 좌표계

> **🌱 17세 눈높이 비유: 조별 과제**
> 다섯 명이 발표 자료를 나눠 만듭니다:
> - **통합을 미루는 조**: 각자 2주간 자기 파트를 만들고 발표 전날 합칩니다 → 폰트도 용어도 결론도 다 다르고, 세 명의 슬라이드가 같은 내용입니다. 밤을 새웁니다 (**merge hell**)
> - **매일 합치는 조**: 하루 끝에 공유 파일에 합쳐봅니다 → 충돌이 나도 어제 것과 오늘 것뿐이라 5분이면 풉니다. **문제가 작을 때 발견**됩니다 (**CI**)
> - **발표 연습(테스트)**: 합칠 때마다 처음부터 읽어봅니다 → 말이 안 되는 곳이 즉시 드러납니다
> - **제출(배포)**: 완성본을 한 번에 내는 대신, 초안을 계속 제출 가능한 상태로 둡니다 (**Continuous Delivery**) — 교수가 언제 걷어가도 낼 수 있습니다
> - **카나리**: 발표를 친구 3명에게 먼저 해보고 반응을 봅니다 → 전체 앞에서 망하지 않습니다

## 1. 세 개의 C — 정확한 정의

| | 정의 | 끝나는 지점 | 실패의 의미 |
|---|------|------------|------------|
| **CI** (Continuous Integration) | 모든 개발자가 **하루에 여러 번** 공유 브랜치에 통합하고, 그때마다 자동 빌드·테스트 | "합쳐진 코드가 건강하다" | 통합이 깨졌습니다 — 즉시 고칩니다(빌드 깨진 채 퇴근 금지) |
| **Continuous Delivery** | 통합된 것이 **언제든 배포 가능한 아티팩트**로 준비됨 | 스테이징까지 자동, 프로덕션은 **버튼** | 배포 준비가 안 됐습니다 |
| **Continuous Deployment** | 게이트를 통과하면 **프로덕션까지 자동** | 프로덕션 | 릴리스가 자동 롤백됩니다 |

주의: **CI는 도구가 아니라 습관입니다.** Jenkins가 돌아도 개발자가 2주짜리 브랜치를 들고 있으면 CI가 아닙니다. 반대로 도구 없이 매일 합치고 손으로 테스트해도 CI의 본질은 지켜집니다(권하진 않지만).

## 2. merge hell의 수학 — 왜 "자주"인가

브랜치가 오래될수록 충돌 가능성은 **선형이 아니라 곱셈**으로 자랍니다:

```
충돌 위험 ≈ (내가 바꾼 파일 수) × (그동안 남들이 바꾼 파일 수) × (겹칠 확률)
           ↑ 시간에 비례            ↑ 시간 × 개발자 수에 비례
→ 브랜치 수명의 제곱에 가깝게 증가
```

게다가 충돌 해결의 **난이도**도 함께 오릅니다 — 2주 전의 내 의도와 남의 의도를 동시에 복원해야 하니까. lab-01에서 이것을 실제 git 명령으로 재현합니다.

여기서 두 가지 실천이 따라 나옵니다:

- **트렁크 기반 개발**(02에서 상술): 짧은 브랜치(1일 이하) 또는 트렁크 직접 커밋
- **피처 플래그**: 코드는 합치되 기능은 꺼둡니다 — "완성돼야 합칠 수 있다"는 제약을 푸는 열쇠

## 3. 파이프라인 설계 3원칙

### ① 빠른 피드백 — 실패는 왼쪽에서

```
빠른 것부터 (실패하면 즉시 중단):
  lint(초) → 단위 테스트(분) → 빌드(분) → 통합 테스트(분~) → e2e(십수 분) → 배포
```

원칙: **비싼 검증 앞에 싼 검증을.** 10분짜리 e2e가 lint 오류로 실패하는 것은 낭비입니다. 그리고 전체 CI가 10분을 넘으면 개발자는 결과를 기다리지 않고 컨텍스트를 전환합니다 — 그 순간 피드백 루프가 끊깁니다.

### ② 아티팩트 불변성 — 한 번 빌드, 여러 번 배포

```
❌ dev용 빌드 → staging용 빌드 → prod용 빌드   (다른 바이너리! 테스트한 것이 안 나갑니다)
✅ 한 번 빌드 → 같은 이미지를 dev→staging→prod로 승격 (환경 차이는 설정으로만)
```

이미지 태그는 **불변**이어야 합니다(`:latest` 금지 — 04·19에서 상술). 승격되는 것은 이미지 다이제스트이고, 바뀌는 것은 ConfigMap/Secret뿐입니다. 12-factor의 "build, release, run 분리"가 이것입니다.

### ③ 신뢰의 게이트 — 자동화의 조건

```
게이트 = "이것을 통과하면 다음 단계로 보내도 된다"는 팀의 신뢰
  테스트가 flaky하면 → 게이트가 무의미 → 사람이 재실행 버튼을 누르는 의식(儀式)이 됩니다
```

**Continuous Deployment의 전제는 게이트에 대한 신뢰**입니다. flaky 테스트(23에서 다룸)를 방치한 채 자동 배포를 켜는 것은 고장난 화재경보기와 함께 사는 것과 같습니다.

## 4. DORA 4지표 — 개선의 좌표계

파이프라인의 성능은 네 숫자로 말합니다 (Google의 DevOps Research):

| 지표 | 정의 | 엘리트 수준 |
|------|------|-----------|
| **배포 빈도** (Deployment Frequency) | 프로덕션 배포 횟수 | 하루 여러 번 |
| **변경 리드 타임** (Lead Time for Changes) | 커밋 → 프로덕션까지 | 1시간 미만 |
| **변경 실패율** (Change Failure Rate) | 배포 중 장애를 유발한 비율 | 15% 미만 |
| **복구 시간** (MTTR / Failed Deployment Recovery) | 장애에서 회복까지 | 1시간 미만 |

**속도(1·2)와 안정성(3·4)은 상충하지 않습니다** — 이것이 DORA 연구의 핵심 발견입니다. 자주 배포하는 조직이 더 안정적입니다: 배포가 작으니 실패해도 작고, 롤백이 쉽고, 자주 해서 능숙합니다. "안정성을 위해 분기 배포"는 두 마리 토끼를 다 놓칩니다.

## 5. 배포 전략 스펙트럼

| 전략 | 방식 | 다운타임 | 롤백 | 비용 |
|------|------|---------|------|------|
| **Recreate** | 다 죽이고 다 띄움 | 있음 | 재배포 | 최소 |
| **Rolling** (k8s 기본) | 점진 교체 | 없음 | 이전 RS로 | 최소 |
| **Blue/Green** | 새 환경 통째 → 전환 | 없음 | 즉시(스위치 반전) | 일시 2배 |
| **Canary** | 소수 트래픽 → 관찰 → 확대 | 없음 | 즉시(가중치 0) | 소량 |
| **Shadow** | 실트래픽 복제해 새 버전에(응답 버림) | 없음 | — (영향 없음) | 2배 연산 |

핵심 통찰: **롤링은 "느린 전면 배포"이지 안전장치가 아닙니다** — 새 버전이 나쁘면 결국 100%에 도달합니다. 안전은 **관찰 후 확대**(카나리)에서 옵니다. 17(Progressive Delivery)에서 이것을 자동화합니다.

k8s에서의 매핑: Recreate/Rolling은 Deployment 전략, Blue/Green과 Canary는 서비스 메시(eks 20)나 Argo Rollouts(17)의 영역.

## 6. 파이프라인의 해부 — 이 파트의 지도

```
[코드]  git push
   │
   ├─ CI (03~06, 12, 13, 16)
   │    lint → test(05) → build(04, 19) → 이미지 스캔·서명(21) → 레지스트리
   │
   ├─ CD — push 모델 (09~11): 파이프라인이 클러스터에 kubectl apply
   │  CD — pull 모델 (14, 15): 클러스터의 컨트롤러가 git을 보고 스스로 맞춘다 ← GitOps
   │
   └─ 배포 전략 (17): 카나리·자동 롤백 — 메트릭이 게이트가 됩니다
```

**push vs pull이 이 파트의 큰 분기점**입니다: 전자는 파이프라인이 클러스터 자격증명을 갖고(권한 유출 위험), 후자는 클러스터가 git을 당겨옵니다(선언이 진실). 14·15에서 그 차이가 왜 GitOps라는 이름을 얻었는지 봅니다.
