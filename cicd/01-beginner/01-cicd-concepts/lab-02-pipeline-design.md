# Lab 02 — 설계 워크시트와 DORA 기준선

도구 없이도 파이프라인은 설계할 수 있습니다. 이 랩의 산출물(설계 문서 + DORA 좌표)이 이후 25개 모듈의 기준선이 됩니다.

## Step 1. 스테이지 배열 — "빠른 피드백" 원칙 적용

가상의 서비스(Python 웹앱, 컨테이너 배포)의 CI를 설계합니다. 아래 검증 항목들을 **실행 시간과 실패 확률**로 정렬하세요:

```markdown
| 검증 | 소요 | 실패 빈도 | 배치 순서 |
|------|------|----------|----------|
| 포맷/lint | 10초 | 높음 | ? |
| 단위 테스트 | 90초 | 중간 | ? |
| 컨테이너 빌드 | 3분 | 낮음 | ? |
| 이미지 취약점 스캔 | 1분 | 중간 | ? |
| 통합 테스트(DB 포함) | 5분 | 중간 | ? |
| e2e (실제 클러스터) | 12분 | 낮음 | ? |
```

정답의 원리: **(빠르고 자주 실패하는 것) → (느리고 드물게 실패하는 것)**. 그리고 병렬화 가능한 것은 병렬로.

```
[병렬] lint(10s) ‖ 단위테스트(90s)
   ↓ 둘 다 통과해야
빌드(3m) → 스캔(1m) → [병렬] 통합테스트(5m) ‖ (아티팩트 푸시)
   ↓
e2e(12m) → 배포 게이트
```

체감 시간 계산:

```bash
# 순차 실행 시
echo "순차: $((10 + 90 + 180 + 60 + 300 + 720))초 = $(( (10+90+180+60+300+720) / 60 ))분"
# 위 설계(병렬 + 조기 중단)의 성공 경로
echo "설계: $((90 + 180 + 60 + 300 + 720))초 = $(( (90+180+60+300+720) / 60 ))분"
# lint 실패 시 (가장 흔한 실패)
echo "lint 실패: 10초에 피드백"
```

✅ 핵심은 총합이 아니라 **실패했을 때의 피드백 시간**입니다. lint 오류로 20분 뒤 알림을 받는 파이프라인은 개발자를 훈련시킵니다 — "CI는 어차피 느리니 나중에 보자"고.

## Step 2. 아티팩트 불변성 — 승격 모델 그리기

```markdown
# ❌ 흔한 안티패턴 (환경마다 빌드)
git push → [dev 빌드] → dev 배포
         → [staging 빌드] → staging 배포     # 다른 바이너리!
         → [prod 빌드] → prod 배포           # 테스트한 것과 다른 것이 나갑니다

# ✅ 승격 모델
git push → [빌드 1회] → image@sha256:abc123
              ↓ 같은 다이제스트가 이동
           dev 배포 → (검증) → staging 배포 → (검증) → prod 배포
           환경 차이 = ConfigMap/Secret/replicas 뿐
```

우리 팀의 규칙을 명시하세요:

```markdown
- [ ] 이미지 태그 규칙: `<repo>:<git-sha>` (mutable tag 금지 — :latest, :main)
- [ ] 배포는 **다이제스트**(@sha256:...)로 참조 (태그는 사람이 읽는 용도)
- [ ] 환경별로 바뀌는 것 목록: __ (여기 이미지가 들어가면 안 됩니다)
```

## Step 3. DORA 기준선 측정 — 지금 우리는 어디 있나

기존 저장소가 있다면 git 히스토리로 두 지표를 근사할 수 있습니다:

```bash
cd <your-repo>

# ① 배포 빈도 근사 — 프로덕션 배포 태그/릴리스가 있다면
git tag --sort=-creatordate | head -20
git log --tags --simplify-by-decoration --pretty="%ci %d" | head -10

# ② 변경 리드 타임 근사 — 커밋 시각 → 그 커밋이 포함된 태그의 시각
LAST_TAG=$(git describe --tags --abbrev=0 2>/dev/null)
if [ -n "$LAST_TAG" ]; then
  TAG_TIME=$(git log -1 --format=%ct $LAST_TAG)
  PREV_TAG=$(git describe --tags --abbrev=0 $LAST_TAG^ 2>/dev/null)
  git log --format=%ct $PREV_TAG..$LAST_TAG 2>/dev/null | while read C; do
    echo $(( (TAG_TIME - C) / 3600 ))
  done | sort -n | awk '{a[NR]=$1} END {print "리드타임(시간) 중앙값:", a[int(NR/2)+1], " 최대:", a[NR]}'
fi
```

③ 변경 실패율과 ④ 복구 시간은 코드에 없습니다 — **인시던트 기록과 배포 기록을 대조**해야 합니다. 없다면 그것 자체가 첫 개선 항목입니다(23에서 자동화).

## Step 4. 배포 전략 결정표

우리 서비스 각각에 전략을 배정하세요 — eks 파트의 사고방식(티어링) 그대로:

```markdown
| 서비스 | 상태성 | 실패 비용 | 트래픽 | 전략 | 근거 |
|--------|-------|----------|--------|------|------|
| 결제 API | 무상태(DB 별도) | 매우 높음 | 높음 | 카나리 + 자동 롤백(17) | 5%에서 오류율 감지 |
| 내부 대시보드 | 무상태 | 낮음 | 낮음 | 롤링 | 단순함이 가치 |
| 배치 워커 | 상태(진행 중 작업) | 중간 | — | Recreate + drain 대기 | 중복 실행 금지 |
| DB 마이그레이션 | — | 매우 높음 | — | 별도 절차(expand-contract) | 롤백 불가 |
```

마지막 행이 이 파트에서 반복될 주제입니다 — **스키마 변경은 롤백이 안 됩니다.** 코드 배포와 데이터 마이그레이션의 리스크는 다른 종류입니다.

## Step 5. 파이프라인 설계 문서 (산출물)

```markdown
# 파이프라인 설계 v1 — <프로젝트>
## 원칙
1. 빠른 피드백: lint 실패는 30초 안에. 전체 CI는 10분 이내(넘으면 병렬화·캐시)
2. 아티팩트 불변: 1회 빌드, sha 다이제스트로 승격. 환경 차이는 설정만
3. 신뢰의 게이트: flaky 테스트는 즉시 격리(quarantine)하고 추적 — 무시하지 않습니다

## 스테이지
[PR] lint ‖ unit → build → scan → integration
[main] 위 + e2e → staging 자동 배포 → (승인) → prod

## DORA 기준선 (측정일: ____)
| 지표 | 현재 | 6개월 목표 |
|------|------|-----------|
| 배포 빈도 | 주 __회 | 일 __회 |
| 리드 타임 | 중앙값 __h | < __h |
| 변경 실패율 | __% (측정 불가면 그것부터) | < 15% |
| 복구 시간 | __ | < 1h |

## 이 문서의 갱신 시점
- 각 모듈 완주 후 해당 항목 보강 (예: 07 후 "OIDC로 자격증명 제거" 반영)
```

## Step 6. 자문 — 이 파트를 관통할 질문

```markdown
1. 우리 CI가 10분을 넘는다면, 개발자는 결과를 기다리는가 아니면 다른 일을 하는가요?
2. 테스트가 실패했을 때, "다시 돌려보자"는 말이 나오는가요? (게이트 신뢰의 리트머스)
3. 프로덕션 배포에 사람의 승인이 필요하다면, 그 사람은 무엇을 보고 승인하는가요?
4. 어제 배포한 것을 30분 안에 되돌릴 수 있는가요? 해본 적 있는가요?
```

이 넷에 자신 있게 답할 수 있게 되는 것이 이 파트의 목표입니다.
