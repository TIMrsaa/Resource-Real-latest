# 이론 — 세 모델의 해부, 짧은 브랜치의 도구, 머지의 정치학

> **🌱 17세 눈높이 비유: 학교 신문 만들기**
> - **git-flow** = 계간지: 원고를 몇 달 모아 편집본(`develop`)을 만들고, 발간 전 교정 기간(`release/*`)을 거쳐 인쇄(`main`). 이미 인쇄된 호에 오타가 발견되면 정오표(`hotfix/*`)를 냅니다. 절차가 많은 이유는 **인쇄를 되돌릴 수 없기** 때문
> - **GitHub flow** = 온라인 뉴스: 기사 하나 쓰면 데스크가 보고 바로 게시. 틀리면 수정해 다시 게시. 교정 기간 같은 건 없습니다
> - **트렁크 기반** = 실시간 생중계 자막: 문장 단위로 즉시 반영. 아직 다듬는 중인 문장은 **화면에 안 보이게 처리**(피처 플래그)해두고 올립니다
> - 셋 중 뭐가 옳은가요? **인쇄기를 쓰는지 웹을 쓰는지**에 달렸습니다. 웹 뉴스를 계간지 절차로 만들면 속보는 늘 늦습니다

---

## 1. git-flow — 인쇄기의 시대

```
main      ────●────────────────●──────  (태그: v1.0, v1.1 — 릴리스만)
               ╲              ╱ ╲
release        ╲    ●───●───●    ╲      (교정 기간: 버그픽스만 허용)
                ╲  ╱              ╲
develop   ───●───●────●────●───────●──  (통합 브랜치)
             ╱        ╲    ╱
feature/x  ●─          ●──●             (기능당 브랜치, 수명 주~월)
hotfix/y                        ●───●   (main에서 갈라져 main+develop으로)
```

- **필요한 이유**: 여러 버전을 동시에 지원해야 하고(v1.x 유지보수 + v2 개발), 릴리스 전 코드 프리즈가 필요한 세계
- **비용**: 브랜치 수명이 깁니다 → merge hell(01) → 통합 지연 → 리드 타임 폭증. `develop`과 `main`의 이중 관리, hotfix의 양쪽 반영 누락
- **적합**: 라이브러리, 온프레미스 설치형 제품, 임베디드 — **롤백이 물리적으로 불가능한 배포**

## 2. GitHub flow — 웹의 기본형

```
main   ───●───●────●────●───   (항상 배포 가능. 여기가 곧 프로덕션)
          ╲  ╱ ╲  ╱
feature    ●─   ●─            (짧은 브랜치 → PR → 리뷰/CI → squash merge)
```

규칙은 다섯 줄로 끝납니다: main은 항상 배포 가능, 브랜치는 짧고 서술적으로, PR로 논의, CI 통과 후 머지, 머지되면 곧 배포. **대부분의 웹 서비스에 옳은 기본값**이고, 이 커리큘럼의 실습도 이 모델을 씁니다.

## 3. 트렁크 기반 개발 — 엘리트의 공통점

```
main  ──●──●──●──●──●──●──●──   (모두가 하루에도 여러 번 여기로)
         ╲╱   ╲╱   (브랜치가 있어도 수명 < 1일, 또는 직접 커밋)
```

- 미완성 기능이 트렁크에 존재합니다 — 그래서 **끄는 장치**가 필수(§4)
- 릴리스는 트렁크의 한 지점에 태그를 찍는 것, 또는 그냥 배포
- 규모가 큰 조직일수록 오히려 이 모델을 씁니다(Google, Meta) — 브랜치 통합 비용이 조직 크기에 비례하기 때문

**DORA 데이터의 상관**: 엘리트 그룹은 브랜치 수명이 짧고, 트렁크에 하루 여러 번 통합하며, 배포 빈도가 높습니다. 인과의 방향은 논쟁적이지만 — 긴 브랜치를 유지하면서 하루 여러 번 배포하는 것은 **구조적으로 불가능**합니다.

## 4. 짧은 브랜치를 가능하게 하는 세 도구

긴 브랜치의 원인은 게으름이 아니라 **"완성돼야 합칠 수 있다"는 제약**입니다. 이것을 푸는 세 가지:

### ① 피처 플래그 (01 lab-01 Step 5)

```python
if flags.enabled("new_checkout", user):   # 코드는 main에, 기능은 꺼둔 채
    return new_checkout(cart)
return legacy_checkout(cart)
```

- 통합 주기와 릴리스 주기를 **분리**합니다 — 배포와 출시가 다른 사건이 됩니다
- 대가: 플래그 부채(끄는 코드를 지우지 않으면 조건문 정글). 플래그마다 **만료일과 담당자**를 (22의 시크릿 관리와 같은 규율)

### ② 브랜치 바이 앱스트랙션 (Branch by Abstraction)

큰 리팩터링을 긴 브랜치 없이:

```
1. 기존 구현 앞에 추상화 계층(인터페이스)을 세웁니다 → main에 머지
2. 새 구현을 그 뒤에 추가합니다(아직 아무도 안 씁니다) → main에 머지
3. 호출부를 하나씩 새 구현으로 옮깁니다 → 각각 main에 머지
4. 기존 구현을 지웁니다 → main에 머지
```

각 단계가 독립적으로 배포 가능합니다 — **"6개월짜리 마이그레이션 브랜치"의 대안**.

### ③ PR 크기 규율

리뷰 품질은 PR 크기에 반비례합니다(400줄 넘으면 결함 발견율이 급락한다는 연구가 여럿). 큰 변경은 **여러 개의 작은 PR로 쪼개는 기술**이 필요하고, 그것이 곧 짧은 브랜치를 만듭니다. 규칙 예: "PR은 400줄 이하, 넘으면 쪼갤 방법을 먼저 논의".

## 5. 머지 방식 세 가지 — 히스토리의 정치학

| 방식 | 결과 | 장점 | 단점 |
|------|------|------|------|
| **merge commit** | 브랜치 구조 보존 | 실제 히스토리 그대로 | 그래프가 복잡, `git bisect` 어려움 |
| **squash** | PR 하나 = 커밋 하나 | 선형 히스토리, bisect 쉬움 | 브랜치 내부 커밋 소실 |
| **rebase merge** | 커밋 개별 유지 + 선형 | 둘의 절충 | 커밋마다 CI를 안 돌렸다면 중간 커밋은 미검증 |

실무 권장: **squash**가 기본(PR = 논리적 변경 단위 = 커밋 하나). 다만 커밋 메시지가 곧 CHANGELOG가 되므로 — squash 시 제목을 다듬는 규율(Conventional Commits: `feat:`, `fix:`, `chore:`)이 따라와야 합니다. 이 규율은 21(SBOM/릴리스 노트 자동화)에서 회수됩니다.

**롤백의 관점**: squash된 main은 `git revert <sha>` 하나로 PR 전체를 되돌립니다 — 01의 "30분 안에 되돌릴 수 있는가"에 대한 가장 단순한 답.

## 6. 브랜치 보호 — 게이트의 첫 번째 물리적 형태

```
main 브랜치에:
  ✔ PR 없이 직접 push 금지 (관리자도 — "예외가 곧 구멍")
  ✔ 필수 상태 검사: CI 통과 (01의 게이트가 여기서 강제됩니다)
  ✔ 최신 base 요구 (stale 브랜치 머지 방지)
  ✔ 리뷰 승인 N명 (+ CODEOWNERS로 도메인별 필수 리뷰어)
  ✔ force-push / 삭제 금지
  ✔ 서명된 커밋 요구 (선택 — 21의 공급망 보안과 연결)
```

주의: 승인 인원을 늘릴수록 리드 타임이 늘고, 리뷰 품질은 **줄어들 수 있습니다**(책임 분산). 대개 1~2명 + CODEOWNERS가 균형점입니다.

## 7. 리뷰는 어디서 시간을 먹는가

리드 타임(커밋→프로덕션)을 분해하면 대개 이렇습니다:

```
코딩 ──▶ PR 열기 ──▶ [리뷰 대기] ──▶ 리뷰 ──▶ [수정 대기] ──▶ CI ──▶ 머지 ──▶ 배포
                      ↑ 여기가 최대 항인 조직이 대부분
```

CI를 3분 줄이는 것보다 **리뷰 첫 응답 시간(time to first review)을 6시간 줄이는 것**이 리드 타임에 훨씬 크게 기여합니다. lab-02에서 이것을 실제로 측정합니다. 대책: 리뷰 SLA(예: 4시간 내 첫 응답), 작은 PR, 리뷰어 로테이션, 비동기 문화.
