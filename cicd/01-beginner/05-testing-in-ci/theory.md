# 이론 — 피라미드의 경제학, 테스트 더블, flaky의 물리학

> **🌱 17세 눈높이 비유: 시험 대비**
> - **단위 테스트** = 단어 암기 퀴즈 — 1초에 한 문제, 틀리면 **어느 단어인지 정확히** 압니다
> - **통합 테스트** = 문법 문제 — 단어 여러 개가 함께 작동하는지. 조금 느리고, 틀리면 원인 후보가 몇 개
> - **e2e 테스트** = 실전 모의고사 — 가장 현실에 가깝지만 3시간 걸리고, 틀렸을 때 **왜 틀렸는지 찾는 데 또 시간**이 듭니다
> - **피라미드** = 단어 퀴즈 많이, 모의고사 가끔. **뒤집으면**(모의고사만 매일) 시간은 다 쓰는데 뭘 모르는지는 끝내 모릅니다
> - **flaky 테스트** = 채점 기계가 가끔 오답을 정답으로 처리 — 이런 기계로 채점하면 **점수 자체가 정보가 아닙니다.** 고칠 때까지 그 문제는 시험에서 빼야 합니다(격리)
> - **커버리지** = "몇 페이지를 봤나" — 봤다고 아는 건 아닙니다. 목표로 삼으면 페이지만 넘깁니다

## 1. 피라미드와 그 역전

```
        /\           e2e (느림·비쌈·불안정·현실적)
       /  \          10%   ← 사용자 여정 몇 개만
      /____\
     /      \        통합 (컴포넌트 경계 — DB, API)
    /        \       20%
   /__________\
  /            \     단위 (빠름·싸고·안정적·정밀)
 /______________\    70%
```

**경제학**: 각 층은 비용(실행 시간 + 유지보수 + 불안정성)과 신뢰도(현실 반영)를 교환합니다.

| | 실행 | 실패 시 원인 특정 | 불안정성 | 현실 반영 |
|---|------|-----------------|---------|----------|
| 단위 | ms | 즉시(그 함수) | 거의 없음 | 낮음 |
| 통합 | 초 | 몇 개 컴포넌트 | 중간(네트워크·상태) | 중간 |
| e2e | 분 | 어려움(전 시스템) | 높음 | 높음 |

### 아이스크림 콘 (역전된 피라미드)

e2e가 대부분인 스위트는 — 느리고(PR마다 못 돌림), flaky하고(재실행 문화), 실패 원인을 못 찾습니다(디버깅 지옥). 그런데도 흔한 이유: **e2e는 코드를 안 고쳐도 쓸 수 있습니다.** 단위 테스트는 테스트 가능한 설계(의존성 주입)를 요구하고, 그게 없으면 쓸 수가 없습니다. 즉 아이스크림 콘은 테스트 전략의 실패가 아니라 **설계 부채의 증상**입니다.

## 2. 테스트 더블 — 정확한 이름 쓰기

| 이름 | 정체 | 예 |
|------|------|----|
| **Dummy** | 자리만 채움(사용 안 됨) | 필수 인자에 `nil` |
| **Stub** | 정해진 답을 반환 | "이 호출엔 항상 200" |
| **Spy** | Stub + 호출 기록 | "몇 번 불렸나" |
| **Mock** | 기대를 미리 선언, 검증 | "정확히 1번, 이 인자로" |
| **Fake** | **간단하지만 진짜 동작하는 구현** | 인메모리 DB, fake k8s client |

실무 조언: **Fake > Mock.** Mock은 구현 세부(호출 순서·횟수)에 결합해 리팩터링을 방해하고, 테스트가 "코드가 이렇게 생겼다"를 검증할 뿐 "동작이 옳다"를 검증하지 못합니다. Fake는 행동을 검증합니다.

> 우리는 이것을 이미 봤습니다: **eks 28의 fake CloudProvider**, **eks 29의 mock netlink** — 큰 프로젝트들이 fake를 제공하는 이유입니다(`k8s.io/client-go/kubernetes/fake`).

## 3. 통합 테스트를 CI에서 격리하는 두 방법

### ① Service containers (GitHub Actions 네이티브)

```yaml
jobs:
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test }
        options: >-
          --health-cmd "pg_isready" --health-interval 5s --health-retries 5
        ports: ["5432:5432"]
    steps:
      - run: pytest tests/integration    # localhost:5432로 접속
```

- 잡 시작 시 컨테이너를 띄우고 끝나면 파괴 — **잡 간 격리는 러너 VM이 보장**(03)
- `--health-cmd`가 중요: 헬스체크 없이 시작하면 "DB가 아직 안 떴는데 테스트 시작"이라는 **flaky의 고전적 원인**이 됩니다

### ② Testcontainers (코드에서 컨테이너 제어)

```python
from testcontainers.postgres import PostgresContainer

def test_repo():
    with PostgresContainer("postgres:17") as pg:      # 테스트가 컨테이너 수명을 소유
        repo = Repo(pg.get_connection_url())
        assert repo.save(...) 
```

장점: 로컬과 CI가 **같은 코드**로 돕니다("로컬에선 되는데" 소멸). 단점: Docker 소켓 필요, 시작 시간.

## 4. flaky 테스트의 물리학

flaky = 코드 변경 없이 결과가 바뀌는 테스트. 원인은 대개 **비결정성의 다섯 원천**:

| 원천 | 예 | 처방 |
|------|----|------|
| 시간 | `datetime.now()`, sleep 기반 대기 | 시계 주입, 조건 폴링(`wait_until`) |
| 순서 | 테스트 간 공유 상태 | 격리(트랜잭션 롤백, 새 스키마), 랜덤 순서 실행으로 탐지 |
| 동시성 | 경합, 스레드 타이밍 | 결정적 스케줄, 동기화 지점 명시 |
| 외부 의존 | 실제 네트워크, 시간 제한 | fake/stub, 재시도 대신 격리된 더블 |
| 자원 | 포트 충돌, 디스크·메모리 | 동적 포트, 격리된 임시 디렉터리 |

### 재실행은 왜 답이 아닌가

```
retry 3회로 "통과"시키면:
  ① 그 테스트는 이제 아무것도 검증하지 않습니다 (실패해도 통과하니까)
  ② 진짜 회귀도 재실행으로 묻힙니다 (1/3 확률로 걸리는 버그를 놓칩니다)
  ③ 다른 flaky를 방치할 명분이 생깁니다 → 게이트 전체가 죽습니다 (01의 신뢰)
```

### 격리(quarantine) 시스템의 구조

```
탐지: 같은 커밋에서 N회 반복 실행 → 결과가 갈리면 flaky
격리: 그 테스트에 마커(@flaky/@quarantine) → 필수 게이트에서 제외, 별도 잡에서 계속 실행(추이 관찰)
추적: 자동 이슈 생성 + 담당자 + 만료일 (격리는 임시 조치입니다)
회수: 고쳐지면 마커 제거, 안 고쳐지면 **삭제**(썩은 테스트는 부채)
```

핵심: 격리는 **무시가 아닙니다.** 게이트에서 빼되 가시성은 유지하고 기한을 둡니다 — eks 파트의 "예외는 기한부로" 규율과 같은 사상.

## 5. 커버리지 — 도구인가 목표인가

**굿하트의 법칙**: "측정이 목표가 되면 좋은 측정이기를 멈춥니다." 커버리지 80% 목표를 세우면 — 어서션 없는 테스트, 게터 테스트, 예외 경로 무시 테스트가 늘어납니다. 숫자는 오르고 신뢰는 그대로입니다.

올바른 사용:

| 용법 | 왜 |
|------|----|
| **diff 커버리지** (이 PR이 바꾼 줄이 검증됐나) | "이 변경을 배포해도 되나"라는 질문과 정확히 일치 |
| **추세** (내려가면 경고) | 절대값이 아니라 방향 |
| **미검증 위험 구역 찾기** (지도로 사용) | 결제 로직 커버리지 0%면 신호 |
| ❌ 절대 목표치 게이트 | 굿하트 — 테스트 품질이 아니라 숫자를 최적화하게 됨 |

그리고 커버리지가 측정하지 않는 것: **어서션의 질**(실행됐다 ≠ 검증됐습니다), 명세의 정확성, 성능·보안·동시성.

## 6. CI에서의 테스트 배치 (01의 원칙 적용)

```
PR:    lint ‖ 단위(전체) ‖ 타입체크    → 통합(변경 영역)      → [게이트: ci]
main:  위 전부 + e2e(핵심 여정) + 성능 스모크
야간:  전체 e2e + flaky 탐지(반복 실행) + 의존성 스캔
```

원칙: **PR에는 빠르고 결정적인 것만.** e2e를 PR에 넣고 싶다면 먼저 그것이 5분 이내이고 flaky가 0인지 물어라. 아니라면 main/야간으로.

## 7. 소스/도구에서 확인하기

- Martin Fowler, *Test Pyramid* / *Test Double* (용어의 원전)
- `k8s.io/client-go/kubernetes/fake` — 대규모 프로젝트의 fake 제공 사례
- Testcontainers: https://testcontainers.com
- pytest: `-p no:randomly` / `pytest-randomly`(순서 의존 탐지), `--count`(반복 실행)
- Go: `go test -race`(경합 탐지), `-count=10`(flaky 탐지), `-shuffle=on`

## 요약 카드

| 질문 | 답 |
|------|----|
| CI에서 테스트의 목적? | "이 변경을 배포해도 되나"에 **빠르고 믿을 수 있게** 답하기 |
| 아이스크림 콘의 진짜 원인? | 테스트 전략이 아니라 **설계 부채**(단위 테스트 불가능한 코드) |
| Mock vs Fake? | Fake 선호 — Mock은 구현에 결합해 리팩터링을 막습니다 |
| service container의 필수 옵션? | health check — 없으면 flaky의 고전적 원인 |
| flaky 대응? | 재실행 ❌ → **격리(게이트 제외 + 가시성 + 기한)** |
| 커버리지의 올바른 용법? | diff 커버리지 + 추세 + 위험 지도. 절대 목표치는 굿하트 함정 |
| PR에 넣을 것? | 빠르고 결정적인 것만 — e2e는 main/야간으로 |
