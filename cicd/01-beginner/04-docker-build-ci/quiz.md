## 정답

**A1.** "한 단계가 바뀌면 **그 뒤의 모든 단계가 무효화**됩니다." 따라서 원칙: **변경 빈도가 낮은 것부터 위에** 배치합니다(베이스 → 시스템 패키지 → 의존성 매니페스트 → 의존성 설치 → 애플리케이션 코드).

**A2.** 캐시 키는 **명령 문자열 그 자체**(원격 저장소의 실제 내용이 아닙니다). 함정: 몇 달 전 캐시된 레이어가 재사용되어 `apt-get update`가 실제로 실행되지 않고 **낡은 패키지 목록**이 고착됩니다. 대책: 베이스 이미지를 다이제스트로 고정하고 주기적 갱신 PR, 시스템 패키지 설치는 최소화, 이미지 스캔을 배포 게이트로.

**A3.** 성능: 런타임 이미지가 작아 노드의 pull 시간이 줄고 스케일 아웃이 빠릅니다(eks 17). 보안: 컴파일러·셸·패키지 매니저가 최종 이미지에 없어 **침해 후 공격자의 도구가 없습니다**(eks 25 관문 ③). 비용: 이미지 전송량 감소 → NAT GW 처리 요금(eks 22의 숨은 3대장) 절감.

**A4.** 버그가 아니라 **설계**입니다 — distroless에는 셸이 아예 없습니다. 의미: 침해된 컨테이너에서 공격자가 명령을 실행하거나 도구를 내려받기 어렵습니다(RCE의 실효성이 크게 떨어집니다). 디버깅이 필요하면 `:debug` 태그 이미지로 임시 교체하거나 `kubectl debug`의 ephemeral container를 씁니다.

**A5.** `ARG` 값은 **이미지 히스토리에 영구 기록**되어 이미지를 pull할 수 있는 누구나 볼 수 있습니다. 확인: `docker history --no-trunc <image> | grep ARG명`. 올바른 방법: BuildKit `RUN --mount=type=secret,id=<id>` + `docker build --secret id=<id>,src=<file>` — 빌드 중에만 `/run/secrets/<id>`로 존재하고 레이어에 남지 않습니다.

**A6.** 러너는 잡마다 **새 VM**이라(03) 이전 실행의 로컬 캐시가 없습니다 — 캐시를 외부에 export하고 import해야 합니다. 백엔드: **GHA cache**(설정 간단, 저장소당 10GB 제한, 7일 미사용 시 삭제) vs **레지스트리 캐시**(무제한·팀/브랜치 간 공유, 레지스트리 저장·전송 비용). `mode=max`로 중간 레이어까지 캐시해야 멀티스테이지에 효과가 있습니다.

**A7.** ① 롤백 불가/모호: 어떤 커밋이 배포됐는지 알 수 없고 이전 이미지를 특정할 수 없습니다. ② 동일 Deployment의 Pod들이 pull 시점에 따라 **서로 다른 이미지**를 실행할 수 있습니다(노드가 다른 시각에 pull, imagePullPolicy 조합에 따라). (+ 태그를 덮어쓰면 "테스트한 것과 배포된 것이 다름"이 되어 게이트가 무의미해집니다.)

**A8.** 태그는 **가변 포인터**(레지스트리에서 다른 이미지로 재지정 가능)이고, 다이제스트는 **콘텐츠 해시**(내용이 바뀌면 값이 바뀝니다 — 위변조 불가). 01의 아티팩트 불변성/승격 모델이 성립하려면 "스테이징에서 검증한 바로 그 바이트"가 프로덕션에 가야 하므로, 배포 매니페스트는 `@sha256:...`을 참조해야 합니다. 태그는 사람이 읽는 별명일 뿐입니다.
