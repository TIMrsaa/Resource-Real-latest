# 흔한 함정 5선

## 1. "K8s 네이티브니까 무조건 좋다"

Tekton이 쿠버네티스 네이티브라는 이유만으로 채택하는 것 — 그리고 몇 주 뒤 EventListener·TriggerBinding·시크릿·UI를 직접 조립하느라 지칩니다. Tekton은 로우레벨 빌딩 블록이지 완성된 CI가 아닙니다. GitHub Actions가 `on: push` 한 줄로 하는 것을 Tekton은 세 리소스로 조립합니다(lab-02 Step 2). 그 조립 비용을 지불할 이유(이식성·플랫폼 구축)가 없으면, "네이티브"는 장점이 아니라 부담입니다.

## 2. Tekton을 직접 쓰려는 것 (플랫폼 없이)

Tekton의 설계 의도는 "그 위에 무언가를 얹는 것"입니다 — OpenShift Pipelines, Jenkins X, 사내 IDP의 엔진. 개발자가 Task/Pipeline YAML을 직접 쓰게 하면 대부분 GitHub Actions보다 나쁜 경험을 줍니다(UI 없음, 트리거 조립, 재사용 관리). Tekton을 채택한다면 그 위에 개발자 인터페이스(플랫폼)를 얹을 계획이 있어야 합니다. 엔진만 사고 차체를 안 만드는 셈.

## 3. Workspace를 emptyDir로만 쓰고 대용량 캐시 기대

Workspace를 emptyDir로 하면 PipelineRun이 끝나면 사라집니다 — 04의 캐시가 안 남습니다(빌드마다 콜드). 지속 캐시가 필요하면 PVC Workspace를, 그리고 04의 원리(레이어 캐시, 레지스트리 캐시)를 적용해야 합니다. 그리고 이미지 빌드는 dind(08의 privileged 위험)가 아니라 **kaniko/buildah**(데몬 없는 빌드)를 Task로 — Tekton 생태계가 이것을 잘 지원합니다.

## 4. Tekton Hub Task를 검증 없이 설치

Task가 클러스터 리소스라 재사용이 자연스럽지만, `tkn hub install`로 설치하는 Task는 **클러스터에서 실행되는 서드파티 코드**입니다(21의 공급망 위험, 06의 액션·13의 플러그인과 같은 문제). 검증 안 된 Task가 시크릿에 접근하거나 악성 이미지를 쓸 수 있습니다. 06의 규율: 신뢰할 수 있는 출처, 버전(다이제스트) 고정, 무엇을 하는지 확인. K8s 네이티브라고 공급망 위험이 사라지지 않습니다.

## 5. CI Pod에 클러스터의 보안을 적용 안 함

Tekton의 강점은 CI가 Pod라 K8s 보안이 적용된다는 것인데(lab-02 Step 4), 정작 그것을 안 하는 것 — CI Pod가 클러스터 관리자급 ServiceAccount로 돌거나, egress가 열려 있거나, privileged로 실행되면(dind), 08에서 배운 self-hosted 러너의 모든 위험이 그대로입니다(오히려 클러스터 안이라 더 위험). CI Pod에 최소 권한 SA, NetworkPolicy, PSA를 적용하세요 — 08·eks 25의 규율이 Tekton에서 특히 중요합니다(CI가 클러스터의 일부니까).

## 실무 사고 사례

> 한 플랫폼 팀이 "GitHub Actions는 SaaS라 종속적입니다, K8s 네이티브 Tekton으로 가자"며 전사 CI를 Tekton으로 전환하는 프로젝트를 시작했습니다. 6개월과 상당한 인력을 투입해 Task 라이브러리, EventListener, 시크릿 관리, 그리고 개발자용 UI까지 조립했습니다 — 사실상 사내 CI 플랫폼을 처음부터 만든 것입니다. 결과물은 동작했지만, 개발자들은 GitHub Actions 시절보다 느리고 불편하다고 느꼈습니다(UI가 조잡하고, 재사용 Task 문서가 부족하고, 디버깅이 어려웠습니다). 1년 뒤 회고에서 냉정한 질문이 나왔습니다: "우리가 SaaS 종속을 피하려고 지불한 비용(6개월+상시 운영 인력)이, 그 종속의 실제 위험보다 컸나요?" 대부분의 서비스는 멀티클라우드도 에어갭도 아니었고, GitHub Actions로 충분했습니다. 진짜 Tekton이 필요했던 것은 규제로 온프레가 강제된 두 팀뿐이었습니다. 조치: 대부분의 팀을 GitHub Actions로 되돌리고, Tekton은 온프레가 필요한 팀에만. 교훈: **"벤더 종속 회피"는 그 자체로 목적이 아니라 비용-편익 계산입니다** — 종속의 위험이 실재하고(멀티클라우드·규제), 그것이 CI 플랫폼을 짓고 운영하는 비용보다 클 때만 Tekton이 정당합니다. "네이티브"라는 매력에 그 계산을 건너뛰면, 아무도 원치 않던 사내 CI 플랫폼을 유지보수하게 됩니다.
