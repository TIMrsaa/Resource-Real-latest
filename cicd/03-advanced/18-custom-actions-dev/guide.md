# 학습 가이드 — 소비자에서 생산자로

## 왜 액션을 직접 만드나

`uses:`로 남의 액션을 쓰는 것으로 대부분 충분합니다. 그런데 직접 만들 이유가 생깁니다:

1. **사내 반복 로직**: 조직 특유의 배포·검증·알림 로직 — 06의 composite/reusable로 부족할 때(복잡한 로직, 상태, API 호출)
2. **생태계 기여**: 유용한 도구를 마켓플레이스에 — 27의 기여 사다리(오픈소스 기여의 CI/CD판)
3. **액션 내부 이해**: 액션을 만들어보면 03에서 배운 실행 모델·보안·인젝션이 생산자 관점에서 완성됩니다

## 소비 지식이 생산으로 완성됩니다

03에서 우리는 소비자로 배웠습니다: 표현식은 셸 파싱 전에 치환됩니다(인젝션), 시크릿은 마스킹됩니다(인코딩 우회), permissions는 최소화합니다. 액션을 **만들면** 이것들이 반대편에서 보입니다:

```
소비자: "이 액션이 안전한가?"
생산자: "내 액션이 안전하다는 것을 어떻게 보증하나요?"
  - 입력을 어떻게 검증하나 (인젝션 방어의 생산자 버전)
  - 어떤 권한을 요구하나 (최소 권한을 액션이 강제)
  - 시크릿을 어떻게 다루나 (로그 노출 방지)
```

좋은 액션을 만드는 능력은 곧 나쁜 액션을 알아보는 능력입니다 — 03의 공급망 위험(pitfall 4)을 생산자 관점에서 이해하는 것.

## 세 종류의 선택

06에서 composite action(스텝 묶음)을 만들었습니다. 이 모듈은 **JavaScript 액션**(로직·API·상태가 필요한 것)에 집중합니다:

```
composite: 스텝 묶음 (06) — 셸 명령의 조합
Docker:    임의 도구/언어 — 무겁지만 자유 (컨테이너 시작 비용)
JavaScript: Node로 실행 — 빠르고 크로스플랫폼, 툴킷(@actions/*) 풍부 ← 이 모듈
```

JavaScript 액션이 마켓플레이스의 주류이고, GitHub Actions 툴킷(@actions/core, @actions/github)이 잘 갖춰져 있습니다.

## 테스트와 배포의 규율

액션도 소프트웨어입니다 — 05의 테스트 원리가 적용되고, 04·03의 버전/공급망 규율(SHA 고정)이 적용됩니다. lab-02는 액션을 배포하며 "내 액션을 쓰는 사람이 SHA로 고정할 수 있게" 만드는 것까지 다룹니다. 생산자로서 소비자의 안전을 책임지는 것.
