# 흔한 함정 5선

## 1. dist를 커밋 안 하거나 src와 불일치

JavaScript 액션은 `dist/index.js`(번들)를 실행하는데, 이것을 커밋 안 하면 소비자의 러너가 액션을 실행할 수 없습니다(node_modules가 없으니). 반대로 dist를 커밋하되 src를 고치고 재빌드를 잊으면 — **소비자는 낡은/다른 코드를 실행**합니다. verify-dist 워크플로(lab-02)로 "dist가 src에서 재현되는가"를 CI 게이트로 강제하세요. dist는 액션의 실제 실행물이자 공급망의 신뢰 지점입니다.

## 2. 입력을 검증 없이 셸/파일 경로에 사용

액션도 03의 인젝션에서 자유롭지 않습니다 — 사용자 입력(`core.getInput`)을 검증 없이 `exec`나 파일 경로에 쓰면, 악의적 입력이 경로 탈출(`../../etc`)이나 명령 주입을 합니다. @actions/core가 입력을 안전하게 가져오지만, 그 값을 어떻게 쓰느냐는 생산자 책임입니다. 경로는 정규화·화이트리스트, 명령은 인자 배열(셸 보간 회피). 내 액션을 쓰는 사람이 그것을 신뢰 경계 안에서 실행함을 기억하세요.

## 3. 과도한 권한 요구 또는 미문서화

액션이 필요 이상의 권한(예: `contents: write`, 시크릿 접근)을 요구하거나, 요구 권한을 문서화하지 않으면 — 소비자는 최소 권한을 줄 수 없고(03의 permissions 최소화가 불가능), 그 액션을 신뢰하기 어렵습니다. 생산자로서 "이 액션은 contents: read만 필요"를 명시하고, 실제로 그 이상을 쓰지 마세요. 넓은 권한을 요구하는 액션은 공급망 위험의 증폭기입니다(그 액션이 탈취되면 소비자의 넓은 권한이 공격자의 것).

## 4. 번들된 의존성의 취약점 방치

dist에 번들된 node_modules는 **소비자에게 배포되는 코드**입니다 — 그 취약점도 함께 배포됩니다. src만 보고 "내 코드는 안전하다"고 생각하지만, 의존성 트리의 취약점이 dist에 들어갑니다. npm audit을 CI 게이트로, Dependabot으로 갱신(그리고 dist 재빌드), 최소 의존성 원칙. 액션의 공급망은 내 코드 + 모든 의존성입니다.

## 5. 이동 태그(v1)를 소비자가 "안전하다"고 착각하게 방치

생산자가 `@v1` 이동 태그를 제공하는 것은 편의지만, 그것이 "움직인다"(새 릴리스마다 v1이 재지정)는 사실을 소비자가 모르면 — 03 pitfall 4의 위험(태그 탈취/변경)에 노출됩니다. README에 "프로덕션은 SHA 고정 권장"을 명시하고, v1 태그의 의미(major 안에서 자동 패치)를 설명하세요. 생산자로서 소비자의 안전한 사용을 안내하는 것이 책임의 일부입니다.

## 실무 사고 사례

> 인기 있던 오픈소스 GitHub Action이 공급망 공격의 통로가 됐습니다 — 유지보수자의 계정이 피싱으로 탈취됐고, 공격자는 그 액션의 dist/index.js에 악성 코드를 주입한 뒤 v1 이동 태그를 그 커밋으로 재지정했습니다. 핵심은 **src는 건드리지 않고 dist만 조작**한 것입니다: PR을 열지 않았고, 코드 리뷰를 우회했으며, src만 보는 사람에게는 정상으로 보였습니다. 그 액션을 `@v1`로 쓰던 수천 개 저장소가 다음 실행에서 악성 dist를 러너(시크릿이 있는 곳)에서 실행했고, 환경변수와 토큰이 유출됐습니다. 이 사건이 두 가지를 바꿨습니다: ① 소비자 측 — 액션을 SHA로 고정하는 관행이 확산(03의 규율), 그리고 조직 차원의 허용 액션 목록. ② 생산자 측 — dist 재현성 검증(lab-02 Step 3)이 표준이 됐습니다("dist가 src에서 나온 것"을 자동 증명해, dist만 조작하면 CI가 잡게). 교훈: **액션의 실제 실행물은 src가 아니라 dist이고, 그 둘의 일치를 보증하는 것이 생산자의 공급망 책임입니다** — 코드 리뷰가 src만 본다면, dist는 검증되지 않은 채 실행되는 코드입니다.
