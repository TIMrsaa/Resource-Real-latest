**Q2.** JavaScript 액션에서 dist/index.js를 커밋하는 이유는? 무엇으로 생성하나요?

**Q3.** 액션 로직을 @actions/core에서 분리하는 이유는? 05의 어떤 원리인가요?

**Q4.** 소비자가 액션을 참조하는 세 가지 방법과 각각의 안전성은?

**Q5.** "dist 재현성 검증"이 왜 생산자의 공급망 책임인가요?

**Q6.** 내 액션이 요구 권한을 문서화하고 최소화해야 하는 이유는? (03의 소비자 관점과 연결)

**Q7.** 번들된 dist의 의존성 취약점이 왜 소비자의 문제가 되는가요?

**Q8.** "src는 정상인데 dist만 조작된" 공급망 공격이 가능한 이유와, 그것을 막는 생산자 측 장치는?

## 정답

**A1.** composite(스텝 묶음 — 셸 조합, 06), Docker(임의 도구·언어 — 무겁지만 자유), JavaScript(로직·API·상태 — Node). JS가 주류인 이유: 빠른 시작(컨테이너 pull 없음), 크로스플랫폼, @actions/* 툴킷이 잘 갖춰져 로직·API·입출력 처리가 쉽습니다.

**A2.** 액션은 dist/index.js를 실행하는데, 그것이 node_modules 의존성을 포함해야 소비자가 npm install 없이 바로 실행할 수 있습니다. @vercel/ncc로 src와 모든 의존성을 단일 파일로 번들해 생성합니다(action.yml의 main이 dist를 가리킴).

**A3.** 로직을 순수 함수로 분리하면 러너·툴킷 없이 단위 테스트가 가능합니다 — 05의 "테스트 가능성은 설계의 성질"과 "아이스크림 콘 회피"(툴킷 통합 테스트는 얇게, 로직은 순수 함수로). @actions/core에 강결합하면 액션 전체를 e2e로만 테스트하게 되어 느리고 깨지기 쉽습니다.

**A4.** `@v1`(이동 태그 — major 안에서 자동 패치, 편하나 태그가 움직임), `@v1.0.0`(semver 릴리스 고정), `@<SHA>`(커밋 고정 — 불변, 가장 안전 — 03의 규율). 프로덕션은 SHA 고정 권장.

**A5.** 소비자가 실제로 실행하는 것은 src가 아니라 dist(번들)이므로, "커밋된 dist가 정말 이 src에서 나온 것"임을 보증해야 소비자가 dist를 신뢰할 수 있습니다. dist가 몰래 조작되면(src 리뷰를 우회한 악성 코드 주입) 소비자가 그것을 실행하게 되므로, verify-dist(재빌드 후 diff 검증)로 재현성을 CI 게이트로 강제하는 것이 생산자 책임입니다.

**A6.** 문서화 안 하면 소비자가 최소 권한을 줄 수 없고(03의 permissions 최소화 불가), 넓은 권한을 요구하는 액션은 탈취 시 소비자의 넓은 권한이 공격자의 것이 됩니다(공급망 위험 증폭). 생산자로서 "이 액션은 contents: read만"을 명시하고 실제로 그 이상 안 쓰는 것이, 소비자가 그 액션을 안전하게 신뢰 경계 안에서 쓸 수 있게 합니다.

**A7.** dist에 번들된 node_modules는 소비자에게 배포되어 러너에서 실행되는 코드입니다 — 그 의존성 트리의 취약점도 함께 배포됩니다. src 코드만 안전해도 의존성 취약점이 dist에 들어가 소비자의 러너(시크릿이 있는 곳)에서 실행되므로, npm audit·Dependabot·최소 의존성이 필요합니다. 액션의 공급망 = 내 코드 + 모든 의존성.

**A8.** JavaScript 액션의 실제 실행물은 dist인데 코드 리뷰는 대개 src만 봅니다 — dist는 번들이라 리뷰하기 어렵습니다. 공격자가 src를 안 건드리고 dist만 조작한 뒤 이동 태그(@v1)를 재지정하면, src 리뷰를 우회하고 악성 코드가 소비자 러너에서 실행됩니다. 생산자 측 장치: **dist 재현성 검증**(CI에서 src로 재빌드해 커밋된 dist와 diff — 불일치면 실패), 그리고 릴리스 서명(21).
