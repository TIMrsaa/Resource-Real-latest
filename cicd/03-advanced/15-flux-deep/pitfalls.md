# 흔한 함정 5선

## 1. 이미지 자동화를 프로덕션에 무통제로

Flux의 image-controller는 강력합니다 — 레지스트리에 새 이미지가 뜨면 자동으로 git을 갱신하고 배포합니다. 그런데 프로덕션에서 ImagePolicy를 "최신 태그"로 열어두면, **CI가 실수로 빌드한 이미지나 검증 안 된 빌드가 자동으로 프로덕션에 배포**됩니다. 통제: 프로덕션은 명시적 semver 범위(`>=1.2.0 <2.0.0`), 또는 자동 갱신 대신 PR(사람 리뷰), 또는 staging 검증 후 승격. 자동화가 강할수록 policy가 중요합니다 — eks 17 Karpenter의 limits와 같은 논리.

## 2. "Flux가 UI가 없어서 안 좋다"는 오해 (또는 그 반대)

Flux에 UI가 없는 것은 결함이 아니라 설계 선택입니다(유닉스 철학 — 툴킷). UI가 필요하면 Weave GitOps/Capacitor 같은 별도 대시보드를 붙입니다. 반대로 "ArgoCD는 무겁다"도 오해 — 그 무게는 통합 UI와 배포 플랫폼 기능의 대가입니다. 도구를 그 철학과 함께 평가하세요: UI 중심 문화면 ArgoCD, 조합·자동화 중심이면 Flux. "우열"이 아니라 "맞음"의 문제입니다(12의 교훈).

## 3. source-apply 분리를 이해 못 해 중복 source

Flux는 GitRepository(source)와 Kustomization(apply)이 분리돼 있어 **하나의 source를 여러 Kustomization이 공유**할 수 있습니다(재사용). 이것을 모르고 앱마다 GitRepository를 만들면 — 같은 git을 여러 번 폴링해 대역폭·부하가 늘고, 인증 설정이 중복됩니다. 같은 저장소면 GitRepository 하나, Kustomization 여럿(경로별). ArgoCD에서 온 사람이 "Application = source+apply"에 익숙해 놓치기 쉬운 지점.

## 4. 자동 커밋이 CI를 다시 트리거하는 루프

image-controller가 config repo에 자동 커밋하는데, 그 config repo가 CI 트리거에 걸려 있으면 — 자동 커밋 → CI 실행 → (혹시 이미지 재빌드) → 또 커밋의 루프가 생길 수 있습니다. 14의 교훈이 여기서도: app repo와 config repo 분리, 그리고 자동 커밋은 CI 트리거에서 제외(`[skip ci]` 또는 봇 커밋 필터). 자동화의 접점(git)은 루프의 위험 지점입니다.

## 5. GitOps 원칙을 도구 기능과 혼동

"우리는 ArgoCD를 쓰니 GitOps다" — 도구를 깔았다고 GitOps인 게 아닙니다. GitOps는 OpenGitOps 4원칙(선언·git 버전관리·자동 pull·지속 reconcile)이고, 도구는 그 구현입니다. ArgoCD를 깔고도 사람들이 여전히 `kubectl apply`로 배포하거나(selfHeal 끄고), 시크릿을 클러스터에 직접 만들거나, git 없이 UI로 변경하면 — GitOps가 아닙니다. 원칙을 지키는 규율이 본질이고 도구는 그것을 돕는 것뿐입니다(14 pitfall 5의 "GitOps는 규율").

## 실무 사고 사례

> 한 팀이 Flux 이미지 자동화를 전 환경에 적용했습니다 — CI가 이미지를 빌드하면 Flux가 자동으로 git을 갱신하고 배포하는, 완전 자동 파이프라인. 개발 속도가 극적으로 올랐습니다. 그런데 어느 금요일, 한 개발자가 실험용 브랜치에서 `latest` 태그로 디버그 이미지를 레지스트리에 push했습니다(프로덕션에 쓸 의도가 전혀 없이). 프로덕션의 ImagePolicy가 "가장 최근 태그"로 설정돼 있었기에 — Flux는 그 디버그 이미지를 프로덕션에 자동 배포했습니다. 디버그 빌드는 verbose 로깅과 프로파일러가 켜져 있어 성능이 1/10이었고, 주말 트래픽에서 서비스가 느려졌습니다. 아무도 "배포"를 하지 않았기에 원인을 찾는 데 오래 걸렸습니다 — 배포 이력을 봐도 사람의 배포가 없었으니까(자동 커밋만 있었습니다). 조치: ① 프로덕션 ImagePolicy를 명시적 semver 범위로(`>=1.0.0 <2.0.0`, 프리릴리스 제외) ② 프로덕션은 자동 갱신 대신 staging에서 검증 후 승격 PR ③ 레지스트리에 프로덕션용/실험용 태그 규약 분리. 교훈: **GitOps 자동화는 "누가 배포했나"를 git 커밋으로 답하지만, 자동 커밋은 그 답을 "봇"으로 만듭니다** — 자동화가 편할수록 무엇이 배포 자격이 있는지(policy)를 명시적으로 통제해야 합니다.
