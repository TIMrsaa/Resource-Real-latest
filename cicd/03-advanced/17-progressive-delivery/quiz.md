# 자가 점검 퀴즈

**Q1.** Progressive Delivery가 어떤 모듈들의 합류인지 설명하고, 각각이 무엇을 기여하는가요?

**Q2.** 11의 "지표 없는 카나리는 느린 배포"라는 지적에 Progressive Delivery는 어떻게 답하는가요?

**Q3.** Rollout이 Deployment와 다른 점 세 가지는?

**Q4.** AnalysisTemplate의 successCondition은 무엇을 코드화한 것인가요? 그 지표의 원천은?

**Q5.** Rollouts가 정밀한 트래픽 분할을 위해 필요로 하는 것과, 그것을 배운 곳은?

**Q6.** 자동 롤백이 01의 DORA 지표를 어떻게 개선하는가요?

**Q7.** 지표를 "절대값"이 아니라 "카나리 vs stable 비교"로 해야 하는 이유는?

**Q8.** Progressive Delivery가 막지 못하는 문제 유형 세 가지와, 그에 대한 대응은?

---

## 정답

**A1.** 11(카나리 = 관찰 후 확대, 그런데 관찰이 수동) + 14/15(GitOps = 배포가 선언) + eks 13(SLI = 무엇을 관찰할지) + eks 15(Prometheus = 메트릭 수집)의 합류. 이 넷이 합쳐져 "카나리 배포 → 메트릭 자동 분석 → 좋으면 자동 확대, 나쁘면 자동 롤백"이 됩니다.

**A2.** 11에서 사람이 대시보드를 보고 판단하던 것을 **AnalysisTemplate의 successCondition으로 코드화**합니다 — 지표(성공률·지연)가 배포의 자동 게이트가 되어, 카나리 각 단계에서 메트릭을 쿼리해 통과/롤백을 결정합니다. "관찰 후 확대"의 관찰이 사람에서 기계로.

**A3.** ① 카나리/블루그린을 네이티브 지원(Deployment는 롤링만). ② 단계별 트래픽 가중치(setWeight)와 pause. ③ 메트릭 자동 분석(AnalysisTemplate)과 자동 롤백. 11에서 replica 조작으로 흉내 낸 것이 1급 기능.

**A4.** 사람이 "오류율/지연을 보고 승격 여부를 판단"하던 것을 코드화 — 예: `successCondition: result >= 0.95`(성공률 95% 이상). 지표의 원천은 eks 15의 Prometheus(앱의 /metrics), 지표 자체는 eks 13의 SLI(성공률·p99).

**A5.** 트래픽 제공자와의 결합 — ALB 타깃 그룹 가중치(eks 14) 또는 Istio VirtualService 가중치(eks 20). Rollouts 자체는 트래픽을 못 나누고, 제공자 없이는 replica 비율 근사(11의 조잡한 방법)뿐입니다. 정밀 % 분할은 eks 14/20에서 배운 트래픽 관리가 하부가 됩니다.

**A6.** 변경 실패율↓(나쁜 배포가 카나리 단계에서 자동 차단되어 전체에 도달 안 함), 복구 시간(MTTR)↓(자동 롤백은 초 단위 — 사람이 알람 보고 반응하는 시간 제거), 배포 빈도↑(안전하니 자주 배포). 01의 "속도와 안정성은 상충하지 않는다"의 궁극적 실현.

**A7.** 절대값("성공률 95% 이상")은 배포와 무관한 외부 요인(하류 장애, 트래픽 급증)으로 성공률이 떨어졌을 때 멀쩡한 카나리를 롤백합니다. 카나리 vs stable 비교("카나리가 stable보다 유의미하게 나쁜가")는 배포 무관 변동이 양쪽에 똑같이 영향을 줘 상쇄되므로, 진짜 카나리의 문제만 감지합니다.

**A8.** ① 지표에 안 잡히는 느린 문제(메모리 누수 — 분석 기간엔 정상). ② 데이터 부작용/손상(즉시 안 나타남). ③ DB 스키마 변경(5%만 새 스키마를 쓸 수 없어 카나리 자체가 불가 — 11의 expand-contract 필요). 대응: 다중·장기 지표(postPromotion 분석), 배포 후 지속 모니터링(자동화가 경계심을 없애면 안 됨), 비가역 변경은 expand-contract 등 다른 안전장치.
