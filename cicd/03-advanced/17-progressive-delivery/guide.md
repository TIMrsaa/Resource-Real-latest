# 학습 가이드 — 세 갈래가 하나로 만나는 곳

## 여러 모듈이 여기서 합류합니다

이 모듈은 이 커리큘럼의 여러 실이 하나로 엮이는 매듭입니다:

```
11 (배포 전략):    카나리 = "관찰 후 확대" — 그런데 관찰이 사람이었습니다
14~15 (GitOps):    배포가 선언이 됨 — 그런데 카나리는 여전히 수동
eks 13 (측정):     SLI = 오류율·p99 — "무엇을 관찰할지"
eks 15 (메트릭):   Prometheus로 메트릭 수집
                        ↓ 이 넷이 합쳐지면
17 (Progressive Delivery):
  카나리를 배포하고 → 메트릭을 자동 분석 → 좋으면 자동 확대, 나쁘면 자동 롤백
```

11에서 "지표 없는 카나리는 그냥 느린 배포"라고 강조했습니다. 이 모듈이 그 지적의 해답입니다 — **지표가 배포의 자동 게이트**가 되어, 사람이 대시보드를 지켜보며 판단하던 것을 기계가 대신합니다.

## 왜 이것이 "안전의 완성"인가

배포 안전의 진화:

```
수동 배포:        사람이 kubectl apply, 사람이 관찰, 사람이 롤백
CI/CD 자동화:     파이프라인이 배포, 사람이 관찰
GitOps:           git이 배포, 사람이 관찰
Progressive:      자동 배포 + 자동 관찰 + 자동 롤백 ← 사람이 루프에서 빠짐
```

01의 DORA 지표로 보면: 변경 실패율↓(나쁜 배포가 5%에서 자동 차단), 복구 시간↓(자동 롤백은 초 단위). 그리고 배포 빈도↑(안전하니 자주). "속도와 안정성은 상충하지 않는다"(01)의 궁극적 실현.

## 사람이 완전히 빠지는가요?

아닙니다 — 사람은 **루프 밖으로** 이동합니다:

```
루프 안(제거됨): 매 배포마다 대시보드 보며 판단
루프 밖(남음):   무엇을 지표로 삼을지 설계, 임계값 결정, 분석 실패 시 조사
```

이것이 SRE의 사상입니다 — 반복적 판단을 자동화하고, 사람은 시스템 설계에 집중. 그리고 자동화의 품질은 **지표 설계**가 정합니다(lab-02의 핵심). 잘못된 지표는 나쁜 배포를 통과시키거나 좋은 배포를 막습니다.

## 도구: Argo Rollouts vs Flagger

- **Argo Rollouts**: ArgoCD 생태계(14), Rollout이라는 Deployment 대체 CRD
- **Flagger**: Flux 생태계(15), 기존 Deployment에 얹음

둘 다 같은 일(메트릭 기반 progressive delivery)을 하되 접근이 다릅니다. 이 모듈은 Argo Rollouts로 실습하고 Flagger를 비교합니다 — 14/15의 GitOps 도구 선택과 짝을 이룹니다.
