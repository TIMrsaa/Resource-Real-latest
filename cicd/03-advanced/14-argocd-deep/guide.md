# 학습 가이드 — 화살표의 방향을 뒤집습니다

## 이 파트의 가장 큰 전환

01에서 "push CD vs pull CD"를 이 파트의 큰 분기점이라고 예고했습니다. 이제 그 pull 쪽으로 넘어갑니다.

```
push CD (지금까지):
  파이프라인 ──kubectl apply──▶ 클러스터
  - 파이프라인이 클러스터 자격증명을 가짐 (유출 위험)
  - "무엇이 배포됐나"는 파이프라인 로그에 (휘발적)
  - 드리프트(누가 kubectl로 손댐)를 아무도 모름

pull CD (GitOps):
  파이프라인 ──git push──▶ git ◀──당겨옴── 클러스터 안 컨트롤러(ArgoCD)
  - 파이프라인은 git 쓰기 권한만 (클러스터 자격증명 불필요!)
  - "무엇이 배포됐나" = git의 현재 상태 (감사·롤백이 git)
  - 드리프트를 컨트롤러가 감지·교정
```

화살표의 방향 하나가 바꾸는 것이 이렇게 많습니다. 이것이 GitOps가 단순한 도구가 아니라 **패러다임**인 이유입니다.

## k8s 39·eks 23과의 관계

k8s 39에서 GitOps의 원리(선언·버전관리·자동조정·drift)와 ArgoCD를 이미 만났습니다. eks 23에서 fleet 표준화(base/overlay + ApplicationSet)를 봤습니다. 이 모듈은 그 둘을 **CI/CD 파이프라인의 완성**으로 통합합니다:

```
CI(03~13): 코드 → 테스트 → 이미지 빌드 → 레지스트리 (+ git의 매니페스트 업데이트)
CD(GitOps): ArgoCD가 git을 보고 클러스터를 맞춥니다
```

CI와 CD가 **git에서 만납니다** — CI의 끝은 "이미지를 만들고 git의 매니페스트를 새 다이제스트로 업데이트"(04의 다이제스트!)이고, CD의 시작은 "그 git 변경을 감지"다. 둘의 접점이 git이라는 것이 GitOps의 우아함이자 경계 문제(§lab-02)입니다.

## reconcile 루프를 이해하세요

ArgoCD의 심장은 reconcile 루프입니다 — k8s 컨트롤러(k8s 30)의 그 패턴입니다: **desired(git) vs live(클러스터)를 비교하고 차이를 좁힙니다.** 이것을 이해하면 sync/health/drift/selfHeal이 전부 이 한 루프의 변주임이 보입니다. Karpenter(eks 17), Velero(k8s 36)와 같은 구조 — 우리는 이미 이 패턴을 여러 번 만났습니다.

## 경계를 정직하게

GitOps는 아름답지만 경계가 있습니다: 시크릿을 git에 어떻게(평문 금지), 이미지 태그를 누가 업데이트하나, CI와 CD의 책임 분계. lab-02가 이 경계를 다룹니다 — 도구를 미화하지 않고 그 한계까지 배우는 것이 이 커리큘럼의 방식입니다.
