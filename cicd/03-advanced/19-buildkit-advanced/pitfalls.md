# 흔한 함정 5선

## 1. 캐시 익스포트에 mode=min (멀티스테이지 배신)

`--cache-to type=registry`만 쓰고 mode를 안 정하면 **min** — 최종 스테이지 레이어만 익스포트됩니다. 멀티스테이지(04)에서는 비싼 빌드 스테이지 캐시가 통째로 빠져, "캐시를 붙였는데 CI가 매번 풀빌드"가 됩니다. lab-01 Step 4에서 숫자로 확인했습니다: 멀티스테이지 + 캐시 익스포트는 **mode=max**. 단 max는 캐시 크기가 커지므로(중간 스테이지 전부) gha 타입의 10GB 한도를 감시하세요.

## 2. QEMU 에뮬레이션으로 컴파일까지 돌리기

`setup-qemu-action`만 넣으면 멀티아치가 "되기는" 합니다 — 그리고 arm64 빌드가 10배 느려진 채 아무도 원인을 모릅니다. 컴파일 같은 CPU 집약 작업이 명령어 단위 번역 위에서 돌기 때문입니다. 크로스 컴파일 가능한 언어(Go/Rust)는 `FROM --platform=$BUILDPLATFORM` + `TARGETARCH` 패턴으로 빌드를 네이티브에서 돌리고, 안 되는 언어는 네이티브 arm64 러너(GHA `ubuntu-24.04-arm`, 08의 ARC+Graviton)를 써라. QEMU는 "설정이 제일 쉬운" 방법이지 "옳은" 방법이 아닙니다.

## 3. 단일 아치 이미지에 멀티아치 태그 기대

`docker build`(기본 driver, 단일 아치)로 만든 이미지를 Graviton 노드그룹에 배포하면 `exec format error`(eks 19). 반대로 `--platform` 두 개로 빌드해도 `--push` 없이 `--load`만 하면 로컬 데몬은 단일 아치만 받습니다(데몬이 index를 저장 못 함). 멀티아치는 **레지스트리에 push해야 index가 삽니다** — 그리고 다이제스트 고정(04)은 아치별 manifest가 아니라 **index의 digest**로 해야 두 아치가 모두 고정됩니다.

## 4. dockerfile frontend 버전 방치

`# syntax=docker/dockerfile:1.7` 첫 줄이 없으면 데몬에 내장된 기본 frontend를 씁니다 — 팀원마다/러너마다 데몬 버전이 달라 **같은 Dockerfile이 다르게 동작**할 수 있습니다(새 문법이 어디선 되고 어디선 안 됨). frontend는 이미지로 배포되므로 첫 줄에 버전을 명시하면 데몬과 무관하게 고정됩니다. 04의 "다이제스트 고정"과 같은 규율의 frontend판 — 빌드 도구 자체도 버전 고정 대상입니다.

## 5. kaniko를 신규 도입 (아카이브된 도구)

"K8s에서 특권 없이 빌드 = kaniko"는 오래 상식이었지만 **2025년 저장소가 아카이브**됐습니다(유지보수 종료 — CVE 대응도 없음). 검색 결과와 블로그는 여전히 kaniko를 권하므로 주의. 신규는 BuildKit rootless나 원격 buildkitd(driver=remote)로, 기존 kaniko 파이프라인은 이전 계획을 세워라. 교훈은 도구를 넘어섭니다: **CI 도구도 공급망입니다** — 유지보수 상태(마지막 릴리스, 아카이브 여부)를 도입 기준에 넣어라(21의 관점).

## 실무 사고 사례

> 한 팀이 비용 절감을 위해 서비스를 Graviton(arm64)으로 이전하기로 했습니다(eks 19). CI에 `setup-qemu-action` 한 줄을 추가해 `--platform linux/amd64,linux/arm64` 빌드를 켰고 — 빌드 시간이 8분에서 52분이 됐습니다. C++ 의존성을 컴파일하는 스테이지가 QEMU 위에서 돌았기 때문입니다. 더 나쁜 것: 빌드가 느려지자 팀은 캐시를 붙였는데(`cache-to type=gha`) mode를 안 정해 min이 됐고, 멀티스테이지의 빌드 스테이지는 여전히 매번 풀빌드였습니다. "멀티아치는 원래 느리다"는 체념이 몇 달 갔습니다. 해결은 두 수였습니다: ① 빌드 스테이지를 `FROM --platform=$BUILDPLATFORM`으로 바꾸고 크로스 컴파일이 안 되는 C++ 부분만 네이티브 arm64 러너 잡으로 분리(매트릭스로 아치별 빌드 후 `imagetools create`로 index 병합) — 52분 → 11분. ② 캐시를 mode=max로 — 11분 → 4분. 교훈: **멀티아치의 비용은 "어디서 에뮬레이션이 도는가"가 결정합니다** — 로그의 스테이지별 시간을 보면 QEMU 위에서 도는 정점이 보입니다. 빌드가 느리면 체념하지 말고 솔버의 기록(어느 정점이 왜 오래·왜 미스)을 읽어라.
