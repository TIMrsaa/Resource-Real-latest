# 학습 가이드 — 모노레포는 저장 전략이 아니라 빌드 전략입니다

## 왜 모노레포인가 (그리고 왜 CI가 문제인가)

여러 서비스를 한 저장소에 두는 이유는 명확합니다: **원자적 변경**(공유 라이브러리와 그 소비자를 한 커밋·한 PR로), 단일 버전(의존성 지옥 회피), 공통 도구. Google·Meta가 전사 모노레포인 이유입니다.

대가는 CI에 옵니다. 폴리레포에서는 "저장소 = 빌드 단위"라 공짜였던 질문을 이제 직접 답해야 합니다:

```
폴리레포: 이 저장소에 커밋 → 이 저장소를 빌드 (자명)
모노레포: 이 저장소에 커밋 → ??? 를 빌드
           전부 빌드      → 커밋당 40분, 90%는 낭비 (01의 피드백 루프 붕괴)
           바뀐 폴더만    → 공유 lib 변경이 소비자를 안 돌림 (침묵의 회귀)
           영향받은 것만  → ★ 이것이 모노레포 CI의 전부
```

## "affected"의 3단계 사다리

```
1단계  path filter      "어느 파일이 바뀌었나" — 폴더 매핑, 의존성 무지
2단계  의존성 그래프     "바뀐 프로젝트 + 그것에 의존하는 모든 것" — Nx/Turborepo
3단계  Bazel            "바뀐 타깃 + 역의존 타깃" — 파일보다 촘촘한 단위, 밀폐 빌드
```

위로 갈수록 정확하고(낭비·누락 모두 감소) 도입 비용이 큽니다. 대부분의 팀은 2단계가 답이고, 3단계는 수천 명 규모의 답입니다 — 이 모듈은 2단계를 실습하고 3단계는 원리만 이해합니다.

## 19와의 연결 — 캐시는 한 가지 아이디어입니다

19에서 BuildKit 캐시 키가 "연산 + 입력의 digest"였습니다. Nx/Turborepo/Bazel의 캐시도 정확히 같습니다: **태스크의 입력(소스·의존성·설정)을 해시해서, 같은 해시면 저장된 출력을 재사용**. 층만 다릅니다 — BuildKit은 이미지 레이어, 빌드 도구는 태스크 출력(dist/, 테스트 결과). 원격 캐시를 붙이면 "동료가 이미 빌드한 것을 내 CI가 재사용"까지 갑니다. 캐시 원리를 한 번 이해하면 세 도구가 모두 같은 도구로 보입니다.

## 03의 `ci` 게이트가 모노레포에서 필수가 되는 이유

프로젝트별로 잡을 스킵하면(affected가 아니니까) required check가 "expected" 상태로 영원히 기다리는 함정이 있습니다 — GitHub은 "스킵된 required check"를 통과로 안 쳐줍니다. 03에서 만든 **단일 `ci` 게이트 잡**(모든 잡을 needs로 모아 결과를 판정)이 모노레포에서는 선택이 아니라 구조적 필수가 됩니다. lab-02에서 이 함정을 직접 밟고 고칩니다.
