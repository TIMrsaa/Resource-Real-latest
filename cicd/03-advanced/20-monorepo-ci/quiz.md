# 자가 점검 퀴즈

**Q1.** 모노레포 CI의 본질 질문은 무엇이고, "전부 실행"과 "path filter"는 각각 어느 축(낭비/누락)에서 실패하나요?

**Q2.** path filter의 맹점을 "공유 라이브러리" 시나리오로 설명하세요. 필터 목록에 lib 경로를 수동 추가하는 것이 왜 근본 해법이 아닌가?

**Q3.** 그래프 기반 affected의 계산 규칙은? Nx/Turborepo는 그래프를 어디서 얻나요?

**Q4.** Turborepo/Nx의 태스크 캐시와 19의 BuildKit 캐시의 공통 원리는? 캐시가 "낡은 출력을 재생"하는 조건은?

**Q5.** Bazel이 Nx/Turbo와 본질적으로 다른 지점 하나와, 그 대가·보상은?

**Q6.** affected 기반 동적 매트릭스에서 required check를 잘못 설정하면 생기는 함정과 해법은?

**Q7.** affected 계산이 CI에서 "매번 전체"로 나오는 흔한 원인 두 가지는?

**Q8.** 원격 캐시에 포크 PR이 쓰기 가능하면 왜 공급망 문제가 되나요?

---

## 정답

**A1.** "이 변경이 무엇에 영향을 주는가(affected)". 전부 실행은 낭비 축에서 실패(커밋당 전체 빌드 — 피드백 루프 붕괴, 01), path filter는 누락 축에서 실패(의존성 무지 — 침묵의 회귀). 그래프 affected가 두 축을 동시에 잡습니다.

**A2.** `libs/shared`를 api·web이 import하는데, `paths: ['services/api/**']` 필터는 shared 변경 시 api 테스트를 안 돌립니다 — shared의 파괴적 변경이 테스트 없이 머지됩니다(침묵의 회귀). 수동 추가는 의존성 그래프를 YAML에 복사하는 것 — 새 import/새 패키지마다 갱신이 필요하고 아무도 갱신하지 않으므로 사본은 반드시 낡습니다. 그래프는 코드에서 자동 추출되어야 합니다.

**A3.** affected = 변경 파일의 소유 프로젝트 + 그것에 의존하는(역방향) 전이 의존자 전부. 그래프는 package.json workspaces의 dependencies와 import 분석에서 자동 추출 — 사람이 관리하는 목록이 없습니다.

**A4.** 공통 원리: 해시(연산+입력) → 같으면 저장된 출력 재사용. BuildKit은 이미지 레이어 층에서(정점 digest), 빌드 도구는 태스크 출력 층에서(소스+의존 출력+설정의 해시). 낡은 재생 조건: 태스크가 **선언 안 된 입력**(환경변수·전역 설정·생성 코드)에 실제로 의존할 때 — 그 입력이 바뀌어도 해시가 안 바뀌어 옛 출력이 나옵니다(캐시 오염, 25).

**A5.** 밀폐성(hermeticity)의 강제 — BUILD 파일로 의존을 명시 선언하고 샌드박스가 선언 밖 접근을 차단합니다. 대가: 빌드 정의 전면 재작성 수준의 도입 비용, 다언어 도구 체인 학습. 보상: 캐시를 "믿을 수 있게" 됨(선언이 거짓일 수 없으므로) — 타깃 단위 affected와 원격 실행(빌드 팜)이 안전해집니다. 수천 명·다언어 규모의 답.

**A6.** 함정: 매트릭스 잡 이름(예: "test (@mono/web)")을 required check로 걸면, 그 프로젝트가 affected가 아닌 PR에서 잡이 생성 안 되고 GitHub이 "expected" 상태로 무한 대기 — 머지 불가. 해법: `if: always()`로 항상 실행되는 단일 `ci` 게이트 잡(03) 하나만 required로 걸고, 게이트 안에서 needs 결과를 판정(success/skipped 통과, failure 차단). 매트릭스가 어떻게 변해도 required check는 불변.

**A7.** ① 얕은 클론(fetch-depth: 1) — base 커밋이 없어 diff 계산 불가, 도구가 안전하게 전체로 폴백. ② 루트/전역 파일(tsconfig, lockfile, turbo.json 자체)의 변경 — 도구가 전역 의존으로 취급해 전부 affected 처리. 전자는 fetch-depth: 0으로 고치고, 후자는 정상 동작(감수)입니다.

**A8.** 원격 캐시는 "한 명의 빌드 출력을 모두가 재실행 없이 재사용"이므로, 캐시 쓰기 권한 = 모두의 빌드 산출물 주입 권한입니다. 포크 PR(신뢰 경계 밖, 03)이 쓰기 가능하면 악성 출력물을 캐시에 심을 수 있고, main의 CI가 같은 해시에서 그것을 재생해 서명·배포(21)까지 흘러갑니다. 쓰기는 신뢰된 브랜치 CI만, PR은 읽기 전용 — 캐시도 공급망의 일부입니다.
