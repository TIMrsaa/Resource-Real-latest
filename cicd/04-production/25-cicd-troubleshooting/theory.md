# 이론 — 진단 방법론과 진단 카드 10장

> **🌱 17세 눈높이 비유: 학교 방송 시스템 고장**
> - 축제 안내 방송이 안 나옵니다. 용의자는 다섯: 원고(코드), 아나운서의 컨디션(flaky), 방송 절차서(파이프라인 정의), 방송실 장비(인프라), 방송국 전체 정전(플랫폼)
> - **첫 분류 3질문** = "항상 안 나오나, 가끔인가요?" "우리 반만인가, 전교인가요?" "어제까지 됐는데 뭐가 바뀌었나요?"
> - **거짓 초록불** = "방송 나갔습니다" 램프는 켜졌는데 스피커에선 지난주 녹음이 나옴 — 램프(잡 성공)가 아니라 스피커(실제 배포물)를 확인해야
> - **재귀성** = 방송 시스템 고장을 알리는 방송을 할 수 없습니다 — 비상 확성기(break-glass)가 미리 있어야

---

## 1. 진단 방법론 — 3질문 분류기

```
Q1. 항상 실패 vs 간헐?
    항상 → 코드/정의/설정 (결정적 원인)         간헐 → flaky/인프라/플랫폼 (비결정적)
Q2. 나만 vs 전원? (한 저장소 vs 조직 전체)
    나만 → 내 커밋/내 워크플로                  전원 → 러너 풀/플랫폼/조직 정책 변경(24)
Q3. 무엇이 변했나요?
    커밋 diff / 워크플로 diff / 의존성 갱신 / 러너 이미지 갱신 / 플랫폼 status 페이지
    ★ "아무것도 안 바꿨는데"는 없습니다 — 안 보이는 변경(러너 이미지, 액션의 이동 태그, 의존성 범위)이 있을 뿐
```

분류 후 해당 카드로. 각 카드: **증상 → 가설 순서(확률순) → 확인 → 처방**.

## 2. 진단 카드 10장

### 카드 1 — 캐시 오염: "고쳤는데 옛 결과" (19·20)

```
증상: 코드를 고쳤는데 CI 산출물/결과가 옛것. 또는 로컬은 되는데 CI만 이상한 실패
가설: ① 캐시 키가 입력을 안 담음 (lockfile 해시 없이 고정 키)
      ② 태스크의 미선언 입력 (20 — 환경변수·전역 설정이 해시 밖)
      ③ 부분 저장된 캐시 (저장 중 취소 → 반쪽 node_modules)
확인: 캐시 키 출력 · "키가 언제 바뀌나" 역추적 · 캐시 없이 재실행(키에 run_id 붙여) → 되면 확정
처방: 키에 입력 해시 포함(hashFiles) · 캐시 무효화(키 버전 접두사 v2-) · 미선언 입력 선언
예방: 캐시는 "지워도 되는 것"만 — 정확성이 캐시에 의존하면 설계 오류
```

### 카드 2 — 러너 고갈: queue 폭증 (08·23)

```
증상: 잡이 pending에 수십 분. 전원 영향
가설: ① 피크 λ > 러너 용량 (L=λW — 23) ② 라벨 불일치(특정 라벨만 병목)
      ③ ARC 스케일 실패(노드 부족 — eks 17) ④ 러너가 좀비(잡 잡고 안 놓음)
확인: queue time 지표(23) · 라벨별 대기 분해 · ARC면 kubectl get pods(러너 Pod 상태)
처방: 증설(오토스케일 상한) · 잡 다이어트(affected — 20) · 좀비 정리(ephemeral이면 자동 — 08)
예방: queue p90 SLO + 용량 계획(L=λW), 피크 시간 스케줄 잡 이동
```

### 카드 3 — 동시성 데드락/직렬화 (03·06)

```
증상: 잡이 서로/자신을 기다림. 배포가 "in progress"인 채 영원
가설: ① concurrency group 충돌 — 같은 그룹의 배포가 승인 대기 중, 새 런이 뒤에 줄섬
      ② cancel-in-progress: true가 배포 도중 취소 → 반쪽 배포(!)
      ③ environment 승인 대기가 그룹을 점유
확인: 그룹명 규칙 점검(워크플로·브랜치 조합) · waiting 런 목록
처방: 대기 런 취소 → 원인 그룹 재설계 (배포는 cancel-in-progress 금지, queue로)
예방: 배포 워크플로의 concurrency는 "그룹당 1개 + 대기", 취소는 CI(테스트)에만
```

### 카드 4 — OIDC/인증 실패 (07·21)

```
증상: "Not authorized to perform sts:AssumeRoleWithWebIdentity" 류. 특정 브랜치/이벤트만
가설: ① sub 조건과 실제 클레임 불일치 (환경 추가·브랜치 개명·PR→push 트리거 변화)
      ② id-token: write 누락 ③ 만료(장기 실행 잡에서 늦게 사용) ④ 신뢰 정책의 저장소 개명 미반영
확인: 토큰 클레임 디코드(07의 방법) vs 역할 신뢰 정책 diff
처방: sub 템플릿 수정 — 단 넓히지 말 것(와일드카드 남발은 07 pitfall)
예방: sub 표준을 조직 정책으로(24), 저장소 개명 체크리스트에 신뢰 정책 포함
```

### 카드 5 — "로컬은 되는데 CI 실패"

```
증상: 개발자 기계에서 초록, CI에서 빨강 (항상)
가설: ① 버전 차이(node/go/docker — 러너 이미지 갱신!) ② 대소문자(맥 개발자 → 리눅스 러너)
      ③ 병렬성/리소스(CI 2코어 — 타임아웃) ④ 미커밋 파일(.gitignore에 들어간 필수 파일)
      ⑤ 환경변수/로캘/타임존
확인: CI 로그의 버전 출력 vs 로컬 · git status --ignored · CI와 같은 컨테이너로 로컬 재현
처방: 버전 고정(.tool-versions, 컨테이너 빌드 — 04) — "같은 환경"을 만들면 부류 전체가 소멸
예방: 빌드를 컨테이너 안으로(로컬도 CI도 같은 이미지) — 19의 재현성
```

### 카드 6 — 간헐 실패: flaky vs 인프라 (23)

```
증상: 같은 커밋 재실행 시 결과가 갈림
가설: ① 테스트 flaky(타이밍·순서·외부 의존 — 05) ② 인프라(러너 디스크·네트워크·레지스트리)
분류법: 실패 지점이 "테스트 스텝"이면 ① / "설치·pull·프로비저닝"이면 ②
처방: ①은 격리(quarantine — 05·23), 재시도 금지 / ②는 재시도 허용 + 집계(23)
예방: "재시도로 성공한 런 %" 대시보드 — 이 카드로 오는 사건 수 자체가 지표
```

### 카드 7 — GitOps sync 실패/드리프트 루프 (14·15)

```
증상: ArgoCD가 OutOfSync ↔ Synced를 반복, 또는 sync가 영원히 Progressing
가설: ① 필드 소유권 다툼 — HPA가 replicas를 바꾸는데 Git에도 replicas가 있음(14의 함정)
      ② 웹훅 유실로 반영 지연(poll 간격 대기 — 15) ③ 헬스체크가 커스텀 리소스를 몰라 Progressing
      ④ prune 대상이 수동 생성 리소스를 삭제(selfHeal의 양날)
확인: app diff로 어떤 필드가 튀는지 · 컨트롤러 로그 · lastTransitionTime
처방: ①은 Git에서 그 필드 제거(ignoreDifferences는 차선) ③은 커스텀 헬스체크
예방: "누가 이 필드의 주인인가"를 매니페스트 설계 시 결정(14)
```

### 카드 8 — 레지스트리/아티팩트: rate limit·소실 (04)

```
증상: pull 실패(429 Too Many Requests), 태그는 있는데 다이제스트 불일치, 태그 소실
가설: ① Docker Hub 익명 rate limit(러너 IP 공유 — 특히 self-hosted NAT 뒤) 
      ② 레지스트리 GC/보존 정책이 태그 삭제 ③ 태그 재사용(누가 같은 태그로 덮음)
확인: 에러 코드(429 vs 404) · imagetools inspect로 현재 다이제스트 vs 기록(감사 — 24)
처방: ①미러/프록시 캐시·인증 pull ②보존 정책에서 배포 태그 제외 ③불변 태그 정책(ECR IMMUTABLE)
예방: 배포는 다이제스트로(04) — 태그 사고 부류 전체에 면역
```

### 카드 9 — 거짓 초록: "배포 성공, 옛 버전이 돎" (04·17)

```
증상: 파이프라인 초록, 프로덕션은 옛 코드
가설: ① :latest 재사용 + imagePullPolicy: IfNotPresent (노드가 캐시된 옛 이미지 사용)
      ② 매니페스트 갱신 누락(이미지는 push됐는데 태그 문자열이 그대로 → K8s는 "변경 없음")
      ③ 롤링 미완료/멈춤(PDB·리소스 부족)인데 잡은 apply까지만 확인
      ④ 다른 클러스터/네임스페이스에 배포(컨텍스트 실수)
확인: kubectl get pod -o jsonpath 로 실행 중 imageID(다이제스트!) vs 의도한 다이제스트
처방: 다이제스트 배포(04) + 배포 후 검증 스텝("rollout status + 다이제스트 대조" — 24의 Knight 교훈)
예방: "성공 = apply 리턴"이 아니라 "성공 = 의도한 다이제스트가 Ready" 로 정의
```

### 카드 10 — 파이프라인 자체의 변경 사고 (24)

```
증상: 어느 순간부터 전 저장소/전 팀의 CI가 실패 — 코드는 아무도 안 바꿈
가설: ① 공유 reusable workflow/사내 액션의 변경(골든 패스의 중앙화 리스크 — 06·24)
      ② 조직 정책 변경(허용 액션 목록·required workflow 추가)
      ③ 러너 이미지 갱신(설치 도구 버전 점프) ④ 외부 액션의 이동 태그가 움직임(03)
확인: Q2에서 "전원"이면 이 카드 직행 — 공유 자원의 변경 이력(golden path 저장소의 최근 머지)
처방: 공유 워크플로 롤백 → 원인 수정 후 재배포
예방: reusable workflow도 버전 태그로 참조(소비자가 @v1 고정 — 06), 골든 패스 변경도 카나리(일부 저장소 먼저)
```

## 3. 조직 대응 — 파이프라인 온콜의 규율

```
선언: main CI 연속 실패 = 인시던트 선언 + "머지 동결" 공지 (녹색 복구가 최우선 — 깨진 main 위에 쌓지 않기)
역할: 파이프라인에도 온콜이 있습니다 (23의 페이지 조건) — "모두의 문제"는 아무의 문제도 아닙니다
재귀 대비: 수정 PR이 게이트를 못 지나는 경우의 break-glass 절차(24)가 문서로 존재해야
사후: 포스트모템 → 재발 방지를 "다짐"이 아니라 게이트로 (카드의 "예방" 행들이 전부 이것)
```
