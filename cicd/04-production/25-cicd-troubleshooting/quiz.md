## 정답

**A1.** 재귀성: 수정 PR도 고장난 파이프라인을 지나야 함 — 대비: 사전 정의된 break-glass 절차(24, 기록·자동 복원 포함). 다층성: 원인이 코드/flaky/정의/인프라/플랫폼 5층 어디에나 — 대비: 3질문 분류로 층을 먼저 좁힘. 침묵성: 거짓 초록(성공인데 실패)이 몇 주를 삶 — 대비: 성공의 재정의(의도한 다이제스트가 Ready, 테스트 N건 이상 실행 등 검증 스텝).

**A2.** ① 항상 vs 간헐 — 항상이면 결정적 원인(코드·정의·설정), 간헐이면 비결정적(flaky·인프라·플랫폼). ② 나만 vs 전원 — 나만이면 내 커밋/워크플로, 전원이면 공유 자원(러너 풀·골든 패스·조직 정책·플랫폼). ③ 무엇이 변했나 — 커밋·워크플로·의존성·러너 이미지·플랫폼 공지의 diff. "아무것도 안 바꿨는데"는 존재하지 않습니다 — 안 보이는 변경(러너 이미지 갱신, 참조 중인 액션의 이동 태그, 의존성의 범위 해석)이 있을 뿐이므로, 보이지 않는 변경 목록을 순서대로 확인합니다.

**A3.** 확정 진단: 캐시를 우회한 재실행(키에 run_id 등을 붙여 강제 미스) — 그러면 정상인데 캐시 켜면 재발할 때 확정. 처방: ① 키에 입력 해시 포함(hashFiles(lockfile) — 키가 입력의 함수가 되게) ② 키 버전 접두사 증가(v1-→v2-)로 오염된 기존 캐시 즉시 무효화. 예방 원칙: 정확성이 캐시에 의존하면 설계 오류 — 캐시는 지워도 결과가 같아야 합니다.

**A4.** 셋: ① concurrency group으로 배포 직렬화(동시 배포 방지 — 옳음) ② cancel-in-progress: false(배포 중단 금지 — 옳음) ③ environment 사람 승인(prod 통제 — 옳음). 메커니즘: 승인 대기(waiting) 상태가 그룹 슬롯을 점유 → 후속 배포가 전부 뒤에 줄섬 → 승인자 부재 시 무한 대기. 재설계: 승인 단계를 concurrency 그룹 밖으로 분리(승인 잡과 배포 잡 분리 — 그룹은 실제 배포 구간만 점유), 또는 대기 시한 초과 시 자동 취소 정책.

**A5.** 원인: ① :latest 재사용 + IfNotPresent(노드가 캐시된 옛 이미지 사용) ② 이미지 push는 됐는데 매니페스트의 태그 문자열이 불변 → K8s가 "변경 없음" 처리 ③ apply는 성공했으나 롤링이 PDB·리소스 부족으로 미완/멈춤인데 잡은 apply까지만 확인. 성공의 재정의: "apply 리턴 = 성공"이 아니라 "rollout 완료 + 실행 중 imageID(다이제스트)가 파이프라인이 push한 다이제스트와 일치 = 성공" — 이 검증 스텝이 부류 전체의 백신(Knight의 교훈, 24).

**A6.** 전원 실패는 개별 저장소의 커밋으로 설명 불가 — 전 저장소가 공유하는 것(reusable workflow·사내 액션·조직 정책·러너 풀·플랫폼)만이 원인일 수 있으므로 공유 자원 변경 이력 직행이 논리적 최단 경로입니다. 예방: ① 소비자가 골든 패스를 버전 태그(@v1)로 고정 — @main 참조는 머지 즉시 전파(06) ② 골든 패스 변경의 카나리 배포 — 소수 저장소에 먼저 적용 후 전파(17의 점진 배포를 파이프라인 자체에).

**A7.** 구멍: "실패 0건 = 성공"의 판정이 "실행 0건"을 통과시킴 — 수집 글롭 오타·경로 변경으로 테스트가 하나도 안 잡혀도 초록. 백신: 최소 실행 수 게이트(tests > 0, 또는 이전 런 대비 급감 경보). 같은 계열: 커버리지 급락 경보(05 — 커버리지가 갑자기 떨어지면 테스트가 수집에서 빠진 신호), 배포 후 다이제스트 대조(카드 9 — "됐다"의 검증).

**A8.** 망치는 것: ① 원인이 통계에서 사라져 영구 방치(flaky 마취제 — 23) ② 결정적 원인(캐시 오염·거짓 초록)의 간헐 오분류 ③ "재실행하면 돼" 문화로 초록불 신뢰 붕괴(05의 깨진 유리창). 올바른 용도: 진단 실험 — "같은 SHA에서 결과가 갈리는가"(카드 6의 flaky 판별), "캐시 우회 시 정상인가"(카드 1의 확정) 등 가설 검증 도구로 쓰고, 결과를 기록합니다.
