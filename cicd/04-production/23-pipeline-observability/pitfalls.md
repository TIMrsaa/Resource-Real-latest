# 흔한 함정 5선

## 1. DORA를 팀 평가 지표로 사용

DORA가 성과 평가에 들어가는 순간 굿하트의 법칙이 작동합니다 — 커밋을 쪼개 리드타임을 낮추고, 무의미한 배포로 빈도를 올리고, "사고"의 정의를 좁혀 실패율을 낮춥니다. 숫자는 좋아지고 실제 전달 능력은 그대로(또는 악화). DORA는 **병목 탐지 도구**입니다: "리드타임 p90이 5일인데 파이프라인은 20분 → 나머지 4일 19시간은 어디에?"(대개 리뷰 대기·승인·배치)를 찾는 데 쓰고, 4지표를 세트로 봐서 한 지표만의 개선(다른 것의 희생)을 걸러내라.

## 2. critical path 밖을 최적화

"lint가 느리다"는 불평에 lint를 2배 빠르게 했는데 전체 시간이 그대로 — lint가 critical path에 없었기 때문입니다(lab-02에서 확인한 것). 반대로 경로 위의 70초짜리 integration을 두 개로 분할하면 즉시 35초 단축. 최적화 전에 반드시: 잡 그래프 + 잡별 시간 → 최장 경로 → 경로 위의 최대 항목. 그리고 한 번 줄이면 **경로가 바뀝니다** — 다시 측정하지 않으면 다음 최적화도 헛손질이 됩니다.

## 3. needs를 습관으로 걸어 가짜 순차 만들기

`needs:`는 "게이트"(실패 시 뒤를 막음)와 "순서"(정말 앞의 산출물이 필요)를 위한 것인데, "왠지 순서대로 도는 게 안전해 보여서" 걸어놓은 needs가 파이프라인을 순차로 만듭니다 — lab-02 Step 3에서 needs 두 개를 지우는 것만으로 40%가 줄었습니다. 각 화살표에 물어라: "뒤 잡이 앞 잡의 **산출물**을 쓰는가요?" 아니라면 병렬로 풀고, 게이트가 목적이면 마지막 잡의 needs 배열로 모아라(fan-in). 공짜 최적화는 대개 여기 숨어 있습니다.

## 4. 전면 자동 재시도 — flaky의 마취제

`retry: 2`(또는 재시도 액션)를 파이프라인 전체에 걸면 당장은 평화롭습니다 — 그리고 flaky가 통계에서 사라집니다. 실패→재시도→성공 런은 "성공"으로 기록되고, 아무도 고치지 않는 flaky가 쌓이며, 어느 날 재시도로도 안 덮이는 수준이 됩니다(그때는 수십 개가 얽혀 있습니다). 게다가 재시도는 러너 시간을 태워 queue time을 늘립니다(L=λW에서 λ 증가). 규율: 재시도는 인프라 원인(프로비저닝·네트워크)에만, 반드시 발생을 집계하고("재시도로 성공한 런 %"를 대시보드에), 테스트 flaky는 격리 시스템(05)으로.

## 5. queue time을 안 보고 러너 사용률만 봄

"러너 사용률 80%면 여유 있네"는 큐 이론의 함정입니다 — 도착이 몰리는 시스템에서 대기 시간은 사용률이 100%에 닿기 훨씬 전에 급증합니다(eks 13의 무릎). 개발자가 체감하는 것은 사용률이 아니라 **기다린 시간**입니다: queue time p90을 SLO로 걸고, 그것이 자라면 사용률이 몇이든 증설(또는 잡 다이어트 — 20의 affected)을 검토하세요. 반대로 사용률이 낮은데 queue가 긴 경우도 있습니다 — 러너 라벨 불일치(특정 라벨만 병목)로, 풀 단위가 아니라 라벨 단위로 봐야 잡힙니다.

## 실무 사고 사례

> 성장 중인 한 조직 — 개발자가 30명에서 90명이 되는 동안 CI는 "느낌"으로 운영됐습니다. 증상은 서서히 왔습니다: 머지까지 걸리는 시간이 조금씩 늘고, 재시도 버튼이 일상이 되고, "CI 기다리느라 오늘 다 갔다"는 농담이 늘었습니다. 티핑 포인트는 채용이 몰린 분기였습니다 — 어느 월요일, 잡이 러너를 기다리는 시간이 40분을 넘겼고 조직 전체의 머지가 사실상 멈췄습니다. 사후 분석이 아픈 부분: **모든 신호가 데이터에 있었습니다**. queue time p90은 6개월간 우상향(아무도 안 봄), "재시도로 성공한 런"은 22%(flaky 방치의 지표), 파이프라인의 needs 그래프에는 가짜 의존이 세 개(전체 시간의 35%). 조직은 세 가지를 했습니다: ① 파이프라인 SLO 수립(duration p90, queue p90, 성공률, 재시도율)과 주간 리뷰 — 서비스와 같은 규율. ② L=λW로 러너 풀 산정 + ARC 오토스케일(08) — 피크 λ 기준. ③ flaky 격리 시스템(05)에 자동 탐지 배치를 연결 — 첫 달에 31개 격리, 재시도율 22% → 4%. 교훈: **파이프라인 붕괴는 사건이 아니라 추세입니다** — 그래프가 있었다면 6개월 전에 보였을 것을, 없어서 월요일 아침에 만났습니다. 내부 시스템에도 SLO를 — 사용자가 동료라는 이유로 관측을 생략하면, 청구서는 조직 전체의 속도로 옵니다.
