# 학습 가이드 — "느낌"을 숫자로 바꾸면 논쟁이 끝납니다

## 파이프라인의 사용자는 개발팀 전체입니다

서비스가 30분 죽으면 사고 보고서를 씁니다. CI가 30분 느려지면? — 개발자 50명이 각자 30분씩 기다리거나 컨텍스트를 잃습니다. 곱하면 서비스 장애보다 비싼 날이 많습니다. 그런데 전자는 대시보드·알림·온콜이 있고 후자는 "요즘 CI 느리지 않아?"라는 슬랙 메시지뿐입니다.

이 모듈의 주장: **파이프라인은 내부 고객에게 제공되는 프로덕션 서비스이고, 같은 규율(메트릭·SLO·용량 계획)로 운영해야 합니다.** eks 12~13에서 서비스에 했던 것(계측 → 큐 이론 → 용량)을 파이프라인에 그대로 적용합니다.

## 3계층 — 누가 어떤 결정에 쓰는 숫자인가

```
DORA (조직)        배포 빈도, 변경 리드타임, 변경 실패율, 복구 시간
                   → 경영·조직 수준: "우리 소프트웨어 전달이 나아지고 있나" (분기 단위)
파이프라인 (팀)    duration, queue time, 성공률, 재시도율
                   → 팀 수준: "러너를 늘릴까, 캐시를 고칠까" (주 단위)
스텝 (엔지니어)    캐시 히트율, 테스트 시간 분포, 아티팩트 크기
                   → 개인 수준: "오늘 뭘 고칠까" (일 단위)
```

계층을 섞으면 이상해집니다 — "DORA를 올리자"는 회의에서 캐시 히트율을 논하거나, 스텝 최적화로 배포 빈도를 바꾸려 하거나. 각 층의 숫자는 그 층의 결정에만 쓰입니다.

## 두 개의 재등장

**Little's Law (eks 13)**: 러너 풀은 큐 시스템입니다 — 잡이 도착(λ)하고, 러너를 기다리고(W_queue), 실행됩니다. queue time이 늘어나는 것은 러너 부족의 **선행** 신호입니다(사용률 그래프보다 빠릅니다 — eks 13에서 배운 무릎의 논리 그대로). lab-01에서 실제 queue time을 뽑습니다.

**flaky 격리 (05)**: 05에서 "flaky는 즉시 격리, 병가 처리"라는 원칙과 시스템을 설계했습니다. 이 모듈은 그 시스템의 **운영 데이터** 쪽을 완성합니다: 재시도 이력에서 flaky를 자동 탐지하고, flake rate를 지표로 관리하고, "재시도 버튼이 flaky를 숨기는" 악순환을 숫자로 드러냅니다.

## 최적화의 순서 — 측정 없이 만지지 마세요

빌드가 느릴 때 하고 싶은 것(캐시 추가! 러너 업그레이드! 병렬화!)부터 하면 안 됩니다. critical path(병렬 그래프에서 가장 긴 경로)가 아닌 곳을 최적화하면 **전체 시간은 1초도 안 줄어듭니다**. 순서는 언제나: 측정(어느 잡·스텝이 경로를 지배하나) → critical path 위의 병목 하나 → 다시 측정. lab-02에서 일부러 만든 느린 파이프라인으로 이 순서를 연습합니다.
