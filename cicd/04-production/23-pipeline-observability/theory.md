# 이론 — 메트릭 3계층, DORA 측정학, 큐로서의 러너 풀, critical path, flaky 운영

> **🌱 17세 눈높이 비유: 학교 급식 줄 개선 프로젝트**
> - **DORA** = 학기말 성적표 — "우리 학교 급식이 전반적으로 나아졌나" (한 학기 단위)
> - **파이프라인 메트릭** = 주간 운영 일지 — "배식 줄이 평균 몇 분? 몇 %가 반찬을 못 받았나요?"
> - **스텝 메트릭** = 조리 단계별 스톱워치 — "국 뜨는 데 3초, 밥 푸는 데 7초"
> - **queue time** = 줄 서서 기다린 시간 — 배식대(러너)가 모자라면 배식 속도(사용률)보다 **줄 길이가 먼저** 늘어납니다
> - **critical path** = 여러 배식대를 병렬로 둬도, 제일 느린 코스(국+밥+반찬 중 최장)가 전체 시간을 정합니다 — 빠른 코스를 더 빠르게 해봤자 소용없음
> - **flaky 재시도** = 가끔 못 받는 반찬을 "다시 줄 서면 되지"로 넘기기 — 편하지만, 문제가 통계에서 사라져 영원히 안 고쳐짐

## 1. 메트릭 3계층 — 층마다 결정이 다릅니다

| 계층 | 지표 | 주기 | 결정 |
|---|---|---|---|
| DORA (조직) | 배포 빈도, 리드타임, 변경 실패율, MTTR | 분기 | 투자 방향, 조직 구조 |
| 파이프라인 (팀) | duration p50/p90, **queue time**, 성공률, 재시도율 | 주 | 러너 용량(08), 캐시 전략(19·20) |
| 스텝 (개인) | 캐시 히트율, 테스트 시간 분포, 이미지 크기 | 일 | 오늘의 최적화 대상 |

원칙: **위 계층은 아래의 합이 아닙니다**. 스텝을 다 빠르게 해도 배포 승인이 주 1회면 리드타임은 그대로입니다 — DORA는 파이프라인 밖(리뷰 대기, 승인 정책, 배치 크기)도 포함하므로 병목이 기술이 아닐 수 있음을 드러내는 것이 DORA의 힘입니다.

## 2. DORA 4지표 — 정의를 먼저 고정하세요

01에서 개념을 배웠습니다. 측정하려면 정의의 모호함부터 없애야 합니다:

| 지표 | 측정 정의(예시 — 조직이 고정해야 함) | 흔한 왜곡 |
|---|---|---|
| 배포 빈도 | prod 배포 워크플로 success 수 / 기간 | 빈 배포·재배포도 셈 (부풀리기) |
| 변경 리드타임 | **커밋 시각 → 그 커밋이 prod에 도달한 시각** (p50/p90) | PR 오픈 기준으로 재정의해 리뷰 대기를 숨김 |
| 변경 실패율 | 배포 후 롤백·핫픽스·사고로 이어진 배포 비율 | "사고" 정의를 좁혀 축소 |
| MTTR(복구 시간) | 장애 인지 → 복구(롤백 완료 등) | 탐지 지연을 제외해 축소 |

측정의 제1함정은 **게이밍**입니다: 지표가 목표가 되는 순간(굿하트의 법칙) 커밋을 쪼개 리드타임을 낮추고, 배포를 쪼개 빈도를 올립니다. 방어: ① 4개를 **세트로** 봅니다(빈도만 올리고 실패율이 오르면 들통) ② 지표를 평가가 아니라 **병목 탐지**에 씁니다 — "리드타임 p90이 5일 → 어디서 기다리나요?"가 올바른 사용법.

## 3. 러너 풀은 큐 시스템입니다 — Little's Law의 재등장

eks 13의 L=λW가 그대로 적용됩니다:

```
λ = 잡 도착률 (개/분, 근무시간 피크 기준)   W = 평균 체류 시간 (queue + run)
L = λ × W = 시스템 안의 평균 잡 수 → 필요한 동시 러너 수의 하한

예: 피크에 분당 6개 잡, 평균 실행 8분 → L = 48 — 러너 20개면 대기가 구조적으로 쌓임
```

- **queue time은 선행 지표입니다**: 사용률이 100%에 닿기 전에 대기가 먼저 자랍니다(eks 13의 무릎) — "러너 사용률 85%니까 괜찮아"가 아니라 queue time p90을 봐야 합니다
- GHA에서 queue time = `started_at - created_at`(런/잡 단위) — lab-01에서 추출
- 처방은 셋: 러너 증설(08의 ARC 오토스케일), 잡 다이어트(affected — 20), 피크 분산(스케줄 잡을 새벽으로)

## 4. critical path — 병렬 시대의 병목 찾기

```
        ┌─ lint (2m) ─────────┐
push ──┼─ unit (6m) ──────────┼─ build (4m) ─ deploy (3m)   전체 = ?
        └─ integration (11m) ─┘
전체 시간 = max(2, 6, 11) + 4 + 3 = 18분
critical path: integration → build → deploy
```

- lint를 1분으로 줄여도 전체는 **1초도 안 줍니다** — critical path 밖이므로
- 순서: ① 그래프와 각 잡 시간을 그린다 ② 최장 경로를 찾는다 ③ 그 경로 위의 최대 항목 하나를 줄입니다(분할·캐시·병렬화) ④ **경로가 바뀌었는지 다시 측정** (integration을 6분으로 줄이면 이제 unit이 경로에 등장)
- 잡 안에서도 같은 논리: 스텝별 시간 → 최장 스텝(대개 의존성 설치 또는 테스트) → 캐시(19)/분할(05)

## 5. flaky 운영 — 05의 시스템에 데이터를 공급합니다

05의 원칙(격리·병가·소유권)이 작동하려면 **flaky를 자동으로 찾아내는 데이터**가 필요합니다:

```
탐지 신호:
  같은 커밋에서 실패 → 재시도 성공        ← 가장 강한 신호 (코드는 같은데 결과가 다름)
  테스트 단위: 이력에서 pass/fail 교차 빈도 (flake rate = 교차 실행 비율)
악순환의 계량:
  재시도 버튼 클릭률↑ = flaky 방치의 지표 — 재시도는 flaky를 통계에서 숨깁니다
  "재시도로 성공한 런" 비율을 대시보드에 — 이것이 커지면 신뢰가 무너지는 중 (05의 깨진 유리창)
운영 루프:
  주간: flake rate 상위 N개 → quarantine(격리) + 소유팀 티켓 → 2주 내 수정 또는 삭제
  지표: quarantine 체류 시간 (격리가 무덤이 되지 않게)
```

**자동 재시도의 규율**: 전면 재시도(`retry: 2`)는 flaky를 숨기는 마취제입니다 — 쓰려면 ① 재시도 발생을 **기록·집계**하고 ② 인프라 원인(러너 프로비저닝, 네트워크)에만 허용하고 ③ 테스트 flaky는 재시도가 아니라 격리로 보내라.

## 6. 수집 구현 — 어디서 숫자를 뽑나

| 소스 | 방법 | 얻는 것 |
|---|---|---|
| GHA API | `gh api /repos/.../actions/runs`, `/timing` | run/잡 duration, queue, 결론 |
| 워크플로 내 계측 | 스텝에서 OTel/StatsD 전송 (buildevents류) | 스텝 단위, 실시간 |
| 테스트 리포터 | JUnit XML → 수집기 | 테스트 단위 시간·flake |
| GitLab/Jenkins | 내장 메트릭/Prometheus 플러그인 | 파이프라인 계층 |

작게 시작하는 법: **주기 배치**(스케줄 워크플로가 API로 지난주 데이터 집계 → 대시보드 커밋)로 시작하고, 필요해지면 실시간 계측으로. lab-01이 이 배치 방식입니다.
