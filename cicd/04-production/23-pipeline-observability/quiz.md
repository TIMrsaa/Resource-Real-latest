## 정답

**A1.** DORA: 분기 주기, 투자·조직 구조 결정. 파이프라인: 주 주기, 러너 용량·캐시 전략 결정. 스텝: 일 주기, 오늘의 최적화 대상. 스텝 최적화가 DORA를 못 움직이는 전형: 병목이 파이프라인 밖 — 리뷰 대기, 배포 승인 정책, 큰 배치 크기. DORA는 커밋→prod 전체를 재므로 기술 밖 병목을 드러냅니다(그것이 DORA의 존재 이유).

**A2.** 커밋 기준이면 리뷰 대기가 포함되고, PR 오픈 기준이면 숨습니다 — 리뷰 대기가 대개 최대 병목이므로 정의 하나로 "우리는 빠르다/느리다"가 갈립니다. 정의를 코드(측정 스크립트)로 고정해 논쟁을 리뷰로 바꿔라. 게이밍 방지: ① 4지표를 세트로(빈도↑ + 실패율↑ = 들통) ② 평가가 아니라 병목 탐지에 사용(지표가 목표가 되면 굿하트).

**A3.** 러너 풀은 큐 시스템(L=λW) — 대기 시간은 사용률 100% 전에 급증합니다(무릎). 개발자 체감은 사용률이 아니라 기다린 시간이므로 queue time이 선행·체감 지표입니다. 사용률 낮은데 queue 긴 경우: 러너 라벨 불일치 — 특정 라벨(예: gpu, arm64)의 잡만 병목인데 풀 전체 사용률은 낮게 보임. 라벨 단위 관측이 필요.

**A4.** critical path = 병렬 잡 그래프에서 시작→끝의 최장 경로 — 전체 시간은 정확히 이 경로의 합입니다. 경로 밖 잡은 아무리 줄여도 max()에 안 잡히므로 전체가 불변. 재측정 이유: 경로 위 항목을 줄이면 최장 경로 자체가 다른 잡으로 **바뀝니다** — 옛 경로 기준의 다음 최적화는 헛손질.

**A5.** 정당한 needs: ① 산출물 의존 — 뒤 잡이 앞 잡의 출력(아티팩트·이미지)을 실제로 사용. ② 게이트 — 실패 시 뒤(배포 등)를 막아야 함, 단 이 경우 fan-in(마지막 잡의 needs 배열)으로 모아 병렬성을 보존. 판별 질문: "뒤 잡이 앞 잡의 **산출물**을 쓰는가요?" — 아니면 가짜 의존이고, 지우는 것이 공짜 최적화입니다.

**A6.** ① 실패→재시도→성공이 "성공"으로 기록돼 flaky가 통계에서 사라짐 — 아무도 안 고침. ② 방치된 flaky가 누적되어 재시도로도 안 덮이는 임계에 도달(그때는 다수가 얽힘). ③ 재시도가 러너 시간을 태워 λ를 늘림 — queue time 악화. 규율: 인프라 원인(프로비저닝·네트워크)에만 허용, 발생을 반드시 집계("재시도로 성공한 런 %"를 대시보드에), 테스트 flaky는 재시도가 아니라 격리(05)로.

**A7.** "같은 커밋(SHA)에서 실행 결과가 갈림(성공과 실패 공존)" — 코드가 동일한데 결과가 다르므로 원인이 코드가 아니라 비결정성(타이밍·순서·외부 의존)임이 논리적으로 확정됩니다. 커밋이 다르면 "코드가 나빠서"일 가능성이 남지만, 같은 SHA의 교차는 그 가능성을 제거합니다.

**A8.** ① ci duration p90 ≤ 10분 — 위반 시 critical path 분석(23 lab-02), 캐시(19)·분할(05)·affected(20). ② queue time p90 ≤ 30초 — 위반 시 L=λW로 러너 산정·ARC 증설(08, eks 13). ③ main 성공률 ≥ 95% — 위반 시 실패 분류(코드/flaky/인프라) 후 각각 처방(25의 진단). ④ 재시도 성공 런 ≤ 5% — 위반 시 flaky 사냥·격리(05, 23 lab-02).
