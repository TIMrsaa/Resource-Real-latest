# 학습 가이드 — 통제는 공짜가 아닙니다, 그러나 무통제는 더 비쌉니다

## 이 모듈이 다루는 긴장

지금까지의 모듈은 "한 파이프라인을 잘 만드는 법"이었습니다. 조직에는 다른 문제가 있습니다: **파이프라인이 200개**이고, 각각이 다르게 생겼고, 보안팀은 "어느 파이프라인이 prod에 닿는지" 목록조차 없습니다. 이때 나오는 반사적 처방 — "전부 표준으로 강제!" — 은 대개 실패합니다: 표준이 팀의 실제 요구를 못 담으면 우회로가 생기고, 우회로는 표준보다 위험합니다.

이 모듈의 프레임: **통제가 필요한 지점(신뢰 경계·규제 대상)은 좁고 명확하게 강제하고, 나머지는 "포장도로"로 유인합니다.**

```
강제 (좁게)   허용 액션 목록(03), OIDC subject 형식(07), 서명 요구(21), prod 승인(SoD)
유인 (넓게)   reusable workflow(06) 골든 패스 — 표준을 따르는 것이 "제일 편한 길"이 되게
측정 (전체)   23의 지표로 — 골든 패스 채택률, 정책 위반률
```

## DORA의 불편한 발견 — CAB에 대하여

많은 조직이 안정성을 위해 변경자문위원회(CAB — 배포 전 위원회 승인)를 둡니다. Accelerate(DORA 연구)의 발견은 불편합니다: **무거운 외부 승인 절차는 속도를 죽이면서 안정성을 올리지 못했습니다.** 이유는 구조적입니다 — 배포 시점의 위원회는 변경 내용을 실제로 이해할 수 없고(고무도장), 승인 대기는 배치 크기를 키워(여러 변경이 한 배포에 뭉침) 오히려 위험을 늘립니다(01의 merge hell 논리).

대안은 승인을 없애는 것이 아니라 **옮기는 것**입니다: 변경을 이해하는 사람의 리뷰(peer review, 02) + 기계가 강제하는 게이트(테스트·서명·정책 — 03~21) + 위험 변경에만 좁게 걸리는 사람 승인(06의 environment). 컴플라이언스 감사관에게도 이쪽이 설명하기 좋습니다 — "위원회 회의록"보다 "모든 배포에 자동 기록된 승인·테스트·서명 체인"이 강한 증거입니다.

## 컴플라이언스를 적이 아니라 요구사항으로

SOX·PCI류가 실제로 요구하는 것은 관료제가 아니라 세 가지입니다: ① **추적성** — 이 배포가 어느 변경·어느 티켓에서 왔는지, ② **승인** — 권한 분리된 누군가가 허가했는지, ③ **불변 기록** — 위 둘의 증거를 사후 조작할 수 없는지. 셋 다 이미 배운 도구로 구현됩니다: Git 이력 + PR 리뷰(02) + environment 승인(06) + 다이제스트(04) + 서명(21) + 워크플로 로그. lab-01에서 이 체인을 "감사관에게 내밀 수 있는 리포트"로 뽑습니다.
