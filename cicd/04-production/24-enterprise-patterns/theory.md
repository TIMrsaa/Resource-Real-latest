# 이론 — 승인 설계, 컴플라이언스 3요소, 감사, 골든 패스, Policy as Code

> **🌱 17세 눈높이 비유: 학교 축제 부스 운영 규정**
> - 부스 3개일 때는 각자 알아서 — 부스 50개가 되면 소방 통로·전기 용량·회계 규정이 필요해집니다
> - **강제 규정(좁게)** = 소방·전기·회계 — 안전과 법에 관한 것만, 명확하게 (허용 액션·서명·승인)
> - **포장도로(넓게)** = 학생회가 만든 "부스 운영 키트"(천막·POS·정산 시트 세트) — 강제는 아니지만 **이걸 쓰는 게 제일 편해서** 다들 씀 (reusable workflow)
> - **SoD(직무 분리)** = 물건 산 사람과 회계 승인자가 달라야 함 — 한 사람이면 부정을 못 잡음
> - **고무도장** = 회계 선생님이 내용도 안 보고 도장 — 절차는 있는데 통제는 없음
> - **감사 로그** = 정산 장부 — 지우개로 지울 수 있으면 장부가 아님 (불변성)

---

## 1. 승인 게이트의 설계 — 어디에, 누가, 무엇을 보고

06에서 environment 승인을 만들었습니다. 엔터프라이즈 관점은 세 가지를 더 묻습니다:

| 질문 | 나쁜 답 | 좋은 답 |
|---|---|---|
| 어디에? | 모든 배포에 | **위험 등급별** — prod·규제 대상만, dev/stage는 자동 |
| 누가? | 아무 시니어나 | **SoD**: 변경 작성자 ≠ 승인자 (GHA environment의 "자기 승인 금지" + CODEOWNERS 리뷰) |
| 무엇을 보고? | 직감 | 게이트가 모아준 증거 — 테스트 결과·diff·영향 범위(20의 affected)·롤백 계획 |

**고무도장화의 역학**: 승인 요청이 하루 20건이고 각각이 "diff 800줄 + 컨텍스트 없음"이면 사람은 도장이 됩니다. 처방은 승인 횟수를 줄이고(위험 등급별) 판단 재료를 만들어주는 것(자동 요약·체크리스트) — 승인의 품질은 승인자의 성실함이 아니라 **요청의 설계**가 정합니다.

### CAB에 대한 DORA의 데이터

Accelerate 연구: 외부 승인 기구(CAB)는 리드타임을 크게 늘리면서 변경 실패율을 **낮추지 못했습니다**. 구조적 이유 — ① 배포 시점의 위원회는 변경을 이해할 수 없습니다(작성자·리뷰어보다 정보가 적음) ② 승인 대기가 배치를 키워 배포당 위험이 증가(01) ③ 진짜 통제(테스트·정책)는 이미 기계가 하고 있습니다. 현대적 배치: peer review(02) + 자동 게이트(03~21) + **좁은** 사람 승인(prod environment, SoD) — 그리고 이 전체가 기록되는 것이 위원회 회의록보다 강한 감사 증거입니다.

## 2. 컴플라이언스 3요소 — 규제가 실제로 요구하는 것

SOX(재무)·PCI-DSS(카드)·ISO27001 등의 CI/CD 관련 요구는 결국 셋으로 수렴합니다:

```
① 추적성   prod의 이 바이너리는 어느 커밋·어느 티켓·어느 요구사항에서 왔나
            구현: 커밋 ↔ 티켓 링크 강제(PR 게이트) + 다이제스트(04) + provenance(19·21)
② 승인     권한 분리된 사람이 허가했나 (SoD)
            구현: 브랜치 보호의 리뷰 필수(02) + CODEOWNERS + environment 승인(06)
③ 불변 기록 위 증거를 사후 조작할 수 없나
            구현: 워크플로 로그(플랫폼 보관) + Rekor(21의 투명성 로그) + 감사 로그 외부 적재
```

**Compliance as Code**: 이 요구를 문서가 아니라 게이트로 — "티켓 없는 PR은 머지 불가", "서명 없는 이미지는 admit 불가(21)", "직접 push 불가(02)". 감사 대응이 "증빙 수집 2주"에서 "리포트 스크립트 실행"이 됩니다(lab-01 Step 4).

## 3. 감사 로그 — 기록의 품질 기준

| 물어야 할 것 | 기록 |
|---|---|
| 누가 | 실행자·승인자 (봇이면 그 봇의 신원 — 07의 OIDC subject) |
| 무엇을 | 커밋 SHA + **산출물 다이제스트** (태그는 움직이므로 — 04) |
| 언제 | 트리거·승인·배포 완료 시각 |
| 어떻게 | 워크플로 정의의 그 시점 버전 (ref가 아니라 SHA) |
| 결과 | 성공/실패/롤백 |

품질 기준 두 가지: ① **불변성** — 기록을 쓰는 사람이 지울 수 있으면 감사가 아닙니다(로그를 별도 계정·외부 스토리지로 적재, CloudTrail의 S3 교차 계정과 같은 원리 — 09·eks) ② **완전성** — "정상 경로만" 기록하면 안 됩니다: 수동 배포·긴급 배포(break-glass)일수록 기록이 중요합니다. break-glass는 금지가 아니라 **고비용·고가시성**으로 설계합니다(사용 시 자동으로 사후 리뷰 티켓 생성).

## 4. 멀티팀 거버넌스 — 강제와 유인의 배치

```
조직 수준 (강제 — 좁고 명확)
  GitHub org 룰셋: 브랜치 보호 표준, 서명 커밋, 직접 push 금지 — 저장소별 설정의 조직판
  허용 액션 목록: 검증된 액션만 (03의 공급망 — verified + 사내 액션)
  required workflow: 조직이 지정한 검사(시크릿 스캔 — 22, 정책 검사 — lab-02)를 전 저장소에
  OIDC subject 표준(07)·서명 요구(21) — 클라우드/클러스터 쪽에서 강제

팀 수준 (자율)
  잡 구성·테스트 전략·내부 스텝 — 팀이 제일 잘 아는 영역

플랫폼 팀 (유인 — golden path)
  reusable workflow(06) 세트: "build-test-deploy 표준판" — 캐시(19)·서명(21)·SBOM이 내장
  starter 템플릿: 새 저장소가 표준으로 시작
  ★ 채택률이 지표(23): 골든 패스가 안 쓰이면 강제할 게 아니라 "왜 불편한가"를 고쳐라
```

**포장도로의 경제학**: 강제된 표준은 우회를 낳고, 우회는 가시성 밖이라 표준보다 위험합니다. 골든 패스는 "따르는 것이 제일 편한 길"로 설계합니다 — 보안·컴플라이언스가 **내장돼서 공짜**로 딸려오게(팀은 서명이 뭔지 몰라도 표준 워크플로를 쓰면 서명이 됩니다). 플랫폼 팀의 성공 지표는 통제율이 아니라 채택률입니다.

## 5. Policy as Code — 파이프라인 자체를 검사합니다

정책 문서("워크플로는 permissions를 명시해야 한다")는 읽히지 않습니다. 정책을 코드로:

```
OPA(Open Policy Agent): 정책 엔진 — rego 언어로 "허용/거부" 규칙
conftest: OPA를 CI에서 파일 검사에 쓰는 CLI — YAML/JSON/Dockerfile에 rego 적용

검사 대상이 "앱"이 아니라 "파이프라인 정의 자체"라는 것이 이 모듈의 포인트:
  deny: permissions 미명시 워크플로       (03의 최소 권한)
  deny: 서드파티 액션의 태그 참조          (03·18의 SHA 고정)
  deny: pull_request_target + checkout    (03의 인젝션 조합)
  deny: self-hosted 러너를 퍼블릭 저장소에 (08)
```

이 검사를 required workflow(조직 수준)로 걸면 — 지금까지 배운 규율(03·07·08·18)이 문서가 아니라 **머지 차단 게이트**가 됩니다. lab-02에서 구현합니다. (같은 OPA가 k8s admission — 21의 Kyverno 자리 — 과 Terraform 검사에도 쓰입니다: 정책 엔진 하나로 조직 전체.)

## 6. 변경 동결과 예외 — 규칙의 가장자리

```
change freeze: 대목(블랙프라이데이 등) 전 배포 금지 — 필요하지만 남용 주의
  동결이 길수록 해제 직후 배치가 커집니다(01의 역설) — 짧게, 명확한 기준으로
break-glass: 동결·승인을 우회하는 긴급 경로 — 금지하면 몰래 하게 됨
  설계: 가능하되 ① 별도 신원·별도 로그 ② 자동 사후 리뷰 생성 ③ 23의 지표에 카운트
금요일 배포 금지?: 증상 처방 — 진짜 문제는 "롤백이 무섭다"(17의 자동 롤백이 답)
```
