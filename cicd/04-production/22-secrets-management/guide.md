# 학습 가이드 — 시크릿 문제를 세 번 줄이고 나서 관리합니다

## 순서가 전부입니다: 없애기 → 줄이기 → 관리하기

시크릿 관리 도구부터 고르는 것은 순서가 틀렸습니다. 올바른 순서:

```
1. 없앤다   AWS 키 → OIDC(07) / 서명 키 → keyless(21) / Pod의 클라우드 키 → IRSA(eks)
            → "비밀번호"를 "신원 증명"으로 대체 — 훔칠 것 자체가 없어짐
2. 줄인다   남는 시크릿의 수명을 줄임 — Vault 동적 발급(DB 계정 TTL 1h)
            → 유출돼도 이미 만료 (07의 단명 토큰과 같은 원리)
3. 관리한다 그래도 남는 것(서드파티 API 키 등)만 도구로 — 보관·주입·순환·감사
```

1·2단계를 건너뛰고 3단계 도구(Vault, ESO...)에 장기 정적 키를 잔뜩 넣으면 — "잘 정리된 화약고"가 될 뿐입니다. CircleCI 2023 사고(pitfalls)에서 두 조직의 운명을 가른 것은 도구가 아니라 **시크릿의 수명**이었습니다.

## GitOps의 난제 — 이 모듈의 중심 문제

14에서 "Git이 진실의 원천"이라 배웠습니다. 그런데 시크릿은 Git에 못 넣습니다(평문 커밋 = 유출). 그럼 시크릿의 진실은 어디에?

```
sealed-secrets  암호문을 Git에 — 클러스터의 컨트롤러만 풀 수 있는 비대칭 암호화
SOPS            암호문을 Git에 — 키는 KMS/age, 값만 암호화라 diff 리뷰 가능
ESO             참조만 Git에 — "진실은 외부 스토어(Vault/ASM)"라고 인정하는 설계
```

셋은 같은 문제의 다른 답이 아니라 **"진실이 어디 있어야 하는가"에 대한 다른 철학**입니다: 앞의 둘은 "암호화해서라도 Git이 진실", ESO는 "시크릿만은 스토어가 진실, Git은 포인터". 조직의 운영 모델(스토어 운영 여력, 멀티클러스터, 순환 빈도)이 답을 정합니다 — lab-02에서 셋을 직접 돌려보고 결정표를 만듭니다.

## 03의 복선 회수

03에서 "마스킹은 인코딩을 우회하면 뚫린다"를 봤습니다 — 그때의 결론이 이 모듈의 출발점입니다: **마스킹은 사고 방지책이 아니라 실수 완화책**입니다. 시크릿이 러너 메모리에 있는 한(tj-actions 사고, 21) 로그 마스킹은 최후의 화장일 뿐. 그래서 이 모듈의 에너지는 "로그에서 가리기"가 아니라 "러너에 장기 시크릿이 아예 없게"에 쓰입니다.
