# 자가 점검 퀴즈

**Q1.** 시크릿 대응의 3단계 순서(없애기→줄이기→관리하기)를 예와 함께 설명하세요. 왜 이 순서인가요?

**Q2.** GHA 플랫폼 시크릿의 한계 두 가지와, fork PR에 시크릿이 안 가는 이유(03 연결)는?

**Q3.** Vault의 본질 기여가 "보관"이 아니라 "발급"이라는 말의 의미는? CI가 Vault에 인증하는 권장 방법은?

**Q4.** GitOps 시크릿 3해법의 "진실의 위치"를 각각 말하고, 순환 시 Git 커밋이 필요한 것/불필요한 것을 구분하세요.

**Q5.** sealed-secrets의 DR 급소는 무엇인가(k8s 36 연결)? SOPS가 sealed 대비 리뷰에서 우월한 지점은?

**Q6.** "순환 완료"의 올바른 정의는? env 주입과 subPath 마운트가 순환에서 위험한 이유는?

**Q7.** 커밋된 시크릿에 이력 rewrite가 해법이 아닌 이유와 올바른 대응은?

**Q8.** CircleCI 2023 사고에서 조직의 피해 크기를 결정한 세 요인은?

---

## 정답

**A1.** ① 없애기: AWS 키→OIDC(07), 서명 키→keyless(21), Pod 클라우드 키→IRSA — 자격증명을 신원 증명으로 대체해 훔칠 것 자체를 제거. ② 줄이기: 없앨 수 없는 것(DB 계정)의 수명 단축 — Vault 동적 발급 TTL 1h, 유출돼도 이미 만료. ③ 관리하기: 그래도 남는 것(서드파티 API 키)만 스토어 보관·주입·순환·감사. 이 순서인 이유: 3단계 도구는 시크릿의 유출 시 피해를 줄이지 못합니다(장기 키는 스토어에 있어도 장기 키) — 피해 크기는 1·2단계가 결정하고, 도구는 남는 최소량의 운영 문제만 풉니다.

**A2.** 한계: ① 플랫폼 자체가 단일 장애점 — 플랫폼 침해 시 저장된 시크릿 일괄 노출(CircleCI 2023). ② 순환·감사가 저장소/조직 설정에 파편화 — 중앙 감사 불가. fork PR: pull_request 이벤트는 신뢰 경계 밖(03) 코드이므로 시크릿을 제공하지 않습니다 — 이것을 우회하는 pull_request_target이 위험한 이유이기도 합니다.

**A3.** Vault는 금고(저장)보다 조폐국(발급)이 본질 — DB/클라우드 계정을 요청 시점에 생성하고 TTL로 자동 폐기합니다. "유출된 자격증명" 개념 자체가 약해집니다(1시간짜리 + 발급 기록). CI 인증: 장기 Vault 토큰이 아니라 **JWT/OIDC 인증** — GHA의 OIDC 토큰으로 Vault에 로그인(07의 패턴 재사용, 부트스트랩 시크릿 없음).

**A4.** sealed-secrets: 진실은 Git(클러스터 컨트롤러만 여는 암호문). SOPS: 진실은 Git(KMS/age 키로 여는 암호문, 값 단위). ESO: **진실은 외부 스토어**, Git에는 참조(ExternalSecret CR)만. 순환: sealed·SOPS는 재암호화+Git 커밋 필요, ESO는 스토어에서 한 번 갱신하면 refreshInterval 내 자동 반영(커밋 불필요).

**A5.** 급소: 복호화 개인키가 클러스터 안에만 존재 — 클러스터 소실(DR) 시 Git의 SealedSecret 전부가 열 수 없는 상자(개인키 백업이 필수 운영 항목). SOPS의 리뷰 우위: `--encrypted-regex`로 값만 암호화되어 키 이름은 평문 — PR diff에서 "어느 항목의 값이 바뀌었는지"가 보입니다(sealed는 통암호문이라 diff가 무의미).

**A6.** 순환 완료 = 새 값이 **앱 메모리까지** 전파되고 옛 값이 폐기된 상태 — 스토어 갱신은 첫 홉일 뿐. env 주입은 Pod 시작 시 고정이라 재시작 전까지 옛 값(옛 값을 먼저 폐기하면 일제 인증 실패 장애), volume의 subPath 마운트는 kubelet 갱신이 전파되지 않는 k8s의 알려진 함정. 해법: Reloader류로 Secret 변경 시 롤링 재시작, 옛/새 값 이중 유효 기간.

**A7.** 지워도 이력에 남고, filter-repo로 이력을 다시 써도 포크·클론·CI 캐시·플랫폼의 dangling commit에 이미 복제됐습니다 — 커밋된 순간 유출로 간주해야 합니다. 올바른 대응: 즉시 순환(새 값 발급→전파→옛 값 폐기, 사용 로그로 악용 확인) + 재발 방지는 커밋 전 차단(pre-commit gitleaks, push protection). rewrite는 순환 후의 청소일 뿐.

**A8.** ① 플랫폼에 저장된 시크릿의 수와 수명 — OIDC 중심 조직은 순환할 것이 거의 없었습니다(없애기·줄이기의 성적표). ② 시크릿 → 권한 지도의 존재 — "뭘 넣어놨는지" 파악에 이틀 vs 즉시(대응 속도). ③ 순환 절차의 성숙도 — 전파(Pod까지)와 누락 방지가 리허설돼 있었는가. 피해는 사고 당일이 아니라 그 전의 구조가 결정합니다.
