# 학습 가이드 — 흩어져 있던 규율이 하나의 체계가 됩니다

## 왜 지금 이 모듈인가

이 커리큘럼에서 공급망은 새 주제가 아닙니다 — 계속 만나왔습니다:

```
03  남의 액션을 SHA로 고정하세요        (이동 태그는 탈취될 수 있습니다)
04  이미지를 다이제스트로 배포하세요     (태그는 움직입니다)
18  dist가 src에서 나온 것을 증명하세요  (verify-dist — 생산자의 책임)
19  빌드가 provenance를 첨부합니다       (--provenance — 증명서의 생성)
20  캐시 쓰기는 신뢰 경계 안에서만     (포크 PR의 캐시 오염)
```

전부 같은 질문의 조각입니다: **"실행/배포되는 그것이, 검토·의도된 그것과 동일한가?"** 이 모듈은 조각을 체계로 조립합니다 — 공격 지도로 "어디가 뚫리는지"를 정리하고, SLSA로 "얼마나 믿을 수 있는지"에 등급을 매기고, sigstore로 "동일함"을 암호학적으로 증명하고, 배포 관문에서 그 증명을 강제합니다.

## 뉴스가 아니라 구조로 이해하기

xz 백도어(2024), SolarWinds(2020), codecov(2021), event-stream(2018), tj-actions(2025) — 사고 이름을 외우는 것은 의미가 없습니다. 각 사고가 **공급망의 어느 고리**를 뚫었는지가 구조입니다:

```
소스 저장소   ← xz (악의적 유지보수자), event-stream (관리권 이양)
의존성 해석   ← dependency confusion (같은 이름, 공개 레지스트리 우선)
빌드 시스템   ← SolarWinds (빌드 서버 침투 — 소스는 깨끗했습니다!)
CI 스크립트   ← codecov (업로더 스크립트 변조), tj-actions (액션 태그 재지정)
아티팩트 저장 ← 태그 변경, 캐시 오염(20)
```

방어도 고리별로 다릅니다 — 서명은 빌드 이후의 변조를 잡지만 빌드 시스템 침투(SolarWinds)는 못 잡습니다(그래서 SLSA L3의 빌드 격리가 따로 있습니다). "cosign 붙였으니 안전"이 왜 착각인지가 이 지도에서 보입니다.

## keyless의 우아함 — 07이 여기서 재등장합니다

서명의 고전적 난제는 키 관리입니다(키가 유출되면 서명 자체가 무기가 됩니다 — 22의 주제이기도 합니다). sigstore의 답이 우아합니다: **키를 없앱니다**. 07에서 배운 OIDC — "GitHub이 이 워크플로의 신원을 토큰으로 증언한다" — 를 그대로 서명에 씁니다: Fulcio가 OIDC 신원에 10분짜리 인증서를 발급하고, Rekor(공개 투명성 로그)에 서명 기록이 남습니다. 검증자는 "이 이미지는 **이 저장소의 이 워크플로**가 서명했다"를 확인합니다. 장기 키가 아예 없으니 유출될 키도 없습니다 — 07의 "장기 키 부채 상환"의 서명판입니다.

## 이 모듈의 끝 — 신뢰가 게이트가 됩니다

17에서 "관찰이 게이트"였다면 여기서는 **"증명이 게이트"**입니다: 서명·provenance·SBOM 스캔을 통과 못 한 아티팩트는 배포 관문(admission)에서 거절됩니다. k8s 34에서 배운 admission 정책이 공급망의 마지막 방어선으로 재등장합니다.
