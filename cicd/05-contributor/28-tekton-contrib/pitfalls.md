# 흔한 함정 5선

## 1. TEP 검색 없이 이슈·제안 열기

16에서 겪은 불편(workspace 장황함, 파라미터 전파 등)은 높은 확률로 이미 TEP나 이슈에서 논의됐습니다 — 검색 없이 "이거 불편해요" 이슈를 열면 "TEP-XXXX 참조"로 닫히며 첫인상만 소모합니다. 순서: teps/ 검색 → 관련 TEP의 상태(proposed/implementable/implemented) 확인 → 기존 논의에 사용 사례를 보태는 코멘트가 새 이슈보다 낫습니다. 선행 논의를 인용하며 말하는 기여자는 그 자체로 신뢰를 얻습니다 — 검색은 예의이자 전략입니다.

## 2. `/ok-to-test` 대기를 무시당함으로 오해

외부 기여자의 첫 PR은 CI가 자동으로 돌지 않습니다 — Prow가 유지보수자의 `/ok-to-test`를 기다립니다(포크 PR의 신뢰 경계, 03의 커뮤니티 구현). 이것을 "무시당했다"로 읽고 PR을 닫거나 감정적 코멘트를 다는 신규 기여자가 있습니다. 실제로는 정상 절차입니다: 이틀쯤 기다리고, 그래도 없으면 정중한 핑 한 번(리뷰어는 OWNERS에서 확인 — lab-02 Step 3). k8s 45에서 배운 인내의 문법이 여기서도 — 커뮤니티의 침묵은 대개 거절이 아니라 큐입니다.

## 3. entrypoint 트릭을 모른 채 실행 문제를 진단

"스텝이 시작을 안 해요"류 문제에서 Pod와 컨테이너 상태만 보면 미궁입니다 — 컨테이너는 전부 Running인데 스텝은 대기 중일 수 있습니다(entrypoint 바이너리가 이전 스텝 완료 파일을 기다리는 중 — theory §3). 진단은 스텝 컨테이너의 로그와 `/tekton/` 경로의 상태로 내려가야 합니다. 이 지식 없이 이슈를 열면 재현 정보가 빗나가고, 있으면 26의 _diag급 진단 리포트를 쓸 수 있습니다 — 실행계 기여의 관문 지식입니다.

## 4. catalog 기여를 "그냥 YAML"로 얕보기

catalog의 심사는 YAML 문법이 아니라 **생산자의 책임**(18)을 봅니다: 스텝 이미지의 다이제스트 고정(04), 파라미터·workspace·results의 문서화, 최소 권한, 테스트. "동작하는 Task"와 "머지되는 Task"의 차이가 여기입니다 — recommendations 체크리스트를 채우지 않은 PR은 왕복만 늘립니다. 거꾸로 이 기준을 채워본 경험은 사내 Task 표준(24의 골든 패스)을 설계하는 능력으로 직결됩니다 — 낮은 문이지 낮은 기준이 아닙니다.

## 5. 세 생태계의 전략을 섞어 쓰기

26의 전략(이슈 중심, 기능 PR 자제)을 tektoncd에 가져오면 소극적이 되고, 28의 전략(코드 PR 환영 기대)을 actions/runner에 가져오면 표류합니다. 거버넌스가 전략을 정합니다(lab-02 Step 6의 표): 기업 주도면 재현·진단으로, 오픈 거버넌스면 절차(TEP/proposal → 테스트 동반 PR)로. 새 프로젝트를 만나면 코드보다 먼저 읽을 것: 거버넌스 문서, OWNERS/유지보수자 구성(단일 회사인가), 최근 머지된 외부 PR의 비율 — 이 셋이 그 동네의 헌법입니다.

## 실무 사고 사례

> 한 CI 플랫폼 엔지니어가 사내 Tekton 도입(16) 후 파이프라인 표준화를 맡았습니다 — 팀마다 제각각인 빌드 Task를 정리하다가, 사내에서 반복 작성되는 패턴(사내 레지스트리 인증 + 다이제스트 검증 + SBOM 첨부)을 하나의 Task로 묶었습니다. 처음엔 사내 저장소에만 두었는데, 동료가 "이거 catalog감인데?"라고 했습니다. 그는 catalog의 recommendations 체크리스트를 채우며 두 번 놀랐습니다 — 첫째, 자신의 Task가 기준 미달이었습니다(스텝 이미지가 태그 참조였고, results 문서화가 없었습니다: 사내에서는 아무도 지적하지 않던 것). 둘째, 기준을 채우는 과정 자체가 Task의 품질을 눈에 띄게 올렸습니다. 제출 PR은 `/ok-to-test` 대기 이틀, 리뷰 왕복 두 번(파라미터 네이밍, 테스트 추가) 후 머지됐습니다. 후일담이 이 트랙의 요지입니다: ① 머지된 catalog Task는 회사 밖 사용자들의 이슈·개선 PR을 받기 시작했고 — 사내 도구였다면 없었을 무료 QA입니다. ② 그 실적을 딛고 그는 pipeline 본진의 cli 이슈를 하나 잡아 첫 Go 코드 PR을 머지시켰습니다. ③ 사내 표준(24의 골든 패스) 문서에는 "catalog 심사 기준을 사내 Task 기준으로 준용"이 들어갔습니다. 교훈: **가장 낮은 문으로 들어가 공개 기준을 통과해보는 것이, 코드 실력보다 먼저 기여자를 만듭니다** — 그리고 공개 생태계의 기준은 언제나 사내 기준을 끌어올립니다.
