# 자가 점검 퀴즈

**Q1.** tektoncd의 거버넌스(재단·프로세스)를 26·27과 대비해 설명하세요.

**Q2.** `ko apply -f config/` 한 명령이 하는 일의 전체 흐름과, 19의 어떤 특성이 이 루프를 가능하게 하나요?

**Q3.** "Task가 Pod가 되는" 코드는 어디이고, 스텝이 순서대로 실행되는 메커니즘은?

**Q4.** 외부 기여자의 첫 PR에서 CI가 자동으로 돌지 않는 이유와, 그 절차의 이름은? (03 연결)

**Q5.** TEP의 두 가지 효용과, 이슈를 열기 전 TEP를 검색해야 하는 이유는?

**Q6.** catalog 기여의 심사 기준이 18·04의 어떤 규율과 일치하는지 구체적으로 들어라.

**Q7.** OWNERS 파일이 기여자에게 주는 실용 정보 두 가지는?

**Q8.** 26~28에서 겪은 세 가지 개발 루프 스타일과, 공통 원칙은?

## 정답

**A1.** tektoncd는 CDF(Continuous Delivery Foundation) 소속 — CNCF(27의 argoproj)와 재단이 다르지만 멀티 벤더 오픈 거버넌스라는 본질은 같고, 프로세스는 Kubernetes에서 이식했습니다(OWNERS 계층, Prow 봇의 /lgtm·/approve, TEP). 26(actions/runner)은 기업 주도라 로드맵을 회사가 정하는 반면, 27·28은 절차를 통과하면 머지의 길이 열립니다 — 27은 proposal, 28은 더 정형화된 TEP.

**A2.** ko가 Go 소스를 빌드해 이미지를 만들고(Dockerfile·데몬 없음), 레지스트리(또는 kind 직접 로드)에 올린 뒤, config/의 매니페스트에서 `ko://` 이미지 참조를 방금 빌드한 이미지로 치환해 kubectl apply까지 수행합니다 — 소스에서 클러스터까지 한 명령. 19에서 배운 ko의 특성(Go 전용, base에 바이너리만 얹는 단순 구조, 재현성)이 "코드 수정→재배포"를 초 단위 루프로 만듭니다. Tekton 자체가 이 방식으로 개발됩니다.

**A3.** pkg/reconciler/taskrun/(ReconcileKind)이 진입점, resources/pod.go의 MakePod가 스텝→컨테이너 매핑의 본체. 순차 실행: Pod의 컨테이너는 원래 동시에 시작하므로, Tekton이 각 스텝 컨테이너의 entrypoint를 자기 바이너리(cmd/entrypoint)로 교체합니다 — 그 바이너리가 이전 스텝의 완료 파일을 기다렸다가 원래 명령을 실행하고 자기 완료 파일을 기록하는 릴레이 구조(pkg/pod). 컨테이너는 전부 Running인데 스텝은 대기 중일 수 있는 이유.

**A4.** 포크 PR은 신뢰 경계 밖의 코드(03)이므로, CI(프로젝트의 자원·시크릿 접근 가능)를 자동 실행하면 악성 PR의 공격 통로가 됩니다 — 유지보수자가 코드를 훑고 `/ok-to-test` 코멘트로 허가해야 Prow가 CI를 돌립니다. cicd 03에서 배운 pull_request 이벤트의 시크릿 미제공과 같은 문제의식을 커뮤니티 프로세스로 구현한 것.

**A5.** ① 기여 전 검색 — 내 불편·아이디어의 선행 논의, 기각 사유, 구현 상태를 확인(중복 방지 + 맥락 학습, 기존 논의에 사용 사례를 보태는 쪽이 새 이슈보다 효과적). ② 설계 교과서 — "왜 이 기능이 이 모양인가"의 1차 사료(26의 ADR과 같은 지위). 검색 없이 열린 이슈는 "TEP-XXXX 참조"로 닫히기 쉽고, 선행 논의를 인용하는 기여자는 그 자체로 신뢰를 얻습니다.

**A6.** 스텝 이미지의 다이제스트(@sha256) 고정 = 04의 불변 참조 규율(태그는 움직입니다). 파라미터·workspace·results의 문서화 = 18의 "요구 권한·사용법 문서화"(소비자가 안전하게 쓸 수 있게). 최소 권한·입력 검증 = 18의 생산자 책임. 버전 디렉터리와 명시적 버저닝 = 18의 semver 규율. 즉 catalog 심사는 "동작하는가"가 아니라 "생산자의 책임을 다했는가"를 봅니다 — 커리큘럼의 규율이 생태계 표준과 일치합니다.

**A7.** ① 내 PR의 리뷰어·승인자가 누구일지 미리 압니다(디렉터리별 reviewers/approvers 명단) — 그들의 최근 리뷰 스타일을 훑어 왕복을 줄일 수 있습니다. ② 변경의 "관할"이 보입니다 — 여러 디렉터리를 건드리는 PR은 여러 OWNERS의 승인이 필요하므로, PR을 관할 단위로 쪼개는 판단 근거가 됩니다.

**A8.** 26 actions/runner: 로컬 빌드(dev.sh) + 러너 등록 + _diag 로그 추적. 27 argo-cd: make start-local(goreman)로 컴포넌트를 로컬 프로세스로 — IDE 디버거 가능. 28 tekton: ko apply로 수정을 클러스터에 재배포. 공통 원칙: **환경 완성이 아니라 "수정→실행→확인" 루프 하나를 가장 싸게 확보하는 것이 기여의 물리적 기초**입니다 — 새 프로젝트를 만나면 루프부터 찾습니다(DEVELOPMENT.md가 첫 문서인 이유).
