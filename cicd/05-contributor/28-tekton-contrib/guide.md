# 학습 가이드 — 세 번째 거버넌스, 그리고 두 갈래의 합류

## 이 모듈이 트랙을 완성합니다

26(기업 주도) → 27(CNCF 오픈 거버넌스) → 28(CDF + k8s식 프로세스). 세 모듈을 지나면 오픈소스 기여의 지형 감각이 생깁니다: **같은 "기여"라는 행위가 거버넌스에 따라 전혀 다른 전략을 요구한다**는 것. tektoncd의 특징은 "k8s 프로세스의 이식"입니다 — OWNERS 파일로 리뷰 권한을 계층화하고, Prow 봇이 /lgtm·/approve·/ok-to-test를 처리하며, 큰 변경은 TEP 문서로 합의합니다. k8s 43에서 이 문법을 배웠다면 여기서는 복습이자 실전입니다.

## ko가 돌아옵니다 — 19의 회수

Tekton의 개발 루프는 이 커리큘럼에서 가장 우아합니다:

```
ko apply -f config/        # 소스 → 이미지 빌드 → push → 매니페스트의 이미지 참조 치환 → kubectl apply
                           # Dockerfile 없음, 데몬 없음 (19에서 배운 그대로)
```

코드 한 줄 고치고 `ko apply` 한 번이면 새 컨트롤러가 클러스터에 돕니다 — eks 28(로컬 프로세스 디버그), 27(start-local)과 또 다른 스타일의 개발 루프입니다. 세 스타일(로컬 프로세스 / goreman / ko 재배포)을 다 겪어보면, 새 프로젝트를 만나도 "개발 루프부터 확보한다"는 감각이 섭니다.

## catalog — 이 생태계의 가장 낮은 문

Tekton Catalog(Artifact Hub에 게시되는 Task/Pipeline 모음)는 **YAML + 셸만으로 기여할 수 있는 문**입니다: 유용한 Task(예: 특정 도구의 빌드·스캔 단계)를 작성 규칙에 맞춰 제출합니다. 18에서 GitHub 액션의 생산자가 됐던 것의 Tekton판 — 재사용 단위의 생산자 경험이 그대로 이식됩니다. 컨트롤러 코드가 부담스러우면 여기서 시작해 신뢰를 쌓아라.

## 16의 상처가 재료가 됩니다

16에서 겪은 것들 — "Task 하나가 Pod 하나라 스텝 간 데이터 전달에 workspace가 필요", "파라미터 전파의 장황함" — 은 tektoncd 이슈 목록의 단골 주제이고, 여러 TEP의 동기였습니다. 27과 같은 원리: 사용자의 불편이 기여의 나침반입니다. 이슈를 열기 전에 관련 TEP를 검색하는 습관(이미 논의됐을 확률이 높습니다)이 이 동네의 예의입니다.
