# 흔한 함정 5선

## 1. 경계 판정 없이 argo-cd만 파기

"sync 순서가 이상하다"를 argo-cd 저장소에서 한 주 내내 찾았는데 코드가 없습니다 — wave 정렬은 gitops-engine에 있기 때문입니다(theory §3). 반대로 diff 정규화 문제를 engine에서 찾다가 argo-cd 쪽 normalizer를 놓치기도 합니다. 증상 → 코드 경로 추적(호출이 어느 모듈로 들어가나)이 먼저입니다. 그리고 engine 수정은 2단계 여정(engine PR 머지 → argo-cd go.mod 갱신 PR)임을 계획에 넣어라 — 한 릴리스에 못 실릴 수 있습니다.

## 2. 재현 테스트 없이 수정 PR

오픈 거버넌스라 PR이 환영받는다고 해서 검증 부담이 사라지는 것은 아닙니다 — 테스트 없는 수정 PR의 첫 리뷰 코멘트는 거의 확실히 "테스트를 추가해달라"이고, 그 왕복에 몇 주가 갑니다. 순서를 지켜라: 실패하는 재현 테스트(fake client — lab-02 Step 2) → 수정 → 초록 + 기존 테스트 회귀 없음 → PR. 빨강→초록의 diff 자체가 가장 설득력 있는 PR 본문입니다(k8s 44의 문법이 여기서도 통화).

## 3. 첫 기여로 컨트롤러 코어를 겨냥

appcontroller.go의 reconcile 본체는 이 프로젝트에서 가장 예민한 코드입니다 — 성능(수천 앱 규모)·호환성·엣지 케이스가 얽혀 있어 신규 기여자의 PR이 오래 표류하기 쉽습니다. 문 순서(theory §6)를 따르라: 문서(14에서 내가 헤맨 지점이 곧 후보) → UI(경쟁 덜함, TS) → 경계가 명확한 영역(rollouts의 trafficrouting 제공자, health check의 리소스별 로직) → 코어. 작은 머지 실적이 쌓인 계정의 코어 PR은 대우가 다릅니다 — 신뢰는 저장소 안에서 복리로 쌓입니다.

## 4. start-local 환경 격투에 하루를 쓰기

로컬 개발 환경(goreman, 도구 버전, Redis)이 한 번에 안 뜨는 것은 흔합니다 — 그때 "환경이 완벽해야 시작"이라는 함정에 빠지면 하루가 갑니다. 우회로가 여럿입니다: 공식 매니페스트로 kind에 설치하고 **바꾸려는 컴포넌트 하나만** 스케일 0 후 로컬 실행(개발 가이드의 절충안), 단위 테스트는 클러스터 없이도 도는 것부터(go test ./controller/...), 문서·UI 기여는 환경이 거의 필요 없습니다. 목표는 환경 구축이 아니라 수정→확인 루프 하나를 확보하는 것 — 가장 싸게 도는 루프로 시작하세요.

## 5. proposal 없이 큰 기능을 코드로 먼저

몇 주에 걸쳐 큰 기능을 구현해 PR을 열면 — "방향이 다릅니다, proposal부터"라는 답과 함께 코드가 통째로 무산될 수 있습니다. 오픈 거버넌스의 거래는 명확합니다: **절차(proposal → 합의 → 구현)를 지키면 길이 열리고, 건너뛰면 노동이 증발합니다.** docs/proposals/의 기존 문서들을 읽으면 "어느 크기부터 proposal인지" 감이 옵니다 — CRD 필드 추가, 동작 변경, 새 컴포넌트는 확실히 대상입니다. 기여자 미팅에서 아이디어를 먼저 말해보는 것이 가장 싼 사전 검증입니다.

## 실무 사고 사례

> 한 SRE가 14를 배우고 회사에 ArgoCD를 도입했습니다 — 그리고 수백 개 Application 규모에서 특정 조건의 refresh 폭주(웹훅 + 주기 갱신이 겹치며 repo-server가 포화)를 겪었습니다. 처음에는 사내 워크어라운드(주기 늘리기)로 덮었습니다. 그러나 25의 규율대로 원인을 파려고 소스를 열었고 — appcontroller의 refresh 큐 처리에서 중복 제거가 특정 경로에 빠진 것을 발견했습니다. 그가 한 일의 순서가 교과서입니다: ① 이슈 검색 — 비슷한 보고 2건이 이미 있었지만 재현이 없어 방치돼 있었습니다. ② fake client로 **재현 테스트**를 작성해 기존 이슈에 코멘트로 첨부 — 방치되던 이슈가 즉시 triage됐습니다. ③ 유지보수자가 수정 방향을 코멘트로 제안했고, 그가 그 방향대로 수정 PR(테스트 포함)을 냈습니다. ④ 다음 마이너 릴리스에 머지 — 회사의 워크어라운드도 제거됐습니다. 몇 달 뒤 그는 반복 기여로 리뷰 권한을 받았습니다. 교훈: **운영의 상처가 가장 좋은 기여 재료입니다** — 사용자로서의 고통(회사에서 겪은 버그)이 재현 테스트라는 형식을 만나면, 방치된 이슈를 움직이고 릴리스를 바꿉니다. 그리고 그 여정 전체(사용 → 상처 → 소스 → 테스트 → PR)가 이 커리큘럼 기여자 트랙의 설계도 그 자체입니다.
