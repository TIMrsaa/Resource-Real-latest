# 자가 점검 퀴즈

**Q1.** Listener와 Worker의 역할 분담과, "잡마다 새 Worker"가 03의 어떤 보장의 구현인지 설명하세요.

**Q2.** 러너의 통신이 아웃바운드 전용(롱폴)인 것이 08의 어떤 운영 특성을 만들었나요?

**Q3.** run 스텝의 인젝션(03)이 "구조적"인 이유를 ScriptHandler의 동작으로 설명하세요.

**Q4.** `_diag`의 Runner 로그와 Worker 로그는 각각 무엇의 일기이고, 25의 어떤 증상에서 어느 쪽을 보나요?

**Q5.** 핸들러 4종과 각각이 처리하는 스텝 종류는? checkout이 일반 액션보다 빠른 경로인 이유는?

**Q6.** 생태계 4저장소의 언어·열림 정도·맞는 사람을 표로 정리하세요.

**Q7.** actions/runner 같은 기업 주도 저장소에서 "통하는 기여"의 형식과, 기능 PR 전에 해야 할 일은?

**Q8.** "어제와 오늘 러너 동작이 다르다"에서 의심해야 할 '안 보이는 변경'(25)은?

---

## 정답

**A1.** Listener: 등록·세션 유지·롱폴로 잡 메시지 수신·Worker 기동(JobDispatcher)·자동 업데이트. Worker: 잡 1개의 실행 엔진(JobRunner → StepsRunner → 핸들러) — 잡이 끝나면 프로세스 종료. "잡마다 새 Worker 프로세스"가 03의 잡 간 격리(이전 잡의 상태·메모리가 다음 잡에 안 남음)의 구현이고, ephemeral 러너(08)는 여기에 Listener까지 1회용으로 만든 것.

**A2.** 러너가 서비스로 HTTPS 아웃바운드 접속해 "일 있나요?"를 묻는 구조(롱폴) — 서비스가 러너로 접속하는 경로가 없습니다. 따라서 인바운드 포트 개방이 불필요해 방화벽·NAT 뒤에서 동작하고(08의 배치 자유), 러너 IP를 외부에 노출하지 않습니다. 반면 아웃바운드 프록시 환경에서는 프록시 설정이 필수라는 제약도 같은 구조에서 나옵니다.

**A3.** 표현식(`${{ }}`)은 러너가 스크립트를 만들기 **전에** 문자열로 치환되고, ScriptHandler는 치환이 끝난 완성 문자열을 임시 셸 스크립트 파일로 써서 실행합니다(lab-01 Step 5에서 파일 경로 확인). 즉 사용자 입력이 셸 코드와 같은 평면에 문자열로 합쳐진 뒤 파싱됩니다 — 이스케이프 단계가 구조적으로 없으므로, 방어는 치환 결과를 코드가 아닌 데이터로 두는 것(env 경유 — 03)뿐입니다.

**A4.** Runner_*.log = Listener의 일기(세션, 롱폴 응답, 잡 수신, 업데이트), Worker_*.log = 잡 실행의 일기(준비, 스텝별 핸들러, 컨테이너 기동, 종료 코드). "잡이 안 잡힌다/pending"(25 카드 2류) → Runner 로그(롱폴·세션), "스텝이 이상하게 실행/실패"(핸들러 문제) → Worker 로그.

**A5.** ScriptHandler(run: — 셸 선택·임시 스크립트 생성·실행), NodeScriptActionHandler(JS 액션 — 18에서 만든 것을 node로 실행), ContainerActionHandler(Docker 액션 — 이미지 빌드/pull 후 docker run), CompositeActionHandler(composite — 스텝 목록을 StepsRunner로 재귀). checkout은 Runner.Plugins의 내장 플러그인 경로로 실행되어 일반 액션의 다운로드·기동 오버헤드를 건너뜁니다.

**A6.** actions/runner: C#, 로드맵 중심으로 보수적, 진단·이슈 품질로 기여할 사람. actions/toolkit: TypeScript, 라이브러리라 상대적으로 열림, 18을 지난 JS 개발자의 추천 첫 문. actions/runner-images: 셸/PowerShell, 커뮤니티 기여가 가장 활발(최저 장벽), 도구 추가·버전 이슈부터. actions-runner-controller(ARC): Go, K8s 오퍼레이터 문법, k8s 42~44를 지난 Go 개발자.

**A7.** 통하는 형식: ① 최소 재현(돌려볼 수 있는 워크플로/저장소) ② _diag 발췌(해당 구간) ③ 기대 vs 실제 한 줄씩 ④ 러너 버전·OS·호스티드 구분 ⑤ (최상급) 소스 의심 지점 지목 — 유지보수자의 재현 비용을 0으로 만드는 것이 본질. 기능 PR 전에: docs/adrs를 읽어 "왜 지금 구조인가"를 확인하고, 이슈로 제안해 방향 합의를 먼저(k8s 45의 "합의가 코드보다 먼저"와 동일).

**A8.** 러너 자동 업데이트 — 서비스 지시로 러너가 스스로 버전을 올리므로, 코드·워크플로·이미지를 아무도 안 바꿔도 러너 버전이 변해 있을 수 있습니다. 진단·리포트에 러너 버전을 항상 기록하고, self-hosted 함대는 버전 분포를 파악(ARC는 이미지 태그로 고정·통제 — 08). 그 외 같은 계열: 러너 VM 이미지 갱신(runner-images), 참조 액션의 이동 태그(03).
