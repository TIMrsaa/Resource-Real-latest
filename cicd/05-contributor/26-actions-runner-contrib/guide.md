# 학습 가이드 — 소비자·운영자·생산자를 지나 개발자로

## 왜 러너의 소스를 읽나

03에서 배운 것들 — "잡마다 새 러너", "표현식은 셸 파싱 전에 치환", "시크릿 마스킹" — 은 전부 러너 소스 어딘가의 코드입니다. 소스를 읽으면 세 가지가 달라집니다:

1. **트러블슈팅의 층이 내려갑니다**: 25에서 "러너가 좀비"라는 증상을 다뤘습니다 — 소스를 알면 `_diag` 로그에서 Listener의 어느 루프가 멈췄는지까지 내려갑니다
2. **문서에 없는 답을 얻습니다**: "composite 액션 안의 composite은 몇 단계까지?" 같은 질문의 답은 문서가 아니라 `CompositeActionHandler`의 재귀 코드에 있습니다
3. **기여의 자격이 생깁니다**: 이슈에 "이 동작이 이상해요"가 아니라 "JobDispatcher의 이 분기에서 이 조건이 빠진 것 같다"고 쓸 수 있습니다

## 이 저장소의 특수한 현실 — 기대치 설정

Kubernetes(k8s 41~45)나 Karpenter(eks 28)와 달리, actions/runner는 **오픈소스이지만 오픈 거버넌스가 아닙니다** — GitHub 직원 팀이 로드맵을 정하고, 외부 PR 수용에 보수적입니다(제품의 일부이므로). 이것은 나쁜 소식이 아니라 **전략 정보**입니다:

```
runner 본체     기능 PR은 로드맵과 맞아야 — 이슈·재현·진단 기여가 현실적 (버그 리포트의 품질이 곧 기여)
toolkit         @actions/core 등 — 18에서 썼던 그 라이브러리. TS, 더 열려 있음, 좋은 첫 문
runner-images   호스티드 러너의 VM 이미지 — 소프트웨어 추가·버전 이슈 등 커뮤니티 기여가 가장 활발
ARC             Go + K8s 오퍼레이터(08의 그것) — k8s 컨트롤러 경험(k8s 42~44)이 그대로 통하는 문
```

eks 27에서 containers-roadmap(이슈로 영향력)을 배웠다면, 여기서는 같은 지혜의 GitHub판입니다: **코드 머지만이 기여가 아닙니다** — 재현 가능한 이슈, 정확한 진단, 문서 수정이 이 생태계에서 실제로 받아들여지는 기여 형태입니다.

## C#이라는 관문에 대하여

러너 본체는 C#입니다 — 이 커리큘럼의 주 언어(Go/TS/셸)가 아니라서 당황할 수 있습니다. 두 가지를 말해두면: ① 읽기는 어렵지 않습니다 — Go를 읽을 줄 알면 C#의 async/await와 인터페이스는 금방 눈에 익습니다(lab-01이 안내합니다). ② 읽기만으로 충분한 목표가 있습니다 — 이 모듈의 목표는 "러너에 큰 기능을 넣기"가 아니라 "러너를 소스 수준에서 이해하고, 자기 언어에 맞는 문(toolkit=TS, ARC=Go)으로 기여를 시작하기"다.

## 27·28로 가는 다리

이 모듈에서 익힌 "실행계 소스 읽기"가, 27(argoproj — 배포계)과 28(tektoncd — K8s 네이티브 실행계)에서 반복됩니다. 세 생태계의 기여 문법(이슈 → 재현 → 테스트 → PR)은 같고, 거버넌스(기업 주도/CNCF/CDF)가 다릅니다 — 그 차이를 보는 것도 학습 목표입니다.
