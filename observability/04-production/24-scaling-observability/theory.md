# 이론 — 토폴로지, Thanos 구조, Mimir 대비, HA·dedup, 테넌시, 판단 지도

> **🌱 17세 눈높이 비유: 학교 도서관에서 시립 도서관 네트워크로**
> - **단일 스택(학교 도서관)** = 우리 학교 책은 다 있음 — 서가(디스크)가 차면 한계
> - **Thanos(도서관 네트워크 + 중앙 서고)** = 각 학교 도서관은 그대로(최근 책 = 단기), 오래된 책은 거대한 중앙 서고(오브젝트 스토리지)로 — 그리고 **통합 검색대(Query)** 하나로 전 학교+서고를 한 번에 검색
> - **sidecar(사서 보조)** = 각 도서관에 파견되어 책을 서고로 나르고 검색 요청에 응답
> - **compactor(서고 정리사)** = 서고의 책을 제본·압축하고 오래된 것은 요약본(다운샘플)으로
> - **HA·dedup** = 중요한 강의는 두 명이 필기(이중 수집) — 통합할 때 겹치는 부분은 하나로, 서로의 빈 곳은 채워서
> - **테넌시** = 공용 서고의 열람 규칙: 반별 서가 구분(격리)·대출 한도(쿼터)·사용 통계(귀속)

---

## 1. 멀티클러스터 토폴로지

```
중앙 집약(push): 각 클러스터 → remote_write → 중앙 저장소(AMP·Mimir)
  + 단순한 전역 뷰·중앙 룰 / - 중앙이 SPOF·네트워크 의존, 전송 비용

연합/분산 쿼리(pull): 각 클러스터에 저장 유지, 쿼리 시 팬아웃(Thanos Query)
  + 클러스터 자율성(로컬은 단절에도 생존)·전송 절약
  / - 쿼리 시 모든 소스 가용성 필요, 토폴로지 복잡

하이브리드(실전 다수): 로컬 단기(수집·알림 자율) + 장기는 오브젝트
  스토리지 집약 + 전역 쿼리 — Thanos가 정확히 이 형태
  (14의 하이브리드 판단과 같은 사상: 자율성과 집약의 균형)
```

## 2. Thanos 구조 (부품별)

```
Sidecar: Prometheus 옆에 — 2시간 블록을 오브젝트 스토리지에 업로드
  + Query의 실시간 질의를 로컬 Prometheus에 프록시
  (★ 08의 스택에 무침습 — 수집 체계 그대로라는 것이 채택 용이성)
Store Gateway: 오브젝트 스토리지의 블록을 쿼리 가능하게 (과거 담당)
Query(Querier): PromQL 창구 — sidecar들(실시간)+store(과거)에 팬아웃·병합·dedup
Compactor: 블록 압축·다운샘플(5m·1h) — 장기 쿼리를 가볍게, 보존 정책 집행
  (★ 싱글톤 운영 — 동시 실행 금지)
Ruler(선택): 전역 recording/alerting rule 평가
Receiver(선택): remote_write 수신 모드 — sidecar 대신 push 토폴로지로 쓸 때

저장의 전환: 로컬 디스크(TSDB 블록) → 오브젝트 스토리지(같은 블록 형식!)
  → 보존 = 스토리지 정책 + Compactor 설정 (디스크 증설의 세계에서 해방)
  → cncf 39·05의 사상("오브젝트 스토리지의 바다")이 메트릭에 적용된 것
```

## 3. Mimir와의 접근 차이 (그리고 Cortex 계보)

```
Thanos: Prometheus를 남기고 옆에 붙임 (sidecar·블록 업로드)
  기존 스택 무침습·점진 도입 / 쿼리 팬아웃의 소스 관리
Mimir(Cortex 계보): remote_write로 중앙에 밀어 넣는 완전 중앙형
  수평 확장 아키텍처(ingester·querier 분리)·강한 테넌시(1급 개념)
  / 중앙 클러스터 운영의 무게

선택 감각:
  기존 Prometheus 다수 + 점진 확장 → Thanos가 자연스러움
  그린필드 초대규모·강한 테넌시 → Mimir 검토
  (둘 다 오브젝트 스토리지 장기 저장·PromQL 호환 — 수렴 진화)
AMP와의 관계(14): AMP는 "관리형 Mimir류" — 이 모듈의 구조를 알면
  AMP가 무엇을 대신해 주는지(그리고 요금이 무엇의 값인지) 정확해집니다
```

## 4. HA 수집과 dedup

```
구성: Prometheus를 replica 2로 (같은 스크레이프 설정, external_labels에
  replica: A/B 구분)
동작: 둘 다 긁고 둘 다 저장/업로드 — 한쪽 다운 시에도 다른 쪽에 데이터
쿼리: Thanos Query --query.replica-label=replica
  → 같은 시계열의 두 벌을 하나로 병합 (구멍은 서로 채움)
비용: 수집·저장 2배 — HA의 값 (핵심 메트릭에 값어치)
알림: 양쪽에서 평가+Alertmanager dedup(그룹핑) — 10의 체계가 흡수
```

## 5. 테넌시 — 공유 저장소의 규율

```
격리: 테넌트 식별을 수집 경로에서 강제 주입(라벨/헤더) —
  쿼리는 자기 테넌트로 스코프 (Mimir·Loki·Tempo의 X-Scope-OrgID)
쿼터: 테넌트별 활성 시계열·수집률·쿼리 동시성/기간 한도
  → 한 팀의 카디널리티 폭발(03)·쿼리 폭주가 이웃을 못 해치게
  (sampleLimit의 저장소판 — 폭발 반경의 격벽)
귀속: 테넌트별 사용량 메트릭 → 22의 showback 데이터
운영: 쿼터 초과의 UX(에러 메시지·요청 절차)까지 설계 — 격벽이
  "플랫폼 팀과 싸우는 벽"이 아니라 "협상의 시작점"이 되게 (cncf 47)
```

## 6. 판단 지도 (최종)

```
규모 1 — 클러스터 1~2·보존 수주·팀 소수:
  단일 kube-prometheus-stack (08) — 끝. 층을 늘리지 않는 것이 설계
규모 2 — 수 개 클러스터·장기 보존·AWS 중심·플랫폼 인력 최소:
  각 클러스터 수집(08 유지) + AMP 집약(14) + AMG(15)
  — 관리형 우선 (09의 원리)
규모 3 — 수십 클러스터·멀티클라우드·시계열 수천만·전담 팀:
  Thanos(점진·기존 활용) 또는 Mimir(중앙·테넌시) + 테넌시·쿼터 체계
  — 단 "설치≠운영"(cncf 45): compactor 사고·스토리지 비용·부품 운영이
    관리형 요금과 교환된다는 정직한 계산

전 규모 공통(이 파트의 결론):
  수집 체계(08)·라벨 규율(03)·구조화(02)·상관 규약(12)·동선(23)은 불변
  — 규모가 바꾸는 것은 저장·쿼리 토폴로지뿐. 기본기가 이식성입니다
```
