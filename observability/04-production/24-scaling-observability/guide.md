# 학습 가이드 — 규모가 바꾸는 질문들

## 클러스터 하나의 세계가 끝날 때

```
조직이 크면 생기는 새 질문:
  "전 클러스터의 payment 에러율을 한 쿼리로" — 글로벌 쿼리
  "us-east 클러스터가 통째로 죽어도 그 메트릭 이력은 남아야" — 장기·중앙 저장
  "Prometheus가 죽으면 그 사이 수집은?" — HA 수집
  "A팀 쿼리 폭주가 B팀 대시보드를 느리게" — 테넌시(격리)
  "13개월 보존 + 시계열 수천만" — 08의 벽 (단일 노드의 한계)
```

이 질문들에 대한 세 갈래 답(14에서 예고): AMP(관리형 집약), Thanos/Mimir(자체 확장), 그리고 "아직 필요 없음"(단일 스택 유지). 이 모듈은 자체 확장의 구조를 이해해 **세 갈래를 진짜로 비교할 수 있는 눈**을 만듭니다 — 구조를 모르면 판단이 아니라 신앙이 됩니다.

## Thanos — 단일 Prometheus를 부품으로 강등시키는 설계

```
발상: Prometheus는 그대로 두고(수집·단기), 그 옆과 위에 부품을 더합니다

[클러스터 A] Prometheus + Thanos sidecar ──┐
[클러스터 B] Prometheus + Thanos sidecar ──┼─→ [오브젝트 스토리지]
                                           │    (S3/MinIO — 장기 블록)
[중앙] Thanos Query ←──────────────────────┘
        ↑ 하나의 PromQL 창구 — 전 클러스터+과거 전체를 한 쿼리로
       Store Gateway(스토리지의 블록을 쿼리에) + Compactor(압축·다운샘플)

핵심 통찰:
  단기·수집 = 각 클러스터의 Prometheus (08의 체계 그대로!)
  장기 저장 = 오브젝트 스토리지 (디스크의 벽 → S3의 바다, cncf 05·39의 사상)
  전역 뷰 = Query가 여러 소스를 팬아웃·병합
→ 14의 "절단선"과 같은 사고: 수집은 그대로, 저장·쿼리를 확장
  (remote_write 방식의 Mimir와 접근이 다를 뿐 — theory에서 비교)
```

## HA와 중복 제거 — 이중화의 사후 처리

```
수집의 HA: 같은 대상을 Prometheus 2대가 긁습니다 (replica A·B)
  → 한 대가 죽어도 공백 없음
  → 그런데 데이터가 2벌 — 쿼리가 2배로 보이면?
  → Thanos Query의 dedup: replica 라벨을 인식해 병합
  (완벽한 두 벌이 아니라 "서로 다른 구멍이 난 두 벌"을 잇는 것 — 그래서
   단순 평균이 아니라 시계열 단위 선택)
```

## 테넌시 — 22의 조직 장치가 기술이 되는 곳

```
공유 저장소의 규율:
  격리: 테넌트 라벨 강제(수집 시 주입) → 쿼리가 자기 것만
  쿼터: 테넌트별 시계열·쿼리 동시성 한도 (한 팀의 폭주가 전체를 못 잡게 —
        03 사고의 조직판 방어)
  귀속: 테넌트별 사용량 = 22의 showback의 데이터
→ Mimir·Loki·Tempo가 테넌트 개념을 1급으로 갖는 이유 (Grafana 스택의 설계)
→ AMP도 워크스페이스 분리로 유사 효과
```

## 판단의 최종 지도 — 이 모듈의 목적지

```
규모 1 (클러스터 1~2, 보존 수주): 단일 스택 (08) — 층을 늘리지 마세요
규모 2 (수 클러스터, 장기, AWS 중심): AMP 집약 (14) — 관리형 우선
규모 3 (수십+, 멀티클라우드, 전담 팀): Thanos/Mimir — 이 모듈의 세계
어느 규모든: 수집 체계(08)·규약(라벨·구조화)·동선(23)은 동일 —
  바뀌는 것은 저장·쿼리의 토폴로지뿐
```
