# 이론 — SLI 설계, SLO 산정, 에러 버짓, 번레이트, 멀티윈도우, 조직 계약

> **🌱 17세 눈높이 비유: 시험 목표 점수와 실수 예산**
> - **100점 목표(100% 가용성)** = 불가능하고, 쫓다 보면 아무 문제도 새로 안 풀게 됨(릴리즈 동결)
> - **SLO(목표 95점)** = "95점이면 충분"이라고 합의 — 그럼 **5점은 실수해도 되는 예산(에러 버짓)**
> - **버짓의 용도** = 예산이 남았으면 어려운 새 문제(위험한 릴리즈)에 도전, 예산을 다 썼으면 복습(안정화)
> - **번레이트(예산 소진 속도)** = 시험 초반 10분 만에 실수 예산 절반을 썼다면(번레이트 높음) 즉시 전략 수정(page), 조금씩 꾸준히 새고 있다면(낮은 번레이트) 쉬는 시간에 점검(ticket)
> - **멀티윈도우** = "방금 5분"과 "최근 1시간"이 둘 다 나쁠 때만 경보 — 한 문제 실수(스파이크)로 호들갑 떨지 않기
> - **조직 계약** = 예산 소진 시 "게임 금지·복습"을 부모와 합의해 둔 것 — 합의 없는 목표는 장식

---

## 1. SLI 설계 — 사용자 관점의 비율

```
표준형: SLI = 좋은 이벤트 / 전체 이벤트  (0~1의 비율)

가용성 SLI:
  sum(rate(http_requests_total{code!~"5.."}[w]))
  / sum(rate(http_requests_total[w]))
  결정 사항: 4xx는? (대개 "사용자 잘못"이라 제외하되 401 폭증 같은
  플랫폼 원인은 예외 — 분모·분자 정의를 문서화, 08 사고의 교훈)

지연 SLI (03의 결실):
  sum(rate(http_request_duration_seconds_bucket{le="0.3"}[w]))
  / sum(rate(http_request_duration_seconds_count[w]))
  = "300ms 이내 응답 비율" — le=0.3 버킷이 그대로 분자
  ★ SLO 경계가 버킷에 없으면 근사 오차 — 버킷 설계 = SLO 설계 (03)

측정 지점:
  앱 메트릭(자기 보고): 구현 쉬움, 앱 앞 장애 못 봄
  LB(ALB)·엣지: 사용자에 가까움 — 교차 검증용 (01 사고의 해독제)
  합성 모니터링(외부 프로브): 최후의 사용자 관점
```

## 2. SLO 산정 — 야망이 아니라 데이터로

```
절차:
  ① 과거 4~12주의 SLI 실적 측정 ("우리는 실제로 몇을 내고 있나")
  ② 사용자 기대·비즈니스 요구와 대조 ("문제 없던 수준은?")
  ③ 실적보다 약간 낮게 시작 (지킬 수 있는 약속부터 — 조이는 건 나중에)

나인의 감각:
  99%    = 30일 중 7.2시간   (내부 도구 수준)
  99.9%  = 43분              (일반 서비스의 출발점)
  99.95% = 21.6분
  99.99% = 4.3분             (매우 비쌈 — 아키텍처 급이 달라짐)
  ★ 한 자릿수 올릴 때마다 비용은 배수로 — "몇이 필요한가"는
    비즈니스 질문 (기술 자존심이 아니라)

의존성의 물리:
  A(99.9%)가 B(99.9%)에 직렬 의존하면 A의 상한은 ~99.8%
  → 내 SLO는 의존하는 것들의 SLO 아래에서만 정직합니다
```

## 3. 에러 버짓 — 계산과 의미

```
버짓 = (1 - SLO) × 기간의 전체 이벤트 (또는 시간)
  99.9%/30일, 월 1억 요청 → 10만 요청의 실패 허용
잔량 = 버짓 - 기간 내 누적 실패
  → 대시보드의 중심 지표 ("이번 달 앞으로 몇 분/몇 건 남았나")

의미의 전환:
  버짓 있음 = 위험 감수 가능 (릴리즈·실험·카오스 테스트도!)
  버짓 없음 = 안정화 모드 (합의된 브레이크)
  ★ "버짓을 안 쓰고 남기는 것"도 실패 신호 — 지나치게 보수적
    (릴리즈를 안 하고 있다는 뜻일 수 있음)
```

## 4. 번레이트 — 소진 속도의 수학

```
번레이트 = 관측 창의 실패율 / (1 - SLO)
  예: SLO 99.9% (허용 실패율 0.1%), 지금 1h 창 실패율 1.44%
  → 번레이트 = 14.4 → 30일 버짓이 2일 만에 증발할 속도

기준 배율 (구글 SRE 워크북의 관례):
  14.4× (1h 창에서 2% 버짓 소진) → page
  6×    (6h 창에서 5% 소진)      → page
  1×~3× (1~3d 창, 느린 누수)     → ticket

단순 임계 대비 우위 (10의 진화):
  스파이크: 1h 평균으로 희석 → 안 울림 (소음 억제)
  낮은 누수(0.2% 지속): 번레이트 2× → ticket으로 잡힘
  (단순 "에러율>1%"는 이걸 영원히 놓칩니다)
```

## 5. 멀티윈도우 알림 — 구현 형태

```
page 규칙 (빠른 소진):
  expr: (
    slo:error_ratio:rate1h  > 14.4 * 0.001    # 긴 창: 지속성 확인
    and
    slo:error_ratio:rate5m  > 14.4 * 0.001    # 짧은 창: "지금도" 진행 중
  )
  → 두 창의 AND: 이미 끝난 스파이크(1h만 높음)나 순간 요동(5m만 높음)
    에 안 울림 — for(10)의 정교한 진화형

ticket 규칙 (느린 누수):
  6h/30m 조합 (6×), 3d/6h 조합 (1×) 등

전부 recording rules(08) 위에:
  slo:error_ratio:rate5m / rate1h / rate6h ... 를 미리 계산
  → 정의 단일화(08의 교훈) + 알림 평가 비용 절감
```

## 6. 조직 계약 — 기술 밖의 절반

```
버짓 정책 (문서화·경영 합의가 핵심):
  50% 소진: 위험 릴리즈 보류·리뷰 강화
  100% 소진: 기능 릴리즈 동결 → 안정화 작업 우선
  (동결 권한과 예외 절차를 명시 — "누가 브레이크를 밟나")

SLO 리뷰 (분기):
  실적 vs 목표: 항상 여유 → 조이거나 릴리즈 가속
                자주 위반 → 목표 재협상 or 신뢰성 투자
  사용자 불만과 SLI의 정합: SLI가 아픔을 못 잡으면 SLI 재설계

안티패턴 예고:
  대시보드용 SLO (계약 없음 — 장식)
  100% 목표 (버짓 0 = 릴리즈 불가라는 뜻인데 아무도 인지 못 함)
  원인 지표 SLI (CPU로 SLO — 사용자와 무관)
```

## 요약 카드

| 질문 | 답 |
|------|----|
| SLI 표준형? | 좋은 이벤트/전체 (가용성=비5xx 비율, 지연=임계 이내 비율) |
| 지연 SLI 구현? | le=경계 버킷/count — SLO 경계가 버킷에 있어야 (03) |
| SLO 산정? | 과거 실적 기반, 지킬 수 있는 수준부터 — 나인당 비용 배수 |
| 에러 버짓? | (1-SLO)×기간 — 혁신의 예산, 남기는 것도 실패 신호 |
| 번레이트? | 실패율/(1-SLO) — 14.4×=30일 버짓 2일 소진 속도 |
| 멀티윈도우? | 긴 창(지속)+짧은 창(현재진행) AND — 스파이크·누수 모두 올바르게 |
| 조직 계약? | 버짓 소진=릴리즈 동결의 합의 — 없으면 숫자는 장식 |
| 의존성? | 내 SLO는 의존 SLO 아래에서만 정직 (직렬 곱) |
