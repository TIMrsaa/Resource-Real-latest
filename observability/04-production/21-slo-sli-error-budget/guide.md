# 학습 가이드 — 100%는 목표가 아닙니다

## 왜 SLO인가 — 두 개의 잘못된 극단

```
극단 A: "무조건 안정" — 릴리즈가 두려워 배포가 분기 1회로
  → 변경이 크고 위험해짐 (역설적으로 더 불안정, cicd의 교훈)
극단 B: "빨리빨리" — 장애가 반복돼도 기능 출시 우선
  → 신뢰 붕괴, 온콜 소진

SLO의 답: "얼마나 안정적이어야 하는지"를 숫자로 합의
  99.9%면 → 30일에 43분의 실패는 허용 = ★ 에러 버짓
  버짓이 남아 있으면 → 과감히 릴리즈 (버짓은 쓰라고 있는 것)
  버짓이 소진되면 → 릴리즈 멈추고 안정화 (합의된 브레이크)
→ 안정 vs 혁신의 다툼을 감정이 아니라 예산 협상으로
```

## SLI — "사용자 관점"이라는 한 가지 기준

```
나쁜 SLI: CPU 사용률, Pod 재시작 수 (사용자는 모름 — 원인 지표)
좋은 SLI: 사용자가 겪는 것
  가용성: 성공 요청 / 전체 요청 (5xx가 실패)
  지연: 임계(예: 300ms) 이내 요청 / 전체 ← ★ 분위수 대신 "좋은 이벤트 비율"로
  (정확성·신선도 등 도메인별 확장)

측정 지점의 정직함:
  앱 자기 보고(08의 메트릭)는 "앱까지 온 요청"만 —
  LB 앞에서 죽은 요청은 안 잡힘 → 가능하면 사용자에 가까운 지점
  (ALB 메트릭·엣지)과 교차 검증. 01의 사고("초록인데 고객 이탈")의 해독제
```

## 지연 SLI의 형태 — 03의 histogram이 여기서 결실

```
"p99 < 300ms" 형태의 문제: 분위수는 창·집계에 민감하고 버짓 계산이 어색
표준 형태: "300ms 이내로 응답한 요청의 비율 ≥ 99.9%"
  = histogram의 le=0.3 버킷 / 전체 (03의 누적 버킷이 그대로 분자!)
  → ★ SLO 경계(0.3)가 버킷에 있어야 정확 — 03에서 "버킷 설계=SLO 경계"
    라 한 이유가 여기서 완성됩니다
```

## 에러 버짓과 번레이트 — 알림의 완성형

```
버짓: (1 - SLO) × 기간 = 허용 실패량
  99.9% / 30일 → 0.1% × 30일 = 43.2분 (또는 요청 수 기준)

번레이트: 지금 속도로 태우면 버짓이 며칠 만에 끝나는가
  번레이트 1 = 정확히 기간 끝에 소진 (설계된 소비)
  번레이트 14.4 = 이 속도면 30일 버짓이 2일 만에 증발 → ★ 깨워야 함

왜 번레이트 알림인가 (10의 진화):
  단순 "에러율 > X%"는: 짧은 스파이크에 울리고(소음), 낮은 지속 누수는
  놓칩니다(30일 내내 0.2%면 버짓 2배 초과인데 임계 미달)
  번레이트는 "버짓 관점의 심각도"라 둘 다 올바르게 다룸

멀티윈도우:
  빠른 소진(1h 창, 높은 배율) → page (지금 불남)
  느린 소진(6h~3d 창, 낮은 배율) → ticket (누수 — 아침에)
  + 짧은 창과 긴 창의 AND (스파이크 소음 억제 — for의 진화형)
```
