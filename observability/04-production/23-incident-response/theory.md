# 이론 — 대응 동선, 역할, 심각도, runbook, 포스트모템, 게임데이, 온콜 지속성

> **🌱 17세 눈높이 비유: 학교 화재 대응 훈련**
> - **감지** = 화재경보(21의 번레이트 — 진짜일 때만 울리도록 이미 조율됨)
> - **완화 우선** = 불의 원인 조사보다 **대피와 초기 진화가 먼저** — "왜 났는지"는 불 끄고 나서
> - **역할 분담** = 지휘(교감=IC)는 소화기를 들지 않습니다 — 전체를 보고 결정. 방송(소통)이 따로 있어야 교무실에 문의 전화가 폭주하지 않음
> - **runbook(비상 매뉴얼)** = "경보 A동 3층 → 이 소화전, 이 대피로" — 패닉 상태의 뇌를 대신하는 절차. 단 매뉴얼이 낡으면(소화전 위치가 바뀌었는데) 배신
> - **포스트모템** = "누가 불냈어!"가 아니라 "왜 배선이 노후했고 점검이 없었나" — 비난하면 다음부터 아무도 신고를 안 함
> - **게임데이(소방 훈련)** = 훈련 없는 매뉴얼은 종이 — 실제로 뛰어 봐야 계단이 막혀 있는 걸 압니다

## 1. 동선의 다섯 단계 (신호 소비의 관점)

```
감지: 알림(10·21) → annotation의 대시보드·runbook 링크가 출발점
  목표 지표: 사용자 신고 대비 알림 선행률 (감지의 품질)

트리아지: 심각도 판정 (아래 3절) + 역할 소집 + 사건 채널 개설
  첫 질문: "사용자 영향의 범위와 정도" (L1·SLO 버짓 — 21)

조사: 05의 반사 + 12의 상관 동선
  메트릭(무엇이·언제부터) → 배포 마커(그때 뭐가 바뀜? — 09)
  → 트레이스(어디가) → 로그(왜) → Events(플랫폼 조치?) → audit(누가?)
  ★ 완화 단서가 나오면 조사를 중단하고 완화로 (동선은 순차가 아닙니다)

완화: 사용자 복구 우선의 선택지 사전 목록화
  롤백(가장 흔한 정답 — 배포 마커가 근거)·스케일 아웃·페일오버·
  기능 플래그 끄기·의존 우회·(카나리면) 트래픽 원복
  ★ 완화 조치도 기록 (타임라인 — 조치가 새 증상을 만들 수 있으므로)

해소·회고: 안정 확인(SLO 회복) → 타임라인 정리 → 포스트모템(5절)
```

## 2. 역할 — IC 체계

```
IC: 결정과 조율만 — 조사 금지 (빠지는 순간 전체를 놓침)
  결정 사항: 심각도 변경·완화 실행 승인·에스컬레이션·해소 선언
조사: 신호를 파는 사람(들) — IC에게 발견을 보고
소통: 상태 페이지·경영·CS 공지 — ★ 조사자를 질문에서 격리하는 방패
서기: 타임라인 (시각·발견·조치·결정) — 포스트모템의 원천

소규모의 현실: 겸직하되 모자를 명시적으로 ("IC 모자 쓴다")
교대: 장기 사건은 IC도 교대 (판단력은 소모품)
```

## 3. 심각도와 에스컬레이션

```
심각도(예시 — 조직마다 정의):
  SEV1: 전면 장애·데이터 위험 — 전원 소집, 경영 통지, 상태 페이지
  SEV2: 주요 기능 저하(SLO 급속 소진 — 21의 fast burn) — IC 체계 가동
  SEV3: 부분·우회 가능(slow burn) — 담당 팀, 업무 시간 처리
기준을 숫자로: "SLO 번레이트 X 이상 = SEV2" — 다툼 없는 판정 (21의 보상)
에스컬레이션: "30분 내 완화 실마리 없으면 다음 단계" — 시간 기반 규칙
  (혼자 끙끙대는 30분이 가장 비싼 30분)
```

## 4. runbook as code

```
저장: Git (알림 annotation이 링크 — 10) — 검색이 아니라 도착
구조(알림당 한 문서):
  ## 의미: 무엇이 위험한가 (한 줄)
  ## 즉시: 첫 확인 3개 (명령·링크 — 복붙 가능하게)
  ## 완화 후보: 조건 → 조치 표 ("배포 30분 내면 롤백 우선")
  ## 에스컬레이션: 기준과 대상
  ## 함정: 하지 말 것 (과거 사고의 유산 — "X 재시작은 캐시 스탬피드 유발")

유지 체계 (낡음과의 싸움):
  포스트모템 액션에 "runbook 갱신" 기본 포함
  게임데이에서 runbook대로 밟아보기 (안 맞으면 그 자리에서 수정)
  분기 스캔: 링크 무결성(09의 uid!)·명령 유효성
★ 자동화와의 관계: 반복 검증된 runbook 절차는 자동화 후보
  (수동 → 문서화 → 자동화의 사다리) — 단 완화 자동화는 신중히
  (잘못된 자동 롤백이 더 큰 사고를)
```

## 5. 포스트모템 — 비난 없음의 구조

```
원칙: 사람은 시스템 안에서 합리적으로 행동했다고 가정
  "왜 실수했나" (X) → "무엇이 그 실수를 가능/유도했나" (O)
  비난의 비용: 다음 사건부터 사실이 숨겨집니다 — 학습 불능 조직

구조:
  요약·영향 (사용자·시간·SLO 버짓 소모 — 21의 숫자로)
  타임라인 (서기 기록 — 감지·조치·결정의 시각)
  분석: 기여 요인들 (근본 "원인"은 대개 복수 — 5 whys를 갈래로)
  잘된 것 (탐지가 빨랐다면 왜? — 강화할 것도 학습)
  액션 아이템: 소유자·기한·유형(예방/탐지/완화/절차)
    ★ 유형 균형 점검 — 전부 "예방"이면 탐지·완화 투자를 놓친 것

액션의 수명: 트래커 등록 → 분기 리뷰에서 미완 소환
  "액션 아이템의 완료율"이 조직 학습의 지표 (미완의 산 = 반복 장애 예고)
```

## 6. 게임데이 설계

```
목적: 동선·배선·runbook·사람의 통합 검증 ("있다"≠"쓰인다")
설계:
  시나리오: 과거 사고 재연 또는 pitfalls의 사고들 (이 파트에 22개 있습니다!)
  주입: 실제 결함 주입 (스테이징 또는 통제된 프로덕션 — 카오스 도구)
  관찰자: 동선을 기록 (어디서 막혔나 — 시간 측정)
  범위 공지: 참가자에겐 시나리오 비공개, 그러나 "게임데이 중" 표식은 명확히

측정(개선의 재료):
  감지까지(알림이 울렸나 — 안 울렸으면 10·21의 구멍)
  착지까지(링크가 이어졌나 — 09·12의 배선)
  원인 후보까지(동선이 돌았나 — 조사 시간)
  완화까지(runbook이 맞았나)
사후: 미니 포스트모템 → 대시보드·배선·runbook 수정 (그 자리에서)
주기: 분기 — 신규 입사자 온보딩과 결합하면 일석이조
```

## 7. 온콜의 지속 가능성

```
부담 측정: 교대당 page 수(10의 통계)·야간 비율·수면 방해
건강선: 교대당 page 소수 — 초과가 상습이면 알림(10)·시스템의 문제
로테이션: 충분한 인원(최소 4~6인 권장)·명확한 인수인계(열린 사건·주의점)
보상·회복: 야간 대응 후 회복 시간 — 소진된 온콜은 판단력이 없습니다
★ 온콜의 부담은 시스템 품질의 후행 지표 — 알림 피로(10)·반복 장애
  (포스트모템 액션 미완)의 청구서가 온콜에게 옵니다
```
