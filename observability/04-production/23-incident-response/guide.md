# 학습 가이드 — 새벽 3시의 설계

## 장애의 순간, 무엇이 사람을 구하나

새벽 3시, 페이저가 울립니다(21의 번레이트 — 울릴 자격이 있는 알림입니다). 그 다음 15분을 결정하는 것들:

```
① 알림에 실려 온 것: 대시보드 링크(09)·runbook(이 모듈) — 검색하지 않게
② 첫 화면(L1, 09): 어디가 아픈가 — 반사적으로
③ 조사 동선(12의 상관): 메트릭→트레이스→로그 클릭 — 수작업 없이
④ runbook: "이 알림이면 이 순서로" — 새벽의 뇌를 대신하는 절차
⑤ 완화 우선의 원칙: 원인 규명보다 사용자 복구가 먼저
```

이 다섯이 이 파트에서 지은 것들의 소비처입니다 — 그리고 이 모듈은 그것들을 **절차와 사람의 설계**로 묶습니다.

## 동선의 표준형 — 다섯 단계

```
감지(Detect): 알림(10·21) — 사용자 신고보다 먼저가 목표
트리아지(Triage): 심각도 판정·역할 소집 — "얼마나 큰불인가"
조사(Investigate): 신호 릴레이(05의 반사) — 단, 완화가 급하면 건너뜁니다
완화(Mitigate): ★ 사용자 복구 우선 — 롤백·스케일·페일오버·기능 끄기
  ("왜"는 몰라도 "언제부터"(배포 마커, 09)만 알면 롤백은 가능합니다!)
해소·회고(Resolve·Learn): 타임라인 기록 → 포스트모템 → 시스템 개선
```

**완화 우선**이 가장 중요한 전환입니다 — 조사는 지적 만족을 주지만, 사용자는 복구를 기다립니다. "원인은 모르지만 15:02 배포 이후입니다 → 롤백"이 새벽의 정답인 경우가 많습니다(배포 마커가 이 판단을 3분에 만듭니다).

## 역할 분담 — 혼자 다 하지 않습니다

```
IC(Incident Commander): 지휘 — 조사하지 않습니다! (전체 상황·결정·자원)
조사(Ops): 신호를 팝니다 (한 명 이상)
소통(Comms): 상태 페이지·내부 공지 — 조사자를 질문에서 보호
서기(Scribe): 타임라인 기록 (포스트모템의 재료 — 기억은 사라집니다)

소규모 팀: 한 사람이 겸하되 역할을 의식적으로 전환
  ("지금부터 나는 IC" — 모자를 명시적으로 바꿔 쓰기)
왜 분리? 조사에 빠진 IC는 전체를 놓치고, 소통 없는 대응은
  조직 전체를 조사자에게 몰려들게 합니다 (질문 폭격이 조사를 죽입니다)
```

## runbook — 새벽의 뇌를 대신하는 문서

```
좋은 runbook의 구조 (알림 하나당):
  이 알림의 의미 (한 줄 — 무엇이 위험한가)
  즉시 확인 (첫 3개 명령/링크 — L1·핵심 쿼리)
  완화 후보 (조건 → 조치: "배포 직후면 롤백", "특정 Pod면 재시작")
  에스컬레이션 (언제 누구를 — 기준 명시)
  주의 (하지 말 것 — 과거 사고에서 배운 함정)

낡음과의 싸움 (09 대시보드와 동일한 문제):
  runbook as code: Git에, 알림 annotation에서 링크(10),
  포스트모템마다 갱신 의무, 게임데이에서 검증 — 낡은 runbook은
  새벽에 사람을 배신합니다
```

## 포스트모템 — 시스템을 고치는 회고

```
비난 없음(blameless)의 이유: 비난하면 다음부터 사실이 숨겨집니다
  → "누가"가 아니라 "무엇이 이것을 가능하게 했나"
구조: 타임라인(서기의 기록) → 영향(SLO·버짓 소모, 21) →
     원인 분석(5 whys — 단, 근본 원인은 대개 복수) →
     액션 아이템 (소유자·기한 — ★ 그리고 실제로 하는지 추적)
액션의 수명 관리: 포스트모템 액션이 백로그에서 썩으면
  같은 장애가 옵니다 — 분기 리뷰에서 미완 액션을 소환
```

## 게임데이 — 이 파트의 실기 시험

lab-02가 이 파트 전체의 캡스톤입니다: 모의 장애를 심고, 알림→동선→runbook→완화를 실제로 밟습니다. 09·12에서 "게임데이로 검증하라"고 미뤄 둔 숙제 — 대시보드가 쓰이는지, 배선이 이어지는지, runbook이 맞는지, 사람이 역할을 아는지는 **리허설만이 드러냅니다.**
