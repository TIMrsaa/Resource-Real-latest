# 이론 — 프로파일 종류, 샘플링 원리, 플레임그래프, diff, 누수 동선, 판단

> **🌱 17세 눈높이 비유: 공부 시간의 스톱워치가 아니라 CCTV 타임랩스**
> - **메트릭** = "오늘 8시간 공부했다" (총량)
> - **트레이스** = "수학에 3시간, 그중 미적분 단원에 2시간" (구간)
> - **프로파일** = 책상 위 타임랩스를 1분에 한 장씩 찍어 보니 "미적분 2시간 중 1시간 20분은 같은 문제 3번을 반복해서 풀고 있었다" — **어느 행동이 시간을 먹었는지**
> - **샘플링이라 가벼움** = 매 순간 기록(비디오)이 아니라 주기적 스냅샷 — 공부를 방해하지 않을 만큼만
> - **지속** = 시험 망친 날에만 찍는 게 아니라 항상 — "지난 화요일과 오늘의 타임랩스 비교(diff)"가 가능
> - **플레임그래프** = 타임랩스를 행동별로 쌓은 막대 — 넓은 막대가 시간 도둑

---

## 1. 프로파일의 종류

```
CPU 프로파일: 어느 콜스택이 CPU 시간을 쓰나 (샘플: 주기마다 실행 중 스택)
  → "CPU 급증의 범인 함수" — 가장 흔한 용도
heap(메모리) 프로파일: 어느 코드가 할당했고/잡고 있나
  alloc(할당량 — churn·GC 압박 조사) vs inuse(보유량 — ★ 누수 조사)
goroutine/스레드: 어디서 대기·블록 중인가 (교착·누수 조사)
mutex/block: 락 경합이 어디서 (동시성 병목)

언어별 소스:
  Go: 런타임 내장 pprof (표준·정확) — Pyroscope류가 주기 수집
  JVM: async-profiler 계열
  전 언어 공통: eBPF 스택 샘플링(19) — 계측 무관, 언어 무관 (Parca류)
    (심볼 정보가 있어야 함수명이 보임 — 스트립된 바이너리 주의)
```

## 2. 샘플링의 원리 — 왜 항상 켜도 되나

```
방식: 초당 N회(예: 19~99Hz) "지금 실행 중인 콜스택"을 기록
  → 통계적 근사: 많이 실행되는 코드일수록 샘플에 많이 잡힘
  → 오버헤드: 주기가 낮으면 ~1% 수준 (전수 기록이 아니므로)
  → 03의 histogram과 같은 사상: 전수가 아니라 분포의 근사로 충분

함의:
  희귀·짧은 이벤트는 안 잡힐 수 있음 (통계의 한계 — 그건 트레이스·로그의 몫)
  시간이 쌓일수록 정확 (지속 수집의 또 다른 이유)
```

## 3. 플레임그래프 읽기 (guide 확장)

```
기본: 가로 넓이=샘플 비율(시간), 세로=콜스택(아래=호출자)
패턴 사전:
  넓은 단일 탑: 명확한 병목 함수 — 최적화 1순위
  낮고 넓은 바닥 + 얇은 탑 다수: 분산된 비용 — 한 방이 없음 (구조 개선)
  runtime/GC 프레임이 넓음: 할당 과입니다 — alloc 프로파일로 (누가 할당?)
  lock/futex 대기가 넓음: 경합 — mutex 프로파일로
  icicle(역방향) 뷰: leaf부터 집계 — "가장 많이 실행된 말단"

diff 플레임그래프 (지속의 보상):
  두 시점(배포 전/후, 정상/이상)의 차이만 색으로
  → "새 버전에서 serialize()가 +30%" — 회귀 범인 특정이 한 화면
```

## 4. 메모리 누수 동선 (05 카탈로그의 완성)

```
① 메트릭(03·08): container_memory_working_set 우상향 + OOMKilled 이력
   → "누수 의심" (여기까지가 05에서 가능했던 것)
② heap 프로파일(inuse)을 시간 축으로: 어느 콜스택의 보유량이 자라나
   → diff(어제 vs 오늘): 자라는 스택만 도드라짐
③ 코드: 그 스택의 할당 지점 — 캐시 무한 증가? 리스너 미해제? 전역 맵?
④ 수정 후: 같은 메트릭·프로파일로 검증 (평평해졌나)

★ ①만으로는 "재시작 처방"(임시)뿐이었습니다 — ②가 범인 코드를 짚습니다
  주의: inuse로 볼 것 (alloc은 churn — GC가 회수하는 건 누수 아님)
```

## 5. 트레이스·신호 연결과 저장

```
span→프로파일: 트레이스의 느린 span → 같은 시간대·서비스·(가능하면 Pod)의
  프로파일 조회 — Grafana에서 Pyroscope/Parca 데이터소스로 점프 (12의 상관 확장)
  OTel의 profiles 신호 표준화 흐름: span과 프로파일의 연결이 점점 1급 시민으로

저장의 물리 (역시!):
  프로파일 = 콜스택 트리의 시계열 — 저장량은 스택 다양성×주기×대상 수
  보존: 최근 상세 + 과거 다운샘플 (메트릭과 같은 노화 전략)
  → 다섯 번째 신호에도 같은 비용 원리 (01의 "관측=비용" 최종 확인)
```

## 6. 판단 — 다섯 번째 층의 자리

```
도입 신호:
  "내부의 왜"가 조사마다 반복 (트레이스가 span까지 좁혀도 그 안이 미궁)
  리소스 비용 최적화 압박 (CPU/메모리 절감 = 직접 비용 절감 — FinOps)
  저지연 요구 (p99 뒤의 GC·경합을 코드 수준으로)
과함:
  소규모·성능 무압박 — 4신호 동선으로 충분
도입 형태:
  eBPF 전체 샘플링(Parca류): 전 워크로드 즉시 — 19의 도입 정석과 동형
  런타임 통합(Pyroscope류): 언어 심층 (Go pprof의 정밀함)
→ 19의 분담표 최종형: eBPF(구간)·OTel(여정)·프로파일(코드)·
  메트릭(총량)·로그(사건) — 완성된 영토 지도
```
