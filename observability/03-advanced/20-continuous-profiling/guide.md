# 학습 가이드 — 조사의 마지막 1미터

## 남아 있던 마지막 질문

커리큘럼의 조사 동선을 복기하면:

```
메트릭(03·08): "payment가 느리다/CPU가 높다"     — 무엇이
트레이스(04·11): "payment의 handler 구간이 1.2s"  — 어디가
로그(02·06): "pg_timeout, retry 3"               — 왜(사건)
eBPF(19): "이 통신이 오갔고 드롭됐다"              — 구간의 사실

남은 질문: "CPU 급증의 범인 함수는? 그 1.2s 중 800ms를 태운 코드는?
          메모리를 계속 잡고 안 놓는 놈은 누구?"
→ 콜스택 수준의 질문 — 프로파일링의 영토 (조사의 마지막 1미터)
```

## "지속"이 바꾸는 것 — 프로파일링의 관측화

```
전통 프로파일링: 문제가 생기면 → 도구 붙이고 → 재현 기다림
  문제 ①: 프로덕션에 붙이기 부담 (오버헤드·재시작)
  문제 ②: "지난주의 그 순간"은 이미 지나감 — 재현 안 되면 끝
  (05의 교훈 그대로: 보존 안 된 신호로는 과거를 조사할 수 없습니다)

지속 프로파일링: 낮은 오버헤드 샘플링으로 항상 수집·저장
  → "지난 화요일 14시의 CPU 프로파일"이 조회 가능 (신호가 됐습니다!)
  → ★ diff: 배포 전후·정상 vs 이상 시점의 프로파일 비교
    "새 버전에서 어느 함수가 더 먹기 시작했나"가 한 화면
```

가능해진 기술적 배경이 19의 eBPF입니다 — 커널에서 주기적으로 콜스택을 샘플링(예: 초당 수십 회)하면 언어 무관·계측 무관·낮은 오버헤드로 전 프로세스가 프로파일됩니다(Parca 계열). 언어 런타임 내장 프로파일러(Go pprof 등)를 긁는 방식(Pyroscope 계열)도 공존합니다.

## 플레임그래프 — 30초 읽기 법

```
       [main ████████████████████████]      ← 아래가 호출자
       [handler ██████████][bg ████]
       [parse ██][calc ████████]             ← 위가 피호출자
                  [hash ███████]  ← 넓다 = 시간을 많이 씀

규칙:
  가로 넓이 = 소요 시간(샘플 수) 비율 — ★ 넓은 것이 범인 후보
  세로 = 콜스택 깊이 (아래가 부모)
  색은 대개 장식 (라이브러리 구분 정도)
읽는 순서: 제일 넓은 탑을 위로 따라가며 "어느 leaf가 넓나"
  → calc→hash가 전체의 40% = hash 최적화가 최대 레버리지
```

## 신호 간 연결 — 트레이스에서 프로파일로

```
11의 span이 "handler 1.2s"라면 → 그 시간대·그 서비스의 프로파일로 점프
  → 12의 상관(메트릭↔트레이스↔로그)에 프로파일이 합류
  (OTel 생태에 profiles 신호 통합이 진행 중 — span↔profile 연결 표준화 흐름)
→ "어디가(트레이스)"에서 "어느 코드가(프로파일)"로 — 동선의 완결
```

## 언제 이 층이 필요한가 — 판단 미리보기

```
필요: 성능이 비용/UX에 직결(대규모·저지연), "내부의 왜"가 반복,
     리소스 최적화 압박(FinOps — CPU 20% 절감이 큰 돈)
과함: 소규모·성능 무압박 — 4신호로 충분한 조직에 다섯 번째 층은 사치
→ 19의 분담표에 프로파일링 열을 채우는 것으로 판단 완성
```
