# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. IRSA 정책 부분 누락 — 한 신호만 조용히 실종
세 정책(AMP·X-Ray·CW) 중 하나를 빠뜨리면 그 목적지만 403으로 실패합니다 — 메트릭은 AMP에 잘 가는데 트레이스만 X-Ray에 없는 식. Collector는 exporter별로 독립 실패하므로 "일부만 안 온다"는 증상이면 exporter별 로그·메트릭(otelcol_exporter_send_failed_*)을 확인하세요. 14의 remote_write 감시 원칙이 exporter마다 적용됩니다 — 목적지별 실패 알림.

### 2. ADOT에 업스트림 최신 컴포넌트를 기대
순정 contrib에 있는 특정 processor/exporter가 ADOT엔 없거나 버전이 뒤일 수 있습니다(검증된 셋 위주). "문서엔 있는데 왜 안 되지"의 원인 — 문서가 업스트림 것이었던 경우입니다. ADOT 릴리스 노트의 컴포넌트 목록으로 확인하고, 꼭 필요하면 해당 층만 순정을 쓰는 혼합 구성을 검토하세요. 배포판과 업스트림의 관계(cncf 27의 감각)를 항상 의식할 것.

### 3. EMF를 주력 메트릭 경로로 사용
"CW에 다 보내자"며 전 메트릭을 awsemf로 흘리면, EMF는 Logs ingest 과금 + 디멘션 조합마다 커스텀 메트릭 과금이라 13의 요금 함정 두 개를 동시에 밟습니다. EMF는 CW 알람·AWS 통합에 꼭 필요한 소수 지표의 보조 경로입니다 — filter로 선별하고, EMF 로그 그룹에도 retention을 설정하세요(잊기 쉬운 지점).

### 4. 샘플링을 SDK와 Collector 양쪽에서 이중으로
11에서 head(SDK)+tail(gateway) 조합을 배웠는데, ADOT 전환 때 X-Ray SDK식 샘플링 규칙과 OTel 샘플러가 섞이면 이중 샘플링으로 "트레이스가 예상보다 훨씬 적다"가 됩니다. 샘플링 결정 지점을 설계도로 명시하세요(SDK head 비율 → Collector tail 정책 → X-Ray는 받은 것 저장). 17의 X-Ray 샘플링 규칙과의 관계도 이 설계도에서 정리됩니다.

### 5. Collector 리소스를 애드온 기본값으로 방치
애드온이 깔아주는 기본 리소스로 대규모 트래픽을 받으면 memory_limiter가 상시 발동(수신 거부)하거나 OOM이 납니다 — 11의 자기 보호는 "죽지 않기"이지 "다 받기"가 아닙니다. 신호 볼륨(샘플·span 수)에 맞춰 replicas·리소스를 용량 계획하고, otelcol_* 자기 메트릭(수신·거부·큐)을 AMP로 보내 감시하세요(관측 수집기의 관측).

## 실무 사고 사례: "반쪽 트레이스의 미스터리 — 두 세계의 샘플링"

한 팀이 ADOT로 전환하며 이상한 현상을 만났습니다: X-Ray 콘솔의 트레이스 수가 기대의 1/10 수준이고, 그마저 **중간이 뚝뚝 끊긴 반쪽 트레이스**가 많았습니다.

조사 과정:

1. **볼륨 미스터리** — OTel SDK의 head 샘플링은 25%로 설정했는데 실제는 ~2.5%만 저장됐습니다. 원인: 일부 서비스가 예전 X-Ray SDK 기반이라 **X-Ray 샘플링 규칙(기본 1req/s + 5%)**을 따로 적용 중이었습니다 — 25% × (X-Ray 규칙) = 이중 샘플링. 두 세계(OTel·X-Ray SDK)의 샘플러가 겹친 것.
2. **반쪽 미스터리** — OTel 서비스는 W3C traceparent(04)로, X-Ray SDK 서비스는 X-Amzn-Trace-Id로 전파하고 있었습니다. 서로의 헤더를 못 읽어 경계에서 trace가 끊기거나(04의 전파 형식 불일치 — 폴리글랏 함정의 AWS판), 각자 샘플링 결정을 따로 해 한쪽만 남았습니다.
3. **suppressed 존재** — 게다가 ALB를 경유하는 경로는 ALB가 X-Amzn-Trace-Id를 붙이는데, OTel 쪽 propagator 설정에 xray가 없어 그 컨텍스트가 이어지지 않았습니다.

수습:

1. **전파 통일** — 전 서비스의 propagator를 [tracecontext, xray] 겸용으로(OTel SDK는 다중 propagator 지원) — 어느 헤더가 와도 읽고, 나갈 때 둘 다 씁니다. AWS 인프라(ALB)의 헤더와도 이어짐.
2. **샘플링 단일화** — 샘플링 결정은 OTel head(parentbased) 한 곳으로, X-Ray SDK 규칙은 비활성(모두 전달). tail 정책은 Collector에.
3. **이관 로드맵** — X-Ray SDK 잔존 서비스를 OTel로 순차 이관(혼재 기간의 규약을 문서화).
4. **검증 절차** — 04 lab-02의 검증(대표 경로 trace가 끝까지 이어지는가)을 ADOT 전환 게이트로.

**교훈:**
- 두 계측 세계(OTel·벤더 SDK)의 혼재는 전파 형식과 샘플링이 **각각** 충돌합니다 — 겸용 propagator와 샘플링 단일화가 브리지
- AWS 인프라(ALB·API GW)는 X-Amzn-Trace-Id의 세계 — xray propagator를 켜야 인프라까지 이어집니다 (17)
- "트레이스가 적다/끊긴다"는 항상 샘플링 설계도와 전파 설정부터 — 04의 원리가 진단의 기준
- 이기종 혼재는 과도기의 현실 — 혼재 기간의 규약(어느 헤더·어느 샘플러)을 명문화하세요

★ 16의 결론: ADOT는 "아는 도구의 AWS 옷"이라 진입은 쉽지만, AWS 세계의 고유 규약(X-Ray ID·헤더·샘플링 규칙)과 OTel 표준이 만나는 접합부가 실전의 함정입니다. 접합부의 규약(전파 겸용·샘플링 단일화)을 설계하면, 수집 한 번으로 세 목적지가 채워지는 우아한 그림이 완성됩니다. 17에서 그 X-Ray를 조사 도구로 부립니다.
