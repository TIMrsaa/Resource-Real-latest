# 자가 점검 퀴즈

**Q1.** X-Ray 모델을 OTel로 번역하세요 (segment·subsegment·annotation·metadata·trace ID·헤더).

**Q2.** annotation과 metadata의 구분 기준은? 어떤 규율(03)의 재연인가요?

**Q3.** X-Ray의 고유 영토는 무엇이고 왜 오픈소스 스택에선 구조적으로 불가능한가?

**Q4.** 서비스 맵의 정체와 조사에서의 역할은? 노드 폭발의 원인과 예방은?

**Q5.** X-Ray 샘플링 규칙의 구조(reservoir+rate)와 운영 가치는? OTel과의 관계 정리는?

**Q6.** "에러 트레이스가 없다"의 원인과 설계 답은?

**Q7.** X-Ray vs Tempo/Jaeger 판단의 두 축과 "계측 통일"이 판단에 주는 효과는?

**Q8.** "범인은 큐였다" 사고의 전개와 "공백의 목록화"란?

---

## 정답

**A1.** trace는 동일 개념. segment = 서비스 하나가 남기는 기록(OTel 서버 span 근사), subsegment = 세그먼트 내부 작업(DB·외부 호출 — OTel 클라이언트/내부 span). annotation = 인덱스되어 필터 표현식으로 검색 가능한 키-값(OTel attribute 중 indexed_attributes로 지정된 것), metadata = 인덱스 안 되는 상세(열면 보임). trace ID: X-Ray는 1-{시각 hex}-{96bit} 형식으로 OTel 128bit와 달라 awsxray exporter가 변환(16). 전파 헤더: X-Amzn-Trace-Id(Root;Parent;Sampled) — W3C traceparent와 겸용 propagator로 공존시킵니다(16의 접합부).

**A2.** 기준: **검색·비교에 실제로 쓸 것인가**. 필터 표현식·Analytics 비교에 쓸 소수의 유한한 조사 차원(order_type·user_tier 등)만 annotation(인덱스)으로, 개별 식별자·상세 페이로드는 metadata(비인덱스 — 트레이스를 열면 보임)로. 이것은 03의 "라벨 vs 본문" 규율의 재연입니다 — 인덱스는 비용(제한·성능)이므로 유한한 차원만 올리고 unbounded 값은 본문에 두는 사상이 메트릭 라벨·Loki 라벨(12)·X-Ray annotation에서 동일하게 반복됩니다.

**A3.** 고유 영토: AWS 관리 서비스들이 트레이스에 직접 참여하는 것 — ALB/API Gateway가 여정의 시작 세그먼트를, Lambda가 자기 세그먼트(콜드스타트 포함)를, SQS/SNS가 컨텍스트를 메시지와 릴레이(04의 비동기 경계 해결)를, DynamoDB·S3 호출이 서브세그먼트(스로틀 가시화)를 남깁니다. 오픈소스에서 불가능한 이유: Jaeger/Tempo는 **우리가 계측한 코드**의 span만 볼 수 있는데, 관리 서비스 내부는 계측을 심을 수 없는 영역이라 앱 span 사이의 "공백"으로만 남습니다 — 그 공백을 채우는 것은 서비스 소유자(AWS)의 자기 증언뿐입니다.

**A4.** 정체: 트레이스 데이터의 세그먼트 관계를 집계해 자동 생성되는 의존 그래프 — 노드(서비스·AWS 리소스)마다 요청율·에러율·지연(RED)이 붙고 상태가 색으로 표시됩니다. "선언한 구조"(cncf 42 카탈로그)가 아니라 실제 트래픽이 그린 "관측된 사실"의 지도. 역할: 조사의 L1 — 빨간 노드·느린 엣지에서 시작해 해당 트레이스 목록→간트로 내려갑니다. 노드 폭발: service.name이 인스턴스·배포별로 달라지면(Pod명 포함 등) 노드가 증식해 지도가 미로가 됩니다 — 예방은 service.name을 논리 서비스 단위로 고정하는 이름 규율(시맨틱 컨벤션, cncf 12).

**A5.** 구조: 규칙마다 reservoir(초당 고정 개수 확보 — 저트래픽에도 최소 샘플 보장) + fixed_rate(초과분의 비율), 서비스·호스트·URL 경로·메서드 매칭과 우선순위로 적용(기본 1req/s+5%). 운영 가치: 콘솔/API에서 규칙을 바꾸면 SDK/ADOT가 폴링해 반영 — **배포 없이** "이 경로만 50%로" 같은 동적 조정이 가능(장애 조사 중 즉시 강화). OTel과의 관계: 결정 지점은 한 곳(16의 교훈) — OTel 샘플러 주도면 X-Ray 규칙은 미사용, X-Ray 규칙 주도면 ADOT에 규칙 연동 — 양쪽 동시 적용은 이중 샘플링 사고입니다.

**A6.** 원인: 비용 절감으로 head 샘플링을 낮게(예: 5%) 잡으면 드물게 발생하는 에러의 트레이스가 확률적으로 안 잡힙니다 — 메트릭은 에러 발생을 알리는데(전수 카운트) 조사할 사례가 없는 상태로, 04의 신호 분담("개수는 메트릭, 사례는 트레이스")에서 사례 쪽이 구멍 난 것. 설계 답: 볼륨 절감은 정상 트래픽에서 하고 "재미있는 것"은 보존합니다 — Collector tail 정책으로 에러·고지연 100% 부스트(11·16), 또는 X-Ray 규칙으로 에러 경로에 reservoir 확보. head(볼륨 통제)+선별 보존의 조합이 기본형입니다.

**A7.** 두 축: ① AWS 관리 서비스 의존도 — ALB·SQS·Lambda·DynamoDB가 아키텍처에 깊으면 그 구간의 가시성(X-Ray의 영토)이 결정적이므로 X-Ray, ② Grafana 상관 완성도 — exemplar·derived fields의 매끈한 클릭 동선(12)과 이식성이 우선이면 Tempo. 계측 통일의 효과: 앱 계측을 OTel(11·16)로 통일해 두면 백엔드 전환이 Collector exporter 설정 변경으로 끝나므로 — 판단이 무겁지 않고(잘못 골라도 갈아타기 쉬움), 시스템별로 다른 백엔드를 쓰거나(사고 사례) copy로 병행 비교하는 유연함도 얻습니다.

**A8.** 전개: 주문 지연 조사에서 오픈소스 스택(Tempo)은 EKS 앱 span만 보여 전부 정상 — "우리는 정상" 상태로 이틀. X-Ray 병행 전송 후 서비스 맵에서 SQS→람다 엣지가 주황으로 즉시 드러남 — 트레이스의 큐 체류 8~12분, 람다 세그먼트의 스로틀 플래그로 원인(예약 동시성 부족) 확정. Tempo에선 이 구간이 계측 불가 공백이라 구조적으로 발견 불가능했습니다. "공백의 목록화": 우리 트레이스에서 안 보이는 구간(관리 서비스들)을 명시적으로 목록으로 만들고, 각 공백에 대체 신호(SQS 큐 깊이·람다 스로틀 메트릭 등)를 배정해 알림으로 감시하는 것 — 안 보이는 곳일수록 메트릭이 지켜야 한다는 신호 분담의 응용이자, 스택의 한계를 아는 것이 스택 이해라는 결론입니다.
