# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 로그 그룹 retention 방치 — Never expire의 복리
로그 그룹의 기본 보존은 "Never expire"다. 아무도 설정하지 않으면 모든 로그가 영원히 쌓입니다 — 저장 요금이 매달 복리로 늘고, 몇 년 뒤 "이 300개 로그 그룹 중 뭘 지워도 되나"를 아무도 모르는 늪이 됩니다. 로그 그룹 생성 시 retention 설정을 관례(IaC 기본값·생성 자동화)로 만들고, retention 없는 그룹을 주기 감사하세요. lab에서 "첫 행동이 retention"인 이유입니다.

### 2. "나중에 정리하지"— ingest는 이미 냈습니다
비용이 걱정되자 오래된 로그를 지우거나 보존을 줄입니다 — 하지만 CW Logs의 지배 항목은 ingest(수집 시점 과금)라 이미 낸 돈은 돌아오지 않습니다. 절감의 레버리지는 시간 역순이 아니라 파이프라인 역순입니다: 보내기 전 필터(최대) > 보내는 곳 분리(S3 계층화) > 보존 단축(최소). 06의 수문이 관리형에서 돈의 수문이 됩니다.

### 3. audit 로깅을 켜 두고 잊음
보안 점검 때 audit을 켰다가 끄지 않으면, API 서버의 모든 요청 기록이 계속 ingest됩니다 — 대형 클러스터에서 audit은 로그 그룹 중 최대 볼륨이 되기 쉽습니다. 규정상 필요하면 보존·계층화(S3)를 설계하고, 조사용이었다면 기간 한정 활성화를 절차화하세요. "켜기"보다 "끄기·계층화"가 설계입니다.

### 4. 고카디널리티를 CW 커스텀 메트릭으로
"Pod별·경로별 메트릭을 CW에 넣자"며 디멘션 조합을 늘리면, CW는 디멘션 조합마다 커스텀 메트릭으로 과금하므로 청구서가 폭발합니다 — 03의 카디널리티 물리가 여기선 요금으로 직접 옵니다. 고카디널리티 앱 메트릭은 AMP(14, Prometheus 요금 모델)가 유리하고, CW 메트릭은 플랫폼·AWS 서비스 지표와 소수의 핵심 지표에 쓰는 분업이 정석입니다.

### 5. Logs Insights를 대시보드처럼 반복 실행
같은 Insights 쿼리를 팀원들이 하루에도 수십 번 실행합니다 — 스캔 GB 과금이 반복됩니다. 반복되는 질문은 승격하세요: 메트릭 필터(로그→메트릭)로 만들어 알람·그래프로, 또는 정기 쿼리 결과를 대시보드에 고정. Insights는 탐색(비정형 조사)용이고, 정형화된 질문은 메트릭의 몫입니다 — 신호 분담(01)의 비용판.

## 실무 사고 사례: "관측 비용이 워크로드 비용을 넘던 날"

한 회사의 월 AWS 청구서를 검토하던 재무팀이 이상한 항목을 발견했습니다 — CloudWatch 비용이 EC2(노드) 비용을 넘어서 있었습니다. 워크로드보다 관측이 비싼 역전. 원인 분석에 들어간 플랫폼 팀이 찾아낸 것들:

1. **디버그 로그의 전면 수집** — 한 팀이 문제 조사를 위해 서비스 전체를 debug 레벨로 올렸다가 되돌리지 않았습니다(02의 레벨 규율 부재). 로그 볼륨이 8배가 됐고, 그 전부가 ingest 과금됐습니다. 아무도 몰랐습니다 — ingest 볼륨 알람이 없었으므로.
2. **retention 전무** — 로그 그룹 200여 개 중 보존 설정이 있는 것은 10개. 나머지는 Never expire로 수년치가 쌓여 있었습니다.
3. **커스텀 메트릭의 증식** — 여러 팀이 저마다 Pod명·고객 ID까지 디멘션으로 넣은 커스텀 메트릭을 밀어 넣고 있었습니다(03의 라벨 사고의 CW 요금판).
4. **audit 3개 클러스터 상시 on** — 1년 전 보안 감사 때 켠 것. 목적은 끝났는데 로그는 계속 흘렀습니다.
5. **Insights 쿼리 남용** — 한 팀의 "모니터링 스크립트"가 5분마다 30일 범위 Insights 쿼리를 돌리고 있었습니다 — 스캔 과금의 자동화.

수습 (요금표를 설계로 번역):

1. **수문 재정비** — Fluent Bit 필터로 debug·헬스체크 차단, 레벨 규율 복원(프로덕션 debug는 기간 한정+자동 원복).
2. **retention 일괄 정책** — IaC로 로그 그룹 생성 시 보존 필수화, 기존 그룹 일괄 설정, 장기 필요분은 S3 내보내기로 계층화.
3. **메트릭 분업** — 고카디널리티는 AMP로 이전, CW 커스텀 메트릭은 승인제(디멘션 상한).
4. **비용 관측 상설화** — 로그 그룹별 IncomingBytes 대시보드+급증 알람, 월간 관측 비용 리뷰를 운영 회의에 (22의 선행 실천).
5. **스크립트 교정** — 반복 Insights를 메트릭 필터로 승격.

석 달 뒤 CloudWatch 비용은 1/5로 — 조사 능력의 손실 없이(지운 것은 질문 없는 데이터뿐).

**교훈:**
- 관리형 관측의 장애 모드는 다운이 아니라 **청구서**입니다 — 비용이 관측 대상이어야 합니다
- ingest 중심 구조에서 절감은 소스(수문)에서 — 시간 역순 정리는 헛수고
- 임시 조치(debug on·audit on)는 자동 원복과 짝지어라 — "끄기"를 설계하세요
- 카디널리티는 어디서나 물리입니다 — Prometheus에선 메모리로, CW에선 요금으로
- 조사 능력과 비용은 상충하지 않습니다 — 질문 없는 데이터를 지우는 것이 둘 다를 지킵니다

★ 13의 결론: CloudWatch는 운영을 대신해 주지만 설계는 대신해 주지 않습니다 — 그리고 그 설계 언어가 요금표입니다. ingest ≫ 저장이라는 물리 하나에서 수문·보존·계층화·분업의 전 판단이 나옵니다. 14(AMP)에서 메트릭의 관리형 판단을, 18(OpenSearch)에서 로그 저장소 3파전을 이어갑니다.
