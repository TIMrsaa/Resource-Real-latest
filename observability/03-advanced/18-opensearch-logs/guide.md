# 학습 가이드 — 인덱스 설계가 곧 비용 구조라는 것의 완성

## 3파전의 마지막 주자

12에서 예고한 표를 완성할 때입니다:

```
             Loki(12)          OpenSearch(지금)      CW Logs(13)
인덱스        라벨만            ★ 전문 역색인          관리형(스캔 시 과금)
검색          라벨+grep         모든 필드 즉시          Logs Insights(스캔)
집계·분석     기본적            ★ 강력(agg·대시보드)    stats 수준
비용 중심     저장 저렴          인덱스·노드(상시)       ingest
운영          가벼움            ★ 무겁습니다(이 모듈)       없음
```

OpenSearch의 존재 이유는 **검색·분석의 최강**입니다: "지난 30일, 이 IP 대역에서, 이 에러 코드를 낸, User-Agent에 X가 포함된 요청" — 어떤 조합 조건이든 즉시. 보안 로그 분석(SIEM)·감사·풀텍스트 조사가 이 힘을 필요로 합니다. 대가는 역색인의 물리입니다.

## 역색인 — 힘과 비용의 근원

```
정색인: 문서 → 단어들 (책을 펴면 내용)
역색인: 단어 → 문서들 (색인 페이지: "timeout"이 나온 모든 문서 목록)

로그 한 줄이 들어오면:
  토큰화 → 필드마다 역색인 갱신 → 여러 자료구조 기록
  → ★ 쓰기가 비쌉니다 (CPU·IO — 색인 작업)
  → ★ 인덱스가 큽니다 (원본 대비 상당 비율 — 전 필드 색인 시)
  → 대신 읽기(검색)가 어떤 조건이든 빠릅니다

Loki와의 대칭:
  Loki: 쓰기 싸고(라벨만) 읽기 일부 느림(grep)
  OpenSearch: 쓰기 비싸고 읽기 전부 빠름
  → "쓰기 최적 vs 읽기 최적" — 사용 패턴이 선택을 정합니다
```

## 인덱스 설계 — 운영의 8할

```
시간 기반 인덱스: logs-2026.07.11 처럼 일/주 단위로 쪼갬
  → 오래된 것은 인덱스째 관리(이동·삭제) — ISM의 단위
샤드: 인덱스를 나누는 물리 단위 — ★ 과다하면 클러스터가 죽습니다 (단골 사고)
매핑: 필드의 타입 정의 — 동적 매핑 방치 시 "매핑 폭발" (02의 구조화 로그가
  필드를 만드니, 무한 필드 = 무한 매핑)
→ 03의 카디널리티, 12의 라벨 규율과 같은 계열의 물리가
  "필드 수·샤드 수"라는 이름으로 또 등장합니다
```

## ISM — 로그의 노화 관리

```
로그의 가치는 시간에 따라 급감합니다:
  0~3일: 활발한 조사 (hot — 빠른 노드·SSD)
  ~30일: 가끔 조회 (warm — 싼 노드)
  ~1년: 규정용 보관 (cold/S3 — 거의 조회 없음)
  이후: 삭제 (delete)
ISM(Index State Management): 이 여정을 인덱스 단위로 자동화
→ 13의 "계층화"가 OpenSearch 안에서는 ISM으로 구현됩니다
→ 수명 정책 없는 OpenSearch = 디스크가 차서 죽는 예약 (단골 사고 2)
```

## AWS에서의 형태

```
Amazon OpenSearch Service: 관리형 도메인 (노드 타입·수를 우리가 정함)
  → "관리형이지만 용량 설계는 우리 몫" — RDS와 같은 급의 관리형
OpenSearch Serverless: 용량 자동 (OCU 과금) — 운영 더 적고 단가 다름
Fluent Bit / Fluentd(07의 copy!) → OpenSearch output — 파이프라인은 그대로
```
