# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 샤드 과입니다 — 조용히 자라는 클러스터 킬러
일 단위 인덱스 × 기본 샤드 수 × 레플리카 × 인덱스 종류가 곱해져 몇 달 뒤 샤드가 수천 개가 됩니다. 샤드마다 메모리·파일핸들을 먹어 마스터 노드가 클러스터 상태 관리에 허덕이고, 어느 날 노드 하나가 죽으면 복구 리밸런싱이 클러스터를 마비시킵니다. 규율: 샤드당 수십 GB 유지, 볼륨에 맞춘 샤드 수 설계(작은 인덱스는 1샤드·주 단위 인덱스), rollover로 크기 기반 분할, _cat/shards 주기 점검.

### 2. 동적 매핑 방치 — 매핑 폭발
02의 구조화 로그는 자유롭게 필드를 만듭니다 — 동적 매핑에 맡기면 팀들이 넣는 필드가 수천 개로 불어나 매핑이 비대해지고 색인·검색이 느려지며, 타입 충돌(같은 필드가 어떤 문서에선 숫자, 어떤 문서에선 문자열)로 색인 거부가 납니다. 인덱스 템플릿으로 핵심 필드를 선언하고 dynamic을 통제(strict 또는 자유 영역 분리)하세요 — 색인의 절제가 네 번째 반복(03·12·17·18)인 이유입니다.

### 3. ISM 없이 운영 — 디스크가 차서 죽는 예약
수명 정책 없이 색인만 하면 디스크는 단조 증가합니다. 워터마크(85%·90%)에 닿으면 OpenSearch가 샤드 배치를 거부하고 인덱스를 read-only로 잠급니다 — **쓰기가 멈추고 파이프라인이 역류**합니다(07의 사고에서 OpenSearch 워터마크가 방아쇠였던 것을 기억하세요). ISM(hot→warm→delete)을 도메인 개통과 동시에 걸고, 디스크 사용률·워터마크 알림을 상설화하세요.

### 4. 보안 설정 없이 로그 저장소 노출
학습용 편의(보안 플러그인 off)를 실전에 가져가면, 로그 저장소는 시크릿·PII·감사 기록이 모이는 곳이라(02·05) 최대급 유출 표면이 됩니다. 관리형은 IAM/SAML·세밀한 접근 제어(FGAC)·VPC 배치를 기본으로, 인덱스 수준 권한(보안 로그는 보안팀만)까지. "관측 데이터도 데이터"라는 보안 원칙 — 15의 서비스 롤 절제와 같은 계열입니다.

### 5. 모든 로그를 OpenSearch로 — 최중량 저장소의 남용
"검색 되니까 다 넣자"로 전 로그를 색인하면, 대부분의 로그(한 번도 검색 안 될 debug·정상 요청)에 역색인의 쓰기·저장 비용을 냅니다 — 13의 CW ingest 남용과 같은 계열의, 더 비싼 버전. 문진(lab-02)대로 패턴별 배정: 전문 검색이 필요한 것(보안·감사·핵심 서비스)만 OpenSearch, 나머지는 Loki/CW/S3. copy(07)가 이 라우팅의 배선입니다.

## 실무 사고 사례: "일요일 새벽, 로그 클러스터가 로그를 거부하다"

한 회사의 OpenSearch(자체 운영)가 일요일 새벽 갑자기 색인을 멈췄습니다. 월요일 아침 팀이 발견한 것: 모든 인덱스가 read-only, Fluent Bit 버퍼는 노드마다 한도 초과로 드롭 중, 지난 30시간의 로그 대부분 유실.

경위 재구성:

1. **디스크 워터마크 도달** — 8개월 전 개통 이후 ISM이 없었습니다. 디스크는 꾸준히 찼고, 일요일 새벽 flood-stage 워터마크(95%)에 닿자 OpenSearch가 자체 보호로 전 인덱스를 read-only로 잠갔습니다(설계된 동작!).
2. **역류** — 색인 거부(429·403)가 Fluent Bit로 역류, 각 노드의 fs 버퍼가 차오르다 total_limit에 도달해 드롭 시작(07 사고의 재연 — 이번엔 워터마크가 방아쇠).
3. **알림의 공백** — 디스크 사용률 알림이 "노드 평균"에 걸려 있었는데, 샤드 불균형으로 특정 노드만 먼저 찼습니다 — 평균은 82%로 초록이었습니다(01·09의 평균의 함정이 저장소 운영에서).
4. **복구의 수렁** — 공간 확보를 위해 오래된 인덱스를 지우려는데 수천 개의 작은 인덱스(일 단위×종류×기본 5샤드 — 함정 1)라 삭제·리밸런싱이 몇 시간. read-only 해제 플래그도 인덱스마다 풀어야 했습니다.

복구 후 재설계:

1. **ISM 전면 적용** — hot 7일→warm 30일(레플리카 축소)→delete. 볼륨 큰 인덱스는 rollover(크기 기준).
2. **샤드 다이어트** — 인덱스 통합(주 단위·종류 통합), 템플릿 기본 샤드 1~2로, 총 샤드 수를 용량 계획 지표에.
3. **알림 재설계** — 노드별 최대 디스크 사용률(평균 금지!)·워터마크 근접·색인 거부율(429)·총 샤드 수. 그리고 Fluent Bit dropped(06)와 연계한 계단 알림(07).
4. **배정 재검토** — 문진 결과 전체 로그의 60%가 "검색된 적 없는" 부류 — Loki·S3로 재배정해 OpenSearch 볼륨 절반 감축.

**교훈:**
- read-only 잠금은 고장이 아니라 **최후의 자기 보호** — 그 전에 울렸어야 할 알림(워터마크 근접)의 부재가 사고입니다
- 저장소의 디스크는 노드별 최대로 감시 — 평균의 함정은 어디에나
- 샤드·ISM은 개통일의 설계 항목 — "나중에"는 수천 샤드가 된 뒤입니다
- 저장소 장애는 파이프라인 역류로 증폭됩니다(07) — 끝단의 건강이 파이프라인 대시보드에 있어야
- 최중량 저장소에는 그럴 가치가 있는 로그만 — 배정(문진)이 최대의 용량 계획입니다

★ 18의 결론이자 advanced 트랙의 마침표: 로그 저장소의 삼각형(Loki·OpenSearch·CW)은 "인덱스를 어디까지 만드나"의 스펙트럼이고, 그 선택은 사용 패턴이 정합니다. 그리고 어느 저장소든 — 관리형이든 자체든 — 수명(ISM·retention)과 감시(워터마크·역류)의 설계는 남습니다. "AWS는 물리를 맡고, 규약은 남는다"가 이 트랙의 마지막 문장입니다.
