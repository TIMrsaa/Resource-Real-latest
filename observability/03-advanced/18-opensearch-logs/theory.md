# 이론 — 역색인, 인덱스·샤드·매핑, ISM, 파이프라인 연결, 3파전 결론

> **🌱 17세 눈높이 비유: 백과사전의 색인 페이지**
> - **Loki(책등만 분류)** = 책등 라벨로 서가를 찾고 그 칸을 훑음 — 서가 정리는 쌉니다
> - **OpenSearch(모든 단어의 색인 페이지)** = 백과사전 뒤의 색인처럼 **모든 단어→페이지** 목록을 만들어 둠 — 어떤 단어든 즉시 찾지만, 새 페이지가 올 때마다 색인을 갱신(쓰기 비용)하고 색인 자체가 두껍습니다(저장 비용)
> - **샤드(색인의 분권)** = 색인을 여러 서랍에 나눔 — 서랍이 너무 많으면 서랍 관리에 사서가 지침(샤드 과입니다)
> - **매핑(색인 규칙)** = "숫자는 숫자로, 날짜는 날짜로" — 규칙 없이 아무 단어나 다 색인하면 색인이 무한히 두꺼워짐(매핑 폭발)
> - **ISM(서고 이동 규정)** = 새 책은 열람실(hot), 한 달 뒤 서고(warm), 일 년 뒤 창고(cold), 이후 폐기(delete) — 자동 이동
> - **핵심** = 색인의 두께가 힘이자 비용 — 무엇을 색인할지가 설계입니다

---

## 1. 역색인의 물리

```
쓰기 경로: 문서 → 분석(토큰화) → 필드별 역색인 갱신 → 세그먼트 기록
  비용: CPU(분석)·IO(색인 기록)·저장(원본+색인)
  → 대량 색인은 bulk API·버퍼(Fluent Bit/Fluentd가 담당 — 06·07)

읽기 경로: 조건 → 역색인 조회(즉시) → 문서 결합·집계
  → 어떤 필드 조합이든 빠름 + aggregation(집계)·풀텍스트

인덱스 통제 수단:
  매핑에서 필드별로: index: false (저장하되 색인 안 함 — 검색 불필요 필드)
  keyword vs text: 정확 일치용 vs 토큰화 풀텍스트용 (둘 다면 2배 색인)
  → "모든 필드 자동 색인"이 기본값의 함정 — 색인할 것을 고르는 게 설계
    (03 라벨·12 Loki 라벨·17 annotation과 같은 계열 — 네 번째 반복!)
```

## 2. 인덱스·샤드·매핑 — 운영 물리

```
시간 기반 인덱스: logs-app-2026.07.11 (일 단위 관례)
  이유: 삭제·이동이 인덱스 단위로 원자적 (오래된 로그 삭제 = 인덱스 drop)

샤드: 인덱스의 분할 단위 (프라이머리 + 레플리카)
  샤드 하나 = 루씬 인덱스 = 메모리·파일핸들 소비
  ★ 샤드 과입니다(수천 개)의 결과: 클러스터 상태 관리 폭주·마스터 부하·OOM
  관례: 샤드 크기 수십 GB 단위 유지, 일 볼륨에 맞춰 샤드 수 설계
       (작은 인덱스 × 많은 날짜 × 기본 5샤드 = 조용한 폭발)

매핑 폭발:
  동적 매핑: 새 JSON 필드가 오면 자동으로 매핑 추가
  02의 구조화 로그가 자유 필드를 만들면 → 필드 수천 개 → 매핑 비대·성능 저하
  대응: 인덱스 템플릿으로 매핑 통제, dynamic: strict/false,
       자유 필드는 flattened 타입이나 비색인으로
```

## 3. ISM — 수명 정책

```
정책 예 (개념):
  hot (0~3일): 색인·조회 활발 — 고성능 노드
    → rollover: 크기/기간 도달 시 새 인덱스로
  warm (3~30일): 조회만 — 저비용 노드로 이동, 레플리카 축소
  cold/ultrawarm (30~365일): 거의 조회 없음 — S3 기반 계층 (AWS)
  delete (>365일): 인덱스 삭제

효과: 저장 단가가 노화에 따라 계단식 하락 — "전부 hot"의 비용을 회피
★ 13의 교훈과 접합: 진짜 장기 아카이브는 OpenSearch 밖(S3 원본)이
  더 쌉니다 — ISM cold조차 "검색 가능성"의 값을 냅니다. 검색 필요 없는
  보관은 07 copy로 S3 직행이 정답
```

## 4. 파이프라인 연결 (06·07의 세 번째 목적지)

```
Fluent Bit output:
  [OUTPUT]
      Name            opensearch
      Match           kube.*
      Host            <도메인 엔드포인트>
      Port            443, tls On
      Index           logs-app          # (또는 Logstash_Format으로 날짜 인덱스)
      Suppress_Type_Name On
      AWS_Auth        On                # SigV4 (관리형 — IRSA, 14 패턴!)
      AWS_Region      ap-northeast-2
      Buffer_Size     ...               # 대량 색인 대비 (06의 버퍼)

운영 포인트:
  OpenSearch가 색인 지연(쓰기 비쌈!) → 백프레셔가 파이프라인으로 역류
  = 07의 사고 그대로 — 출력 버퍼 격리·계단 알림이 여기서도
  대량 유입 시 bulk 거부(429) → Fluent Bit 재시도·버퍼가 흡수해야
```

## 5. 3파전 결론 — 사용 패턴이 저장소를 정합니다

```
질문으로 고르기:
  "탐색적 전문 검색·복합 조건·집계 분석이 주 패턴인가요?" (보안·감사·SIEM)
    → OpenSearch (그 힘의 대가를 낼 가치)
  "라벨(서비스·네임스페이스)로 좁혀 최근 로그를 조사하는 패턴인가요?" (K8s 앱 조사)
    → Loki (12) — 저비용, Grafana 상관과 결합
  "AWS 통합(알람·audit)·운영 제로가 우선이고 볼륨이 통제되나요?"
    → CW Logs (13) — ingest 요금 설계 전제

실전은 조합 (07의 copy가 배선):
  앱 조사: Loki 또는 CW (짧은 보존)
  보안·감사: OpenSearch (ISM 계층)
  장기 아카이브: S3 (+ Athena)
  → "하나의 저장소로 전부"가 아니라 패턴별 라우팅 — tag 라우팅(06)·
    copy(07)가 이 설계의 구현 수단이었습니다

운영 무게 경고 (cncf 45의 "설치≠운영"):
  자체 OpenSearch는 이 파트 최중량 운영물 — 관리형(Service/Serverless)
  우선, 그것도 용량·샤드·ISM 설계는 우리 몫
```
