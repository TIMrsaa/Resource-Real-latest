# 이론 — eBPF 관측 원리, Hubble, 프로토콜 파싱, 한계, 분담 설계

> **🌱 17세 눈높이 비유: 건물 복도의 CCTV vs 방 안의 인터뷰**
> - **OTel 계측(방 안 인터뷰)** = 각 방(앱)에 기자를 들여보내야(SDK) 안에서 무슨 일이 있었는지 들을 수 있음 — 방마다 허락(계측)이 필요
> - **eBPF 관측(복도 CCTV)** = 복도(커널)에 카메라를 달면 **모든 방의 출입**이 즉시 보임 — 방 허락 불필요, 전 건물 한 번에
> - **보이는 것** = 누가 어느 방에 드나들었나(L4), 들고 나온 소포의 겉면(L7 — 프로토콜 헤더)
> - **안 보이는 것** = 방 안에서 뭘 했는지(앱 내부), 소포들 중 어느 것이 "같은 심부름"인지(trace_id 여정), 밀봉 소포의 내용(TLS)
> - **핵심** = CCTV는 인터뷰를 대체하지 않습니다 — 즉시·전체(CCTV)로 시작해, 깊이(인터뷰)가 필요한 곳에 기자를 보냅니다

---

## 1. 원리 — 커널 훅에서 신호로 (cncf 22의 관측 얼굴)

```
eBPF (cncf 22 복습): 커널 안 검증된 샌드박스에서 프로그램 실행
관측에 쓰는 훅:
  kprobe/tracepoint: 시스템 콜(connect·accept·read·write) 진입/복귀
  소켓·tc 훅: 패킷·페이로드 관찰
  uprobe: 유저 공간 함수 (TLS 라이브러리 후킹 등 — 조건적)

흐름: 훅에서 이벤트 수집 → eBPF 맵 → 유저 공간 에이전트 → 신호화
  (메트릭·흐름 로그·프로파일로 가공되어 기존 파이프라인 합류)

"계측 제로"의 의미:
  앱 변경 0, 재배포 0 (에이전트 DaemonSet만) — 04의 조직 마찰 우회
  언어 무관 (Go도!·서드파티 바이너리도) — 11의 언어 편차 우회
  단, "제로"인 것은 계측이지 오버헤드가 아닙니다 (미미하지만 존재)
```

## 2. Hubble — Cilium의 관측 층

```
Cilium(CNI, cncf 22)이 이미 모든 트래픽을 eBPF로 다루므로
Hubble은 그 위의 관측 창:
  flow 로그: 소스/목적지(Pod 신원!)·verdict(FORWARDED/DROPPED)·L4/L7
  hubble observe: 흐름의 tail -f
  hubble ui: 서비스 맵 (17의 맵과 비슷하되 — 네트워크 사실 기반)
  메트릭: flow·DNS·HTTP를 Prometheus로 (08 파이프라인 합류)

즉답하는 질문 (05 카탈로그 확장):
  "이 Pod가 어디로 나가나요?" — 흐름 목록
  "왜 연결이 안 되지?" — verdict DROPPED (network policy가 막음!)
  "DNS가 뭘 물어보나요?" — DNS 흐름 (cncf 20의 ndots 증폭이 눈에 보입니다!)
★ cncf 22의 "판정=관찰 지점" — 정책 드롭이 관측 이벤트가 되는 것이
  Hubble의 고유 가치 (네트워크 정책 디버깅의 표준 동선)
```

## 3. 프로토콜 파싱 자동 관측 (Pixie류)

```
원리: 커널을 지나는 소켓 데이터에서 프로토콜(HTTP·gRPC·DNS·MySQL·Redis...)
  을 파싱 → 요청 단위 레코드 → RED 메트릭·요청 로그 자동 생성
결과: 계측 없이 서비스별 HTTP 경로·코드·지연, DB 쿼리까지 보임
  → "배포 다음 날부터 전 서비스 RED"의 매력

위치 감각:
  강점: 초기 가시성·계측 사각(레거시·서드파티)·개발 환경 즉석 디버깅
  약점: 한계 ①②③(앱 내부·여정·TLS) + 데이터 볼륨(전 트래픽 파싱)
  → "OTel 도입 전의 다리" 또는 "OTel 옆의 안전망"으로 위치
```

## 4. 한계의 구조적 이해 (guide 심화)

```
① 앱 내부: 커널은 syscall 사이의 일을 모릅니다
   "핸들러 안에서 1.2초"의 내역은 프로파일링(20)·계측(11)의 몫
② 여정(trace 전파): trace_id는 앱이 헤더에 실어 나르는 약속(04)
   커널 관점: connection A와 B가 "같은 요청"이라는 표식이 없음
   (스레드·시간 상관으로 근사하는 연구·구현이 있으나 일반해 아님)
   → eBPF만으로 분산 트레이스를 대체 불가 — 구간 관측까지
③ TLS: 소켓 레벨은 암호문. uprobe로 SSL_write/read를 후킹하면
   평문 접근 가능하나 라이브러리·버전 의존 (일반화 어려움)
④ 환경: 커널 버전·BTF·권한, Fargate류 노드 접근 불가 환경에선 제약
```

## 5. 분담 설계 — 조합의 정석

```
층별 배치:
  기본 지도(전 클러스터·즉시): eBPF (Hubble 흐름·자동 RED)
  여정·비즈니스 맥락: OTel 계측 (11 — 핵심 서비스부터)
  앱 내부 성능: 프로파일링 (20)
  AWS 관리 구간: X-Ray (17)
→ 17의 "공백 목록화"를 전 도구로 확장한 것 —
  각 도구의 영토를 표로 만들고, 시스템의 질문들이 어느 영토에
  떨어지는지 매핑하는 것이 관측 아키텍처 설계입니다 (24·SIGNALS-MAP)

도입 순서의 실용해:
  ① eBPF 기본 지도 (즉시, 조직 마찰 0)
  ② 핵심 경로부터 OTel (여정이 필요한 곳 — 04의 가치)
  ③ 필요 지점에 프로파일링 (20)
```

## 요약 카드

| 질문 | 답 |
|------|----|
| eBPF 관측 원리? | 커널 훅(syscall·소켓)에서 이벤트 → 맵 → 에이전트 → 신호화 |
| 계측 제로의 의미? | 앱 변경·재배포 0, 언어 무관 — 04·11의 마찰 우회 (오버헤드 제로는 아님) |
| Hubble 고유 가치? | Pod 신원 기반 흐름 + verdict(DROPPED!) — 정책 디버깅의 표준 동선 |
| 자동 RED? | 프로토콜 파싱(Pixie류)으로 계측 없이 HTTP·DB 가시화 |
| 못 하는 것? | 앱 내부·trace_id 여정·TLS 본문(조건부)·특수 환경 |
| 분산 트레이스 대체? | 불가 — 구간 관측까지. 여정은 OTel의 영토 |
| 분담 정석? | eBPF(즉시·전체 지도) → OTel(여정·맥락) → 프로파일링(내부) |
| 도입 순서? | eBPF 먼저(마찰 0) → 핵심 경로 OTel → 필요 지점 프로파일링 |
