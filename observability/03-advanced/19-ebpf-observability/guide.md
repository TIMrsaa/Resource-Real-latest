# 학습 가이드 — 커널에서 보는 것과 볼 수 없는 것

## 왜 eBPF 관측인가 — 04의 벽 복습

```
트레이스 도입의 구조적 마찰(04):
  모든 서비스가 SDK를 붙여야 → 조직적 협조 → 도입 지연 → 반쪽 전파
자동 계측(11)이 마찰을 낮췄지만:
  언어별 편차(Go!), 레거시·서드파티 바이너리는 여전히 사각

eBPF의 제안:
  앱이 아니라 커널에 훅을 → 모든 프로세스의 시스템 콜·소켓이 지나는 길목
  → 언어·프레임워크·계측 여부와 무관하게 "통신"이 보입니다
  → 배포 즉시, 전 워크로드, 계측 제로
```

cncf 22에서 eBPF로 정책·kube-proxy 대체를 봤다면, 여기서는 같은 기술의 **관측 얼굴**입니다(Hubble이 그 산물).

## 무엇이 보이나 — 세 층위

```
① L3/L4 흐름 (가장 확실):
  누가 누구와 통신하나 (Pod↔Pod·외부), 연결 성공/거부/드롭
  → Hubble의 기본기 — "네트워크 정책이 막았나요?"의 즉답

② L7 프로토콜 (파싱 가능하면):
  HTTP 메서드·경로·코드, DNS 질의, gRPC, DB 프로토콜
  → 커널을 지나는 바이트에서 프로토콜을 해석 → RED가 계측 없이!

③ 프로세스·성능 (도구에 따라):
  CPU 스택 샘플링(→20 프로파일링과 이웃), 파일·소켓 활동
```

## 그러나 — 정직한 한계 (이 모듈의 절반)

```
한계 ① 앱 내부는 안 보입니다:
  커널은 "함수 A가 B를 불렀다"는 앱 로직을 모릅니다
  "재고 계산이 왜 1.2초?"의 답은 여전히 계측(11)·프로파일링(20)의 몫

한계 ② 분산 컨텍스트 전파가 안 됩니다:
  trace_id 릴레이(04)는 앱이 헤더를 옮겨 붙이는 행위 —
  커널 관점에선 개별 연결들일 뿐, "같은 요청의 여정"을 이을 실이 없습니다
  (일부 도구가 근사를 시도하지만 일반해가 아님)
  → eBPF는 "구간들"을 주고, "여정"은 OTel이 줍니다

한계 ③ 암호화(TLS) 본문:
  커널 소켓에선 암호문 — L7 파싱이 막힘
  (uprobe로 TLS 라이브러리를 후킹하는 접근이 있으나 조건적)

한계 ④ 커널 의존:
  커널 버전·권한(CAP_BPF)·관리 노드 제약(일부 관리형 환경)
```

## 그래서 — 분담의 설계 (lab-02의 결론)

```
eBPF 관측이 최고인 자리:
  전 클러스터 네트워크 가시성 (계측 불가 영역 포함 — 서드파티·레거시)
  도입 즉시의 기본 지도 ("누가 누구와, 얼마나, 성공률은")
  네트워크 정책·DNS·연결 문제의 조사 (cncf 22·20모듈의 단골)

OTel 계측이 여전히 필요한 자리:
  분산 트레이스 (여정 — trace_id)
  비즈니스 컨텍스트 (주문 금액·테넌트 — 앱만 아는 것)
  앱 내부 단계

→ "eBPF로 시작해(즉시·전체) OTel로 깊어집니다(여정·맥락)" —
  대체가 아니라 층의 보완. 17의 "공백 목록화"와 같은 사고방식으로
  각 도구의 영토를 정확히 알고 조합합니다
```
