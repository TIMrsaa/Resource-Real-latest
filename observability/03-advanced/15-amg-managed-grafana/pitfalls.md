# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. Viewer 대량 할당 — 사용자당 과금의 함정
"전사가 볼 수 있게" 수백 명을 할당하면, 활성 사용자당 과금이라 열람만 해도 비용이 쌓입니다. 필요한 사람(온콜·운영·관련 팀)에게만 할당하고, 대량 열람 요구(경영 리포트 등)는 스냅샷·리포트 내보내기·별도 자체 뷰어 같은 대안을 검토하세요. 사용자 수가 AMG 판단의 핵심 축인 이유입니다.

### 2. UI에서만 대시보드 관리 — 관리형이라 더 위험
"AWS가 관리하니 안전하겠지"라며 as code 없이 UI로만 만듭니다. 서버는 안 죽지만 **실수 삭제·워크스페이스 재생성·리전 이전** 앞에서는 자체와 똑같이 무방비입니다(09의 교훈은 관리형에서도). API push나 Terraform으로 Git에 진실을 두고, uid를 고정하세요. "관리형 = 백업됨"이 아닙니다 — 대시보드의 진실은 여전히 우리 몫입니다.

### 3. 서비스 롤 권한 과다·크로스 계정 방치
워크스페이스 서비스 롤에 필요 이상(쓰기·전 리소스)을 부여하거나, 크로스 계정 role chain을 검증 없이 넓게 엽니다 — 화면 도구가 조직 전체 관측 데이터의 관문이 되는 만큼 그 롤의 권한이 곧 노출 면입니다. 데이터소스별 최소 읽기 권한, 크로스 계정은 명시적 role 목록으로. 관측 도구도 보안 검토 대상입니다(audit·시크릿이 로그에 있음을 기억 — 02·05).

### 4. Grafana Alerting과 Alertmanager의 이중 정의
편하다고 Grafana UI에서 알림을 몇 개 만들기 시작하면, 10·14의 체계(PrometheusRule·Alertmanager)와 정의가 갈라집니다 — "어디서 울렸지?"·이중 발화·한쪽만 수정되는 분기(08·14의 사고 계열). 알림 정의 위치를 규약으로 일원화하고(메트릭 알림은 룰 체계로), Grafana Alerting을 쓸 거면 그 범위(다중 소스 조합 등)를 명문화하세요.

### 5. Identity Center 그룹 설계 없이 개인 단위 할당
사용자를 개인 단위로 추가하다 보면 퇴사·이동 때마다 수동 정리가 필요하고 권한이 썩습니다. Identity Center 그룹(팀 단위) ↔ Grafana 팀/폴더 권한으로 매핑해 조직 변경이 자동 반영되게 하세요 — cncf 42(카탈로그 소유권)와 같은 "조직 정보는 한 곳에서" 원칙입니다.

## 실무 사고 사례: "워크스페이스 재생성, 그리고 사라진 석 달"

한 팀이 AMG 워크스페이스의 리전을 옮기기로 했습니다(조직 정책 변경). "관리형이니 금방"이라 생각했습니다 — 새 워크스페이스를 만들고 옛것을 지웠습니다. 그리고 깨달았습니다:

1. **대시보드가 전부 UI 산물이었습니다** — 석 달간 온콜·팀들이 UI에서 다듬어 온 대시보드 40여 장이 옛 워크스페이스와 함께 사라졌습니다. as code가 아니었으므로 Git엔 아무것도 없었습니다.
2. **백업도 없었습니다** — "AWS가 관리하는데"라는 막연한 신뢰. AMG는 서버를 관리하지 워크스페이스 삭제로부터 사용자를 보호하지 않습니다(삭제는 정당한 API 호출이었습니다).
3. **재구축 중 2차 발견** — 알림 몇 개가 Grafana Alerting에 정의돼 있었다는 것도 사라진 뒤에야 알았습니다(이중 정의의 발굴). 어떤 알림이 있었는지의 목록조차 없었습니다.
4. **권한도 수작업 복원** — 개인 단위 할당이라 "누가 어디 접근했었는지"를 기억으로 재구성.

복구에 3주 — 스크린샷·기억·옛 PR 코멘트를 뒤져 대시보드를 다시 그렸습니다. 재발 방지는 이 모듈의 내용 그대로가 됐습니다: 전 대시보드 Terraform 관리(주기적 드리프트 검출), 알림 정의는 룰 체계로 일원화+목록화, 그룹 기반 권한, 그리고 "관리형 리소스도 IaC와 백업의 대상"이라는 원칙 명문화.

**교훈:**
- 관리형은 인프라 장애에서 지켜주지, **우리의 실수와 변경**에서 지켜주지 않습니다
- "재생성"은 언제나 옵니다(리전 이전·계정 통합·실수) — 그날 Git에 없는 것은 없는 것입니다
- 보이지 않는 자산(UI 산물·개인 할당·임시 알림)이 가장 먼저 사라집니다 — 자산의 전수 as code화
- 09의 규율(Git이 진실)은 도구가 아니라 원칙 — 자체든 관리형이든 동일하게 적용

★ 15의 결론: AMG는 Grafana 운영의 무게(서버·SSO·자격)를 훌륭하게 덜어주지만, 화면 자산의 진실(as code)·알림의 일원화·권한의 구조화는 여전히 설계자의 규율입니다. 관리형 시리즈(13~15)의 공통 결론이 보이기 시작합니다: **AWS는 물리를 맡고, 규약은 남습니다.** 16(ADOT)에서 수집기까지 관리형 부품으로 완성합니다.
