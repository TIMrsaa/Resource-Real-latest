# 자가 점검 퀴즈

**Q1.** 자체 Grafana 운영의 실체(부담 4가지)와 AMG가 넘겨받는 것·못 받는 것은?

**Q2.** AMG의 인증 모델과 자체 대비 우위는?

**Q3.** 데이터소스 자격이 "키 없는" 방식으로 배선되는 구조는?

**Q4.** sidecar 없는 AMG에서 as code를 유지하는 두 방법과 불변의 규율은?

**Q5.** AMG 과금 모델과 그것이 판단에 주는 함의는?

**Q6.** Grafana Alerting과 Alertmanager 체계의 역할 정리는? 왜 필요한가?

**Q7.** 자체 vs AMG 판단의 우선순위 축 세 가지와 시나리오 적용은?

**Q8.** "사라진 석 달" 사고의 원인과 관리형 시리즈(13~15)의 공통 결론은?

---

## 정답

**A1.** 자체 운영의 실체: ① 서버·DB(대시보드 저장)·업그레이드·플러그인 호환 관리, ② 인증 통합(SSO — 기업에서 최대 골치), ③ 데이터소스 자격 증명 관리(CW 키·AMP SigV4 프록시), ④ HA(화면이 죽으면 장애 조사 불능). AMG가 넘겨받는 것: 서버 운영·확장·HA, SSO(Identity Center 내장), AWS 데이터소스 자격(IAM 롤). 못 받는 것: 대시보드 자산의 진실(as code — 실수·재생성에서 보호 안 됨), 알림 정의의 일원화, 권한의 구조화 — 규율은 남습니다.

**A2.** 로컬 계정 없이 IAM Identity Center(AWS 계정 체계 통합) 또는 SAML(기존 IdP — Okta·Azure AD·Google)이 유일한 문입니다 — 처음부터 기업 SSO가 기본값. 자체 대비 우위: 자체 Grafana에서 SSO 통합은 별도 구축(설정·인증서·그룹 매핑)에 상당한 공수가 드는 일인데 AMG에선 생성 시 옵션입니다. 역할 매핑(Identity Center 사용자/그룹 → Admin/Editor/Viewer)으로 조직 체계가 화면 권한에 이어지며, 금융권 등 인증·감사 요구가 강한 조직에서 결정적 축이 됩니다.

**A3.** AMG 워크스페이스에 서비스 IAM 롤이 연결되고, 데이터소스들이 이 롤로 AWS API를 호출합니다 — AMP는 SigV4 서명 자동(같은 계정이면 드롭다운 선택 수준), CloudWatch·X-Ray는 롤의 읽기 권한으로. 어디에도 API 키·비밀번호를 저장하지 않습니다(14의 IRSA와 같은 "키 없는 인증" 사상이 화면 층에서). 다계정 조직은 role chain(assume role)으로 크로스 계정 데이터소스를 집약하되, 명시적 롤 목록·최소 권한으로 통제합니다.

**A4.** ① Grafana API push: 서비스 어카운트 토큰을 발급하고 CI(GitHub Actions 등)가 Git의 대시보드 JSON을 API로 배포 — sidecar의 pull이 push로 바뀐 GitOps 변형. ② Terraform grafana provider: 대시보드·데이터소스·폴더·권한까지 선언 관리(IaC 통합, 드리프트 검출 가능). 불변의 규율(09): Git이 진실(UI는 초안 — 확정되면 JSON을 Git에), uid 고정(링크·알림 착지 안정), datasource 변수화, PR 리뷰. 관리형은 서버를 대신 운영하지 규율을 대신 지키지 않습니다.

**A5.** 활성 사용자당 과금(Editor/Admin이 Viewer보다 단가 높음) — 인프라비 기반인 자체와 달리 사용자 수가 직접 비용이 됩니다. 함의: 소수~중간 규모 사용자(온콜·운영·관련 팀)면 AMG가 운영 절감으로 정당화되지만, 수백~수천 명 열람(사내 포털형)이면 Viewer 과금이 지배 항목이 되어 자체가 압도적으로 유리해집니다 — 사용자 수가 자체 vs AMG 판단의 핵심 축 중 하나인 이유이며, 대량 열람 요구는 스냅샷·리포트 등 대안으로 흡수합니다.

**A6.** 역할 정리: 메트릭 기반 핵심 알림은 Prometheus/AMP 룰 + Alertmanager(또는 AMP 관리형 Alertmanager) 체계로 일원화(10·14의 체계 유지)하고, Grafana Alerting은 보조적 용도(다중 데이터소스 조합 알림 등)로 범위를 명문화하거나 미사용으로 합니다. 필요한 이유: 알림이 두 곳에서 정의되면 정의 분기(08의 "같은 이름 다른 수식")와 평가 주체 혼선(14의 교훈)이 재연됩니다 — 한쪽만 수정되고, 이중 발화하고, "어디서 울렸는지"부터 조사해야 하는 상태가 됩니다. "어디서 알리는가"는 팀 규약으로 명문화할 사항입니다.

**A7.** 우선순위 축: ① SSO·인증 요구(Identity Center·감사 통합이 필요하면 AMG 결정적), ② 사용자 수(과금 — 대량 열람이면 자체), ③ 데이터소스 중심축(AWS 중심이면 AMG의 IAM 통합이 빛나고, 멀티클라우드 중심이면 강점 반감). 시나리오: 15명 스타트업+AWS 스택+Google SSO → AMG(SAML), 3,000명 열람 포털 → 자체(과금 지배), 데이터소스 절반이 GCP → 자체 우세(운영 역량 전제), 금융권 Identity Center 표준 → AMG(인증·감사 결정적). 화면은 JSON 이식이 쉬워 결정의 무게가 저장소보다 가볍습니다 — ADR로 남기되 가볍게 재평가.

**A8.** 원인: ① 대시보드 40장이 전부 UI 산물(as code 부재)이라 워크스페이스 삭제와 함께 소멸 — Git에 아무것도 없었음, ② "관리형=백업됨"이라는 막연한 신뢰(AMG는 서버를 관리하지 워크스페이스 삭제라는 정당한 API 호출로부터 보호하지 않음), ③ Grafana Alerting에 이중 정의된 알림들이 목록조차 없이 소멸, ④ 개인 단위 권한 할당이라 접근 체계도 기억으로 재구성. 공통 결론(13~15): **AWS는 물리를 맡고, 규약은 남습니다** — 요금표 읽기(13), 절단선·평가 주체(14), as code·알림 일원화(15) 전부 관리형이 대신해 주지 않는 설계자의 몫이며, 관리형의 장애 모드는 다운이 아니라 청구서와 우리 자신의 실수입니다.
