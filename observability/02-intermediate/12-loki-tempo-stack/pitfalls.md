# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. trace_id를 Loki 라벨로 승격
"trace_id로 바로 검색하고 싶어서" 라벨로 올리면 요청 수만큼 스트림이 생겨 Loki의 인덱스·청크가 폭발합니다 — 03의 카디널리티 사고가 Loki에서 재연됩니다(같은 물리!). trace_id는 본문(JSON 필드)에 두고 `| json | trace_id="..."` 필터나 derived fields로 다룹니다. Loki 라벨은 메트릭 라벨과 같은 규율: 유한한 소수(namespace·app·level)만.

### 2. 라벨 매핑 불일치로 trace to logs가 빈 화면
트레이스 속성은 `k8s.namespace.name`, Loki 라벨은 `namespace` — 매핑 설정 없이는 "Logs for this span"이 항상 빈 결과입니다. 배선은 됐는데 결과가 비면 십중팔구 이 이름 매핑(또는 시간 시프트 부족)입니다. 06(kubernetes 필터)과 11(k8sattributes)이 각자 붙이는 이름의 차이를 데이터소스 설정의 Tags 매핑으로 흡수하고, 배선 후 반드시 실제 span에서 검증하세요.

### 3. "전문 검색이 느려요" — Loki를 OpenSearch처럼 씀
라벨 없이 `{job=~".+"} |= "어떤단어"`로 전 기간을 뒤지면 Loki는 모든 청크를 brute force로 훑습니다 — 설계상 느린 게 정상입니다. Loki의 검색 습관은 "시간 범위를 좁히고, 라벨로 좁히고, 그 다음 grep"입니다. 이 습관이 조직에 안 맞으면(자유 전문 검색이 주 사용 패턴) Loki가 아니라 OpenSearch(18)가 맞는 선택일 수 있습니다 — 도구의 설계와 사용 패턴의 정합이 판단 축입니다.

### 4. exemplar가 안 보이는 세 가지 이유를 못 가림
그래프에 ◆가 없을 때: ① Prometheus 기능 플래그(exemplar-storage) 미활성, ② 계측이 exemplar를 안 실음(라이브러리·설정 확인), ③ Grafana 패널에서 Exemplars 토글 꺼짐. 세 층(저장·계측·표시)을 순서대로 점검합니다. 배선류 문제의 공통 패턴: 여러 층이 관여하고 각 층은 조용히 실패합니다 — 층별 점검 순서를 runbook으로.

### 5. 상관 배선을 만들고 검증·유지하지 않음
배선을 깔고 캡스톤까지 완주했지만, 몇 달 뒤 라벨 개편·로그 필드명 변경·데이터소스 재생성으로 **조용히 끊깁니다**(09의 uid 단절과 같은 계열). 장애의 날 "View Trace를 눌렀는데 안 열려요"가 됩니다. 신규 서비스 온보딩과 라벨·필드 변경 시 배선 체크리스트(lab-02 5절)를 절차화하고, 분기 게임데이(23)에서 클릭 완주를 리허설하세요.

## 실무 사고 사례: "세 개의 최고 도구, 이어지지 않은 세 개의 섬"

한 회사가 관측에 제대로 투자했습니다 — 메트릭은 Prometheus+Grafana, 로그는 별도 팀이 OpenSearch, 트레이스는 또 다른 팀이 Jaeger. 각각은 훌륭하게 운영됐습니다. 그런데 장애 조사 회고마다 같은 불만이 나왔습니다: "결국 세 창을 띄워 놓고 시각을 손으로 맞춰가며 봤습니다."

구체적으로:

1. **로그에 trace_id가 없었습니다** — 트레이스 도입 팀과 로깅 규약 팀이 달라, 구조화 로그 필드에 trace_id가 빠졌습니다. 트레이스에서 이상한 span을 찾아도 그 순간의 로그를 "시각 ± 몇 초"로 눈대중 매칭 — 초당 수천 건에서는 사실상 불가능(04 사고의 재연).
2. **라벨 체계가 달랐습니다** — 메트릭은 `service`, 로그는 `app_name`, 트레이스는 `service.name`. 같은 대상을 세 이름으로 불러 어떤 자동 연결도 성립하지 않았습니다.
3. **도구 간 링크가 없었습니다** — 대시보드에서 로그 시스템으로 가려면 URL을 새로 열어 검색어를 다시 입력. 조사 한 번에 복사-붙여넣기 수십 번.
4. **각 팀은 자기 도구에 만족했습니다** — 개별 도구의 완성도가 높아서 문제의식이 늦었습니다. "관측은 잘 갖춰져 있다"는 인식과 "조사가 느리다"는 현실이 공존했습니다.

전환점은 대형 장애의 포스트모템이었습니다 — 타임라인 재구성에만 4시간이 걸렸고, "도구가 아니라 연결이 없다"는 결론이 나왔습니다. 조치:

1. **공통 규약 제정** — trace_id 로그 필드 의무화(02), 라벨 사전 통일(service/namespace/env — 세 신호가 같은 이름), 시맨틱 컨벤션(cncf 12) 채택.
2. **배선 우선 투자** — 도구 추가가 아니라 연결에: exemplar, derived fields(로그→트레이스), span→로그 링크. 스택도 상관이 쉬운 조합으로 점진 통합.
3. **"클릭 완주"를 SLO처럼** — "대표 시나리오를 클릭만으로 원인까지 N분 내"를 분기 게임데이로 측정.

**교훈:**
- 관측의 성숙도는 도구 개수가 아니라 **신호 간 이동 시간**입니다
- 상관은 도구를 사면 오는 게 아니라 규약(trace_id·라벨 사전)에서 나옵니다 — 01부터의 논지가 조직 스케일에서 증명됨
- 팀별 도구 소유가 사일로를 만듭니다 — 신호는 팀 경계를 넘어 이어져야 합니다
- 개별 도구의 만족도가 전체 경험의 문제를 가립니다 — 측정할 것은 "조사 완주 시간"

★ 12의 결론이자 intermediate 트랙의 결론: 파이프라인(수집·저장)은 절반이고, 나머지 절반은 **연결**입니다 — trace_id 필드, 라벨 일관성, exemplar, 데이터소스 배선. 이 연결이 있어야 01의 릴레이가 클릭의 원이 되고, 조사가 수작업 고고학에서 분 단위 동선이 됩니다. 다음 트랙(13~18)에서 같은 구조를 AWS 관리형 부품으로 다시 세웁니다 — 부품은 바뀌어도 규약과 연결의 원리는 그대로입니다.
