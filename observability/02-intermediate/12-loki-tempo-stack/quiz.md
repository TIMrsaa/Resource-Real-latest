## 정답

**A1.** Prometheus가 시계열을 라벨로 식별하듯, Loki는 로그 스트림을 라벨 조합으로만 식별·인덱스하고 본문은 인덱스하지 않기 때문입니다(전문 역색인의 OpenSearch와 대조). 본문은 압축 청크로 오브젝트 스토리지에 저장되어 인덱스 비용이 극적으로 작습니다. 검색 동작: ① 라벨·시간으로 청크를 좁힘(인덱스, 빠름) → ② 좁혀진 청크 안을 순차 검색(brute force). 따라서 검색 습관이 설계에 종속됩니다 — "시간을 좁히고, 라벨로 좁히고, 그 다음 grep" — 라벨 없이 전 기간 전문 검색은 설계상 느린 것이 정상입니다.

**A2.** 메트릭(03)과 동일한 규율: 라벨은 유한하고 낮은 카디널리티의 소수(namespace·app·level·cluster)만. 스트림 수 = 라벨 조합의 곱이고 스트림마다 청크·인덱스 항목이 생기므로, trace_id(요청마다 고유 = unbounded)를 라벨로 하면 요청 수만큼 스트림이 생겨 인덱스·청크가 폭발합니다 — 03의 카디널리티 사고가 Loki에서 재연되는 것. 대안: trace_id는 본문(JSON 필드)에 남기고, `| json | trace_id="..."` 파이프라인 필터나 derived fields(자동 링크)로 다룹니다.

**A3.** 두 단계: ① 스트림 선택 `{namespace="shop", app="payment"}` — 라벨로 인덱스를 써서 좁힘, ② 파이프라인 — `|= "문자열"`(본문 grep), `| json`(필드 추출 — 02 구조화의 보상), `| level="error"`(추출된 필드 필터), line_format(가공). 메트릭화: `rate({...} |= "timeout" [5m])`, `count_over_time(...)`으로 로그 발생율을 메트릭처럼 — 용도는 계측 없는 레거시의 에러율 근사·로그 기반 알림. 한계: 정식 메트릭(03)보다 비싸고(청크 스캔) 정밀도가 떨어지므로 보완재이지 대체재가 아닙니다.

**A4.** Tempo는 trace_id를 키로 오브젝트 스토리지에 저장하고 인덱스를 최소화합니다 — "트레이스는 ID로 찾아온다"는 철학(TraceQL 속성 검색도 있지만 주력은 ID 착지). 상관을 전제한다는 의미: 그 ID가 어디서 오는가 — 로그의 trace_id 필드(derived fields), 메트릭의 exemplar에서 옵니다. 즉 Tempo는 단독 검색 엔진이 아니라 다른 신호가 ID를 물어다 주는 생태계(Grafana 상관)의 일원으로 설계됐고, 그 덕에 저장이 싸서 tail 샘플링 부담도 완화됩니다.

**A5.** ① derived fields(Loki 데이터소스): 로그→트레이스 — 로그 본문에서 trace_id를 정규식/JSON으로 감지해 Tempo 링크 버튼 생성. 전제: 로그에 trace_id 필드(02의 규약). ② trace to logs(Tempo 데이터소스): 트레이스→로그 — span의 시간 범위와 라벨 매핑(k8s.namespace.name→namespace)으로 Loki 쿼리 생성. 전제: 라벨 체계의 일관성(06↔11) 또는 이름 매핑 설정. ③ exemplar(Prometheus): 메트릭→트레이스 — histogram 관측에 첨부된 trace_id 견본이 그래프 ◆점이 되어 클릭 시 Tempo로. 전제: exemplar 지원 계측 + Prometheus 기능 플래그 + Grafana 패널 토글.

**A6.** ① 메트릭(p99 급등 확인 + exemplar 클릭) — "무엇이 이상한가", ② 트레이스(간트) — "어디가 느린가": GET /pay 서버 span 1.2s에 자식 span이 없음, ③ 로그(span에서 점프) — "왜": pg_timeout·재시도 3회, ④ 정량화(로그 메트릭화 또는 에러율) — "얼마나": 30%. "자식 없는 긴 부모 span"의 해석(04의 간트 읽기): 하위 호출(DB·외부 API span)이 없는데 오래 걸렸다면 그 시간은 앱 자신이 쓴 것 — 내부 로직·대기·GC 등. 이 사례에선 계측 안 된 내부 sleep(PG 대기 흉내)이었고, 그래서 "앱 내부"로 좁힌 뒤 로그가 원인을 말해줬습니다.

**A7.** 끊기는 원인: 라벨 개편(매핑 불일치화), 로그 필드명 변경(derived fields 정규식 불일치), 데이터소스 재생성(내부 링크 참조 소실), Grafana·계측 업그레이드로 기능 플래그·exemplar 동작 변화 — 전부 에러 없이 조용히 끊깁니다(09의 uid 단절과 같은 계열). 유지 절차: 배선 체크리스트(로그의 View Trace 동작, span의 Logs 비지 않음, 그래프 ◆ 클릭)를 신규 서비스 온보딩과 라벨·필드 변경 시 필수 확인으로, 분기 게임데이(23)에서 대표 시나리오 클릭 완주를 리허설.

**A8.** 원인: ① 로그에 trace_id 부재(팀 간 규약 불일치)로 트레이스↔로그 수동 시각 매칭, ② 라벨 사전 불일치(service/app_name/service.name)로 자동 연결 불가, ③ 도구 간 링크 부재로 복사-붙여넣기 조사, ④ 각 팀이 자기 도구에 만족해 문제의식 지연 — 개별 완성도가 전체 경험의 결함을 가림. 재정의: 관측의 성숙도는 도구의 개수·개별 품질이 아니라 **신호 간 이동 시간**(조사 완주 시간)입니다 — 상관은 도구 구매가 아니라 규약(trace_id 필드·라벨 사전·시맨틱 컨벤션)에서 나오고, "클릭 완주 N분"을 게임데이로 측정하는 것이 성숙도 관리입니다.
