# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 애그리게이터를 단일 replica로 — 전 노드의 단일 장애점
집계층을 replicas 1로 두면, 그 Pod 하나가 죽는 순간 **모든 노드의 로그가 막힙니다**(노드층 버퍼가 버텨주는 동안만 유예). 노드 장애는 그 노드만 잃지만 집계층 장애는 전체를 잃습니다 — 반경이 다릅니다. replicas 2+ / PDB / 리소스 여유 / 버퍼 디스크가 집계층의 기본이고, 집계층 자신의 메트릭(버퍼 적체·재시도)도 감시 대상입니다.

### 2. match 순서 실수 — 조용한 라우팅 구멍
캐치올(`<match **>`)을 위에 두거나 패턴이 겹치면, 아래 match는 영원히 도달하지 못합니다 — **에러 없이**. "S3 아카이브가 몇 주째 비어 있었어요"의 정체. 좁은 패턴을 위에, 캐치올은 마지막에. 그리고 설정 변경 후엔 각 목적지에 실제 레코드가 도달하는지 검증(테스트 레코드·카운터 비교)을 절차화하세요 — 라우팅 누락은 조용합니다.

### 3. ack 없이 forward — 구간 유실
`Require_ack_response`(Bit) 없이 forward하면 TCP 전송 성공 = 완료로 취급되어, Fluentd가 받자마자(버퍼 기록 전) 죽으면 그 chunk는 증발합니다. 2층의 신뢰성은 구간마다의 버퍼×ack의 곱입니다 — 한 구간이라도 약하면 거기가 유실 지점(04의 "가장 약한 고리"). 감사급 로그는 ack 필수, 대량 저가치는 트레이드오프로 판단(등급별 설계).

### 4. 집계층 버퍼를 emptyDir/메모리에
Fluentd의 `<buffer>`를 메모리로 두거나 file 버퍼를 emptyDir에 두면, 집계층 재시작(배포·축출) 때 미전송분이 증발합니다 — 06의 사고(수집기 업그레이드 유실)가 집계층에서 재연됩니다. 집계층 버퍼는 PVC(또는 최소한 노드 로컬 영속)로, 그리고 업그레이드 전 버퍼 드레인(플러시 완료 후 종료 — 종료 유예시간 확보)을 절차에 넣어라.

### 5. 집계층에 가공을 몰아넣다 병목이 됨
"집계층에서 다 한다"며 무거운 정규식 수십 개·복잡한 ruby 변형·대량 재라우팅을 쌓으면, 집계층 CPU가 병목이 되어 처리량이 급락하고 노드층 버퍼가 일제히 적체됩니다. 가공의 분업 원칙: 레코드 단위의 싼 것(파싱·메타데이터)은 노드층에서 이미 끝냈고, 집계층은 정책적인 것(마스킹·라우팅)에 집중하되 **처리량을 측정**하며 넣습니다. 병목이면 replicas 확장 + 가공 간소화 — 집계층도 용량 계획의 대상입니다.

## 실무 사고 사례: "권역 센터가 막히자 온 동네가 역류했다"

한 회사가 노드 400대 규모에서 2층 구조(Bit→Fluentd 3대→OpenSearch+S3)를 운영했습니다. 어느 날 OpenSearch 클러스터가 인덱싱 지연을 일으켰습니다(디스크 워터마크 — 18의 단골). 그러자:

1. **집계층 버퍼 폭증** — Fluentd의 OpenSearch 출력 버퍼가 쌓이기 시작했습니다. copy로 S3와 묶여 있었는데, 버퍼 설정이 출력별 분리가 아니라 공유에 가깝게 잡혀 있어 **S3 배달까지 함께 느려졌습니다**(한 목적지의 장애가 copy 동료를 인질로).
2. **집계층 디스크 고갈** — file 버퍼가 total_limit 없이 자라 집계 노드의 디스크를 채웠고, Fluentd가 에러 루프에 빠졌습니다.
3. **역류 — 노드층으로** — 집계층이 받지 못하자 400대의 Bit이 일제히 재시도+fs 버퍼 적재에 들어갔습니다. 각 노드의 storage.total_limit_size에 도달한 순서대로 **드롭이 시작**됐습니다.
4. **감시 공백** — 드롭 메트릭 알림이 노드층에만 있고 집계층 버퍼 적체 알림이 없어, 발견이 "OpenSearch가 이상해요"라는 사용자 신고로부터였습니다 — 이미 역류가 한참 진행된 뒤.

복구: OpenSearch 워터마크 해소 → 집계층 버퍼 정리·재시작 → 밀린 로그 소화(몇 시간). 유실은 노드층 드롭분(등급 구분 없이 균일하게 잃음 — 아픈 부분).

재발 방지:

1. **버퍼 격리** — copy의 store별로 `<buffer>`를 분리(한 목적지 장애가 다른 목적지를 인질로 잡지 않게) + 출력별 total_limit.
2. **계단식 알림** — 집계층 버퍼 적체(1차) → 노드층 재시도 급증(2차) → 드롭(3차)의 계단 알림으로 역류를 조기에.
3. **등급별 드롭 정책** — 노드층 필터로 저가치 로그를 미리 줄이고(수문), 감사급은 별도 태그·별도 버퍼로 마지막까지 보호.
4. **목적지 건강 = 파이프라인 건강** — OpenSearch 워터마크·인덱싱 지연을 파이프라인 대시보드에 함께(끝단이 원인의 대부분).

**교훈:**
- 2층의 장애는 **역류**합니다: 목적지→집계층→노드층→드롭 — 각 단의 버퍼·한도·알림이 계단이어야 조기 발견
- copy의 출력들은 버퍼를 격리하세요 — 한 목적지의 장애가 동료를 인질로 잡습니다
- 집계층은 "정책의 단일점"인 동시에 "장애의 증폭점" — HA·디스크·감시를 노드층보다 두텁게
- 유실은 등급 없이 균일하게 오지 않게 — 가치 높은 로그의 별도 보호 경로

★ 07의 결론: 2층은 연결·정책·버퍼를 집중시켜 규모를 이기는 설계지만, 집중은 곧 증폭이기도 합니다(cncf의 "힘에는 규율" — 41·44와 같은 계열). 집계층의 HA·버퍼 격리·계단식 감시가 그 규율입니다. 다음 모듈들에서 이 로그 파이프라인의 실제 목적지(12 Loki·13 CloudWatch·18 OpenSearch)를 답니다.
