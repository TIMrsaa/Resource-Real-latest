# 학습 가이드 — 왜 한 층이 더 필요해지나

## 단층 구조의 성장통

06의 구조(노드 Fluent Bit → 목적지 직행)는 단순하고 훌륭합니다. 그런데 조직이 크면:

```
문제 1 — 연결의 폭발:
  노드 300대 × 목적지 3개(OpenSearch·S3·SaaS) = 900개 연결
  목적지 입장: 300개 클라이언트의 커넥션·인증 관리
  인증서·API 키를 노드 300대에 배포·로테이션

문제 2 — 가공의 무게:
  민감정보 마스킹(정규식 무거움), 레코드 변형, 조건 라우팅...
  노드 수집기가 무거워짐 = 모든 노드의 앱과 리소스 경쟁

문제 3 — 정책 변경의 반경:
  라우팅 규칙 하나 바꾸면 → DaemonSet 300대 롤링

문제 4 — 버퍼의 분산:
  목적지 장애 시 버퍼가 노드 300곳에 분산 — 관리·모니터링 복잡
```

## 2층 구조의 답

```
[노드층] Fluent Bit (DaemonSet) — 가볍게: 읽기·CRI 파싱·메타데이터만
    │ forward (단일 프로토콜, 단일 목적지)
    ▼
[집계층] Fluentd (Deployment ×N) — 무겁게: 마스킹·변형·라우팅·배달
    │
    ├→ OpenSearch (검색)
    ├→ S3 (아카이브)
    └→ SaaS (알림)

노드층: 목적지를 하나(애그리게이터)만 알면 됨 — 단순·가벼움 유지
집계층: 가공·정책·목적지 인증이 한곳에 — 변경 반경 축소, 확장은 replicas
```

이 분업이 "수집은 Bit(C, 경량), 집계는 D(Ruby, 플러그인 방대)"라는 두 프로젝트의 성격(cncf 14)과 정확히 맞물립니다 — Fluentd의 수백 개 출력 플러그인·복잡한 라우팅이 집계층에서 빛납니다.

## 그러나 공짜가 아닙니다 — 새 층의 비용

```
+ 노드 단순화·정책 집중·연결 축소
- 새 운영점: 애그리게이터 자체의 HA·스케일·버퍼 관리
- 새 홉: 지연 +1, 장애 지점 +1 (애그리게이터 다운 = 전 노드 영향)
- forward 구간의 신뢰성 설계 필요 (ack? 재시도? LB?)
```

**판단의 축** (theory에서 상세): 노드 수·목적지 수·가공 복잡도가 크면 2층, 작으면 Bit 단독 직행이 낫습니다. "크면 언젠가 필요하지만, 처음부터는 과함" — cncf의 반복 판단(필요한 만큼만)이 여기도 적용됩니다.

## Fluentd 설정 모델 — Bit과의 문법 차이

```
Fluent Bit: 섹션 나열 + tag/match (평면적)
Fluentd: XML풍 디렉티브 + 순차 매칭 + label로 파이프라인 격리

<source>           # 입력 (forward 수신)
<filter tag>       # 가공
<match tag>        # 출력 — ★ 위에서부터 첫 일치가 소비 (순서 중요!)
  @type copy       # 한 레코드를 여러 출력으로 (S3+OpenSearch 동시)
<label @NAME>      # 별도 파이프라인 공간 (내부 라우팅)
```

"match는 첫 일치가 소비한다"가 Bit과 가장 다른 감각입니다 — 순서 실수가 조용한 라우팅 구멍을 만듭니다(pitfalls).

## 이 모듈의 실습 동선

lab-01: Bit(수집)→Fluentd(집계) forward 연결 + ack 신뢰성 → 2층이 실제로 돕니다
lab-02: 집계층의 대표 역할 — 민감정보 마스킹(한곳에서!), copy로 S3+검색 동시 배달, 그리고 단층 vs 2층 판단 정리

06의 SIGNALS-MAP에 "로그: Bit→Fluentd→(목적지들)"로 갱신하는 것까지가 과제입니다.
