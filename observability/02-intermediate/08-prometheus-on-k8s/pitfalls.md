# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 매칭 사슬 불일치 — 조용한 미수집
ServiceMonitor를 배포했는데 안 긁힙니다: release 라벨 누락(Prometheus selector 불일치), Service 라벨 오타, 포트 "이름" 불일치(번호를 쓰거나 이름 없는 포트). 셋 다 **에러 없이 조용히** 실패합니다(lab-01에서 체험). 점검 순서를 외우고, `absent(up{job=...})` 알림으로 "조용한 미수집"을 시끄럽게 만들어라. 신규 서비스 온보딩 체크리스트에 "타깃 등록 확인"을 넣는 것이 정석.

### 2. KSM과 cAdvisor를 혼동
"Pod 메모리 사용량"을 KSM에서 찾거나(없습니다 — KSM은 상태·개수), "Pending Pod 수"를 cAdvisor에서 찾습니다(없습니다 — cAdvisor는 사용량). 소스의 관점을 혼동하면 "메트릭이 없다"고 오판하거나 엉뚱한 지표로 알림을 만듭니다. 3대장 구분(기계=node-exporter, 오브젝트 상태=KSM, 컨테이너 사용량=cAdvisor)은 어휘입니다 — 대시보드·알림 작성 전에 항상 "이 질문은 누구의 관점인가"를 묻습니다.

### 3. Prometheus 자신의 리소스를 방치
Prometheus는 시계열 수에 비례해 메모리를 먹습니다(cncf 11). requests/limits를 대충 잡으면 클러스터가 크면서 OOMKilled → WAL replay → 또 OOM의 루프(03 사고)에 빠집니다. prometheus_tsdb_head_series를 상시 감시하고, 성장 추세에 맞춰 리소스를 계획하며, sample_limit·수문(relabeling)으로 유입을 통제하세요. 관측의 심장 자체가 관측·용량 계획의 대상입니다.

### 4. 보존(retention)을 늘려 장기 저장을 해결하려 함
"1년치 보고 싶다"고 retention=365d로 잡으면 로컬 디스크·블록 관리가 감당 못 합니다 — 단일 Prometheus는 장기·대규모 저장용이 아닙니다(cncf 11의 벽). 장기는 원격 쓰기(remote_write)로 AMP(14)나 Thanos/Mimir(24)에 위임하고, 로컬은 며칠~몇 주의 "뜨거운" 조회용으로. 아키텍처의 역할 분담이지 설정값의 문제가 아닙니다.

### 5. scrape interval을 제각각·과도하게
"실시간이 좋으니" 1s 간격, 팀마다 제각각 간격을 쓰면 — 부하·저장이 배수로 늘고, rate() 창과 간격의 관계(창은 간격의 4배 이상 권장)가 꼬여 그래프가 끊기거나 왜곡됩니다. 표준 간격(15s/30s)을 정하고 예외는 심사로. interval은 "신선도"가 아니라 부하·비용·쿼리 정합의 파라미터입니다.

## 실무 사고 사례: "알림이 안 울린 이유 — 지표는 있었지만 정의가 달랐다"

한 조직에서 결제 서비스 장애가 났습니다. 에러율이 30%까지 치솟았지만 **알림은 침묵**했습니다. 사후 조사에서 드러난 것:

1. **팀마다 다른 에러율 정의** — 대시보드 A는 `5xx/(전체)`, 알림 규칙은 `5xx/(2xx+5xx)`(3xx·4xx 제외), 다른 대시보드는 특정 path 제외. 장애 유형이 4xx 급증+5xx 소폭이라, 알림의 정의로는 임계 미달이었습니다.
2. **쿼리 복붙의 진화** — 초기 누군가의 쿼리가 복붙되며 각자 "개선"되어 갈라졌습니다. 어떤 것은 rate 창이 1m(민감·불안정), 어떤 것은 15m(둔감).
3. **인스턴스 라벨 함정** — 한 알림은 `sum` 없이 인스턴스별 에러율에 걸려 있었는데, 배포로 Pod가 교체되며 시계열이 리셋되어 평가가 불안정했습니다.
4. **아무도 몰랐습니다** — 정의가 갈라진 것을 장애 전까지 아무도 몰랐습니다. "에러율"이라는 같은 단어가 네 가지 다른 수식이었습니다.

조치가 recording rule 중심의 재편이었습니다:

1. **정의의 단일화** — `service:http_error_ratio:rate5m` 등 표준 SLI를 recording rule로 하나만 정의(PrometheusRule, GitOps 관리). 대시보드·알림은 **이 시계열만** 소비.
2. **명명 관례 강제** — level:metric:operations 관례와 리뷰(cicd의 코드 리뷰처럼 rule PR 리뷰).
3. **정의 문서화** — 각 rule에 주석으로 "분모·분자에 무엇이 포함되나"를 명시(4xx 포함 여부 같은 결정을 명문화).
4. **알림은 반드시 집계 위에** — 인스턴스별이 아니라 서비스 수준 집계(sum by service)에 걸기(Pod 교체에 흔들리지 않게).

**교훈:**
- 같은 이름의 지표가 팀마다 다른 수식이면, 장애의 날 **알림과 대시보드가 서로 다른 세계**를 봅니다
- recording rule의 진짜 가치는 성능보다 **정의의 단일화** — "우리 조직의 에러율은 이것"
- 쿼리 복붙은 정의의 분기 — 소비는 rule 시계열로, 원시 쿼리는 rule 안에만
- 알림은 집계 수준에 — 인스턴스 시계열은 배포마다 리셋됩니다

★ 08의 결론: Prometheus 운영의 본체는 서버 유지가 아니라 **체계의 유지**입니다 — 등록(ServiceMonitor 셀프서비스), 수문(relabeling·limit), 정의(recording rule 단일화). 이 체계가 09(대시보드)·10(알림)·21(SLO)이 서는 땅이고, 14(AMP)에서 "저장만 관리형으로 바꿔도 체계는 그대로"임을 보게 됩니다.
