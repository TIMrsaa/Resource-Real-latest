# 학습 가이드 — 계측의 마찰을 줄이는 기술

## 04의 숙제 — "전 서비스의 협조"라는 벽

04의 결론: 트레이스의 가치는 가장 약한 고리가 정하고, 도입의 벽은 기술이 아니라 조직(모든 팀이 SDK를 붙여야)이었습니다. 이 모듈은 그 벽을 낮추는 세 기술을 다룹니다:

```
① 자동 계측: 프레임워크 훅에 끼어들어 코드 수정 없이 span 생성
② Operator 주입: K8s 어노테이션 하나로 자동 계측을 Pod에 심기
   → 앱 팀의 작업이 "SDK 통합"에서 "어노테이션 한 줄"로
③ Collector: 앱은 가까운 곳에 던지기만 — 백엔드 지식은 Collector가
```

## 자동 vs 수동 — 무엇을 공짜로 얻고 무엇은 직접 해야 하나

```
자동 계측이 주는 것 (언어 런타임에 따라):
  HTTP 서버/클라이언트 span (요청 수신·발신)
  DB 드라이버 span (쿼리 — 어떤 쿼리가 느린가)
  메시징 클라이언트 (전파 포함 — 04의 큐 끊김 해결!)
  → "서비스 경계"는 거의 공짜

수동 계측이 필요한 것:
  비즈니스 로직 내부 단계 (예: "재고 계산" 구간)
  커스텀 속성 (주문 금액대·테넌트 등급 — 조사에 쓸 차원)
  비표준 라이브러리·자체 프로토콜

전략: 자동으로 80%(경계) + 핵심 경로만 수동 보강 20%
언어별 온도차: Java/Python(런타임 주입 강력) > Node > Go(컴파일 언어라
  라이브러리 통합 방식 — 주입 마법이 제한적)
```

## Operator 주입 — 어노테이션 한 줄의 마법과 그 실체

```
Instrumentation CRD를 만들어 두면:
  Pod에 annotation: instrumentation.opentelemetry.io/inject-java: "true"
  → Operator의 웹훅이 Pod 생성 시:
     init 컨테이너로 에이전트 jar 주입 + JAVA_TOOL_OPTIONS 환경변수
  → 앱 이미지는 그대로, 재배포만으로 트레이스가 태어남

실체를 알아야 하는 이유: "마법"은 admission webhook + 환경변수입니다
  → 문제가 생기면(주입이 안 됨) 웹훅·라벨·언어별 한계를 봐야 (pitfalls)
```

## Collector — 앱과 백엔드 사이의 완충재

```
앱이 백엔드(Jaeger·Tempo·X-Ray)로 직접 보내면:
  백엔드 교체 = 전 앱 설정 변경, 인증·재시도·배치를 앱마다
Collector를 사이에:
  앱 → (OTLP, 가까운 Collector) → [가공·샘플링·배치] → 백엔드(들)
  → 06·07의 로그 파이프라인과 같은 사상! (receiver=INPUT,
    processor=FILTER, exporter=OUTPUT)
  → 그리고 Collector는 로그·메트릭도 받습니다 — 신호 3종의 단일 파이프라인
    (07에서 예고한 "OTel gateway로 통일" 흐름의 실체)
```

## 배포 3패턴 — 미리 보는 판단

```
sidecar: Pod마다 — 격리 좋음, 리소스 무거움 (특수 케이스)
DaemonSet(agent): 노드마다 — 앱은 localhost로 던짐, k8s 메타 부착에 유리
gateway: 중앙 Deployment — tail 샘플링·백엔드 연결 집중 (07의 애그리게이터와 동형!)
실전 조합: agent(수집) → gateway(정책) — 로그의 2층(06→07)과 같은 그림
```

같은 구조가 신호마다 반복된다는 것 — 이것이 Part 5 중반의 큰 그림입니다: **수집기의 사상은 하나입니다**(가까이서 받고, 가공하고, 중앙에서 정책).
