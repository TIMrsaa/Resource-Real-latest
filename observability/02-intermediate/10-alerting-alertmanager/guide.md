# 학습 가이드 — 알림은 빚입니다

## 알림의 경제학

알림 하나를 만들 때마다 조직은 빚을 집니다:

```
알림 1개 = 미래의 인터럽트 N회
  진짜 문제의 알림: 빚이 아니라 투자 (조기 대응)
  거짓·무의미 알림: 이자만 나가는 빚 (수면·집중·신뢰를 지불)

알림 피로의 악순환:
  소음 알림 → 무시가 습관 → 진짜 알림도 무시 → 대형 장애
  → "늑대야!" 소년의 시스템 버전
  → 침묵(놓침)보다 소음이 더 위험한 이유: 소음은 진짜를 가립니다
```

이 모듈의 관점: 알림 작성은 기능 추가가 아니라 **부채 심사**입니다. "울릴 자격"의 기준을 먼저 세웁니다.

## 울릴 자격 — 세 가지 심사 기준

```
① 증상 기반인가 (사용자가 아픈가)
  O: 에러율 5% 초과, p99가 SLO의 2배 (사용자 영향)
  X: CPU 80% (그래서 사용자가 아픈가? 아닐 수 있습니다 — 09의 USE는
     조사용이지 페이지용이 아닌 경우가 많습니다)
  원인 기반 알림의 문제: 원인 후보는 수백 개 — 다 걸면 폭풍
  증상은 소수 — 걸 곳이 명확 (RED가 알림의 원천인 이유)

② 행동 가능한가 (받은 사람이 뭘 할 수 있나)
  O: runbook 링크 + 대시보드 착지(09) — 다음 행동이 있습니다
  X: "노드 어딘가의 inode가 …" 받아도 할 게 없으면 소음

③ 긴급한가 (지금 사람을 깨울 일인가)
  page(즉시): 사용자 영향 진행 중 — 새벽에 깨울 자격
  ticket(업무시간): 곧 문제 될 것 (디스크 3일 내 고갈) — 아침에
  → 긴급하지 않은 것을 page로 보내는 것이 피로의 최대 원인
```

## for — 순간과 지속의 구분

```
expr: error_ratio > 0.05
  순간 스파이크(배포 직후 10초)에도 발화 → 소음

for: 5m — 조건이 5분 지속되어야 발화
  → 일시 요동을 거르고 "진짜 진행 중"만
  트레이드오프: 발견이 5분 늦음 — 심각도별로 for를 조절
  (page는 짧게+높은 임계, ticket은 길게+낮은 임계)
```

## Alertmanager — 발화 이후의 여정

Prometheus가 "발화"를 결정하면, Alertmanager가 "전달"을 담당합니다:

```
발화된 알림들 → [라우팅 트리] 팀·심각도별 분기
             → [그룹핑] 같은 사건의 알림 묶음 (Pod 50개 다운 = 1통)
             → [억제] critical이 울리면 관련 warning은 침묵
             → [사일런스] 계획 작업 중 임시 소거
             → 수신자 (PagerDuty·Slack·웹훅)
```

이 네 장치가 "알림 100개 발화 = 전화 1통"을 만듭니다 — 장애의 순간 온콜을 보호하는 설계입니다.

## 이 모듈이 놓는 다리

- 08의 recording rule(단일 정의) 위에 알림 → 대시보드와 같은 세계를 봄
- 09의 대시보드 = 알림의 착지점 (annotation에 링크)
- 21의 SLO 번레이트 = 이 모듈 규율의 고급판 (임계·for의 다중 창 조합)
- 23의 온콜 = 이 알림을 받는 사람의 운영 설계
