## 정답

**A1.** 로그 원천이 **노드의 파일**(/var/log/pods)이기 때문입니다 — 파일이 있는 곳마다 읽는 자가 있어야 하므로 노드마다 하나(DaemonSet)가 자연스럽고, 노드 수에 따라 수집 능력이 자동으로 수평 확장됩니다. 사이드카(Pod마다 수집기)는 Pod 수만큼 무거워 파일 쓰는 레거시 예외용(02)이고, 중앙 단일 수집기는 원격 노드의 파일을 읽을 수 없어 성립 불가입니다. DaemonSet + hostPath /var/log가 K8s 로그 수집의 표준형입니다.

**A2.** 구성: [SERVICE](전역 — flush·메트릭 서버·storage), [INPUT](소스 — tail 등, 레코드에 tag 부여), [PARSER/multiline](해석), [FILTER](가공 — match로 선택), [OUTPUT](배달 — match로 선택). tag는 레코드의 주소(tail은 파일 경로에서 유래 — 네임스페이스·Pod명이 포함됨), match는 라우팅 규칙입니다 — 같은 레코드 흐름이 tag에 따라 다른 필터·다른 목적지로 분기됩니다(prod→장기 보존, dev→단기, 감사→S3 같은 정책 분기가 이걸로).

**A3.** 층1 — CRI 벗기기(multiline.parser cri): containerd가 붙인 시각·스트림·플래그 접두어를 분리하고 P/F 조각을 재조립합니다(안 하면 접두어가 본문에 섞이고 긴 JSON이 조각남 — 02의 CRI 포맷). 층2 — JSON 승격(kubernetes 필터 Merge_Log On): 앱이 쓴 JSON을 최상위 필드로 승격합니다(level·event·user_id가 쿼리 가능한 필드로 — 02의 구조화가 여기서 보상받음, 비JSON 레거시는 정규식 파서 유지보수 지옥). 층3 — 앱 멀티라인: Java 스택트레이스처럼 여러 줄인 한 사건을 정규식(시작줄 패턴)으로 한 레코드로 합침.

**A4.** 하는 일: tag에서 Pod·네임스페이스를 추출하고 kubelet/API에서 Pod 정보를 조회해 kubernetes.* 필드(namespace·pod명·라벨·컨테이너)를 레코드에 부착합니다 — "어느 앱의 로그인가"가 데이터가 되어 저장소에서 {namespace, app} 필터가 가능해집니다. 주의점: ① API 서버 부하 — 대규모(노드 수백)에서 조회가 API 서버를 때리므로 Use_Kubelet On으로 로컬 kubelet 조회로 분산, ② 레코드 비대 — 라벨·어노테이션 전부를 붙이면 전송·저장 비용이 커지므로 필요한 것만 선별(Labels/Annotations 설정).

**A5.** mem 버퍼: 빠르고 단순하지만 한도(Mem_Buf_Limit) 도달 시 신규 수용 불가(pause/드롭)이고 재시작 시 미전송분이 증발합니다. filesystem 버퍼: 디스크에 chunk를 저장해 목적지 장애를 훨씬 크게 완충하고 재시작에도 생존하지만, 노드 디스크를 쓰므로 한도(storage.total_limit_size)가 필수입니다. 프로덕션 표준은 filesystem — K8s에서 수집기 재시작(업그레이드·노드 교체)은 일상이고, 목적지 장애도 언젠가 반드시 오기 때문입니다(lab-02에서 같은 장애에 mem은 드롭 3200, fs는 드롭 0).

**A6.** 유리한 조건: 소스가 **파일**이라는 점 — 버퍼가 차서 tail을 pause해도 로그는 노드 파일에 계속 쌓이므로, 재개 후 이어 읽으면 됩니다(스트림 소스라면 pause = 즉시 유실). 한계: pause 동안에도 로테이션(10Mi×5)은 돌아갑니다 — 대량 로그 앱이면 pause 중 파일이 회전·삭제되어 읽지 못한 구간이 영구 유실됩니다(02의 물리와의 경주). 따라서 백프레셔는 "짧은 적체"의 방어이고, 장기 적체는 fs 버퍼 용량과 폭주 통제(앱 rate-limit·필터)로 다뤄야 합니다.

**A7.** 현실적 목표: "**보이는 유실, 버티는 버퍼, 의도된 포기**" — 유실이 발생하면 즉시 알고(메트릭+알림), 일시 장애는 버퍼로 흡수하고(fs+한도), 영구 실패는 정책적으로 포기(Retry_Limit)하되 그 사실을 기록합니다. 메트릭 네 가지: fluentbit_input_records_total(읽은 양), fluentbit_output_proc_records_total(보낸 양 — input과의 격차로 적체 감지), fluentbit_output_retries_total/retries_failed_total(목적지 불안·재시도 소진), fluentbit_output_dropped_records_total(유실 발생 — 알림 1순위). 여기에 storage(fs chunk 수)로 적체를 봅니다.

**A8.** 원인: ① mem 버퍼 — 업그레이드 재시작 순간 미전송 chunk 증발, ② tail DB를 emptyDir에 둠 — 오프셋 기억이 사라져 새 수집기가 파일 끝부터 읽어 공백 발생, ③ 트래픽 피크로 로테이션이 빨라 건너뛴 구간이 원본째 소멸(복구 불능 확정), ④ 드롭·볼륨 메트릭 무감시로 일주일간 유실을 모름. 조치: fs 버퍼+hostPath 영속(storage.path·DB 모두), 업그레이드 절차에 카나리 노드+전후 카운터 연속성 검증, dropped/retries_failed/볼륨 급감 알림 상설화, 로그 등급 정의(감사 대상은 유실 허용 ~0으로 설계 강화, 일반은 현실적 목표 — 등급별 설계). 교훈: 재시작은 일상이므로 재시작 생존이 기본값이어야 하고, 유실은 조용하므로 메트릭만이 조기 경보입니다.
