# 학습 가이드 — 수집기의 네 가지 일

## 위치 확인 — 우리는 지금 어디를 짓나

```
[앱 stdout] → [containerd] → [/var/log/pods/*.log]  ← 02에서 완성
                                    │
                                    ▼
                          [Fluent Bit (이 모듈)]      ← DaemonSet, 노드마다
                                    │
                                    ▼
                    [목적지: Loki(12)·CloudWatch(13)·OpenSearch(18)·S3...]
```

Fluent Bit이 하는 일은 네 가지로 요약됩니다:

```
① 읽기(INPUT): 노드 파일을 tail (어디까지 읽었는지 DB로 기억)
② 해석(PARSER): CRI 포맷 벗기기 → 앱 JSON 파싱 (02의 두 층!)
③ 가공(FILTER): k8s 메타데이터 부착, 소음 제거, 변형
④ 배달(OUTPUT): 목적지로 전송 — 실패하면? (버퍼·재시도의 세계)
```

## 왜 Fluent Bit인가 (Fluentd와의 관계 예고)

```
Fluent Bit: C로 짠 경량 수집기 — 노드마다 놓기에 적합 (메모리 수십 MB)
Fluentd: Ruby 기반, 플러그인 방대 — 중앙 애그리게이터에 적합
→ 07에서 "수집은 Bit, 집계는 D" 2층 패턴을 다룹니다
→ 이 모듈은 노드 수집기로서의 Bit에 집중
```

cncf 14에서 이 둘의 내부(버퍼 구조·백프레셔의 물리)를 팠습니다. 여기서는 그 지식을 **설정 언어로 번역**합니다 — "버퍼가 차면 어떻게 되나"를 알았으니, 이제 `storage.type filesystem`이 왜 필요한지 압니다.

## 파이프라인 문법 — tag와 match

Fluent Bit 설정의 뼈대는 **tag 기반 라우팅**입니다:

```
[INPUT]  → 읽은 레코드에 tag를 붙입니다 (kube.var.log.pods.default_web...)
[FILTER] → match로 태그를 골라 가공 (match kube.*)
[OUTPUT] → match로 태그를 골라 배달 (kube.* → loki, host.* → s3)

같은 레코드가 태그에 따라 다른 여정을 — 라우팅 테이블과 같습니다
```

이 문법을 잡으면 설정 파일이 "주문"이 아니라 "지도"로 읽힙니다.

## 이 모듈의 운영 핵심 — 유실은 설정으로 막습니다

02·cncf 14에서 유실의 물리를 배웠습니다:

```
유실 지점 1: tail이 로테이션을 못 따라감 (읽기 속도 < 쓰기 속도)
유실 지점 2: 목적지 장애 시 버퍼 초과 (mem 버퍼가 차면 드롭)
유실 지점 3: Fluent Bit 재시작 (mem 버퍼는 휘발)

방어 설정:
  filesystem 버퍼 (재시작·목적지 장애에도 보존)
  버퍼 한도 + 백프레셔 (pause tail — 소스가 파일이라 가능한 전략!)
  재시도 정책 (Retry_Limit)
  DB 파일 (읽던 위치 기억 — 재시작 시 이어서)
```

lab-02에서 목적지를 일부러 죽여 이 시나리오들을 재현합니다 — "설정 항목 암기"가 아니라 "장애 시나리오 → 설정"의 대응으로 익힙니다.

## 필터링 = 비용의 첫 수문

01부터 강조한 "관측=비용"의 첫 통제 지점이 여기입니다:

```
모든 로그가 중앙으로 갈 필요는 없습니다:
  헬스체크 로그 (GET /healthz 200 — 초당 수십 건의 무의미)
  debug 레벨 (프로덕션에선 대부분 불필요)
  특정 시끄러운 네임스페이스
→ Fluent Bit filter(grep·lua)로 소스에서 거르면
  전송·저장·인덱싱 비용이 전부 절약 (22의 첫 실천)
```

## SIGNALS-MAP 갱신 예고

이 모듈을 마치면 05의 지도에서 "로그: 수집 ❌"가 "✅ Fluent Bit → (목적지)"로 바뀝니다 — 첫 파이프라인 완공입니다.
