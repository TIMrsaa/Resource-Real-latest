# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. CRI 파서 없이 tail — 접두어가 본문에 섞임
`multiline.parser cri` 없이 수집하면 모든 레코드가 "2026-...Z stdout F {json}" 통째로 들어갑니다 — 시각·스트림이 본문에 섞여 JSON 파싱이 깨지고, P/F 조각도 재조립되지 않아 긴 로그가 깨진 조각으로 저장됩니다(02). "저장소에서 JSON 필드 검색이 안 돼요"의 단골 원인. containerd/CRI-O 환경에서 cri 파서는 기본값처럼 취급하세요.

### 2. mem 버퍼로 프로덕션 운영 — 조용한 유실
기본(memory) 버퍼로 두면 목적지 장애·재시작 때마다 미전송분이 드롭/증발합니다(lab-02 시나리오 A). 더 나쁜 것은 **아무 소리 없이** 사라진다는 것 — dropped 메트릭을 안 보면 몇 달간 유실을 모른 채 "로그가 가끔 비네?"로 삽니다. filesystem 버퍼 + total_limit_size + dropped/retries_failed 알림이 프로덕션 최소선입니다.

### 3. kubernetes 필터의 API 부하를 무시
kubernetes 필터가 Pod 메타데이터를 API 서버에서 조회하는데, 대규모(노드 수백)에서 기본 설정이면 API 서버에 무시 못 할 부하가 됩니다(캐시 미스·재시작 폭풍 시). `Use_Kubelet On`(로컬 kubelet에서 조회)으로 API 서버 부하를 노드로 분산하세요. 또한 라벨·어노테이션 전부를 붙이면 레코드가 비대해집니다(전송·저장 비용) — 필요한 것만 선별.

### 4. 필터 순서·match 실수 — 파이프라인의 조용한 구멍
FILTER는 선언 순서대로 적용됩니다. grep(제거)을 kubernetes 필터보다 먼저 두면 메타데이터 기반 매칭이 안 되고, match 패턴 오타(kube.* vs kube_*)면 필터가 그냥 건너뜁니다 — 에러 없이 **조용히** 의도와 다르게 흐릅니다. 변경 후엔 반드시 출력 샘플로 검증(lab-01 2절의 방식) — "설정이 적용됐다"와 "의도대로 동작한다"는 다릅니다.

### 5. 과잉 필터링 — 아낀 돈보다 비싼 조사 불능
비용 절감에 심취해 warn 이하 전부 제거, 성공 요청 전부 제거 같은 공격적 필터를 걸면, 장애 조사에서 "그 시점 정상 요청의 모습"(비교 기준)이 없어 원인 분석이 불가능해집니다(01의 함정 5와 동일 계열). 필터 대상은 "답할 질문이 확실히 없는 것"(헬스체크·알려진 소음)에 한정하고, 판단이 서지 않으면 **짧은 보존으로 남기는** 절충(저장 계층화, 18·22)을 택하세요.

## 실무 사고 사례: "수집기 업그레이드가 이틀치 로그를 지웠다"

한 팀이 Fluent Bit 버전 업그레이드를 했습니다. helm upgrade 한 번 — 롤링으로 각 노드의 수집기가 재시작됐고, 별 문제 없이 끝난 듯 보였습니다. **일주일 뒤** 보안팀이 특정 기간의 접근 로그를 요청했을 때에야 발견됐습니다: 업그레이드 시점 전후로 **이틀치 로그에 큰 구멍**이 나 있었습니다.

무슨 일이 있었나:

1. **mem 버퍼의 증발** — 당시 설정이 memory 버퍼였습니다. 업그레이드 재시작 순간, 각 노드에서 미전송 chunk들이 그대로 증발했습니다(lab-02 시나리오 C의 나쁜 쪽).
2. **DB 파일 유실** — tail DB를 emptyDir에 두고 있었습니다(hostPath가 아니라). 재시작으로 오프셋 기억이 사라지자, 새 수집기는 `Read_from_Head false` 기본값대로 **파일 끝부터** 읽기 시작 — 재시작 직전~직후 사이에 쌓인 로그를 건너뛰었습니다.
3. **하필 그날 트래픽 피크** — 대량 로그로 로테이션이 빨랐고, 건너뛴 구간이 회전으로 삭제되며 복구 불능이 확정됐습니다.
4. **드롭 메트릭 무감시** — dropped·input/output 격차 메트릭을 아무도 안 보고 있어, 유실이 일주일간 조용했습니다.

복구는 불가능했습니다(원본이 로테이션으로 소멸). 사후 조치:

1. **fs 버퍼 + hostPath 영속** — storage.type filesystem, storage.path와 tail DB를 hostPath로(재시작·업그레이드 생존).
2. **업그레이드 절차에 검증 추가** — 업그레이드 전후 input/output 카운터 연속성 확인, 카나리 노드 1대 먼저.
3. **유실 감시 상설화** — dropped_records·retries_failed 알림 + "수집량이 평소 대비 급감" 알림(볼륨 이상 감지).
4. **로그 유실의 등급 정의** — 감사 대상 네임스페이스(보안·결제)는 유실 허용 0에 가깝게(fs 한도 상향·이중화), 일반은 현실적 목표 — 등급별 설계(22).

**교훈:**
- 수집기 재시작은 일상(업그레이드·노드 교체)입니다 — **재시작 생존을 기본값으로** 설계하세요 (fs 버퍼+hostPath DB)
- 유실은 조용합니다 — 발견 시점이 "필요한 순간"(감사·조사)이면 이미 늦습니다. 드롭·볼륨 메트릭 알림이 유일한 조기 경보
- 업그레이드는 파이프라인의 장애 시나리오입니다 — 카나리와 전후 검증을 절차에
- 로그의 가치는 균일하지 않습니다 — 등급별(감사 vs 일반) 유실 허용치와 설계를 달리

★ 06의 결론: 수집기는 "설치하면 끝"인 부품이 아니라, 유실의 물리(02·cncf 14) 위에서 버퍼·영속·감시로 싸우는 시스템입니다. lab-02의 시나리오들(다운·재시작·폭주)은 언젠가 반드시 일어납니다 — 그날 유실이 "보이고 버텨지는가"는 오늘의 설정이 정합니다.
