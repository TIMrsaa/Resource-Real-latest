# 학습 가이드 — 보여줄 것을 고르는 기술

## 대시보드의 실패 방정식

```
흔한 실패: 만들 수 있는 그래프를 다 만듭니다
  → 40개 패널의 벽 → 장애 때 어디를 볼지 모름 → 안 씀 → 낡음
  (01 함정 3 "대시보드 수집가")

성공의 조건: 각 대시보드에 "누가, 어떤 질문으로 오는가"가 있습니다
  온콜: "지금 서비스가 아픈가? 어디부터 보나요?" → 개요 대시보드
  조사자: "payment가 왜 느리지?" → 서비스 대시보드 → Pod 드릴다운
  용량 계획: "다음 분기 리소스는?" → 추세 대시보드
```

방법론(USE·RED)은 이 "질문"을 표준화해 줍니다 — 뭘 넣을지 고민을 절반으로 줄이는 틀.

## RED — 서비스를 보는 세 숫자

```
Rate     초당 요청 수      — 트래픽이 정상 범위인가
Errors   에러율(비율!)     — 실패가 늘었나
Duration 지연 분위수(p99)  — 느려졌나

→ 요청을 처리하는 모든 것(API·워커)에 적용
→ 08의 recording rules(service:*)가 정확히 이 세 개였습니다 — 우연이 아님
→ 21의 SLI도 대부분 RED에서 나옵니다
```

## USE — 리소스를 보는 세 숫자

```
Utilization  사용률 (CPU 몇 %)
Saturation   포화도 (큐·스로틀링·스왑 — 한계에 눌리는 정도)
Errors       에러 (하드웨어·OOM)

→ 리소스(노드·디스크·네트워크)에 적용
→ node-exporter·cAdvisor(08의 3대장)가 재료
→ 주의: 사용률 100%보다 포화(스로틀·큐)가 진짜 신호일 때가 많습니다
```

**두 방법론의 관계** — RED는 "사용자가 아픈가"(증상), USE는 "자원이 눌리는가"(원인 후보). 조사 동선: RED에서 이상 감지 → USE로 원인 탐색(또는 트레이스로). 대시보드 계층도 이 순서를 따릅니다.

## 변수 — 대시보드 증식을 막는 장치

```
나쁜 패턴: payment 대시보드, order 대시보드, user 대시보드... (복붙 증식)
  → 하나 고치면 열 개 고쳐야 (구조화 로깅 이전의 로그와 같은 문제)

변수: $namespace, $service를 쿼리에 —
  sum(rate(http_requests_total{namespace="$namespace"}[5m]))
  → 대시보드 하나가 모든 서비스를 커버 (드롭다운 선택)
  → label_values()로 변수 목록을 메트릭에서 자동 추출
```

## 드릴다운 — 동선을 화면에 심습니다

```
계층 설계:
  L1 개요: 전 서비스 RED 히트맵/목록 — "어디가 아픈가"
   ↓ 클릭(링크 + 변수 전달)
  L2 서비스: $service의 RED 상세 + 배포 마커 — "언제부터, 어떤 패턴"
   ↓ 클릭
  L3 인스턴스/Pod: USE + 재시작 — "어느 Pod가, 자원 문제인가"
   → 여기서 로그·트레이스 링크로 점프 (12의 상관)

→ 23(장애 대응)의 "알림 → L1 → L2 → L3 → 로그" 동선이 이 위에
```

## 코드로 — 클릭 대시보드의 운명

```
UI에서 클릭으로 만든 대시보드:
  누가 언제 왜 바꿨는지 모름 → 실수로 삭제 → 복구 불가
  환경(스테이징/프로덕션) 간 불일치

as code:
  JSON을 Git에 → ConfigMap → sidecar가 자동 로드 (프로비저닝)
  리뷰(PR)·이력·복구·환경 일관성 — cncf 14(GitOps)의 대시보드판
```

## 이 모듈의 관점

대시보드는 UI 작업이 아니라 **정보 설계**입니다: 질문 정의(누가 오나) → 방법론(RED/USE)으로 지표 선정 → 계층·링크로 동선 → 코드로 유지. lab에서 이 순서 그대로 만듭니다.
