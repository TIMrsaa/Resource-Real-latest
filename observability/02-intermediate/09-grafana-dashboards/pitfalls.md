# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 그래프 벽 — 패널 수가 실력이라는 착각
만들 수 있는 그래프를 다 만들어 40패널 대시보드를 완성하고 뿌듯해합니다. 장애의 순간, 온콜은 어디를 봐야 할지 몰라 결국 kubectl로 돌아갑니다. 대시보드의 단위는 패널이 아니라 **질문**입니다 — L1(어디가 아픈가)·L2(언제부터 어떤 패턴)·L3(어느 Pod, 자원인가)의 계층으로 나누고, 각 패널에 "이건 무슨 질문의 답"이 답변 가능해야 합니다. 답 못 하는 패널은 지웁니다.

### 2. 평균 지연 패널 — 03의 함정이 화면에 박제됨
`avg(duration)` 패널은 p99 5초를 100ms로 보여줍니다(01의 사고). 히스토그램이 있는데도 평균을 그리는 것은 정보를 버리는 것 — 지연은 p50/p95/p99 세 선이 표준입니다. 마찬가지로 에러는 개수가 아니라 **비율**(트래픽이 늘면 개수도 늡니다 — 비율만이 악화를 말합니다), counter는 rate로. 03의 규율이 화면 규율로 이어집니다.

### 3. uid·링크 방치 — 조용히 끊기는 동선
대시보드를 복사·재생성하며 uid가 바뀌면, L1→L2 드릴다운 링크와 알림의 착지 링크(10)가 **조용히** 404가 됩니다. 장애의 날 온콜이 알림을 클릭했는데 "Dashboard not found" — 동선이 거기서 끊깁니다. uid를 명시·고정하고(Git의 JSON에), 링크 무결성을 주기 점검(또는 대시보드 린트)하세요. 조용한 실패(08의 매칭 사슬)와 같은 계열입니다.

### 4. 무한 시계열 패널 — 브라우저와 Prometheus를 함께 죽임
`sum by (pod)` 없이 인스턴스·컨테이너 라벨 전체를 그리면 수백 선이 렌더링되고, 변수 All + 짧은 갱신 주기까지 겹치면 대시보드를 여는 것 자체가 Prometheus에 무거운 쿼리 폭탄이 됩니다("대시보드 열면 느려져요"). 집계 기본 + 필요시 topk(5, ...)로 이상치만, 갱신은 30s~1m, 무거운 정의는 recording rule(08)로 — 대시보드도 쿼리 비용의 소비자입니다.

### 5. 남의 대시보드를 그대로 — 우리 질문이 없는 화면
grafana.com 커뮤니티 대시보드를 수십 개 임포트하고 "관측 구축 완료"라 합니다. 좋은 출발점이지만 그것은 **남의 질문의 답**입니다 — 우리 서비스의 SLI·우리 장애 패턴·우리 동선이 없습니다. 커뮤니티 대시보드는 재료로 쓰되, L1/L2 동선과 서비스 RED는 우리 질문으로 직접 설계하세요(그리고 as code로 소유).

## 실무 사고 사례: "대시보드는 있었습니다. 다만 아무도 그 앞에 있지 않았다"

한 팀이 야심 차게 관측을 구축했습니다 — 대시보드 60여 장, 팀·컴포넌트별로 빠짐없이. 몇 달 뒤 대형 장애가 났고, 사후 리뷰에서 뼈아픈 사실들이 나왔습니다.

1. **온콜의 첫 행동은 kubectl이었습니다** — "어느 대시보드부터 봐야 할지 몰라서요." 60장 중 "장애의 첫 화면"으로 설계된 것이 없었습니다 — 전부 L2·L3급 상세였고 L1(전 서비스 개요)이 없었습니다.
2. **알림과 대시보드가 안 이어졌습니다** — 알림 메시지에 대시보드 링크가 없거나, 있어도 uid 변경으로 끊겨 있었습니다. 온콜은 알림을 보고 **검색**으로 대시보드를 찾아 헤맸습니다.
3. **찾은 대시보드는 낡아 있었습니다** — 서비스 개편 전의 라벨 기준이라 절반이 No data. 클릭으로 만든 뒤 관리가 안 됐고(as code 아님), 만든 사람은 퇴사했습니다.
4. **정작 조사는 CLI로 끝났습니다** — 그날 실제 원인 규명은 한 시니어의 kubectl+PromQL 수작업이었습니다. 60장의 대시보드는 장애 대응 시간에 0분 기여했습니다.

재편은 "장식에서 도구로"였습니다:

1. **동선 기준 재설계** — L1 하나(전 서비스 RED + 클러스터 포화, 온콜의 첫 화면 공식화) → L2 서비스(변수) → L3 Pod. 60장을 동선에 편입되는 것만 남기고 아카이브(과감한 삭제).
2. **알림→대시보드 계약** — 모든 알림에 착지 링크(uid 고정) 의무화(10에서 구현). "알림 클릭 = L1/L2 도착"을 보장.
3. **as code 전환** — 남긴 대시보드 전부 Git+CM 프로비저닝. 라벨 개편 시 PR로 함께 수정(낡음 방지).
4. **게임데이 검증** — 분기마다 모의 장애에서 "대시보드만으로 원인 후보까지 가는지"를 리허설(23) — 못 가면 동선 수정.

**교훈:**
- 대시보드의 성공 지표는 개수가 아니라 **장애 때 실제 사용 시간**입니다
- 온콜의 첫 화면(L1)을 공식화하세요 — "어디부터 보나"가 정해져 있어야 동선이 시작됩니다
- 알림→대시보드→로그의 사슬은 계약(링크·uid)입니다 — 끊긴 사슬은 없느니만 못합니다
- 낡은 대시보드는 부채입니다 — as code + 과감한 삭제가 유지의 조건
- 검증은 게임데이로 — "있다"와 "쓰인다"의 간극은 리허설만이 드러냅니다

★ 09의 결론: 대시보드는 데이터의 전시가 아니라 조사 동선의 포장입니다. L1→L2→L3의 계층, 변수, 링크, 배포 마커, as code — 전부 "장애의 순간 3분 안에 원인 후보에 도달"이라는 하나의 목표를 위한 장치입니다. 10(알림)이 이 동선의 출발점을, 23(장애 대응)이 전체 리허설을 다룹니다.
