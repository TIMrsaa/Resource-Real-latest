## 정답

**A1.** RED — 대상: 요청을 처리하는 것(API·워커 등 서비스). 지표: Rate(초당 요청)·Errors(에러 **비율**)·Duration(지연 **분위수** p50/p95/p99). "사용자가 아픈가"의 증상 신호. USE — 대상: 리소스(노드·디스크·네트워크·컨테이너 리소스). 지표: Utilization(사용률)·Saturation(포화 — 큐·스로틀)·Errors(OOM·하드웨어). "자원이 눌리는가"의 원인 후보 신호. 관계: RED에서 증상을 감지하고 USE(또는 트레이스)로 원인을 탐색합니다 — 대시보드 계층(L1 RED 개요 → L3 USE 상세)도 이 순서를 따릅니다.

**A2.** 포화(Saturation)를 놓친 것입니다. CPU 사용률 70%로 여유로워 보여도 CPU limits가 낮으면 스로틀링(container_cpu_cfs_throttled_periods)이 걸려 요청이 눌립니다 — 사용률은 "얼마나 쓰나"만 말하고, 포화는 "한계에 눌리나"를 말합니다. 메모리도 마찬가지(working_set/limits가 1.0에 근접하면 OOM 임박). USE에서 실전 신호는 사용률보다 포화인 경우가 많습니다 — "여유 있어 보이는데 느려요"의 단골 원인이 limits에 의한 스로틀입니다.

**A3.** 푸는 문제: 서비스마다 대시보드를 복붙 증식하면 하나 고칠 때 열 개를 고쳐야 하고 금세 불일치가 납니다. 변수를 쿼리에 넣으면({namespace="$namespace", service=~"$service"}) 대시보드 하나가 모든 서비스를 커버하고, label_values()로 목록을 메트릭에서 자동 추출하므로 새 서비스가 생겨도 수정이 0입니다(08의 ServiceMonitor 셀프서비스와 짝). 연쇄 변수: $namespace를 먼저 정의하고 $service의 쿼리가 $namespace를 참조(label_values(http_requests_total{namespace="$namespace"}, service)) — 네임스페이스를 고르면 그 안의 서비스만 나옵니다. All·다중 선택은 정규식 매칭(=~)으로.

**A4.** L1 개요(온콜의 첫 화면): 전 서비스 에러율·p99 테이블(임계 초과 강조·정렬) + 클러스터 포화 — "어디가 아픈가". L2 서비스(변수 $service): RED 상세 + 배포 마커 — "언제부터, 어떤 패턴, 그때 무슨 배포". L3 인스턴스: Pod별 분해 + USE + 재시작 — "어느 Pod가, 자원 문제인가", 여기서 로그·트레이스 링크로 점프(12). 링크 구현의 핵심: data link의 URL에 **변수를 전달**하는 것 — `/d/svc-red/...?var-service=${__data.fields.service}` — 테이블 행 클릭이 변수가 채워진 L2로 착지해 클릭 한 번이 질문 하나를 답합니다.

**A5.** "언제부터 이상해졌나"(추세 변화 시점)에 "그때 무엇이 바뀌었나"(배포·설정 변경)를 겹쳐 보여줍니다 — 05의 이벤트 문맥("그때 무슨 변화가?")을 그래프 위 세로선으로 내장한 것. 에러율 급등 지점과 배포 마커가 겹치면 회귀(regression)가 즉시 유력 원인이 됩니다. 실전 자동화: CD 파이프라인(GitHub Actions·ArgoCD 등)이 배포 완료 시 Grafana annotation API(POST /api/annotations)를 호출해 서비스·버전 태그와 함께 기록 — 사람이 손으로 찍는 게 아니라 배포 절차의 일부로.

**A6.** Import한 대시보드는 Grafana 내부 DB(기본 SQLite, 영속볼륨 없음)에만 저장되어 Pod 재생성 시 초기화와 함께 소멸했습니다. 내장 대시보드는 **ConfigMap 프로비저닝**으로 공급되기 때문에 Pod가 죽어도 sidecar가 CM에서 다시 로드합니다 — 진실이 Pod 밖(CM→Git)에 있으므로 Pod는 소모품입니다. as code의 계약: `grafana_dashboard: "1"` 라벨이 달린 ConfigMap에 대시보드 JSON을 넣으면 sidecar가 감지해 자동 로드합니다 — 그 CM을 Git+GitOps(kustomize configMapGenerator → ArgoCD/Flux)로 관리하면 PR 리뷰·이력·롤백·환경 일관성이 따라옵니다.

**A7.** 루프: ① 조사 중 UI에서 자유롭게 실험(패널 추가·수정) → ② 확정되면 JSON Model을 복사해 → ③ Git의 json 파일에 반영, PR 리뷰 후 머지 → GitOps가 CM에 반영 → ④ UI의 임시 수정은 원복돼도 무방(진실은 Git). 규율 ①: uid 고정 — 드릴다운·알림 착지 링크가 uid 기반이라 uid가 바뀌면 동선이 조용히 404가 됩니다(Git의 JSON에 uid를 명시). 규율 ②: datasource를 변수/기본값으로 — 특정 datasource 이름을 하드코딩하면 스테이징/프로덕션 등 환경 간 이식이 깨집니다.

**A8.** 원인: ① L1 부재 — 60장 전부 상세(L2·L3)뿐이라 "장애의 첫 화면"이 없어 온콜이 kubectl로 회귀, ② 알림→대시보드 사슬 부재/단절 — 링크가 없거나 uid 변경으로 404, 온콜이 검색으로 헤맴, ③ 낡음 — 클릭으로 만들어 관리가 안 됐고 라벨 개편으로 절반이 No data(제작자 퇴사), ④ 결국 조사는 시니어의 CLI 수작업 — 대시보드의 실사용 0분. 재편: 동선 기준 재설계(L1 공식화→L2→L3, 편입 안 되는 것 과감히 아카이브), 모든 알림에 착지 링크 의무화(uid 고정), 전량 as code 전환(라벨 개편 시 PR로 함께 수정), 분기 게임데이로 "대시보드만으로 원인 후보까지"를 리허설. 교훈: 성공 지표는 장수(張數)가 아니라 장애 때 사용 시간입니다.
