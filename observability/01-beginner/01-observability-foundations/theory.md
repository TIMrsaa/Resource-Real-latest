# 이론 — 모니터링 vs 관측, 신호 4종, 원산지 지도, 조사 동선, 비용

> **🌱 17세 눈높이 비유: 건강검진 vs 종합병원 진단 능력**
> - **모니터링(가정용 체온계·혈압계)** = 미리 정한 것만 잽니다 — "열 37.5도 넘으면 병원 가자" (정한 질문에 답)
> - **관측 가능성(종합병원의 진단 능력)** = 어떤 증상이 와도 조사할 수 있습니다 — 혈액검사(메트릭), 진료 기록(로그), CT로 몸속 경로 추적(트레이스), 입원 기록(이벤트)
> - **신호 분담** = 체온(메트릭)이 "이상함"을 알리고 → CT(트레이스)가 "어디가"를 좁히고 → 조직검사(로그)가 "왜"를 말합니다
> - **비용** = 모든 환자에게 매일 전신 MRI를 찍으면 병원 파산 — 필요한 검사를 필요한 만큼 (샘플링·보존)
> - **핵심** = 관측 가능성은 장비가 아니라 **"새로운 질문에 답할 수 있는 능력"** — 장비(도구)는 그 수단

---

## 1. 모니터링 vs 관측 가능성

```
모니터링 (monitoring):
  미리 정한 질문에 답합니다
  "CPU 80% 넘었나요?" "프로세스 살아있나요?" "5xx 비율 1% 넘나요?"
  → 알려진 장애 모드(known unknowns)에 강함
  → 대시보드·알림·체크

관측 가능성 (observability):
  아직 하지 않은 질문에 답할 수 있는 시스템의 성질
  "왜 어제 15:00에 ap-northeast-2a의 v2 Pod로 간
   결제 요청만 p99가 3배였지?"
  → 몰랐던 장애 모드(unknown unknowns)를 조사 가능
  → 풍부한 신호 + 신호를 넘나드는 조사 능력

관계: 대립이 아니라 포함
  관측 가능한 시스템 위에서 모니터링(정한 질문·알림)도 합니다
  모니터링만 있으면 → 새로운 형태의 장애에 눈뜬장님

★ K8s가 관측 가능성을 강제하는 이유:
  동적(Pod 생멸·이동) + 분산(요청이 여러 서비스) + 조합 장애
  → "고정된 서버의 그래프"로는 조사 불가
```

## 2. 신호 4종 (MELT) — 성격과 분담

```
              성격                강점                약점/비용
Metrics       숫자의 시계열        쌉니다, 집계·알림·추세    개별 사건 안 보임
              (구조: 이름+라벨+값)  수학 가능(율·분위수)    카디널리티=돈(cncf 11)
Events        사건의 기록          문맥(배포·스케일·퇴거)  그 자체론 단편
              (구조: 무엇이 언제)   "그때 뭐 있었지?"에 답
Logs          사건의 서술          상세·유연·어디나 있음    볼륨=돈, 검색이 과제
              (구조: 시각+본문)     "왜?"의 최종 답변       구조화 안 하면 무력
Traces        요청의 여정          분산 인과·병목 지목      계측 필요, 샘플링 필수
              (구조: trace>span)   "어디가 느린가"에 답

분담(조사 동선 — cncf 13의 원형):
  메트릭이 "이상함"을 감지(알림)
    → 트레이스가 "어느 구간"인지 좁힘
    → 로그가 "왜"를 서술
    → 이벤트가 "그때 무슨 변화가 있었는지"(배포? 퇴거?) 문맥 제공
★ 넷은 경쟁이 아니라 릴레이 — 잇는 것(상관, 12모듈)이 실력
```

## 3. K8s 신호의 원산지 지도 (이 파트의 밑그림)

```
[앱 컨테이너]
  로그: stdout/stderr → containerd가 노드 파일로
        /var/log/pods/<ns>_<pod>_<uid>/<container>/N.log (02에서 심층)
  메트릭: 앱이 :PORT/metrics로 노출 (Prometheus 형식, 03)
  트레이스: 앱 SDK가 생성해 Collector로 push (04·11)

[kubelet (노드마다)]
  cAdvisor 내장: 컨테이너 CPU·메모리·네트워크 (kubectl top의 원천)
  kubelet 자체 메트릭: Pod 시작 지연, 볼륨 등
  summary API: /stats/summary

[API 서버 (컨트롤 플레인)]
  Events: kubectl get events의 그것 (기본 1시간 보존! — 05)
  audit 로그: 누가 무엇을 요청했나 (보안·규정, 05)
  API 메트릭: 요청 지연·큐·인증 실패

[노드 OS]
  node-exporter(설치 시): CPU·디스크·네트워크·파일시스템
  journald/syslog: kubelet·containerd 데몬 로그

[컨트롤 플레인 컴포넌트]
  etcd(cncf 21)·스케줄러·컨트롤러 매니저: 각자 /metrics

★ 수집기(Fluent Bit·Prometheus)를 깔기 전에 신호는 이미 태어나 있습니다
  수집기의 일 = 원산지에서 목적지로 나르기 (06~18의 전부)
```

## 4. "어떤 질문에 어떤 신호" 미리보기 (05에서 완성)

```
"서비스가 느려졌나요?"          → 메트릭 (p99 지연 추세)
"어느 구간이 느린가?"          → 트레이스 (span별 소요)
"그 구간에서 무슨 일이?"       → 로그 (해당 시각·trace_id로)
"그때 배포·스케일 있었나요?"     → 이벤트 (+ GitOps 이력)
"Pod가 왜 재시작했지?"        → 이벤트(OOMKilled) + 이전 로그(--previous)
"디스크가 언제 차나요?"          → 메트릭 (predict_linear)
"누가 이 리소스를 지웠나요?"     → audit 로그
```

## 5. 비용의 첫 인식 (22의 씨앗)

```
신호별 비용 구조:
  로그   = 볼륨(GB/일) × 보존(일) + 인덱싱 → 가장 흔한 폭탄
  메트릭 = 활성 시계열 수(카디널리티) → 메모리·저장 (cncf 11의 물리)
  트레이스 = 요청 수 × 샘플 비율 × span 크기 → 샘플링이 필수인 이유
  이벤트 = (K8s 기본은 1h 휘발) 남기려면 별도 수집 = 로그 비용

설계 원칙 (처음부터):
  "다 모으고 나중에 정리" X → 모으는 순간부터 돈
  신호마다 "이 신호로 무슨 질문에 답하려고?"를 먼저
  → 답할 질문이 없는 신호는 모으지 않는 것도 설계 (cncf 27의 정신)
```
