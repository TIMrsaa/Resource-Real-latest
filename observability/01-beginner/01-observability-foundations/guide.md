# 학습 가이드 — 왜 "모니터링"으로는 부족해졌나

## 출발 질문

쿠버네티스 이전 시대의 운영을 상상해 보자. 서버 10대, 각 서버에 앱 하나. 모니터링은 단순했습니다:

```
서버마다: CPU·메모리·디스크 그래프 + "80% 넘으면 알림"
앱마다: 프로세스 살아있나 + 에러 로그 tail
→ 무엇이 어디 있는지 고정돼 있으니, 미리 정한 질문으로 충분
```

쿠버네티스 세계에선 이 전제가 무너집니다:

```
Pod는 태어나고 죽고 옮겨 다닙니다 (어제의 IP는 오늘 없습니다)
서비스 하나가 수십 Pod, 요청 하나가 서비스 5개를 거칩니다
장애의 형태: "전체가 죽음"보다 "특정 조합만 느림"이 많습니다
  (특정 노드의 특정 버전 Pod로 간 요청만 5% 느림)
→ 미리 정한 질문으로는 못 잡습니다
→ "아직 하지 않은 질문"에 답할 수 있어야 = 관측 가능성
```

## 이 모듈의 두 기둥

### 기둥 1 — 신호 4종의 성격 (MELT)

```
Metrics(메트릭): 숫자의 시계열 — 싸고, 집계·알림에 최적, 대신 개별 사건은 안 보임
Events(이벤트): 시스템의 사건 기록 — K8s Events·배포·스케일 (문맥 제공)
Logs(로그): 사건의 서술 — 상세하고 유연, 대신 비싸고 검색이 과제
Traces(트레이스): 요청의 여정 — 분산 시스템의 인과, 대신 계측 필요
```

핵심은 "어느 것이 최고냐"가 아니라 **역할 분담**입니다 — 메트릭이 "뭔가 이상함"을 알리고, 트레이스가 "어디가 느린지"를 좁히고, 로그가 "왜"를 말해줍니다. 이 조사 동선이 cncf 13에서 배운 것이고, Part 5에서 실제로 구축합니다.

### 기둥 2 — 신호의 원산지 지도

K8s 클러스터에서 신호가 태어나는 곳을 전부 알아야 파이프라인을 설계할 수 있습니다:

```
앱 컨테이너: stdout/stderr(로그), /metrics(메트릭), SDK(트레이스)
kubelet: cAdvisor(컨테이너 리소스 메트릭), 노드 상태
API 서버: Events, audit 로그, API 메트릭
노드: node-exporter(하드웨어·OS), systemd/journal
컨트롤 플레인: etcd·스케줄러·컨트롤러 매니저의 메트릭
```

lab-01에서 이 원산지들을 kubectl로 직접 두드려 봅니다 — 수집기를 깔기 전에, **신호가 이미 거기 있다**는 것을 눈으로 확인하는 것이 순서입니다.

## 관측의 첫 번째 배신 — 공짜가 아닙니다

처음부터 새겨야 할 사실: **관측은 비용입니다.**

```
로그: 볼륨 × 보존 기간 = 저장 비용 (+ 전송·인덱싱)
메트릭: 카디널리티(라벨 조합 수) = 메모리·저장 (cncf 11의 물리)
트레이스: 전 요청 저장은 불가 → 샘플링 필수
→ "다 모으자"는 설계가 아니라 파산 계획
→ 무엇을 모으고 무엇을 버릴지가 22(비용 공학)의 주제
```

이 인식을 1번 모듈부터 갖고 가면, 이후 모든 파이프라인 설계에서 "이건 얼마짜리 신호인가"를 자연히 묻게 됩니다.
