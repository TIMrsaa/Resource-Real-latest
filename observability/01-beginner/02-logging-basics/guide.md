# 학습 가이드 — 로그의 한 줄이 흐르는 길

## 왜 "stdout에 써라"인가

쿠버네티스 이전, 앱은 로그를 파일에 썼습니다 (`/var/log/myapp/app.log`). 컨테이너 세계에서 이 습관은 문제가 됩니다:

```
컨테이너에 로그 파일을 쓰면:
  컨테이너 재시작 → 파일 소멸 (컨테이너 파일시스템은 휘발)
  파일이 쌓이면 → 컨테이너/노드 디스크 압박 (누가 로테이션?)
  수집기가 각 컨테이너 안의 서로 다른 경로를 알아야 함

stdout/stderr에 쓰면 (12-factor: 로그는 이벤트 스트림):
  런타임(containerd)이 받아서 노드의 표준 위치에 기록
  로테이션은 kubelet이 (앱은 신경 끔)
  수집기는 노드의 한 디렉터리만 보면 됨 (01에서 확인한 /var/log/pods/)
→ 앱은 "쓰기만", 플랫폼이 "관리" — 관심사 분리
```

이 표준 덕에 06(Fluent Bit)의 DaemonSet 하나가 모든 앱의 로그를 수집할 수 있습니다.

## 이 모듈에서 파는 세 층

```
층 1 — 물리: stdout → CRI 포맷 파일 → 로테이션
  containerd가 붙이는 접두어(시각·스트림·플래그)의 의미
  kubelet이 파일을 자르는 규칙 (기본 10Mi × 5개 — 넘치면 유실!)

층 2 — 접근: kubectl logs의 실전 옵션
  -f(팔로), --previous(죽은 컨테이너의 마지막 로그 — 재시작 조사의 열쇠),
  --since/--tail(범위), -l(라벨로 여러 Pod), --prefix(누가 쓴 줄인지)

층 3 — 품질: 구조화 로깅
  "Payment failed for user 123" (사람용 문장)
  vs {"level":"error","event":"payment_failed","user_id":123} (기계용 데이터)
  → 검색·집계·알림이 되는 로그 vs grep만 되는 로그
```

## 구조화가 왜 분기점인가

lab-02에서 직접 겪겠지만, 미리 감을 잡자:

```
질문: "지난 1시간, 유저별 결제 실패 횟수 상위 10명은?"

비구조화 로그: grep "failed" | 정규식으로 user 추출 | sort | uniq -c ...
  → 로그 형식이 조금만 달라도 깨짐, 필드 경계 모호, 느림

JSON 로그: 수집 파이프라인이 필드로 파싱해 저장
  → level=error, event=payment_failed로 필터, user_id로 group by
  → CloudWatch Logs Insights(13)·OpenSearch(18)·Loki(12)에서 쿼리 한 줄
```

구조화는 "예쁜 로그"가 아니라 **로그를 데이터로 만드는 결정**입니다. 그리고 이 결정은 앱 코드에서 일어납니다 — 파이프라인(06~)이 아무리 좋아도 원천이 비구조면 한계가 있습니다(01의 "신호 품질" 논지).

## 예외 패턴 — stdout이 안 될 때

레거시 앱이 파일에만 쓴다면? 세 가지 선택지를 theory에서 다룹니다:

```
① 앱 수정 (최선 — 가능하면)
② 사이드카 스트리밍: 파일을 tail해 자기 stdout으로 (표준 경로 복귀)
③ 사이드카 수집기: 파일을 직접 수집기로 (비표준, 최후)
```

## 06으로 가는 다리

이 모듈이 끝나면 로그의 "원천~노드 파일"이 완성됩니다. 06(Fluent Bit)은 그 다음 — 노드 파일을 tail해 파싱(여기서 JSON 구조화가 빛납니다)하고 목적지로 나릅니다. 층 1을 모르면 06의 tail 설정이, 층 3을 모르면 06의 파서 설정이 주문(呪文)이 됩니다.
