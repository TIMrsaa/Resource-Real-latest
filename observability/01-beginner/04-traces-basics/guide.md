# 학습 가이드 — 하나의 요청, 다섯 개의 서비스, 그리고 실

## 문제부터 — "누가 느린 거야?"

마이크로서비스에서 요청 하나가 이렇게 흐릅니다:

```
사용자 → 게이트웨이 → 주문 서비스 → 재고 서비스
                          └→ 결제 서비스 → 외부 PG
```

사용자: "주문이 5초 걸려요." 각 팀의 반응:

```
게이트웨이 팀: "우리 로그엔 주문 서비스 호출이 4.9초로 나와요" (떠넘김)
주문 팀: "우리는 결제 응답을 기다렸을 뿐" (떠넘김)
결제 팀: "우리 처리시간은 50ms인데요?" (자기 로그만 봄)
→ 각자 자기 조각만 보고, 조각을 이을 방법이 없습니다
```

문제의 본질: **각 서비스의 로그·메트릭은 있지만, "같은 요청"이라는 연결이 없습니다.** 트레이스는 이 연결 — 요청마다 고유한 ID(trace_id)를 부여하고, 그 ID를 서비스 경계 너머로 전달(전파)해, 여정 전체를 하나의 트리로 재구성하는 것입니다.

## 두 개의 개념만 잡으면 됩니다

### 개념 1 — trace/span 모델

```
trace = 요청 하나의 전체 여정 (trace_id로 식별)
span = 여정 속 작업 하나 (이름·시작시각·소요시간·부모)

주문 요청의 trace (트리):
  [gateway: POST /orders          ████████████████████ 5.0s]
    [order-svc: create_order       ███████████████████ 4.9s]
      [inventory: check_stock      █ 30ms]
      [payment-svc: charge         ██████████████████ 4.8s]   ← 병목!
        [external-pg: api_call     ██████████████████ 4.75s]  ← 진범!
→ 간트 차트 한 장이 "누가 느린가"를 끝냄 — 회의 세 번 대신
```

### 개념 2 — 컨텍스트 전파

트리를 만들려면 각 서비스가 "나는 어느 trace의, 누구의 자식인가"를 알아야 합니다. 그 정보가 **HTTP 헤더로 요청과 함께 여행**합니다:

```
traceparent: 00-{trace_id}-{parent_span_id}-{flags}

게이트웨이가 주문 서비스를 호출할 때 이 헤더를 붙이고,
주문 서비스는 받은 trace_id를 이어받아 자기 span을 만들고,
결제를 호출할 때 다시 (자기 span_id를 부모로) 헤더를 붙입니다
→ 실이 끊기지 않고 이어집니다
```

전파는 대개 라이브러리(OTel SDK)가 자동으로 하지만, **끊기는 지점**(큐를 거치는 비동기, 계측 안 된 서비스, 커스텀 스레드)이 있고 — 끊기면 트리가 조각납니다(lab-02).

## 왜 "계측"이 진입 장벽인가 — 그리고 완화책

```
로그·메트릭: 플랫폼이 공짜로 (01)
트레이스: 모든 서비스가 SDK를 붙여야 그림이 완성
  한 서비스만 빠져도 그 구간이 블랙박스
→ 조직적 협조가 필요 = 도입이 늦어지는 구조적 이유

완화책 (뒤 모듈들):
  자동 계측(11): 코드 수정 없이 SDK 주입 (Java/Python 등)
  서비스 메시(cncf 24): 프록시가 span 생성 (단, 앱 내부는 못 봄)
  eBPF(19): 커널에서 관찰 (단, 컨텍스트 전파는 한계)
```

## 샘플링 — 왜 전부 저장하지 않나

```
초당 1만 요청 × span 5개 × 수 KB = 초당 수십 MB — 전수 저장 불가
→ 대표만 저장 (샘플링)
  head: 시작 시점에 결정 (단순·저비용, "재미있는" 요청을 못 고름)
  tail: 끝난 뒤 결정 (에러·느린 것만 골라 저장, 대신 버퍼 필요)
→ 개념만 여기서, 실전 설계는 cncf 12와 11·17에서
```

## 이 모듈의 실습 철학

SDK·Collector 없이 **traceparent 헤더를 손으로** 만들어 전파해 봅니다. 도구가 자동으로 해 주는 것을 한 번 손으로 해 봐야, 11에서 자동 계측이 "무엇을 대신해 주는지" 정확히 알게 됩니다 — 커리큘럼 전체의 방식(원리 먼저, 도구 나중)입니다.
