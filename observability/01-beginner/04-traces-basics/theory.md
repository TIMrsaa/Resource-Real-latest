# 이론 — trace/span 모델, traceparent, 전파, 끊김, 샘플링, 조사에서의 위치

> **🌱 17세 눈높이 비유: 택배 송장 번호의 여행**
> - **trace(송장 번호 하나의 전체 여정)** = 주문→물류센터→허브→배송기사→문 앞
> - **span(각 구간 기록)** = "허브 도착 14:00, 출발 14:30" — 구간마다 소요시간·담당자
> - **traceparent(상자에 붙은 송장)** = 상자가 어디를 가든 송장이 함께 감 — 그래서 모든 구간 기록이 같은 번호로 묶임
> - **전파 끊김(송장이 떨어짐)** = 중간에 송장 없이 새 상자에 옮겨 담으면 → 이후 기록은 새 번호 — "그 택배 어디 갔어?"에 답 못 함
> - **샘플링(모든 상자를 검사하진 않음)** = 전 상자 개봉 검사는 불가능 — 무작위 일부(head) 또는 문제 있어 보이는 것만(tail)
> - **핵심** = 실(송장)이 이어져야 여정이 보입니다 — 트레이스의 전부는 "ID를 끊지 않고 나르기"

---

## 1. trace/span 모델

```
trace: 요청 하나의 여정 전체. trace_id(16바이트 hex)로 식별
span: 여정 속 작업 단위. 구성:
  - trace_id (어느 여정의)
  - span_id (자신, 8바이트 hex)
  - parent_span_id (누구에게서 불렸나 — 트리를 만드는 연결)
  - name (예: "HTTP GET /orders", "SELECT orders")
  - start_time, duration
  - attributes (라벨: http.status_code, db.system 등 — cncf 12의 시맨틱 컨벤션)
  - status (OK/ERROR), events(예외 등 시점 기록)

트리 구조:
  root span (parent 없음, 보통 최초 진입점)
    └ child spans (parent_span_id가 상위 span_id)
       └ ... (DB 호출·외부 API도 각각 span)

읽는 법 (간트 차트):
  부모 구간 안에서 자식들이 어떻게 시간을 쓰나
  - 자식이 순차로 길게 → 순차 병목 (병렬화 후보)
  - 자식 사이 빈 공간 → 부모 자신의 시간 (앱 로직·GC?)
  - 특정 자식이 대부분 → 그 서비스가 병목 (guide의 PG 사례)
```

## 2. W3C traceparent — 전파의 표준

```
HTTP 헤더:
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └────────── trace_id ──────────┘ └─ parent span ─┘ │
          version                                                flags(01=sampled)

동작 (서비스 A → B 호출):
  A: 자기 span(span_id=X)을 만들고, 나가는 요청에
     traceparent: 00-<trace_id>-X-01 을 붙임
  B: 헤더를 읽어 같은 trace_id 이어받고, parent=X인 자기 span 생성
     B가 C를 부르면 다시 자기 span_id를 넣어 전달
  → ID 릴레이 — 이것이 전파(propagation)의 전부

tracestate 헤더: 벤더 확장 (부가 정보 릴레이)

W3C 표준의 의미:
  OTel·Jaeger·X-Ray·메시 등 이종 시스템이 같은 헤더를 이해
  → 반쪽은 OTel, 반쪽은 X-Ray여도 실이 이어질 수 있는 기반
  (X-Ray 고유 헤더도 있음 — 17에서, ADOT가 변환)

비HTTP 경계:
  gRPC: metadata로 동일 개념
  메시징(Kafka·SQS): 메시지 헤더/속성에 실어 릴레이 (40의 CloudEvents도
  extension으로) — ★ 여기가 가장 자주 끊기는 곳 (4절)
```

## 3. 계측 — span은 누가 만드나

```
수동 계측: 코드에서 SDK로 span 시작/종료 (정밀, 비용=개발 공수)
자동 계측: 에이전트/라이브러리가 프레임워크 훅에 끼어듦
  (HTTP 서버/클라이언트·DB 드라이버가 자동으로 span)
  Java: -javaagent, Python: 래퍼, K8s: OTel Operator가 주입 (11)
메시/프록시: 사이드카가 통신 span 생성 — 앱 내부는 안 보임
  ★ 그리고 메시만으로는 전파가 안 됨: 앱이 받은 traceparent를
    나가는 요청에 옮겨 붙여야 (최소한의 앱 협조는 필수 — cncf 24)

현실 조합: 자동 계측(80%) + 핵심 구간 수동 보강(20%)
```

## 4. 전파가 끊기는 지점 (lab-02에서 재현)

```
① 계측 안 된 서비스: 받기만 하고 안 넘김 → 이후 새 trace로 조각
② 비동기 경계: 큐에 넣을 때 헤더를 안 실음 → 소비자는 고아 trace
③ 커스텀 스레드/고루틴: 컨텍스트가 스레드 로컬이라 새 스레드로 안 넘어감
④ 프록시/게이트웨이가 헤더를 제거 (보안 필터가 낯선 헤더 스트립)
⑤ 폴리글랏: 언어별 SDK 설정 불일치 (전파 형식이 서로 다름 — B3 vs W3C)

끊김의 결과: 트리가 조각남
  "게이트웨이까지는 보이는데 그 뒤가 없어요"
  → 반쪽 트레이스는 반쪽 답 — 도입 시 전파 검증이 필수 (lab-02)
```

## 5. 샘플링 — 전수 저장 불가의 물리

```
비용: 요청 수 × span 수 × span 크기 — 대규모에선 전수 저장 불가 (01)

head 샘플링 (시작 시 결정):
  root에서 "이 trace는 저장(1%)"을 정하고 flags로 전파
  장점: 단순·저비용·모든 서비스가 일관되게 같은 결정
  단점: 결정 시점에 미래(에러가 날지, 느릴지)를 모름
       → 흥미로운 트레이스가 1%에 안 걸릴 수 있음

tail 샘플링 (종료 후 결정):
  일단 모아서 (Collector가 버퍼) 에러·고지연만 저장
  장점: "재미있는 것"을 골라 담음
  단점: 버퍼 메모리·모든 span이 같은 곳에 모여야 (운영 복잡)

실무: head(기본 비율) + tail(에러·느린 것 부스트) 조합 (cncf 12·11에서 실전)
★ 어느 쪽이든 "트레이스는 전수 기록이 아니다" — 정확한 카운트는
  메트릭의 몫 (신호 분담: 개수는 메트릭, 사례는 트레이스)
```

## 6. 조사 동선에서 트레이스의 자리 (01의 릴레이 완성)

```
메트릭 알림: "orders p99가 5초" (무엇이 이상한지)
  ↓ (exemplar 또는 시간대로)
트레이스: 느린 trace를 열어 간트 차트 → "payment→PG 구간이 4.8s" (어디가)
  ↓ (trace_id로)
로그: 그 trace_id의 payment 로그 → "PG timeout, retry 3회" (왜)
  ↓
이벤트/변경 이력: "PG 엔드포인트 설정 변경이 오늘 아침" (무엇이 바뀌어서)

★ 이 점프가 되려면: 로그에 trace_id 필드(02의 구조화 규약!),
  메트릭에 exemplar(12에서) — 신호 상관은 설계의 산물이지 우연이 아닙니다
```

## 요약 카드

| 질문 | 답 |
|------|----|
| trace/span? | trace=요청의 여정(trace_id), span=작업 단위(부모 연결로 트리) |
| 간트 읽기? | 순차 긴 자식=병목, 자식 사이 공백=부모 자신, 최장 자식=진범 |
| traceparent? | 00-trace_id-parent_span-flags — ID 릴레이의 표준 헤더 |
| 전파의 본질? | 받은 ID를 나가는 요청에 옮겨 붙이기 — 끊기면 트리 조각 |
| 자주 끊기는 곳? | 미계측 서비스·큐(비동기)·커스텀 스레드·헤더 스트립·형식 불일치 |
| head vs tail? | 시작 시 결정(단순, 미래 모름) vs 종료 후 선별(정확, 버퍼 필요) |
| 트레이스로 카운트? | 금지 — 샘플이라 부정확. 개수는 메트릭, 사례는 트레이스 |
| 상관의 전제? | 로그에 trace_id 필드(02), 메트릭 exemplar — 설계의 산물 |
