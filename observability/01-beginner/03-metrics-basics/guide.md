# 학습 가이드 — 숫자에도 종류가 있습니다

## 왜 타입이 4개나 있나

"메트릭 = 숫자 시계열"이라면 타입이 왜 필요할까요? **숫자의 의미가 다르기 때문**입니다:

```
"지금까지 요청 1,000,000건" (누적) — 절대값은 무의미, 증가 속도가 의미
"지금 메모리 1.2GB" (순간값) — 지금 값 자체가 의미
"요청 지연들의 분포" (분포) — 평균은 거짓말, 분위수(p99)가 의미
```

누적엔 counter, 순간엔 gauge, 분포엔 histogram — 타입은 **"이 숫자를 어떻게 읽어야 하는가"의 계약**입니다. 타입을 모르면 counter를 그래프에 그대로 그려 "우상향 직선"을 보며 고개를 갸웃하게 됩니다(누구나 한 번은 하는 실수).

## counter와 rate — 이 모듈의 첫 고비

```
counter: 재시작하면 0부터 다시 (리셋), 계속 증가
  http_requests_total = 1,000,000   ← 이 값 자체는 "서버가 오래 살았네" 정도

의미 있는 질문: "초당 몇 건?"
  rate(http_requests_total[5m])  ← 5분 창에서 증가 속도
  → counter는 항상 rate()/increase()로 읽습니다
  → 리셋(재시작)도 rate가 알아서 처리 (내려간 지점을 보정)
```

왜 처음부터 초당 값으로 안 내보내나요? — 앱이 평균 창을 정해버리면 소비자가 창을 바꿀 수 없습니다. 누적으로 내보내면 **읽는 쪽이 어떤 창(1m·5m·1h)으로도** 계산할 수 있습니다. 이 "원본은 누적, 해석은 쿼리"가 Prometheus 설계의 핵심 감각입니다.

## histogram — 평균의 거짓말을 이기는 도구

```
지연의 평균이 100ms여도:
  대부분 50ms + 일부 5초 (p99가 5초!) 일 수 있습니다 — 평균이 은폐
  → 분위수(p50/p95/p99)가 필요

histogram의 방식: 버킷 카운터
  le=0.1(100ms 이하): 9,500건 / le=0.5: 9,900건 / le=5: 10,000건
  → 이 버킷들로 p99를 "근사" (histogram_quantile)
  → 근사 정밀도 = 버킷 경계 설계에 달림 (08·21에서 실전)
```

01의 사고 사례("전체 평균에 묻힌 p99 8초")가 histogram이 존재하는 이유입니다.

## 두 개의 메트릭 세계 — 혼동의 근원

K8s에는 목적이 다른 두 메트릭 파이프라인이 공존합니다:

```
① 리소스 메트릭 파이프라인 (플랫폼 내부용)
   cAdvisor → metrics-server → Metrics API
   소비자: kubectl top, HPA(08의 그것!)
   특징: 최신 값만(저장 안 함), CPU/메모리만, 짧은 주기
   → "지금 스케일 판단"을 위한 실시간 스냅샷

② 모니터링 파이프라인 (사람·알림용)
   /metrics 엔드포인트들 → Prometheus → 저장(TSDB)
   소비자: Grafana·Alertmanager·조사
   특징: 이력 저장, 모든 종류 메트릭, 유연한 쿼리
   → "추세·조사·알림"을 위한 시계열 데이터베이스
```

"kubectl top과 Grafana가 다르다"는 질문의 답: **다른 파이프라인, 다른 집계 창, 다른 시점**이라 다른 게 정상입니다. lab-02에서 직접 비교합니다.

## 라벨 — 강력함과 위험의 양날

```
http_requests_total{method="GET", path="/api/orders", code="200"}
→ 라벨 덕에 "경로별 에러율" 같은 분해가 가능 (01 사고의 해법!)

하지만: 시계열 수 = 라벨 값 조합의 곱
  method(5) × path(50) × code(10) = 2,500 시계열 (괜찮음)
  여기에 user_id(100만)를 라벨로? → 수억 시계열 → 폭발 (cncf 11)
→ 라벨 설계 원칙: 유한하고 낮은 카디널리티만 (unbounded 값 금지)
```

이 감각을 여기서 심어야 08(relabeling)·22(비용)의 통제가 이해됩니다.
