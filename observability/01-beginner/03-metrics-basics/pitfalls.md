# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. counter를 그대로 그래프에 그림
`http_requests_total`을 그대로 대시보드에 올리면 영원히 우상향하는 직선만 보입니다 — 트래픽이 늘었는지 줄었는지 아무 정보가 없습니다. counter는 반사적으로 `rate()`(초당)나 `increase()`(구간 증가량)로 감쌉니다. 반대 함정도 있습니다: gauge에 rate()를 걸면 무의미한 값이 나옵니다(오르내리는 값의 "증가율"은 해석 불가). **타입을 확인하고 타입에 맞는 함수** — TYPE 선언을 읽는 습관이 기본기입니다.

### 2. 평균으로 지연을 말함
`_sum/_count`(평균)만 보고 "지연 정상"이라 판단합니다. 평균 100ms 아래에 p99 5초가 숨습니다(01의 사고). 지연·크기 같은 분포형 지표는 반드시 분위수(p50/p95/p99)로 봅니다 — 그래서 histogram으로 계측하고 `histogram_quantile`로 읽습니다. 또 하나: **p99들의 평균·요약(summary)의 합산은 수학적으로 무의미**합니다. 인스턴스별 p99를 평균 내지 말고, 버킷을 합산(sum by le)한 뒤 분위수를 구하세요 — K8s에서 histogram이 표준인 이유입니다.

### 3. unbounded 값을 라벨로 — 카디널리티 폭발
user_id·request_id·원시 URL·에러 메시지를 라벨에 넣습니다. 시계열 수 = 라벨 값 조합의 곱이라, unbounded 라벨 하나가 수백만 시계열을 만들어 Prometheus 메모리를 삼킵니다(cncf 11의 물리). 개별 식별자는 로그·트레이스의 몫입니다(신호 분담). path는 반드시 라우트 패턴(`/orders/{id}`)으로 정규화 — 계측 라이브러리의 라우터 통합을 확인하세요. 새 라벨을 추가하기 전 "값이 몇 개까지 갈 수 있나"를 계산하는 습관이 22(비용)의 시작입니다.

### 4. metrics-server를 모니터링으로, Prometheus를 HPA로 혼용
"metrics-server 있는데 Prometheus 왜 필요?"(이력·커스텀 메트릭·알림이 없습니다) 또는 "Prometheus 있는데 kubectl top이 왜 안 돼?"(Metrics API는 metrics-server의 것). 두 파이프라인은 목적이 다릅니다 — metrics-server는 저장 없는 스냅샷으로 top·HPA 전용, Prometheus는 이력·쿼리로 사람·알림 전용. 접점이 필요하면 어댑터(prometheus-adapter)나 KEDA(cncf 18)라는 명시적 다리를 놓습니다. 혼동하면 "설치했는데 왜 안 되지"의 미궁에 빠집니다.

### 5. 버킷 경계를 기본값으로 방치
histogram 기본 버킷은 범용 값이라 내 서비스의 관심 구간과 어긋나기 쉽습니다. SLO가 "300ms 이하 99%"인데 버킷이 0.1/0.5/1.0이면, p99 근사가 0.1~0.5 사이 어딘가로 뭉개져 "SLO를 지켰는지"를 정밀하게 답할 수 없습니다. 관심 경계(0.3)를 버킷에 넣어라 — 분위수 정밀도는 버킷 설계가 정합니다(21의 SLO 측정에서 결정적). 단, 버킷 수도 시계열 수(×라벨 조합)이므로 무한정 늘리면 함정 3과 만납니다.

## 실무 사고 사례: "라벨 하나 추가했을 뿐인데 관측이 먼저 죽었다"

한 팀이 고객 문의 대응을 위해 "고객사별 API 사용량을 보고 싶다"는 요구를 받았습니다. 개발자는 간단히 계측 코드에 라벨 하나를 추가했습니다 — `http_requests_total{..., tenant_id="..."}`. 고객사(tenant)는 8,000개였습니다.

배포 후 몇 시간 만에:

1. **시계열 폭발** — 기존 메트릭이 method(5)×path(40)×code(10) ≈ 2,000 시계열이었는데, ×8,000 테넌트로 **수백만~수천만 시계열**이 됐습니다(모든 테넌트가 모든 조합을 치진 않지만 활성 조합만으로도 수십 배).
2. **Prometheus 메모리 급증** — 활성 시계열 수에 비례하는 head 메모리(cncf 11)가 치솟아 OOMKilled. 재시작 후 WAL replay가 다시 메모리를 요구하며 **재시작 루프**에 빠졌습니다.
3. **관측의 전면 장애** — Prometheus가 죽자 대시보드·알림이 모두 멈췄습니다. 하필 그 주 다른 서비스에서 장애가 났는데, **알림이 안 와서** 발견이 늦었습니다 — 관측이 죽으면 다른 모든 장애가 눈에 안 보인다는 이중 사고.
4. **롤백의 함정** — 계측을 롤백해도 이미 수집된 시계열은 TSDB에 남아 블록이 compaction될 때까지 부담이 지속됐습니다.

수습: 계측 롤백 + 문제 시계열 강제 삭제 + Prometheus 메모리 임시 증설. 그리고 재발 방지:

1. **라벨 심사** — 새 라벨은 "값의 상한"을 계산해 리뷰(수십 이하만 허용, unbounded 금지)를 코드 리뷰 체크리스트에.
2. **요구의 재해석** — "고객사별 사용량"은 메트릭 라벨이 아니라 **로그 기반 집계**(13·18의 쿼리)나 별도 과금 파이프라인이 맞는 요구였습니다. 신호 분담(01)의 실패였던 것.
3. **카디널리티 감시** — 시계열 수 자체를 메트릭으로 감시하고 급증 알림(22의 "관측의 관측"). scrape 대상별 시계열 상한(sample_limit)도 설정.

**교훈:**
- 라벨 추가는 곱셈입니다 — 커밋 한 줄이 수천만 시계열이 될 수 있습니다
- "X별로 보고 싶다"는 요구를 다 메트릭으로 받지 마세요 — unbounded면 로그·트레이스·별도 파이프라인의 몫 (신호 분담)
- 관측 시스템의 장애는 **모든 장애를 가립니다** — 관측 자체의 보호(리소스·한도·감시)가 우선순위
- sample_limit 같은 방어선을 미리 — 사고는 막지 못해도 폭발 반경을 줄입니다

★ 03의 결론: 메트릭의 힘(라벨 분해·수학)은 카디널리티라는 비용 위에 서 있습니다. 타입의 계약(rate·quantile)과 라벨의 규율(유한한 값만)을 지키면 메트릭은 가장 싸고 빠른 신호이고, 어기면 관측이 먼저 죽습니다. 08(운영)·22(비용)에서 이 규율을 시스템으로 만듭니다.
