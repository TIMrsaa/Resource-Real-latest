## 정답

**A1.** 구조: involvedObject(무엇에 관한 사건), reason(사건 유형 코드 — 조사의 열쇠), message(설명), type(Normal/Warning), count+first/lastTimestamp(같은 사건 반복 압축), source(보고자: kubelet·scheduler 등). 단골 reason: FailedScheduling(리소스 부족·taint 불일치 확인), OOMKilled(limits·메모리 추세 확인), Evicted(노드 Disk/MemoryPressure 확인), ImagePullBackOff/ErrImagePull(태그 오타·레지스트리 인증 확인), Unhealthy(프로브 설정·앱 상태 확인), BackOff(CrashLoop — logs --previous로), FailedMount(PVC·시크릿 존재 확인), NodeNotReady(노드 이상).

**A2.** Events는 기본 TTL 약 1시간(--event-ttl)으로 etcd 부담을 줄이기 위해 휘발됩니다 — 새벽 장애의 아침 조사, 간헐 패턴 분석이 불가능해집니다. 해법: exporter(kubernetes-event-exporter 등)가 Events를 watch해 stdout(JSON)으로 내보내면, 02의 원리대로 그 stdout이 로그 파이프라인(06)에 합류해 중앙 보존됩니다. 수집된 Events는 사실상 **구조화 로그**가 됩니다 — 검색("지난달 OOMKilled 전부")과 알림("Evicted 발생 시")이 가능해지는 신호의 전환입니다.

**A3.** audit는 "누가?"에 답합니다 — 모든 API 요청의 행위자(user/SA)·행위(verb+resource)·시각·출처 IP·결과를 기록해 "누가 이 Deployment를 지웠나", "이 SA가 뭘 조회했나"(보안), "누가 RBAC을 바꿨나"(규정)에 답합니다. 레벨: None(기록 안 함)/Metadata(누가·무엇을·언제)/Request(+요청 본문)/RequestResponse(+응답 본문, 가장 비쌈). 관례: 시크릿 접근·삭제·RBAC 변경 등 민감 행위는 상세하게(Request+), 대량 읽기(get/list/watch)는 Metadata 이하 또는 제외, 헬스체크 등 소음은 None — 전부 상세로 켜면 볼륨 폭발이므로 "누가에 답할 최소 집합"을 고르는 비용 설계입니다.

**A4.** 로그 — 원산지: 노드 /var/log/pods(containerd 기록), 수명: 로테이션 10Mi×5(분~시), 비용: 볼륨×보존, 질문: 왜?(서술). 메트릭 — 원산지: 각 /metrics(cAdvisor·컴포넌트·앱), 수명: scrape 안 하면 순간값뿐, 비용: 카디널리티, 질문: 얼마나·추세·비율? 트레이스 — 원산지: 앱 SDK(계측 필수), 수명: 수집 안 하면 없음, 비용: 샘플링율×span, 질문: 어디가?(여정). Events — 원산지: API 서버(kubelet 등이 보고), 수명: TTL 1시간, 비용: 수집 시 로그화(저렴), 질문: 플랫폼이 왜?(조치·사건). audit — 원산지: API 서버(정책 필요), 수명: 파일/CloudWatch 설정에 따름, 비용: 레벨×범위, 질문: 누가?(행위자).

**A5.** 전제는 **그 시각의 신호가 보존되어 있는 것**입니다 — Events는 1시간이면 휘발됐고, 노드 로그는 로테이션됐을 수 있으며, 메트릭은 scrape·저장하지 않았으면 이력이 없습니다. 즉 수집·보존해 두지 않은 신호로는 과거를 조사할 수 없습니다("휘발된 신호는 없는 신호"). 파이프라인(06~)의 존재 이유가 바로 이것입니다: 실시간 조회(kubectl)는 현재만 답하고, 과거·패턴·간헐 문제는 중앙 수집·보존된 신호만이 답합니다.

**A6.** "앱의 문제인가"는 로그(앱의 서술 — logs, --previous)로, "플랫폼의 조치인가"는 Events(플랫폼의 언어 — describe, Evicted·OOMKilled 등)로 갑니다. 사고의 교훈: 배치 실패를 사흘간 앱 로그·코드로만 조사했지만 실제는 노드 DiskPressure에 의한 Evicted(플랫폼 조치)였습니다 — Pod가 축출당하는 순간은 앱 로그에 남지 않습니다(앱은 그냥 SIGKILL당함). Pod 소멸·재시작 문제는 Events부터 여는 것이 정석이고, Events가 휘발되기 전에 수집해 둬야 간헐 패턴("실패 시각마다 Evicted")을 쿼리로 잡을 수 있습니다.

**A7.** 고객사(tenant) 식별자는 unbounded 값이라 메트릭 라벨로 넣으면 카디널리티 폭발입니다(03의 규율·사고 사례). 따라서 개별 식별자 기반 조사는 구조화 로그의 필드(tenant) 필터로 시작합니다 — 신호 분담의 전형: 집계·추세는 메트릭(유한 라벨), 개별 사례·식별자는 로그·트레이스. 이후 해당 요청의 trace_id로 트레이스에 점프해 "어디가" 느린지 좁힙니다(04·12의 상관).

**A8.** 구성: ① 신호 인벤토리(원산지·수명·비용·질문 — 실습으로 확인한 경로·명령 포함), ② 수집·보존 현황(신호별 수집기·저장소·보존·상태 — 초기엔 대부분 ❌가 정상이고 그 ❌가 다음 트랙의 할 일 목록), ③ 나의 질문 카탈로그(조사 반사 — 자기 언어로), ④ 갱신 로그. living document여야 하는 이유: 파이프라인이 생기고(06~) 서비스·보존 정책이 바뀌면 지도가 낡아 거짓말이 되기 때문(cncf 42의 낡은 위키와 같은 실패) — 각 모듈 수료·시스템 변경마다 2절을 갱신하고 로그를 남겨야 "장애의 순간 첫 질문을 고르는" 지도의 가치가 유지됩니다.
