# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. Events를 "kubectl describe에서 보는 것"으로만 소비
describe 하단의 이벤트만 보고 끝냅니다 — 그건 그 순간, 그 오브젝트, 남아있는 것만입니다. 1시간 TTL이 지나면 사라지고, 지워진 Pod의 이벤트는 따라 사라지며, 클러스터 전체 패턴("오늘 Evicted가 몇 번?")은 안 보입니다. Events는 수집(로그화)해야 조사 가능한 신호가 됩니다 — "새벽에 무슨 일이?"는 수집 없이는 영원히 답 없는 질문입니다.

### 2. audit를 안 켜거나, 반대로 전부 켬
안 켜면 "누가?"에 답할 수단이 0입니다 — 사고·보안 조사에서 치명적 공백. 반대로 전 리소스 RequestResponse로 켜면 읽기 요청(list/watch/헬스체크)이 대부분인 API 트래픽이 전부 본문까지 기록되어 볼륨이 폭발합니다. 정책 설계가 본체입니다: 민감 행위(시크릿·RBAC·삭제·변경)는 상세히, 대량 읽기는 Metadata 이하, 소음은 None — "누가?"에 답할 최소 집합.

### 3. 질문 없이 신호부터 모음 (지도 없는 수집)
"일단 다 수집"으로 시작하면 22의 비용 폭탄 + 정작 필요한 질문("누가?", "새벽의 Events")은 공백인 기형이 됩니다. 순서는 반대입니다: 질문 카탈로그(우리 팀이 답해야 하는 질문들) → 신호 지도(그 질문에 어떤 신호) → 수집 계획(그 신호를 어떻게). SIGNALS-MAP.md가 그 순서를 강제하는 장치입니다.

### 4. 신호 간 대응을 외우고 상황에선 못 씀
표로는 알지만("Events는 플랫폼의 왜"), 실제 장애에서 앱 로그만 30분 파다가 describe 한 번이면 나올 OOMKilled를 놓칩니다. 반사신경은 표 암기가 아니라 훈련입니다 — lab-02의 15문항을 "답 보기 전에 스스로"가 중요한 이유고, 23(장애 대응)에서 게임데이로 다시 단련합니다. 조사 시작 시 "이 질문은 어느 신호?"를 소리 내 묻는 습관이 지름길입니다.

### 5. 지도를 한 번 그리고 방치
SIGNALS-MAP.md를 졸업 과제로 내고 끝. 파이프라인이 생기고(06~), 서비스가 늘고, 보존 정책이 바뀌어도 지도는 v1 그대로 — 6개월 뒤 지도는 거짓말이 됩니다(cncf 42의 "낡은 위키"와 같은 실패). 지도는 living document입니다: 각 모듈 수료·시스템 변경 때마다 갱신 로그 한 줄. "지도가 현실과 같은가"를 분기마다 점검하는 것까지가 운영입니다.

## 실무 사고 사례: "범인은 노드 축출인데, 사흘간 앱만 의심했다"

한 팀의 배치 작업이 몇 주에 걸쳐 간헐적으로 실패했습니다. 패턴이 안 보였습니다 — 같은 코드가 어떤 날은 성공, 어떤 날은 실패. 팀은 당연히 **앱을 의심**했습니다: 재시도 로직 점검, 메모리 프로파일링, 의존 라이브러리 업그레이드… 사흘을 썼습니다.

실마리는 우연히 나왔습니다. 한 엔지니어가 실패 시각과 클러스터 상태를 대조하다가, 실패한 배치 Pod들이 전부 **같은 노드에서 사라졌음**을 발견했습니다. 하지만 그 시각의 Events는 이미 휘발(1시간 TTL)된 지 오래 — "왜 사라졌는지"의 플랫폼 기록이 없었습니다.

재현을 기다려 실시간으로 잡았습니다: `kubectl get events -w`를 걸어두고 실패 순간을 포착하니 —

```
Warning  Evicted  Pod The node had condition: [DiskPressure]
```

**노드 디스크 압박 축출**이었습니다. 다른 팀의 로그 폭주(02의 사고와 같은 계열)가 특정 노드 디스크를 주기적으로 채웠고, kubelet이 배치 Pod를 축출했던 것. 앱은 아무 잘못이 없었습니다.

복기:

1. **첫 질문이 틀렸습니다** — "앱이 왜 실패하지?"(로그)로 시작했지만, 올바른 첫 질문은 "Pod에 무슨 일이 있었지?"(Events)였습니다. Pod가 사라진 사건은 플랫폼의 언어(Evicted)로 기록되지, 앱 로그에는 안 남습니다(앱은 그냥 SIGKILL당함).
2. **Events 보존이 없었습니다** — 수집해 뒀다면 첫날 "실패 시각마다 Evicted" 패턴이 쿼리 한 번에 나왔습니다. 휘발된 신호는 존재하지 않는 신호입니다.
3. **간헐 문제는 보존된 신호로만 잡힙니다** — 재현 대기는 운에 기대는 조사입니다.

조치: Events 수집(exporter→로그 파이프라인) 상시화, Evicted·OOMKilled·FailedScheduling에 알림, 노드 디스크 메트릭 알림(predict_linear), 그리고 팀 runbook 첫 줄에 "Pod 소멸/재시작 문제는 Events부터".

**교훈:**
- Pod의 생사는 플랫폼의 언어(Events)로 기록됩니다 — 앱 로그에는 그 순간이 없습니다
- **휘발된 신호는 없는 신호** — 간헐·과거 문제는 보존된 Events가 유일한 목격자
- 조사의 첫 갈림길: "앱의 문제인가(로그), 플랫폼의 조치인가(Events)" — 여기서 사흘이 갈립니다
- 신호 지도의 가치는 평시가 아니라 **첫 질문을 고르는 그 순간**에 나옵니다

★ beginner 트랙의 결론: 다섯 신호는 각자 다른 질문의 목격자이고, 목격자를 잘못 고르면 사흘을 잃습니다. 그리고 어떤 목격자(Events)는 1시간이면 증발합니다 — 그래서 다음 트랙(06~)에서 파이프라인을 짓습니다: 목격자들의 증언을 보존하고, 검색하고, 잇기 위해.
