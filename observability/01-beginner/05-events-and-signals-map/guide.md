# 학습 가이드 — 지도를 완성하고 반사신경을 만들기

## 왜 Events를 따로 다루나

01에서 "Events는 1시간 휘발"을 스쳤습니다. 따로 한 모듈의 절반을 쓰는 이유:

```
Events가 답하는 질문들이 실무 조사의 최전선이기 때문:
  "Pod가 왜 안 뜨지?"     → FailedScheduling (리소스 부족? taint?)
  "왜 재시작했지?"          → OOMKilled, Liveness 실패
  "왜 쫓겨났지?"           → Evicted (노드 압박)
  "이미지가 왜 안 와?"      → ImagePullBackOff
→ 이 질문들은 로그(앱의 말)가 아니라 Events(플랫폼의 말)에 답이 있습니다
  앱 로그만 보면 "그냥 죽었는데요"로 끝나는 미스터리들
```

그런데 이 보물이 **기본 1시간이면 사라집니다**. 새벽 장애의 아침 조사, 간헐 재발 패턴 분석이 불가능해집니다 — 그래서 Events도 파이프라인의 수집 대상입니다(수집하면 로그가 됩니다 — 신호의 전환).

## audit 로그 — 다섯 번째 질문 "누가?"

네 신호(무엇이·어디가·왜·언제)에 없는 질문이 하나 있습니다: **"누가 했나요?"**

```
"이 Deployment 누가 지웠어?"
"어젯밤 이 ConfigMap 누가 바꿨어?"
"이 서비스어카운트가 뭘 조회하고 다니지?" (보안!)
→ 답은 API 서버의 audit 로그에 — 모든 API 요청의 기록
```

audit은 관측과 보안(cncf 07·30)의 교차점입니다. 레벨(어디까지 기록하나)과 비용(전부 기록하면 폭발)의 트레이드오프를 lab-01에서 직접 설정해 봅니다.

## 이 모듈의 본체 — 신호 지도라는 종합

01~05의 지식을 한 장으로 압축합니다:

```
신호      원산지               수명(기본)        비용 축         답하는 질문
로그      노드 /var/log/pods   로테이션(분~시)    볼륨×보존       왜?
메트릭    /metrics 노출         scrape 안 하면 0  카디널리티      얼마나요? 추세는?
트레이스  앱 SDK               수집 안 하면 0    샘플링율        어디가?
Events   API 서버             ★1시간           (수집 시 로그)   플랫폼이 왜?
audit    API 서버(설정 시)     설정에 따라       레벨×범위       누가?
```

이 표가 머리에 있으면, 어떤 질문이 와도 "그건 X 신호, 원산지는 Y, 수집은 Z로"가 나옵니다 — intermediate에서 파이프라인을 지을 때의 요구사항 명세이기도 합니다.

## 반사신경 훈련 — 질문 카탈로그

lab-02는 표를 외우는 게 아니라 **질문→신호 대응 훈련**입니다:

```
"결제 서비스가 느려졌대" → 메트릭(p99 확인)부터
"Pod가 CrashLoop이야" → describe(Events) + logs --previous
"누가 프로덕션 시크릿을 읽었지?" → audit
"이 요청이 어디서 막혔지?" → 트레이스
"디스크 언제 차?" → 메트릭(추세·예측)
```

이 반사신경이 23(장애 대응 동선)의 기초 체력입니다.

## 졸업 과제 — SIGNALS-MAP.md

cncf 파트의 MY-MAP.md처럼, 이 트랙의 졸업 과제는 **자기 손으로 그리는 신호 지도**입니다. 템플릿을 주지만 채우는 것은 실습으로 확인한 사실들이어야 합니다("문서에 그렇대요"가 아니라 "제가 확인했어요"). 이 지도는 06~12를 지나며 계속 갱신됩니다 — 파이프라인이 생길 때마다 "수집·보존" 칸이 채워지는 living document입니다.
