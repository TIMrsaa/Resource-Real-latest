# 자가 점검 퀴즈

**Q1.** 4대 생태계(fluent·prometheus·open-telemetry·grafana)의 거버넌스 성격을 비교하세요.

**Q2.** OTel의 조직 구조와 "언어 SIG가 1차 진입로"인 이유는?

**Q3.** "자기 영토성"이 높은 기여 경로들과 그 장점·책임은?

**Q4.** 기업 주도 오픈소스 참여의 올바른 기대 설정은?

**Q5.** 이 파트의 경험이 기여 재료가 되는 매핑을 다섯 개 들어라.

**Q6.** 대상 선정의 3축과 각 축의 판단 재료는?

**Q7.** 경로의 순서(문서·재현→자기 영토→본체)가 권장되는 이유는?

**Q8.** "세 번의 두드림" 사례에서 각 시도의 교훈은?

---

## 정답

**A1.** fluent: CNCF Graduated, 메인테이너 중심의 간결·실용 구조 — 플러그인(fluent-bit의 Go/WASM, fluentd의 Ruby gem)이 1급 기여 경로. prometheus: 팀 합의제(GOVERNANCE.md에 멤버십·투표 명문화) — 본체는 성숙 코어라 벽이 높고, exporter 생태(별도 저장소들)가 진입로. open-telemetry: 관측 최대 조직 — K8s급 SIG 체계(GC·TC + 스펙 SIG + 언어별 SIG 10+ + Collector SIG), 회의·캘린더 공개. grafana 계열: Grafana Labs 기업 주도 — 기여는 활발히 받되 로드맵·머지 권한이 사실상 사내에, 플러그인 생태가 자기 영토. 같은 "오픈소스"라도 운영 모델이 다르므로 모델을 알고 문을 두드려야 합니다(cncf 49).

**A2.** 구조: GC(거버넌스)·TC(기술) 위원회 아래 — 스펙 SIG(신호·시맨틱 컨벤션 표준, cncf 12를 만드는 곳), 언어 SIG 10여 개(각자 SDK·자동 계측), Collector SIG(코어+contrib 수백 컴포넌트), Operator·eBPF 등. 언어 SIG가 1차 진입로인 이유: ① 자기 주력 언어라 코드가 읽히고, ② 11에서 쓴 자동 계측의 "미지원 라이브러리"처럼 실무 마찰이 곧 이슈·기여 대상이 되며, ③ SIG 단위라 커뮤니티가 작아 관계 형성이 빠릅니다. contrib는 CODEOWNERS로 컴포넌트별 오너가 있어 작은 단위 기여가 구조적으로 가능합니다.

**A3.** 경로: Prometheus exporter(우리 시스템의 exporter 신규/개선), fluent-bit output 플러그인, Grafana 패널/데이터소스 플러그인, OTel Collector contrib 컴포넌트(준-자기 영토 — 코드오너제). 장점: 사실상 독립 프로젝트라 머지 대기·조율 마찰이 적어 첫 성취가 빠르고, "자기 필요"(우리 목적지·우리 시스템)가 동기라 지속됩니다 — 03의 노출 형식, 06의 파이프라인, 09의 패널 지식이 그대로 설계 역량이 됩니다. 책임: 만들기보다 유지가 깁니다 — 의존성 업데이트·버그 응답·API 추종을 못 하면 deprecated 후보(생태계 부채)가 되므로, 열 때 유지 의지까지 계획합니다(그 응답의 이력이 신뢰의 사다리이기도).

**A4.** "기여가 환영받는가"와 "방향을 함께 정하는가"를 분리해서 기대합니다 — 전자는 예(버그·문서·플러그인은 활발히 머지), 후자는 제한적(로드맵은 기업이 주도). 따라서: 큰 기능·방향성 제안은 코드 전에 반드시 이슈로 타진해 로드맵 정렬을 확인하고, 독립성이 높은 기여(플러그인 — 자기 영토)를 주 무대로 삼으며, 라이선스(AGPL 계열)와 거버넌스 모델을 알고 들어갑니다. 모델을 알면 실망이 없고, 모르면 "석 달 PR"(cncf 49)이 구조적으로 재연됩니다.

**A5.** ① 모듈들에서 헤맨 문서 지점(06의 CRI 파서·11의 언어별 예시) → 문서 PR, ② pitfalls의 사고·실습의 이상 동작 → kind 최소 재현을 붙인 이슈 리포트(05·50의 재현 기술), ③ needs-repro 이슈에 재현 붙이기 → 트리아지 기여, ④ "우리 시스템의 exporter가 없다"(03의 노출 형식 지식) → 신규 exporter, ⑤ "이 목적지 output이 없다"(06) → fluent-bit 플러그인, ⑥ 11에서 만난 미지원 라이브러리 → 언어 SIG의 계측 기여, ⑦ 운영자의 관점 → 스펙·컨벤션 텍스트 기여. 실습 노트·SIGNALS-MAP의 "막혔던 곳" 목록이 가장 정직한 기여 백로그입니다.

**A6.** 관심 — 파트에서 재밌었던 모듈이 가리키는 생태계(06~07→fluent, 03·08→prometheus, 04·11·16→OTel, 09·12→grafana, 19·20→프로파일링 계열): 억지는 지속되지 않으므로 1순위 축, 실무와 겹치면 최상(선순환). 역량 — 주력 언어의 경로 매핑(Go=최다 경로, Python/Java/JS=OTel 언어 SIG, C=fluent-bit 코어, TS=Grafana 플러그인, 코드 전이면 문서·재현). 건강 — lab-01 온도표(직접 본 근거: 메인테이너 다양성·외부 PR 처리 속도·good-first-issue 신선도)+49 정찰 시트+관측 특화 체크(플러그인 절차·스펙 정책·외부 머지율). 세 축의 교집합에서 하나를 골라 ADR 형식(재평가 조건 포함)으로 문서화합니다.

**A7.** ① 문서·재현·트리아지: 마찰이 가장 적고(리뷰 부담 소), 커뮤니티에 이름과 신뢰를 만들며, 프로젝트의 실제 흐름(리뷰 문화·절차)을 배우는 저위험 학습 구간. ② 자기 영토(exporter·플러그인·컴포넌트): 독립성이 높아 첫 "작품"의 성취가 빠르고, 유지 응답으로 코드오너급 신뢰를 축적. ③ 본체: 성숙 코어는 설계 논의(proposal)·높은 리뷰 기준이 필요해 신뢰와 도메인 이해가 쌓인 뒤가 효율적. 이 순서는 cncf 50의 "작게 시작해 신뢰를 쌓는" 원리의 관측판이며, 역순(본체부터 크게)은 "석 달 PR"의 공식입니다.

**A8.** 1차(본체에 예고 없이 큰 PR → 표류): 실패의 원인은 실력이 아니라 순서 — 로드맵·proposal 절차 정찰과 사전 타진(이슈·슬랙) 없이 코드부터 던진 것(cncf 49의 교훈 재연). "텃세"가 아니라 절차였습니다. 2차(유행 신생 프로젝트 → 6개월 뒤 동면): 기여 경험 자체는 즐겁고 배움도 있었으나, 정찰(단일 스폰서 리스크 — cncf 45의 패턴) 없이 들어가 상실감 — 신생 기여는 리스크를 알고 배움 중심의 기대로 들어가면 유효한 전략. 3차(3축 선정+잠복+자기 마찰에서 작게 → 머지·코드오너 후보): 성공 공식의 확인 — 관심(실무 계측)×역량(Python)×건강(온도표), 첫 기여는 실무의 미지원 라이브러리, 도메인 지식(11)이 리뷰 대화의 언어, 그리고 운영↔기여의 선순환. 종합: 방법론(정찰→잠복→작게→자기 영토)이 같은 실력의 결과를 가릅니다.
