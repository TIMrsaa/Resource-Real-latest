# 학습 가이드 — 쓰던 도구의 뒷마당으로

## 이 트랙의 전제 — 당신은 이미 자격이 있습니다

24개 모듈을 지나온 지금, 회원님이 가진 것:

```
도메인 지식: 파이프라인의 물리(버퍼·유실), 카디널리티, 상관의 규약,
  샘플링의 수학 — 이 파트의 theory들이 곧 프로젝트들의 설계 문서 수준
실전 경험: 24개 모듈의 실습에서 겪은 마찰들 —
  "문서가 여기서 불친절했다", "이 에러 메시지가 오해를 부른다",
  "이 조합에서 이상했다" — ★ 전부 기여 재료입니다 (cncf 50의 원리)
운영 관점: 프로젝트들이 가장 원하는 기여자 유형 —
  실제로 운영하며 만나는 문제의 보고자
```

cncf 50에서 배운 기여의 길을, 이제 관측이라는 도메인에서 걷습니다.

## 4대 생태계 — 성격이 다른 이웃들

```
fluent (CNCF Graduated):
  fluent-bit(C)·fluentd(Ruby) + 방대한 플러그인 생태
  거버넌스: 메인테이너 중심의 실용적 구조
  특징: ★ 플러그인이 1급 기여 경로 (Go로 output 플러그인도 가능)

prometheus (CNCF Graduated):
  prometheus 본체(Go) + exporter 생태 + client 라이브러리들
  거버넌스: 팀 합의제 (cncf 49 lab-02에서 정찰한 그곳!)
  특징: ★ exporter는 본체 밖 생태 — 진입 장벽이 낮은 자기 영토

open-telemetry (CNCF — 관측 최대 조직):
  스펙 + 언어별 SIG 수십 개 + Collector + 자동 계측
  거버넌스: ★ K8s급 SIG 체계 (GC·TC·SIG 메인테이너)
  특징: 언어만큼 SIG가 있습니다 — 자기 주력 언어의 SIG가 진입로
  Collector contrib: 컴포넌트(receiver/processor/exporter) 단위 기여

grafana 계열 (Grafana Labs 주도 오픈소스):
  grafana·loki·tempo·pyroscope·mimir 등
  거버넌스: ★ 기업 주도 오픈소스 — CNCF 중립형과 다른 모델
  (cncf 49의 "기여자 다양성" 렌즈로 볼 것 — 기여는 활발히 받되
   방향은 기업이 주도하는 구조의 장단을 이해하고 참여)
```

## 기여 지점의 유형 — 이 파트의 경험과 매핑

```
겪은 마찰 → 기여 유형:
  "CRI 파서 문서가 불친절했다"(06) → 문서 PR
  "이 설정 조합에서 이상 동작"(어느 모듈이든) → 재현 이슈 (kind 재현!)
  "우리 시스템의 메트릭 익스포터가 없다" → exporter 신규 (자기 영토)
  "Collector에 이 processor가 있으면"(11) → contrib 컴포넌트 제안
  "우리 언어 자동 계측이 이 라이브러리를 미지원"(11) → 계측 기여
  "Fluent Bit에 이 목적지 output이 없다"(06) → 플러그인
→ cncf 50의 "코드 밖 기여"까지 포함하면 진입로는 넓습니다
```

## 이 모듈의 산출물

lab-02에서 cncf 49의 정찰 시트를 관측 프로젝트에 적용해 **26에서 실제로 걸을 대상 하나**를 고릅니다 — 관심(파트에서 재밌던 모듈)×역량(언어·도메인)×건강(거버넌스·활동)의 교집합. 26이 그 대상으로 빌드·첫 기여까지 갑니다.
