# 학습 가이드 — 사용자에서 만드는 사람으로

## 이 모듈의 특별함 — 검증 가능한 기여

관측을 배운 기여자의 고유한 이점:

```
일반적 기여: 수정 → 테스트 통과 → 제출 (동작의 확인)
관측 기여자: 수정 → 빌드 → ★ 자기 스택으로 관측하며 검증
  "내가 고친 버퍼 설정의 효과를 fluentbit_* 메트릭으로 본다"(06)
  "내가 만든 exporter의 카디널리티를 tsdb_head_series로 확인한다"(03·08)
  "내가 추가한 processor의 오버헤드를 프로파일로 잰다"(20)
→ 이 파트에서 만든 검증 능력이 기여의 품질을 올립니다 —
  PR 설명에 "측정 결과"가 붙는 기여는 리뷰가 빠릅니다
```

## 세 갈래 빌드 — 왜 셋 다 해보나

25에서 하나를 골랐지만, 세 갈래의 빌드를 모두 맛보는 이유:

```
① fluent-bit (C·CMake): 시스템 소프트웨어의 빌드 —
   06에서 판 버퍼·파서가 실제 C 코드로 어디 있는지
② Prometheus·exporter (Go): 관측 생태 최다 언어 —
   특히 exporter 스캐폴드는 "자기 영토"의 출발점
③ OTel Collector (builder 도구): ★ 독특한 조립형 빌드 —
   "필요한 컴포넌트만 담은 나만의 Collector"를 만드는 공식 도구.
   contrib 기여의 개발 루프이자, 실무(경량 커스텀 배포판)에도 유용
```

빌드가 되는 순간 심리적 벽이 무너집니다 — "저 코드"가 "내가 고칠 수 있는 코드"로 바뀝니다(k8s 파트 05-contributor에서 겪은 그 전환의 관측판).

## 개발 루프 — 이 파트의 환경이 그대로 실험실

```
수정 → 빌드 → 컨테이너로 → kind에 배포 → 트래픽 → 관측으로 검증
        (이 파트에서 수십 번 한 그 동선 — 대상만 "내 빌드"로 바뀜)

예: fluent-bit의 어떤 동작을 수정했다면
  06 lab의 구성(tail→필터→output) 그대로에 내 빌드 이미지만 교체
  → 같은 시나리오(로테이션·백프레셔)로 전후 비교
→ 24개 모듈의 실습 자산이 전부 기여 검증 환경이 됩니다
```
