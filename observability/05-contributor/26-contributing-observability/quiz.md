## 정답

**A1.** ① fluent-bit — C·CMake 빌드: 시스템 소프트웨어의 빌드 경험 + 06의 theory(tail·버퍼·kubernetes 필터)가 실제 코드 어디에 있는지 지도 확인(plugins/·src/flb_input_chunk 등). ② Prometheus·exporter — Go(make build·go build): 관측 생태 최다 언어의 개발 루프 + promtool(룰 검증 — 기여이자 실무 도구), exporter 스캐폴드는 "자기 영토"의 출발점. ③ OTel Collector — ocb(builder): 조립형 빌드라는 독특한 모델 — 컴포넌트를 선언해 나만의 Collector를 생성. 셋 다 해보는 이유: 빌드가 되는 순간 "저 코드"가 "고칠 수 있는 코드"로 바뀌는 심리적 전환 + 25의 대상이 어느 갈래든 즉시 착수 가능.

**A2.** ① 실무 용도: contrib 전체 배포판은 수백 컴포넌트로 무겁습니다 — 필요한 receiver/processor/exporter만 담은 경량 커스텀 Collector를 만들어 배포(공격 표면·리소스 절감). ② 기여 용도: 새 컴포넌트 개발의 실험실 — builder 설정에 replace로 로컬 모듈을 끼워 조립·실행하면, contrib에 제출하기 전에 자기 컴포넌트를 실제 Collector 파이프라인에서 개발·검증할 수 있습니다. 11·16에서 쓴 Collector들(ADOT 포함)이 이 조립의 산물이라는 이해까지가 이 도구의 의미입니다.

**A3.** ① 타입의 계약 — "이 숫자는 어떻게 읽히나": 순간값(큐 깊이)은 gauge, 누적(처리 건수)은 counter+_total 접미사(그래야 rate()가 올바로 동작). 질문: "재시작하면 0이 되는 값인가(counter), 오르내리는 값인가(gauge)?" ② 라벨의 유한성 — 질문: "이 라벨의 값이 몇 개까지 갈 수 있나요? unbounded(ID·URL)가 없나요?"(카디널리티=곱셈). ③ 이름의 규약 — 주체_대상_단위(_total) 형식, 단위를 이름에. 이 세 점검이 exporter PR 리뷰에서 실제로 오가는 대화이며, node_exporter의 collector 패키지가 살아 있는 교과서입니다.

**A4.** 파트 내내 밟은 동선 — 빌드/설치 → 이미지 → kind 배포 → 트래픽 → 관측으로 검증 — 의 대상이 "남이 만든 도구"에서 "내가 수정/작성한 코드"로 바뀌는 것. 재사용의 실제: 06의 구성(tail→필터→output)에 내 fluent-bit 빌드 이미지만 교체해 같은 시나리오(로테이션·백프레셔)로 전후 비교, 08의 ServiceMonitor 체계에 내 exporter를 등록해 PromQL로 검증, 11의 Collector 구성에 ocb 빌드를 끼워 텔레메트리(otelcol_*)로 확인 — 24개 모듈의 실습 자산 전체가 기여 검증 환경이 됩니다.

**A5.** 공식: 무엇을(변경 내용) + 왜(이슈·마찰의 맥락) + **어떻게 확인했나(측정)**. 측정의 예: ① 버퍼·파이프라인 수정 → 06 lab-02 시나리오 재현의 전후 dropped/retries/처리율 비교, ② exporter 신규 → 노출 형식 검증 + 카디널리티 계산(시계열 수 견적, 03) 명시, ③ processor 수정 → otelcol_* 메트릭의 처리율·메모리와 프로파일 diff(20)로 오버헤드 증명, ④ 문서 수정 → "이 절차로 kind에서 실제 재현/해결됨" 로그 첨부. 측정이 붙은 PR은 리뷰어의 검증 부담을 덜어 빠르게 흐릅니다 — 이 파트 전체가 그 측정 능력의 훈련이었다는 것이 26의 관점입니다.

**A6.** 절차: 제안 이슈(무엇을 왜) → **Sponsor 확보**(기존 코드오너/승인자의 지지 — 유지·리뷰를 함께할 후견) → 스켈레톤 PR(뼈대만) → 기능 PR(분할 제출이 관례). "바로 코드 금지"인 이유: contrib는 수백 컴포넌트의 유지 부담을 안고 있어, 방향(중복·설계·유지 계획)의 합의 없이 온 큰 코드는 리뷰 자원을 배정받지 못하고 표류합니다(cncf 49의 "석 달 PR" 구조) — Sponsor 절차가 그 합의를 제도화한 것이며, 분할 제출은 "작게"(50)의 구조화입니다.

**A7.** 무게: 관측 도구들은 형식·프로토콜의 계약(03의 노출 형식, OTel 스펙·시맨틱 컨벤션, remote_write, CRI 로그 포맷) 위에 생태계 전체가 서 있습니다 — 기본 동작·형식의 변경은 수많은 하위 시스템을 깨뜨릴 수 있어 하위 호환성 심사가 엄격합니다. 올바른 접근: 동작 변경은 opt-in 옵션으로 추가하고 기존 기본값을 보존, 제거는 deprecation 절차(경고→유예→제거)를 따르며, 스펙 영역이면 구현 전에 스펙 저장소·이슈에서 방향을 확인합니다(컨벤션도 그렇게 자랍니다 — cncf 12). "더 낫다"는 확신보다 "무엇이 깨지나"의 조사가 먼저입니다.

**A8.** ① 재현 먼저: "버그인지 설정인지" 불확실한 상태에서 PR이 아니라 kind 최소 재현부터 — 닫힌 이슈("재현 불가") 2건을 자기 재현으로 되살려 하루 만에 메인테이너 반응(첫 기여는 코멘트였습니다 — 유명한 곳에 큰 것부터의 함정 회피). ② 의사 표시와 방향 합의 후 착수("제가 해볼까요") — 예고 없는 코드 던지기(49의 표류) 회피. ③ 12줄 수정에서 주변 리팩터링 유혹을 별도 이슈로 분리 — 한 PR 한 가지(함정 2 회피). ④ 측정이 붙은 PR — 전후 비교(중복 0·dropped 불변·처리율 ±1%)와 회귀 테스트로 리뷰 2라운드 머지(함정 3 회피). ⑤ 머지 후 같은 영역의 재현·검증 코멘트를 지속해 트리아저로 — 잠적(함정 5) 대신 유지·축적, 그리고 실무와의 선순환. 종합: 방법(재현→합의→작게→측정→지속)이 첫 기여를 사다리의 첫 칸으로 만들었습니다.
