## Step 3 — 첫 기여 실행 (형태별 경로)

### 경로 A: 문서 (가장 확실한 시작)

```
□ 파트에서 실제로 헤맨 문서 지점 하나 (예: 06의 멀티라인 설정,
  11의 언어별 주입 예시, 08의 매칭 3연쇄 설명)
□ 개선 문안 작성 — "내가 몰랐던 것을 그때의 나에게" 기준
□ 검증: 그 문서대로 kind에서 재현되는가 (lab-01 환경!)
□ PR: 작게, DCO(-s), "왜"(어디서 막혔었는지)를 설명에
```

### 경로 B: 재현 이슈 (운영자의 무기)

```
□ 파트 실습에서 만난 이상 동작(또는 pitfalls급 시나리오의 실제 재현)
□ kind 최소 재현 만들기 — 매니페스트·설정·재현 명령을 통째로
  (05·이 파트 전체의 재현 기술이 여기서 무기)
□ 기존 이슈 검색 → 있으면 재현을 코멘트로(그것도 기여!) /
  없으면 템플릿대로 신규 (버전·기대vs실제·재현·로그)
```

### 경로 C: 작은 코드 수정

```
□ good-first-issue 또는 자기 재현 이슈에서
□ "I'd like to work on this" → 응답 후 시작
□ 수정 + 테스트 + ★ 측정 (theory 5절 — 전후 비교를 PR에)
□ lab-01의 개발 루프로 검증 후 제출
```

### 경로 D: 자기 영토의 첫 삽 (exporter·플러그인·컴포넌트)

```
□ 중복 확인 (기존 목록·contrib 디렉터리)
□ 설계 메모: 03(메트릭 설계)·06(파이프라인)·11(컴포넌트) 규율 적용
□ contrib면: 제안 이슈 → Sponsor 절차 확인 (바로 코드 금지!)
□ 독립(exporter·FB Go 플러그인)이면: lab-01 스캐폴드에서 시작 —
  작동하는 최소를 만들어 공개, 등록(exporter 목록 등)은 성숙 후
□ ★ 유지 계획 한 줄 (25의 책임)
```

## Step 4 — 제출과 그 후 (50의 예절)

```
□ PR/이슈 제출 — 템플릿 성실히, CI 실패는 스스로 수정
□ 리뷰 대응: 감사·신속·방어 금지 (지적은 코드에 대한 것)
□ 1~2주 무응답 시 정중한 ping → 채널에서 리뷰 요청
□ 머지되면: 축하 — 그리고 다음 이슈로 (꾸준함이 사다리)
□ 거절/방향 불일치면: 배움을 기록하고 다음 재료로 (개인화 금지)
```
