# 학습 가이드 — 컨트롤러는 전부 "조정 루프 + 책임 분리"다

## 구조 먼저

```
Deployment      "버전 관리자"   — 업데이트/롤백 담당. ReplicaSet을 만듭니다
   └─ ReplicaSet  "인원수 반장" — 개수 유지만 담당. Pod를 만듭니다
        └─ Pod × N
```

왜 2단이 아니라 3단인가요? **책임 분리** 때문입니다. "개수 유지"(RS)와 "버전 교체"(Deployment)를 분리하면, 롤링 업데이트가 "옛 RS 줄이고 새 RS 늘리기"라는 단순한 산수가 됩니다. 이 구조를 모르면 `kubectl get rs` 출력(이전 버전 RS들이 0개로 남아있는 것)이 영원히 미스터리로 남습니다.

## 학습 전략

1. lab-01의 **파괴 실험이 본체**입니다. Pod를 직접 죽이고, 라벨을 떼보고, 컨트롤러가 어떻게 반응하는지 관찰하세요. "라벨을 떼면 어떻게 될까요?"를 먼저 예상하고 실행할 것.
2. 롤링 업데이트는 `kubectl get rs -w`로 **두 RS의 숫자가 교차하는 순간**을 봐야 이해됩니다. 문서 그림 100번보다 한 번의 관찰.
3. selector와 label의 관계는 이후 Service(모듈 05), 모든 컨트롤러에서 반복되는 **K8s의 연결 문법**입니다. 여기서 확실히.

## 미리 답해두는 질문

- "DaemonSet은 왜 replicas가 없나요?" — 복제 수가 아니라 **"노드마다 1개"** 가 계약이라서. 노드가 늘면 따라 늡니다.
- "StatefulSet은요?" — 상태(고유 ID/디스크)가 필요한 워크로드용. 중급 모듈 19에서. 지금은 "무상태 앱 = Deployment"만 확실히.
