# 학습 가이드 — 스토리지의 3분할이 풀려는 문제

## 왜 PV/PVC/StorageClass 3개나 되나

초심자의 불만: "그냥 Pod에 디스크 달면 되지 왜 리소스가 3개야?" — 역할(사람)이 다르기 때문입니다:

```
개발자        "10GB 필요해요. 빠른 걸로요"          → PVC (신청서)
인프라 관리자  "우리 회사 디스크 종류는 이것들"        → StorageClass (메뉴판)
시스템        "신청 들어왔네, EBS 하나 만들어 연결"    → PV (실물, 자동 생성)
```

개발자는 **EBS가 뭔지 몰라도** PVC만 쓰면 되고, 인프라팀은 디스크 정책(타입/암호화/확장 가능 여부)을 StorageClass에 한 번만 정의합니다. 클라우드를 옮겨도 PVC YAML은 그대로 — 추상화의 목적이 이식성과 분업입니다.

## 수명(lifetime)으로 분류하면 전부입니다

| 볼륨 | 데이터 수명 | 용도 |
|------|------------|------|
| emptyDir | = Pod | 캐시, 컨테이너 간 공유(모듈 03에서 사용) |
| hostPath | = 노드 | 노드 에이전트 전용 (앱에는 금지) |
| PVC(EBS 등) | = PVC/정책 | DB, 업로드 파일 — 진짜 데이터 |

lab-01에서 앞 두 개의 수명을 **죽여보며** 확인하고, lab-02에서 PVC만 살아남는 것을 봅니다.

## EKS 맥락 미리 알기

- K8s에 EBS 코드가 내장돼 있던 시대(in-tree)는 끝났습니다. 지금은 **CSI 드라이버**(표준 플러그인)를 설치해야 합니다 — lab-02에서 EKS 애드온으로 설치.
- EBS는 **AZ에 묶입니다**: 볼륨이 2a에 만들어지면 Pod도 2a 노드에만 뜰 수 있습니다. `WaitForFirstConsumer`가 이 순서 문제를 푸는 장치 — theory에서 자세히.
