# 이론 — 컨테이너의 정체: namespace, cgroup, 이미지, OCI

> **🌱 17세 눈높이 비유: 컨테이너는 "독서실 칸막이 좌석"입니다**
> 가상머신(VM)이 **집을 한 채 더 짓는 것**이라면, 컨테이너는 **한 건물 안에 칸막이 좌석을 만드는 것**입니다.
> 칸막이 좌석에 앉으면 옆자리가 안 보이고(=namespace, 시야 격리), 좌석마다 "콘센트는 1개만, 책상은 이만큼만" 규칙이 있습니다(=cgroup, 자원 제한).
> 하지만 건물(커널)은 하나입니다. 그래서 집 짓기(VM 부팅, 수 분)보다 칸막이 설치(컨테이너 시작, 수 밀리초)가 압도적으로 빠릅니다.

---

## 1. 충격적인 사실부터: 컨테이너라는 것은 없습니다

리눅스 커널 소스코드에는 "container"라는 타입이 없습니다. 컨테이너는 **커널의 격리 기능 몇 개를 조합해서 실행한 평범한 프로세스**에 붙인 별명일 뿐입니다.

```
"컨테이너" = 리눅스 프로세스
             + namespace  (다른 프로세스/네트워크/파일이 안 보이게)
             + cgroup     (CPU/메모리를 이만큼만 쓰게)
             + 격리된 루트 파일시스템 (이미지에서 온 파일들)
```

호스트에서 `ps aux`를 치면 컨테이너 안의 프로세스가 **그냥 보입니다**. lab-01에서 직접 확인합니다.

## 2. Namespace — "무엇이 보이는가"를 격리

namespace는 프로세스에게 **세상의 일부만 보여주는 커널 기능**입니다. 종류별로 가리는 대상이 다릅니다:

| Namespace | 격리 대상 | 컨테이너 안에서 보이는 것 |
|-----------|----------|--------------------------|
| **PID** | 프로세스 목록 | 자기가 PID 1, 다른 프로세스 안 보임 |
| **NET** | 네트워크 | 자기만의 IP, 포트, 라우팅 테이블 |
| **MNT** | 마운트(파일시스템) | 자기만의 / (루트 디렉터리) |
| **UTS** | 호스트네임 | 자기만의 hostname |
| **IPC** | 프로세스 간 통신 | 자기만의 공유메모리 |
| **USER** | 사용자 ID | 안에선 root(0), 밖에선 일반 유저로 매핑 가능 |
| **CGROUP** | cgroup 뷰 | 자기 cgroup만 보임 |
| **TIME** | 시계 | 부팅 시각 오프셋 (최신 커널) |

> **💡 핵심 통찰**: 나중에 배울 **Pod의 정의가 바로 "namespace를 공유하는 컨테이너 그룹"** 입니다. 같은 Pod의 컨테이너들이 `localhost`로 서로 통신할 수 있는 이유 = **NET namespace를 공유**하기 때문. 이 한 줄이 모듈 03(Pod)의 절반입니다.

```
호스트 커널 (단 하나)
├── namespace 세트 A  ←  컨테이너 1 (nginx)    : "나는 PID 1이고 IP는 10.0.0.5야"
├── namespace 세트 B  ←  컨테이너 2 (redis)    : "나는 PID 1이고 IP는 10.0.0.6이야"
└── (기본 namespace)  ←  호스트의 일반 프로세스들: 위 둘 다 그냥 프로세스로 보임
```

## 3. Cgroup — "얼마나 쓸 수 있는가"를 제한

cgroup(control group)은 프로세스 그룹의 **자원 사용량을 측정하고 제한**하는 커널 기능입니다. 현재 표준은 **cgroup v2** (K8s는 1.31부터 v1을 유지보수 모드로 전환).

| 제어 항목 | 예시 |
|-----------|------|
| CPU | "이 그룹은 CPU 0.5개까지" (`cpu.max`) |
| 메모리 | "512MiB 넘으면 OOM kill" (`memory.max`) |
| PID 수 | fork 폭탄 방지 (`pids.max`) |
| I/O | 디스크 읽기/쓰기 속도 제한 |

> **🌱 비유**: 스마트폰의 "앱별 데이터 사용량 제한"과 같습니다. 앱(프로세스)은 자기가 제한당하는지도 모른 채 쓰다가, 한도에 도달하면 차단당합니다.
>
> **💡 K8s 연결**: Pod YAML의 `resources.limits.memory: 512Mi` 가 **바로 이 cgroup 파일에 512Mi를 적는 행위**입니다. K8s에서 OOMKilled를 만나면 커널 cgroup이 죽인 것입니다.

## 4. 컨테이너 이미지 — 읽기 전용 레이어의 겹침

이미지는 "프로그램 + 그 실행에 필요한 모든 파일"을 **레이어(층)** 로 쌓은 묶음입니다.

```
Dockerfile                          이미지 레이어 (각 층은 읽기 전용)
─────────────────                   ─────────────────────────────────
FROM python:3.13-slim          →    [레이어 1] 데비안 최소 파일들 + 파이썬
COPY requirements.txt .        →    [레이어 2] requirements.txt 한 개
RUN pip install -r requirements.txt →  [레이어 3] 설치된 라이브러리들
COPY app.py .                  →    [레이어 4] app.py 한 개

컨테이너 실행 시:
                                    [쓰기 가능 레이어]  ← 컨테이너가 만드는 변경은 전부 여기
                                    [레이어 4] ┐
                                    [레이어 3] ├ 읽기 전용 (모든 컨테이너가 공유)
                                    [레이어 2] │
                                    [레이어 1] ┘
```

> **🌱 비유: 투명 필름(OHP) 겹치기.** 맨 아래 필름에 지도가 그려져 있고, 그 위에 도로 필름, 그 위에 상점 필름을 겹치면 하나의 완성된 그림으로 보입니다. 원본 필름은 아무도 못 고치고, 내가 메모하고 싶으면 **내 빈 필름을 맨 위에 한 장 얹어서** 거기에만 씁니다. 그 빈 필름이 컨테이너의 쓰기 레이어입니다. 컨테이너를 지우면 그 필름만 버려집니다 — **그래서 컨테이너 안에 저장한 데이터는 사라집니다** (해결책은 모듈 08 스토리지).

이 겹침을 실제로 구현하는 것이 **overlayfs** 같은 유니온 파일시스템입니다. 효과:

- **공유**: nginx 이미지로 컨테이너 100개를 띄워도 읽기 레이어는 디스크에 1벌
- **캐시**: Dockerfile에서 안 바뀐 줄까지의 레이어는 재빌드 안 함 (빌드 속도의 핵심)
- **배포 효율**: 이미 받은 레이어는 다시 안 받음 (`docker pull` 시 "Already exists")

## 5. OCI — 컨테이너의 국제 표준 규격

> **🌱 비유**: 화물 컨테이너가 전 세계 어느 항구·배·트럭에도 실리는 이유는 **크기 규격이 국제 표준**이기 때문입니다. 소프트웨어 컨테이너도 똑같은 일을 OCI(Open Container Initiative)가 했습니다.

| OCI 스펙 | 내용 | 대표 구현 |
|----------|------|----------|
| **Image Spec** | 이미지 포맷 (레이어, 매니페스트, config) | docker build, buildkit, kaniko |
| **Runtime Spec** | "이 config.json대로 프로세스를 격리 실행하라" | **runc**, crun, kata, gVisor |
| **Distribution Spec** | 레지스트리 푸시/풀 API | Docker Hub, **ECR**, Harbor |

그래서 이런 호환이 성립합니다:

```
docker build로 만든 이미지
  → ECR에 푸시 (Distribution Spec)
  → EKS 노드의 containerd가 풀 (Image Spec)
  → runc가 실행 (Runtime Spec)
```

**Docker 없이도 K8s는 잘 돕니다.** K8s 1.24에서 dockershim이 제거된 뒤 노드 런타임은 containerd/CRI-O가 표준이고, Docker는 "개발자 PC에서 이미지를 만들고 실행해보는 도구"의 위치입니다. 둘 다 내부적으로는 같은 runc를 씁니다.

```
[개발 PC]  docker CLI ─→ dockerd ─→ containerd ─→ runc ─→ 컨테이너
[K8s 노드] kubelet ──── CRI ─────→ containerd ─→ runc ─→ 컨테이너
                                     (같은 엔진!)
```

## 6. VM vs 컨테이너 — 정확한 비교

```
        VM                                  컨테이너
┌─────────────────┐              ┌──────────────────────────┐
│  앱             │              │ 앱   │ 앱   │ 앱          │
│  게스트 OS(커널!)│  ← 통째로    ├──────┴──────┴──────────── │
│  가상 하드웨어   │     복제     │  컨테이너 런타임           │
├─────────────────┤              ├──────────────────────────┤
│  하이퍼바이저    │              │  호스트 OS 커널 (공유!)    │
│  호스트 OS      │              │                          │
└─────────────────┘              └──────────────────────────┘
부팅: 분 단위                      시작: 밀리초 단위
격리: 강함 (커널 분리)              격리: 상대적으로 약함 (커널 공유)
크기: GB 단위                      크기: MB 단위
```

- 격리가 약하다는 것의 의미: 커널 취약점이 뚫리면 컨테이너 탈출이 가능 → 그래서 보안 민감 환경은 Kata Containers(경량 VM)나 gVisor를 씁니다 (모듈 32와 cncf 파트에서).
- EKS 노드는 사실 "VM 위에서 컨테이너를 돌리는" 구조입니다 — 두 기술은 적이 아니라 겹쳐 쓰는 관계.
