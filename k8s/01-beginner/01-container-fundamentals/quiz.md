# 자가 점검 퀴즈

**Q1.** 컨테이너와 VM의 가장 근본적인 차이 한 가지는?

**Q2.** 같은 Pod 안의 컨테이너들이 `localhost`로 통신할 수 있는 이유를 namespace 용어로 설명하세요.

**Q3.** Pod에 `resources.limits.memory: 256Mi`를 설정했습니다. 이 값은 리눅스의 어떤 메커니즘의 어떤 파일에 반영되는가요? 초과 시 무슨 일이 일어나는가요?

**Q4.** `docker build`를 두 번 연속 실행하면 두 번째가 순식간에 끝나는 이유는?

**Q5.** 컨테이너 안에서 만든 파일이 컨테이너 삭제 후 사라지는 이유를 레이어 구조로 설명하세요.

**Q6.** "K8s 1.24부터 Docker를 못 쓴다"는 말은 어디까지 맞고 어디부터 틀렸나요?

**Q7.** exit code 137의 의미는?

---

## 정답

**A1.** VM은 게스트 **커널을 통째로** 별도 실행하지만, 컨테이너는 **호스트 커널을 공유**하는 격리된 프로세스입니다. (그래서 시작 속도/밀도에서 유리하고, 격리 강도에서 불리)

**A2.** 같은 Pod의 컨테이너들은 **NET namespace를 공유**합니다. 같은 네트워크 스택(IP, 포트 공간)을 쓰므로 서로가 localhost입니다.

**A3.** **cgroup(v2)** 의 `memory.max` 파일에 바이트 값으로 기록됩니다. 초과 시 커널 OOM killer가 프로세스를 SIGKILL → Pod 상태에 `OOMKilled` 표시.

**A4.** 레이어 캐시. Dockerfile의 각 지시는 레이어를 만들고, 입력(명령/파일)이 안 바뀐 지시는 캐시된 레이어를 재사용합니다.

**A5.** 이미지 레이어는 전부 읽기 전용이고, 변경 사항은 컨테이너별 **쓰기 가능 레이어**에만 기록됩니다. 컨테이너 삭제 = 그 쓰기 레이어 삭제.

**A6.** 맞는 부분: K8s **노드의 런타임**으로 dockershim이 제거되어 kubelet이 Docker 데몬과 직접 통신하지 않습니다. 틀린 부분: `docker build`로 만든 이미지는 OCI 표준이므로 containerd가 그대로 실행합니다 — 개발 도구로서 Docker는 여전히 유효합니다.

**A7.** 128 + 9(SIGKILL). 컨테이너가 SIGKILL로 강제 종료됨 — 대부분 cgroup 메모리 한도 초과(OOM kill)가 원인.
