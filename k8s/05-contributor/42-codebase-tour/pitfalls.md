# 흔한 함정 5선

## 1. 목적 없는 통독 시도

"pkg/를 처음부터 읽겠다" — 3일 안에 번아웃. 코드 읽기는 항상 질문 주도("X는 어디서/어떻게?")여야 하고, 질문에 답할 만큼만 읽고 **멈추는 것**도 기술입니다. 원정 노트에 답을 적는 순간 그 원정은 끝.

## 2. vendor/와 staging의 중복에 혼란

같은 코드가 `vendor/k8s.io/client-go`와 `staging/src/k8s.io/client-go` 두 곳에 보입니다 — **staging이 원본**, vendor는 빌드용 사본(staging을 가리키는 symlink)입니다. 검색할 때 `--include`나 경로 지정으로 한쪽만 보라. 안 그러면 모든 검색 결과가 2배로 나와 길을 잃습니다.

## 3. 거대 함수에서 한 줄씩 정독

syncDeployment류는 수백 줄 — 한 줄씩 읽으면 미아가 됩니다. 전술: ① 함수의 **분기 골격**만 먼저 (if/switch와 호출되는 함수 이름들) ② 질문과 관련된 분기만 파고들기 ③ 나머지는 "이런 게 있다"로 표시만. 코드 독해는 DFS가 아니라 **가지치기 있는 BFS**입니다.

## 4. 옛 블로그/글의 코드 위치를 그대로 믿기

K8s 코드는 계속 이사합니다(파일 분리, 패키지 개편). "2022년 글에서 schedule_one.go가..."는 지금 다를 수 있습니다 — **글의 경로가 아니라 글의 키워드로 현재 리포를 grep** 하세요. `git log --follow`로 파일의 이사 이력도 추적 가능.

## 5. 코드만 보고 "왜"를 추측

"왜 이렇게 짰지?"를 코드만 보며 고민 — 답은 보통 코드 밖에 있습니다: `git log -S`로 그 줄을 만든 커밋 → 커밋 메시지의 PR 번호 → PR 논의 → (크면) KEP 링크. **K8s는 모든 설계 결정이 문서 사슬로 남는 프로젝트**입니다(모듈 43). 추측 30분보다 git 고고학 5분.

## 실무(기여) 사고 사례

> 한 입문자가 "Deployment가 가끔 옛 RS를 안 지운다"는 이슈를 잡겠다며 syncDeployment 전체를 2주간 정독 — 끝내 원인을 못 찾았습니다. 멘토의 접근: 증상 키워드("revisionHistoryLimit", "cleanup")로 grep → `cleanupDeployment` 함수 발견(10분) → 그 함수의 테스트를 읽고 경계 조건 파악(30분) → 단위 테스트로 재현(1시간) → 원인은 정렬 안정성 가정 하나. 교훈: **입구는 통독이 아니라 증상 문자열이고, 이해의 지름길은 테스트입니다.**
