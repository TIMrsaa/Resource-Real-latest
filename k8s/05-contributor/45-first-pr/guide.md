# 학습 가이드 — 첫 PR의 목표는 "작게 성공하기"다

## 야망을 줄여라 (진심입니다)

첫 PR로 멋진 기능을 꿈꾸기 쉽습니다 — 실패 공식입니다. 첫 PR의 진짜 목표:

```
기술적 성과:   사소해도 됨 (문구 수정, 테스트 추가, 작은 버그)
절차적 성과:   fork→PR→CI→리뷰→머지의 전 과정을 한 번 완주  ★ 이게 전부
사회적 성과:   "절차를 아는 사람"이라는 첫 평판
```

전 과정을 한 번 완주하면 두 번째부터는 **기술 난이도만** 남습니다. 거꾸로 첫 PR이 크면: 리뷰 수십 회 왕복 → 수개월 → 지쳐서 포기 — 가장 흔한 탈락 코스입니다.

## 좋은 첫 이슈의 조건

| 조건 | 이유 |
|------|------|
| `good first issue` 라벨 | 멘토링을 전제로 큐레이션된 것 |
| 아무도 /assign 안 함 + 최근 활동 없음 | 선점/중복 방지 |
| 재현/수정 범위가 이슈에 이미 명확 | 설계 논쟁 없이 실행만 |
| 본체 외 리포도 고려 (kind, kubectl 플러그인, website/docs) | 리뷰가 빠르고 경쟁 덜함 |

**문서(kubernetes/website) 기여를 무시하지 마세요** — 같은 절차(prow, 리뷰, OWNERS)를 더 빠른 호흡으로 경험할 수 있고, 한국어 번역(ko/) 영역은 한국어 사용자의 홈그라운드입니다.

## 호흡에 대하여

첫 PR은 **며칠~몇 주짜리 프로젝트**입니다 (리뷰어도 자원봉사자입니다). 이 모듈을 "하루에 끝내는 실습"으로 여기지 말고, lab-01·02를 절차서 삼아 실전을 병행하세요. 방치된 것 같아도 초조해하지 말 것 — 대응법은 theory에 있습니다.

## 이 커리큘럼 전체와의 관계

45개 모듈의 설계 목표가 이 순간이었습니다: 동작 원리(이론) → 내부 해부(고급) → 운영(실무) → **생산자(기여자)**. 첫 PR이 머지되는 순간, kubernetes는 "배우는 대상"에서 "함께 만드는 프로젝트"가 됩니다.
