# 자가 점검 퀴즈

**Q2.** KEP이 필요한 변경과 필요 없는 변경의 경계는?

**Q3.** KEP README에서 정보 밀도가 가장 높은 두 섹션과 그 이유는?

**Q4.** 기능의 일생(KEP→GA)을 feature gate와 묶어 설명하세요.

**Q5.** kep.yaml에서 30초 안에 읽어낼 수 있는 4가지는?

**Q6.** "이 기능 왜 이런 모양이지?"의 답을 찾는 3단 경로는?

**Q7.** PR 접수의 행정적 전제 조건과, 미리 해야 하는 이유는?

**Q8.** 한국 시간대 기여자의 현실적인 SIG 참여 방법 3가지는?

---

## 정답

**A1.** SIG = 영역별 **상설** 조직(차터/리더/회의/채널 보유), WG = SIG 횡단 **한시** 조직(목적 달성 시 해산). 주인 찾기: 코드 디렉터리의 OWNERS 파일 → `labels: sig/xxx` → community 리포의 해당 SIG 디렉터리.

**A2.** API 변경, 사용자 가시 동작 변경, 기본값 변경, 새 기능 등 "사소하지 않은" 것은 KEP 필요. 버그 수정, 문구/문서, 리팩터링, 테스트 추가는 일반 PR로 충분. 애매하면 SIG에 먼저 질문.

**A3.** **Non-Goals**(범위의 경계 — 무엇을 의도적으로 안 하는지가 설계 이해의 핵심)와 **Alternatives**(검토 후 버린 설계와 이유 — 재제안 방지 + 설계 감각 학습).

**A4.** KEP 승인 → feature gate(기본 off) 뒤에서 구현 → **Alpha** 출시(gate 수동 on) → Graduation Criteria 충족 시 **Beta**(대부분 기본 on) → 운영 검증 후 **GA**(gate 제거 수순). 각 승격 조건이 KEP에 명문화되어 있고, 결함 시 후퇴도 가능.

**A5.** ① owning-sig(주인) ② stage(현재 단계) ③ latest-milestone(단계 변경 버전) ④ feature gate 이름. (= 기능의 주민등록증)

**A6.** ① 코드에서 gate 이름 확인(pkg/features) ② enhancements 리포에서 그 이름으로 KEP 검색 ③ KEP의 Motivation/Alternatives에서 설계 의도 — 필요하면 원 이슈/승격 PR의 논의까지.

**A7.** **CLA 서명** — 미서명이면 봇이 PR을 차단(cncf-cla: no). 개인은 몇 분이지만 회사 소속(CCLA)은 법무 절차로 수 주 걸릴 수 있어, PR 만들기 전(지금) 해두어야 흐름이 안 끊깁니다.

**A8.** ① 회의 녹화(YouTube)와 회의록으로 비동기 참관 ② 결정이 기록되는 이슈/PR/KEP에 코멘트로 참여(1급 참여입니다) ③ Slack은 시간대 무관 — 질문은 공개 채널에 맥락과 함께. (회의 출석은 참여의 필요조건이 아닙니다)
