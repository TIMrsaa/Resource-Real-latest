# 흔한 함정 5선

## 1. KEP 없이 큰 변경 PR

"코드로 보여주면 되겠지"라며 API 변경급 PR을 바로 — 정중히 닫히고 "KEP부터"라는 답을 받습니다. 사소하지 않은 변경(API/동작/기본값)은 **설계 합의가 먼저**입니다. 거꾸로 활용하면: 내 아이디어가 KEP감인지 애매하면 SIG Slack에 먼저 물어보세요 — 5분 대화가 2주 헛수고를 막습니다.

## 2. 이미 결정된 역사를 모르고 재제안

"왜 sidecarContainers 필드가 따로 없죠? 만들어 올게요" — Alternatives에서 이미 검토·기각된 설계입니다. 제안 전 **고고학(lab-01) 먼저**: enhancements 리포 검색 + 관련 이슈의 과거 논의. "검토했던 것을 아는 사람"과 "모르는 사람"의 제안은 같은 내용이라도 대접이 다릅니다.

## 3. 질문을 DM으로

리더/리뷰어에게 개인 DM으로 질문 — 대부분 무응답이거나 "채널에 올려달라"는 답. 공개 채널이 규칙인 이유: 답변이 모두의 검색 자산이 되고, 한 사람에게 부담이 안 쏠립니다. 답을 빨리 받는 기술은 DM이 아니라 **좋은 질문**(맥락+시도한 것+구체적 물음)입니다.

## 4. 회의 시간대 좌절

SIG 회의가 대부분 미국 시간(한국 새벽)이라 "참여 불가능"이라 단정 — 회의는 녹화·회의록이 전부 공개되고, **결정은 결국 이슈/PR에 글로** 남습니다. 비동기 참여(회의록 읽기, 이슈 코멘트)가 1급 참여입니다. 실제로 많은 비미주 기여자가 회의 없이 활동합니다.

## 5. CLA를 PR 직전에

첫 PR을 올리고 나서야 CLA 미서명 발견 — 회사 소속이면 법무 승인까지 수 주가 걸릴 수 있습니다. PR의 흥분이 식는 동안 이슈는 남이 가져갑니다. **행정은 미리**(lab-02를 지금 한 이유). 회사 업무로 기여한다면 소속 회사의 CCLA 여부부터 확인.

## 실무(기여) 사고 사례

> 어느 기여자가 kubelet에 좋은 아이디어가 있어 3주간 구현해 1,500줄 PR을 올렸습니다. 결과: "흥미롭지만 이 방향은 KEP #XXXX에서 다른 설계로 합의됨 + 이 규모는 KEP 필요"로 클로즈. 낙담했지만 멘토의 조언대로 다시: 해당 KEP의 논의에 자기 사용 사례를 코멘트 → SIG 회의 안건에 채택 → 기존 설계에 자기 요구를 반영시키고 **그 구현의 일부를 맡았습니다**. 교훈: 오픈소스에서 코드는 마지막 수단입니다 — **맥락 파악(고고학) → 대화 → 합의 → 코드** 순서가 결국 가장 빠릅니다.
