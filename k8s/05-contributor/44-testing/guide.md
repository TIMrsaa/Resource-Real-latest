# 학습 가이드 — 기여의 절반은 테스트입니다

## 관점 전환: 테스트는 "증명서"다

혼자 짜는 코드에서 테스트는 선택이었을지 모릅니다. 수천 명이 같은 코드를 만지는 K8s에서 테스트는 **소통 수단**입니다:

- 리뷰어에게: "이 변경은 이 경우들을 보장합니다" (말 대신 코드로)
- 미래 기여자에게: "이 동작은 의도된 것이니 깨뜨리지 마시오" (회귀 방지)
- 나에게: 빌드 사다리의 1단 — 가장 싼 검증 (모듈 41)

그래서 K8s의 PR 관례: **버그 수정 PR = (실패하는) 테스트 + 수정**이 한 세트. 테스트 없는 수정은 "정말 고쳐졌는지, 다시 안 깨질지"를 증명할 수 없습니다.

## 3층 구조 미리보기

```
e2e          진짜 클러스터에서 사용자 시나리오     느림/비쌈 — CI가 주로
integration  진짜 etcd+API서버, 가짜 노드        중간 — 컴포넌트 상호작용
unit         함수/패키지 단위, fake client       빠름/공짜 — 우리의 주력 ★
```

입문 기여(45)의 99%는 unit 레벨로 충분합니다 — integration/e2e는 "읽고 돌릴 줄 알면" 됩니다.

## 이미 아는 것들의 재조립

- 모듈 31의 fake client 감각 → unit 테스트의 핵심 도구가 그것
- 모듈 42의 "테스트로 이해" 전술 → 이번엔 이해를 넘어 **작성**
- 모듈 20의 Job/멱등성 사고 → 좋은 테스트의 조건(독립적, 반복 가능)과 동형

## 한 가지 마음가짐

K8s 테스트 코드는 양이 본체 코드급입니다 — 전부 이해하려 들지 말고, **내가 만질 패키지의 테스트 스타일을 모방**하는 것부터. 오픈소스에서 독창적인 테스트 스타일은 미덕이 아닙니다 (리뷰어가 익숙한 모양이 미덕입니다).
