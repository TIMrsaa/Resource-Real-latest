# 자가 점검 퀴즈

**Q1.** 테스트 3층을 "무엇이 진짜인가"로 구분하고 각 층의 실행 비용을 말하세요.

**Q2.** table-driven 테스트가 K8s 표준인 이유와, 버그 수정 PR에서의 활용 형태는?

**Q3.** fake client가 검증할 수 있는 것과 없는 것의 경계는?

**Q4.** "테스트를 먼저 쓰고 FAIL을 확인"하는 순서가 증명하는 것은?

**Q5.** integration 테스트가 기동하는 것과, 그 층에서만 잡히는 버그의 예는?

**Q6.** `[Conformance]` 라벨의 의미와 EKS와의 관계는?

**Q7.** PR의 CI가 빨갈 때의 표준 절차 4단계는?

**Q8.** 테스트에서 `time.Sleep`이 금기인 이유와 대안은?

## 정답

**A1.** unit: 전부 가짜(fake client, 메모리) — 초. integration: API 서버+etcd **진짜**, 노드 가짜 — 분. e2e: 노드까지 진짜(실 클러스터) — 수십 분+. 버그는 잡을 수 있는 가장 낮은 층에서.

**A2.** 케이스 추가가 "표에 한 줄"이라 명세가 한눈에 보이고 리뷰/확장이 쉽습니다. 버그 수정 PR의 정석: **표에 버그 재현 케이스 추가(FAIL) + 코드 수정(PASS)** — 한 PR에 증거와 치료가 함께.

**A3.** 가능: 내 로직이 어떤 API 호출을 하는가(Actions 검증), 객체 입출력 처리. 불가능: admission/검증(strategy)/기본값/낙관적 동시성 등 **API 서버의 실제 반응** — 그건 integration의 영역.

**A4.** "이 테스트가 이 버그를 실제로 잡는다"는 사실. FAIL 없이 추가된 테스트는 원래부터 통과하는(버그와 무관한) 것일 수 있어 회귀 방지 능력이 증명되지 않습니다.

**A5.** 테스트 프로세스 안에서 진짜 etcd + API 서버를 기동. 예: GC의 cascade 삭제(컨트롤러-API 상호작용), admission 거부 동작, 검증/기본값 적용 — fake에선 전부 통과해버리는 것들.

**A6.** 모든 인증(Certified) Kubernetes 배포판이 통과해야 하는 핵심 계약 테스트 모음. EKS도 이 Conformance를 통과해 인증받은 배포판입니다 — 우리가 배운 동작들이 어디서나 같았던 이유.

**A7.** ① 실패 로그에서 어떤 테스트가 왜 죽었나 ② 내 변경과의 관련성 판단 ③ 무관해 보이면 testgrid에서 그 테스트의 평소 성적(flake 여부) ④ 그 후 /retest 한 번 — 반복되면 멈추고 원인 규명(또는 flake 이슈 검색/보고).

**A8.** 머신 속도에 따라 통과/실패가 갈리는 **flake의 제조법**이라서. 대안: 조건 충족까지 폴링(`wait.PollUntilContextTimeout`), 채널/콜백 동기화 — "시간을 기다리지 말고 상태를 기다려라."
