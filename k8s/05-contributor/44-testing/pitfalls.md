# 흔한 함정 5선

## 1. 실패를 본 적 없는 테스트

수정부터 하고 테스트를 나중에 추가 — 그 테스트가 "원래부터 통과하는" 것일 수 있습니다(버그를 안 잡는 테스트). 정석: **테스트 먼저 → FAIL 확인 → 수정 → PASS.** FAIL을 본 순간만이 "이 테스트는 이 버그를 잡는다"의 증명입니다.

## 2. fake client 결과를 과신

fake는 admission, 검증(strategy), 기본값 주입, resourceVersion 의미론을 **건너뜁니다** — "fake에서 되는데 진짜에서 거부"가 흔합니다. 변경이 API 동작(검증/admission/GC)에 닿으면 integration까지. fake의 용도는 "내 로직이 어떤 호출을 하는가"이지 "API 서버가 뭐라 답하는가"가 아닙니다.

## 3. 독창적인 테스트 스타일

자기만의 헬퍼/assert 라이브러리/구조로 작성 — 내용이 옳아도 리뷰가 길어집니다. **그 패키지의 기존 테스트를 모방**하세요: 같은 표 구조, 같은 팩토리 함수, 같은 비교 방식. 오픈소스에서 일관성은 창의성보다 위입니다.

## 4. sleep으로 타이밍 맞추기

`time.Sleep(2초)` 후 결과 확인 — 로컬에선 통과, CI(느린 머신)에선 flake가 됩니다. **내가 flake를 만들어 모두를 괴롭히는 것.** 폴링(`wait.PollUntilContextTimeout`)이나 채널/동기화로 "조건 충족까지 대기"가 정석. K8s 테스트에서 맨 sleep은 리뷰 지적 1순위.

## 5. /retest 연타

빨간 CI를 보자마자 /retest, 또 빨가면 또 /retest — CI 자원 낭비에 평판 하락, 그리고 진짜 버그(내 변경의)를 운으로 통과시킬 위험까지. 절차: 로그 → 내 변경 관련성 → testgrid 성적 → 그 후에 한 번. 반복 실패면 멈추고 원인 규명이 먼저입니다.

## 실무(기여) 사고 사례

> 첫 PR에서 e2e 잡이 실패한 기여자가 /retest를 다섯 번 연타 — 다섯 번 다 같은 테스트가 죽었습니다. 리뷰어의 코멘트: "로그를 보세요. 당신의 변경이 이 필드의 기본값을 바꿔서, 이 e2e의 기대값이 깨진 겁니다." 알고 보니 unit 테스트에는 그 경로의 케이스가 없었고, e2e가 마지막 그물이었던 것. 수습: 기대값 수정이 아니라 **unit 표에 그 케이스를 추가**(FAIL 확인) → 코드 보완 → 전부 초록. 교훈: ① CI 실패의 절반은 진짜 신호다 ② 낮은 층에 테스트를 보강하는 것이 올바른 수습 ③ /retest는 도구지 주문(呪文)이 아닙니다.
