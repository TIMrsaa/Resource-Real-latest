# 학습 가이드 — "빌드되는 순간, 남의 프로젝트가 아니게 된다"

## 기여자 트랙의 지형도

```
41. 빌드        "내 손으로 컴파일된다"          ← 심리적 장벽 제거
42. 코드 투어    "어디에 뭐가 있는지 안다"        ← 지도 획득
43. KEP/SIG     "누가 어떻게 결정하는지 안다"     ← 사회 구조 이해
44. 테스트       "내 변경이 옳음을 증명한다"      ← 기여의 절반은 테스트
45. 첫 PR       "실제로 보낸다"                 ← 졸업
```

## 왜 빌드가 첫 번째인가

오픈소스 기여의 가장 큰 장벽은 기술이 아니라 심리입니다 — "저건 구글 엔지니어들이 만드는 거대한 무언가"라는 거리감. 그 거리감은 **`make` 한 번에 거의 다 사라집니다**: 내 노트북에서 컴파일되고, 내가 한 줄 바꾸면 동작이 바뀌는, 그냥 (큰) Go 프로그램이라는 사실을 몸으로 확인하기 때문입니다.

그리고 실리적 이유: 45번(첫 PR)까지 가려면 "수정 → 빌드 → 검증" 루프가 손에 붙어 있어야 합니다. 이 모듈이 그 루프의 첫 바퀴입니다.

## 이미 가진 무기 점검

- Go 환경과 감각: 모듈 30(kubebuilder), 31(client-go)에서 확보
- 컴포넌트별 동작 이해: 21(API 서버), 22(etcd), 25(스케줄러), 26(kubelet) — **빌드할 대상이 뭘 하는지 이미 압니다**
- kind: 모듈 37에서 사용 — 이번엔 "공식 이미지" 대신 "내 이미지"로 띄웁니다

## 마음가짐

빌드가 한 번에 안 될 수 있습니다(Go 버전, 메모리, WSL 설정). **그 트러블슈팅 자체가 커리큘럼입니다** — 실제 기여자들이 매일 겪는 환경 문제이고, 모듈 38의 루틴(증상→계층→확인)은 빌드 에러에도 통합니다.
