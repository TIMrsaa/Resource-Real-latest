# 흔한 함정 5선

## 1. Go 버전 불일치

시스템 Go가 최신이어도 K8s가 요구하는 버전(`.go-version`)과 다르면 빌드 거부/이상 동작. K8s는 Go 버전에 보수적입니다 — 리포가 말하는 버전을 따르라. 여러 버전 공존은 `go install golang.org/dl/go1.NN@latest` 패턴이나 gimme로.

## 2. 전체 빌드(`make all`)를 매번

첫 의식으로 한 번이면 충분합니다 — 이후 매번 수십 분을 태우는 건 루프 파괴. `make WHAT=cmd/<컴포넌트>`로 좁히고, 검증 사다리(테스트→바이너리→클러스터)의 아래 단부터. "빌드가 느려서 기여 못 하겠다"의 8할은 사다리를 거꾸로 타는 것.

## 3. WSL2 메모리/디스크 기본값

기본 WSL2는 메모리를 절반만 쓰고, 노드 이미지 빌드는 그걸 넘깁니다 — OOM으로 빌드가 "조용히" 죽습니다. `%UserProfile%\.wslconfig`에 `memory=12GB` 이상 + `wsl --shutdown` 후 재시도. 디스크도 클론+빌드 캐시로 30GB+ 먹습니다.

## 4. vendor/와 생성 코드를 직접 수정

`vendor/`(의존성 사본)나 `zz_generated.*.go`(생성물)를 고치면 — 빌드는 되지만 PR에서 즉시 반려됩니다. 생성 코드의 원본(타입 정의, 마커 주석)을 고치고 `make generated_files`(또는 해당 hack 스크립트)로 재생성하는 것이 규칙. "이 파일 손으로 고쳐도 되나요?"가 들면 파일 머리의 주석을 읽어라 — 생성물은 표시돼 있습니다.

## 5. main 브랜치에서 직접 작업

lab은 원복으로 끝났지만, 진짜 작업을 main에 쌓으면 upstream 동기화가 지옥이 됩니다. 습관: **수정 전 `git switch -c <topic>`** — fork의 main은 upstream 미러로 깨끗하게 유지(45에서 절차화). 그리고 "일단 커밋"이 아니라 단위 테스트 통과 후 커밋.

## 실무(기여) 사고 사례

> 첫 기여 도전자가 kubelet 버그를 고치겠다며: main 브랜치에서 수정 → 확인하려고 매번 `kind build node-image`(40분) → 3회 만에 하루가 끝났고, 다음 날 upstream과 충돌까지. 멘토의 교정: ① 토픽 브랜치 ② 해당 패키지 단위 테스트(30초)로 로직부터 고정 ③ kubelet은 local-up-cluster(3단)로 확인, kind는 마지막 1회 — 같은 작업이 2시간이 됐습니다. 교훈: **기여 속도 = 검증 사다리를 아래부터 타는 기술.**
