## 1. 한 문장 정의

> **Kubernetes(쿠버네티스, K8s)는 "수백 대의 컴퓨터를 한 대처럼 쓰게 해주는 운영체제"다.**

여러분의 노트북에서 윈도우가 하는 일을 생각해봅시다. 카톡, 크롬, 게임을 동시에 켜면 윈도우가 알아서 CPU와 메모리를 나눠줍니다. 프로그램이 죽으면? 다시 실행하면 됩니다.

이제 컴퓨터가 1대가 아니라 **500대**라고 합시다. 어떤 프로그램을 어느 컴퓨터에 띄울지, 죽으면 누가 다시 띄울지, 컴퓨터 한 대가 고장 나면 거기서 돌던 프로그램들을 어디로 옮길지 — 이걸 사람이 손으로 하는 건 불가능합니다. **그 일을 대신 해주는 소프트웨어가 K8s입니다.**

## 2. 핵심 등장인물 — 회사에 비유하면

| K8s 용어 | 비유 | 설명 |
|----------|------|------|
| **클러스터(Cluster)** | 회사 전체 | 컴퓨터(노드) 여러 대의 묶음 |
| **노드(Node)** | 사무실 건물 1개 | 실제 컴퓨터(서버/VM) 1대 |
| **컨테이너(Container)** | 직원 1명 | 실제로 일하는 프로그램 1개 |
| **Pod(파드)** | 같은 방을 쓰는 팀 | 항상 붙어 다녀야 하는 컨테이너 묶음. K8s의 최소 단위 |
| **Deployment** | "그 팀은 항상 3개 유지" 인사규정 | Pod가 죽으면 자동으로 다시 만듭니다 |
| **Service** | 부서 대표번호 | Pod는 자주 바뀌니까(이사/퇴사), 고정된 "대표 전화번호"로 연결 |
| **Control Plane** | 본사 경영진 | 전체를 지휘하는 두뇌 (스케줄러, API 서버 등) |
| **kubelet** | 각 건물의 관리소장 | 본사 지시대로 자기 건물에 직원을 배치하는 담당자 |

## 3. K8s의 작동 철학 단 하나 — "선언하면, 맞춰준다"

K8s에게는 명령하지 않습니다. **원하는 상태를 선언**합니다.

- ❌ 명령형: "서버 3번에 nginx 띄워. 죽으면 다시 띄워. 5번 서버 고장나면 옮겨."
- ✅ 선언형: **"nginx가 항상 3개 떠 있는 상태를 원합니다."** (끝)

그러면 K8s 안의 수많은 "감시 로봇(컨트롤러)"들이 24시간 내내 이렇게 반복합니다:

```
무한 반복 {
    현재 상태 확인  →  "지금 nginx가 2개네?"
    원하는 상태와 비교 →  "3개여야 하는데!"
    차이를 메꿈      →  "1개 더 띄우자"
}
```

이걸 **조정 루프(reconciliation loop)** 라고 합니다. **K8s의 모든 기능은 이 패턴 하나의 변주입니다.** 이것만 기억하면 절반은 이해한 것입니다.

> 🌱 비유: 에어컨의 온도 조절과 같습니다. "26도로 맞춰줘"라고 선언하면, 에어컨이 알아서 현재 온도를 재고 차이만큼 냉방합니다. 우리가 "지금 컴프레서를 30초 돌려"라고 명령하지 않는 것처럼.

## 4. YAML — K8s에게 보내는 주문서

원하는 상태는 YAML이라는 형식의 텍스트 파일로 선언합니다. 음식점 주문서라고 생각하면 됩니다.

```yaml
apiVersion: apps/v1      # 주문서 양식 버전
kind: Deployment         # 주문 종류: "항상 유지" 규정
metadata:
  name: my-web           # 이 주문의 이름
spec:                    # ← 여기부터가 "원하는 상태"
  replicas: 3            # 3개 유지해줘
  selector:
    matchLabels:
      app: my-web
  template:              # Pod를 만들 때 쓸 설계도
    metadata:
      labels:
        app: my-web      # 이름표 (selector가 이걸 보고 자기 Pod를 찾음)
    spec:
      containers:
      - name: web
        image: nginx:1.27   # 어떤 프로그램(이미지)을
        ports:
        - containerPort: 80 # 어떤 문(포트)으로
```

읽는 법 요령:
1. `kind` 부터 봅니다 — "이게 무슨 종류의 주문인지"
2. `spec` 이 본문입니다 — "원하는 상태"
3. `metadata.labels` 와 `selector` 는 **이름표와 이름표 찾기** — K8s의 모든 연결은 이름표(label)로 이루어집니다

## 5. kubectl — K8s와 대화하는 전화기

```bash
kubectl apply -f order.yaml   # 주문서 제출 ("이 상태로 맞춰줘")
kubectl get pods              # 직원 명단 확인
kubectl describe pod my-web   # 한 직원의 상세 인사기록 열람
kubectl logs my-web           # 그 직원의 업무일지(로그) 읽기
kubectl delete -f order.yaml  # 주문 취소
```

30분 생존 가이드: 위 5개 명령이면 초급 전체를 따라갈 수 있습니다. 자세한 건 [10-kubectl-mastery](./01-beginner/10-kubectl-mastery/)에서.

## 6. 전체 그림 — 주문서가 처리되는 길

```
나 ──kubectl──▶ API 서버 (본사 접수창구)
                   │  주문서 검사 후 etcd(금고)에 보관
                   ▼
              스케줄러: "이 Pod는 3번 건물(노드)이 여유 있네" 배정
                   │
                   ▼
          3번 노드의 kubelet(관리소장): "우리 건물에 배정됐네"
                   │  containerd(실행 담당)에게 지시
                   ▼
              컨테이너 실행! ──▶ 감시 로봇들이 계속 상태 유지
```

이 그림이 [02-k8s-architecture](./01-beginner/02-k8s-architecture/)에서 정밀하게 확장됩니다.

## 7. 자주 막히는 멘탈 블록 3가지

1. **"Pod가 자꾸 죽는데 비정상 아닌가요?"** — 정상입니다. K8s에서 Pod는 **소모품**입니다. 죽으면 새로 만듭니다. "이 Pod를 살리자"가 아니라 "같은 Pod가 다시 뜨면 된다"가 기본 사고방식.
2. **"IP로 접속하면 되지 Service가 왜 필요해요?"** — Pod는 죽고 다시 태어날 때마다 IP가 바뀝니다. 전화번호가 매일 바뀌는 친구에게는 연락이 안 되니, 변하지 않는 대표번호(Service)를 두는 것.
3. **"YAML이 너무 길어요"** — 전부 외우는 사람은 없습니다. `kubectl explain deployment.spec` 처럼 물어보면서 쓰는 것이고, 반복 패턴은 Helm/Kustomize(중급)가 줄여줍니다.
