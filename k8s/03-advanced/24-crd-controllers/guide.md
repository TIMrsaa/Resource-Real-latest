# 학습 가이드 — K8s가 "플랫폼의 플랫폼"인 이유

## 이 모듈의 위치

여러분은 이미 CRD 소비자입니다: Gateway API(모듈 06), ValidatingAdmissionPolicy의 paramKind(23), VPA(13) — 전부 CRD였습니다. 이제 **공급자** 쪽으로 넘어갑니다. 이 모듈에서 리소스 모델을, 모듈 30에서 컨트롤러 코드를, 모듈 31에서 그 아래 client-go를 봅니다.

```
CRD            "새 명사를 등록한다"        (이 모듈)
컨트롤러        "그 명사를 동사로 만든다"    (모듈 30 — kubebuilder)
   └ informer/workqueue                    (모듈 31 — client-go)
```

## 미리 연결해두면 좋은 직관 3개

1. **CRD를 만들면 API 서버가 즉시 REST 엔드포인트를 엽니다** — 스키마 검증, RBAC, watch, kubectl 지원까지 공짜로. "DB 테이블 + CRUD API + 이벤트 스트림"을 YAML 한 장으로 얻는 셈입니다. 이것이 K8s를 범용 컨트롤 플레인으로 만든 발명.
2. **ownerReference는 이미 봤습니다** — 모듈 04에서 Pod의 부모가 RS였던 것. "부모 지우면 자식도"의 가비지 컬렉션이 모든 컨트롤러 체인의 청소부입니다.
3. **finalizer도 이미 봤습니다** — 모듈 09 pitfall의 "ns가 Terminating에 갇히는" 그것. 갇히는 게 버그가 아니라 "뒷정리 보장" 메커니즘의 정상 동작임을 이번에 정확히 이해합니다.

## 설계 안목 기르기

lab-01에서 CRD를 "동작하게"만 만들지 말고, 설계 질문을 계속 던져라: spec과 status를 왜 나누나요? (사용자 의도 vs 컨트롤러 보고 — 모듈 02) 검증을 스키마/CEL 어디에 두나요? 버전 업그레이드는? — 좋은 CRD 설계는 좋은 API 설계입니다.
