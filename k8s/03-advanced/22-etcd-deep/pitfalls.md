# 흔한 함정 5선

## 1. etcd를 일반 DB처럼 쓰려는 설계

"CRD에 대용량 데이터/고빈도 시계열을 넣자" — etcd는 **소량의 합의된 메타데이터** 전용입니다(권장 객체 ≤1.5MiB, DB ≤ 수 GiB). 시계열은 Prometheus, 블롭은 S3, 대량 레코드는 RDB로. etcd에 들어갈 것은 "상태 선언"뿐입니다.

## 2. 짝수 노드 / 멀티 리전 etcd

4노드: 정족수 3 = 3노드와 장애 허용 동일, 선거만 복잡. 멀티 리전: 합의 왕복이 리전 간 지연(수십 ms)에 묶여 모든 쓰기가 느려지고 분할 시 정족수 상실 위험 — etcd는 **한 리전 내 멀티 AZ 홀수**가 정석.

## 3. defrag를 전 노드 동시에

defrag 중 그 노드는 **응답 정지**입니다. 전 노드 동시 실행 = 클러스터 전체 정지. 반드시 한 대씩, 리더는 마지막에 (defrag로 인한 불필요한 리더 교체 방지). 자동화 시 잠금/순서 보장 필수.

## 4. NOSPACE 복구에서 alarm disarm 누락

compact+defrag로 공간을 다 비워놓고 "왜 아직도 쓰기가 안 되지?" — 알람은 자동 해제되지 않습니다. `etcdctl alarm disarm`이 복구의 마지막 단계임을 runbook에 명시.

## 5. 스냅샷 백업만 믿고 리소스 백업 생략 (또는 그 반대)

etcd 스냅샷: 전체 되감기만 가능 — "어제 지운 네임스페이스 하나만 복구"는 불가. Velero류 리소스 백업: 선택 복구 가능하지만 etcd 자체 장애(정족수 상실+디스크 소실)에는 무력. **둘은 보완재입니다** — 자체 운영이면 둘 다, EKS면 (etcd는 AWS 몫이므로) Velero에 집중.

## 실무 사고 사례

> 자체 운영 클러스터에서 어떤 컨트롤러의 버그가 초당 수십 개의 Event 객체를 생성. 며칠 뒤 etcd가 8GiB 쿼터 도달 → NOSPACE → **클러스터 전체 쓰기 정지** (기존 Pod는 동작 — "뇌사"의 실사례). 야간 대응팀이 compact/defrag는 했지만 alarm disarm을 몰라 복구가 2시간 지연. 교훈: ① `etcd_mvcc_db_total_size_in_bytes`에 70% 알람 ② Event TTL과 수다스러운 컨트롤러 감시 ③ NOSPACE runbook(4단계)을 소방 훈련처럼 연습 — 이 모듈의 lab-02가 그 훈련입니다.
