# 흔한 함정 5선

## 1. Alpha 기능을 운영 설계에 박기

블로그에서 본 멋진 기능이 Alpha였고, 다음 버전에서 API가 바뀌거나 사라짐 — 설계 전체가 좌초. 단계 확인 습관: 공식 문서의 "FEATURE STATE: Kubernetes v1.NN [alpha|beta|stable]" 배지부터 보라. 운영 의존은 GA만.

## 2. in-place resize를 영구 변경으로 착각

Deployment 산하 Pod를 resize → 다음 롤링 업데이트에서 template 값으로 원복. resize는 "긴급 라이브 조정"이고 영구 변경은 template(Git) 수정입니다 — 모듈 10의 "라이브 수정은 빚" 원칙이 여기도 적용됩니다.

## 3. topology-mode: Auto를 만능 비용 스위치로

백엔드가 AZ별로 불균형하면 힌트가 안 붙거나(안전장치), 붙은 상태에서 한 AZ 백엔드가 줄면 그 AZ 클라이언트만 과부하를 겪을 수 있습니다. **AZ 균형 분산(topologySpread — 모듈 12)과 세트**로만 의미가 있습니다. 적용 후 EndpointSlice hints 존재를 반드시 확인.

## 4. schedulingGates를 빼먹은 채 "Pod가 안 떠요"

외부 큐 시스템이 넣은 게이트를 모르고 Pending류 디버깅 루틴(자원? taint?)만 도는 경우 — STATUS가 `SchedulingGated`로 **다르게 표시**된다는 것만 알면 1초에 끝납니다. 모듈 02의 상태표에 이 항목을 추가해두라.

## 5. audience 없는 토큰을 외부에 넘기기

기본 SA 토큰(audience=API 서버)을 외부 서비스 인증에 재사용 — 그 토큰을 받은 외부 서비스가 **우리 API 서버에 그대로 재전송(replay)** 할 수 있는 권한 위임 사고. 외부 연동은 반드시 audience를 그 서비스로 지정한 projected 토큰으로 (수신자가 다르면 API 서버가 거부).

## 실무 사고 사례

> 비용 절감 스프린트에서 topology-mode: Auto를 전 서비스에 일괄 적용한 팀. AZ 간 전송비는 실제로 줄었는데, 2주 뒤 한 서비스의 카나리 배포에서 신버전 Pod가 우연히 한 AZ에 몰렸고 — 힌트 라우팅 탓에 **그 AZ 사용자들만 카나리 버전에 100% 노출**되며 장애 영향이 AZ 단위로 갈렸습니다. 모니터링은 전체 평균만 봐서 늦게 발견. 교훈: 토폴로지 라우팅은 트래픽의 지리적 구조를 바꿉니다 — **배포 전략(분산)과 모니터링(AZ 차원 분리)을 함께 조정**해야 하는 기능이지, 스위치 하나가 아닙니다.
