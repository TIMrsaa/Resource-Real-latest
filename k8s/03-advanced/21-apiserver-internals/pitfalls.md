# 흔한 함정 5선

## 1. 409 Conflict를 에러로 취급해 알람 울리기

Conflict는 동시성 제어가 **정상 작동**한 신호입니다 — 재시도하면 됩니다. 컨트롤러 로그의 산발적 conflict에 알람을 걸면 노이즈만 생깁니다. 문제인 경우는 "같은 객체에서 지속적으로" — 두 컨트롤러가 같은 필드를 서로 고치는 싸움(필드 소유권 — 모듈 24의 SSA가 해법).

## 2. LIST를 루프에서 호출하는 컨트롤러/스크립트

`while true; kubectl get pods -A` 류 — LIST는 etcd/API 서버에 비싼 연산입니다. 수백 노드에서 이런 클라이언트 몇 개면 APF가 막기 시작(429)하고, 막히지 않던 시절엔 control plane이 통째로 느려졌습니다. 올바른 패턴: **watch 기반**(informer) — 한 번 LIST 후 변경분만 구독.

## 3. 감사 로그를 사고 후에 켜기

audit는 켜진 시점부터만 기록됩니다 — 유출 의심 시점이 그 전이라면 답이 없습니다. 운영 클러스터는 **상시 활성 + 보관 기간 정책**(CloudWatch retention)이 기본. 비용이 부담이면 최소 authenticator+audit만이라도.

## 4. resourceVersion을 숫자로 비교하는 코드

rv는 "불투명 문자열"이 공식 계약입니다 — 크기 비교/산술은 미정의 동작(etcd 외 스토리지, 압축 후 재발급 등). 같다/다르다만 판단하세요. (실제로 숫자처럼 보여서 저지르기 쉬운 실수)

## 5. "apply가 만능"이라는 오해

apply(클라이언트 사이드)는 last-applied annotation 기반 3-way 병합이라, 다른 도구가 만진 필드와 얽히면 미묘한 결과를 만듭니다. 여러 주체(HPA, 컨트롤러, 사람)가 한 객체를 만지는 환경의 정답은 **Server-Side Apply + 필드 소유권**(모듈 24) — conflict가 "누구 소유 필드인지"로 명시화됩니다.

## 실무 사고 사례

> 새로 배포된 사내 운영 도구가 10초마다 전체 네임스페이스의 전체 Pod를 LIST(필터 없이). 클러스터가 커지자 etcd 응답이 느려지고, **모든 컨트롤러의 reconcile이 함께 느려지는** 전면 둔화 — 범인 찾기에 이틀. APF 메트릭(`apiserver_flowcontrol_*`)과 감사 로그의 userAgent 집계로 해당 도구를 특정했습니다. 수정: informer 기반 + 라벨 셀렉터. 교훈: **API 서버는 공유 자원입니다. 클라이언트의 매너(watch, 셀렉터, 페이지네이션)가 클러스터 성능입니다.**
