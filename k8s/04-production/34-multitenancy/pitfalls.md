# 흔한 함정 5선

## 1. 테넌트를 "ns 하나"로 만들고 끝

패키지 5종 중 무엇이 빠지든 그 방향이 뚫립니다 — Quota 없으면 자원 독식, NetPol 없으면 옆 팀 네트워크 개방, PSA 없으면 privileged 탈출구, RBAC 없으면 방 구분 자체가 없습니다. 테넌트 생성은 **원자적**이어야 합니다: 수동 `create ns`를 금지하고 차트(17)나 Tenant Operator(30)를 유일한 통로로. lab-01의 검증 매트릭스를 온보딩 자동 테스트로 돌리면 "부품 누락"이 사람 눈에 의존하지 않게 됩니다.

## 2. "전용 노드 = taint 달았으니 끝"

lab-02 Step 4가 증명했습니다 — toleration은 매니페스트에 베껴 쓰면 그만이고, taint 키는 비밀이 될 수 없습니다. taint는 스케줄러에게 주는 **안내**지 테넌트 간 **계약의 강제**가 아닙니다. admission(VAP의 namespaceObject 대조, 또는 Kyverno)까지 얹어야 잠깁니다. "전용 노드인데 남의 Pod가 있어요"라는 문의가 오기 전에.

## 3. 외부/비신뢰 테넌트를 ns로 격리

ns 경계는 API 수준의 경계입니다 — **커널은 노드 위 모든 컨테이너가 공유**하므로, 커널 취약점 하나면 ns 라벨은 장식이 됩니다. 사내 팀(실수 방지가 목적)까지가 소프트 멀티테넌시의 정직한 사용 범위. 외부 고객·규제 워크로드는 별도 클러스터, 최소한 Kata 같은 가상화 런타임 + 전용 노드. 이 선을 넘는 순간 보안 리뷰에서 반드시 걸립니다.

## 4. Quota를 "자원 보장"으로 파는 것

Quota는 천장이지 바닥이 아닙니다. 클러스터가 꽉 차면 Quota가 절반 남은 테넌트도 Pending입니다. 핵심 테넌트에게 "Quota 드렸잖아요"는 답이 아닙니다 — 보장은 PriorityClass(12)와 전용 노드, 필요하면 자리 맡기용 placeholder(과잉 프로비저닝)로 만듭니다. 플랫폼팀이 이 구분을 흐리면 SLA 분쟁의 씨앗이 됩니다.

## 5. 테넌트에게 클러스터 스코프 권한을 "조금만"

"CRD 하나만 보게 해달라", "ClusterRole 하나만 만들게 해달라" — 클러스터 스코프 권한은 조금만 줄 방법이 없는 경우가 많습니다. 특히 ClusterRole/ClusterRoleBinding 생성권은 escalation(11)으로 cluster-admin까지 자력 도달하는 사다리입니다. 클러스터 스코프 요구가 반복되는 테넌트는 권한을 여는 게 아니라 **vCluster로 옮기는** 것이 답입니다(theory §4).

## 실무 사고 사례

> 사내 PaaS를 ns 멀티테넌시로 운영하던 플랫폼팀. ML팀에게 GPU 노드풀을 전용으로 주며 taint를 달았는데, 몇 주 뒤 GPU 노드에 웹 서비스 Pod들이 올라와 있었습니다 — 다른 팀이 사내 위키의 예제 매니페스트에서 toleration을 복사해 쓴 것. 악의도 아니었습니다: "Pending이 길래 붙여넣으니 스케줄이 되더라"는 것입니다. GPU 시간당 비용을 낸 ML팀이 항의하며 발각. 조치는 lab-02 Step 5 그대로 — VAP로 ns 라벨과 toleration 값 대조를 강제하고, 위키 예제에서 toleration을 삭제했습니다. 교훈: **소프트 멀티테넌시의 구멍은 공격자가 아니라 "빨리 되게 하려는 동료"가 먼저 찾습니다.** 그래서 안내(taint)가 아닌 강제(admission)가 필요합니다.
