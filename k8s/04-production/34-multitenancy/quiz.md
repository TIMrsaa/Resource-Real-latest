**Q2.** 멀티테넌시 수준을 정할 때 던져야 할 결정 질문들은?

**Q3.** 테넌트 ns 패키지 5종 세트 — 각 부품이 빠졌을 때 뚫리는 방향을 매핑하세요.

**Q4.** LimitRange가 Quota의 "짝꿍"인 이유는? (빠지면 생기는 구체적 현상으로)

**Q5.** lab-02 침입 실험이 증명한 것과, 그 구멍을 메운 수단은?

**Q7.** "Quota를 줬는데 왜 Pod가 Pending이죠?"에 대한 정확한 답과, 진짜 보장 수단은?

**Q8.** 테넌트가 "우리만 다른 버전의 CRD"를 요구합니다 — 왜 ns로는 불가능하고, 답은 무엇인가요?

---

## 정답

**A1.** ① ns 격리 — 실수와 가벼운 월경(API 수준)을 막습니다. ② +노드 격리 — 노이지 네이버와 노드 레벨 측면 이동을 막습니다. ③ vCluster — CRD/웹훅/버전 충돌(클러스터 스코프 공유 문제)을 막습니다. ④ 클러스터 분리 — control plane 공유와 커널 공유까지 끊습니다.

**A2.** 테넌트끼리 얼마나 못 믿는가(사내 팀 vs 외부), 노이지 네이버를 얼마나 허용하나, 클러스터 스코프 리소스(CRD/웹훅/버전)를 테넌트별로 달리 원하나, 클러스터를 여럿 운영할 인력/비용이 있나.

**A3.** RBAC 없음 → 남의 ns 출입. ResourceQuota 없음 → 클러스터 자원 독식. LimitRange 없음 → A4의 현상. NetworkPolicy 없음 → 옆 테넌트 네트워크 직접 접근(09의 실험). PSA 없음 → privileged로 노드 장악(32).

**A4.** compute Quota가 걸린 ns에서는 requests/limits 없는 Pod가 **생성 거부**됩니다 — LimitRange가 기본값을 주입해줘야 "requests 안 쓴 평범한 매니페스트"가 계속 동작합니다. 빼면 Quota가 온보딩 민원 제조기가 됩니다 (09).

**A5.** 증명: taint는 안내일 뿐, toleration을 베끼면 전용 노드에 침입할 수 있습니다(스케줄러는 소유권을 묻지 않습니다). 메운 수단: **admission** — VAP로 "tenant toleration 값 = 자기 ns의 tenant 라벨"을 강제해 API 문턱에서 거부.

**A6.** 검증 규칙이 Pod 단독이 아니라 **Pod와 그 ns의 관계**("이 toleration이 이 ns의 것인가")이기 때문 — namespaceObject가 ns 라벨을 CEL에 노출해줘서 테넌트가 늘어도 정책 하나로 일반화됐습니다.

**A7.** Quota는 사용 상한이지 자원 예약이 아닙니다 — 클러스터(노드) 용량이 바닥이면 Quota 잔량과 무관하게 Pending입니다. 보장: PriorityClass(선점 우선권) + 전용 노드 + 필요시 placeholder 과잉 프로비저닝.

**A8.** CRD는 클러스터 스코프라 버전이 클러스터당 하나 — ns를 아무리 나눠도 공유됩니다. 답: vCluster(테넌트별 가상 control plane이라 자기 CRD를 가짐) 또는 클러스터 분리.
