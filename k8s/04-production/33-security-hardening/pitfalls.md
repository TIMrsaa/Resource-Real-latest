# 흔한 함정 5선

## 1. 도구 도입 = 보안이라는 착각

kube-bench/trivy를 "설치"하고 끝 — 보고서를 아무도 안 읽으면 없는 것과 같습니다. 도구의 가치는 **루틴(주기 실행) + 추세(전회 대비) + 결정(항목별 처리)** 에서 나옵니다. lab-02의 보고서 양식이 그 뼈대.

## 2. CVE 0개를 목표로 잡기

모든 CVE를 없애려는 시도는 번아웃과 형식주의로 끝납니다 — 패치가 없는 것, 도달 불가능한 코드 경로의 것이 절반입니다. 기준선: **CRITICAL+Fixed는 N일 내, HIGH는 다음 릴리스에** 같은 SLA를 정하고 지키는 것이 현실적 보안.

## 3. 감사 예외를 구두로

"그건 어쩔 수 없어서 그래요"가 구전되면 — 다음 담당자는 그게 예외인지 구멍인지 모릅니다. 예외는 **문서화(이유+승인자+재검토일)** 가 붙어야 예외입니다. kube-bench의 항목 번호가 그 문서의 키가 됩니다.

## 4. 보안 강화를 한 번의 빅뱅으로

PSA restricted + NetworkPolicy 기본 거부 + 이미지 정책을 같은 주에 전부 — 무엇이 무엇을 깨뜨렸는지 구분 불가. 모듈 15/23/32에서 반복한 원칙: **한 번에 한 층, warn부터, 측정하며.**

## 5. 사람/프로세스 구멍 방치

기술 통제가 완벽해도 — 퇴사자 IAM 미회수(모듈 11 사례), kubeconfig 공유, "급해서" 권한 임시 부여 후 미회수가 뚫립니다. 분기 감사에 **사람 항목**(access entries 전수, 미사용 자격증명)을 포함하세요.

## 실무 사고 사례

> 보안팀이 연 1회 외부 감사 직전에만 kube-bench를 돌리던 조직 — 감사 통과용 임시 수정이 반복됐고, 실제 침해는 **9개월 전 도입된 서드파티 Operator의 cluster-admin 바인딩**을 통해 일어났습니다 (도입 시점엔 아무도 권한을 리뷰하지 않았습니다). 사후 도입된 룰: ① 신규 Helm 차트/Operator의 RBAC을 PR 리뷰 필수 항목으로 ② 분기 감사에 "cluster-admin diff" 포함 ③ 감사를 CI 크론으로 상시화. 교훈: **보안 사고는 감사 사이의 빈 시간에 일어납니다 — 감사를 이벤트가 아니라 파이프라인으로.**
