# 학습 가이드 — 실무 트랙을 읽는 법

## 트랙의 성격 전환

고급 트랙이 "깊이"였다면 실무 트랙은 **"체계와 루틴"** 입니다. 개별 지식은 이미 갖췄습니다 — 이제 그것을 ① 빠짐없이 ② 반복 가능하게 ③ 팀이 공유할 수 있게 조직하는 법을 다룹니다. 각 모듈의 산출물이 체크리스트/runbook/대시보드인 이유입니다.

## 보안의 전체 지도 — 4C와 배운 모듈의 매핑

```
Cloud      (EKS/AWS 계정)   IAM 최소화, SG, 퍼블릭 엔드포인트 제한    [eks 파트 25]
Cluster    (K8s 설정)       RBAC(11), PSA(32), NetworkPolicy(15),
                            admission 정책(23), 감사 로그(21)
Container  (이미지/런타임)   스캔/서명/digest(이 모듈), non-root(32), 런타임 탐지(cncf Falco)
Code       (앱)             시크릿 관리(07), 의존성 — cicd 파트(공급망)
```

안쪽 층의 방어는 바깥 층이 뚫렸을 때를 위한 것 — 모듈 32 사고사례의 "겹침"을 클러스터 전체로 확장하는 그림입니다.

## 도구 2개만 우선

보안 도구는 수십 개지만 출발은 둘이면 됩니다:
- **kube-bench**: "클러스터 설정이 CIS 기준에 맞나" (설정 감사)
- **trivy**: "이미지/리소스에 알려진 구멍이 있나" (취약점 스캔)

이 둘을 분기 루틴으로 돌리는 것이 lab의 내용이고, CI에 박는 것은 cicd 파트(21)의 일입니다.

## EKS 분업 명심

control plane 하드닝(etcd 암호화, apiserver 플래그)은 AWS 몫 — kube-bench의 EKS 프로파일이 그래서 따로 있습니다. 우리 몫은 **노드/워크로드/RBAC/네트워크** — 책임 경계를 모르면 "AWS가 해주겠지"와 "이미 돼 있는 걸 또 하기" 양쪽으로 헛돕니다.
