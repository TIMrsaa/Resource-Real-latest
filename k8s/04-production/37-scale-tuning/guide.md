# 학습 가이드 — 스케일 문제는 "느려짐"으로 시작해 "전면 장애"로 끝납니다

## 왜 작은 클러스터 운영자도 배워야 하나

"우린 노드 20개인데?" — 스케일 병목의 대부분은 **노드 수가 아니라 API 호출 패턴**에서 옵니다:
- 잘못 짠 operator 하나가 초당 수백 번 full LIST → 20노드 클러스터도 API 서버가 마비됩니다
- CronJob이 만든 수십만 개의 완료 Job/Pod 객체 → etcd가 가득 찹니다
- 모듈 31에서 informer를 배운 이유가 바로 이것 — 스케일 문제는 **클라이언트의 죄**가 절반입니다

즉 이 모듈은 "큰 클러스터 만들기"가 아니라 **"control plane을 아프게 하는 패턴 이해하기"**입니다.

## 병목의 순서 (theory의 뼈대)

```
부하 증가 →
1. etcd: 저장 한도(기본 수 GB) + watch 증폭 — 가장 먼저, 가장 치명적
2. API 서버: expensive LIST가 메모리/CPU 폭발 — APF가 방어선
3. 스케줄러: 초당 배치 수의 한계 — 대량 생성 시 Pending 적체
4. 그 외: DNS, conntrack, 이미지 풀 — 노드 쪽 한계
```

이 순서를 알면 "API가 느려요"라는 증상에서 **어느 층을 먼저 의심할지**가 나옵니다.

## EKS에서의 분업

EKS는 control plane(API 서버/etcd)을 부하에 따라 **자동 스케일**해 줍니다 — 그래서 1·2번 병목의 "서버 측 튜닝"(etcd 쿼터, API 서버 플래그)은 AWS 몫입니다. 우리 몫은:
- **클라이언트 행동**: informer 쓰기, full LIST 피하기, QPS 설정
- **객체 위생**: 완료 Job/이벤트/오래된 객체 정리 (etcd는 커져도 비용·지연으로 돌아옵니다)
- **APF 읽기**: 누가 API를 점유하는지 관측하고 필요시 FlowSchema로 제어

직접 etcd를 만질 일은 없지만, **관리형이라도 한계는 있습니다** — 한계의 위치를 아는 사람만 사고 전에 손을 씁니다.

## 실습 전략

1000노드를 실제로 만들면 수백 달러가 나갑니다. **kwok**(Kubernetes WithOut Kubelet)는 kubelet 없는 "가짜 노드"를 만들어 스케줄러/컨트롤러가 진짜라고 믿게 합니다 — 로컬 kind에서 1000노드 스케줄링 실험이 공짜가 됩니다. lab-02가 이 모듈의 하이라이트.
