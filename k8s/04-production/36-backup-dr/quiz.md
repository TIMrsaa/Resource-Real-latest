**Q1.** "실수로 shop ns를 지웠다" — etcd 스냅샷 복원이 아니라 Velero가 답인 이유 두 가지는? (EKS 관점 포함)

**Q2.** Velero의 구조를 모듈 30의 용어로 설명하세요. BSL의 역할은?

**Q3.** 백업의 "클러스터 독립성"이 열어주는 세 가지 시나리오는?

**Q4.** CSI 스냅샷과 File System Backup(Kopia)을 언제 각각 고르는가요?

**Q5.** 쓰기 중인 DB 볼륨 백업의 위험과, 층위별 대응은?

**Q6.** `velero schedule create --schedule="0 2 * * *"`의 RPO는? 이 값이 부족한 서비스의 다음 단계는?

**Q7.** RPO와 RTO가 각각 결정하는 설계 요소와, "티어링"이 필요한 이유는?

**Q8.** 사고 당일 "마지막 성공 백업이 11일 전"이 되는 메커니즘과 예방책은?

---

## 정답

**A1.** ① EKS의 etcd는 AWS 관리 영역 — 우리가 스냅샷을 뜨고 복원할 수 없습니다. ② 가능하더라도 etcd 복원은 클러스터 **전체** 되감기라 "그 ns만" 부분 복구가 안 됩니다 — Velero는 ns/라벨/종류 단위 선택 복구.

**A2.** Backup/Restore/Schedule **CRD** + 그것을 reconcile하는 **컨트롤러**(velero ns의 Deployment) = Operator 패턴. BSL(BackupStorageLocation)은 백업이 저장되는 S3 위치 선언으로, Available 상태여야 백업/복구가 성립하는 1차 관문.

**A3.** S3의 백업은 특정 클러스터에 묶이지 않으므로: ① DR(새 클러스터에 restore) ② 마이그레이션(리전/버전 이동) ③ 클론(prod→staging 복제). 모듈 35의 클러스터 Blue/Green도 이 토대 위.

**A4.** CSI/EBS 스냅샷: 같은 클라우드·리전 안에서 빠르고 증분 — 평시 기본값. Kopia 파일 백업: 느리지만 리전/클라우드를 넘는 이식성 — 크로스 리전 DR·클라우드 이동·CSI 스냅샷이 없는 볼륨일 때 (Pod annotation으로 지정).

**A5.** 위험: torn write — 쓰다 만 블록이 박제되어 복구 후 DB 기동 실패. 대응: 1층 backup hook(pre: flush/fsfreeze, post: 해제), 2층 애플리케이션 백업(pg_dump/WAL/논리 복제) 병행 — DB는 2층이 1순위.

**A6.** 매일 새벽 2시 백업 = **RPO 최대 24시간**(2시 직전 사고 시 하루치 손실). 부족하면: 주기 단축(시간별) → 그래도 부족하면 백업이 아닌 **복제 기반**(파일럿 라이트/웜 스탠바이/액티브-액티브)으로 전략 자체를 올립니다.

**A7.** RPO(허용 데이터 손실) → **백업 주기/복제 여부**. RTO(허용 다운타임) → **복구 방식**(복원 vs 대기 클러스터). 서비스마다 이 숫자가 달라서 — 결제와 분석에 같은 전략을 쓰면 한쪽은 도박, 한쪽은 낭비 — 티어링이 설계의 본질.

**A8.** 권한 회전/정책 변경 등으로 백업이 **조용히** 실패하기 시작 + 백업 자체를 모니터링하지 않음 → 실패가 누적돼도 무증상. 예방: 백업 실패·BSL 상태·"마지막 성공 백업의 나이"를 알람으로, 그리고 분기 Game Day가 이런 부패를 강제로 드러냅니다.
