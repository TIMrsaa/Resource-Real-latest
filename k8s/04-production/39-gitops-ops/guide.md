# 학습 가이드 — "누가 apply 하는가"가 운영의 절반을 바꿉니다

## 지금까지의 방식과 그 한계

모듈 10부터 선언형(`apply -f`, Git에 YAML)을 지켜왔습니다. 그런데 **apply를 치는 게 사람**인 한:

- 누가 언제 뭘 배포했는지 = 그 사람의 터미널 히스토리에만
- Git에는 v2인데 클러스터엔 v1 (깜빡함) — 또는 그 반대 (긴급 패치 후 커밋 안 함)
- 클러스터 접근 권한을 배포자 전원에게 — 권한 관리 비대화
- 클러스터가 통째로 죽으면? "재구축 절차"가 누군가의 머릿속에만

## GitOps의 답

**클러스터 안의 에이전트(ArgoCD)가 Git을 바라보며 스스로 맞춥니다(pull).** 사람은 Git에 커밋/PR만 합니다:

```
기존(push):  사람/CI ──kubectl/helm──▶ 클러스터        (밖에서 밀어넣기)
GitOps(pull): Git ◀──감시── ArgoCD(클러스터 안) ──apply─▶ 자기 클러스터
```

이 구조가 공짜로 주는 것: 배포 이력 = git log, 권한 = Git PR 리뷰, 재해 복구 = 새 클러스터에 ArgoCD만 설치하면 전부 재현, 드리프트 = 자동 감지/치유.

## 낯익은 패턴입니다

"원하는 상태(Git)를 보고 현재 상태(클러스터)를 맞추는 루프" — **모듈 02/30의 reconcile 그 자체**입니다. ArgoCD는 "Git을 desired state로 삼는 거대한 컨트롤러"라고 이해하면 새 개념이 거의 없습니다.

## 이 모듈의 범위

K8s 운영자 관점의 ArgoCD 기본기까지만. 이미지 빌드부터 Git 커밋까지의 왼쪽 절반(CI), 멀티 환경 승격 전략, 시크릿 관리는 **cicd 파트**에서 제대로 다룹니다.
