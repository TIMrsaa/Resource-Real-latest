# 학습 가이드 — 장애는 외우는 게 아니라 "루틴"으로 잡습니다

## 왜 10선인가

K8s 장애의 표면 증상은 수백 가지지만, 현장 통계로 보면 **소수의 패턴이 대부분을 차지**합니다. 이 10가지를 직접 일으켜보고 잡아본 사람과 아닌 사람의 차이는, 새벽 장애 콜에서 "30분 vs 4시간"으로 갈립니다.

더 중요한 것: 10가지를 외우는 게 아니라, **모르는 11번째 장애**를 만났을 때도 통하는 루틴을 만드는 것입니다.

## 표준 루틴 (theory에서 상세)

```
1. 증상을 한 문장으로     "Pod가 안 뜬다" → 어느 상태에서? (Pending? CrashLoop? Running인데 503?)
2. 계층을 가른다          스케줄 전(Pending)? 기동 중? 기동 후? 연결 문제?
3. 표준 3종을 읽는다      describe(이벤트!) → logs --previous → get -o yaml
4. 가설 → 최소 확인       "DNS겠지"라고 짐작 말고 nslookup 한 방으로 확정
5. 고치고 → 재발 방지     원인 제거 + "이걸 미리 잡을 장치"(probe/quota/알림) 추가
```

## 이 모듈을 읽는 법

각 시나리오는 같은 구조입니다: **일으킵니다 → 증상을 봅니다 → 루틴으로 추적합니다 → 고칩니다 → 교훈**. lab을 따라 치지 말고, 증상을 본 시점에 **먼저 스스로 진단**해보고 다음 단계와 대조하세요 — 그 간극이 실력입니다.

## 비유 하나

응급실 의사는 질병 수천 개를 다 외우지 않습니다 — **분류(triage) 프로토콜**이 있습니다: 의식? 호흡? 맥박? → 계통 좁히기 → 검사로 확정. 이 모듈은 K8s의 응급실 프로토콜입니다. describe가 문진, events가 활력 징후, logs가 혈액 검사입니다.
