# 학습 가이드 — Helm이 푸는 문제를 정확히 알기

## YAML의 두 가지 고통

모듈 4~16을 거치며 느꼈을 것입니다:

1. **반복**: 서비스 10개 = 거의 똑같은 Deployment+Service+HPA YAML 10벌
2. **환경 차이**: dev는 replicas 1, prod는 5 + 리소스 + 도메인... 파일 복사는 금방 어긋납니다

Helm의 답: **YAML을 템플릿으로, 환경 차이를 values 파일로.** 추가 보너스로 릴리스 관리(버전 이력, 원자적 롤백)와 패키징(차트 공유)이 따라옵니다.

## v4에서 알아둘 것 (옛 자료 주의)

- v3에서 넘어온 사용자라면 명령 체계는 거의 동일합니다. v2의 tiller(서버 컴포넌트) 이야기가 나오는 자료는 아주 오래된 것이니 버려라.
- 차트 apiVersion: `v2`가 현행 차트 포맷입니다 (Helm 버전과 헷갈리지 말 것).

## 템플릿 디버깅의 황금 루틴

```
helm template . --debug          # 로컬 렌더링 (클러스터 불요) — 가장 많이 침
helm lint .                      # 정적 검사
helm install --dry-run --debug   # 서버 검증 포함 리허설
helm get manifest <release>      # 배포된 릴리스의 실제 YAML
```

"템플릿이 뭘 뱉는지 모른 채 install"이 모든 고통의 시작입니다. **렌더링 결과를 먼저 보라.**

## Kustomize와의 관계 (다음 모듈 예고)

Helm = 템플릿+패키지+릴리스 관리(앱 배포판). Kustomize = 패치 기반 오버레이(템플릿 없는 변형). 경쟁이 아니라 용도가 다르고, "외부 차트를 Kustomize로 후처리"처럼 같이 씁니다 — 비교는 모듈 18에서.
