# 학습 가이드 — 배치의 제1원칙은 멱등성

## 관점 전환: 성공의 정의가 다릅니다

| | Deployment | Job |
|---|---|---|
| 성공 | 계속 떠 있음 | **exit 0으로 끝남** |
| 컨테이너 종료 | 장애 (재시작) | 정상 (완료) |
| restartPolicy | Always | **Never / OnFailure만 허용** |

이 표 하나로 "Job의 Pod가 Completed인데 왜 재시작 안 해요?" 같은 혼란이 사라집니다.

## 기술보다 먼저: "두 번 실행되면 어떻게 되는가"

K8s는 Job 실행을 **최소 1회(at-least-once)** 보장합니다 — 정확히 1회가 아닙니다. 노드 장애, 재시도, CronJob의 놓친 스케줄 보정 등으로 **같은 작업이 두 번 돌 수 있습니다.** 따라서:

- "포인트 적립 배치"가 두 번 돌면? → 이중 적립 사고
- 설계 원칙: **멱등(idempotent)하게** — 처리 여부를 기록하고 건너뛰기, upsert 사용, 고유 키 제약

이 질문을 던지는 습관이 이 모듈의 진짜 수확입니다. YAML 문법은 그다음.

## 미리 보는 도구 선택

```
한 번 실행하고 끝       → Job
주기 실행              → CronJob
이벤트(큐)에 반응해 실행  → KEDA ScaledJob (cncf 파트 — 큐 길이만큼 Job 생성)
복잡한 의존성 파이프라인  → Argo Workflows (cncf 파트)
```

CronJob으로 큐 폴링을 구현하기 시작하면 그건 KEDA가 풀 문제라는 신호입니다.
