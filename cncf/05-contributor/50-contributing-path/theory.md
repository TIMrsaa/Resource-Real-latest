# 이론 — 대상 선정, 기여의 형태, 이슈·PR의 기술, 멘토링·커뮤니티, ladder

> **🌱 17세 눈높이 비유: 동네 축구팀에 들어가기**
> - **구경(잠복 관찰)** = 몇 주 경기를 보며 팀 분위기·전술(거버넌스·로드맵)을 파악
> - **공 줍기부터(코드 밖 기여)** = 처음부터 스트라이커? 아니 — 공 줍고 물 나르는 것(문서·재현)도 팀엔 소중하고, 이름을 알리는 길
> - **작은 경기부터(good first issue)** = 연습 경기 → 후보 → 주전 (신뢰의 축적)
> - **매너(PR 예절)** = 패스를 받으면 고맙다고, 태클 당해도(리뷰 지적) 화내지 않기
> - **코치 프로그램(LFX)** = 주전 선수(메인테이너)가 몇 달간 붙어서 가르쳐 줌
> - **주장까지(ladder)** = 팀원 → 부주장 → 주장 — 실력+신뢰+꾸준함
> - **핵심** = 팀은 잘하는 사람보다 "꾸준히 오는 사람"을 먼저 신뢰합니다

---

## 1. 대상 선정 — 세 축의 교집합

```
기여 대상 = 관심 ∩ 역량 ∩ 거버넌스 건강

관심: 커리큘럼에서 재밌던 영역
  (관측? 네트워크? 스토리지? — 억지는 못 갑니다)
역량: 언어(Go가 CNCF 주류)·도메인 지식
  (11을 팠으면 Prometheus 코드가 읽힙니다)
거버넌스 건강: 49 lab-02의 정찰 시트
  (ladder 있음·외부 PR이 살아 있음·초보 진입로 있음)

규모의 선택:
  거대(K8s): 체계적이나 절차 많음 — SIG 하나로 좁혀서
  중간(Prometheus·Argo·Cilium...): 균형 — 추천 시작점
  작음(신생 Sandbox): 기여 영향 크고 빠름, 단 지속성 리스크(45)

★ "제일 유명한 곳"이 아니라 "내가 계속 갈 수 있는 곳"
```

## 2. 기여의 형태 — 코드는 하나일 뿐

```
문서 기여 (진입 장벽 최저, 가치 높음):
  오타·깨진 링크 수정
  ★ "내가 헤맨 부분" 개선 — 커리큘럼에서 문서가 불친절했던 곳!
  튜토리얼·예제 추가, 번역(k8s는 한국어 번역팀 활발)

이슈 기여:
  좋은 버그 리포트 (재현 절차 포함 — 아래 3절)
  이슈 트리아지: 남의 리포트에 재현 붙이기, 중복 찾기, 라벨 제안
  → 메인테이너의 시간을 아껴주는 귀한 기여

코드 기여:
  good first issue → 버그 수정 → 기능 (신뢰 순서대로)
  테스트 추가·플레이키 테스트 수정 (항상 환영받음)

리뷰·커뮤니티 기여:
  남의 PR 리뷰 (reviewer가 되는 길)
  슬랙·포럼에서 질문 답변 (커리큘럼 지식이 여기서 빛남)
  밋업·블로그·발표 (채택을 돕는 것도 기여)

★ 트리아지·재현·문서가 "낮은" 기여가 아닙니다 —
  많은 메인테이너가 그 경로로 시작했고, 가장 부족한 일손입니다
```

## 3. 좋은 이슈의 기술 — 운영 경험을 기여로

```
나쁜 리포트: "안 돼요. 고쳐주세요"
좋은 리포트:
  환경: 버전(정확히)·플랫폼·설정
  기대 동작 vs 실제 동작
  ★ 최소 재현 절차 (kind + 매니페스트 몇 줄로 재현되게)
  로그·에러 (관련 부분만, 포맷팅)
  이미 시도한 것

→ 커리큘럼의 실습(kind로 재현)이 그대로 이 기술입니다
  pitfalls에서 배운 함정을 실무에서 만나면 → 재현 → 리포트
  = 실무자만 할 수 있는 기여

보안 취약점은 예외: 공개 이슈 금지 →
  SECURITY.md의 비공개 채널로 (책임 있는 공개, cicd 21)
```

## 4. 좋은 PR의 기술 — 예절과 범위

```
PR 전:
  이슈 먼저 (버그면 리포트, 기능이면 제안 — 49의 교훈)
  "제가 해볼게요" 코멘트로 중복 방지·의사 표시
  CONTRIBUTING.md 숙지 (DCO 서명! git commit -s)

PR 자체:
  ★ 작게 — 한 PR은 한 가지 일 (리뷰 가능한 크기)
  테스트 포함 (수정이 증명되게)
  커밋 메시지·PR 설명은 "왜"를 (이슈 링크)
  프로젝트 스타일 준수 (린터·컨벤션)

PR 후 (예절):
  리뷰 지적은 코드에 대한 것, 나에 대한 것이 아님
  수정 요청엔 신속·감사히 (방어 아닌 배움)
  느린 응답에 인내 (메인테이너는 대부분 자원봉사·겸직)
  ping은 정중히, 1~2주 간격
  방치되면: SIG 회의·슬랙에서 정중히 리뷰 요청

★ 첫 PR의 목적은 머지가 아니라 신뢰의 시작
  → 태도가 코드만큼 봅니다
```

## 6. Contributor Ladder — 구성원으로 성장

```
전형적 사다리 (K8s 기준, 49 lab-02):
  Contributor: 누구나 (첫 PR부터)
  Member: 기여 이력 + 스폰서 2인 → org 멤버 (테스트 트리거 등 권한)
  Reviewer: 특정 영역 리뷰 담당 (OWNERS 등재)
  Approver: 머지 승인권 (높은 신뢰)
  Maintainer/Chair: 프로젝트·SIG 운영

오르는 법 = 지름길 없음:
  꾸준함 (주 몇 시간이라도 지속)
  한 영역에 깊이 (넓게 얕게 X — 45의 교훈과 동일)
  가시성 (회의 참석·리뷰 참여·슬랙 활동)
  ★ 시간이 걸립니다 — reviewer까지 보통 수개월~1년의 꾸준함

의미: 어느 회사 소속이든 기여와 신뢰로 오릅니다 (49의 벤더 중립)
```

## 7. 지속 가능한 기여 생활

```
번아웃 방지:
  작게 꾸준히 > 몰아치고 소진
  즐거운 영역에서 (의무가 되면 끝)
  거절·정체를 개인화하지 않기 (합의 비용일 뿐 — 49)

받기도 기여의 일부:
  리뷰에서 배우기 (공짜 코드 리뷰!)
  커뮤니티 관계 (동료·멘토·때론 커리어)

커리어와의 선순환:
  기여 이력 = 공개된 실력 증명 (git log는 거짓말 안 함)
  많은 클라우드 네이티브 기업이 기여 이력을 채용에서 높게 봄
  단, 커리어"만"을 위한 기여는 오래 못 갑니다 — 재미가 연료
```
