# 학습 가이드 — 표준의 가치는 "이식성"에 있습니다

## OTel을 도구로 보면 실망하고, 표준으로 보면 이해됩니다

"OTel을 깔았는데 화면이 없네요"는 정확한 관찰입니다 — OTel은 저장하지 않고 그리지 않습니다(06의 경계). 그럼 왜 CNCF에서 두 번째로 큰 프로젝트가 됐나요? 답은 **계측의 소유권**에 있습니다.

```
벤더 SDK 시대:  앱 코드에 벤더 A의 SDK → 벤더 B로 옮기려면 전 서비스 재계측 (수개월)
OTel 시대:      앱 코드에 OTel SDK → 백엔드 교체는 Collector의 exporter 한 줄
```

계측은 앱 코드에 박히는 가장 이동하기 어려운 자산입니다. OTel은 그 자산을 벤더로부터 떼어냈습니다 — 05의 CSI가 스토리지에서, 03의 OCI가 이미지에서 한 일과 정확히 같은 종류의 해방입니다.

## 이 모듈의 세 축

**① 컨텍스트 전파** — 이것이 트레이스의 심장입니다. 서비스 A가 B를 호출할 때 "같은 요청"임을 어떻게 아는가요? HTTP 헤더 `traceparent`(W3C 표준)에 trace_id와 부모 span_id를 실어 보냅니다. 전파가 끊기면(비동기 큐, 스레드 풀, 수동 HTTP 클라이언트) 트레이스는 조각납니다 — 06의 사고 사례에서 결제 서비스가 트레이스에서 사라진 이유가 정확히 이것입니다. lab-01에서 직접 끊고 잇습니다.

**② 시맨틱 컨벤션** — 표준의 가장 저평가된 부분. `http.request.method`인가 `http.method`인가 `httpMethod`인가요? 컨벤션이 있으면 **대시보드와 알람이 이식 가능**합니다. 서비스마다 속성 이름이 다르면 OTel을 써도 아무것도 통일되지 않습니다.

**③ Collector** — 관측의 게이트웨이. 앱이 OTLP로 던지면 Collector가 받아 가공하고 어디로든 보냅니다. 여기서 샘플링·필터링·강화(k8s 메타데이터 추가)가 일어나고, 배포 토폴로지(노드별 agent + 중앙 gateway)가 성능과 기능을 가릅니다.

## 샘플링 — 이 모듈의 실무 급소

트레이스를 100% 저장하면 비용이 감당 안 되고, 무작정 1%를 남기면 **정작 필요한 에러 트레이스가 버려집니다**. 그래서 tail 샘플링(요청이 끝난 뒤 판단: 에러면 남기고, 느리면 남기고, 나머지는 1%)이 존재하고, 그것을 하려면 한 트레이스의 모든 span이 같은 Collector에 모여야 합니다(로드밸런싱 exporter). 이 제약이 Collector 토폴로지 설계를 지배합니다 — lab-02에서 직접 만듭니다.
