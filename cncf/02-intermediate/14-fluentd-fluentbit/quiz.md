## 정답

**A1.** 앱 stdout/stderr → 컨테이너 런타임이 가로채 `/var/log/pods/<ns>_<pod>_<uid>/<container>/0.log`에 CRI 형식으로 기록(`/var/log/containers/*.log`는 심볼릭 링크) → 에이전트(Fluent Bit)가 tail → 백엔드. 첫 유실 지점은 **kubelet의 로그 로테이션**(기본 10Mi × 5) — 에이전트가 백엔드 지연·다운으로 못 따라가면 읽기 전에 파일이 삭제됩니다. 버퍼도 재시도도 소용없습니다(읽지 못한 데이터는 재시도 대상이 아니므로).

**A2.** ① input(tail): 파일 추적·오프셋 DB — 오프셋 손실 시 중복/누락, inode 재사용 문제. ② parser: CRI/JSON/정규식 파싱, 멀티라인 병합 — 스택트레이스가 줄마다 조각남. ③ filter: k8s 메타 부착·재작성·드롭 — K8s API 부하, RBAC 누락. ④ buffer: 메모리/파일 큐 — 백프레셔로 인한 유실. ⑤ output: 백엔드 전송·재시도 — 429·타임아웃·부분 실패.

**A3.** ① drop: 버퍼 한계 초과 시 새 데이터 폐기(또는 input 일시정지) — 조용하고 가장 흔합니다. ② block: 파이프라인 정지 — 파일이 계속 쌓이다 kubelet 로테이션에 삭제되고, 극단적으로 앱의 stdout 쓰기가 막힐 수 있습니다. ③ 디스크 버퍼로 흘림 — 여유를 벌지만 디스크가 차면 다시 ①/②. 유실이 최대인 순간은 **백엔드가 느려진 때 = 장애 중** — 에러 로그가 폭증하고 백엔드가 밀리는 그 시각이므로, 로그가 가장 필요한 순간에 가장 많이 잃는 구조입니다.

**A4.** Fluentd: Ruby 기반, 플러그인 1000개 이상, 무겁고 유연 → 중앙 **애그리게이터**. Fluent Bit: C 기반, 메모리 수 MB, 빠르고 가벼움, 플러그인 제한적 → 노드 **에이전트**. 표준 패턴: Fluent Bit(DaemonSet) → Fluentd(중앙, 복잡 라우팅) → 백엔드, 또는 요즘은 Fluent Bit → 백엔드 직결. OTel Collector는 filelog receiver로 이 자리를 노립니다 — 06의 대통일 운동이 로그 행에 도달하는 중이며, 세 신호를 단일 파이프라인으로 다룰 수 있다는 이점이 있으나 플러그인·성숙도에서 Fluent Bit가 아직 강합니다.

**A5.** ① Fluent Bit의 multiline 파서로 병합(첫 줄 패턴으로 시작 감지). ② **앱이 처음부터 구조화 JSON 한 줄로** 출력(스택트레이스를 필드 하나에). 후자가 근본적인 이유: 정규식 기반 파서는 앱의 로그 형식이 바뀔 때마다 조용히 깨지고(그 사실을 아무도 모릅니다), 파서 유지보수는 누적되는 기술 부채이며, 구조화 로그는 파싱 없이 필드 검색·인덱싱·상관이 가능하기 때문입니다.

**A6.** 구조화 로그는 `trace_id`를 필드로 담을 수 있고, 그것이 13의 조사 동선 마지막 홉("트레이스에서 얻은 trace_id로 로그를 조회해 '왜'를 읽는다")을 성립시킵니다. 또한 level·duration_ms·error_kind 같은 필드로 정규식 없이 검색·알람이 가능합니다. 06 사고 사례의 실패 지점: **서비스마다 요청 ID가 달라 로그를 이어 붙일 수 없었습니다** — 트레이스도 있고 로그도 있었지만 둘을 잇는 공통 키가 없었습니다.

**A7.** 메트릭은 라벨 조합마다 **시계열이 하나씩 상주**합니다(인덱스 항목 + head 청크 + 메모리) — 카디널리티가 곧 메모리이고 OOM으로 이어집니다(11). 로그는 레코드마다 필드가 붙을 뿐 상주 구조가 없습니다 — 카디널리티는 저장·인덱싱 비용에만 영향을 줍니다. 따라서 개별 사건의 식별자(user_id·request_id·trace_id)는 로그·트레이스의 영토이고, 이것이 06의 신호 분업입니다. 단 로그에도 비용은 있어서, 백엔드가 모든 필드를 인덱싱하면 폭발합니다 — Loki처럼 인덱싱 라벨은 저카디널리티만, 나머지는 본문 스캔.

**A8.** 올바른 순서(위가 쌉니다): ① 앱 — 프로덕션 로그 레벨 억제, 반복 로그 dedupe, 디버그 게이트. ② 에이전트 — 노이즈 필터 drop(헬스체크 200 등), 불필요 필드 프루닝. ③ 백엔드 — 인덱싱 최소화, 보존 정책, 콜드 티어. 대부분의 조직은 ③부터 손댑니다(보존 축소·인덱스 튜닝) — 가장 비싸고 효과가 늦은 지점입니다. 헬스체크 로그가 전체의 40%인 경우가 드물지 않으므로, 에이전트 필터 한 줄이 백엔드 튜닝 한 달보다 큰 절감을 낳는 일이 흔합니다.
