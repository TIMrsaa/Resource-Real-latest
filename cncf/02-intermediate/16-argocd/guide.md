# 학습 가이드 — 같은 프로젝트를 세 번째 각도에서

## 이미 두 번 만났습니다

```
cicd 14: 사용자로 — push→pull 역전, refresh vs sync, selfHeal/prune의 양날
cicd 27: 개발자로 — appcontroller.go, gitops-engine 경계, 로컬 실행
이 모듈: 운영자로 — 수천 앱·수십 클러스터·수십 팀에서 무엇이 무너지는가
```

세 각도가 필요한 이유는 각 각도에서만 보이는 것이 있기 때문입니다. 사용자는 진동(OutOfSync 루프)을 보고, 개발자는 그 코드를 보고, 운영자는 **컨트롤러가 3분 주기를 못 지키는 순간**을 봅니다.

## 규모가 드러내는 것

ArgoCD가 느려질 때 사람들은 CPU를 늘립니다. 그러나 병목은 대개 다른 곳에 있습니다:

```
repo-server:  Git clone + helm template/kustomize build — CPU·디스크·동시성이 병목
              (같은 저장소를 수백 앱이 참조하면? 캐시가 생명)
application-controller: 클러스터 상태 watch + diff 계산 — 메모리(캐시)와 리스트 부하
              (샤딩으로 클러스터를 나눠 담당)
redis:        렌더링·상태 캐시 — 여기가 죽으면 전부 느려집니다
API/UI:       사용자 부하(대개 문제 아님)
```

그리고 **감춰진 부하**가 있습니다: 대상 클러스터의 API 서버. ArgoCD는 관리 대상 클러스터의 모든 리소스를 watch합니다 — 클러스터 100개면 100개의 watch 세트입니다. "왜 대상 클러스터 API 서버가 바쁜가"의 답이 ArgoCD인 경우가 흔합니다.

## 멀티클러스터는 아키텍처 결정입니다

"ArgoCD 하나로 클러스터 100개를 관리한다"는 매력적이고 위험합니다 — 중앙 ArgoCD가 SPOF이고, 네트워크가 클러스터 경계를 넘어야 하며, 자격증명이 한곳에 모입니다(07의 신뢰 경계!). 대안은 "클러스터마다 ArgoCD"(운영 부담↑, 폭발 반경↓)와 그 중간(허브-스포크, 리전별 허브)입니다. 02의 멀티클러스터 지도가 여기서 실무 결정이 됩니다.

## 거버넌스 — cicd 24가 배달 층으로

50개 팀이 한 ArgoCD를 쓰면 즉시 질문이 생깁니다: A팀이 B팀 네임스페이스에 배포할 수 있는가요? 어느 Git 저장소를 신뢰하는가요? 누가 prod에 sync할 수 있는가요? 답은 **AppProject**(소스·목적지·리소스 종류의 화이트리스트)와 **RBAC**입니다. cicd 24의 "강제는 좁게" 원칙을 배달 층에서 구현하는 것이고, 이것 없이 규모를 키우면 GitOps가 곧 무제한 배포 권한이 됩니다.
