# 학습 가이드 — Helm의 발명품은 템플릿이 아니라 릴리스입니다

## 템플릿은 수단, 릴리스가 개념

Helm을 "YAML 템플릿 도구"로 요약하면 Kustomize와의 비교(08)에서 멈춥니다. 진짜 발명은 다른 곳에 있습니다:

```
K8s에는 "애플리케이션"이라는 개념이 없습니다
  → Deployment 하나, Service 하나, ConfigMap 셋... 흩어진 오브젝트들뿐
  → "이 앱을 지워라"를 하려면 무엇을 지울지 사람이 알아야 합니다

Helm의 릴리스(Release):
  "이 이름(release name)으로 설치된 오브젝트 목록 + 그때의 values + 렌더링된 매니페스트"
  를 클러스터의 Secret에 저장 → 업그레이드·롤백·삭제가 하나의 명령이 됩니다
```

그래서 `helm upgrade`는 단순한 apply가 아닙니다 — 이전 릴리스의 매니페스트(저장된 것), 현재 클러스터 상태(live), 새 매니페스트(desired)를 놓고 **3-way 병합**을 합니다. 이 구조를 알면 "helm으로 설치한 걸 kubectl로 고쳤더니 다음 upgrade에서 되돌아갔다/안 되돌아갔다"의 미스터리가 풀립니다.

## 그리고 그것이 GitOps와 부딪힙니다

cicd 14에서 배운 GitOps는 "Git이 진실, 컨트롤러가 수렴"입니다. Helm은 "릴리스 Secret이 진실, helm 명령이 변경"입니다. 두 진실이 한 클러스터에 있으면 어떻게 되는가요?

```
ArgoCD의 답: helm template으로 렌더링만 하고 릴리스를 안 만듭니다 (helm은 템플릿 엔진일 뿐)
Flux의 답:   HelmRelease CR로 릴리스를 컨트롤러가 관리 (helm의 상태 기계를 유지)
★ 두 답이 다르다는 것 자체가 이 긴장의 증거
```

이 모듈은 그 긴장을 이해시키고, 조직이 무엇을 택할지의 근거를 줍니다(16·17에서 각각 심화).

## 템플릿의 대가를 정확히 알기

Go 템플릿은 YAML을 **문자열로** 다룹니다 — 들여쓰기, 따옴표, 타입이 전부 사람의 책임입니다. `nindent`, `toYaml`, `quote`, `default`를 언제 쓰는지 모르면 렌더링 전까지 유효성을 알 수 없는 코드가 쌓입니다. lab-01에서 실제로 깨뜨려보고, 방어(dry-run·lint·values 스키마)를 손에 넣습니다.

## v4 — 무엇이 바뀌었나

Helm v3가 Tiller를 없앤 것이 혁명이었다면, v4는 진화입니다: 서버사이드 apply 지향, WASM 플러그인, SDK 개편 등. **v3의 정신 모델(릴리스 Secret, 3-way 병합, 훅)은 유지**되므로 이 모듈의 개념은 그대로 유효하고, 차이는 실무 주의사항으로 다룹니다(루트 버전표: v3는 2026-11 보안픽스 종료).
