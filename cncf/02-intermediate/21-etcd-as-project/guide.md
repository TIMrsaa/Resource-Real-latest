# 학습 가이드 — 전제를 이해한다는 것

## 왜 etcd만 "채택 판단"이 없나

09에서 말했듯 etcd는 고를 수 있는 DB가 아닙니다 — K8s를 쓰면 이미 쓰고 있습니다. 그래서 이 모듈의 목적은 다릅니다:

```
다른 프로젝트: "우리에게 맞는가요?" (채택 판단)
etcd:          "이것이 어떻게 동작하기에 K8s가 그 모양인가요?" (원리 이해)
               "이것이 아플 때 어떻게 알아채고 고치는가요?" (운영)
```

K8s의 성질 — 선언적 API, watch 기반 컨트롤러, resourceVersion으로 낙관적 동시성, Lease로 리더 선출 — 은 전부 etcd 능력의 표면입니다. etcd를 이해하는 것은 K8s를 아래에서 이해하는 것입니다.

## Raft를 외우지 말고 "왜 그래야 하는가"로 이해하기

분산 시스템에서 여러 노드가 같은 상태를 갖게 하는 것은 어렵습니다. Raft의 답은 놀랍도록 단순합니다:

```
① 리더 한 명만 씁니다 (동시 쓰기 충돌 제거)
② 리더가 로그를 복제하고, 과반이 받았다고 하면 커밋합니다 (내구성)
③ 리더가 죽으면 최신 로그를 가진 자만 리더가 될 수 있습니다 (안전성)
```

여기서 **과반(쿼럼)**이 나옵니다. 3노드면 2, 5노드면 3. 그리고 짝수(4노드)는 쿼럼이 3이라 여전히 1대 손실만 견디면서 합의 지연만 늘어납니다 — 그래서 홀수입니다. 이 계산이 "왜 etcd는 3대 또는 5대인가"의 전부입니다.

## 디스크가 클러스터의 속도를 정합니다

etcd의 커밋은 **디스크 fsync**를 기다립니다(내구성 보장). 그래서:

```
느린 디스크 → wal fsync 지연 → 커밋 지연 → API 서버의 쓰기 지연
→ 컨트롤러가 타임아웃 → 재시도 → 부하 증폭 → 더 느려짐 → 리더 교체 → 더 나빠짐
```

"클러스터가 왠지 느리다"의 1번 용의자가 etcd 디스크인 이유이고, 그래서 etcd에는 전용 SSD가 권장됩니다. `etcd_disk_wal_fsync_duration_seconds`의 p99가 25ms를 넘으면 경보입니다.

## 컴팩션과 디프래그 — 두 개의 다른 청소

혼동하기 쉬운 둘:

```
컴팩션(compaction): 옛 리비전을 논리적으로 지웁니다 → keyspace 사용량 감소
디프래그(defrag):   실제 파일의 빈 공간을 회수합니다 → 디스크 파일 크기 감소
★ 컴팩션만 하면 파일은 안 줄어듭니다. 디프래그는 그 순간 etcd가 블록됩니다(순차 수행!)
```

`mvcc: database space exceeded`는 K8s를 통째로 읽기 전용으로 만드는 유명한 장애이고, 그 복구가 이 두 작업입니다. lab-01에서 직접 만들고 고칩니다.
