# 흔한 함정 5선

## 1. 짝수 노드 etcd

4노드 etcd는 쿼럼이 3이라 **3노드와 똑같이 1대 손실만 견디면서** 합의 지연(과반 응답 대기)과 비용만 늘어납니다. 6노드는 쿼럼 4로 2대 손실 — 5노드와 동일. 규칙은 단순합니다: **3(표준) 또는 5(고가용)**, 그 이상은 합의 지연 때문에 드뭅니다. "짝수로 늘리면 더 안전하겠지"는 Raft의 과반 규칙을 모르는 직관이고, 멤버를 하나씩 추가하는 과정에서 일시적으로 짝수가 되는 것과 영구적으로 짝수를 유지하는 것은 다릅니다.

## 2. compact만 하고 defrag를 안 함

`mvcc: database space exceeded`를 만나 컴팩션을 실행했는데도 여전히 쓰기가 막힙니다 — 컴팩션은 옛 리비전을 **논리적으로** 지울 뿐 파일의 빈 공간을 회수하지 않기 때문입니다(lab-01 Step 7에서 dbSize가 그대로인 것을 확인). 복구는 세 단계입니다: `compact` → `defrag` → `alarm disarm`. 그리고 defrag는 그 노드를 **블록**하므로 절대 모든 멤버에서 동시에 실행하면 안 됩니다(쿼럼 상실 = 클러스터 마비). 순차로, 그리고 가능하면 트래픽이 적은 시간에.

## 3. etcd 디스크를 다른 워크로드와 공유

etcd의 커밋은 WAL fsync를 기다리므로 디스크 지연이 곧 클러스터 지연입니다. 컨트롤 플레인 노드에 로그 수집기나 다른 I/O 집약 워크로드가 함께 있으면 fsync p99가 수십~수백 ms로 튀고, 그것이 API 서버 쓰기 지연 → 컨트롤러 타임아웃 → 재시도 폭풍 → 리더 교체로 번집니다(theory §4의 번짐 경로). etcd는 **전용 SSD**를 쓰고, `etcd_disk_wal_fsync_duration_seconds`의 p99 > 25ms를 알람으로 걸어라. "클러스터가 왠지 느리다"의 1번 용의자입니다.

## 4. 백업은 있는데 복구를 리허설하지 않음

스냅샷 CronJob은 대부분의 조직에 있습니다. 그런데 복구를 해본 조직은 드물고, 실제 재해 때 발견합니다: etcdutl 명령의 `--initial-cluster` 인자를 어떻게 채우는지 아무도 모릅니다, 복구된 클러스터의 cluster ID가 달라 옛 멤버와 섞으면 안 된다는 것을 모릅니다, 인증서가 만료됐습니다, 스냅샷 파일이 실은 0바이트였습니다. **리허설하지 않은 백업은 백업이 아닙니다**(k8s 36의 명제). 분기마다 별도 환경에서 복구하고 RTO/RPO를 실측하며, 스냅샷의 `status`(revision·해시)를 매번 검증하세요.

## 5. K8s가 만드는 etcd 부하를 방치

etcd가 커지고 느려지는 원인은 대개 K8s 쪽에 있습니다: Event 리소스가 keyspace를 채우고(별도 etcd로 분리 가능), 오퍼레이터가 status를 초당 갱신해 리비전을 폭증시키고, CRD(CiliumEndpoint 등)가 수만 개 쌓이고, 큰 ConfigMap이 들어옵니다. 진단은 키 공간 분석부터: `etcdctl get /registry --prefix --keys-only | awk -F/ '{print $3}' | sort | uniq -c | sort -rn`. 상위 항목이 곧 처방입니다. 그리고 컨트롤러 재시작이 relist 폭풍을 일으키는 것(컴팩션된 revision을 watch하려다 실패 → 전체 목록 재조회)도 같은 계열의 부하 — 대규모 클러스터에서 컨트롤 플레인 재시작이 위험한 이유입니다.

## 실무 사고 사례

> 한 금융사의 K8s 클러스터가 어느 화요일 오후부터 "이상하게 느려"졌습니다. `kubectl get pods`가 3초, 배포가 2분씩 걸렸습니다. 애플리케이션은 멀쩡했습니다(이미 실행 중인 Pod는 영향 없었습니다). SRE 팀은 API 서버를 스케일하고, 컨트롤러를 재시작하고, 네트워크를 의심했습니다 — 그리고 컨트롤러 재시작이 상황을 **악화**시켰습니다(relist 폭풍). 사흘째, 한 엔지니어가 etcd 메트릭을 열었습니다: `wal_fsync_duration` p99가 340ms였습니다(정상은 5ms 이하). 원인은 두 달 전의 무해한 변경이었습니다 — 로그 수집기(Fluent Bit)의 버퍼를 디스크로 바꾸면서(14의 방어 설계!) 컨트롤 플레인 노드의 같은 디스크에 대량 I/O가 발생하기 시작했고, 그것이 etcd의 fsync와 경쟁했습니다. 두 달간 서서히 나빠졌고, 로그 볼륨이 임계를 넘은 화요일에 증상이 드러났습니다. 복구는 로그 버퍼를 별도 디스크로 옮기는 것으로 30분. 그러나 사후 분석은 더 많은 것을 드러냈습니다: ① etcd 메트릭이 대시보드에 없었습니다(있었다면 두 달 전에 보였습니다). ② `db_total_size`가 1.7GiB로 quota(2GiB)에 근접해 있었습니다 — Event가 keyspace의 60%였고, 아무도 몰랐습니다. ③ 백업은 매일 돌고 있었지만 `snapshot status` 검증이 없었고, 확인해보니 최근 12일치가 손상돼 있었습니다(디스크 포화로 쓰기가 잘렸습니다). 즉 **성능 문제가 백업 문제를 감추고 있었습니다.** 개선: etcd 6종 메트릭 알람, 전용 NVMe 분리, Event 전용 etcd, 스냅샷 status 검증 + 오프사이트, 분기 복구 리허설. 교훈: **etcd는 조용히 나빠지고, 조용히 백업을 망가뜨립니다** — 전제이기 때문에 아무도 안 보고, 안 보기 때문에 가장 늦게 발견됩니다.
