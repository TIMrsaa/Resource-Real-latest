# 학습 가이드 — 왜 모두가 같은 프록시를 쓰는가

## 로고 벽의 비밀

04에서 그린 계보도를 다시 보자:

```
Envoy ──┬─ Istio (사이드카/ambient의 데이터플레인)
        ├─ Contour (인그레스 컨트롤러)
        ├─ Emissary-ingress (API 게이트웨이)
        ├─ Envoy Gateway (Gateway API 구현)
        └─ 수많은 상용 게이트웨이의 코어
```

이들의 공통점은 "Envoy를 데이터플레인으로 쓴다"이고, 차이점은 "누가 Envoy에게 설정을 만들어주느냐"뿐입니다. 즉 이 프로젝트들은 서로 다른 프록시를 만든 것이 아니라, **같은 프록시에 다른 설정 생성기를 붙인 것**입니다. Contour vs Emissary를 비교할 때 데이터플레인(둘 다 Envoy)은 논점이 아니고 컨트롤플레인의 API·운영 모델만 논점이라는 것 — 04에서 예고한 이 통찰의 근거가 이 모듈입니다.

## xDS — 이 모든 것을 가능하게 한 한 가지

전통적 프록시(nginx, HAProxy)는 설정 파일을 읽고, 바꾸려면 리로드합니다. Envoy의 발명은 **설정을 gRPC 스트림으로 실시간 받는다**는 것입니다:

```
nginx:  파일 수정 → nginx -s reload (연결 끊김 가능, 파일 관리)
Envoy:  컨트롤플레인이 xDS 스트림으로 "이제 이 라우트를 추가해" → 무중단 반영
```

이 차이가 왜 혁명인가요? K8s에서 Pod는 계속 뜨고 죽습니다 — 백엔드 목록이 초 단위로 바뀝니다. 파일 리로드로는 못 따라갑니다. xDS는 그 변화를 스트림으로 밀어넣습니다. 그래서 Istio의 컨트롤플레인(istiod)이 하는 일의 본질은 "K8s를 watch해서 xDS로 번역"입니다 — 06의 OTel Collector가 신호를 번역하듯, istiod는 K8s 상태를 Envoy 설정으로 번역합니다.

## 이 모듈을 먼저 하는 이유

24(Istio)와 25(Linkerd)를 이해하려면 데이터플레인을 먼저 알아야 합니다. Istio를 "메시"로만 배우면 istiod가 무엇을 하는지, 사이드카가 왜 필요한지, ambient 모드가 무엇을 바꾸는지가 안 보입니다. Envoy를 직접 손으로 돌려보면(lab-01) 그 위의 모든 것이 "설정을 어떻게 생성하느냐"의 문제로 환원됩니다.

## 프록시는 라우팅만이 아닙니다

Envoy가 단순 프록시가 아닌 이유는 **필터 체인**입니다 — 요청이 리스너에 도착해 라우트로 가기까지 여러 필터(인증, rate limit, 헤더 조작, WASM 확장)를 통과합니다. 서킷 브레이커·아웃라이어 감지·재시도 같은 복원력 기능도 여기 있습니다. eks 14에서 ALB로 배운 L7 기능들의 오픈소스·확장 가능 버전이고, 22에서 본 Cilium의 L7 정책이 경유하는 그 Envoy이기도 합니다.
