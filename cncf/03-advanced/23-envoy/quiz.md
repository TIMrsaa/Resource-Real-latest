# 자가 점검 퀴즈

**Q1.** Envoy의 4계층(listener/route/cluster/endpoint)과 요청의 여정을 설명하세요. 각각은 xDS의 무엇에 대응하나요?

**Q2.** xDS가 "혁명"인 이유를 nginx의 파일 리로드와 대비해 설명하세요. 왜 K8s 시대에 특히 중요한가?

**Q3.** "Contour vs Emissary"가 데이터플레인 비교가 아닌 이유는? 04의 계보도로 설명하세요.

**Q4.** istiod가 하는 일의 본질을 한 문장으로 말하세요. 이것이 06의 무엇과 같은 종류의 일인가요?

**Q5.** 필터 체인에서 router 필터가 항상 마지막인 이유는? 그 앞에 오는 필터의 예 셋은?

**Q6.** 서킷 브레이커와 아웃라이어 감지의 차이는? 각각 무엇을 방어하나요?

**Q7.** Envoy 재시도의 위험 두 가지와 방어책은? 18의 무엇과 같은 계열인가요?

**Q8.** 메시 디버깅에서 config_dump가 왜 핵심인가요? CRD만 보면 놓치는 것은?

## 정답

**A1.** listener(어디서 받는가 — 포트·TLS·필터체인) → route(어디로 보내는가 — 도메인·경로 매칭으로 cluster 선택) → cluster(무엇의 그룹인가 — 백엔드 집합 + LB·복원력 정책) → endpoint(실제 인스턴스 IP:port). 요청은 이 순서로 흐릅니다. 대응: LDS(listener), RDS(route), CDS(cluster), EDS(endpoint) — 4계층이 xDS 네 종류와 정확히 대응합니다.

**A2.** nginx는 설정을 파일로 읽고 바꾸려면 리로드합니다(연결 끊김 가능, 파일 관리 부담). Envoy는 설정을 gRPC 스트림(xDS)으로 실시간 받아 무중단 반영합니다. K8s에서 중요한 이유: Pod가 초 단위로 뜨고 죽어 백엔드 엔드포인트 목록(EDS)이 끊임없이 바뀌는데, 파일 리로드로는 못 따라갑니다 — xDS는 그 변화를 스트림으로 밀어넣어 무중단으로 반영합니다. 이것이 K8s 시대에 Envoy가 프록시 표준이 된 핵심 이유입니다.

**A3.** 둘 다 Envoy를 데이터플레인으로 쓰므로 트래픽 처리 성능·프로토콜 지원의 상당 부분이 동일합니다 — 다른 것은 컨트롤플레인(설정 생성기)입니다: 어떤 CRD로 설정하는가(HTTPProxy vs Mapping), 운영 모델, Gateway API 지원. 04의 계보도가 보여주듯 이 프로젝트들은 서로 다른 프록시를 만든 것이 아니라 같은 프록시(Envoy)에 다른 컨트롤플레인을 붙인 것이므로, 비교의 축은 데이터플레인이 아니라 "어떤 API로 라우팅을 선언하고 싶은가"다.

**A4.** "K8s의 상태(Service·EndpointSlice·Istio CRD)를 watch해서 Envoy가 이해하는 xDS 설정으로 번역해 각 사이드카에 밀어넣습니다." 06의 OTel Collector가 다양한 신호를 받아 백엔드가 이해하는 형식으로 번역·전달하는 것과 같은 종류의 일입니다 — 둘 다 "한쪽의 표현을 다른 쪽의 표현으로 번역하는 컨트롤플레인/게이트웨이"다.

**A5.** router 필터가 실제 라우팅과 업스트림 전송을 수행하므로 — 그 앞의 필터들이 요청을 가공·검증·인증한 뒤 마지막에 목적지로 보내야 합니다(router 이후에는 필터가 실행될 기회가 없습니다). 앞에 오는 필터 예: cors(CORS), jwt_authn(JWT 인증), ext_authz(외부 인가 — OPA 호출), ratelimit(전역 rate limit), lua/wasm(커스텀 로직). 필터는 순서가 의미이며(12의 Collector processors, 20의 CoreDNS 체인과 같은 계열) router는 항상 종착점입니다.

**A6.** 서킷 브레이커: cluster로의 동시 연결·요청·대기 요청 수에 한도를 두어 초과 시 즉시 실패(빠른 실패) — 느린/과부하 백엔드가 프록시 리소스를 소진해 전체를 마비시키는 것을 방어합니다. 아웃라이어 감지: 연속 5xx 등으로 문제를 보이는 개별 엔드포인트를 로드밸런싱 풀에서 일시 격리(ejection) — 죽어가는 특정 인스턴스로 트래픽이 계속 가는 것을 방어합니다(수동적 헬스체크). 전자는 cluster 전체 부하 보호, 후자는 개별 인스턴스 격리.

**A7.** 위험 ① 비멱등 요청(POST)의 재시도가 중복 생성(중복 결제 등)을 일으킵니다 → retry_on을 멱등 요청·안전한 실패 유형(connect-failure, reset)에 한정. 위험 ② 백엔드 과부하 시 재시도가 부하를 증폭해 장애를 키웁니다(재시도 폭풍) → retry_budget으로 재시도를 전체 트래픽의 일정 비율로 제한, per_try_timeout을 전체보다 짧게. 18(KEDA)에서 "오토스케일러가 지키는 것은 replicas이지 메시지가 아니다"와 같은 계열 — 자동화(재시도)의 편의가 규율 없이 쓰이면 사고를 부릅니다.

**A8.** CRD(VirtualService·DestinationRule)는 설정의 **의도**이고, config_dump는 istiod가 실제로 Envoy에 밀어넣은 설정의 **실체**입니다 — 번역 버그·충돌·적용 지연으로 둘이 다를 수 있습니다. CRD만 보면 놓치는 것: DestinationRule의 아웃라이어 감지가 번역된 실제 Envoy 클러스터 설정(사고 사례에서 엔드포인트 플래핑의 원인), 여러 CRD의 병합 결과, 적용되지 않은/충돌한 설정. 메시를 운영한다는 것은 사이드카의 admin 인터페이스(:15000/config_dump, /clusters, /stats)로 실제 xDS 설정을 읽을 줄 안다는 것입니다.
