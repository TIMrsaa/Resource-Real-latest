# 학습 가이드 — 두 얼굴을 구분하기

## 09에서 예고한 혼동

09에서 "NATS vs Kafka는 어느 모드인지 밝혀야 성립한다"고 했습니다 — core NATS는 큐(pub/sub, fire-and-forget)이고 JetStream은 스트림(영속 로그)이라, "NATS"라고만 하면 둘 중 무엇을 말하는지 모릅니다. 이 모듈의 첫 목표는 그 두 얼굴을 명확히 구분하는 것입니다:

```
core NATS: 초경량 pub/sub — 메시지를 보내고 잊습니다(fire-and-forget)
  구독자 없으면 메시지 유실 (저장 안 함)
  용도: 실시간, 저지연, 서비스 디스커버리, request-reply

JetStream: 영속 스트림 — 메시지를 로그에 저장
  나중에 재생 가능, 여러 컨슈머, at-least-once
  용도: 이벤트 소싱, 재처리, 감사, Kafka 대안
```

같은 NATS 서버에서 둘 다 제공하지만 성격이 완전히 다릅니다 — 이 구분을 못 하면 "NATS는 메시지를 유실한다"(core만 보고)나 "NATS는 무겁다"(JetStream만 보고) 같은 절반의 오해가 생깁니다.

## 왜 하나의 시스템에 둘 다

NATS의 설계 철학은 "단순함에서 시작해 필요하면 영속성을 더한다"입니다:

```
core NATS: 극도로 단순·빠름 (수 MB 바이너리, 마이크로초 지연)
  → 대부분의 실시간 통신에 충분
JetStream: core 위에 영속성 계층 (필요할 때만 켭니다)
  → 스트림이 필요한 경우에만
```

이것은 25(Linkerd)의 "단순함도 설계", 27(CRI-O)의 미니멀리즘과 같은 계열입니다 — NATS는 "가벼운 기본 + 필요시 확장"을 택했습니다. Kafka가 처음부터 무거운 분산 로그인 것과 대비됩니다.

## 18·29와의 연결

NATS는 이 커리큘럼의 여러 곳에서 이미 등장했습니다:

```
18(KEDA): NATS JetStream 스케일러 — 미처리 메시지로 워커 스케일
29(Dapr): pub/sub 컴포넌트로 NATS — 앱이 표준 API로 발행/구독
09: 큐 vs 스트림 판단의 예시
```

이 모듈은 그 NATS 자체를 깊게 봄으로써, 18에서 스케일하던 그 큐/스트림이 무엇인지, 29에서 pub/sub하던 그 백엔드가 어떻게 동작하는지를 완성합니다.

## 선택 — NATS의 자리

NATS가 모든 메시징의 답은 아닙니다. 09에서 배운 판단("나중에 다시 읽어야 하는가")이 여기서도 적용되고, 추가로 규모·생태계가 요인입니다:

```
NATS가 빛나는 곳: 초경량, 저지연, 엣지·IoT, 마이크로서비스 통신, 멀티테넌시
Kafka가 빛나는 곳: 대규모 로그, 풍부한 생태계(Connect·Streams), 초고처리량
→ "가벼운 실시간 + 필요시 스트림"이면 NATS, "대규모 이벤트 로그"면 Kafka
```
