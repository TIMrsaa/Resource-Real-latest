# 학습 가이드 — 컨테이너가 아닌 것을 컨테이너 플랫폼에

## 왜 VM을 K8s에?

컨테이너가 모든 것을 대체하지 못합니다. 현실에는 컨테이너로 못 옮기는 워크로드가 있습니다:

```
레거시 앱: 컨테이너화 비용이 재작성 수준 (수십 년 된 모놀리스)
특수 OS: Windows(일부), 특정 커널 버전 의존
커널 모듈: 컨테이너는 호스트 커널 공유 → 자체 커널이 필요한 것
완전 격리: 규제상 VM 수준 격리 필요 (03의 격리 스펙트럼 오른쪽 끝)
하드웨어 접근: 특정 디바이스·드라이버
```

이런 것들을 위해 별도 가상화 인프라(vSphere 등)를 유지하는 것과, K8s 하나로 컨테이너와 VM을 함께 관리하는 것 중 후자를 원할 때 KubeVirt가 답입니다. "인프라를 하나의 API(K8s)로 통일"이 KubeVirt의 가치 제안입니다.

## 08의 질문 "무엇 위의 추상인가"

08에서 5단의 네 주민을 구분했습니다: Knative(워크로드 위), Dapr(앱 코드 위), Crossplane(인프라 위), Backstage(조직 위). KubeVirt는 **VM 위**입니다 — 가상머신을 K8s 리소스(VirtualMachine CRD)로 선언하고, K8s의 스케줄러·네트워킹·스토리지를 VM에 적용합니다.

핵심 트릭은 "VM을 Pod 안에서 돌리는 것"입니다. VM(QEMU 프로세스)을 컨테이너로 감싸면, K8s는 그것을 Pod로 취급해 스케줄링·네트워킹을 적용할 수 있습니다. 컨테이너 네이티브가 아닌 것을 컨테이너 네이티브 플랫폼에 끼워 넣는 영리한 방법입니다.

## 근본적 긴장

그러나 이 끼워 넣기에는 대가가 있습니다. K8s의 전제와 VM의 성질이 충돌합니다:

```
K8s 전제           VM 성질
무상태             상태 있음 (디스크, 메모리)
재생성 저렴        재생성 비쌈 (부팅 시간, 상태 재구성)
수명 짧음          수명 김 (몇 달씩)
Pod 이동 자유      VM 이동 = 라이브 마이그레이션(복잡)
수평 확장          수직 확장이 흔함
```

09에서 배운 "스테이트풀을 K8s에" 판단 프레임이 여기서 극대화됩니다 — VM은 가장 스테이트풀한 워크로드입니다. KubeVirt는 이 긴장을 라이브 마이그레이션, 영속 스토리지 통합, VM 특화 CRD로 완화하지만 없애지는 못합니다.

## 이 모듈의 정직함

KubeVirt는 "컨테이너로 다 되니 VM은 필요 없다"도, "VM이 더 나으니 KubeVirt로 다 하자"도 아닙니다. **컨테이너화할 수 없는 것을, 별도 인프라 없이, 같은 K8s API로 관리하고 싶을 때**의 도구입니다. 그 범위를 정확히 아는 것 — 언제 쓰고 언제 안 쓰는가 — 이 이 모듈의 목적입니다.
