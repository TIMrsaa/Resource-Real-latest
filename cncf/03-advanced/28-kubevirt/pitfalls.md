# 흔한 함정 5선

## 1. 컨테이너화할 수 있는 것을 "편해서" VM으로

KubeVirt가 있으면 "재작성 귀찮으니 VM으로 K8s에 올리자"는 유혹이 생깁니다 — 그러나 VM은 장기적으로 컨테이너보다 비쌉니다(스토리지·마이그레이션·백업·복잡도). 컨테이너화 가능한 워크로드는 대개 재작성 비용이 몇 달의 VM 운영 부담보다 작습니다. KubeVirt는 **컨테이너화할 수 없는 것**을 위한 도구이고, 그 판단을 흐리면 K8s 위에 관리하기 어려운 VM 팜이 쌓입니다. "이것을 컨테이너로 만들 수 있는가"를 먼저 묻고, 답이 Yes면 KubeVirt가 아니라 컨테이너화가 답입니다.

## 2. VM에 컨테이너의 무상태 습관을 적용

liveness probe가 실패하면 컨테이너는 재시작하면 그만입니다 — VM에서 재시작은 게스트 OS 재부팅이고 인메모리 상태 손실입니다. 컨테이너의 "죽으면 새로 만들기" 습관을 VM에 적용하면(공격적 liveness, replicas식 사고, PVC 없이 운영) 상태를 잃습니다. VM은 09에서 배운 가장 스테이트풀한 워크로드입니다 — probe는 신중히, 스토리지는 영속(PVC/DataVolume)으로, 그리고 "이 VM을 죽이면 무엇을 잃나"를 항상 의식하세요. 컨테이너 네이티브 습관은 컨테이너 네이티브가 아닌 워크로드에서 사고가 됩니다.

## 3. 노드 드레인이 라이브 마이그레이션임을 간과

k8s 35의 노드 업그레이드에서 드레인은 컨테이너 Pod를 다른 노드에 재생성하면 끝이지만, VM에게는 라이브 마이그레이션(메모리 복사 + 전환) 또는 상태 손실을 의미합니다. 라이브 마이그레이션은 공유 스토리지(RWX)·네트워크 대역·마이그레이션 정책을 요구하고, 이것이 준비되지 않으면 드레인이 VM을 죽입니다. VM 노드의 드레인 정책, PodDisruptionBudget, 마이그레이션 설정을 클러스터 업그레이드 계획에 반드시 넣어라(09의 StatefulSet 교훈의 확대). "노드 유지보수 중 VM이 죽었다"는 이 준비 부재의 전형입니다.

## 4. 스토리지·백업을 나중에 생각

VM은 디스크가 곧 워크로드입니다 — 스토리지 설계(05)와 백업(k8s 36)이 KubeVirt 운영의 핵심인데, "일단 VM 띄우고 스토리지는 나중에"로 시작하면 containerDisk(무상태)로 운영하다 데이터를 잃거나, PVC를 썼는데 백업이 없어 노드 장애 시 복구 불능이 됩니다. 채택 전에 정해야 합니다: 어떤 스토리지 클래스(블록 RWO? 마이그레이션 위한 RWX?), VM 스냅샷 전략, 디스크 백업(Velero + CDI), 그리고 복구 리허설. VM은 가장 스테이트풀하므로 05·09·36의 모든 교훈이 최대로 적용됩니다.

## 5. 복잡도 2배를 과소평가

KubeVirt를 운영한다는 것은 K8s와 가상화(libvirt/QEMU/KVM) **양쪽**을 아는 것입니다 — VM이 안 뜨는 문제가 K8s 층(스케줄·스토리지)인지 가상화 층(QEMU·KVM·게스트 OS)인지를 구분해야 하고(08의 추상 누수가 여기서 극심), 두 세계의 도구·개념·장애 모드를 모두 다뤄야 합니다. "K8s를 아니까 KubeVirt도 금방"은 착각입니다. 가상화 운영 경험이 없는 팀이 KubeVirt를 도입하면 VM 문제 앞에서 마비됩니다. 도입 전에 가상화 지식(libvirt, VM 마이그레이션, 게스트 튜닝)을 확보하거나, 그 학습 곡선을 프로젝트 계획에 넣어라.

## 실무 사고 사례

> 한 금융사가 20년 된 정산 시스템을 K8s로 옮기려 했습니다 — 그 시스템은 특정 커널 버전과 하드웨어 보안 모듈(HSM)에 의존해 컨테이너화가 사실상 불가능했습니다. KubeVirt가 정답으로 보였고, 실제로 옳은 선택이었습니다: 별도 vSphere 라이선스를 줄이고 컨테이너 워크로드와 같은 K8s API로 관리할 수 있었습니다. 도입 자체는 성공이었습니다. 문제는 운영 6개월 차에 왔습니다. ① 첫 클러스터 업그레이드(k8s 35) 때, 팀은 컨테이너 습관대로 노드를 드레인했고 — 정산 VM들이 라이브 마이그레이션 설정 없이 죽으며 진행 중이던 배치가 손실됐습니다(다행히 재실행 가능한 배치였습니다). ② VM 디스크를 PVC로 썼지만 백업은 컨테이너 워크로드용 Velero 설정 그대로였고, VM 디스크의 정합성 있는 스냅샷(CDI 연동)이 아니어서 복구 테스트에서 디스크가 깨졌습니다. ③ 어느 VM이 부팅에 실패했을 때, K8s 팀은 Pod 이벤트만 봤고(정상) 실제 원인은 게스트 OS의 fstab 문제였는데 아무도 게스트 콘솔(virtctl console)을 볼 줄 몰랐습니다 — 가상화 지식의 공백이었습니다. 개선은 세 방향이었습니다: ① VM 노드에 라이브 마이그레이션 정책 + PDB + RWX 스토리지, 클러스터 업그레이드 절차에 VM 마이그레이션 단계 추가. ② CDI 연동 VM 스냅샷 + 정합성 있는 백업 + 분기 복구 리허설(k8s 36). ③ 가상화 경험자를 팀에 합류시키고 K8s 팀에 libvirt/QEMU 기초 교육. 회고 문장이 이 모듈의 요지였습니다: "KubeVirt 도입은 옳았지만, 우리는 그것이 **K8s 프로젝트가 아니라 K8s + 가상화 프로젝트**임을 몰랐습니다 — 컨테이너 네이티브가 아닌 것을 K8s에 올리면, 컨테이너 네이티브가 아닌 운영 지식도 함께 필요합니다."
