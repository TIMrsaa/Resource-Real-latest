# 학습 가이드 — 메시를 "마법"에서 "번역"으로 내리기

## Istio를 신비화하지 않기

메시를 처음 배우면 "코드 수정 없이 mTLS·트래픽 관리·관측이 생긴다"는 것이 마법처럼 보입니다. 23을 거친 지금은 그것을 정확히 분해할 수 있습니다:

```
istiod = K8s 상태 + Istio CRD를 watch → Envoy xDS 설정으로 번역 → 사이드카에 push
사이드카(Envoy) = 그 설정대로 트래픽을 처리 (mTLS 종단, 라우팅, 통계)
→ "마법"의 실체 = 23에서 배운 Envoy 기능 + 그것을 자동 설정하는 번역기
```

VirtualService는 Envoy의 route가 되고, DestinationRule은 Envoy의 cluster(LB·아웃라이어)가 되고, PeerAuthentication은 Envoy의 TLS 설정이 됩니다. lab-01에서 CRD를 만들고 그것이 사이드카의 config_dump에 나타나는 것을 직접 확인합니다 — 메시 디버깅의 근본 기술입니다(23 사고 사례).

## 세 가지 기능, 하나의 데이터플레인

Istio가 파는 것은 셋입니다:

```
트래픽 관리: 카나리·트래픽 분할·미러링·재시도·타임아웃 (17의 Progressive Delivery가 이 위에)
보안:        mTLS(서비스 간 자동 암호화·인증) + 인가(AuthorizationPolicy) — 07의 신원 축
관측:        자동 메트릭·트레이스·액세스 로그 (사이드카가 모든 트래픽을 봄 — 06)
```

셋 다 Envoy의 기능이고, Istio는 그것을 K8s 네이티브하게 만든 것입니다. eks 20에서 사용자로 이 셋을 만졌다면, 여기서는 각각이 어느 Envoy 설정으로 환원되는지를 봅니다.

## ambient — 메시의 자기 부정

2023년 이후 Istio의 가장 큰 변화는 **사이드카를 없애는 것**입니다. 사이드카 모델의 대가(Pod마다 Envoy 컨테이너 = 메모리·CPU·시작 지연·업그레이드 시 전체 재시작)가 메시 도입을 막는 큰 이유였습니다. ambient는 이것을 둘로 쪼갭니다:

```
ztunnel (노드당 하나): L4(mTLS·인증) — 가벼운 노드 프록시
waypoint (필요시):     L7(라우팅·인가) — 네임스페이스/서비스 단위로 선택적
→ "mTLS만 원하면 ztunnel만, L7 기능이 필요하면 waypoint 추가"
```

이것이 왜 중요한가? 22(Cilium)에서 "L7은 필요한 곳에만"을 배웠습니다 — ambient는 그 원칙을 메시 아키텍처에 새긴 것입니다. 대부분의 워크로드는 L4 mTLS만 필요하고, L7 기능(HTTP 라우팅·인가)은 소수에만 필요합니다. ambient는 그 현실에 맞춰 비용을 지불합니다.

## "정말 메시가 필요한가"

이 모듈은 Istio 도입을 권하지 않습니다. eks 20에서 물었던 질문이 여기서도 유효합니다: mTLS·트래픽 관리·관측 중 몇 개가 실제 요구인가요? mTLS만이면 더 가벼운 수단(Cilium 투명 암호화, ambient의 ztunnel만)이, 카나리만이면 Argo Rollouts + Gateway API(17)가 답일 수 있습니다. 메시는 세 요구가 겹칠 때, 그리고 그 복잡도를 운영할 팀이 있을 때의 답입니다.
