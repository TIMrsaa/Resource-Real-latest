# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. resource requests 미설정 → 노드 계산 오작동
Karpenter(와 CA)는 Pod의 `requests`로 필요한 노드 크기를 계산합니다. requests가 없으면 스케줄러는 Pod를 "0 리소스"로 보고, Karpenter는 노드 크기를 잘못 잡습니다 → 노드가 과부하되거나 통합이 Pod를 너무 많이 몰아넣습니다. **정확한 requests는 노드 오토스케일의 절대 전제**(08). requests 없는 Pod는 노드 오토스케일 세계에서 시한폭탄입니다.

### 2. PDB 없이 통합·중단 → 순간 가용성 붕괴
Karpenter가 통합·노드 만료로 노드를 제거할 때 Pod를 drain합니다. PDB가 없으면 한 노드의 여러 replica가 **동시에** 퇴거될 수 있습니다 → 그 순간 서비스가 비거나 용량이 급락합니다. `minAvailable`/`maxUnavailable` PDB로 동시 퇴거를 제한해야 합니다(09). 노드가 동적인 세계에서 PDB는 선택이 아니라 필수입니다.

### 3. 스팟 100% → 대량 동시 회수
스팟은 저렴하지만 클라우드가 회수할 수 있습니다. NodePool을 스팟 단일 타입 100%로 두면, 그 타입이 대량 회수될 때 **많은 노드가 동시에** 사라집니다 → 대규모 재스케줄·용량 부족. 완화: 다양한 인스턴스 타입 허용(회수가 분산됨), 스팟+온디맨드 혼합, 중요 워크로드는 온디맨드. 스팟은 중단을 견디는 상태 없는 워크로드에.

### 4. 과도한 통합 → churn 폭발
`consolidateAfter`를 너무 짧게(적극적으로) 두면 Karpenter가 끊임없이 노드를 재편해 Pod가 계속 이동합니다 → 재시작·연결 끊김·캐시 무효화가 반복됩니다. 특히 부하가 자주 오르내리면 통합과 확장이 진동(flapping)할 수 있습니다. 워크로드 안정성이 중요하면 통합을 보수적으로(길게), 배치·내성 워크로드면 적극적으로. **비용과 안정성의 다이얼**입니다.

### 5. 스테이트풀 워크로드를 순진하게 노드 오토스케일에 맡김
데이터베이스·Kafka(40)·Ceph(39) 같은 스테이트풀은 노드가 사라지면 데이터·쿼럼에 직접 영향받습니다(09). Karpenter의 통합이 상태 Pod를 이동시키면 리밸런싱·복구가 유발되고, 최악엔 쿼럼 손실입니다. 스테이트풀은 전용 NodePool(통합 비활성 또는 보수적)에 두거나, `karpenter.sh/do-not-disrupt` 애너테이션으로 보호하고, 관리형(RDS·MSK)을 우선합니다(09·39·40의 반복).

## 실무 사고 사례: "통합이 데이터베이스 쿼럼을 무너뜨리다"

한 팀이 비용 절감을 위해 Karpenter를 전면 도입했습니다. 적극적인 통합(consolidateAfter: 30s)으로 클라우드 비용이 눈에 띄게 줄어 만족했습니다. 스테이트리스 서비스들은 잘 돌았습니다.

문제는 같은 클러스터에 **3-노드 etcd 기반 내부 도구**(작은 분산 DB)를 셀프 호스팅하고 있었다는 것입니다. 이 DB의 Pod에는 PDB도, `do-not-disrupt`도 없었습니다. 어느 밤, 전체 부하가 낮아지자 Karpenter가 통합을 시작했습니다:

1. DB Pod 3개가 서로 다른 노드에 있었는데, 통합이 노드들을 합치며 **DB Pod 2개를 거의 동시에** 다른 노드로 이동시키려 drain했습니다.
2. PDB가 없어 2개가 동시에 퇴거됐습니다 → 3-노드 쿼럼에서 2개 손실 → **쿼럼 상실**(21의 과반 규칙).
3. DB가 읽기 전용으로 전환되며 그 위 내부 도구들이 마비됐습니다.
4. Pod들이 새 노드에서 다시 떴지만, 급작스런 다중 이동으로 일부 데이터가 재동기화 필요 상태가 됐고 복구에 시간이 걸렸습니다.

원인 분석:

1. **스테이트풀에 무방비 노드 오토스케일** — 09·39·40에서 반복한 "스테이트풀은 노드 이동에 취약"을 무시했습니다.
2. **PDB 부재** — 21의 쿼럼(과반)을 지키려면 동시 퇴거를 1개로 제한하는 PDB가 필수였습니다.
3. **통합이 너무 적극적** — 30초는 스테이트풀에 너무 공격적이었습니다.
4. **워크로드 분리 없음** — 스테이트리스와 스테이트풀이 같은 NodePool·통합 정책을 공유했습니다.

**교훈:**
- 스테이트풀은 **전용 NodePool** + 통합 보수적/비활성 + `do-not-disrupt`로 보호
- 쿼럼 기반(etcd·Kafka·Ceph, 21)은 **PDB로 동시 퇴거를 반드시 제한**(minAvailable로 과반 보장)
- 노드 오토스케일의 비용 절감은 **스테이트리스에서 크고, 스테이트풀에선 위험** — 관리형 우선(09)
- 통합 정책은 워크로드별로 — 하나의 공격적 정책을 전체에 적용하지 말 것
- **자동화(통합)가 물리(노드는 Pod를 옮겨야 사라짐)를 숨기지만 없애지 않습니다** — 37·39·41·43에서 반복된 교훈이 노드 층에서도

★ Karpenter(44)는 노드를 실시간으로 빚어 비용·속도를 최적화하는 강력한 도구지만, 그 힘은 "노드가 언제든 생기고 사라진다"는 전제를 워크로드에 강요합니다. 스테이트리스는 이를 잘 견디지만, 스테이트풀(특히 쿼럼 기반, 21)은 무방비면 무너집니다. 노드 오토스케일의 자유는 워크로드의 중단 내성(PDB·graceful shutdown·상태 외부화)이라는 규율을 요구합니다 — 이것이 데이터 트랙(36~40)과 플랫폼 트랙(41~44)을 관통하는 결론입니다.
