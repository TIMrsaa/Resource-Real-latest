# 학습 가이드 — 두 층의 스케일

## 스케일의 두 층 — Pod와 노드

지금까지 배운 오토스케일은 모두 **Pod** 층이었습니다:

```
HPA(08): 부하로 Pod 수 늘림 (replicas ↑)
KEDA(18): 이벤트로 Pod 수 늘림 (0↔N)
Knative(43): 요청으로 Pod 0↔N (scale-to-zero)
VPA(08): Pod의 리소스 요청 조정
→ 전부 "Pod를 몇 개, 얼마나 크게"
```

그런데 Pod는 **노드 위에서** 돕니다. Pod를 100개로 늘렸는데 노드에 공간이 없으면? Pod는 `Pending`(스케줄 못 됨) 상태로 멈춥니다. 그래서 **노드 층 오토스케일**이 필요합니다:

```
노드 오토스케일: Pending Pod가 있으면 노드를 늘리고,
               노드가 놀면(비면) 줄입니다
도구: Cluster Autoscaler(전통), Karpenter(진화형)
```

이 모듈은 이 **노드 층**을 다룹니다. Pod 스케일(HPA·KEDA·Knative)이 노드 스케일과 **협력**해야 완전한 탄력성이 됩니다.

## 08의 스케줄링이 열쇠

08에서 스케줄러가 Pod를 노드에 배치하는 것(리소스 요청·노드 셀렉터·어피니티·taint)을 배웠습니다. 노드 오토스케일은 그 **역방향**입니다:

```
08 스케줄러: "이 Pod를 어느 (기존) 노드에 놓지?"
Karpenter:   "이 Pending Pod들을 놓으려면 어떤 노드를 만들지?"
→ 스케줄링을 거꾸로 풀어 노드를 빚습니다
```

Karpenter를 이해하려면 08의 스케줄링(리소스 요청·제약)을 정확히 알아야 합니다 — Karpenter는 그 제약을 만족하는 노드를 고르기 때문입니다.

## Cluster Autoscaler vs Karpenter — 핵심 대비

```
Cluster Autoscaler (전통):
  미리 노드그룹(예: m5.large 10개짜리)을 정의
  Pending Pod → 노드그룹의 노드 수를 늘림
  제약: 노드그룹이 고정 타입 → 딱 안 맞을 수 있음
        (작은 Pod에 큰 노드, 큰 Pod에 작은 노드그룹뿐)

Karpenter (진화):
  노드그룹 없이, Pending Pod의 실제 요구를 봄
  "이 Pod들엔 이 크기·타입 노드가 최적"을 계산해 즉시 프로비저닝
  → just-in-time, 딱 맞는 노드 (빈패킹 최적)
  + 통합(consolidation): 놀거나 비효율 노드를 더 싼 구성으로 재편
```

이 차이(고정 노드그룹 vs 동적 딱 맞춤)가 Karpenter의 핵심 가치입니다 — 비용 절감(딱 맞는 크기·스팟 활용)과 속도(직접 프로비저닝, 노드그룹 스케일 대기 없음).

## "CNCF" 관점 — 왜 이 모듈은 클라우드 중립인가

Karpenter는 AWS가 만들었지만, 이제 **Kubernetes 프로젝트**로 core와 cloud-provider가 분리됐습니다:

```
karpenter-core: 클라우드 중립 로직 (Pod 관찰·노드 결정·통합)
provider(AWS/Azure/...): 실제 노드를 만드는 부분
→ Crossplane(41)의 provider 모델과 유사한 분리
```

그래서 이 모듈은 특정 클라우드 API가 아니라 **노드 오토스케일링의 원리**에 집중합니다. eks 파트에서 AWS 특화 Karpenter를 다룬다면, 여기선 "왜 이렇게 동작하나"의 원리입니다. 실제 노드 프로비저닝은 클라우드가 필요하므로, 랩은 개념(Pending Pod·스케줄링·빈패킹)을 kind로 익힙니다.

## 판단 축 — 노드 오토스케일의 대가

노드를 동적으로 빚는 것은 강력하지만 대가가 있습니다:

```
+ 비용 최적 (딱 맞는 크기, 스팟, 통합으로 낭비 제거)
+ 빠른 확장 (노드그룹 우회, 직접 프로비저닝)
- 노드 churn (통합이 노드를 자주 교체 → Pod 재스케줄)
- 중단 관리 (노드가 사라질 때 Pod 이동 — PDB·drain 필수)
- 스팟 중단 (싸지만 회수될 수 있음)
```

09의 노드 관리·PDB, 43의 "자동화가 물리를 숨기지만 없애지 않음"이 여기서 다시 나옵니다 — 노드가 자동으로 생기고 사라지는 세계에서 **워크로드의 중단 내성**(PDB·graceful shutdown)이 더 중요해집니다.
