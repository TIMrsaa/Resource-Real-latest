# 학습 가이드 — 지도를 완성하는 법

## 왜 라운드업인가

advanced 트랙에서 우리는 프로젝트를 깊게 팠습니다 — Prometheus의 카디널리티, Ceph의 CRUSH, Karpenter의 빈패킹. 하지만 CNCF 랜드스케이프에는 수백 개의 프로젝트가 있고, 계속 늘어납니다. **모두를 깊게 배울 수는 없습니다.** 그럴 필요도 없습니다.

진짜 필요한 능력은 05에서 배운 것입니다:

```
05의 교훈: 랜드스케이프는 외우는 게 아니라 항해하는 것
  새 프로젝트를 만나면 →
    "어느 축(관측·네트워크·스토리지·보안·런타임...)인가요?"
    "이미 아는 무엇의 대안·보완인가요?"
    "왜 존재하나(어떤 문제를 좁혀 푸나)?"
  → 이 세 질문으로 지도에 즉시 놓습니다
```

이 모듈은 그 항해술을 **실전 프로젝트들로 연습**합니다. 각 프로젝트를 깊이 아는 게 아니라, 만났을 때 당황하지 않고 위치시키는 것이 목표입니다.

## 범주별 접근 — 축으로 묶기

낱개로 외우면 금세 잊습니다. 01~10의 축으로 묶으면 기억되고 새 프로젝트도 그 축에 붙습니다:

```
관측(06·11·12): Thanos, Cortex, Mimir, Loki, Pixie, ...
네트워크(04·26·27): Submariner, Antrea, Kube-OVN, ...
보안(07·28·30·31·32): in-toto, Notary, Keylime, Kubescape, ...
런타임·워크로드(25·29): WasmEdge, Kubevirt(다룸), Volcano, ...
CI/CD·GitOps(13·14·15): Keptn, Devfile, Score, ...
스토리지·데이터(36·39): Longhorn(다룸), OpenEBS, ...
멀티클러스터: Karmada, Open Cluster Management, ...
비용·FinOps: OpenCost, KubeCost, ...
```

각 프로젝트를 "이 축의, 이미 배운 X의 변형/대안"으로 자리매김하는 게 핵심입니다.

## 이미 배운 것과의 연결이 열쇠

새 프로젝트를 고립돼 배우면 안 됩니다. 항상 아는 것에 연결합니다:

```
Thanos/Cortex/Mimir → "11 Prometheus의 장기 저장·수평 확장" (같은 문제)
Loki → "11이 메트릭이라면, 이건 로그의 Prometheus식 접근"
OpenCost → "비용을 06의 관측처럼 — 리소스 사용을 돈으로"
Karmada → "14·15의 GitOps를 여러 클러스터로"
Volcano → "08의 스케줄러를 배치·AI 워크로드에 특화"
Score/Devfile → "42 Backstage·41 Crossplane과 같은 플랫폼 축"
```

연결이 되면 "새것"이 아니라 "아는 것의 변주"가 됩니다 — 이것이 05의 항해술입니다.

## 성숙도와 채택 판단 (08 종합)

Incubating·Sandbox는 Graduated보다 젊습니다. 채택엔 08의 판단이 필요합니다:

```
Sandbox: 초기·실험적 — 프로덕션은 신중, 트렌드 관찰용
Incubating: 검증 진행 — 채택 사례 확인 후 신중히
Graduated: 성숙 — 프로덕션 후보

판단 축(08·39·40의 반복):
  성숙도 + 채택 사례 + 커뮤니티 활성 + 대안 대비 이점
  + "설치의 쉬움 ≠ 운영의 쉬움"
  + 관리형/대안이 충분하면 그것
```

## 이 모듈의 정직한 태도 — 경계 긋기

이 커리큘럼은 CNCF의 많은 것을 다뤘지만 전부는 아닙니다. 이 모듈은 **다룬 것과 안 다룬 것의 경계**를 정직하게 긋고, 안 다룬 것을 만났을 때 스스로 배우는 법을 줍니다. 백과사전이 모든 항목을 담을 수 없듯, 중요한 것은 **찾아보는 법과 위치시키는 법**입니다. 그것이 contributor(49~50)의 태도이기도 합니다 — 모르는 프로젝트에 기여하려면 먼저 지도에 놓을 줄 알아야 합니다.
