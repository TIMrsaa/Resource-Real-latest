# 학습 가이드 — 신원의 근본 문제

## 반복된 주제의 뿌리

이 커리큘럼은 "비밀번호를 신원 증명으로"를 계속 반복했습니다:

```
cicd 07: AWS 키(장기 시크릿) → OIDC 토큰(단명 신원)
cicd 21: 서명 키 → keyless(OIDC 신원 기반 서명)
eks:     Pod의 클라우드 키 → IRSA(신원 기반)
24:      서비스 간 통신에 SPIFFE ID 기반 mTLS
```

이것들이 전부 같은 질문의 변주였습니다: **"이것(워크로드)이 진짜 누구인지를, 공유된 비밀 없이 어떻게 증명하나요?"** SPIFFE/SPIRE는 그 질문에 대한 근본적·표준적 답입니다.

## 왜 IP도 시크릿도 답이 아닌가

전통적으로 서비스를 식별하는 두 방법이 있었습니다:

```
IP 주소: "10.1.2.3에서 오면 결제 서비스"
  → K8s에서 Pod IP는 계속 바뀝니다. 그리고 IP는 위조 가능(스푸핑)
공유 시크릿: "이 API 키를 아는 자가 결제 서비스"
  → 시크릿 유출 = 신원 도용. 시크릿을 어떻게 안전하게 전달?(부트스트랩 문제)
```

SPIFFE의 답: **암호학적으로 검증 가능한 신원 문서(SVID)를 워크로드에 발급**합니다. Pod가 재생성되어 IP가 바뀌어도 신원은 같고(22의 Cilium identity와 같은 문제의식), 공유 시크릿이 아니라 각자의 검증 가능한 인증서라 유출돼도 그 워크로드 하나뿐입니다.

## 부트스트랩 신뢰 — turtles all the way down

SPIFFE/SPIRE의 가장 깊은 통찰은 부트스트랩 문제입니다:

```
워크로드에게 신원을 주려면 → "네가 진짜 그 워크로드임"을 먼저 확인해야
확인하려면 → 뭔가를 검증해야 → 그 뭔가의 신뢰는 어디서?
→ 무한 후퇴 (turtles all the way down)
```

이것이 07에서 OIDC를 "부트스트랩 시크릿 없는 신원"이라 한 것의 심층입니다. SPIRE의 답: **어테스테이션(attestation)** — 워크로드가 자기가 누구라고 "주장"하는 게 아니라, 플랫폼의 검증 가능한 속성(이 노드가 이 클라우드의 이 인스턴스인가, 이 프로세스가 이 K8s SA의 Pod인가)으로 신원을 **증명**합니다. 노드를 증명하고, 그 노드 위에서 워크로드를 증명하는 신뢰의 사슬입니다.

## 이 모듈이 통일하는 것

SPIFFE ID는 24(Istio)의 mTLS 신원이고, 21(keyless)의 OIDC 신원과 같은 계열이며, 07의 신원 축의 인프라입니다. 이 모듈은 흩어져 있던 "신원" 조각들이 하나의 표준(SPIFFE) 위에 모이는 것을 보여줍니다 — 서비스 메시, 서명, 클라우드 접근이 전부 같은 "검증 가능한 워크로드 신원"을 공유할 수 있다는 것이 SPIFFE의 비전입니다.
