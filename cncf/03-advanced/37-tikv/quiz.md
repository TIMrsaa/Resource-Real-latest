## 정답

**A1.** Vitess는 기존 MySQL을 샤딩으로 확장하는 접근이고(출발: 이미 있는 MySQL, 샤딩: 명시적으로 VSchema로 사용자가 정의), TiKV는 처음부터 분산으로 설계된 트랜잭션 KV입니다(출발: 분산 네이티브, 샤딩: 자동으로 Region 단위로 시스템이 관리). Vitess는 "기존 MySQL 자산을 무한히 확장", TiKV는 "분산이 필요하면 처음부터 분산 설계된 것을"이라는 철학입니다. 확장이냐 재설계냐의 차이.

**A2.** Region은 연속된 키 범위(예: [a, m))의 데이터 조각으로 각 Region이 독립된 Raft 그룹(3 복제본)입니다. 자동 관리: 데이터가 쌓여 Region이 커지면 자동 분할(split), 작은 것들은 병합(merge), 부하 불균형이면 PD가 노드 간 이동(balance) — 사용자·앱은 Region을 모릅니다(완전 자동). Vitess의 샤드는 사용자가 VSchema로 명시적으로 정의하고 리샤딩도 명시적으로 실행하지만, TiKV의 Region은 시스템이 자동으로 나누고 옮깁니다("자동 샤딩" vs "명시적 샤딩").

**A3.** 같은 점: 21의 Raft 알고리즘(리더 선출·로그 복제·쿼럼) 그대로 — Region 리더가 로그를 append하고 과반(3중 2)이 복제하면 커밋합니다. 다른 점: etcd는 하나의 Raft 그룹(작은 클러스터 메타데이터)이지만 TiKV는 각 Region이 Raft 그룹이라 수만 개가 동시에 돕니다(multi-Raft). 스케일 도전: 수만 그룹의 하트비트·선거를 효율적으로 처리해야 해서 batching·hibernation(유휴 Region의 Raft를 잠재움) 같은 최적화가 필요합니다 — etcd(단일 그룹)에 없던 문제입니다.

**A4.** ① Region 메타데이터(어느 Region이 어느 노드에 — 라우팅), ② 스케줄링(Region split/merge/balance 결정), ③ TSO(Timestamp Oracle — 전역 타임스탬프로 트랜잭션 순서). 36의 VTctld(관리·리샤딩 오케스트레이션)와 Topology(메타데이터)를 합치고 더 자동화한 것에 대응합니다 — Vitess는 사람이 리샤딩을 실행하지만 PD는 자동으로 스케줄링합니다. PD 자체는 etcd 기반(21)이라 SPOF이며 HA·성능이 중요합니다.

**A5.** Percolator 모델(Google) 기반 — 2PC(2단계 커밋) + MVCC이고, PD의 TSO(전역 타임스탬프)로 트랜잭션 순서를 정합니다. Vitess는 크로스 샤드 트랜잭션이 부담이라(2PC를 신중히 써야 하고 성능 주의) 가급적 단일 샤드에 트랜잭션을 가두는 반면, TiKV는 여러 Region에 걸친 분산 트랜잭션이 설계에 내장되어 자연스럽습니다 — "처음부터 분산" 설계의 이점으로 분산 트랜잭션이 1급 기능입니다.

**A6.** ① Raft(합의): etcd가 클러스터 메타데이터를 단일 Raft 그룹으로 복제하던 것이 TiKV에서 데이터를 Region마다 Raft로 복제하는 multi-Raft로. ② MVCC(버전): etcd의 리비전(resourceVersion)이 TiKV의 트랜잭션 버전(Percolator)으로. ③ 디스크(fsync): "etcd fsync가 K8s를 정한다"가 "RocksDB 성능이 TiKV를 정한다"로. ④ etcd 자체: PD가 etcd 기반. 21의 분산 시스템 원리(합의·버전·디스크·SPOF)가 메타데이터에서 대규모 데이터 저장으로 일반화됩니다 — 이것이 분산 상태 시스템의 공통 언어입니다.

**A7.** 자동 샤딩은 데이터 분포(Region 크기)를 관리하지만 접근 패턴의 편향은 못 막습니다 — 순차 키(auto-increment ID, 타임스탬프)를 쓰면 모든 새 쓰기가 "가장 최근" Region 하나에 몰려(write hotspot), 자동 분할·밸런싱으로도 그 한 Region이 병목이 됩니다(사고 사례: 이벤트 로그의 타임스탬프 키). 키 설계(해시 접두사 등)로 쓰기를 분산해야 합니다. Vitess에서 "샤딩 키를 고려한 쿼리 설계"가 필요했듯, TiKV에서도 "핫스팟을 피하는 키 설계"가 필요합니다 — 자동화는 물리(데이터가 어디에)를 숨기지만 접근 패턴 설계를 대신하지는 않습니다.

**A8.** 09의 판단 프레임이 동일하게 적용됩니다: ① 단일 DB로 정말 안 되나(측정 — 대부분 여기서 끝), ② 안 되면 어떤 분산 DB(기존 MySQL 확장은 Vitess/PlanetScale, 새 분산 SQL은 TiDB/TiKV/TiDB Cloud), ③ 자체 운영 vs 관리형(관리형 우선 — TiDB Cloud가 극단적 스테이트풀 복잡도를 흡수). TiKV/TiDB도 09의 극단적 스테이트풀입니다(PD SPOF, 수만 Region의 Raft, RocksDB 저장 엔진, 백업) — 자체 운영은 분산 시스템 + DB + TiDB 특화 지식 팀 + 온프레·규제·비용이 정당화할 때만이고, 대부분 관리형이 답입니다(36의 사고 사례 교훈).
