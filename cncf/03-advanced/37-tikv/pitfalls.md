# 흔한 함정 5선

## 1. "자동 샤딩이니 아무것도 신경 안 써도 된다"

TiKV의 Region 자동 관리는 편리하지만, 핫스팟(hotspot)은 여전히 문제입니다 — 순차 키(auto-increment ID, 타임스탬프)를 쓰면 항상 마지막 Region에만 쓰기가 몰려 자동 분할·밸런싱으로도 한 Region이 병목이 됩니다(write hotspot). 자동 샤딩은 데이터 분포를 관리하지만 접근 패턴이 편향되면 여전히 불균형입니다. 키 설계(해시 접두사, 샤딩 친화적 키)로 쓰기를 분산해야 하고, PD의 핫스팟 스케줄링을 모니터링하세요. Vitess(36)에서 "샤딩 키를 고려한 쿼리 설계"가 필요했듯, TiKV에서도 "핫스팟을 피하는 키 설계"가 필요합니다 — 자동화가 접근 패턴 설계를 대신하지는 않습니다.

## 2. PD를 SPOF로 방치

PD(Placement Driver)는 TiKV의 두뇌입니다 — Region 라우팅, 스케줄링, 전역 타임스탬프(TSO)가 여기 있고, PD가 아프면 클러스터가 라우팅·트랜잭션을 못 합니다(21의 etcd, 36의 Topology와 같은 교훈). PD 자체가 etcd 기반이라 그 HA·성능·백업이 필요하고, 특히 TSO는 모든 트랜잭션이 의존하므로 PD 지연이 곧 트랜잭션 지연입니다. "데이터는 TiKV 노드에 분산되어 안전하다"고 PD를 부차적으로 여기면, PD 장애 시 데이터는 멀쩡한데 클러스터가 마비되는 상황을 만납니다. PD를 클러스터의 심장으로 취급하세요(21의 fsync·has_leader 감시가 PD에도).

## 3. 저장 엔진(RocksDB) 성능을 간과

TiKV는 각 Region의 Raft 로그와 데이터를 RocksDB에 저장합니다 — 21에서 "etcd fsync가 클러스터를 정한다"고 한 것이 TiKV에서는 "RocksDB 성능이 TiKV를 정한다"가 됩니다. 느린 디스크, 잘못된 RocksDB 튜닝(compaction, write amplification), 부족한 IOPS가 쓰기 지연 → Raft 커밋 지연 → 트랜잭션 지연으로 번집니다(21의 번짐 경로). TiKV 노드에 전용 고성능 SSD(NVMe)를 쓰고, RocksDB 메트릭(compaction 지연, write stall)을 모니터링하세요. 분산 DB의 성능은 결국 각 노드의 로컬 저장 성능에 뿌리를 둡니다.

## 4. 관리형 대안을 검토하지 않고 자체 운영

36의 함정이 여기서도입니다 — TiKV/TiDB는 극단적 스테이트풀이고(PD·multi-Raft·RocksDB·수만 Region), TiDB Cloud가 이 복잡도를 관리형으로 흡수합니다. "우리가 직접 TiDB를 운영하자"는 결정은 분산 시스템 + 데이터베이스 + TiDB 특화 지식을 갖춘 팀이 있고, 온프레·규제·비용이 자체 운영을 정당화할 때만 옳습니다. 단일 DB의 벽을 만났다면 대부분 관리형(TiDB Cloud, PlanetScale, Aurora)이 답이고, 자체 운영은 그 무게를 정확히 알고 내리는 결정이어야 합니다(09의 판단, 36의 사고 사례).

## 5. Vitess vs TiKV를 "어느 게 낫나"로

두 프로젝트는 다른 출발점(기존 MySQL 확장 vs 처음부터 분산)과 다른 철학(명시적 제어 vs 자동 편의)을 가집니다 — "어느 게 우수한가"가 아니라 "우리 상황에 맞나"다. 기존 MySQL 자산이 크고 점진적 확장·세밀한 제어를 원하면 Vitess가, 새로 분산 SQL을 시작하고 자동 샤딩·분산 트랜잭션의 편의를 원하면 TiDB/TiKV가 맞습니다. 성숙도(Vitess는 YouTube에서 오래 검증, TiDB는 성장 중), 생태계, 팀 경험도 요인입니다. 25(Linkerd vs Istio), 31(OPA vs Kyverno)에서 반복한 "대칭적 트레이드오프, 상황이 정한다"가 분산 DB에서도 성립합니다.

## 실무 사고 사례

> 한 게임 회사가 급성장하며 사용자·플레이 데이터가 단일 MySQL의 한계를 넘었습니다 — 실제로 측정된 벽이었습니다(쓰기 처리량 포화, 데이터 크기). 팀은 TiDB를 골랐습니다: MySQL 호환이라 앱을 크게 안 바꿔도 되고, 자동 샤딩이라 Vitess처럼 샤딩을 설계할 필요가 없어 보였습니다. 마이그레이션은 성공했고 확장성 문제가 풀렸습니다. 그런데 몇 달 뒤 특정 시간대(이벤트 시작)에 쓰기 지연이 급증했습니다 — 조사해보니 게임 이벤트 로그가 타임스탬프를 primary key로 쓰고 있어서, 모든 쓰기가 "가장 최근" Region 하나에 몰리는 write hotspot이었습니다. 자동 샤딩이 Region을 나눠도 새 쓰기는 항상 마지막 Region으로 갔고, PD의 밸런싱이 따라잡지 못했습니다. "자동 샤딩이니 신경 안 써도 된다"는 오해였습니다. 두 번째 문제도 왔습니다: PD를 최소 구성(3노드지만 저사양)으로 운영했는데, 대규모 트랜잭션 시 TSO(PD의 타임스탬프 발급)가 병목이 되어 트랜잭션 전체가 느려졌습니다 — PD가 두뇌라는 것을 과소평가했습니다. 개선: ① 이벤트 로그 키를 해시 접두사 + 타임스탬프로 바꿔 쓰기를 분산(핫스팟 해소). ② PD를 고사양·전용 노드로, TSO 지연 모니터링. ③ RocksDB 튜닝과 NVMe 스토리지. 그리고 회고에서 팀이 인정한 것: "우리는 '자동'이라는 단어에 속아서 접근 패턴 설계를 건너뛰었습니다 — 자동 샤딩은 데이터 분포를 관리하지만, 우리가 데이터에 어떻게 접근하는지(키 설계)는 여전히 우리 책임이었습니다. 그리고 PD를 부차적으로 여겼는데, 사실 그것이 클러스터의 심장이었습니다." 교훈: **자동화는 물리를 숨기지만 없애지 않습니다** — 자동 샤딩도 핫스팟을, 자동 복제도 디스크 성능을, 자동 라우팅도 PD 성능을 여전히 요구합니다(21의 분산 시스템 원리가 자동화 아래에서도 작동합니다).
