# 이론 — pull 병목, P2P 아키텍처, 통합, 지연 로딩, 판단

> **🌱 17세 눈높이 비유: 전교생에게 유인물 나눠주기**
> - **전통(star)** = 선생님(레지스트리)이 1,000명에게 한 장씩 복사해 나눠줍니다 — 선생님이 1,000번 복사, 줄이 깁니다
> - **P2P(Dragonfly)** = 선생님이 몇 명에게 주고, 받은 학생이 옆 학생에게 나눠줍니다 — 받은 사람이 늘수록 나눠줄 사람도 늘어 순식간에 전교생에게
> - **조각(piece)** = 유인물을 여러 페이지로 나눠, 각자 가진 페이지를 교환 — 한 명이 다 가질 때까지 기다릴 필요 없음
> - **seed peer** = 반장 (레지스트리에서 먼저 받아 다른 학생들의 시드 역할)
> - **scheduler** = 반 편성 담당 (누가 누구에게서 받을지 조율)
> - **AI 이미지** = 두꺼운 교재(수 GB) — 이걸 1,000명이 동시에 받아야 할 때 P2P의 가치가 폭발

---

## 1. pull 병목 — 스케일의 벽

```
star 토폴로지 (전통):
  N개 노드가 레지스트리(34)에서 pull
  → 레지스트리 전송량 = N × 이미지 크기
  → 동시 pull 시 레지스트리 대역·연결·네트워크 포화

병목이 나타나는 지점:
  대규모 배포: 1,000+ 노드가 새 버전을 동시 배포
  오토스케일 폭발: Karpenter(18)가 수백 노드 동시 생성 → 동시 pull
  AI 학습: 수 GB 이미지 × 수천 노드 동시
  → pull이 몇 분씩 → 배포·스케일 지연 (01·18)

★ eks 13의 무릎:
  노드 수가 임계를 넘으면 레지스트리 응답이 급격히 나빠집니다
  → 성능 튜닝이 아니라 토폴로지 문제
```

## 2. P2P 아키텍처

```
Dragonfly 컴포넌트:
  Manager     클러스터 관리·설정·모니터링
  Scheduler   피어 조율 (누가 누구에게서 받을지, 조각 스케줄링)
  Seed Peer   레지스트리에서 먼저 받아 시드 역할 (back-to-source)
  Peer (dfdaemon): 각 노드의 데몬 — 조각을 받고·제공

배포 흐름:
  1. 노드가 이미지 pull → dfdaemon(peer)이 가로챔
  2. Scheduler에 "이 이미지 조각들이 필요"
  3. Scheduler가 조각 소스를 알려줌:
     - 다른 peer가 가졌으면 그 peer에서 (P2P!)
     - 없으면 Seed Peer가 레지스트리에서 받아 (back-to-source)
  4. 여러 소스에서 조각을 병렬로 받아 조립
  5. 이제 이 노드도 그 조각의 소스가 됨 (다음 노드에 제공)

→ 노드가 늘수록 조각 소스도 늘어 → 레지스트리 부하 거의 일정
  (BitTorrent 원리 — swarm이 클수록 빠릅니다)
```

## 3. 이미지 pull 경로 통합 (26과 연결)

```
containerd(26)의 pull 경로에 Dragonfly가 끼어듭니다:

방법 ① registry mirror:
  containerd config.toml에서 레지스트리 미러를 dfdaemon으로
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors]
    "docker.io" → "http://127.0.0.1:65001" (dfdaemon)
  → containerd가 pull 요청을 dfdaemon으로 → P2P

방법 ② CRI 프록시 / 기타:
  다양한 통합 방식

효과:
  앱·K8s는 아무것도 안 바뀜 (그냥 이미지 pull)
  dfdaemon이 투명하게 P2P로 처리
  → 26의 pull 경로가 P2P mesh로 (투명)
```

## 4. 지연 로딩과의 관계 (26의 stargz)

```
26의 지연 로딩(stargz/nydus):
  이미지 전체를 안 받고 필요한 부분만 lazy pull
  → 큰 이미지의 콜드스타트 단축 (18)

Dragonfly + 지연 로딩:
  Nydus(Dragonfly 자매 프로젝트)가 이미지 포맷 + P2P
  → "필요한 조각만" + "그 조각을 P2P로"
  = 큰 이미지를 빠르게 (전체 안 받음 + 레지스트리 부하 분산)

★ 두 최적화의 결합:
  지연 로딩: 받을 양을 줄입니다 (필요한 것만)
  P2P: 받는 경로를 분산합니다 (노드끼리)
  → AI 대형 이미지의 콜드스타트에 둘 다 효과
```

## 5. AI 워크로드 — Dragonfly의 성장 배경

```
AI 워크로드의 특성:
  거대 이미지: CUDA + 프레임워크 + 모델 = 수 GB~수십 GB
  대량 동시: 분산 학습 = 수천 노드가 동시에 같은 이미지
  → star 토폴로지로는 레지스트리가 무너집니다

Dragonfly의 확장:
  이미지뿐 아니라 AI 모델·데이터셋 배포로 (대용량 파일 P2P)
  → "대용량 파일의 P2P 배포"가 본질
  → AI 시대의 인프라 (2026 Graduated 배경)

연결:
  02의 갱 스케줄링(Volcano): AI 학습 잡의 스케줄
  Dragonfly: 그 잡의 이미지·모델 배포
  → AI 인프라의 여러 조각
```

## 6. 판단 — 규모의 임계

```
P2P 배포가 필요한 임계:
  노드 수 × 이미지 크기 × 동시성이 레지스트리 용량을 넘을 때

작은 클러스터 (P2P 불필요):
  노드 수십 개, 이미지 수백 MB → 레지스트리로 충분 (오버엔지니어링)

P2P가 빛나는 곳:
  대규모 클러스터 (수백~수천 노드)
  대형 이미지 (AI, 큰 앱)
  동시 배포 폭발 (오토스케일, 롤아웃)
  엣지·다중 지역 (레지스트리에서 먼 노드들)
  제한된 레지스트리 대역

대가:
  dfdaemon·scheduler·seed peer 운영 (또 하나의 인프라)
  P2P 네트워크 자체의 복잡도
  작은 규모에선 이득 없음

★ 판단: 우리 규모가 임계를 넘었나요?
  "배포 시 이미지 pull이 병목인가" (메트릭으로 — pull 시간)
  넘었으면 P2P, 아니면 오버엔지니어링
```
