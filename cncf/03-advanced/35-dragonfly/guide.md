# 학습 가이드 — 스케일이 만드는 새로운 병목

## 작을 때 안 보이는 문제

이미지 pull은 작은 클러스터에서 아무 문제가 없습니다 — 노드 몇 개가 레지스트리에서 이미지를 받으면 끝입니다. 그런데 규모가 커지면 새로운 병목이 나타납니다:

```
노드 10개:   레지스트리가 이미지를 10번 전송 — 여유
노드 1,000개: 배포 시 1,000개 노드가 동시에 같은 이미지를 pull
             → 레지스트리 대역 포화, 네트워크 혼잡, pull이 몇 분씩
노드 10,000개 (대규모 AI 학습): 수 GB 이미지 × 수천 노드 동시
             → 레지스트리가 무릎을 꿇습니다 (eks 13의 무릎)
```

이것은 성능 튜닝의 문제가 아니라 **구조의 문제**입니다. 중앙 레지스트리(34)가 모든 노드에 이미지를 전송하는 star 토폴로지는 노드 수에 선형으로 부하가 늡니다. 배포가 느려지고(01의 피드백 루프), 오토스케일(18의 Karpenter가 만든 새 노드)이 이미지 pull에 막혀 느려집니다.

## P2P라는 답

Dragonfly의 답은 토폴로지를 바꾸는 것입니다 — 노드들이 서로에게서 이미지 조각을 받습니다:

```
전통(star): 모든 노드 ← 레지스트리 (레지스트리가 N번 전송)
P2P(mesh):  첫 노드들 ← 레지스트리, 이후 노드들 ← 이미 받은 노드들
           → 레지스트리는 한 번만(또는 몇 번), 나머지는 노드끼리
           → BitTorrent가 파일을 배포하는 것과 같은 원리
```

이미지를 조각(piece)으로 나누고, 각 노드가 가진 조각을 다른 노드에 제공합니다. 노드가 많아질수록 조각을 공유할 소스도 많아지므로 — 노드 수가 늘어도 레지스트리 부하는 거의 일정합니다. 이것이 대규모에서 게임을 바꿉니다.

## 26·18과의 연결

이 모듈은 앞의 두 런타임 모듈과 이어집니다:

```
26(containerd): 이미지 pull이 콘텐츠 저장소·스냅샷터를 거칩니다
  → Dragonfly는 그 pull 경로에 registry mirror로 끼어듭니다
18(콜드스타트): scale-to-zero의 콜드스타트에 이미지 pull이 큰 비중
  → 대규모에서 P2P가 pull을 빠르게 → 콜드스타트 완화
26의 지연 로딩(stargz): 이미지 전체를 안 받고 필요한 부분만
  → P2P와 결합 가능 (조각을 P2P로 + 필요한 것만)
```

## AI 워크로드 — Dragonfly가 뜨는 이유

Dragonfly가 최근 Graduated한 배경에는 AI 워크로드가 있습니다. AI 학습·추론 이미지는 거대합니다(수 GB~수십 GB — CUDA, 프레임워크, 모델). 그리고 대규모 학습은 수천 노드가 동시에 같은 이미지를 필요로 합니다. 이 조합(대형 이미지 × 대량 노드 × 동시)이 정확히 P2P 배포가 빛나는 지점입니다. 뿐만 아니라 Dragonfly는 이미지를 넘어 AI 모델·데이터셋 배포로도 확장되고 있습니다 — "대용량 파일의 P2P 배포"가 본질입니다.

## 판단 — 규모의 임계

이 모듈은 P2P 배포가 항상 필요하다고 말하지 않습니다. 작은 클러스터에서는 오버엔지니어링입니다. "언제 P2P가 필요한가"는 규모의 임계 문제이고, 그 임계(노드 수 × 이미지 크기 × 동시성)를 판단하는 것이 실무 가치입니다.
