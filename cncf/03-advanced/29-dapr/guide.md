# 학습 가이드 — 메시가 아닌 것, 라이브러리가 아닌 것

## Dapr를 두 가지와 구분하기

Dapr를 처음 보면 두 가지로 오해합니다: 서비스 메시(24·25)이거나, 라이브러리이거나. 둘 다 아닙니다.

```
서비스 메시(24·25): 네트워크 관심사 — 트래픽·mTLS·관측 (앱 코드는 모름, 투명)
라이브러리:         언어별 SDK — 각 언어로 재구현, 프로세스 안에서
Dapr:              앱 관심사를 사이드카 API로 — 상태·pub/sub·시크릿을 HTTP/gRPC로
```

메시가 "네트워크에서 무엇이 일어나는가"를 다룬다면 Dapr는 "앱이 분산 시스템에서 반복하는 일"을 다룹니다. 상태 저장, 메시지 발행/구독, 시크릿 읽기, 다른 서비스 호출, 재시도·서킷브레이커 — 이것들을 모든 마이크로서비스가 각 언어로 재구현하는 대신, 사이드카가 표준 API로 제공합니다.

## 핵심 아이디어: 관심사를 밖으로

```
전통: 앱 코드에 Redis 클라이언트 + 재시도 로직 + 직렬화 + 시크릿 읽기 코드
     → 언어마다 재구현, Redis를 DynamoDB로 바꾸면 코드 수정

Dapr: 앱이 localhost의 Dapr 사이드카에 HTTP 호출
     POST http://localhost:3500/v1.0/state/mystore   {"key":"x","value":1}
     → 사이드카가 실제 백엔드(Redis/DynamoDB/...)를 처리
     → 백엔드 교체 = 컴포넌트 YAML 수정 (코드 무수정)
     → 언어 무관 (HTTP만 하면 됨)
```

이것이 "앱 코드 위의 추상"(08)의 의미입니다 — 앱은 분산 시스템의 세부를 모르고, Dapr가 그것을 표준화합니다. 05의 CSI, 06의 OTel Collector, 23의 Envoy가 각각 스토리지·관측·프록시에서 한 "구현을 추상 뒤로 숨기기"를 Dapr는 앱 관심사에서 합니다.

## 빌딩블록 — 표준화된 관심사들

Dapr는 분산 관심사를 "빌딩블록"으로 표준화합니다:

```
State management: 키-값 상태 저장 (Redis·DynamoDB·Cosmos... 뒤에)
Pub/sub:          메시지 발행/구독 (Kafka·RabbitMQ·NATS... 뒤에 — 09)
Service invocation: 서비스 간 호출 (mTLS·재시도·트레이싱 내장)
Bindings:         외부 시스템 트리거·출력 (S3·큐·크론...)
Secrets:          시크릿 읽기 (Vault·K8s Secret... 뒤에 — 22)
Actors:           가상 액터 모델 (상태 있는 동시성)
Configuration, Workflow, ...
```

각 블록이 표준 API를 가지고, 그 뒤의 실제 구현은 컴포넌트로 교체 가능합니다.

## 대가 — 정직하게

Dapr도 공짜가 아닙니다. 사이드카(메모리·지연·홉), 또 하나의 API를 배우는 비용, Dapr에 대한 의존(그것이 죽으면 앱의 상태·pub/sub이 멈춤), 그리고 "이미 잘 만든 클라이언트 라이브러리가 있는데 왜"라는 질문. 이 모듈은 Dapr가 빛나는 곳(다언어 조직, 백엔드 이식성이 중요한 곳, 분산 관심사를 표준화하려는 곳)과 과한 곳(단일 언어·단순 앱)을 구분합니다.
