**Q2.** Dapr의 사이드카 모델을 설명하세요. 앱과 daprd는 어떻게 통신하나요?

**Q3.** 빌딩블록 다섯 가지와 각각의 커리큘럼 접점은?

**Q4.** 컴포넌트 추상의 이식성과 그 한계는? 05의 무엇과 같은 트레이드오프인가요?

**Q5.** Dapr와 메시가 겹치는 지점(service invocation)에서 둘의 차이는? 공존 시 주의점은?

## 정답

**A1.** Dapr는 앱 관심사(상태 관리·pub/sub·시크릿·명시적 서비스 호출·actor 등 분산 시스템에서 앱이 반복하는 일)를 다루고, 서비스 메시는 네트워크 관심사(전 트래픽·투명한 mTLS·세밀한 라우팅·관측)를 다룹니다 — 다른 층입니다. 겹치는 영역은 service invocation(Dapr의 서비스 간 호출은 mTLS·재시도·트레이싱을 포함해 메시의 서비스 간 통신 기능과 겹칩니다). 다만 Dapr는 앱이 명시적으로 API를 호출하고(앱이 Dapr를 압니다), 메시는 투명합니다(앱 무관).

**A2.** 각 Pod에 daprd 사이드카가 주입되고(annotation dapr.io/enabled), 앱은 localhost(기본 3500 HTTP / 50001 gRPC)의 Dapr API를 호출합니다. daprd가 그 요청을 받아 실제 백엔드(state store·pub/sub broker·secret store 등)를 처리합니다. 즉 앱은 백엔드를 직접 알지 못하고 표준 API로 Dapr에 말하며, 언어 무관(HTTP/gRPC만 하면 됨)합니다. 컨트롤 플레인(operator·injector·placement·sentry)이 컴포넌트·주입·actor 배치·mTLS를 관리합니다.

**A3.** State management(키-값 상태 — 09의 데이터), Pub/sub(메시지 발행/구독 — 09의 큐/스트림), Service invocation(서비스 간 호출 with mTLS·재시도·트레이싱 — 24의 메시, 12의 트레이싱), Secrets(시크릿 읽기 — 22), Bindings(외부 시스템 트리거·출력 — S3·큐·크론), (+Actors: 가상 액터 모델). 각 블록이 표준 API를 갖고 뒤의 실제 구현은 컴포넌트로 교체 가능합니다.

**A4.** 컴포넌트의 type만 바꾸면(state.redis → state.dynamodb) 앱 코드 수정 없이 백엔드를 교체할 수 있어 이식성(온프레↔클라우드, 벤더 독립)을 얻습니다. 한계: **공통 분모만** 이식됩니다 — 백엔드 고유 기능(DynamoDB GSI, Redis 특수 자료구조, Cosmos 지리 분산)은 표준 API에 없습니다. 05의 CSI가 스토리지 고유 기능을 다 노출하지 못하는 것과 같은 트레이드오프입니다("이식성을 얻는 대신 고유 기능을 포기, 공통 분모로 충분한가가 기준").

**A5.** Dapr service invocation과 메시의 서비스 간 통신은 둘 다 서비스 디스커버리·mTLS·재시도·트레이싱을 제공하지만 — Dapr는 앱이 명시적으로 Dapr API(`/v1.0/invoke/<app>/method/<m>`)를 호출하고(앱이 Dapr를 압니다), 메시는 네트워크 레벨에서 투명하게(앱 무관, 모든 트래픽) 처리합니다. 공존 시 주의: 둘 다 사이드카라 Pod에 사이드카 2개 + 앱 = 오버헤드, mTLS가 이중(Dapr sentry + 메시 CA)이 되어 조정이 필요합니다 — 대개 하나로 충분하므로 "둘 다 정말 필요한가"를 먼저 물어야 합니다.

**A6.** 맞는 경우: ① 다언어 조직(각 언어로 분산 관심사 재구현이 부담 — Dapr가 언어 무관 표준). ② 백엔드 이식성 중요(온프레↔클라우드, 벤더 독립). ③ 분산 관심사를 조직 표준으로 만들려는 플랫폼 팀(또는 actor 모델 도메인). 과한 경우: ① 단일 언어 + 좋은 클라이언트 라이브러리로 충분. ② 단순 앱(사이드카·API 학습 비용 > 이득). ③ 백엔드 고정(이식성 불필요) 또는 이미 메시가 service invocation 처리(중복).

**A7.** 앱이 상태·pub/sub·시크릿을 daprd에 의존하면 daprd(또는 컨트롤 플레인 sentry·operator·placement)의 장애가 앱의 그 기능 중단으로 이어집니다 — Dapr가 앱과 백엔드 사이의 필수 경로가 됩니다. 라이브러리와의 차이: 라이브러리는 앱 프로세스와 함께 살고 죽지만(같은 운명), 사이드카는 **별도로 죽을 수 있습니다**(앱은 살아있는데 daprd만 죽는 상황). 따라서 컨트롤 플레인 HA, 사이드카 헬스 모니터링, 컴포넌트 변경 카나리, 중요 경로의 폴백이 필요합니다 — "추상은 공짜가 아니라 새로운 신뢰 지점을 만든다".

**A8.** ① 재시도의 멱등성 규율: 비멱등 연산(증분 상태 저장·POST)의 재시도는 중복을 만들므로 멱등 연산에만(사고 사례의 중복 증가). ② 재시도 budget: budget 없는 재시도는 백엔드 과부하 시 폭풍을 일으키므로 재시도를 전체의 일정 비율로 제한. ③ 서킷 브레이커: 연속 실패 시 빠른 실패로 장애 확산 차단. 이 규율은 도구가 KEDA(18)든 Envoy(23)든 Dapr든 동일합니다 — 자동 재시도·복원력의 편의는 규율 없이 쓰면 사고가 됩니다.
