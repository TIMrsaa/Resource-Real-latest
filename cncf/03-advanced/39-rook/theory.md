# 이론 — Ceph 아키텍처, CRUSH, Rook 자동화, 통합 스토리지, 판단

> **🌱 17세 눈높이 비유: 대형 물류센터와 그 운영 매니저**
> - **Ceph(물류센터)** = 수천 개의 창고(디스크)에 물건을 분산 보관하는 거대 시스템
>   - **OSD** = 각 창고 담당자 (디스크 하나당 하나, 실제 물건 저장)
>   - **MON** = 센터 관제실 (전체 지도·상태 관리, 여럿이 합의로 — 21)
>   - **MGR** = 통계·모니터링 담당
>   - **CRUSH** = 물건 배치 알고리즘 ("이 물건은 어느 창고들에" — 중앙 조회 없이 계산)
> - **Rook(운영 매니저)** = 물류센터를 대신 운영 — "창고 담당자 채용(OSD 추가), 고장 창고 교체, 물건 재배치, 시스템 업그레이드"를 자동화
> - **Rook은 물건을 안 나른다** = 매니저는 운영만, 실제 보관은 Ceph
> - **극한의 상태** = 이 물류센터가 회사의 모든 물건을 담습니다 → 잃으면 전부 잃음

---

## 1. Ceph 아키텍처 — Rook을 알려면 먼저

```
Ceph 컴포넌트:
  OSD (Object Storage Daemon):
    디스크 하나당 하나 (또는 몇 개)
    실제 데이터 저장 + 복제 + 복구
    수백~수천 개 (규모에 따라)
  MON (Monitor):
    클러스터 맵(어떤 OSD가 있나, 상태) 관리
    쿼럼으로 합의 (21의 Raft/Paxos 계열) — 홀수(3/5)
  MGR (Manager):
    통계·모니터링·대시보드
  MDS (Metadata Server):
    CephFS(파일)의 메타데이터 (파일 시스템일 때)

RADOS: Ceph의 기반 (신뢰성 있는 분산 오브젝트 저장)
  → 그 위에 블록(RBD)·파일(CephFS)·오브젝트(RGW)
```

## 2. CRUSH — 중앙 조회 없는 배치

```
문제: 데이터가 어느 OSD에 있나요? (수천 OSD)
전통: 중앙 메타데이터 서버가 위치 관리 (병목·SPOF)
Ceph CRUSH: 알고리즘으로 계산 (조회 없이)
  CRUSH(오브젝트 ID, 클러스터 맵) → OSD 목록
  → 클라이언트가 직접 계산 (중앙 조회 불필요)
  → 확장성 (메타데이터 병목 없음)

장애 도메인 인식:
  CRUSH 맵에 계층(호스트·랙·데이터센터)
  → 복제본을 다른 장애 도메인에 (하나 죽어도 안전)
  → 04의 안티어피니티, 21의 복제와 같은 사고

★ CRUSH가 Ceph 확장성의 핵심:
  중앙 메타데이터 없이 수천 OSD에 데이터 분산
  (37 TiKV의 Region·PD와 다른 접근 — 계산 vs 조회)
```

## 3. Rook 자동화 — Ceph 운영을 코드로

```
Rook 오퍼레이터가 자동화하는 Ceph 운영 (08):
  ① 설치: CephCluster CR → OSD·MON·MGR 배포
  ② OSD 관리: 디스크 추가 → OSD 생성, 디스크 실패 → 교체
  ③ MON 쿼럼: MON 유지, 실패 시 재생성 (21의 쿼럼)
  ④ 재분배: 노드 추가/제거 시 데이터 rebalance 오케스트레이션
  ⑤ 업그레이드: Ceph 버전 업그레이드 (데이터 실은 채)
  ⑥ 헬스: Ceph 상태 모니터링 → CR status

CR 모델 (08의 오퍼레이터):
  CephCluster: 클러스터 정의 (노드·디스크·복제)
  CephBlockPool: 블록 스토리지 풀
  CephFilesystem: 파일 스토리지
  CephObjectStore: 오브젝트(S3) 스토리지
  → K8s 선언으로 Ceph를 (kubectl로 스토리지 시스템 운영)

★ Rook은 Ceph 운영 지식을 코드화하지만:
  Ceph의 복잡성(성능 튜닝, 심각한 장애 복구)을 다 없애진 못함
  → "설치는 쉽지만 운영은 여전히 Ceph"
```

## 4. 통합 스토리지 — 하나로 셋 (05의 3형태)

```
Ceph = RADOS 위에 세 인터페이스 (05의 3형태를 하나로):
  RBD (블록): PVC RWO → DB 등 (05의 블록)
  CephFS (파일): PVC RWX → 공유 (05의 파일)
  RGW (오브젝트): S3 호환 → 아카이브 (05의 오브젝트)

→ 하나의 Ceph 클러스터로 블록·파일·오브젝트 모두
  05에서 "3형태를 다른 시스템으로" 하던 것을 통합
  장점: 통합 운영, 하드웨어 공유
  단점: Ceph 하나에 전부 의존 (blast radius)

★ 05의 CSI(스토리지 추상)와 연결:
  Rook이 Ceph-CSI 드라이버를 배포
  → PVC → Ceph-CSI → Ceph RBD/CephFS
  → 05에서 배운 CSI 사이드카가 Ceph를 백엔드로
```

## 5. Capability Level — 08의 채점표 (05의 사고)

```
Rook-Ceph의 오퍼레이터 성숙도 (08):
  L1 설치: CephCluster CR로 설치 ✅
  L2 업그레이드: Ceph 버전 업그레이드 ✅
  L3 백업·복구: 복잡 (Ceph 자체 복제 + 별도 백업)
  L4 인사이트: Ceph 메트릭·대시보드 ✅
  L5 오토파일럿: 부분 (자동 재분배·복구, but 심각한 장애는 사람)

★ 05의 사고 사례 경고:
  "설치의 쉬움 ≠ 운영의 쉬움"
  Rook이 L1~L2를 쉽게 하지만 L3(복구)는 여전히 어렵습니다
  → 백업·복구 리허설(k8s 36), Game Day 필수
  → "새벽 3시에 OSD 여러 개가 죽으면?" 대응 가능한가 (09)
```

## 6. 판단 — 언제 Rook-Ceph인가

```
Rook-Ceph가 맞는 경우:
  온프레미스 (관리형 스토리지 없음 — 05의 자체 운영 조건)
  통합 스토리지 (블록+파일+오브젝트를 하나로)
  대규모 (Ceph의 확장성 — 수천 OSD)
  + 그 운영 역량 (Ceph + 분산 시스템 + Rook)

Rook-Ceph가 아닌 경우:
  클라우드 → 관리형(EBS·EFS·S3)이 대개 낫습니다 (05)
  단순 블록만 → Longhorn(05 — 더 가벼움)
  운영 역량 없음 → Ceph의 무게를 감당 못 함

★ 05·09·36·37의 반복:
  스토리지 시스템 = 가장 근본적 상태
  자체 운영은 온프레·통합·대규모 + 역량 (관리형 우선)
  "설치의 쉬움에 속지 마라" (05의 사고)
```
