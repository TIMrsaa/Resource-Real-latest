# 자가 점검 퀴즈

**Q1.** "Rook은 스토리지가 아니다"의 의미와, 올바른 평가 방법은?

**Q2.** Ceph의 네 컴포넌트와 각 역할은? MON이 21의 무엇과 연결되나요?

**Q3.** CRUSH가 하는 일과, 37(TiKV)의 위치 결정과 어떻게 다른가?

**Q4.** Rook 오퍼레이터가 자동화하는 Ceph 운영 여섯 가지는? 자동화하지 못하는 것은?

**Q5.** Ceph의 통합 스토리지(블록·파일·오브젝트)와 05의 3형태의 관계는?

**Q6.** Rook-Ceph의 Capability Level에서 어느 것이 성숙하고 어느 것이 어려운가?

**Q7.** Ceph 복제가 왜 백업이 아닌가? 무엇에 무력한가?

**Q8.** Rook-Ceph 도입 판단은 무엇인가요? 데이터 트랙(36~39)의 반복 주제는?

---

## 정답

**A1.** Rook은 데이터를 저장하지 않는 오퍼레이터이고, 데이터의 저장·성능·내구성은 Ceph(스토리지 시스템)의 속성입니다 — "Rook을 쓴다"는 "Ceph를 운영한다 + 그 운영을 Rook에 위임한다"입니다. 올바른 평가: 시스템(Ceph의 아키텍처·성능·내구성)과 오케스트레이터(Rook의 자동화 품질·업그레이드 안전)를 나눠서 평가하며, "Rook vs Longhorn"이 아니라 "Rook-Ceph vs Longhorn"으로 비교합니다(05). Rook을 이해하려면 그 자동화 대상인 Ceph를 먼저 이해해야 합니다.

**A2.** OSD(Object Storage Daemon — 디스크 하나당 하나, 실제 데이터 저장·복제·복구, 수백~수천 개), MON(Monitor — 클러스터 맵 관리, 쿼럼 합의), MGR(Manager — 통계·모니터링·대시보드), MDS(Metadata Server — CephFS 파일의 메타데이터). MON은 21의 합의(Raft/Paxos 계열)와 연결됩니다 — 클러스터 맵(어떤 OSD가 있고 상태가 어떤지)을 홀수(3/5) MON이 쿼럼으로 합의하며, MON 과반이 살아야 클러스터가 동작합니다(etcd·TiKV MON과 같은 계보).

**A3.** CRUSH는 수천 OSD 중 데이터가 어느 OSD에 있는지를 중앙 메타데이터 조회 없이 알고리즘으로 계산합니다(CRUSH(오브젝트ID, 클러스터맵) → OSD 목록) — 클라이언트가 직접 계산하므로 중앙 메타데이터 병목·SPOF가 없어 확장성이 좋고, CRUSH 맵의 장애 도메인 계층(호스트·랙·DC)으로 복제본을 다른 도메인에 배치합니다. 37(TiKV)은 PD가 Region 위치를 조회하는 중앙 메타데이터 방식입니다 — 위치 결정의 두 접근(계산 vs 조회)이며, Ceph의 계산 방식이 중앙 병목을 없애는 대신 클러스터 맵 변경 시 재계산이 필요합니다.

**A4.** ① 설치(CephCluster CR → OSD·MON·MGR 배포), ② OSD 관리(디스크 추가 → OSD 생성, 실패 → 교체), ③ MON 쿼럼 유지(실패 시 재생성), ④ 재분배(노드 추가/제거 시 데이터 rebalance 오케스트레이션), ⑤ 업그레이드(Ceph 버전 업, 데이터 실은 채), ⑥ 헬스 모니터링(Ceph 상태 → CR status). 자동화하지 못하는 것: Ceph 성능 튜닝(풀·PG 수·CRUSH 규칙), 심각한 장애 복구(다중 OSD 동시 실패, 데이터 손상, inconsistent PG) — "설치는 쉽지만 운영은 여전히 Ceph"다.

**A5.** Ceph는 RADOS(기반 분산 오브젝트 저장) 위에 세 인터페이스를 제공합니다 — RBD(블록, PVC RWO → 05의 블록), CephFS(파일, PVC RWX → 05의 파일), RGW(오브젝트, S3 호환 → 05의 오브젝트). 05에서 "3형태를 다른 시스템으로" 제공하던 것을 하나의 Ceph 클러스터로 통합합니다 — 장점은 통합 운영·하드웨어 공유, 단점은 Ceph 하나에 전부 의존(blast radius). 그리고 Rook이 Ceph-CSI 드라이버를 배포해 05에서 배운 CSI 사이드카가 Ceph를 백엔드로 삼습니다(PVC → Ceph-CSI → Ceph RBD/CephFS).

**A6.** 성숙(쉬움): L1(설치 — CephCluster CR), L2(업그레이드 — Rook이 오케스트레이션), L4(인사이트 — Ceph 메트릭·대시보드). 어려움: L3(백업·복구 — Ceph 복제로 노드 장애는 견디지만 클러스터 전체 복구·마이그레이션은 복잡, 별도 백업 필요), L5(오토파일럿 — 자동 재분배·복구는 하지만 심각한 장애는 사람 필요). 05의 사고 사례가 정확히 L3(복구)의 어려움을 경고합니다 — "설치의 쉬움 ≠ 운영의 쉬움"이며, 복구 리허설(k8s 36)이 필수입니다.

**A7.** Ceph의 복제본(replica)은 데이터를 여러 OSD에 저장해 노드·디스크 하드웨어 장애를 견디게 하지만 — 논리적 손상(실수로 데이터 삭제, 앱 버그로 잘못된 쓰기, 랜섬웨어)에는 무력합니다. 잘못된 데이터가 모든 복제본에 그대로 복제될 뿐이기 때문입니다(21·36의 "복제 ≠ 백업"). 그래서 별도 백업(Ceph 스냅샷 → 외부 스토리지, Velero + CSI)이 필요하고 그 복구를 리허설해야 합니다. 스토리지 시스템 자체가 가장 근본적인 상태이므로 그 손실은 그 위의 모든 데이터를 잃는 것입니다.

**A8.** 판단: 클라우드면 관리형(EBS·EFS·S3)이 대개 낫고, 온프레미스에서 통합 스토리지(블록+파일+오브젝트를 하나로)가 필요하고 대규모이며 Ceph·분산 시스템 운영 역량이 있을 때 Rook-Ceph, 온프레미스라도 단순 블록만 필요하면 Longhorn(더 가벼움)이 답입니다. 데이터 트랙(36~39)의 반복 주제: ① 09의 스테이트풀 판단(관리형 우선, 자체는 역량+조건), ② 21의 분산 원리(Raft·MVCC·쿼럼·합의)가 곳곳에(TiKV multi-Raft, NATS JetStream Raft, Ceph MON 합의), ③ 시스템 vs 오케스트레이터(Rook은 Ceph 운영), ④ 자동화는 물리를 숨기지만 없애지 않음(37 핫스팟, 39 Ceph 복잡성), ⑤ "설치의 쉬움 ≠ 운영의 쉬움"(05·39), ⑥ 관리형 우선.
