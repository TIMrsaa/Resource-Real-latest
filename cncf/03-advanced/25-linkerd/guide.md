# 학습 가이드 — 두 철학을 나란히 놓기

## 같은 문제, 정반대의 답

24와 25는 짝입니다. 같은 메시 문제를 정반대로 풉니다:

```
             Istio                          Linkerd
데이터플레인  Envoy (범용, C++)              linkerd2-proxy (전용, Rust, 초경량)
기능         최대 (온갖 트래픽·정책·확장)    최소 (핵심만)
CRD          많음 (VS/DR/PeerAuth/...)       적음 (거의 없이 동작)
설정         강력하지만 복잡                 "설정이 거의 필요 없음"
철학         "무엇이든 할 수 있게"           "메시가 안 보이게"
```

어느 것이 옳은가요? 둘 다 CNCF Graduated이고 둘 다 옳습니다 — 다른 질문에 답할 뿐입니다. Istio는 "복잡한 트래픽 요구를 전부 충족"에, Linkerd는 "운영 부담 최소로 mTLS·관측"에 답합니다. 이 모듈은 Linkerd를 통해 "덜 하는 것도 설계"임을 배우고, 48에서 이 축으로 선택합니다.

## 왜 Envoy를 안 쓰나

Linkerd의 가장 논쟁적인 결정은 Envoy 대신 자체 프록시를 만든 것입니다(04의 계보도에서 유일한 예외). 근거:

```
Envoy: 범용 프록시 → 모든 기능을 담아 크고 복잡, 메모리·설정 표면이 넓습니다
linkerd2-proxy: 사이드카 전용으로 특화 → Rust로 작고 안전하게, 메시가 필요한 것만
```

트레이드오프가 명확합니다: Envoy의 방대한 기능(WASM 확장, 온갖 프로토콜, ext_authz)을 포기하는 대신, 사이드카당 메모리를 줄이고(수 MB 대 수십 MB) 공격 표면과 설정 복잡도를 낮췄습니다. 22에서 "L7은 필요한 곳에만"을 배웠다면, Linkerd는 "애초에 L7 기능을 최소화"로 같은 목표에 접근합니다.

## "보이지 않는 메시"

Linkerd의 설계 원칙은 "메시가 운영자에게 보이지 않아야 한다"입니다. 설치하면 mTLS가 켜지고, 사이드카를 주입하면 골든 메트릭(성공률·RPS·지연)이 자동으로 나옵니다 — 설정할 것이 거의 없습니다. Istio가 "무엇이든 설정할 수 있다"면 Linkerd는 "설정할 필요가 없다"입니다.

이것이 강점이자 한계입니다. 복잡한 트래픽 관리(세밀한 라우팅, 외부 인가, WASM 확장)가 필요하면 Linkerd는 답이 아닙니다. 하지만 대부분의 조직이 메시에서 실제로 원하는 것(서비스 간 mTLS + 골든 메트릭 + 간단한 트래픽 분할)이라면, Linkerd는 그것을 최소 운영 부담으로 줍니다.

## 이 모듈의 목적

Linkerd 자체보다 **"단순함도 설계 결정"**이라는 것을 배우는 것이 목적입니다. 소프트웨어 선택에서 "더 많은 기능"이 항상 우월하지 않습니다 — 운영하지 않을 기능은 부채이고, 24의 사고 사례(전 서비스 L7으로 비용 폭발)가 그 증거입니다. Linkerd는 "덜 함으로써 더 낫다"의 사례 연구입니다.
