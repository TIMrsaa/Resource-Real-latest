# 학습 가이드 — 단일 DB의 벽과 그 너머

## 문제가 시작되는 곳

MySQL(또는 어떤 단일 DB든)은 놀랍도록 멀리 갑니다 — 수직 확장(더 큰 서버), 읽기 복제본, 캐싱으로 대부분의 조직은 단일 DB로 충분합니다. 그런데 어느 지점에서 벽에 부딪힙니다:

```
쓰기 한계: 단일 primary의 쓰기 처리량 (복제본은 읽기만 분산)
데이터 크기: 단일 서버 디스크·메모리에 안 들어가는 데이터
운영 한계: 거대한 단일 DB의 백업·스키마 변경·장애 반경
```

이 벽을 넘는 전통적 방법이 **샤딩**입니다 — 데이터를 여러 DB로 나눕니다(user_id % 100으로 100개 샤드). 문제는 샤딩을 애플리케이션이 하면 지옥이라는 것입니다:

```
앱이 샤딩하면:
  - 모든 쿼리에 "어느 샤드?" 로직 (코드 복잡도 폭발)
  - 여러 샤드에 걸친 쿼리(JOIN, 집계) 직접 구현
  - 리샤딩(샤드 추가) 시 앱 수정 + 데이터 이동
  - 트랜잭션이 샤드를 넘으면 직접 처리
```

## Vitess의 답 — 샤딩을 DB 계층으로

Vitess의 통찰은 이 복잡성을 앱에서 데이터베이스 계층으로 옮기는 것입니다:

```
앱 → VTGate (하나의 MySQL처럼 보임) → 뒤에서 수백 샤드로 라우팅
```

앱은 그냥 MySQL에 쿼리합니다("SELECT * FROM users WHERE user_id = 123"). VTGate가 그 쿼리의 샤딩 키(user_id)를 보고 올바른 샤드로 라우팅합니다. 여러 샤드에 걸친 쿼리는 VTGate가 각 샤드에 보내 결과를 모읍니다(scatter-gather). 리샤딩은 Vitess가 무중단으로 데이터를 이동합니다. 즉 **샤딩의 복잡성이 앱에서 사라지고 Vitess가 흡수**합니다.

이것은 03의 CSI(스토리지 추상), 29의 Dapr(앱 관심사 추상)와 같은 계열입니다 — 복잡성을 추상 뒤로 숨깁니다. 다만 여기서 숨기는 것은 "데이터가 어디 있나(샤딩)"입니다.

## 09의 판단이 극대화되는 곳

09에서 "스테이트풀을 K8s에" 판단 프레임을 배웠습니다. Vitess는 그 판단이 가장 극단적으로 적용되는 워크로드입니다:

```
Vitess = 대규모 분산 데이터베이스 = 가장 스테이트풀
  → 상태(데이터)가 수백 샤드에 분산
  → 백업·복구·리샤딩·장애가 전부 복잡
  → 운영에 MySQL + 분산 시스템 + Vitess 지식 모두 필요
```

09의 오퍼레이터 성숙도, 스토리지, "새벽 3시에 고칠 사람"이 여기서 최대로 중요합니다.

## 이 모듈의 정직함

Vitess는 YouTube·Slack·기타 초대형 서비스가 쓰는 강력한 도구입니다 — 그러나 대부분의 조직은 단일 DB(또는 관리형 분산 DB)로 충분하고, Vitess의 운영 복잡도를 감당할 필요가 없습니다. "언제 Vitess인가"는 단일 DB의 벽을 실제로 만났을 때이고, 그 벽을 안 만났으면 오버엔지니어링입니다. 35(Dragonfly)와 같은 원칙 — 스케일의 벽을 만난 조직의 도구.
