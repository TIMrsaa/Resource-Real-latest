# 자가 점검 퀴즈

**Q1.** 단일 DB가 부딪히는 세 가지 벽은? 앱이 직접 샤딩할 때의 복잡성 다섯 가지는?

**Q2.** Vitess의 핵심 통찰은? 03·29의 무엇과 같은 계열인가요?

**Q3.** Vitess의 컴포넌트와 각 역할은? Topology는 21의 무엇과 유사한가?

**Q4.** VSchema/VIndex는 무엇을 하나요? 샤딩 키 있는 쿼리와 없는 쿼리의 라우팅 차이는?

**Q5.** "Vitess가 샤딩을 흡수하지만 완전 투명하지 않다"는 무슨 뜻인가요?

**Q6.** 무중단 리샤딩(VReplication)의 단계는? 17의 무엇과 같은 패턴인가요?

**Q7.** Vitess에서 09의 스테이트풀 판단이 극대화되는 이유는?

**Q8.** Vitess를 써야 하는 경우와 대부분이 관리형을 택해야 하는 이유는?

---

## 정답

**A1.** 세 가지 벽: ① 쓰기 처리량(단일 primary의 한계 — 읽기 복제본은 읽기만 분산), ② 데이터 크기(단일 서버 디스크·메모리에 안 들어감), ③ 운영 한계(거대 단일 DB의 백업·스키마 변경·장애 반경). 앱이 직접 샤딩할 때의 복잡성: ① 모든 쿼리에 "어느 샤드?" 라우팅 로직, ② 크로스 샤드 쿼리(JOIN·집계) 직접 구현, ③ 크로스 샤드 트랜잭션(2PC 등) 직접, ④ 리샤딩 시 앱 수정 + 데이터 이동 + 다운타임, ⑤ 스키마 변경을 모든 샤드에 — 애플리케이션 코드가 분산 시스템 코드가 되어 도메인 로직이 묻힙니다.

**A2.** 샤딩의 복잡성을 애플리케이션에서 데이터베이스 계층으로 옮기는 것 — 앱은 하나의 큰 MySQL로 보이지만(VTGate에 그냥 쿼리) Vitess가 뒤에서 수백 샤드로 라우팅하고 크로스 샤드 쿼리·리샤딩을 흡수합니다. 03의 CSI(스토리지 구현을 추상 뒤로), 29의 Dapr(앱 관심사를 추상 뒤로)와 같은 계열 — 복잡성을 추상 뒤로 숨깁니다. 다만 여기서 숨기는 것은 "데이터가 어디 있나(샤딩)"입니다.

**A3.** VTGate(프록시 — 앱에 하나의 MySQL로 보이고 쿼리를 샤드로 라우팅, 23의 Envoy처럼 프록시지만 MySQL 프로토콜), VTTablet(각 MySQL 앞의 에이전트 — 쿼리·헬스·백업·복제 관리), MySQL(실제 데이터, 샤드마다 primary + replica), Topology(클러스터 메타데이터 — etcd/ZooKeeper), VTctld(관리 — 리샤딩·스키마 변경 오케스트레이션), VSchema(샤딩 스키마). Topology는 21의 etcd와 유사합니다 — 분산 시스템의 진실의 원천(어떤 샤드·태블릿, 누가 primary)이고, 아프면 Vitess가 아프며 HA·백업이 핵심입니다.

**A4.** VSchema는 "이 테이블이 어떻게 샤딩되나"(keyspace의 샤딩 여부·키·VIndex)를 정의하고, VIndex는 샤딩 키를 샤드로 매핑합니다(hash: 키를 해시해 균등 분산, lookup: 별도 테이블로 secondary 매핑). 라우팅 차이: 샤딩 키를 WHERE에 쓰는 쿼리(user_id = 123)는 hash(123)로 단일 샤드에 라우팅되어 빠르고, 샤딩 키 없는 쿼리(email = ...)나 집계는 모든 샤드에 보내 결과를 모으는 scatter-gather가 되어 느리고 부하가 큽니다(100 샤드면 100개 쿼리).

**A5.** Vitess가 라우팅·크로스 샤드 쿼리·리샤딩을 앱에서 숨겨주지만, 쿼리 성능은 여전히 샤딩 키에 의존합니다 — 샤딩 키를 WHERE에 쓰면 단일 샤드(빠름), 안 쓰면 scatter-gather(느림). 그래서 앱은 샤딩을 "무시"할 수는 있어도 최적 성능을 위해서는 자주 쓰는 쿼리가 샤딩 키를 포함하도록 설계해야 합니다. 29(Dapr)의 이식성 한계, 03(CSI)의 고유 기능 한계와 같은 계열 — 추상은 복잡성을 숨기지만 그 아래의 물리적 현실(어디에 데이터가 있나)을 완전히 지우지는 못합니다.

**A6.** ① 새 샤드 생성(빈 상태), ② VReplication으로 기존 샤드 → 새 샤드 데이터를 온라인 복제(앱은 계속 기존 샤드에 읽고 쓰는 중), ③ 복제가 따라잡으면 트래픽 전환 — 읽기 먼저(SwitchReads), 쓰기 나중(SwitchWrites), ④ 검증 후 기존 샤드 정리. 앱 무중단으로 Vitess가 오케스트레이션합니다. 17의 Progressive Delivery와 같은 패턴 — 읽기→쓰기의 점진적 트래픽 전환으로 위험을 단계적으로 관리하고, 각 단계에서 검증하며 문제 시 되돌립니다.

**A7.** Vitess는 가장 스테이트풀한 워크로드입니다 — 데이터가 수백 샤드에 분산되고 각 샤드가 (primary + replica) MySQL이라 인스턴스 수천 개 규모이며, 백업·복구·리샤딩·스키마 변경·장애가 전부 분산 스케일입니다. 09의 판단 프레임 모든 항목이 최대로 적용됩니다: 관리형 대안(PlanetScale·Aurora·TiDB Cloud) 검토, 오퍼레이터 성숙도, 각 샤드의 스토리지(05), MySQL + 분산 시스템 + Vitess 3중 지식을 갖춘 "새벽 3시에 고칠 사람", 각 태블릿의 안티어피니티·primary 재선출·Topology 관리 등 K8s 함정. 가장 무거운 스테이트풀이라 판단이 극대화됩니다.

**A8.** 써야 하는 경우: 단일 MySQL의 벽(쓰기 처리량·데이터 크기·운영 한계)을 실제로 만났고, MySQL 호환이 필수이며(기존 앱·생태계), 초대형 규모(YouTube·Slack급)일 때. 대부분이 관리형을 택하는 이유: ① 단일 DB로 충분한 경우가 대부분(수직 확장·복제본·캐싱으로 여유), ② 벽을 만났어도 PlanetScale(Vitess 관리형 — Vitess 창립자들이 만든)이 그 극단적 운영 복잡도를 흡수하거나 Aurora·TiDB Cloud로 충분한 경우가 많고, ③ 자체 운영이 정당한 경우는 온프레·규제·특수 비용 + 3중 지식 팀이 있을 때뿐입니다. 사고 사례처럼 "미래를 위해" 막연히 자체 운영을 고르면 관리형이 흡수했을 복잡도를 스스로 짊어집니다.
