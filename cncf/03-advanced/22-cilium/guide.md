# 학습 가이드 — "같은 자리에서 한다"가 무슨 뜻인가

## eBPF를 먼저 이해해야 Cilium이 보입니다

eBPF는 "커널 안에서 안전하게 실행되는 작은 프로그램"입니다. 세 가지가 이것을 가능하게 합니다:

```
① 훅 지점: 커널의 특정 위치(패킷 수신, 시스템콜, 함수 진입...)에 프로그램을 붙일 수 있습니다
② 검증기(verifier): 로드 시점에 프로그램을 정적 분석 — 무한 루프 없음, 메모리 안전, 종료 보장
③ 맵(map): 커널의 프로그램과 유저스페이스가 공유하는 자료구조(해시맵, 배열...)
```

즉 커널 모듈을 짜는 위험(패닉, 크래시) 없이 커널의 동작을 바꿉니다. 네트워킹에서 이것이 뜻하는 바:

```
iptables:  규칙을 커널의 넷필터 체인에 넣습니다 → 패킷마다 체인 순회(선형)
eBPF:      패킷 처리 지점에 프로그램을 붙입니다 → 해시맵 조회(O(1)) + 임의의 로직
```

## "같은 자리"의 의미 — 통합의 근거

Cilium이 CNI·kube-proxy·정책·관찰·암호화를 하나로 묶은 것은 야심이 아니라 **구조적 귀결**입니다. 패킷이 지나는 그 지점에 프로그램이 붙어 있으면:

```
그 자리에서 목적지를 정할 수 있습니다      → Service 라우팅 (kube-proxy 대체)
그 자리에서 허용/거부를 판단할 수 있습니다  → NetworkPolicy 집행
그 자리에서 무슨 일이 있었는지 기록합니다 → Hubble (판정 근거와 함께!)
그 자리에서 암호화할 수 있습니다           → 투명 암호화 (WireGuard/IPsec)
```

별도의 에이전트가 패킷을 복사해 추측하는 것과, 판정하는 자리에서 기록하는 것은 다릅니다. 04에서 "관찰과 정책이 데이터 경로 안으로 들어왔다"고 한 것의 실체가 이것입니다.

## identity — Cilium의 가장 독창적인 개념

전통적 방화벽은 IP로 정책을 씁니다. K8s에서 Pod IP는 계속 바뀝니다 — 그래서 Cilium은 **라벨 집합에 숫자 ID(identity)를 부여**하고, 그 identity로 정책을 집행합니다:

```
Pod의 라벨 {app=frontend, env=prod}  →  identity 12345
정책: "identity 12345 → identity 67890 의 TCP:8080 허용"
패킷: 출발지 IP로 identity를 조회(맵) → 정책 맵 조회 → 허용/거부
```

Pod가 재생성되어 IP가 바뀌어도 identity는 같습니다. 그리고 identity가 **클러스터 전역에 캐시**되므로(kvstore 또는 CRD), 정책 규칙 수가 Pod 수가 아니라 **라벨 조합 수**에 비례합니다 — 확장성의 핵심입니다.

## 얻는 것과 잃는 것

이 모듈은 Cilium 홍보가 아닙니다. pitfalls에서 다룰 대가들: 커널 버전 요구, 디버깅 난이도(iptables는 `iptables -L`로 보이지만 eBPF 맵은 도구가 필요합니다), 기존 도구·정책과의 상호작용, 그리고 "너무 많은 것을 하는 하나의 컴포넌트"라는 운영 리스크. 04의 pitfall "eBPF 열풍에 검증 없이 올라타기"를 여기서 구체화합니다.
