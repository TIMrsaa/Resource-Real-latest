# 학습 가이드 — "결정을 분리한다"는 아이디어

## OPA의 한 문장

OPA의 전부는 이것입니다: **"할 수 있나요?"라는 질문의 답을 애플리케이션 코드에서 빼내 정책 엔진에 맡깁니다.**

```
전통: 앱 코드에 인가 로직이 흩어져 있습니다 (if user.role == "admin" && ...)
     → 정책이 코드에 박혀 언어마다 다르고, 바꾸려면 재배포, 감사 어렵습니다

OPA: 앱이 OPA에 묻습니다 — "user X가 resource Y에 action Z를 할 수 있나요?"
    OPA가 rego 정책으로 답합니다 — allow/deny + 이유
    → 정책이 코드에서 분리, 언어 무관, 중앙 관리, 감사 가능
```

이 분리가 왜 강력한가? 같은 질문-응답 모델이 **어디서나** 작동하기 때문입니다:

```
K8s admission: "이 Pod를 생성해도 되나요?" → OPA(Gatekeeper)
CI 파이프라인:  "이 워크플로 YAML이 정책을 지키나요?" → OPA(conftest — cicd 24)
앱 인가:       "이 사용자가 이 API를 호출해도 되나요?" → OPA(사이드카/라이브러리)
Terraform:     "이 인프라 변경이 규정을 지키나요?" → OPA(conftest)
```

07에서 "OPA는 관통하는 정책 엔진"이라 한 것의 의미가 이것입니다 — 하나의 엔진, 하나의 언어(rego)로 조직 전체의 정책을 통일합니다.

## rego — 낯설지만 강력한 언어

OPA를 배우는 가장 큰 벽은 rego입니다. rego는 명령형이 아니라 **선언적**입니다 — "이렇게 해라"가 아니라 "이것이 참이다"를 씁니다:

```
명령형 사고: "위반을 찾아서 리스트에 추가해라"
rego 사고:  "violation은 이 조건이 참일 때 존재한다"
```

이 사고 전환이 rego 학습의 핵심이고, 한 번 넘으면 정책을 놀랍도록 간결하게 표현할 수 있습니다. lab-01이 이 전환을 안내합니다 — cicd 24에서 conftest로 rego를 살짝 썼다면, 여기서 그 사고법을 제대로 익힙니다.

## 배포 형태 — 같은 엔진, 다른 옷

OPA는 여러 형태로 배포됩니다:

```
라이브러리(Go):  앱에 임베드 — 최저 지연, 앱과 한 몸
서버(사이드카/데몬): REST/gRPC로 질의 — 언어 무관, 앱과 분리
Gatekeeper:      K8s admission 전용 패키징 — CRD로 정책 관리
conftest:        CI에서 파일 검사 (cicd 24)
```

핵심은 rego 정책이 이 형태들 사이에서 재사용된다는 것입니다 — CI에서 검증한 정책과 admission에서 강제하는 정책이 같은 rego일 수 있습니다.

## 32와의 대비 예고

32(Kyverno)는 같은 K8s admission 문제를 rego 없이 YAML로 풉니다. OPA/Gatekeeper의 강점(범용성, 한 언어로 전 영역)과 약점(rego 학습 곡선)이 Kyverno의 강점(K8s 친숙, 진입 쉬움)과 약점(K8s 전용)과 정확히 대칭입니다. cicd 24에서 "OPA vs Kyverno"를 예고했고, 이 모듈과 32가 그 선택을 완성합니다.
