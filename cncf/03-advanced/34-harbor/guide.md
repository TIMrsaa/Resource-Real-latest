# 학습 가이드 — 레지스트리를 관문으로

## 왜 레지스트리가 보안의 자리인가

cicd 21에서 공급망 보안을 시간선으로 배웠습니다: 빌드 전(서명·SBOM), 배포 시점(admission 검증). 그런데 이 둘 사이에 모든 이미지가 반드시 거치는 지점이 있습니다 — **레지스트리**입니다.

```
빌드 → [레지스트리] → 배포
        ↑ 모든 이미지가 여기를 통과합니다
```

Harbor의 통찰은 이 통과 지점을 보안 관문으로 만드는 것입니다. 이미지가 push될 때 스캔하고, pull될 때 서명·스캔 결과로 차단하고, 누가 무엇에 접근하는지 통제합니다. cicd 21에서 별도 도구들(Trivy 스캔, cosign 서명, Kyverno admission)로 흩어져 있던 것을 레지스트리 하나에 통합합니다:

```
Trivy 스캔(21) → Harbor에 내장 (push 시 자동 스캔)
cosign 서명(21) → Harbor가 서명 저장·검증
admission 차단(21) → Harbor가 "취약/미서명 이미지 pull 차단"
SBOM(21) → Harbor가 OCI 아티팩트로 저장
```

## "이미지 아닌 것도" — OCI 아티팩트

Harbor(그리고 현대 레지스트리)의 확장은 OCI 아티팩트입니다. 레지스트리가 이미지만 저장하던 시대는 지났습니다:

```
같은 레지스트리에:
  컨테이너 이미지 (전통)
  Helm 차트 (15 — OCI 차트)
  SBOM (21 — 이미지에 첨부)
  서명·attestation (21 — 이미지 옆에)
  WASM 모듈, 파일 번들, AI 모델...
```

cicd 21에서 "provenance·SBOM이 이미지 옆에 첨부된다"고 한 것, 15에서 "Helm 차트가 OCI로"라고 한 것이 전부 이 OCI 아티팩트 표준(03의 distribution-spec 확장) 덕입니다. 레지스트리는 이제 "OCI 아티팩트 저장소"이고 Harbor가 그것을 관리합니다.

## 레지스트리는 신뢰 경계입니다

레지스트리가 관문이라는 것은 곧 신뢰 경계라는 뜻입니다 — 레지스트리가 침해되면 모든 배포가 오염됩니다(cicd 21의 공급망 공격 지도에서 "아티팩트 저장" 고리). Harbor의 RBAC, 복제(재해 대비), 취약점 관리는 이 신뢰 경계를 지키는 장치입니다. 그리고 프록시 캐시는 cicd 25에서 배운 Docker Hub rate limit 문제의 답이기도 합니다.

## 이 모듈의 자리

Harbor 자체보다 "레지스트리 = 공급망 관문 = 신뢰 경계"라는 관점이 핵심입니다. 관리형 레지스트리(ECR·GCR·GHCR)를 쓰든 Harbor를 자체 운영하든, 이 관점 — 레지스트리에서 스캔·서명·접근통제를 어떻게 하나 — 은 동일하게 적용됩니다. cicd 21의 공급망 보안이 레지스트리 층에서 어떻게 구현되는지가 이 모듈의 실무 가치입니다.
