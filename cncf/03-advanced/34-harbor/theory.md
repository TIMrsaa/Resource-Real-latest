# 이론 — 아키텍처, 스캔·서명·정책, 복제·프록시, OCI 아티팩트, 신뢰 경계

> **🌱 17세 눈높이 비유: 세관이 붙은 물류 창고**
> - **일반 레지스트리** = 그냥 창고 — 물건(이미지)을 넣고 뺍니다
> - **Harbor** = 세관이 붙은 창고 — 들어올 때 검사(스캔), 나갈 때 위조 확인(서명)·통관 심사(정책), 출입 통제(RBAC)
>   - **스캔** = 물건에 위험물(취약점)이 있나 검사 (push 시 자동)
>   - **정책** = "위험물 있으면 반출 금지"(pull 차단)
>   - **서명 확인** = 진품 홀로그램 검증 (미서명 반출 금지)
>   - **복제** = 다른 지역 창고에 사본 (재해 대비·지연 감소)
>   - **프록시 캐시** = 외부 창고(Docker Hub) 물건을 미리 받아 보관 (rate limit 회피)
> - **OCI 아티팩트** = 창고가 이제 물건뿐 아니라 설명서(SBOM)·차트·인증서도 보관

---

## 1. 아키텍처

```
Harbor:
  core          API·인증·권한·정책 (두뇌)
  registry      실제 이미지 저장 (distribution — OCI)
  jobservice    비동기 작업 (스캔·복제·GC)
  trivy         취약점 스캐너 (내장 — 또는 외부 스캐너 플러그인)
  database      메타데이터 (프로젝트·사용자·정책)
  redis         캐시·잡 큐
  portal        웹 UI

프로젝트 모델:
  프로젝트 = 이미지 그룹 + 정책·RBAC 경계
  public/private, 스캔 정책, 서명 정책, 쿼터, 보존 정책
  → 24의 멀티팀 거버넌스를 레지스트리에
```

## 2. 취약점 스캔 — Trivy 통합 (cicd 21)

```
push 시 자동 스캔 (또는 수동/스케줄):
  Trivy가 이미지 레이어의 패키지를 CVE DB와 대조
  → Critical/High/Medium/Low 카운트 + CVE 목록

배포 차단 정책:
  "Critical 취약점 있으면 pull 차단"
  → 취약한 이미지가 프로덕션에 못 나감 (레지스트리에서 게이트)

cicd 21과의 관계:
  21: CI에서 Trivy 스캔 → 게이트
  34: 레지스트리에서 스캔 → pull 차단 (다층)
  → 빌드 시점(CI)과 저장 시점(레지스트리) 이중 방어
  ★ 신규 CVE: 레지스트리에 이미 있는 이미지를 재스캔 (21의 SBOM 소급의 레지스트리판)
```

## 3. 서명 — 미서명 이미지 차단 (cicd 21)

```
Harbor의 서명 통합:
  cosign(sigstore) 서명을 OCI 아티팩트로 저장 (이미지 옆에)
  notation(notary v2) 서명 지원

배포 차단:
  프로젝트 정책: "서명된 이미지만 pull 허용"
  → 미서명 이미지 배포 차단 (레지스트리 레벨)

cicd 21의 admission과 다층:
  21: Kyverno admission이 서명 검증 (배포 시점)
  34: Harbor가 서명 없으면 pull 차단 (저장/전송 시점)
  → 07의 시간선 여러 층에 서명 검증
```

## 4. 복제와 프록시 캐시

```
복제(replication):
  Harbor ↔ 다른 레지스트리(Harbor·ECR·Docker Hub·GCR)
  push/pull 기반, 필터(태그·라벨)
  용도: 재해 대비(다중 지역), 지연 감소(엣지), 마이그레이션

프록시 캐시(proxy cache):
  Harbor가 외부 레지스트리(Docker Hub)의 프록시
  → 처음 pull 시 원본에서 받아 캐시, 이후는 캐시에서
  용도: ★ cicd 25의 Docker Hub rate limit 회피!
        (러너들이 Docker Hub를 직접 안 치고 Harbor 프록시로)
        오프라인·에어갭 환경

★ cicd 25 카드 8(레지스트리 rate limit)의 답:
  프록시 캐시로 외부 의존을 내부 레지스트리로 흡수
```

## 5. OCI 아티팩트 — 이미지 아닌 것도

```
같은 레지스트리에 저장 (03의 distribution-spec 확장):
  컨테이너 이미지 (전통)
  Helm 차트 (15 — helm push oci://...)
  SBOM (21 — 이미지에 첨부된 성분표)
  서명·attestation (21 — provenance)
  WASM 모듈, AI 모델, 파일 번들

Harbor가 이들을 관리:
  아티팩트 타입별 표시, 서명·스캔 연계, 보존 정책
  → "레지스트리 = OCI 아티팩트 저장소"

cicd 21·15와의 연결:
  21: "provenance·SBOM이 이미지 옆에 첨부" → OCI 아티팩트
  15: "Helm 차트가 OCI로" → 같은 레지스트리에
  → 흩어진 공급망 산출물이 한 레지스트리에 통합
```

## 6. 신뢰 경계 — 레지스트리가 침해되면

```
cicd 21의 공급망 공격 지도에서 "아티팩트 저장" 고리:
  레지스트리 침해 = 모든 배포 오염 (악성 이미지 주입, 태그 변경)

Harbor의 방어:
  RBAC: 누가 push/pull/삭제 (프로젝트별 역할)
  불변 태그: 태그 덮어쓰기 금지 (04의 다이제스트, 태그 변경 방지)
  보존·GC 정책: 오래된/미사용 이미지 정리 (26의 디스크)
  감사 로그: 누가 무엇을 (24의 감사)
  로봇 계정: CI용 제한된 자격증명 (사람 계정과 분리)

★ 레지스트리는 신뢰 경계 (07):
  거기서 스캔·서명·접근통제를 하는 것이 공급망 방어의 중심 고리
  관리형(ECR·GHCR)이든 Harbor든 이 관점은 동일
```

## 7. 관리형 vs 자체 운영

```
관리형 (ECR·GCR·GHCR·ACR):
  운영 부담 없음, 클라우드 통합(IAM), 스캔·서명 기능 제공
  → 대부분의 클라우드 사용자

Harbor 자체 운영:
  온프레·에어갭 (관리형 없음)
  멀티 클라우드 통합 레지스트리
  세밀한 정책·복제 제어
  벤더 독립
  → 05·09의 자체 운영 판단 프레임 (스토리지·백업·운영 역량)
  ★ Harbor도 스테이트풀(이미지 = 데이터) → 05의 스토리지·백업 적용
```
