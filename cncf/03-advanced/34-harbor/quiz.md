## 정답

**A1.** 레지스트리는 빌드와 배포 사이에서 **모든 이미지가 반드시 통과하는 지점**이므로, 이 통과 지점을 보안 관문으로 만들면 스캔·서명·접근통제를 한곳에서 강제할 수 있습니다. Harbor의 통찰은 cicd 21에서 별도 도구(Trivy·cosign·Kyverno)로 흩어져 있던 공급망 보안 기능을 레지스트리에 통합해, 이미지가 push될 때 스캔하고 pull될 때 서명·스캔 결과로 차단하며 누가 접근하는지 통제하는 것입니다. 레지스트리는 공급망 공격 지도(21)의 "아티팩트 저장" 고리이자 신뢰 경계입니다.

**A2.** 취약점 스캔(Trivy 내장 — 21의 CI Trivy 스캔), 이미지 서명(cosign/notation 저장·검증 — 21의 keyless 서명), 배포 차단 정책(취약/미서명 pull 차단 — 21의 Kyverno admission), SBOM(OCI 아티팩트로 첨부 — 21의 syft SBOM), 불변 태그(태그 변경 방지 — 04의 다이제스트, 21의 tj-actions 방어), RBAC·감사(24의 거버넌스). 21에서 파이프라인·admission에 흩어져 있던 것을 레지스트리 층에 통합합니다.

**A3.** CI 스캔(21)은 빌드 시점에 취약 이미지를 잡아 레지스트리에 안 가게 하고(빠른 피드백), Harbor의 스캔 게이트는 저장 시점에 pull을 차단해 빌드 우회 경로도 막습니다(다층). 두 층이 서로 다른 시점을 담당합니다. 신규 CVE: 빌드 시점엔 없던 CVE가 나중에 발표되면 CI 스캔은 못 잡지만, Harbor가 이미 저장된 이미지를 스케줄로 재스캔해 "어제 안전했던 이미지가 오늘 Critical"을 발견합니다 — 21의 SBOM 소급 조회의 레지스트리판입니다.

**A4.** 여러 층: ① Harbor가 pull 시 서명 확인(34 — 전송/저장 시점). ② Kyverno verifyImages가 admission에서(32 — 배포 시점). ③ cicd 21의 admission 서명 검증(21 — 배포 시점, Kyverno/policy-controller). (+ CRI-O의 policy.json이 런타임 pull 시 — 27.) 같은 서명 검증이 07의 시간선 여러 층(저장·전송·배포·런타임)에 배치되어 다층 방어를 이룹니다 — 한 층이 우회돼도 다른 층이 잡습니다.

**A5.** cicd 25 카드 8의 Docker Hub 익명 rate limit(429) 문제를 해결합니다 — 러너들이 Docker Hub를 직접 안 치고 Harbor 프록시 캐시를 통해 pull하면, Harbor가 처음 한 번만 원본에서 받아 캐시하고 이후는 캐시에서 줍니다(외부 의존을 내부 레지스트리로 흡수). 한계: Harbor가 원본에서 처음 받을 때는 여전히 원본 rate limit을 받으므로 인증된 계정 설정으로 한도를 상향해야 하고, 아직 캐시 안 된 이미지는 원본과 끊기면 pull이 실패합니다(프록시는 원본 의존을 줄이지만 없애지 않습니다).

**A6.** 컨테이너 이미지(전통), Helm 차트(15 — OCI 차트, ArgoCD/Flux가 소스로), SBOM(21 — 이미지 성분표 첨부, 신규 CVE 소급), 서명·attestation(21 — provenance, 19의 --provenance), WASM 모듈·AI 모델·파일 번들. cicd 21의 "provenance·SBOM이 이미지 옆에 첨부"와 15의 "Helm 차트가 OCI로"가 같은 OCI distribution-spec(03) 확장 덕에 한 레지스트리에 통합되며, 하나의 다이제스트/image index로 이미지+서명+SBOM이 연결됩니다 — 배포에 필요한 모든 것이 한 곳에.

**A7.** 레지스트리가 모든 이미지의 통과 지점이므로 침해되면 모든 배포가 오염됩니다(악성 이미지 주입, 태그 변경 — 21의 아티팩트 저장 고리). Harbor의 방어 계층: RBAC(프로젝트별 push/pull/삭제 역할), 로봇 계정(CI용 제한 자격증명, 사람과 분리 — 22), 불변 태그(덮어쓰기 금지 — 04·21의 태그 변경 방지), 스캔 게이트(취약 차단), 서명 검증(미서명 차단), 감사 로그(누가 무엇을 — 24), 복제(재해 대비). 관리형(ECR·GHCR)이든 Harbor든 "레지스트리에서 스캔·서명·접근통제·감사"라는 관점은 동일합니다.

**A8.** Harbor는 스테이트풀(이미지=데이터, 메타데이터=DB, 정책=상태)이므로 05·09의 자체 운영 판단 프레임이 적용됩니다: 이미지 스토리지·DB의 백업, 복구 리허설(k8s 36), 복제로 다중 지역 사본, 이미지 데이터의 데이터 중력(05 — 이전·복제가 곧 데이터 이동), "새벽 3시에 레지스트리를 고칠 사람". 사고 사례의 교훈: 레지스트리를 저장소가 아니라 인프라로 취급해야 합니다 — 백업 없이 운영하다 이미지 스토리지를 잃으면, 프로덕션이 참조하던 다이제스트(04)는 재빌드로 복원 불가능하고(다이제스트가 다르므로) 소스를 잃은 이미지는 재현 불가입니다. 레지스트리가 공급망의 관문이라면 그 관문 자체의 가용성·백업이 공급망의 전제 조건입니다.
