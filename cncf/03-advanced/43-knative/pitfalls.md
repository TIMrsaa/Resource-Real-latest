# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 지연 민감 서비스에 scale-to-zero 적용
콜드 스타트(0→1, Pod 뜨는 시간 + 이미지 풀 + 앱 부팅)는 수백ms~수초입니다. 사용자 대면 API처럼 첫 요청 지연이 치명적인 곳에 scale-to-zero를 켜면, 첫 사용자가 매번 느린 응답을 받습니다. 대응: `minScale: 1`(최소 1 유지, scale-to-zero 포기하되 웜 유지) 또는 지연 민감 서비스는 일반 Deployment로. **scale-to-zero는 지연을 감내할 수 있는 워크로드(배치·드문 이벤트·내부 도구)에만.**

### 2. 상시 트래픽에 Knative를 써서 손해만
트래픽이 항상 있으면 Pod가 0으로 갈 일이 없습니다 → scale-to-zero 이점은 못 얻고, Activator 경유·KPA·여러 컴포넌트의 오버헤드만 집니다. 상시 고트래픽은 일반 Deployment+HPA가 더 단순하고 빠릅니다. Knative는 **트래픽이 드문드문하거나 0으로 갈 시간이 있을 때** 값어치가 있습니다. "서버리스가 멋져서" 도입하면 안 됩니다.

### 3. 콜드 스타트를 무거운 이미지로 악화
콜드 스타트 시간은 이미지 풀 + 컨테이너 시작 + 앱 초기화의 합입니다. 이미지가 크거나(수GB), 앱 부팅이 느리거나(JVM 웜업·대형 프레임워크), 초기 커넥션 풀 생성이 무거우면 콜드 스타트가 수초로 늘어 서버리스가 못 쓸 수준이 됩니다. 대응: 작은 이미지(03의 멀티스테이지·distroless), 빠른 시작 런타임(Go·Node), 지연 초기화 최소화, 필요시 `minScale`.

### 4. Knative를 KEDA로 충분한 곳에 도입
"이벤트로 스케일"만 필요한데 Knative 전체(Serving+Eventing+여러 컴포넌트)를 깝니다. 대부분의 "이벤트로 워커 스케일" 요구는 KEDA(18)로 충분하고 훨씬 가볍습니다. Knative는 서버리스 플랫폼(리비전·트래픽·Eventing 라우팅)이 정말 필요할 때. 도구 무게를 필요에 맞춰라 — HPA < KEDA < Knative(theory 5절).

### 5. Eventing의 전달 보장·재시도를 이해 못 함
Knative Eventing의 이벤트 전달은 채널 구현(인메모리·Kafka·NATS)에 따라 보장이 다릅니다. 학습용 인메모리 채널은 재시작 시 이벤트가 사라집니다(영속 아님). 프로덕션에서 이벤트 유실이 문제면 Kafka(40)·NATS JetStream(38) 백엔드 채널을 써야 하고, Trigger의 재시도·데드레터(dead letter sink)를 설정해야 합니다. "이벤트는 당연히 안전하다"는 착각이 유실을 부릅니다.

## 실무 사고 사례: "콜드 스타트가 만든 연쇄 타임아웃"

한 팀이 내부 API 여러 개를 Knative Serving으로 옮겼습니다. "비용 절감(scale-to-zero) + 카나리 편의"가 매력이었습니다. 대부분 잘 돌았습니다. 그런데 **월요일 아침**마다 장애 알림이 쏟아졌습니다.

주말 동안 트래픽이 거의 없어 모든 서비스가 0으로 내려갔습니다. 월요일 오전 9시, 직원들이 일제히 접속하자 **모든 서비스가 동시에 콜드 스타트**를 시작했습니다. 문제는 서비스들이 서로를 호출하는 체인(A→B→C)이었다는 것:

1. A가 콜드 스타트 중 B를 호출 → B도 콜드 스타트 → C도 콜드 스타트
2. 각 콜드 스타트가 2~3초 → 체인 전체가 6~9초
3. A의 타임아웃(5초)이 먼저 터짐 → A가 실패 → 재시도 → 또 콜드 스타트 유발
4. 재시도 폭주로 KPA가 급격히 스케일 업 → 노드 리소스 압박 → 더 느려짐
5. 24의 "재시도 폭풍"이 콜드 스타트와 겹쳐 증폭

결국 몇 분간 내부 시스템이 마비됐다가, Pod들이 다 웜업되자 정상화됐습니다. 매주 월요일 반복됐습니다.

원인 분석:

1. **콜드 스타트 체인** — 여러 서비스가 동시에 0에서 시작하며 지연이 누적됐습니다.
2. **타임아웃이 콜드 스타트를 고려 안 함** — 5초 타임아웃이 콜드 스타트 체인(6~9초)보다 짧았습니다.
3. **재시도 폭풍(24)** — 콜드 스타트 실패 → 재시도 → 더 많은 콜드 스타트.
4. **scale-to-zero의 오적용** — 매일 아침 반드시 트래픽이 오는(예측 가능한) 서비스에 0을 적용했습니다.

**교훈:**
- 서비스 체인에 일괄 scale-to-zero는 위험 — 콜드 스타트가 누적·증폭
- 예측 가능한 트래픽(매일 아침)엔 **`minScale: 1`이나 스케줄 기반 사전 워밍**(KEDA cron 스케일러로 아침 전에 미리 띄우기)
- 타임아웃은 **콜드 스타트를 포함한** 최악 경로를 고려 (24의 타임아웃 예산)
- 재시도에 백오프·서킷 브레이커(24) — 콜드 스타트 실패가 폭풍이 되지 않게
- **scale-to-zero는 "0으로 가도 되는" 워크로드에만** — 아침마다 확실히 쓰는 내부 API엔 부적합

★ Knative(43)의 scale-to-zero는 강력한 비용 절감이지만, 콜드 스타트라는 물리적 대가가 있습니다. 이 대가는 서비스가 독립적이고 지연을 감내할 때는 작지만, 24의 서비스 체인·재시도와 만나면 증폭됩니다. 자동화(scale-to-zero)가 물리(Pod 시작 시간)를 숨기지만 없애지 않습니다 — 37·39·41에서 반복된 이 교훈이 서버리스에서도 그대로입니다. "서버리스가 정말 맞는 워크로드인가"를 먼저 판단하세요.
