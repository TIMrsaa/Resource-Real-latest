# 이론 — 나머지 다섯 갈래, 플랫폼 엔지니어링, 그리고 종합 지도

> **🌱 17세 눈높이 비유: 학교 축제가 끝나고 지도를 접습니다**
> - **오토스케일** = 손님이 몰리면 부스 직원을 늘리고(KEDA: 대기줄을 보고 직원 추가), 부스가 모자라면 천막을 더 치는 것(Karpenter: 자리 없는 부스를 보고 천막 설치) — **다른 층**
> - **서버리스/Wasm** = 손님이 없으면 부스를 아예 접어두는 것(Knative의 스케일 투 제로)
> - **비용(OpenCost)** = 각 부스가 전기·자리를 얼마나 썼는지 정산서
> - **카오스 엔지니어링** = 축제 전에 일부러 정전을 내보는 훈련 — 진짜 정전 때 안 무너지려고
> - **레지스트리(Harbor)** = 물품 창고 — 들어오는 물건을 검사(스캔)하고 봉인(서명)까지
> - **플랫폼 엔지니어링** = 부스 운영 키트 — 도구가 너무 많아 각자 헤매니, 잘 조립한 한 세트를 제공
> - **종합 지도** = 축제 지도를 접어 주머니에 — 이제 어떤 문제가 생기든 "어느 구역인지" 압니다

## 1. 나머지 다섯 갈래 (기준 시점 2026-06)

### 갈래 1 — 오토스케일링: 층을 반드시 구분하세요

| 프로젝트 | 성숙도 | 층 | 트리거 |
|---|---|---|---|
| **KEDA** | Graduated | **워크로드** (Pod 수) | 외부 이벤트 — 큐 길이, Kafka lag, Prometheus 쿼리, cron... |
| **Karpenter** | (CNCF 이관) | **노드** | Pending Pod의 요구사항 → 딱 맞는 인스턴스 프로비저닝 (eks 17) |
| HPA/VPA | (k8s 코어) | 워크로드 | CPU·메모리·커스텀 메트릭 |
| Cluster Autoscaler | (k8s-sigs) | 노드 | 노드그룹 단위 스케일 (Karpenter의 선배) |

```
직렬 관계:  이벤트 → KEDA가 Pod 증가 → Pending 발생 → Karpenter가 노드 생성 → 스케줄
KEDA의 특별함: scale-to-zero (HPA는 최소 1) — 이벤트가 없으면 Pod가 0개
              내부적으로 HPA를 만들어 관리 (HPA의 대체가 아니라 확장·전면)
```

## 2. 플랫폼 엔지니어링 — 지도의 조립 문법

```
문제: 지도에 200개 프로젝트가 있습니다 → 개발자에게 "골라 쓰세요"는 잔인합니다
답:   플랫폼 팀이 조립해 골든 패스를 만듭니다 (cicd 24의 "강제는 좁게, 유인은 넓게")

전형적 IDP 조립도:
  입구        Backstage (카탈로그·템플릿·문서)                    [08의 조직 추상]
  인프라      Crossplane 또는 Terraform (RDS·S3·VPC)             [08의 인프라 추상]
  배달        ArgoCD/Flux (GitOps)                               [cicd 14·15]
  런타임      K8s + Karpenter + KEDA                             [02·10]
  관측        Prometheus + OTel + Grafana                        [06]
  보안        Kyverno + cosign + cert-manager                    [07]
  ★ 부품 목록 = 이 지도 트랙 전체
```

성공 지표는 통제율이 아니라 **채택률**(cicd 24)이고, 최대 위험은 **추상 누수**(08 사고 사례)입니다 — 지도를 아는 사람이 플랫폼을 만들어야 장애 때 덮개를 열 수 있습니다.

## 3. 종합 지도 — 아홉 장을 접는 법

### 3-a. 각 지도의 축 (읽기 기술의 총정리)

| 지도 | 축 | 대표 실수 |
|---|---|---|
| 02 오케스트레이션 | 중심 + 주변(배치·멀티클러스터·엣지) | "K8s가 이겼으니 볼 것 없다" |
| 03 런타임 | **층** (CRI / OCI / 격리 스펙트럼) | containerd vs runc |
| 04 네트워킹 | **층 + 계보** (CNI/DNS/프록시/메시, Envoy 계보) | Cilium vs Istio |
| 05 스토리지 | **역할** (시스템 vs 오케스트레이터 vs 백업) | Rook vs Longhorn |
| 06 관측 | **격자** (신호 × 단계) | OTel vs Jaeger |
| 07 보안 | **시간선** (빌드전/배포시점/런타임 + 신원) | admission만으로 안전 |
| 08 앱 배포 | **사다리** (매니페스트→…→상위 추상) | Helm vs ArgoCD |
| 09 데이터 | **부류 + 판단 프레임** (etcd/메시징/DB) | 관리형 검토 없이 K8s로 |
| 10 나머지 | **갈래 + 조립** | KEDA vs Karpenter |

공통 규율: **좌표 없이 비교하지 마세요.** 로고를 나란히 놓기 전에 "같은 층/역할/단/칸인가"를 묻습니다.

### 3-b. 판단 순서도 (이 트랙의 최종 산출물)

```
1. 증상을 문장으로 쓴다        "GPU 클러스터가 만석인데 아무 잡도 안 끝난다"
2. 카테고리를 특정합니다         → 02(배치 스케줄링)
3. 그 지도의 축으로 좁힙니다     → 갱(Volcano) vs 큐잉(Kueue) — 다른 층
4. 후보를 소견서로 검진합니다    → 01의 5종 + 카테고리 특화 항목(05는 +3, 08은 Capability Level)
5. 관리형/자체운영, 추상 높이  → 09의 판단 프레임, 08의 추상 누수 질문
6. "우리 몫"을 명시합니다        → 백업·복구·업그레이드·온콜
7. 결정 + 재검토 시점을 적습니다 → 지도는 움직입니다(01의 역학: 승격·아카이브·이탈)
```

### 3-c. 지도 유지법

```
분기마다: lab-01 방식으로 landscape.yml 재집계 → 승격·신규·아카이브 diff
연 1회:  우리 스택의 각 항목에 소견서 갱신 (특히 단일 벤더·비CNCF 의존)
사건마다: 사고가 나면 그 카테고리의 지도를 다시 읽습니다 (증상이 지도를 가르칩니다)
```
