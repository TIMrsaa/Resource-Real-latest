# 학습 가이드 — 상태 앞에서는 지도보다 판단 프레임이 먼저입니다

## 이 카테고리가 다른 이유

지금까지의 지도(런타임·네트워킹·관측·배포)는 "무엇을 고를까"였습니다. 여기서는 선택 이전의 질문이 더 큽니다: **이 시스템을 K8s에 올릴 것인가, 관리형(RDS·MSK·SQS)에 맡길 것인가.** 스테이트풀 워크로드는 05에서 배운 데이터 중력 + 08에서 배운 오퍼레이터 성숙도 + 팀의 운영 역량이 곱해지는 지점이고, 잘못 오르면 되돌리기가 가장 비쌉니다.

그래서 이 모듈의 절반은 프로젝트 목록이 아니라 **판단 프레임**입니다:

```
관리형이 있는가요? → 있고, 비용·주권 문제가 없다면 대개 그것이 답
없거나 못 쓴다면 → 오퍼레이터의 Capability Level은? (L3 미만이면 백업·복구는 우리 몫)
                 → 스토리지는? (05의 3형태 매칭 + 복원 리허설)
                 → 새벽 3시에 이것을 고칠 사람이 있는가요?
```

## etcd — 지도의 특별 시민

etcd는 "고를 수 있는 DB"가 아닙니다. K8s를 쓴다면 이미 쓰고 있고, K8s의 모든 선언·상태·watch가 그 위에 있습니다. 그래서 이 지도에서 etcd를 다루는 목적은 채택 판단이 아니라 **이해**입니다: 왜 K8s는 Raft 기반 KV를 골랐고(선형화 읽기·watch·리스), etcd가 아플 때 클러스터가 어떻게 아픈지(느린 디스크 → API 지연 → 컨트롤러 폭주). k8s 파트에서 스치듯 만난 etcd를, lab-02에서 watch와 lease를 직접 만지며 "K8s의 원리가 왜 그 모양인지"로 되짚습니다.

## 메시징 계보 — 큐인가 스트림인가

이 칸의 로고들(NATS, Pulsar, Kafka/Strimzi, RabbitMQ, CloudEvents)은 두 축으로 갈립니다:

```
큐(queue):    메시지를 소비하면 사라집니다 — 작업 분배, 요청/응답
스트림(log):  메시지가 로그에 남습니다 — 재생(replay), 여러 소비자 그룹, 시간 여행
표준(CloudEvents): 메시지의 봉투 형식 — 무엇을 쓰든 이벤트를 같은 형식으로
```

NATS는 흥미로운 사례입니다 — core NATS는 큐(초경량, fire-and-forget)인데 JetStream을 켜면 스트림이 됩니다. "NATS vs Kafka"가 성립하는지 아닌지는 어느 모드냐에 달려 있습니다(또 하나의 층 혼동 방지 훈련).

## Strimzi가 알려주는 것

Strimzi(Kafka 오퍼레이터)는 이 카테고리에서 08의 관통 개념이 어떻게 작동하는지 보여주는 표본입니다 — Kafka는 K8s와 무관하게 태어난 거인이고, Strimzi는 그것을 CRD로 운영합니다(05의 Rook-Ceph 구조와 동형: 시스템 vs 오퍼레이터). "Strimzi를 쓴다"는 곧 "Kafka를 운영한다"이고, 평가 대상은 둘 다입니다.
