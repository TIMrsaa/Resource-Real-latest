# 이론 — etcd의 필연, 메시징 계보, 분산 DB, 스테이트풀 판단 프레임

> **🌱 17세 눈높이 비유: 학교의 기록과 방송**
> - **etcd** = 학교의 유일한 공식 학적부 — 모든 결정(누가 몇 반인지)의 근원. 여러 부본이 있지만 **항상 같은 내용**이어야 하고(합의), 누군가 바뀌면 즉시 알림(watch), 일정 시간 도장을 안 찍으면 자동 만료(lease = 노드의 심장박동)
> - **큐** = 심부름 목록 — 한 사람이 가져가면 목록에서 사라집니다 (작업 분배)
> - **스트림** = 방송 녹화본 — 여러 사람이 각자 원하는 지점부터 다시 볼 수 있습니다 (재생·시간 여행)
> - **CloudEvents** = 방송 형식 표준 — 어느 방송국이든 같은 자막 규격
> - **분산 DB** = 여러 교실에 나눠 보관하는 도서관 — 책이 어디 있는지 아는 색인(샤딩)이 생명
> - **스테이트풀을 K8s에?** = 학적부를 학교 건물이 아니라 이동식 컨테이너 교실에 둘 것인가 — 편의(오퍼레이터)와 위험(데이터 중력)의 저울

---

## 1. etcd — 왜 이것이어야 했나 (K8s 원리의 뿌리)

K8s의 요구를 나열하면 etcd의 스펙이 됩니다:

| K8s가 필요한 것 | etcd의 답 | 이것이 없으면 |
|---|---|---|
| 모든 컨트롤러가 **같은 상태**를 봅니다 | Raft 합의 + **선형화 읽기** | 컨트롤러마다 다른 진실 → 무한 충돌 |
| 변경을 즉시 압니다(폴링 없이) | **watch** (리비전 기반 스트림) | 폴링 지옥, 반응 지연 |
| 실패를 시간으로 감지 | **lease** (TTL + keepalive) | 죽은 노드의 Pod가 영원히 살아 있음 |
| 낙관적 동시성 | **리비전·CAS**(compare-and-swap) | 마지막 쓰기가 이김(lost update) |
| 강한 일관성 우선 | CP 시스템(가용성보다 일관성) | 스플릿 브레인 |

```
쿼럼(quorum) = N/2 + 1  →  3노드는 1대 손실 허용, 5노드는 2대
  ★ 짝수 노드는 무의미(4노드도 쿼럼 3 — 1대 손실 허용, 비용만 증가)
etcd가 아프면 K8s가 아픕니다:
  느린 디스크(fsync 지연) → 쓰기 지연 → API 서버 지연 → 컨트롤러 타임아웃·재시도 폭주
  → "클러스터가 느려요"의 진단은 항상 etcd 디스크 지연(wal fsync)부터
```

etcd는 K8s의 선택 대상이 아니라 **전제**입니다 — 심층 21에서 Raft·컴팩션·백업을 다루지만, 지도 단계의 통찰은 이것입니다: **k8s API의 성질(선언·watch·리소스버전·리스)은 전부 etcd의 성질이 위로 드러난 것**입니다.

## 2. 메시징·스트리밍 — 계보 지도 (기준 시점 2026-06)

| 프로젝트 | 성숙도 | 모델 | 한 줄 |
|---|---|---|---|
| **NATS** | Graduated | 큐(core) + **스트림(JetStream)** | 초경량·저지연. 모드에 따라 성격이 바뀝니다 (심층 38) |
| **Pulsar** | (Apache) | 스트림 + 큐 통합 | 저장·서빙 분리(BookKeeper), 멀티테넌시 |
| **Strimzi** | Incubating | Kafka **오퍼레이터** | Kafka를 CRD로 운영 — 시스템 vs 오퍼레이터(05의 Rook 구조) |
| Kafka | (Apache — 비CNCF) | 스트림 | 사실상 표준 로그. 무게급 |
| RabbitMQ | (비CNCF) | 큐 | AMQP 전통 |
| **CloudEvents** | Graduated | **표준** | 이벤트 봉투 형식 — 어떤 브로커든 같은 형식(심층 40) |
| **Knative Eventing** | (Knative 일부, 08) | 이벤트 라우팅 | CloudEvents 기반 |

### 큐 vs 스트림 — 선택의 실질

```
큐(consume = 삭제):    작업 분배, 요청/응답, "누가 처리했는지"만 중요
                       → NATS core, RabbitMQ, SQS
스트림(append-only 로그): 재생 가능, 여러 소비자 그룹이 각자 오프셋, 이벤트 소싱
                       → Kafka, Pulsar, NATS JetStream
판정 질문: "이 메시지를 나중에 다시 읽어야 하는가요?" (감사·재처리·새 소비자 추가)
  Yes → 스트림 (저장 비용과 운영 무게를 지불)
  No  → 큐 (가볍고 단순)
```

"NATS vs Kafka"는 core NATS를 말하면 층 혼동(큐 vs 스트림)이고, JetStream을 말하면 성립합니다 — 어느 모드인지 먼저 물어라(guide의 훈련).

## 3. 분산 데이터베이스

| 프로젝트 | 성숙도 | 한 줄 |
|---|---|---|
| **TiKV** | Graduated | 분산 트랜잭션 KV — Raft 기반, TiDB의 스토리지 층 (심층 37) |
| **Vitess** | Graduated | MySQL 수평 샤딩 — YouTube 출신, "MySQL을 무한히" (심층 36) |
| CockroachDB / YugabyteDB 등 | 비CNCF | 분산 SQL — 라이선스(BSL 등) 확인 필요 (01) |
| **Strimzi/기타 오퍼레이터** | — | Postgres·MySQL 오퍼레이터들(CloudNativePG 등)이 이 칸의 실무 주역 |

지도적 통찰: 분산 DB 프로젝트 자체보다 **오퍼레이터의 성숙도**가 K8s 채택 가능성을 결정합니다 — CloudNativePG처럼 L3~L4(백업·페일오버·인사이트)에 도달한 오퍼레이터가 "K8s에 DB를" 논의를 현실로 만들었습니다.

## 4. 스테이트풀 판단 프레임 — 이 지도의 핵심 산출물

```
① 관리형이 존재하고 쓸 수 있는가요? (RDS, MSK, MemoryDB, SQS...)
   Yes → 대개 그것이 답. "K8s에 올리는 것"의 이득이 운영 위험을 넘는지 증명 책임은 도전자에게
   No/못 씀(온프레·주권·비용) → ②

② 오퍼레이터의 Capability Level은? (08)
   L1~L2(설치·업그레이드) → 백업·복구·페일오버는 우리 몫 → ③이 아주 무거워짐
   L3+ (백업·복구·페일오버 자동) → 현실적 후보

③ 스토리지는 준비됐는가요? (05)
   3형태 매칭(DB=블록/RWO), 스냅샷·복원의 리허설, StorageClass의 토폴로지 이해

④ 사람: 새벽 3시에 이것을 고칠 수 있는 사람이 있는가요?
   + Game Day(k8s 36)로 복구가 리허설됐는가요?

⑤ K8s 특유의 함정을 아는가요?
   - StatefulSet의 순서 보장은 "생성 순서"이지 "데이터 정합성"이 아닙니다
   - 노드 드레인·재스케줄이 DB에는 페일오버 이벤트입니다 (PDB·안티어피니티 필수)
   - Pod 재시작이 싼 세계의 습관이 상태 시스템에는 사고입니다
```

## 5. 이 카테고리의 K8s 함정 세 가지

```
① 볼륨과 Pod의 결합: StatefulSet은 PVC를 유지하지만, 노드 소멸 시 재부착 가능한 스토리지여야 함
   (로컬 PV면 그 노드가 죽으면 데이터도 끝 — 앱 레벨 복제가 전제)
② 스케줄러는 DB를 모릅니다: 리더 Pod와 팔로워가 같은 노드/AZ에 몰릴 수 있습니다 (안티어피니티 필수)
③ 헬스체크의 의미 차이: HTTP 200이 "쓰기 가능"을 뜻하지 않습니다 (readiness에 실제 쓰기 검사?)
```
