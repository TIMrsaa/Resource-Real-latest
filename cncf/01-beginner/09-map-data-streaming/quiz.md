## 정답

**A1.** ① 모든 컨트롤러가 같은 상태를 봐야 함 → Raft 합의 + 선형화 읽기. ② 변경을 폴링 없이 즉시 앎 → watch(리비전 기반 스트림). ③ 실패를 시간으로 감지 → lease(TTL+keepalive). ④ 낙관적 동시성 → 리비전·CAS. ⑤ 일관성 우선 → CP 시스템. 연결: K8s API가 선언적이고, informer가 watch로 반응하고, resourceVersion으로 충돌을 감지하고, Lease로 리더를 뽑는 것 — 전부 etcd의 능력이 위로 드러난 형태입니다. K8s를 이해한다는 것은 etcd의 성질을 이해한다는 것과 상당 부분 같습니다.

**A2.** 쿼럼 = N/2+1 — 3노드는 2대가 살아야(1대 손실 허용), 5노드는 3대(2대 손실). 짝수(4노드)는 쿼럼이 3이라 여전히 1대 손실만 허용하면서 비용과 합의 지연만 늘어납니다. 아픔의 경로: 느린 디스크로 wal fsync가 지연 → etcd 쓰기 지연 → API 서버의 쓰기 요청 지연 → 컨트롤러 타임아웃·재시도 폭주 → 부하 증폭 → 리더 교체·클러스터 전반의 미스터리한 느림. "클러스터가 느리다"의 1번 용의자가 etcd 디스크인 이유.

**A3.** watch: etcd의 1급 기능으로 특정 키 프리픽스의 변경을 리비전 순서로 스트리밍 — K8s informer/컨트롤러가 폴링 없이 반응하는 메커니즘의 뿌리(lab-02 Step 3에서 ConfigMap 생성이 즉시 PUT 이벤트로). lease: TTL을 가진 임차권으로, keepalive가 끊기면 그 리스에 묶인 키가 자동 삭제 — K8s의 리더 선출(Lease 오브젝트)과 노드 하트비트의 뿌리. "노드가 죽었다"의 실체는 "리스가 갱신되지 않았다"입니다.

**A4.** 큐: 소비하면 메시지가 사라집니다(작업 분배, fire-and-forget) — 구독자가 없으면 유실. 스트림: append-only 로그에 남아 여러 소비자 그룹이 각자 오프셋으로 재생 가능(재처리·감사·이벤트 소싱). 판정 질문: "이 메시지를 나중에 다시 읽어야 하는가" — Yes면 스트림(저장·운영 비용 지불), No면 큐. "NATS vs Kafka"는 **NATS의 어느 모드인지**를 먼저 밝혀야 합니다 — core NATS는 큐라 Kafka(스트림)와 층이 다르고, JetStream이면 같은 층의 비교가 성립합니다.

**A5.** Strimzi는 Kafka 자체가 아니라 **Kafka를 K8s에서 운영하는 오퍼레이터**입니다(CRD로 Kafka·KafkaTopic·KafkaUser 등을 선언). 05의 **Rook**과 동형: Rook이 Ceph를 운영하듯 Strimzi가 Kafka를 운영하며, 평가 대상은 시스템(Ceph/Kafka)과 오케스트레이터(Rook/Strimzi) **둘 다**입니다. "Strimzi를 쓴다"는 곧 "Kafka를 운영한다"입니다.

**A6.** ① 관리형이 존재하고 쓸 수 있는가 → 산출: 쓸 수 있다면 그것이 기본값이고, K8s 채택 주장에 증명 책임. ② 오퍼레이터 Capability Level → 산출: L3 미만이면 백업·복구·페일오버가 "우리 몫" 목록에 기재. ③ 스토리지 준비(05의 3형태 매칭·스냅샷·복원 리허설) → 산출: StorageClass·토폴로지·복원 절차. ④ 사람(새벽 3시에 고칠 수 있는가 + Game Day) → 산출: 온콜과 런북. ⑤ K8s 특유 함정 인지(드레인=페일오버, 스케줄러는 DB를 모름, 헬스체크 의미) → 산출: PDB·안티어피니티·probe 설계. 프레임의 최종 출력은 "무엇을 쓴다"가 아니라 **"무엇이 우리 몫으로 남는다"**입니다.

**A7.** 보장: 안정적 네트워크 ID(파드 이름·DNS), 순서 있는 생성/삭제, PVC의 유지·재사용. 보장하지 않음: 데이터 정합성, 클러스터 멤버십(Raft 부트스트랩·리밸런싱), 페일오버 판단, "쓰기 가능" 여부. 즉 StatefulSet은 **인프라 수준의 안정성**만 주고 앱의 도메인 지식은 없습니다 — 그 지식(언제 브로커를 내려도 되는가, 어떻게 백업하는가)을 코드로 담는 것이 오퍼레이터이고, 그래서 이 카테고리가 오퍼레이터 패턴을 가장 절실히 요구했습니다.

**A8.** Strimzi는 "ISR을 확인하며 브로커를 하나씩 안전하게 롤링한다"는 도메인 지식을 갖고 있었는데, 운영자가 K8s의 일반 절차(노드 드레인)로 Pod를 퇴거시켜 그 지식을 건너뛰었습니다 — 오퍼레이터는 관여할 기회조차 없었습니다. 원칙: **상태 시스템의 유지보수는 K8s 절차가 아니라 오퍼레이터 절차를 따릅니다.** 구체적으로는 PDB로 동시 퇴거를 제한하고, 노드 유지보수 시 오퍼레이터가 주도하는 롤링을 사용하며, 그것을 런북과 Game Day로 강제합니다 — 관리형이 대신해주던 지식을 자체 운영에서는 우리가 갖고 있어야 하고, 오퍼레이터는 그 지식의 저장소이지 우회 가능한 편의 도구가 아닙니다.
