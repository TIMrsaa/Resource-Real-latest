# 자가 점검 퀴즈

**Q1.** CSI 사이드카 패턴에서 공용 사이드카들과 벤더 드라이버의 책임 분리를 설명하세요 — 이 설계가 CRI·CNI와 공유하는 철학은?

**Q2.** PVC 한 장의 여정(선언→시공→입주)을 컴포넌트 이름으로 나열하고, 증상별 진단 층 3개를 말하세요.

**Q3.** `WaitForFirstConsumer`가 존재하는 이유와, eks의 어떤 제약과 같은 문제인가요?

**Q4.** "Rook vs Longhorn"이 절반만 성립하는 비교인 이유와, 올바른 비교 문장은?

**Q5.** 3형태(블록/파일/오브젝트)의 접근 모델과 대표 실수 두 가지는?

**Q6.** 자체 운영 스토리지가 정당해지는 네 조건과, 그 전제 조건은?

**Q7.** 스토리지 소견서에 01의 5종 외에 추가되는 3항목과 그 이유는?

**Q8.** 데이터 중력이 이 카테고리의 의사결정 태도를 어떻게 바꾸는가요?

## 정답

**A1.** 공용 사이드카(external-provisioner/attacher/snapshotter, node-driver-registrar): K8s API 감시(PVC·VolumeAttachment 등)와 K8s 쪽 절차를 담당 — 모든 드라이버가 공유. 벤더 드라이버: CSI gRPC 함수(CreateVolume, ControllerPublish, NodeStage/NodePublish...)만 구현 — K8s 내부를 몰라도 됩니다. 공유 철학: 좁고 명확한 인터페이스(CRI·CNI·CSI)로 코어와 구현을 분리해 교체 가능성과 생태계 경쟁을 만듭니다 — 02의 확장 지점, 03의 OCI와 같은 계열.

**A2.** PVC 생성(선언) → external-provisioner가 감시·CreateVolume 호출(발주) → 벤더 드라이버가 볼륨 생성(시공) → PV 생성·바인딩(등기) → Pod 스케줄 → external-attacher가 노드 연결(어태치) → kubelet의 NodeStage(포맷·글로벌 마운트)/NodePublish(Pod 경로 마운트)(입주). 진단 층: ① Pending = 프로비저닝 층(provisioner 로그·StorageClass provisioner 이름·드라이버 상태) ② Multi-Attach/ContainerCreating 고착 = 어태치 층(attacher 로그·RWO 다툼) ③ MountVolume.SetUp failed = 노드 층(kubelet·registrar·소켓).

**A3.** 즉시 바인딩하면 Pod가 어느 노드(어느 토폴로지 — AZ 등)에 뜰지 모른 채 볼륨 위치가 정해집니다 — Pod가 다른 AZ에 스케줄되면 블록 볼륨을 붙일 수 없습니다. WaitForFirstConsumer는 소비자 Pod의 스케줄 결정을 기다렸다가 그 토폴로지에 맞게 프로비저닝합니다. eks의 EBS AZ 제약(볼륨은 AZ에 묶입니다 — 다른 AZ 노드에 어태치 불가)과 정확히 같은 문제의 일반화.

**A4.** Rook은 데이터를 저장하지 않는 오퍼레이터(Ceph의 설치·복구·업그레이드 자동화)이고 Longhorn은 스토리지 시스템 자체입니다 — 층이 다릅니다. 성능·내구성은 Ceph의 속성이므로 "Rook의 성능"은 범주 오류. 올바른 문장: "**Rook-Ceph vs Longhorn**" — 그리고 평가 항목도 시스템(아키텍처·내구성·성능)과 오케스트레이터(자동화 품질·업그레이드 안전)로 나눠서.

**A5.** 블록: 단일 노드 마운트(RWO) — DB·단독 쓰기. 파일: 다중 노드 공유(RWX) — 공유 콘텐츠·ML 데이터셋. 오브젝트: 마운트가 아니라 API(S3) — 아카이브·백업·정적 자산. 대표 실수: ① RWX 요구에 블록(EBS)을 줘서 Multi-Attach 에러 ② DB를 파일(NFS)에 올려 성능·잠금 문제 — (+오브젝트에 파일시스템 의미론 기대: 목록·rename이 비쌈).

**A6.** ① 온프레미스/베어메탈(관리형 부재 — 가장 흔한 정당 사유) ② 초대규모에서 비용 곡선 역전 ③ 데이터 주권·규제 ④ 특수 성능(로컬 NVMe 직결 등). 전제 조건: "새벽 3시에 이것을 고칠 사람"이 조직에 실재할 것 — 분산 스토리지 운영 역량 + 복구 Game Day 리허설. 조건 없이 자체 운영을 고르면 설치의 쉬움에 속은 것.

**A7.** ① 업그레이드 경로 문서의 품질(데이터를 실은 채 버전을 올리는 서사가 검증돼 있나) ② 데이터 마이그레이션 도구(들어갈 때가 아니라 나올 때의 경로) ③ 데이터 손실 이슈의 사후 보고 이력(사고 시 투명성과 대응 품질). 이유: 데이터 중력 때문에 잘못된 선택의 비용이 다른 카테고리보다 압도적으로 크고, 이 3항목이 "깨졌을 때의 서사"를 미리 보여주는 지표이기 때문.

**A8.** 데이터가 쌓일수록 서비스가 그 위에 앉고 이사 비용(전송·정합성 검증·이중 운영)이 기하급수로 자랍니다 — 결정이 사실상 비가역이 됩니다. 태도의 변화: 신선함보다 지속성(소견서 최중량 적용), 기능보다 복구 서사, 벤치마크보다 운영 이야기, "5년 뒤 유효한가"의 명시적 질문, 라이선스·거버넌스 리스크의 법무 검토. 빠른 결정이 미덕인 카테고리(실험적 도구)와 정반대의 규율이 적용됩니다.
