# 학습 가이드 — 시간선으로 방어를 세우면 겹침과 공백이 보입니다

## 왜 시간선 축인가

보안 도구를 기능(스캔·정책·탐지·암호화)으로 나열하면 겹쳐 보입니다 — SBOM 스캔도 이미지 검사고 admission도 이미지 검사입니다. 겹침이 사라지는 축은 **언제 작동하는가**입니다:

```
빌드 전         배포 시점(admission)        실행 중(런타임)
서명·SBOM·정책   서명 검증·정책 강제          비정상 행위 탐지
(cicd 21)       (k8s 34 · cicd 21)          (Falco)
   │                  │                          │
   └──── 관통: 신원(cert-manager·SPIFFE) + 정책(OPA·Kyverno) ────┘
```

이 시간선의 힘은 **공백을 드러내는 것**입니다: admission만 있고 런타임 탐지가 없으면 "들여보낸 후 나빠지는 것"을 못 봅니다(정상 이미지가 실행 중 익스플로잇당하는 경우 — admission은 이미 통과시켰습니다). cicd 21에서 "서명이 못 막는 것"(빌드 중 주입)을 배운 것과 같은 사고 — 각 층은 자기 시간대만 방어하고, 방어는 층들의 곱입니다.

## 이미 아는 도구들의 지도 위 좌표

이 지도의 상당수를 우리는 이미 만났습니다 — 여기서 하는 일은 그것들에게 **카테고리 좌표를 부여**하는 것입니다:

```
sigstore/cosign (cicd 21)  → 빌드 전(서명 생성) + 배포 시점(admission의 검증 attestor)
OPA (cicd 24)              → 관통 정책 엔진 — CI(conftest)에도 admission(Gatekeeper)에도
Kyverno (cicd 21)          → 배포 시점 K8s 네이티브 정책 + 서명 검증(verifyImages)
in-toto (언급)             → 빌드 전 — 공급망 각 단계의 증명 연쇄(SLSA의 뿌리)
```

새로 만나는 주민은 주로 **런타임(Falco)과 신원(cert-manager·SPIFFE/SPIRE)** — 시간선의 양 끝(실행 중)과 관통축(신원)입니다.

## 신원 — 보안의 숨은 척추

cicd에서 반복한 주제("비밀번호를 신원 증명으로" — OIDC 07, keyless 21, IRSA)가 이 지도에서 두 프로젝트로 구체화됩니다: **cert-manager**(인증서의 자동 발급·갱신 — TLS의 만료 사고를 없앰)와 **SPIFFE/SPIRE**(워크로드에 검증 가능한 신원을 부여 — "이 Pod가 정말 결제 서비스인가"를 암호학적으로). 메시의 mTLS(eks 20), 서비스 간 인증의 뿌리가 여기입니다 — 신원이 없으면 나머지 방어(정책·암호화)가 "누구를"에 답할 수 없습니다.

## 시식 방침 — 예방과 탐지를 각각 한 번씩

lab-02는 시간선의 두 지점을 대비시킵니다: Kyverno(배포 시점 — 나쁜 것을 **못 들어오게**)와 Falco(런타임 — 들어온 것이 **나빠지면 알아채게**). 둘을 나란히 만지면 "왜 둘 다 필요한가"가 몸에 새겨집니다 — 하나는 문지기, 하나는 CCTV입니다.
