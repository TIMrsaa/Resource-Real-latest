# 흔한 함정 5선

## 1. NetworkPolicy를 쓰면서 CNI의 지원 여부를 안 물음

NetworkPolicy는 API일 뿐 **집행자는 CNI**입니다 — 정책을 지원하지 않는 CNI(Flannel 단독 등)에서는 정책이 만들어져도 조용히 무시됩니다(에러조차 없습니다!). "정책 걸었으니 격리됐겠지"가 감사에서 뒤집히는 고전 사고. 채택·감사 체크리스트에 "우리 CNI가 NetworkPolicy를 집행하는가, 어느 수준(L3/L4/L7)까지인가"를 명시하세요 — lab-02 Step 4에서 Cilium이 집행하는 것을 확인했듯, 확인은 정책 생성이 아니라 **차단의 실측**입니다.

## 2. 층 섞은 비교 — "Cilium vs Istio 뭐 써요?"

Cilium은 CNI 층(+정책·관찰·부분 메시), Istio는 메시 층 — 겹치는 부분(메시 기능)은 있지만 본질이 다른 층이라 "vs"가 성립하지 않는 경우가 많습니다(함께 쓰는 조합도 흔합니다: Cilium CNI + Istio 메시). 질문을 층으로 분해하세요: "CNI는 무엇으로?" "메시가 필요한가(eks 20의 그 질문)?" "필요하면 데이터플레인은?" — 이 순서면 조합의 문제가 되고, 로고 대결이면 영원히 안 끝납니다. 03의 층 규율이 네트워킹에서 가장 자주 깨집니다.

## 3. eBPF 열풍에 검증 없이 올라타기

eBPF의 구조적 이점(theory §5)은 진짜지만, "eBPF니까 도입"은 근거가 아닙니다 — 소규모 클러스터(Service 수백 개)에서 iptables는 병목이 아니고, 전환 비용(운영 지식 재학습, 커널 버전 요구, 기존 도구와의 상호작용)은 실재합니다. 도입 근거는 증상이어야 합니다: Service 수천 개의 규칙 갱신 지연, kube-proxy 성능, 정책·관찰의 통합 요구. 반대편 함정도 — "우린 작으니 영원히 무관"이 아니라, 성장 곡선에서 어느 지점에 그 증상이 오는지를 아는 것(eks 13의 무릎 감각)이 지도를 가진 자의 태도입니다.

## 4. 메시를 기본 채택 — "다들 쓰니까"

메시는 이 지도에서 가장 비싼 층입니다 — 사이드카(또는 노드 프록시)라는 상주 비용, 운영 복잡도, 장애 표면의 확대. eks 20에서 물었던 질문이 여기서도 유효합니다: mTLS·트래픽 관리·관찰 중 **무엇이 실제 요구**인가요? mTLS만이면 Cilium의 투명 암호화나 더 가벼운 수단이, 카나리만이면 Gateway API + Argo Rollouts(cicd 17)가 이미 답일 수 있습니다. 메시는 요구 목록이 세 개 이상 겹칠 때의 답이지 기본값이 아닙니다 — 그리고 도입한다면 Envoy 계보인지 자체 플레인인지(운영 지식의 방향)가 첫 분기입니다.

## 5. Gateway API 전환기를 방치 — Ingress에 눌러앉기

Ingress는 유지보수 모드입니다(루트 버전표) — 신규 기능은 Gateway API로만 옵니다. "지금 잘 도니까"로 몇 년을 미루면, 어느 날 필요한 기능(가중치 라우팅, 역할 분리, TCP 라우팅)이 Ingress에 없다는 것을 마이그레이션 압박과 함께 발견합니다. 반대로 하루아침의 전면 전환도 불필요합니다 — 신규 서비스부터 Gateway API로, 기존은 기능 요구가 생길 때 — 라는 점진 경로가 표준이고, 우리 인그레스 컨트롤러의 Gateway API 구현 성숙도(lab-01의 변동 관찰 목록)를 반기마다 확인하는 것이 지도 유지법입니다.

## 실무 사고 사례

> 한 핀테크 회사가 보안 감사를 앞두고 "전 서비스 간 통신 격리"를 선언했습니다 — 팀들이 몇 주에 걸쳐 NetworkPolicy 수백 장을 작성해 적용했고, 감사 문서에 "네임스페이스 간 기본 차단 적용"이라고 썼습니다. 감사 직전의 모의 침투에서 결과가 뒤집혔습니다: 침투 팀이 아무 Pod에서나 결제 서비스에 바로 닿았습니다. 원인은 정책이 아니라 **집행자**였습니다 — 이 클러스터의 CNI는 초기 구축 때 "단순해서" 고른 Flannel이었고, Flannel은 NetworkPolicy를 집행하지 않습니다. 수백 장의 정책은 etcd에 저장만 된 장식이었고, 그 사실을 알려주는 에러는 어디에도 없었습니다(API는 유효한 오브젝트로 받아들이니까). 사후 대응이 이 지도 모듈의 요약입니다: ① CNI를 Cilium으로 교체(정책 집행 + Hubble 관찰) — 단, 야간 창구에서 노드 롤링으로(CNI 교체는 데이터플레인 공사입니다). ② 정책의 "적용"과 "집행"을 분리해 검증 — 배포 파이프라인에 차단 실측 테스트(허용 경로는 통과, 그 외는 timeout이어야 성공)를 게이트로(cicd 24의 Policy as Code와 합류). ③ Hubble의 POLICY_DENIED 카운트를 대시보드에 — 집행이 살아 있다는 상시 증거. 교훈: **네트워킹 지도에서 층을 모르면, 보안이 문서로만 존재합니다** — API(정책)와 데이터플레인(CNI)은 다른 층이고, 아래층이 위층의 약속을 집행하는지는 직접 실측해야만 압니다.
