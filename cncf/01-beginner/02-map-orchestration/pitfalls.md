# 흔한 함정 5선

## 1. "K8s가 이겼으니 이 카테고리는 볼 것 없다"

중심의 승부가 끝났다는 것과 카테고리가 끝났다는 것은 다릅니다 — 실무의 새 고통(ML 배치의 자원 굶김, 클러스터 스프롤, 엣지의 오프라인)은 전부 이 카테고리의 주변부에서 풀리고 있습니다. "GPU 클러스터가 만석인데 아무 잡도 안 끝난다"는 증상을 스케줄러 튜닝으로 몇 주 씨름하다가 갱 스케줄링이라는 단어를 몰라 헤매는 팀이 흔합니다. 지도의 가치는 **증상에 카테고리 이름을 붙여주는 것** — 이름을 알면 검색이 되고, 모르면 바퀴를 재발명합니다.

## 2. Volcano와 Kueue를 경쟁자로 놓고 고르기

둘은 같은 문제의 다른 층입니다: Volcano는 **스케줄러를 대체**해 갱 배치(어느 노드에, 전부 아니면 대기)를 하고, Kueue는 기본 스케줄러를 유지한 채 **수락 제어**(자원 쿼터가 확보될 때까지 잡을 큐에)를 합니다. "어느 것이 이기나"가 아니라 "우리 문제가 배치 원자성인가, 큐잉·쿼터·공정성인가"가 질문이고, 대형 ML 플랫폼은 둘을 병용하기도 합니다. 카테고리 내 로고들을 자동으로 대체재로 가정하는 것 — 지도 읽기의 대표 오류입니다(48에서 일반화).

## 3. 멀티클러스터 도구부터 도입 — 문제 정의 없이

"클러스터가 3개가 됐으니 Karmada"는 성급합니다 — 먼저 물을 것: 필요한 것이 워크로드 **배분**(같은 앱을 N곳에, 페일오버)인가, 클러스터 **수명주기**(생성·업그레이드 자동화 — Cluster API)인가, 아니면 그냥 **배포 대상 여러 개**(GitOps의 ApplicationSet — cicd 14 — 로 충분)인가. 상당수의 "멀티클러스터 요구"는 ApplicationSet + 표준화(cicd 24)로 끝납니다 — 중앙 컨트롤플레인이라는 새 단일 장애점을 들이기 전에, 이미 가진 도구의 사정거리를 확인하세요.

## 4. 엣지에 표준 K8s를 그대로 밀어넣기

매장·공장 노드에 표준 kubelet+컨트롤플레인 연결을 깔면 두 가지가 깨집니다: ① 자원 — 엣지 박스에 컨트롤플레인급 여유가 없습니다(K3s가 존재하는 이유) ② **연결 가정** — kubelet은 API 서버와의 연결을 전제하는데 엣지 회선은 끊깁니다(KubeEdge의 오프라인 자율이 존재하는 이유: 단절 중에도 로컬 메타데이터로 Pod 유지·재시작). "어디까지가 K8s의 연결 가정인가"를 모르고 엣지에 가면, 회선 단절마다 매장 전체가 재시작 루프에 빠지는 사고가 납니다. 문제의 모양(독립 소형 vs 중앙 연장)이 도구(K3s vs KubeEdge)를 정합니다.

## 5. Nomad류 대안을 라이선스 확인 없이 검토

"K8s가 무거우니 Nomad"는 기술적으로 정당한 검토입니다 — 그러나 2023년 HashiCorp가 Terraform과 함께 Nomad도 BSL로 전환했다는 사실을 빼면 검토가 아닙니다(01의 세 기둥: 라이선스를 바꿀 권리가 한 회사에 있습니다). 채택 체크리스트에 기술 항목과 나란히 거버넌스 항목(상표·IP 소유자, 라이선스 변경 주체, 01의 소견서)을 넣어라. 반대 방향의 함정도: "BSL이니 무조건 배제"가 아니라, 우리 사용 형태가 라이선스 조항에 실제로 저촉되는지 법무와 확인하는 것까지가 검토입니다.

## 실무 사고 사례

> 한 AI 스타트업이 GPU 클러스터(노드 16대)를 K8s로 운영했습니다 — 초기는 평화로웠습니다. 연구팀이 커지며 분산 학습 잡(워커 8개짜리, 4개짜리)이 동시에 던져지기 시작했고, 어느 주부터 기묘한 상태가 됐습니다: **GPU 점유율 100%, 완료되는 잡 0**. 잡 A가 8개 중 5개, 잡 B가 4개 중 3개, 잡 C가... 전부 "일부만" 뜬 채 나머지를 기다리고 있었습니다 — 뜬 워커들은 rendezvous 대기로 GPU를 쥔 채 아무 연산도 안 했습니다. 팀은 처음에 스케줄러 설정(우선순위, preemption)을 몇 주 만졌지만, preemption은 문제를 옮길 뿐이었습니다(이번엔 쫓겨난 잡이 굶음). 전환점은 한 엔지니어가 "이거 gang scheduling 문제 아니야?"라고 **이름을 붙인 순간**이었습니다 — 검색 30분 만에 Volcano와 Kueue가 나왔고, 문제가 "우리만의 이상한 상황"이 아니라 HPC 세계가 수십 년 전에 정의한 고전임을 알았습니다. Volcano의 minAvailable(갱) + 큐 공정 배분 도입 후 첫 주: GPU 실효 사용률(점유가 아니라 연산)이 31%에서 78%로. 팀의 회고록 한 줄이 이 지도 모듈의 존재 이유입니다: "우리는 3주를 문제 정의에 쓰고 30분을 해결에 썼습니다 — **카테고리의 이름을 알았다면 순서가 반대였을 것**." 지도는 도구 목록이 아니라, 증상에 이름을 붙여주는 사전입니다.
