# 이론 — 오케스트레이션 지형: 전쟁의 결말, 주변부의 문제들, 전수 지도

> **🌱 17세 눈높이 비유: 도시의 교통 체계**
> - **오케스트레이션 전쟁(2014~2017)** = 도시 교통 표준 경쟁 — 버스 회사 셋(Mesos·Swarm·K8s)이 싸웠고, 노선 확장이 제일 쉬운 체계(K8s의 API·확장성)가 이겼습니다
> - **기본 스케줄러** = 택시 배차 — 손님(Pod) 한 명씩 최적의 차(노드)를 찾습니다. 훌륭하지만...
> - **갱 스케줄링** = 수학여행 버스 — 40명이 **전부** 타야 출발합니다. 20명씩 두 대에 나눠 태우고 "나머지 기다려"를 하면, 두 학교가 서로 상대 버스를 기다리며 아무도 못 떠납니다(데드락)
> - **멀티클러스터** = 도시가 여러 개 — 중앙 교통청이 배분하거나(Karmada), 도시끼리 협약을 맺거나(연합)
> - **엣지** = 산간 마을 정류장 — 본부와 통신이 끊겨도 마을 버스는 계속 다녀야 합니다(KubeEdge의 오프라인 자율)
> - **Nomad** = 버스 말고 승합차 체계 — 단순함이 장점인 대안. 단, 운영 회사가 요금 규정을 바꿨습니다(BSL — 01)

## 1. 전쟁의 결말 — K8s는 왜 이겼나 (표준이 되는 조건의 사례 연구)

| | Mesos | Docker Swarm | Kubernetes |
|---|---|---|---|
| 강점 | 초대형 검증(트위터) | Docker와 통합, 쉬움 | **API 중심 + 확장성**(CRD·컨트롤러) |
| 약점 | 앱 프레임워크 이원화(Marathon) | 표현력 부족 | 초기 복잡도 |
| 결말 | Apache 아카이브(2021) | 사실상 유지보수만 | 표준 |

승부를 가른 것은 기능 목록이 아니라 **구조**였습니다: ① 선언적 API + reconcile(모든 것이 리소스 — k8s 파트에서 배운 그 모델)이라 생태계가 그 위에 쌓을 수 있었고(CRD·오퍼레이터 — 오늘의 Argo·Karpenter·Tekton 전부가 그 증거) ② 중립 재단(CNCF 창립 기증 — 01)이라 경쟁사들이 안심하고 베팅했습니다. 교훈은 일반화됩니다: **표준이 되는 것은 최고의 제품이 아니라 최고의 확장 지점을 가진 플랫폼**입니다.

## 2. 전수 지도 — 기준 시점 2026-06 (성숙도는 lab-01로 재확인)

### 배치·잡 스케줄링 — "Pod 하나씩"으로 못 푸는 문제

| 프로젝트 | 성숙도 | 한 줄 |
|---|---|---|
| **Volcano** | Incubating급* | 갱 스케줄링·큐·공정 배분 — ML/HPC 배치의 표준격. kube-batch의 후계 |
| **Kueue** | (k8s-sigs 서브프로젝트) | 잡 **큐잉·수락 제어** — 스케줄러를 바꾸지 않고 "언제 잡을 들여보낼지"를 관리 |
| YuniKorn | (Apache — CNCF 아님) | 빅데이터(Spark) 친화 스케줄러 — Hadoop 세계에서 온 관점 |

*승격 이력은 시점에 따라 다름 — 지도 모듈의 성숙도는 전부 lab-01 방식으로 재확인이 규율.

구분법: **Volcano는 스케줄러를 대체**(어느 노드에, 갱으로)하고 **Kueue는 그 앞의 수문장**(자원이 준비될 때까지 잡을 큐에 — 기본 스케줄러 유지)입니다. 겹치는 듯 다른 층 — 함께 쓰이기도 합니다.

### 멀티클러스터 — 클러스터가 여러 개가 되는 순간

| 프로젝트 | 성숙도 | 한 줄 |
|---|---|---|
| **Karmada** | Incubating | 중앙 컨트롤플레인이 워크로드를 클러스터들에 **배분** — "클러스터의 스케줄러" |
| **Open Cluster Management (OCM)** | Incubating | 허브-에이전트 모델의 클러스터 등록·정책 배포 프레임워크 |
| Cluster API | (k8s-sigs) | 클러스터 **자체를** K8s 리소스로 생성·관리 — "클러스터의 Deployment" |
| Clusternet / Fleet 등 | Sandbox~외부 | 같은 문제의 변주들 |

두 접근의 구분: **워크로드 배분**(Karmada — "이 Deployment를 3개 클러스터에 2:1:1로")과 **클러스터 수명주기**(Cluster API — "클러스터를 만들고 업그레이드")는 다른 문제입니다. eks 21의 멀티클러스터 운영 고민이 이 프로젝트들의 존재 이유.

### 엣지 — 노드가 데이터센터 밖으로

| 프로젝트 | 성숙도 | 한 줄 |
|---|---|---|
| **KubeEdge** | Incubating급* | 엣지 노드의 **오프라인 자율**(클라우드와 단절돼도 동작) + 디바이스 관리 |
| K3s | (SUSE — CNCF Sandbox) | 경량 단일 바이너리 K8s — 엣지·IoT·개발용. "작은 K8s" 그 자체 |
| SuperEdge / OpenYurt | Sandbox | 같은 문제의 변주 (기존 클러스터를 엣지로 확장) |

구분법: K3s는 "작은 곳에서 도는 K8s", KubeEdge는 "본부 클러스터의 팔을 엣지까지" — 독립 클러스터냐 확장이냐.

## 3. 갱 스케줄링 — 카테고리의 존재 이유 (lab-02의 예습)

```
분산 학습 잡: 워커 8개가 전부 떠야 진행 (all-or-nothing)
기본 스케줄러: Pod 하나씩 배치 → 자원이 6개분뿐이면 6개만 뜨고 2개 Pending
  → 뜬 6개는 자원을 점유한 채 대기 (아무 일도 못 하면서)
  → 잡 A(6/8)와 잡 B(6/8)가 서로의 나머지 자원을 쥔 채 영원히 대기 = 데드락
갱 스케줄링(Volcano): "8개 전부 배치 가능할 때만 시작" — PodGroup 단위 판정
큐잉(Kueue): "8개분 자원이 확보될 때까지 잡을 큐에서 대기" — 애초에 반쪽 진입을 차단
```

k8s의 스케줄러 지식(필터·스코어)이 무효가 되는 게 아니라 — 그 위에 **잡 단위 원자성**이라는 새 층이 얹히는 것입니다.

## 4. 선택 가이드 — 증상 → 처방

```
ML/배치 잡이 서로 자원을 쥐고 굶습니다        → Volcano(갱) 또는 Kueue(큐) — 층 구분 후
클러스터 N개에 같은 앱을 배분·페일오버       → Karmada (GitOps ApplicationSet과 비교 검토 — cicd 14)
클러스터 생성·업그레이드 자체를 자동화        → Cluster API (eks면 eksctl/Terraform과 비교)
매장·공장의 오프라인 내성 노드               → KubeEdge / 독립 소형이면 K3s
수만 Pod의 제자리 업데이트·사이드카 갱신      → OpenKruise
소규모·이종 워크로드·K8s 운영 여력 없음       → Nomad 검토 — 단 BSL 리스크를 01의 눈으로
```
