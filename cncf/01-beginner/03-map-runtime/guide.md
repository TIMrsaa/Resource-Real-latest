# 학습 가이드 — 체인을 알면 지도가 외워지지 않고 이해됩니다

## 이 카테고리의 로고 벽이 유독 혼란스러운 이유

landscape의 런타임 칸에는 containerd, CRI-O, runc, crun, Kata, gVisor, youki, WasmEdge... 가 나란히 있습니다 — 마치 서로 대체재인 것처럼. 혼란의 원인은 **층이 다른 것들이 한 칸에 있기 때문**입니다:

```
CRI 레벨 (kubelet의 대화 상대):  containerd  vs  CRI-O          ← 이 둘이 경쟁
OCI 레벨 (프로세스를 실제 생성):  runc / crun / youki            ← 이 셋이 경쟁
격리 변주 (OCI 레벨의 대체재):    gVisor(runsc) / Kata           ← 보안 요구가 있을 때
다음 세대 (컨테이너 밖):          WasmEdge 등 Wasm 런타임        ← 아예 다른 실행 모델
```

층을 나누는 순간 지도는 단순해집니다: 위층에서 하나, 아래층에서 하나를 고르는 것이고, 아래층의 선택은 RuntimeClass로 Pod 단위 혼용까지 됩니다. 이 구조 감각이 이 모듈의 절반입니다.

## 나머지 절반 — 격리 스펙트럼이라는 축

runc 컨테이너는 커널을 호스트와 **공유**합니다 — 빠르지만, 커널 취약점 하나가 탈출구가 됩니다(멀티테넌트의 악몽 — k8s 34의 문제의식). 그래서 격리를 강화한 변주들이 있습니다: gVisor는 시스템콜을 유저스페이스 커널이 대신 받아내고, Kata는 아예 Pod마다 마이크로VM을 띄웁니다. 격리↑ = 오버헤드↑ — 이 스펙트럼 위 어디에 설지가 런타임 선택의 실질이고, "신뢰 못 할 코드를 실행하는가"가 판정 질문입니다.

## 실습 방침 — 스펙트럼 전체 설치가 아니라 체인 하나를 깊게

gVisor·Kata를 kind에 다 깔아보는 것은 환경 격투가 되기 쉽습니다. 대신 lab-02는 **표준 체인 하나를 끝까지 해부**합니다: kind 노드에 들어가 kubelet→containerd→shim→runc의 프로세스 트리를 보고, ctr로 OCI 번들(config.json — 명세의 실물)을 엽니다. 체인을 한 번 눈으로 본 사람은 gVisor 문서를 읽을 때 "아, runsc가 runc 자리에 들어가는 거구나"를 즉시 이해합니다 — 하나를 깊게가 전부를 얕게를 이깁니다.
