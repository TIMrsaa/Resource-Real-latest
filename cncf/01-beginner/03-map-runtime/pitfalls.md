# 흔한 함정 5선

## 1. 층이 다른 것을 비교표에 올리기

"containerd vs runc 중 뭐가 낫나요?"는 성립하지 않는 질문입니다 — containerd가 runc를 **호출합니다**(요리 지시와 요리사). 채택 회의에서 CRI 레벨과 OCI 레벨, 격리 변주를 한 표에 놓고 점수를 매기는 순간 결론은 무의미해집니다. 이 카테고리의 첫 기술은 층 분류(lab-01 Step 2)입니다: CRI에서 하나, OCI에서 하나 — 그리고 OCI 선택은 RuntimeClass로 Pod 단위 혼용까지 가능하므로 "전사 단일 선택"일 필요도 없습니다.

## 2. dockershim 제거를 "Docker 금지"로 이해한 흔적들

1.24의 dockershim 제거 때 "Docker로 빌드한 이미지를 K8s가 못 돌린다"는 오해가 퍼졌습니다 — 이미지는 OCI 표준이라 빌드 도구와 무관하게 돕니다(진실은 "kubelet의 번역층 제거"). 이 오해의 잔재가 아직 사내 위키·온보딩 문서에 남아 있는 조직이 있습니다. 교훈은 역사보다 구조입니다: **이미지 형식(OCI image-spec)과 런타임 인터페이스(CRI)는 독립**이고, 이 분리를 이해하면 다음 전환(예: Wasm shim)이 와도 같은 종류의 공포에 흔들리지 않습니다.

## 3. 멀티테넌트에 runc 기본 격리로 버티기

"컨테이너 = 격리"라는 믿음으로 신뢰 경계 밖 코드(사용자 제출 코드, 서드파티 플러그인, CI의 포크 PR — cicd 08!)를 runc 컨테이너에서 돌리는 것 — 커널 취약점 하나가 곧 이웃 침해입니다(컨테이너는 커널을 공유합니다). 판정 질문을 상시화하세요: "이 워크로드의 코드를 우리가 신뢰하는가요?" No라면 스펙트럼 오른쪽(gVisor/Kata)을 RuntimeClass로 그 워크로드에만 적용 — 전부 옮기는 게 아니라 위험한 것만. 반대 함정은 전면 Kata화 — 오버헤드(기동·메모리)를 전 워크로드가 내는 과잉 처방입니다.

## 4. 강화 격리 도입 시 호환성·성능 검증 생략

gVisor는 시스템콜을 유저스페이스에서 재구현하므로 **전부를 지원하지 않습니다** — 특정 시스템콜·/proc 의존이 있는 앱이 미묘하게 다르게 동작할 수 있고, I/O 집약 워크로드는 오버헤드가 두드러집니다. Kata는 중첩 가상화 요구(클라우드 인스턴스 타입 제약 — eks에서 metal/지원 타입 확인)와 기동 시간·메모리 상수가 붙습니다. "보안 강화니까 좋은 것"으로 벤치마크 없이 전환하면 성능 회귀가 미스터리 장애(25의 3질문에서 '무엇이 변했나'의 안 보이는 변경)로 돌아옵니다. 강화 격리는 대상 워크로드의 실측 후 도입이 규율입니다.

## 5. Wasm을 "컨테이너의 다음 버전"으로 오독

"Wasm이 컨테이너를 대체한다"는 헤드라인은 지도를 왜곡합니다 — 실행 모델이 다릅니다(리눅스 프로세스가 아니라 샌드박스 VM 바이트코드, 시스템 인터페이스는 WASI로 제한적). 기존 앱 대부분은 재컴파일·재설계 없이는 못 옮기고, 옮길 이유도 없습니다. Wasm의 자리는 컨테이너의 약점이 본질인 곳부터입니다: ms 콜드스타트(함수·엣지), 수 MB 배포물, 기본 거부 샌드박스(플러그인 실행). 관찰 목록에 두고(lab-01 산출물) 그 자리의 워크로드가 생길 때 꺼내는 것 — 대체 서사가 아니라 자리 서사로 읽어라.

## 실무 사고 사례

> 한 SaaS 회사가 "고객 정의 스크립트 실행" 기능을 출시했습니다 — 고객이 올린 코드를 K8s 잡으로 실행하는 구조였고, 격리는 "컨테이너니까"로 넘어갔습니다(runc, 공유 커널, 같은 노드에 다른 고객 워크로드). 보안 리뷰에서 한 엔지니어가 판정 질문을 던졌습니다: "이 코드를 우리가 신뢰하는가요?" — 답은 명백히 No였고, 그 주에 마침 커널 권한 상승 CVE가 공개되며 리뷰가 급물살을 탔습니다. 팀은 전면 재설계 대신 **RuntimeClass 한 장**을 썼습니다: gVisor를 노드풀 하나에 설치하고, 고객 코드 잡에만 `runtimeClassName: gvisor` + 해당 노드풀 지정(taint/toleration — k8s 34의 격리 사다리와 결합). 나머지 자사 워크로드는 runc 그대로. 출시 후 실측에서 고객 스크립트의 평균 실행 시간이 12% 늘었지만 — 그 워크로드에서는 아무도 신경 쓰지 않는 수치였고, 보안 리뷰는 "커널 CVE가 터져도 Sentry 층이 먼저 맞는다"로 통과됐습니다. 두 달 뒤 실제로 또 다른 커널 취약점이 공개됐을 때, 이 회사의 대응은 "고객 코드 경로는 gVisor 뒤라 긴급도 하향, 정기 패치로" — 옆 회사가 전 노드 긴급 재부팅을 하는 동안이었습니다. 교훈: **격리 스펙트럼은 전사 선택이 아니라 워크로드별 배치입니다** — 판정 질문("신뢰하는가") 하나와 RuntimeClass 한 장이, 전면 재설계 없이 신뢰 경계를 구조로 만듭니다.
