# Lab 01 — 대결 구도 종합과 판단 축 훈련

> 판단 훈련입니다. 세 개의 가상 조직 프로필에 대해, 배운 대결 구도들(GitOps·메시·정책·메시징·IaC·노드)의 선택을 3층 방법론으로 직접 내려봅니다. 답보다 **축을 대는 과정**이 핵심입니다.

## 훈련 방법

각 조직 프로필에 대해 스택을 고르고, 각 선택마다 "3층 근거"(기능→철학→조직 적합)를 한 줄씩 씁니다. 먼저 스스로, 그다음 예시 답과 비교.

## 조직 A — 시리즈B 스타트업

```
프로필:
  개발자 25명(3팀), 플랫폼 전담 1명(겸직)
  서비스 15개, 단일 클라우드(관리형 K8s), 트래픽 성장 중
  요구: mTLS(보안 감사), 빠른 배포, 비용 민감
```

<details><summary>예시 판단</summary>

```
GitOps: Flux
  3층: 전담 1명 → 경량·조합. UI 필요성 낮음(팀 작음). ArgoCD도 무방하나 무게.

메시: Linkerd — 아니 그 전에, "정말 필요한가?"
  mTLS가 유일 요구라면 → Linkerd(운영 최소, mTLS 자동)가 적합
  복잡한 트래픽 관리 요구 없음 → Istio는 과함(24의 비용)

정책: Kyverno
  3층: rego 배울 여력 없음(1명), K8s만 정책 대상 → YAML 네이티브

메시징: 관리형 (클라우드 큐/스트림)
  3층: 자체 운영 여력 없음 → 09·38·40의 관리형 우선

IaC: Terraform (기존 익숙) — Crossplane은 IDP 요구가 생길 때
노드: 관리형 K8s의 기본 오토스케일러부터 (Karpenter는 비용 최적화가 아플 때)
공통 근거: 팀이 작습니다 → 모든 선택에서 "운영 최소·관리형 우선"
```
</details>

## 조직 B — 대형 엔터프라이즈

```
프로필:
  개발자 800명(60팀), 플랫폼 조직 20명, 보안·규제 강함(금융)
  서비스 400개, 멀티클라우드+온프레, 복잡한 트래픽(카나리·A/B)
  요구: 강한 거버넌스, 감사 추적, 세밀한 트래픽 제어, 정책을 CI·K8s 전반에
```

<details><summary>예시 판단</summary>

```
GitOps: ArgoCD
  3층: 중앙 플랫폼 조직+가시성(UI·RBAC·감사)+멀티클러스터 → 16의 강점

메시: Istio (ambient 고려)
  3층: 카나리·A/B 등 복잡 트래픽 요구 + 전담 인력 있음 → 기능 최대가 정당
  사이드카 부담은 ambient(24)로 완화 검토

정책: OPA/Gatekeeper (+Kyverno 병용도 흔함)
  3층: 정책을 K8s 밖(CI·API·앱)까지 통일 요구 → rego의 범용성이 값어치
  전담팀이 rego 학습 가능

메시징: Kafka(Strimzi 또는 관리형)
  3층: 이벤트 소싱·재처리·감사 로그 요구 → 영속 로그. 규모가 자체 운영 정당화 가능(역량 있음)

IaC: Crossplane (+기존 Terraform 병존)
  3층: 60팀 셀프서비스(IDP 47) 요구 → 41의 Composition. 기존 TF는 점진 이관

노드: Karpenter
  3층: 다양한 워크로드 400개 → 딱 맞춤·통합의 비용 절감이 규모에서 큼
공통 근거: 규모·전담팀이 "기능 최대"의 운영 비용을 정당화
```
</details>

## 조직 C — 엣지/IoT 기업

```
프로필:
  개발자 40명, 수백 개 엣지 사이트(작은 K8s)+중앙 클러스터
  요구: 엣지 자원 제약(경량 필수), 간헐적 연결, 실시간 데이터
```

<details><summary>예시 판단</summary>

```
GitOps: Flux
  3층: 엣지 수백 사이트에 각각 → 경량 pull 모델·툴킷이 적합(17)

메시: 없음 (또는 중앙만 Linkerd)
  3층: 엣지 자원 제약에 사이드카 부담 → "정말 필요한가" = 아니오

정책: Kyverno (중앙에서 검증 후 배포)
메시징: NATS
  3층: 경량·엣지·실시간·간헐 연결(leaf node) → 38의 정확한 강점
  Kafka는 엣지에 무거움

노드: 해당 없음(엣지는 고정 하드웨어) — 중앙만 오토스케일
공통 근거: 자원 제약이 모든 선택을 "경량"으로 강제
```
</details>

## 핵심 관찰 — 같은 질문, 다른 답

```
세 조직이 같은 대결(GitOps·메시·정책...)에서 다른 답:
  A(스타트업): Flux·Linkerd·Kyverno·관리형 — 운영 최소
  B(엔터프라이즈): ArgoCD·Istio·OPA·Kafka — 기능·거버넌스
  C(엣지): Flux·메시없음·NATS — 경량 강제

→ 도구가 아니라 조직 프로필이 답을 정했습니다
→ "최고의 스택"은 없습니다. 프로필→축→결론의 방법만 있습니다
→ 이것이 3층 방법론의 실체 (결정은 3층에서)
```

## 추가 훈련 — 자기 조직으로

```
자기(또는 가상의) 조직 프로필을 쓰고:
  개발자 수 / 플랫폼 인력 / 서비스 수 / 클라우드 / 규제 / 특수 제약
각 대결에 3층 근거로 답하세요.
그리고 6개월 뒤 조건이 어떻게 바뀌면 답이 바뀌는지도 써라(ADR의 재평가 조건 — lab-02).
```

## 정리

- 같은 대결 구도라도 조직 프로필(팀·규모·규제·제약)이 다른 답을 만듭니다
- 작은 팀 → 운영 최소·관리형, 대규모+전담팀 → 기능·거버넌스 정당화, 자원 제약 → 경량 강제
- 판단의 순서: 프로필 정의 → 각 층에 "정말 필요한가" → 3층 축 대기 → 결론
- **★ "최고의 스택"은 없습니다 — 프로필→축→결론의 방법이 있을 뿐 (그 방법이 이 커리큘럼의 산물)**
