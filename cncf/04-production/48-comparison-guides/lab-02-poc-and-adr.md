# Lab 02 — PoC 설계와 ADR 작성

> 비교의 마지막 두 규율을 실습합니다 — 문서로 좁힌 후보를 **올바른 PoC**로 검증하고, 결정을 **ADR**로 기록하는 것. lab-01의 조직 A(스타트업) 시나리오로 실제 문서를 써봅니다.

## 1. PoC 설계 — 메시 선택 (조직 A: Linkerd vs "안 쓰기")

lab-01에서 조직 A는 "Linkerd 또는 메시 없이"로 좁혔습니다. PoC를 설계합니다:

```
# PoC 계획: 서비스 메시 도입 검증
기간: 2주 (기한 엄수 — 늘어지면 결정 회피)
참여: 플랫폼 담당 1명 + 앱 개발자 1명 (운영할 사람이 직접)

검증 질문 (사전 정의 — "느낌" 방지):
  Q1. mTLS가 코드 변경 없이 되는가 (핵심 요구)
  Q2. 우리의 가장 까다로운 서비스(gRPC 스트리밍)에서 문제없는가
      ← 데모 앱이 아니라 어려운 케이스!
  Q3. 사이드카 리소스 오버헤드가 예산 내인가 (측정: Pod당 CPU/Mem)
  Q4. 운영 시나리오: 업그레이드 해보기, 프록시 장애 내보기,
      "메시 때문인지" 디버깅 해보기 (관측으로 판별 가능한가)
  Q5. 안 쓰는 선택지: mTLS만이면 cert-manager+앱 TLS로 충분한가
      (메시 없이 요구를 충족하는 비용과 비교)

평가 기준 (사전 합의):
  Q1~Q3 전부 통과 + Q4 "1명이 감당 가능" 판정 → 도입
  Q5의 대안이 더 싸면 → 메시 보류
```

**설계 포인트** (theory 5절 적용):
- **어려운 케이스**(gRPC 스트리밍)로 — hello world는 아무것도 검증 안 함
- **운영 시나리오**(업그레이드·장애·디버깅) — 설치는 문서만 봐도 됨, 운영이 진짜 질문
- **"안 쓰기" 후보 포함** — 최고의 선택은 때로 도입하지 않는 것(24)
- **기한과 기준을 사전에** — 안 그러면 영원한 PoC 또는 느낌 결정

## 2. PoC 실행 기록 (가상 결과)

```
결과:
  Q1 통과 — linkerd inject만으로 mTLS 확인 (linkerd viz로 검증)
  Q2 부분 — gRPC 스트리밍 OK, 단 특정 keepalive 설정 조정 필요 (문서화)
  Q3 통과 — 프록시당 ~15m CPU / 20Mi (예산 내, Istio 대비 가벼움 확인)
  Q4 통과 — 업그레이드 CLI 단순, 프록시 로그·viz로 디버깅 가능,
            "1명 감당 가능" 판정
  Q5 비교 — 앱 TLS 직접 구현: 15개 서비스 × 인증서 배포·갱신·코드 변경
            = 메시보다 비쌈 (그리고 골든 시그널 관측을 덤으로 못 얻음)

결론: Linkerd 도입
```

## 3. ADR 작성 — 결정의 기록

PoC 결과를 ADR로 남깁니다:

```markdown
# ADR-003: 서비스 메시로 Linkerd 채택

## 상태
승인 (2026-07-11)

## 맥락
- 보안 감사에서 서비스 간 mTLS 요구
- 서비스 15개, 플랫폼 전담 1명(겸직), 복잡한 트래픽 관리 요구는 없음
- PoC 2주 수행 (계획·결과: poc-mesh.md)

## 결정
Linkerd를 도입합니다. 이유:
- mTLS가 코드 변경 없이 충족 (핵심 요구)
- 운영 최소 철학(25)이 전담 1명 체제에 적합
- 사이드카 오버헤드 예산 내, 골든 시그널 관측을 덤으로

## 검토한 대안
- Istio: 기능은 최대지만 현 팀 규모에 운영 과잉 (24의 비용 구조)
- Cilium Mesh: 현재 CNI가 아니라 교체 비용 큼
- 메시 없이 (앱 TLS): 15개 서비스 인증서 관리·코드 변경이 더 비쌈,
  관측 이점도 없음 (PoC Q5)

## 결과 (trade-offs)
- (+) mTLS 자동, 관측 확보, 낮은 운영 부담
- (-) 고급 트래픽 기능(A/B·복잡 라우팅) 부재 — 현재 요구 없음
- gRPC keepalive 설정 조정 필요 (runbook에 문서화)

## 재평가 조건
다음 중 하나라도 해당하면 재검토:
- 서비스 100개 초과 또는 복잡한 트래픽 정책(카나리 자동화) 요구 발생
- 플랫폼 전담이 3명 이상으로 → Istio(ambient) 재검토
- Linkerd 거버넌스·라이선스에 중대 변화 (45의 지속성 관찰)
```

**ADR 포인트** (theory 6절):
- **재평가 조건이 핵심** — 결정은 그 시점 조건의 함수. 조건이 바뀌면 트리거가 당겨져 교조를 방지합니다
- 검토한 대안과 **버린 이유**를 남김 — 6개월 뒤 "왜 Istio 아니었지?"에 즉답
- PoC 문서와 연결 — 근거가 추적 가능

## 4. 재평가의 실제 — 조건이 바뀌면

```
1년 뒤 가정: 조직 A가 성장해 서비스 120개, 플랫폼팀 4명, A/B 테스트 요구

ADR-003의 재평가 조건 발동:
  → ADR-015: 메시 재평가
     새 조건으로 3층 재적용 → Istio ambient PoC → 결정
     ADR-003은 "대체됨(superseded by ADR-015)"으로 표시 (삭제 아님 — 역사)

★ 이것이 건강한 결정 수명주기:
  결정 → 기록 → 조건 감시 → 재평가 → 새 결정
  (한 번 정하고 교조화 X, 유행 따라 재변경 X — 조건 기반)
```

## 5. 정리

- PoC는 어려운 케이스+운영 시나리오+운영할 사람+사전 기준 — "돌아가나"가 아니라 "우리가 운영할 수 있나"
- "안 쓰기"도 항상 후보 — 대안의 총비용과 비교
- ADR: 맥락·결정·버린 대안·트레이드오프·**재평가 조건** — 결정은 조건의 함수
- 조건이 바뀌면 재평가 발동, 이전 ADR은 대체 표시(역사 보존)
- **★ 비교→PoC→ADR→재평가의 수명주기가 아키텍트의 규율 — 교조도 유행도 아닌 조건 기반 결정**
