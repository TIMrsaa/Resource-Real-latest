# 이론 — 비교 방법론, 주요 대결 종합, 반복 패턴, PoC·ADR

> **🌱 17세 눈높이 비유: 스마트폰 고르기의 어른 버전**
> - **기능표 비교(1층)** = "카메라 화소가 더 높습니다!" — 하지만 넌 사진을 안 찍잖아?
> - **철학 비교(2층)** = 아이폰(통제된 단순) vs 안드로이드(자유·다양) — 왜 그렇게 만들었는지가 미래를 예측
> - **적합 비교(3층)** = 가족이 다 아이폰(생태계)? 예산은? 수리점이 근처에? — **네 상황**이 결정
> - **PoC** = 매장에서 네가 쓰는 앱을 직접 돌려보기 (광고 데모 말고)
> - **ADR** = "왜 이걸 샀는지" 메모 — 2년 뒤 바꿀 때 기준이 됨
> - **핵심** = 최고의 폰은 없습니다, 너에게 맞는 폰이 있습니다 — 도구도 같습니다

---

## 1. 비교의 3층 방법론

```
1층 기능: 무엇을 할 수 있나 (체크리스트)
  함정: 안 쓸 기능은 가치가 아니라 복잡성(운영 비용)
  질문: "그 기능이 우리의 실제 요구인가요?"

2층 철학·구조: 왜 그렇게 설계됐나
  설계 철학이 미래 방향·트레이드오프를 예측
  예: Linkerd의 "운영 최소" 철학 → 앞으로도 단순 유지
      Istio의 "기능 최대" → 계속 확장(복잡성도)
  질문: "이 철학이 우리 방향과 맞나요?"

3층 조직 적합: 우리에게 맞나 (결정 층)
  팀 크기·역량 (rego를 배울 사람이 있나 — 31·32)
  운영 모델 (중앙 플랫폼 팀? 분산 팀? — 16·17)
  규모 (지금과 3년 뒤)
  기존 스택 정합 (이미 Cilium이면 메시도 Cilium? — 22)
  운영 비용 ("설치의 쉬움 ≠ 운영의 쉬움")
  질문: "우리 팀이 이것을 3년 운영할 수 있나요?"

★ 대부분 비교 글은 1층에서 끝납니다. 결정은 3층에서 납니다.
```

## 2. 주요 대결 종합 (커리큘럼 회수)

```
GitOps: ArgoCD(16) vs Flux(17)
  1층: 둘 다 GitOps 조정 (기능 유사해짐)
  2층: ArgoCD=통합 제품(UI 중심), Flux=툴킷(컨트롤러 조합)
  3층: 중앙 플랫폼팀+가시성 중시 → ArgoCD
       경량·유연 조합·멀티테넌시 → Flux

메시: Istio(24) vs Linkerd(25) vs Cilium Mesh(22)
  2층: 기능 최대 vs 운영 최소 vs eBPF·CNI 통합
  3층: 복잡한 트래픽 요구+전담팀 → Istio(ambient로 완화)
       mTLS·관측이 주목적+소팀 → Linkerd
       이미 Cilium CNI+사이드카리스 → Cilium
  ★ 그 전에: "메시가 정말 필요한가?"(24의 비용 구조)

정책: OPA/Gatekeeper(31) vs Kyverno(32)
  2층: rego(범용 언어) vs K8s YAML(네이티브)
  3층: K8s 밖(CI·앱)까지 정책 통일 → OPA
       K8s만+YAML 친숙 → Kyverno (mutate/generate도 강점)

런타임: containerd(26) vs CRI-O(27)
  2층: 범용 데몬(Docker 계보) vs K8s 전용 미니멀
  3층: 사실상 디폴트·생태계 → containerd
       K8s 정렬·최소 표면(OpenShift 계열) → CRI-O
  ★ 대부분은 배포판이 정해줌 (직접 고를 일 적음)

메시징: Kafka/Strimzi(40) vs NATS(38)
  2층: 영속 이벤트 로그·대규모 생태계 vs 경량·실시간·엣지
  3층: 이벤트 소싱·재처리·생태계 → Kafka
       경량 pub/sub·엣지·낮은 지연 → NATS(JetStream으로 영속도)
  ★ 09의 큐vs스트림 + 규모 + 관리형 우선

IaC: Terraform vs Crossplane(41)
  2층: 일회성 apply·state 파일 vs 지속 조정·K8s 네이티브
  3층: 검증·생태계·단순 → Terraform
       GitOps 통합·셀프서비스 API(IDP) → Crossplane

노드: Cluster Autoscaler vs Karpenter(44)
  2층: 고정 노드그룹 vs JIT 딱 맞춤·통합
  3층: 균일 워크로드·단순 → CA
       다양·가변·비용 최적화 → Karpenter

관측 수집: (반복 없음 — OTel(12)이 표준으로 수렴)
  ★ 표준이 있는 곳은 표준을 (06·12·40)
```

## 3. 반복 패턴 인식

```
패턴 ① 기능 최대 vs 운영 최소
  Istio/Linkerd, OPA/Kyverno, Kafka/NATS ...
  → "필요 기능을 먼저 정의, 그걸 가장 단순하게 주는 것"
  → 27의 "범위를 좁히는 것도 설계"

패턴 ② 범용 vs 전용
  OPA(범용 정책) vs Kyverno(K8s 전용)
  containerd(범용) vs CRI-O(K8s 전용)
  → 전용은 그 영역에서 더 매끈, 범용은 통일의 힘

패턴 ③ 통합 제품 vs 조합 툴킷
  ArgoCD vs Flux
  → 통합은 시작 쉬움, 툴킷은 유연

패턴 ④ 표준 수렴 영역은 고민 불요
  OTel(12)·OCI(03)·CloudEvents(40)·Gateway API·
  cert-manager(19)·Prometheus(11)
  → 사실상 표준은 그냥 채택 (비교 에너지를 경쟁 영역에)

패턴 ⑤ "그 전에: 정말 필요한가"
  메시(24)·서버리스(43)·IDP(47) 모두
  → 최고의 선택은 때로 "아직 안 쓰는 것"
```

## 4. 벤치마크·기능표의 함정

```
벤치마크 함정:
  벤더 벤치마크는 자기에게 유리한 시나리오
  우리 워크로드와 다른 조건 (규모·패턴·하드웨어)
  → 참고만, 결정은 우리 PoC로

기능표 함정:
  "체크 개수"가 많은 쪽이 이겨 보임
  하지만 안 쓸 기능은 복잡성 비용
  최신 비교 글도 금세 낡음 (도구는 빠르게 진화 — 예: Istio ambient)
  → 기능표는 1층일 뿐, 3층(조직 적합)으로

날짜 확인:
  "X vs Y (2023)"은 2026년에 틀릴 수 있습니다
  → 항상 최신 문서·릴리스 노트로 재확인 (45의 항해술)
```

## 5. PoC 설계 — 올바른 검증

```
나쁜 PoC: 데모 시나리오 (hello world)
  → 뭐든 잘 됨, 아무것도 검증 안 됨

좋은 PoC:
  ① 우리의 어려운 케이스로 (가장 큰 앱, 가장 복잡한 라우팅,
     가장 까다로운 정책)
  ② 운영 시나리오 포함 (업그레이드해보기, 장애 내보기,
     디버깅해보기 — 설치 말고 운영을 검증)
  ③ 팀이 직접 (외부 컨설턴트 아니라 운영할 사람이)
  ④ 기간 제한 + 평가 기준 사전 정의
     (안 그러면 PoC가 영원히… 또는 "느낌"으로 결정)

★ PoC의 진짜 질문: "우리 팀이 이걸 운영할 수 있나"
  (돌아가느냐가 아니라 — 돌아가는 건 문서만 봐도 압니다)
```

## 6. ADR — 결정의 기록과 재평가

```
ADR(Architecture Decision Record):
  # ADR-007: 서비스 메시로 Linkerd 채택
  ## 상태: 승인 (2026-07)
  ## 맥락: mTLS·골든 시그널 필요, 전담 인력 1명, 서비스 40개
  ## 결정: Linkerd (운영 최소 철학이 팀 규모에 적합)
  ## 검토한 대안: Istio(기능 과잉·운영 부담), Cilium(CNI 교체 비용)
  ## 결과: (+) 단순 운영 (-) 고급 트래픽 기능 부재
  ## 재평가 조건: 서비스 200개 초과, 복잡한 트래픽 정책 필요,
                 전담팀 3명 이상 시 Istio 재검토

가치:
  6개월 뒤 "왜 이거였지?"에 답 (기억은 사라집니다)
  신규 합류자가 맥락 이해
  재평가 조건이 명시 → 조건 바뀌면 트리거 (교조 방지)
  ★ 결정은 그 시점 조건의 함수 — 조건이 바뀌면 결정도 재검토
```
