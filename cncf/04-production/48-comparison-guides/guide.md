# 학습 가이드 — 비교하는 법을 배우기

## 왜 "비교 방법론"인가

인터넷엔 "X vs Y" 글이 넘칩니다. 대부분 기능표입니다 — "X는 이 기능이 있고 Y는 없다". 하지만 커리큘럼에서 배웠듯, 실제 선택을 가르는 것은 기능이 아니었습니다:

```
24·25에서: Istio(기능 최대) vs Linkerd(운영 최소)
  → 갈랐던 것: 팀이 감당할 운영 복잡성
31·32에서: OPA(rego·범용) vs Kyverno(K8s YAML)
  → 갈랐던 것: 팀의 언어·범용성 필요
16·17에서: ArgoCD(UI·중앙) vs Flux(툴킷·경량)
  → 갈랐던 것: 조직의 운영 모델(중앙 팀 vs 분산)
```

공통점: **기능이 아니라 조직·팀·운영이 갈랐습니다.** 이 모듈은 그 판단 축을 방법론으로 만듭니다.

## 반복 패턴 — "기능 최대 vs 운영 최소"

커리큘럼의 비교들에 반복해서 나타난 패턴이 있습니다:

```
한쪽: 기능이 많고 강력, 대신 복잡·무거움
  Istio, OPA, ArgoCD(상대적), Kafka, Crossplane(대 Terraform 아님, IDP 맥락)
다른쪽: 기능을 좁히고 단순, 대신 운영 쉬움
  Linkerd, Kyverno, Flux, NATS, (관리형)

교훈 (27의 "범위를 좁히는 것도 설계"):
  "기능이 많다 = 좋다"가 아닙니다
  안 쓸 기능의 복잡성도 운영 비용입니다
  → 필요한 기능 집합을 먼저 정의하고, 그걸 가장 단순하게 주는 것을
```

## 비교의 3층 — 기능표 너머

```
1층: 기능 (표면) — 대부분 비교가 여기서 끝남
  "X는 A 기능이 있다" → 하지만 그 기능이 우리에게 필요한가?

2층: 철학·구조 (중간) — 커리큘럼이 판 것
  왜 그렇게 설계됐나 (Linkerd는 왜 기능을 줄였나)
  → 철학이 미래 방향을 예측하게 함

3층: 조직 적합 (심층) — 실제 결정 층
  우리 팀 크기·역량·운영 모델에 맞나
  운영 비용을 감당하나 ("설치의 쉬움 ≠ 운영의 쉬움")
  기존 스택·기술과 정합하나
```

이 모듈의 핵심 훈련: 어떤 비교든 3층까지 내려가기.

## PoC와 ADR — 결정의 규율

비교는 문서 읽기로 끝나지 않습니다:

```
PoC(개념 검증): 우리 환경·우리 워크로드로 직접 검증
  단, 올바른 PoC 설계가 중요 (데모 시나리오가 아니라
  우리의 어려운 케이스로 — lab-02)

ADR(Architecture Decision Record): 결정을 기록
  무엇을, 왜, 어떤 대안을 검토했고, 어떤 조건이면 재평가하나
  → 6개월 뒤 "왜 이걸 골랐지?"에 답할 수 있게
  → 조건이 바뀌면(규모·팀) 재평가 트리거
```

## 이 모듈의 위치 — 커리큘럼의 회수

이 모듈은 새 지식이 거의 없습니다. 대신 배운 것을 **판단으로 회수**합니다:

```
16·17, 24·25, 26·27, 31·32, 38·40, 41, 44의 "vs"들
  → 각 모듈에서 부분 판단
  → 여기서 방법론으로 종합
  → 이제 커리큘럼에 없는 새로운 "vs"(45의 새 프로젝트)도
    같은 방법으로 판단할 수 있습니다
```

45(항해술)가 "새 프로젝트를 지도에 놓는 법"이었다면, 48은 "지도 위 이웃한 것들 사이에서 고르는 법"입니다. 둘이 합쳐져 완전한 자립 — 커리큘럼 이후에도 스스로 배우고 스스로 결정합니다.
