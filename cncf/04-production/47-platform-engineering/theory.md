# 이론 — 인지 부하, Team Topologies, IDP, 황금 경로, 제품 사고, 측정

> **🌱 17세 눈높이 비유: 학교 급식실 vs 각자 요리**
> - **각자 요리(플랫폼 없음)** = 학생 300명이 각자 장보고 요리(인프라 직접) → 공부(비즈니스)할 시간 없음
> - **급식실(플랫폼 팀)** = 급식 팀이 재료·조리(복잡성)를 흡수, 학생은 식판 들고 받기만(셀프서비스)
> - **황금 경로(오늘의 메뉴)** = 잘 짜인 균형식 — 대부분 이걸로 충분(쉬우니 자연히 선택), 하지만 알레르기 있으면 다른 선택 가능(강제 아님)
> - **제품으로서의 플랫폼** = 급식이 맛없으면 학생이 매점 감(우회) → 급식 팀이 만족도 조사하고 개선 → "학생이 먹고 싶은 급식"
> - **측정** = "급식을 차렸다"가 아니라 "학생이 잘 먹고 공부에 집중하나"가 성공
> - **핵심** = 복잡성을 없애는 게 아니라 전담 팀이 흡수 → 다수는 본업에 집중

---

## 1. 인지 부하의 재배치 (본질)

```
복잡성은 사라지지 않습니다 (46의 플랫폼은 본질적으로 복잡)
질문: 그 인지 부하를 누가 지나요?

플랫폼 없음:
  모든 개발자가 K8s·Istio·Prometheus·Crossplane을 알아야
  → 인지 부하가 개발자 전원에 분산 → 아무도 본업에 집중 못 함

플랫폼 엔지니어링:
  플랫폼 팀이 복잡성 흡수 → 개발자에겐 단순 인터페이스
  → 인지 부하를 소수 전문팀에 집중, 다수는 해방

★ 핵심: 인지 부하를 없애는 게 아니라 재배치
  (Team Topologies의 근본 통찰)
```

## 2. Team Topologies — 조직 구조

```
네 팀 유형:
  스트림 정렬(Stream-aligned): 제품·기능 개발팀 (다수, 빠른 흐름이 목표)
  플랫폼(Platform): 스트림 팀에 셀프서비스 제공 (인지 부하↓)
  활성화(Enabling): 전문 지식 전수 (일시적 코칭)
  난해한 하위시스템(Complicated-subsystem): 특수 전문 (예: ML 엔진)

세 상호작용 모드:
  협업(Collaboration): 함께 (탐색적, 일시적)
  X-as-a-Service: 서비스로 제공 (플랫폼 팀의 주 모드)
  촉진(Facilitating): 돕기 (활성화 팀)

플랫폼 팀의 목표:
  스트림 팀의 흐름(flow)을 빠르게 = 인지 부하를 낮춰
  X-as-a-Service로 셀프서비스 제공
```

## 3. IDP 통합 — 41·42·46이 하나로

```
내부 개발자 플랫폼(IDP) = 41 + 42 + 46:

  포털(42 Backstage):     개발자 접점 (카탈로그·템플릿·문서)
     ↓
  황금 경로(템플릿):       "새 서비스" → 스캐폴딩
     ↓
  인프라 API(41 Crossplane): DB·버킷을 Claim으로
     ↓
  배포(46 GitOps):         ArgoCD/Flux가 조정
     ↓
  플랫폼 층(46):           관측·메시·보안이 자동 적용
     ↓
  런타임(K8s)

개발자 경험:
  Backstage에서 "새 결제 서비스" 클릭 →
    레포·CI·DB(Crossplane)·관측(자동)·배포(GitOps)·메시(자동)
    이 몇 분 만에 준비 →
  개발자는 비즈니스 로직만 (인프라는 플랫폼이)

★ 41·42·46은 부품, IDP는 완성품, 플랫폼 엔지니어링은 그것을 운영하는 규율
```

## 4. 황금 경로 — 설계 원칙

```
황금 경로(Golden Path): 잘 닦인 표준 경로
  모범 사례를 내장 (관측·보안·배포가 기본으로 켜짐)
  개발자 결정을 줄임 (인지 부하↓)
  일관성 (모든 서비스가 같은 표준)

설계 원칙:
  ① pave, not fence (닦되 가두지 마세요)
     매력적이어서 자연히 선택 (강제 아님)
     벗어날 정당한 이유 있으면 벗어날 수 있게
  ② 80% 케이스를 덮되, 20% 예외를 허용
     대부분에 맞는 경로 + 벗어날 문(escape hatch)
  ③ 넓히기 쉽게 (새 요구가 생기면 경로에 추가)
  ④ 안전한 기본값 (개발자가 잊어도 관측·보안이 켜짐)

강제의 함정 (pitfalls):
  경로를 강제 → 개발자가 우회(그림자 IT) → 플랫폼 불신
  → 41(새는 추상)·42(감옥이 된 경로)의 반복
```

## 5. 제품으로서의 플랫폼 — 핵심 사고 전환

```
프로젝트 사고 (실패):
  플랫폼을 만들고 "이제 이거 써" → 낡고 안 씀 (42 사고)

제품 사고 (성공):
  내부 고객(개발자)이 있습니다
    → 그들의 니즈를 조사 (인터뷰·설문)
    → 로드맵을 만듭니다 (개발자가 원하는 것)
    → 채택률·만족도를 측정
    → 피드백으로 개선 (끝나지 않음)
    → 마케팅도 합니다 (플랫폼을 알리고 온보딩)

제품 관리 요소:
  - 내부 고객 조사 (개발자가 뭘 힘들어하나)
  - 로드맵·우선순위 (임팩트 큰 것부터)
  - 채택 지표 (강제 아닌 자발적 사용)
  - 문서·온보딩 (42 TechDocs)
  - 지원·피드백 채널

★ "우리가 만든 걸 써라" → "개발자가 원하는 걸 만든다"
  이 전환이 성패를 가릅니다 (도구가 아니라 태도)
```

## 6. 측정 — 성공의 지표

```
플랫폼 성공 지표 (제품처럼):
  채택률: 자발적 사용률 (강제하면 무의미)
  DORA(cicd 26): 배포빈도·리드타임·MTTR·변경실패율 개선?
  인지 부하: 개발자가 인프라에 쓰는 시간↓ (설문)
  개발자 만족(DevEx): NPS·만족도 조사
  온보딩 시간: 신입 첫 배포까지 (Time to First Deploy)
  Time to Provision: 인프라 요청→준비 시간(41이 며칠→분)

측정의 의미:
  "플랫폼을 깔았다"(산출물) ≠ "개발자 흐름이 빨라졌다"(결과)
  → 결과(outcome)로 검증, 산출물(output)로 만족 금지
  → 안 쓰이는 플랫폼은 실패 (아무리 정교해도)
```

## 7. 판단 — 언제 플랫폼 팀인가

```
플랫폼 엔지니어링이 맞는 때:
  개발팀이 여럿 + 인프라 인지 부하가 흐름을 막음
  중복(각 팀이 같은 셋업 반복)이 심함
  규모가 전담 플랫폼 팀을 정당화

과한 때:
  팀이 작음 (몇 명) → 관리형(Heroku·Vercel·클라우드 PaaS)로 충분
  플랫폼 팀 유지 비용 > 이득
  → 41·42·46을 다 만들 필요 없음 (관리형 우선, 09의 정신)

핵심 균형:
  플랫폼 팀도 비용 → 그 비용이 스트림 팀 전체의 흐름 개선으로 정당화되나
  → 소수 대기업 패턴을 소규모가 흉내내면 오버엔지니어링
```
