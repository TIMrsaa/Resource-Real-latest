# 흔한 함정과 실무 사고

## 흔한 함정 5선

### 1. 도구를 깔면 플랫폼 엔지니어링이 된다는 착각
Backstage(42)+Crossplane(41)+ArgoCD(46)를 깔고 "우리도 IDP가 있다"고 선언합니다. 하지만 플랫폼 엔지니어링의 본질은 도구가 아니라 **조직 구조(플랫폼 팀)와 제품 사고(내부 고객·측정·개선)**입니다. 도구만 있고 조사·측정·개선 루프가 없으면 42의 "3개월 만에 죽은 포털"이 반복됩니다. 도구는 마지막에, 사고와 팀이 먼저.

### 2. 강제 채택 — fence를 치고 채택률 100%를 자랑
"모든 팀은 반드시 플랫폼을 쓰라"고 강제하고 채택률 100%를 성과로 보고합니다. 강제된 채택은 아무것도 증명하지 않습니다 — 개발자가 원해서 쓰는지(제품이 좋은지)를 알 수 없고, 불만은 지하로(그림자 IT·불신) 갑니다. 채택은 **자발적이어야 신호**입니다. 경로가 매력적이면 강제 없이 채택됩니다(pave not fence). 강제하고 싶어질 때가 경로를 개선할 때입니다.

### 3. 플랫폼 팀이 티켓 처리 팀으로 변질
셀프서비스를 만든다더니, 실제로는 개발자 요청을 플랫폼 팀이 **대신 처리**합니다(티켓 → 플랫폼 팀이 YAML 작성). 인지 부하가 재배치된 게 아니라 병목이 인프라팀에서 플랫폼팀으로 이동했을 뿐입니다. Team Topologies의 X-as-a-Service(개발자가 스스로)가 핵심 — 플랫폼 팀은 경로(도구·템플릿·문서)를 만들고, 실행은 개발자가 셀프서비스로. 티켓이 늘면 경로가 부족하다는 신호입니다.

### 4. 대기업 패턴을 소규모가 흉내
개발자 10명 회사가 Spotify의 Backstage, Netflix의 플랫폼 팀을 흉내 냅니다. 플랫폼 팀 유지 비용(사람·도구·운영)이 이득을 초과하고, 정작 제품 개발이 느려집니다. 소규모는 관리형 PaaS+템플릿 레포+좋은 문서로 "인지 부하 재배치"의 정신만 실현하는 게 맞습니다(theory 7절). 플랫폼 엔지니어링은 규모가 정당화할 때의 답입니다 — 09의 "관리형 우선"이 조직 설계에도 적용됩니다.

### 5. 산출물 지표로 자축 — 결과를 안 봄
"온보딩한 서비스 50개, 플랫폼 가동률 99.9%, 템플릿 12종"으로 성공을 보고합니다. 전부 산출물(output)이지 결과(outcome)가 아닙니다 — 개발자 흐름(DORA)이 빨라졌는지, 인지 부하가 줄었는지, 만족도가 올랐는지가 결과입니다. 산출물은 좋아 보여도 결과가 없으면(배포는 그대로 느리고 개발자는 불행) 플랫폼은 실패입니다. 측정 체계(lab-02)를 결과 중심으로.

## 실무 사고 사례: "완벽한 IDP를 만들고 개발자를 잃다"

한 중견 기업의 신설 플랫폼 팀(6명)이 1년짜리 IDP 프로젝트를 시작했습니다. 목표는 원대했습니다 — Backstage 포털, Crossplane 인프라 API, 풀 GitOps, 완벽한 황금 경로. 팀은 1년간 **개발자와 거의 대화하지 않고** 조용히 만들었습니다("완성되면 놀랄 거야").

1년 뒤 대대적 론칭. 그런데:

1. **경로가 실제 니즈와 어긋났습니다** — 플랫폼 팀이 상상한 "표준 서비스"는 Go 마이크로서비스였지만, 실제 개발팀 절반은 Python 모노리스+배치 작업이었습니다. 템플릿이 안 맞았습니다.
2. **기존 워크플로 무시** — 개발팀들은 이미 자기들 CI·배포 스크립트가 있었습니다. 이관 비용(기존 것을 버리고 새로 배우기)이 커서 아무도 옮기지 않았습니다.
3. **강제 시도 → 반발** — 채택이 안 되자 경영진을 통해 "분기 내 전 팀 이관"을 강제했습니다. 개발팀들은 형식적으로 등록만 하고 실제 작업은 기존 방식으로(그림자 IT). 플랫폼 팀과 개발팀 사이에 불신이 쌓였습니다.
4. **측정 부재** — 채택률·만족도·DORA를 측정하지 않아, 무엇이 문제인지 데이터도 없었습니다.

2년 차에 플랫폼 팀은 절반으로 축소됐고, IDP는 "비싼 카탈로그"로 남았습니다.

**원인 분석:**

1. **1년 잠수함 개발** — 제품 사고의 정반대. 내부 고객(개발자) 조사 없이 상상으로 만들었습니다.
2. **빅뱅 론칭** — 46의 빅뱅 함정의 조직판. 작게 시작해 한 팀과 검증하며 넓혀야 했습니다.
3. **이관 비용 무시** — 기존 워크플로가 있는 팀에겐 "새것이 좋다"만으론 부족합니다. 이관 비용 < 이득을 증명해야 합니다.
4. **강제로 도피** — 매력으로 채택시키지 못하자 강제했고, 그림자 IT와 불신만 얻었습니다.

**교훈:**
- **첫 주부터 개발자와** — 조사 → 최소 경로(MVP) → 한 파일럿 팀과 검증 → 넓히기 (제품 개발 그대로)
- **가장 고통받는 팀부터** — 니즈가 절실한 팀이 첫 고객 (성공 사례가 최고의 마케팅)
- **이관 비용을 설계** — 기존 워크플로에서 점진 이관 경로 제공 (한꺼번에 버리라고 하지 말 것)
- **강제 금지** — 채택이 안 되면 경로를 고칠 것 (강제는 신호를 죽입니다)
- **처음부터 측정** — 채택률·만족도·DORA가 없으면 항해 계기판 없이 나는 것

★ 47(플랫폼 엔지니어링)의 최종 교훈: 41·42·46의 도구가 아무리 정교해도, "내부 고객을 조사하고, 작게 검증하고, 결과를 측정하고, 끝없이 개선하는" 제품의 규율이 없으면 실패합니다. 플랫폼은 기술 프로젝트가 아니라 **개발자를 고객으로 하는 제품 조직**입니다 — 이 사고 전환이 production 트랙의 핵심이며, 48(선택 가이드)의 판단도 결국 "우리 고객(개발자·조직)에게 맞는가"로 수렴합니다.
