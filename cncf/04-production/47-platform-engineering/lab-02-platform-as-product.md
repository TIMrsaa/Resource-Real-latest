# Lab 02 — 제품으로서의 플랫폼: 운영과 측정

> lab-01에서 황금 경로를 설계했습니다. 이 랩은 그 플랫폼을 **제품처럼 운영**하는 연습입니다 — 내부 고객 조사, 로드맵, 채택·성과 측정(DORA), 그리고 "산출물이 아니라 결과"로 성공을 검증하는 틀을 세웁니다.

## 1. 내부 고객 조사 설계 (제품 관리의 시작)

플랫폼 팀이 분기마다 돌릴 개발자 조사를 설계합니다:

```
개발자 설문 (분기, 10분 이내):
  [인지 부하]
  Q1. 지난 달, 인프라(K8s·CI·배포 설정)에 쓴 시간 비율은?
      (0~10% / 10~30% / 30~50% / 50%+)
  Q2. 인프라 작업 중 가장 고통스러운 것 하나는? (주관식)

  [황금 경로]
  Q3. 새 서비스를 템플릿으로 시작했나, 수동으로 했나요? 이유는?
  Q4. 경로를 벗어난 적이 있다면 무엇이 부족해서였나요?

  [만족도]
  Q5. 플랫폼이 당신의 개발 속도에 도움이 되나요? (1~5)
  Q6. 동료에게 플랫폼 사용을 추천하겠나요? (NPS)

★ Q4가 보물 — 경로를 벗어난 이유가 다음 로드맵
  (벗어남은 실패가 아니라 니즈 신호, lab-01의 pave 정신)
```

## 2. 측정 대시보드 설계 — 산출물이 아니라 결과

```
플랫폼 성과 대시보드 (Grafana — 46의 관측 층 활용):

  [채택 (자발적 사용)]
  - 템플릿으로 생성된 서비스 비율 (전체 신규 중 %)
  - Backstage 주간 활성 사용자 / 전체 개발자
  - Crossplane Claim 수 vs 수동 인프라 티켓 수

  [흐름 (DORA — cicd 26)]
  - 배포 빈도 (팀별·전체)
  - 변경 리드타임 (커밋→프로덕션)
  - MTTR (장애→복구)
  - 변경 실패율

  [효율]
  - Time to First Deploy (신입 온보딩→첫 배포)
  - Time to Provision (인프라 요청→준비: 41 도입 전 며칠 → 후 몇 분)

읽는 법:
  채택률이 낮습니다 → 경로가 매력 없거나 몰라서 (조사로 원인)
  DORA가 안 좋아집니다 → 플랫폼이 흐름을 방해? (병목 조사)
  ★ "플랫폼 가동률 99.9%"는 결과 지표가 아님 (산출물 지표)
    개발자 흐름이 빨라졌는가가 결과
```

## 3. 로드맵 연습 — 임팩트로 우선순위

조사 결과(가상)로 분기 로드맵을 짭니다:

```
조사 결과:
  a. "DB 마이그레이션 도구가 경로에 없어 수동" (개발자 12명 언급)
  b. "ML 워크로드용 GPU 템플릿이 없다" (2명)
  c. "Backstage 대시보드가 느리다" (5명)
  d. "스테이징 환경 셀프서비스가 안 된다" (9명)

우선순위 (임팩트 × 노력):
  1. a — 다수 고통 + 황금 경로 확장 (임팩트 큼)
  2. d — 다수 + Crossplane Composition 추가로 가능 (41의 힘)
  3. c — 중간, 성능 개선
  4. b — 소수지만 ML팀 우회(그림자 IT) 위험 → escape hatch 먼저 안내, 전용 경로는 다음 분기

★ 제품 관리 그대로: 고객(개발자) 소리 → 임팩트 우선순위 → 로드맵 공개
  플랫폼 팀이 "하고 싶은 것"이 아니라 "개발자가 필요한 것" 순서
```

## 4. 안티패턴 자가진단

자기 조직이 "프로젝트 사고"에 빠졌는지 점검하는 체크리스트:

```
□ 플랫폼 로드맵이 개발자 조사 없이 플랫폼 팀 내부에서만 나옵니다
□ 채택률을 측정하지 않습니다 (또는 강제로 100%)
□ "깔았다/만들었다"로 보고하고 결과(흐름 개선)는 안 봅니다
□ 경로 이탈을 금지합니다 (fence)
□ 피드백 채널이 없습니다 (또는 응답하지 않습니다)
□ 문서·온보딩이 뒤처져 있습니다
□ 플랫폼 팀이 티켓 처리 팀이 됐습니다 (셀프서비스가 아니라 대행)

3개 이상 해당 → 프로젝트 사고 경고
특히 마지막 항목: 플랫폼 팀이 "대신 해주는 팀"이 되면
  인지 부하가 재배치된 게 아니라 병목이 이동한 것
  → X-as-a-Service(셀프서비스)로 돌아가야 (theory 2절)
```

## 5. 플랫폼 팀의 규모 판단 (theory 7절 실전)

```
자가 판단 질문:
  개발팀이 몇 개인가요? (2~3팀이면 플랫폼 팀이 과할 수 있음)
  중복 셋업에 낭비되는 시간이 플랫폼 팀 인건비를 넘나요?
  관리형(PaaS·클라우드)으로 같은 셀프서비스가 되지 않나요?

소규모의 대안:
  풀 IDP(41+42+46) 대신:
    관리형 PaaS + 템플릿 레포 + 좋은 README
  → "플랫폼 엔지니어링의 정신(인지 부하↓)"은 도구 없이도 실현 가능
  → 대기업 패턴 흉내가 아니라 자기 규모의 답 (오버엔지니어링 경계)
```

## 6. 정리

- 조사(분기 설문·인터뷰)가 로드맵의 원천 — 경로 이탈 이유(Q4)가 보물
- 측정은 결과로: 채택률·DORA·Time to First Deploy (산출물 지표에 만족 금지)
- 우선순위는 임팩트 × 노력 — 개발자가 필요한 것 순서
- 안티패턴: 조사 없는 로드맵, 강제 채택, 티켓 처리 팀化(병목 이동)
- 소규모는 관리형+템플릿으로 정신만 — 도구가 아니라 인지 부하 재배치가 본질
- **★ "플랫폼을 깔았다"가 아니라 "개발자 흐름이 빨라졌다"가 성공 — 제품처럼 끝없이**
