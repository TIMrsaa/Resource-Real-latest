# 자가 점검 퀴즈

**Q1.** 프로덕션 K8s 플랫폼의 층을 위(앱)에서 아래(기반)로 나열하면?

**Q2.** 부트스트랩 순서는 무엇이 강제하나요? 권장 순서는?

**Q3.** cert-manager와 관측을 왜 "일찍" 깔아야 하나요?

**Q4.** app-of-apps 패턴과 sync-wave(16)는 무엇을 하나요?

**Q5.** 층 사이의 통합점 예시는? 왜 "층이 서로 강화"인가요?

**Q6.** "플랫폼 = 코드"의 재현 가능성과 그 한계는?

**Q7.** 빅뱅 도입이 왜 위험한가? 점진 도입의 권장 단계는?

**Q8.** "메시를 성급히 넣어 멈춘" 사고의 원인과 교훈은?

---

## 정답

**A1.** 위에서 아래로: 애플리케이션(비즈니스 워크로드) → 개발자 플랫폼(Backstage 42·Crossplane 41, 셀프서비스) → 배포(ArgoCD/Flux 14·15 + Helm/Kustomize) → 트래픽·메시(Istio/Linkerd/Cilium 24·25·22 + 인그레스) → 보안(cert-manager 19·SPIFFE 33·Kyverno 32·Falco 30) → 관측(Prometheus 11·OTel 12·Grafana·Loki·Jaeger 13) → 데이터·시크릿(ESO/Vault·CSI·오퍼레이터 39·40) → 클러스터 기반(K8s·CNI 26·CoreDNS 20·containerd·etcd 21). 각 층은 아래 층에 의존합니다.

**A2.** 층 사이의 **의존**이 순서를 강제합니다(A가 B를 필요로 하면 B를 먼저). 권장 순서: ① 클러스터 기반(K8s·CNI·CoreDNS) → ② GitOps(나머지를 배포할 뼈대) → ③ cert-manager(웹훅·mTLS·인증서의 전제) → ④ 관측(일찍! 뒤 층 디버그용) → ⑤ 보안·정책(앱 전 가드레일) → ⑥ 메시·인그레스(사이드카는 앱 전) → ⑦ 데이터·시크릿 오퍼레이터 → ⑧ 애플리케이션. 순서를 틀리면 닭-달걀·디버그 불가.

**A3.** cert-manager는 웹훅 TLS·인그레스 인증서·메시 mTLS 등 많은 층의 전제라, 나중에 깔면 그것들이 막힙니다(웹훅 있는 Kyverno·메시 등이 인증서를 못 얻음). 관측은 이후 모든 층 도입이 그 위에서 이뤄져야 문제를 볼 수 있기 때문입니다 — 관측 없이 메시·정책·앱을 도입하다 문제가 생기면 볼 수단이 없어 "눈 감고 운전"이 됩니다. 둘 다 다른 층의 전제/디버그 기반이므로 일찍 깝니다.

**A4.** app-of-apps는 루트 Argo Application 하나가 각 층을 다시 Application으로 선언·배포하는 패턴입니다 — `git clone` + 루트 apply만으로 전체 플랫폼이 조립되어 "플랫폼 = 코드"가 됩니다. sync-wave(16의 순서 제어)는 각 Application에 붙는 애너테이션(낮을수록 먼저)으로, 부트스트랩 순서(cert-manager 0 → 관측 1 → 보안 2 → 메시 3 → 앱 4)를 GitOps가 강제하게 합니다 — 손으로 지키던 의존 순서를 코드로 만듭니다.

**A5.** 예시: 메시(Istio/Linkerd)가 프록시 메트릭을 Prometheus로, 추적을 OTel로 보내 관측 층이 자동으로 서비스 간 골든 시그널을 수집; cert-manager가 메시 mTLS 인증서를, SPIFFE가 워크로드 신원을 제공해 메시의 mTLS가 보안 층 위에; Kyverno가 GitOps로 들어온 배포도 admission 검증; ArgoCD 상태가 Prometheus로 가 배포 건강도까지 관측. "층이 서로 강화"인 이유: 개별 프로젝트일 땐 없던 시너지가 생깁니다 — 앱 코드 변경 없이 모든 통신이 관측되고, 모든 층(자기 자신 포함)이 관측 가능해집니다.

**A6.** "플랫폼 = 코드(GitOps)"면 클러스터를 통째로 잃어도 새 클러스터 + ArgoCD 설치 + 루트 apply로 전체 플랫폼이 sync-wave 순서로 재조립됩니다(36 재해 복구가 GitOps로 재현). 한계: **구성(코드)만 재현되고 데이터(상태)는 재현되지 않습니다** — etcd·DB·PV의 실제 데이터는 GitOps로 복원되지 않으므로 별도 백업(Velero·스냅샷)이 필요합니다. 구성(Git에서 재현)과 데이터(백업에서 복원)를 분리해 각각 다루고 둘 다 복구를 리허설해야 합니다(36·39·40의 "복제≠백업").

**A7.** 빅뱅(처음부터 모든 층)은 팀이 이해하지 못한 층이 장애의 근원이 되고, 운영 부담이 폭발하며, 문제 원인 파악이 불가능합니다 — 이해·운영 능력을 초과합니다. 점진 도입 권장 단계: 1단계 관측+GitOps+cert-manager(기본), 2단계 정책+시크릿(가드레일), 3단계 메시(트래픽이 정말 복잡해질 때 — 24는 비용), 4단계 개발자 플랫폼(규모 커지면 — 42는 문화). 각 층을 이해·운영 가능할 때 추가하며, 층마다 "정말 필요한가·관리형으로 되나·운영 감당되나"를 판단합니다.

**A8.** 원인: ① 관측 없이 메시를 먼저 도입해 지연 원인을 못 봄, ② cert-manager 설정 미비로 Istio mTLS 통신 실패(순서 문제), ③ 20개 서비스 × 사이드카 리소스가 노드를 압박해 Pod Pending(44), ④ 팀이 Istio(24)를 깊이 이해 못 한 채 도입해 트래픽 오설정. 교훈: 관측을 먼저, 순서 준수(cert-manager→관측→보안→메시), 점진 도입(메시는 트래픽이 정말 필요하고 팀이 24를 이해한 후), 빅뱅 금지, 각 층의 비용 인지(24 메시는 "비용 구조"), 그리고 "20개 서비스에 풀 메시가 정말 필요했나"라는 근본 질문 — 더 단순한 것으로 충분했을 수 있습니다. 조립의 지혜는 순서·통합·점진성에 있습니다.
