# 이론 — 층, 의존·순서, GitOps 조립, 통합점, 점진 도입

> **🌱 17세 눈높이 비유: 집을 짓는 순서**
> - **집(플랫폼)** = 여러 공정이 층층이 (기초→골조→배관·전기→벽→인테리어)
> - **순서가 강제됨** = 배관(cert-manager)을 벽(앱) 치기 전에, 전기(관측)를 먼저 넣어야 나중에 안 뜯음
> - **기초(K8s+CNI+DNS)** = 이게 없으면 아무것도 못 올림
> - **감리·설계도(GitOps)** = 집 전체가 설계도(Git)대로 — 무너져도 설계도로 재건축
> - **완벽한 집은 없다** = 원룸엔 원룸에 맞는 공정, 대저택엔 대저택 — 필요한 층만
> - **핵심** = 도구를 아는 것과 "어떤 순서로 어떻게 쌓나"를 아는 것은 다릅니다

## 1. 플랫폼의 층 (전체 지도)

```
층 (위 = 앱에 가까움, 아래 = 인프라):

 애플리케이션        비즈니스 워크로드
────────────────────────────────────────
 개발자 플랫폼(47)   Backstage(42)·Crossplane(41) — 셀프서비스
────────────────────────────────────────
 배포               ArgoCD(16)/Flux(17) + Helm(15)/Kustomize
────────────────────────────────────────
 트래픽·메시        인그레스(Gateway API)·Istio(24)/Linkerd(25)/Cilium(22)
────────────────────────────────────────
 보안               cert-manager(19)·SPIFFE(33)·Kyverno(32)·OPA(31)·Falco(30)
────────────────────────────────────────
 관측               Prometheus(11)·OTel(12)·Grafana·Loki·Jaeger(13)·Fluent(14)
────────────────────────────────────────
 데이터·시크릿      ESO/Vault(cicd23)·CSI 스토리지·오퍼레이터(39·40)
────────────────────────────────────────
 클러스터 기반      K8s·CNI(26)·CoreDNS(20)·containerd(26)·etcd(21)
────────────────────────────────────────

★ 각 층은 아래 층에 의존 — 이 의존이 순서를 강제
```

## 2. 각 층의 선택지 (48 예고)

```
관측:      Prometheus(사실상 표준) + Grafana + Loki(로그) + Jaeger/Tempo(추적) + OTel(수집)
배포:      ArgoCD(UI·멀티클러스터) vs Flux(툴킷·경량)
메시:      Istio(기능 최대) vs Linkerd(운영 최소) vs Cilium(eBPF·CNI 통합)
인그레스:  Gateway API(표준) + 컨트롤러(Envoy Gateway·Istio·NGINX)
정책:      Kyverno(K8s 네이티브) vs OPA/Gatekeeper(rego·범용)
런타임보안: Falco(탐지) + seccomp/AppArmor(예방)
인증서:    cert-manager(사실상 표준)
신원:      SPIFFE/SPIRE(워크로드 신원)
시크릿:    External Secrets Operator + Vault/클라우드 시크릿

★ "사실상 표준"(Prometheus·cert-manager)은 선택 고민이 적고,
  경쟁(메시·배포·정책)은 48에서 판단 (조직 특성으로)
```

## 3. 의존과 순서 — 부트스트랩

```
부트스트랩 순서 (의존이 강제):

1. 클러스터 기반 (K8s·CNI·CoreDNS)
   → 이게 없으면 아무것도 안 됨

2. GitOps (ArgoCD/Flux)
   → 나머지를 선언형으로 배포할 뼈대
   → 자기 자신도 GitOps로 관리(self-management)

3. cert-manager
   → 많은 것의 전제(웹훅 TLS·인그레스·mTLS)
   → 일찍 깔아야 뒤 층이 막히지 않음

4. 관측 (Prometheus·OTel)
   → 일찍! 안 보이면 뒤 층 도입 시 디버그 불가
   → "관측 없이 복잡한 것 도입 = 눈 감고 운전"

5. 보안·정책 (Kyverno·SPIFFE·Falco)
   → 앱 배포 전에 가드레일

6. 메시·인그레스
   → 사이드카 주입(24)은 앱 전에 준비
   → 트래픽 관리 인프라

7. 데이터·시크릿 오퍼레이터
   → 앱이 필요로 하는 상태·비밀

8. 애플리케이션
   → 위 층들이 준비된 위에

★ 닭-달걀 위험 (pitfalls):
  cert-manager 웹훅이 cert-manager 인증서를 필요로 하는 부트스트랩 순환,
  GitOps가 자신을 배포하는 순환 → 초기 부트스트랩은 신중히
```

## 4. GitOps 조립 — app-of-apps

```
루트 Application (부트스트랩)
  → platform/ 디렉터리를 sync
     ├── 00-cert-manager/     (sync-wave 0, 먼저)
     ├── 01-observability/    (sync-wave 1)
     ├── 02-security/         (sync-wave 2)
     ├── 03-mesh/             (sync-wave 3)
     └── 04-apps/             (sync-wave 4, 마지막)

sync-wave (16의 순서 제어):
  argocd.argoproj.io/sync-wave: "0"  # 낮을수록 먼저
  → 의존 순서를 GitOps가 강제

결과:
  git clone → 루트 Application apply → 전체 플랫폼이 순서대로 조립
  → 클러스터를 잃어도 Git에서 재현 (재해 복구, 36)
  → "플랫폼 = 코드"
```

## 5. 층 사이의 통합점 (프로젝트가 만나는 곳)

```
관측 ↔ 메시:
  Istio/Linkerd가 메트릭을 Prometheus로, 추적을 OTel로
  → 메시의 골든 시그널이 자동으로 관측 층에

보안 ↔ 메시:
  cert-manager가 메시 mTLS 인증서를, SPIFFE가 워크로드 신원(33)
  → 24의 mTLS가 19·33 위에

배포 ↔ 정책:
  Kyverno(32)가 배포 시 검증(admission) — GitOps로 들어온 것도 검사
  → 14의 배포에 32의 가드레일

관측 ↔ 배포:
  ArgoCD 상태·동기화가 Prometheus로 → 배포 건강도 관측
  → 42 Backstage가 이 모두를 한 화면에

★ 통합점이 플랫폼의 진짜 가치 — 층이 서로를 강화
  (개별 프로젝트일 땐 안 보이던 시너지)
```

## 6. 점진 도입 — 완벽한 스택의 함정

```
안티패턴: 처음부터 모든 층을 다 (빅뱅)
  → 운영 부담 폭발, 이해 못 한 층이 장애원

권장: 점진적 (성숙도에 따라)
  1단계: 관측 + GitOps + cert-manager (기본)
  2단계: 정책 + 시크릿 (가드레일)
  3단계: 메시 (트래픽 필요해질 때 — 24는 비용)
  4단계: 개발자 플랫폼 (규모 커지면 — 42는 문화)
  → 각 층을 이해·운영 가능할 때 추가

판단 (전체 커리큘럼 종합):
  각 층: 정말 필요한가? 관리형으로 되나요? 운영 감당되나요?
  "설치의 쉬움 ≠ 운영의 쉬움"을 층마다
  작은 팀은 관리형 최대 + 최소 층
```
