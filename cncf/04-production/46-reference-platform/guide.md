# 학습 가이드 — 프로젝트에서 플랫폼으로

## 관점의 마지막 전환

이 커리큘럼의 여정을 돌아봅시다:

```
beginner(01~10): 지형 — "무엇이 있나"
intermediate·advanced(11~45): 개별 프로젝트 — "각각 어떻게 동작하나"
production(46~48): 플랫폼 — "이것들을 어떻게 조립하나"  ← 지금
```

실무 엔지니어가 마주하는 것은 Prometheus 하나, Istio 하나가 아니라 **수십 개가 맞물린 플랫폼**입니다. 이 모듈은 그 조립의 원리 — 층(layer), 의존, 순서 — 를 다룹니다.

## 층으로 생각하기

플랫폼은 뒤죽박죽 도구 모음이 아니라 **층의 쌓임**입니다:

```
┌─────────────────────────────────────────┐
│ 애플리케이션 (비즈니스 워크로드)          │
├─────────────────────────────────────────┤
│ 개발자 플랫폼: Backstage(42)·Crossplane(41)│ ← 47에서
├─────────────────────────────────────────┤
│ 배포: ArgoCD/Flux(14·15) + Helm/Kustomize │
├─────────────────────────────────────────┤
│ 메시·트래픽: Istio/Linkerd/Cilium(24·25·22)│
│ 인그레스: Gateway API·인그레스 컨트롤러    │
├─────────────────────────────────────────┤
│ 보안: cert-manager(19)·SPIFFE(33)·        │
│       Kyverno(32)·Falco(30)               │
├─────────────────────────────────────────┤
│ 관측: Prometheus(11)·OTel(12)·Grafana·    │
│       Loki·Jaeger(13)                     │
├─────────────────────────────────────────┤
│ 시크릿: ESO/Vault(cicd 23) · 스토리지(CSI) │
├─────────────────────────────────────────┤
│ 클러스터: K8s + CNI(26)·CoreDNS(20)·       │
│           containerd(26)                  │
└─────────────────────────────────────────┘
```

각 층은 아래 층에 의존합니다. 이 **의존과 순서**가 이 모듈의 핵심입니다.

## 순서가 중요합니다 — 부트스트랩 의존

층을 아무 순서로나 깔 수 없습니다. 의존이 순서를 강제합니다:

```
예: cert-manager(19)는 많은 것의 전제
  cert-manager 없이 → 웹훅 TLS·인그레스 인증서·mTLS가 막힘
  → cert-manager를 먼저

예: 관측은 일찍
  Prometheus·OTel이 있어야 다른 층 도입 시 관측 가능
  → 관측을 초기에 (안 보이면 디버그 불가)

예: 메시는 앱보다 먼저(또는 함께)
  사이드카 주입(24)은 앱 배포 전에 메시가 준비돼야
  → 메시 인프라 → 앱

예: GitOps는 부트스트랩의 축
  ArgoCD/Flux가 나머지를 배포 (app-of-apps)
  → GitOps를 먼저 세우고 그 위에 층을 선언
```

이 순서를 틀리면 닭-달걀 문제(A가 B를 필요로 하는데 B가 A를 필요로 함)에 빠집니다 — theory·pitfalls에서 다룹니다.

## GitOps가 조립의 뼈대

레퍼런스 플랫폼의 조립 방식은 **GitOps**입니다(14·15):

```
app-of-apps 패턴:
  루트 Argo Application → 각 층을 Application으로 선언
    → cert-manager Application
    → prometheus Application
    → istio Application
    → ...
  → Git이 "플랫폼 전체의 진실의 원천"
  → 클러스터를 잃어도 Git에서 재구축 (재현 가능)
```

이것이 41(Crossplane)·42(Backstage)와 합쳐지면 47의 IDP가 됩니다. 이 모듈은 그 배포 뼈대를 세웁니다.

## 이 모듈의 철학 — 완벽한 스택은 없습니다

```
흔한 오해: "최고의 스택"이 있어서 그걸 깔면 됨
진실: 조직 성숙도·규모·팀 역량에 맞는 스택이 있을 뿐
  작은 팀: 관리형 최대 활용 + 최소 층
  큰 조직: 풀스택 + 플랫폼 팀
→ 층을 다 채울 필요 없습니다. 필요한 층만, 점진적으로.
```

그래서 이 모듈은 "이 스택을 깔아라"가 아니라 "층과 의존을 이해하고, 너의 조직에 맞게 골라 쌓아라"를 가르칩니다. 48(비교 가이드)이 각 층의 선택을 돕습니다.

## 실습 방식

kind에 축소판 플랫폼을 층별로 올려, 의존 순서와 통합을 체감합니다. 실제 프로덕션은 규모(노드·HA·저장)만 다를 뿐 구조는 같습니다 — 구조를 이해하면 규모는 확장의 문제입니다.
